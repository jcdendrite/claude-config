# pr-description — References

Edit-time reference for `SKILL.md`. Not loaded at runtime — read it manually
when changing a rule, to check whether the source still supports it.

## Primary source for the authoring standard

**Google Engineering Practices, "Writing good CL descriptions":**
`https://google.github.io/eng-practices/review/developer/cl-descriptions.html`

The skill body states each rule on its own rationale and does not name this
source. That is deliberate: `SKILL.md` files under `claude/.claude/skills/`
are stowed to every user of this repo, and a named organization's practice
cited inline as the reason a rule holds is a source-material anchor the
platform-genericness convention keeps out of a global skill body. The
attribution belongs here.

"CL" (changelist) is that source's term for what this repo calls a PR. The
rules transfer; the vocabulary does not, and the skill body uses PR
throughout.

### Quotes the rules rest on

**What and why** — the two questions the body must answer:

> A CL description is a public record of change, and it is important that it
> communicates: 1. **What** change is being made? 2. **Why** are these changes
> being made?

On *what*: *"This should summarize the major changes such that readers have a
sense of what is being changed without needing to read the entire CL."*

On *why*: *"What contexts did you have as an author when making this change?
Were there decisions you made that aren't reflected in the source code? etc."*

**First line stands alone:**

> That is, the first line should stand alone, allowing readers to skim through
> code history much faster.

**Generated descriptions get no exemption** — the clause that rules out a
`git log`-derived body:

> Some CLs are generated by tools. Whenever possible, their descriptions
> should also follow the advice here. That is, their first line should be
> short, focused, and stand alone, and the CL description body should include
> informative details that help reviewers and future code searchers understand
> each CL's effect.

The page's own list of first lines that carry too little information includes
*"Moving code from A to B"* and *"Phase 1"* — alongside *"Fix bug"*, *"Fix
build"*, *"Add patch"*, *"Add convenience functions"*, and *"kill weird
URLs"*. A bulleted list of commit subjects is a sequence of exactly these,
which is why the skill rules that shape out rather than merely discouraging
it.

**Sync mode rests on the same source:**

> CLs can undergo significant change during review. It can be worthwhile to
> review a CL description before submitting the CL, to ensure that the
> description still reflects what the CL does.

## Sources checked and set aside

**GitHub, "Creating a pull request":** carries no normative guidance on body
*content* — it instructs only to "Type a title and description for your pull
request." Useful for the mechanics of opening a PR, not for what belongs in
one.

**Conventional Commits (`https://www.conventionalcommits.org/`):** governs
commit-message *format*, not PR body content. This repo's PR title convention
is `<TICKET-ID>: <slug>`, derived from the branch name by `/ready-for-review`
step 6, so adopting a second title grammar would conflict with an existing
rule rather than fill a gap.

## Tool behavior the skill depends on

**`--body-file` exists on both subcommands.** `gh pr create --help` and
`gh pr edit --help` (gh 2.93.0) both list `-F, --body-file file`, and both
accept `-` for stdin. The skill uses the file form on both paths.

**Neither `--body` nor `--body-file` applies a repository pull request
template.** `.github/PULL_REQUEST_TEMPLATE.md` is applied by GitHub's web
compose view; supplying a body on the command line bypasses it entirely.
This is why the skill reads the template file itself rather than assuming
it will be merged in.

**`mktemp` needs no template argument** on GNU coreutils (*"If TEMPLATE is
not specified, use tmp.XXXXXXXXXX"*), FreeBSD, or macOS — the latter two both
document *"If no arguments are passed or if only the −d flag is passed mktemp
behaves as if −t tmp was supplied."* The skill still passes an explicit
template, for a filename that identifies itself to whoever meets it in `/tmp`
or in a halt message, not for portability.

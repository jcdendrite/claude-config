# Changelog

All notable changes to `claude-config` are documented here. Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Changed

- **This repo's own `.claude/settings.json` now excludes `claude/.claude/CLAUDE.md` from nested-CLAUDE.md discovery.** A session working in this repo, and every subagent it dispatches, previously loaded the global-instructions file twice: once at user scope through the `~/.claude/CLAUDE.md` stow symlink, and again as a fresh system-reminder block the first time anything under `claude/.claude/**` was read. The `claudeMdExcludes` pattern `**/claude/.claude/CLAUDE.md` covers both a main-checkout session and a worktree-anchored one. See `docs/design-decisions.md` §39.
- **`struggle`, `user-input`, and `friction-count` no longer score a forwarded `<task-notification>` envelope's text against `STRUGGLE_PHRASES`.** On this repo's own corpus (`user-input --projects '*claude-config*' --corrections-only`), "Explicit corrections" drops from 82 to 25. Two residuals are left standing on purpose:
  - A notification record still appears in `user-input --corrections-only` output as a `FOLLOWUP` entry, since that filter drops only `INITIAL`.
  - A friction checkpoint already in progress keeps whatever `struggle_turns` total it accumulated under the old rule until the checkpoint file self-evicts at 30 days.
- **`select-tests.py` no longer falls open to the full suite for `.claude/plans/`, `CHANGELOG.md`, or `docs/transcript-analysis.md` changes.** No test in the suite reads any of these by path or subprocess. A `docs/transcript-analysis-architecture.md` change now correctly selects just `claude/.claude/scripts/tests/` instead of the full suite, since two tests there pin its content by path.
- **`HANDOFF_NUDGE_ABS_CAP`'s default drops from 360000 to 150000 tokens.** Regrounded against cost per unit of delivered work rather than nudge-dismissal frequency: `transcript-analysis.py pr-cost --record` populated a 145-row per-PR ledger, and bucketing those rows by `mean_context_at_turn` shows both $/PR and $/1k output tokens rising monotonically past the 100–150k bucket (n=23) — the cheapest bucket with a trustworthy sample. 150000 is that bucket's upper edge. See `docs/handoff-nudge.md`'s "Why this cap" and `docs/cost-levers-considered.md` for the full measurement. **Migration:** a consumer who already exports `HANDOFF_NUDGE_ABS_CAP` explicitly never reaches this fallback default and is unaffected either way — not a bug, just worth noting so an existing override isn't mistaken for having silently adopted the new grounding.
- **Agent-initiated harness plan-mode entry is now blocked, and the session default model flips from `opusplan` to `sonnet`.** Harness plan mode forces every downstream subagent dispatch to Opus regardless of a `model:` pin — 489 of 500 measured plan-mode dispatches resolved to Opus, including all 70 that carried an explicit `model: sonnet` param, and the override is gated on `permissionMode`, not on any model setting (`docs/case-studies/plan-mode-model-resolution.md`). `claude/.claude/CLAUDE.md`'s Agent Briefing now tells the agent not to enter plan mode on its own initiative, and `permissions.deny` gains `"EnterPlanMode"` so the tool is unavailable even if the prose is ignored — the repo's first bare tool-name deny entry. Neither closes a human's own entry paths (`Shift+Tab`, `/plan` prefix, `defaultMode`). With agent-initiated planning routed off plan mode, `opusplan`'s Opus half is reachable only through a path the agent no longer takes, so the session default flips to `sonnet` to match — a coherence fix, not a fix for the escalation itself, and not a behavior change for a default session: outside plan mode `opusplan` and `sonnet` are identical, so nothing about an ordinary session's model changes. **Migration:** for Opus planning turns with Sonnet fan-out, start the session with `--model opus` and run `/plan-it` — a plan-mode session is no longer the path there. See `docs/auto-mode.md`'s plan-mode subsection and `docs/case-studies/plan-mode-model-resolution.md` for the measurement.
- **PR cost disclosure re-scoped from per-repo to per-Claude-account.** The opt-in sentinel moves from the repo-tracked, content-addressed `.claude/pr-cost-disclosure` (content had to equal the repo's own `owner/repo`, checked live against `gh repo view` at gate time) to `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/pr-cost-disclosure`, whose content selects a disclosure mode instead of proving a repo identity: exactly `dollars` enables the `## Cost` section, anything else — absent, empty, unrecognized — disables it (fail-closed). Cost is an organizational fact tracked per Claude account, not per repository, and the old scope forced the same opt-in decision to be re-entered once per repo while requiring a committed config artifact that a linked worktree — the tree PRs are authored from under this repo's worktree enforcement — never checks out. The repo-tracked `.claude/pr-cost-disclosure` file is deleted; `install.sh`'s `repo-content-addressed` inventory row is replaced by an `account` row that reports the resolved path and mode. **Migration:** disclosure is off until re-enabled at the new location: `echo dollars > "${CLAUDE_CONFIG_DIR:-$HOME/.claude}/pr-cost-disclosure"`.
- **New global instruction: "Locate before a whole-file read," plus a `read-scope` subcommand that measures whether it is followed.** Stow consumers get the new `CLAUDE.md` bullet on `git pull` with no re-install, so it is called out here: when you don't already know which part of a file you need, `Grep` returns matching line numbers and `wc -l` bounds the file, and you read that range plus a margin. It is deliberately scoped to a file you have *already decided to read* — codebase discovery still routes through `subagent-delegation`'s dispatch mandate rather than an inline sweep. The line covers only the complement of what Claude Code's built-in `Read` description already says ("when you already know which part of the file you need, only read that part"), which is why it is one line and not a section. `transcript-analysis.py read-scope` reports the `Read`-call census split into targeted (`offset`/`limit`) and whole-file cohorts by main-thread vs subagent scope, a result-size histogram with per-bucket token sums, repeat whole-file reads, locate-step cost, and `Read`-result tokens as a share of prompt-token growth — a denominator computed per source file and per `sessionId`, reset at each compaction boundary, which no other subcommand had. Percentages divide by the full call census, so reads whose scope is unknowable (129 in the measured corpus, carrying an `__unparsedToolInput` payload with no `file_path`) stay visible rather than being filed under whole-file. Measured before adopting: **45.6% of 22,687 `Read` calls already carried `offset`/`limit`**, so the premise that whole-file reads dominate holds only on token mass (76.8%), not on call count — which is why the source proposal's `PostToolUse` hook and its "re-read narrowly after an edit" clause were both declined, the latter on a measured 0.49% of prompt-token growth. Shared-code impact: `_read_session_file` is now a flattening wrapper over a new `_read_session_file_partitioned`, and `_price_turn`'s context sum is extracted as `_context_at_turn` — both behaviour-preserving and pinned by tests. See [`docs/case-studies/targeted-read-discipline.md`](docs/case-studies/targeted-read-discipline.md) for the full measurement, its honest limits, and the numeric revisit triggers.
- **`cleanup-merged-branches.sh` now queries every repo — including a plain single-repo run, not only `--all-projects` — with that repo's own `gh` credentials, and aggregates skip lines by reason.** On a machine where per-directory tooling (direnv) supplies a different `GH_TOKEN`/`GH_HOST` per top-level container, the script previously queried every repo with the invoking shell's credentials — direnv's shell hook is installed into `PROMPT_COMMAND`, which a script's own `cd` never fires — so under `--all-projects`, `gh pr list` failed and `classify_branch` failed closed for every repo outside that container, reported as a wall of `gh lookup failed; skipping to fail closed` lines with no indication credentials were the cause. New `load_repo_environment()`, called unconditionally from `run_repo_cleanup` right after `REPO_ROOT` resolves, evals `direnv export bash </dev/null` (stdin redirected so a stdin-reading `.envrc` can't hang the sweep; direnv's stdout, which carries secret values verbatim, is never printed) when `direnv` is installed — a no-op otherwise, so absent-direnv behavior (most stow consumers) is unchanged. `DRY_RUN` and `ALL_PROJECTS` are made `readonly` right after arg parsing so an `.envrc` clobber aborts loudly under `set -e` rather than silently flipping `--dry-run`; the same applies to three git-identity values captured right after `REPO_ROOT` resolves (`--show-toplevel`, `--absolute-git-dir`, `--path-format=absolute --git-common-dir`), re-checked immediately after the eval and aborting that repo with a purpose-built message if an `.envrc` repointed `GIT_DIR`/`GIT_WORK_TREE`/`GIT_COMMON_DIR` at another repository — `refs/heads/*` (what `git branch -D` mutates) is a non-worktree file that `git` takes from `GIT_COMMON_DIR` when set, independent of `GIT_DIR`/`GIT_WORK_TREE`, so all three needed their own check. `print_skip_reason_lines` now groups by identical reason text instead of printing one line per branch, so a repo where every branch shares one `gh` failure reports it once with a count and the branch names; distinct-PR-number skips (open PR, stale name) keep their own line since their text differs per branch. Under `--all-projects`, `gh auth status` failing for the invoking shell is downgraded from a hard exit to a warning, but only when `direnv` is present — without it, the invoking shell's auth state is what every repo actually gets, so the hard exit is unchanged. See [`docs/scripts.md`](docs/scripts.md).
- **`require-respond-pr.sh` gates comment-write shapes it previously let through.** Newly denied: `gh issue comment` and its `--edit-last` / `--delete-last` forms, which post and rewrite through the same `issues/{n}/comments` endpoint `gh pr comment` uses and formerly missed the gate entirely; lowercase and mixed-case `-X delete` / `--method patch`, which `gh` normalizes before sending, so they executed as real writes while reading to the gate as a GET; `gh api graphql` comment mutations, including multi-line and file-sourced bodies; a REST URL wrapped across lines with a backslash continuation, now matched the way the shell would join it; and `gh pr`/`gh issue` writes with `-R`/`--repo` anywhere ahead of the verb rather than after it — `gh pr --repo o/r comment N`, `gh --repo o/r pr comment N`, and the glued `gh pr -Ro/r comment N` all dispatch the same write and all previously fell through every arm, including for the current repo. The `pr`/`issue` arms now tolerate that flag and its value in either position and in all three spellings, and nothing wider: `gh pr list --search comment` and `gh pr -R review view 5` both stay allowed. Cross-repo *writes* now deny for every repo — reads are unaffected — and the write denial no longer directs you to `/respond-pr` for a PR that skill cannot service. **If you drive any of these shapes from a script or a session hook, expect a deny where you previously got through**: route the write through `/respond-pr`, or run it outside a hooked session. Match arms moved to POSIX `[[:space:]]` and bash `[[ =~ ]]`, so the gate no longer depends on GNU-only regex classes that a BSD/macOS `grep` could silently fail to honour.
- **Code-review marker directory renamed to `~/.claude/code-review-markers/`** — it was the only one of the four review gates whose directory did not derive from its skill name (`plan-review` → `plan-review-markers/`, `skill-review` → `skill-review-markers/`, `ready-for-review` → `ready-for-review-markers/`, but `code-review` → `review-markers/`). Sessions debugging a blocked commit inferred `code-review-markers/`, found nothing, and read the absent directory as a failed marker write. `TestMarkerDirectoryNamingConvention` now runs each of the four `write` skills and asserts the marker lands in `<skill>-markers/` and nowhere else, pinning the convention on the write side; `TestMarkerWriteSatisfiesTheGate` adds the first end-to-end round trip (`marker.sh write code-review` → real `require-code-review.sh` → allow), so write and read side are proven consistent by execution rather than by matching literals in two files. The four read-side hooks still hard-code their marker paths independently, so the same asymmetry could still be introduced there. `/code-review`'s body also names the marker path outright and states that the command chains only to `git commit`. **Migration:** none required — markers are per-session and ephemeral, so the gate simply re-arms once and the next `/code-review` writes to the new path. Delete a leftover `~/.claude/review-markers/` at leisure.
- **Citation placement normalized across skills** — `SKILL.md` bodies carry the rule and the rationale that lets it generalize; canonical URLs and verbatim source quotes live in a co-located `REFERENCES.md`, which is never loaded at skill runtime. Four skills moved their citations (`ai-instruction-and-memory-files`, `branch-creation`, `claude-hook-review`, `npm-semver`), and `test_skill_bodies_carry_no_citation_urls` now asserts the split so it cannot silently regress. Plugin bumps: `claude-hook-review` 2.0.1, `npm-semver` 1.0.2 — both patch, provenance storage only, no rule change, so pinning consumers need not re-pin.
- **Four macOS-only bugs closed across `require-memory-skill.sh`, `require-plan-review.sh`, `enforce-marker-script-shape.sh`, `require-ready-for-review.sh`, `require-plugin-version-bump.sh`, and `cleanup-merged-branches.sh`/`cleanup-idle-open-pr-worktrees.sh`'s shared `_worktree-lib.sh`.** All four silently degraded a security-relevant check into an unconditional allow, or a live worktree into a false "idle," rather than erroring loudly — confirmed absent from CI (which runs `ubuntu-24.04`) and reproduced only under stock macOS tooling. (1) `realpath -m`, used for lexical path-boundary checks, is GNU-only; BSD/macOS `realpath` rejects `-m` outright, and none of the three call sites checked its exit status, so `REAL_REPO`/`REAL_PATH` silently went empty and every boundary check became a no-op. New `_lib_realpath_m` in `_lib.sh` prefers native `-m` support, falls back to `grealpath` (Homebrew coreutils), and finally to resolving the nearest existing ancestor via plain `realpath` and reattaching the not-yet-existing suffix — no external dependency required. (2) `sed -E`'s `\s` is a GNU extension that BSD/macOS `sed` doesn't support in `-E` mode and fails to match rather than erroring; `require-ready-for-review.sh`'s `--tags`-push branch-detection always saw an empty capture on macOS, silently bypassing the gate for every `git push --tags` that also pushed a branch ref. Switched to POSIX `[[:space:]]`. (3) `require-plugin-version-bump.sh` iterated `"${PLUGIN_ROOTS[@]}"` while the array could still be empty — bash <4.4 (including macOS's frozen system bash 3.2) treats that as an unbound-variable error under `set -u` rather than zero iterations, crashing the hook outright (silent-allow, since a crashed `PreToolUse` hook emits no deny). Guarded with the same `${#ARR[@]} -gt 0` pattern `npm-semver`'s sibling hook already established. (4) `collect_process_cwds` excluded only its own PID (`$$`) from the `lsof`-based live-process scan, but `lsof` itself is a running process at scan time and inherits the caller's cwd — its self-report, under a different PID, made every worktree the scanning shell was itself sitting in read as "in use." Runs `lsof` in the background now specifically so its PID (`$!`) can be excluded alongside `$$`. On Linux, `lsof` additionally forks a short-lived helper that inherits and reports the same cwd before exiting — invisible to CI (`ubuntu-24.04` always has `/proc`, so this branch never runs there in production) but caught by a synthetic test that forces the branch; a `kill -0` check scoped to entries matching the scanning shell's own cwd drops the exited helper without risking a false negative against another user's live process elsewhere. Also fixed: `require-skill-review.sh`'s structural-validator Python fallback assumed system `python3` has `pyyaml` installed; it doesn't on a properly venv-isolated contributor machine. Added a second-choice fallback to this repo's own contributor `.venv` (located via `git rev-parse --git-common-dir` from the hook's own on-disk path, not the target repo's — the two differ in the plugin's own cross-repo test fixtures). Plugin bumps: `plugin-semver` 1.1.4, `skill-management` 3.0.3 — both patch, bug fixes only, no behavior change for anyone the bug didn't already affect.
- **`plan-review/ROUTING.md` now carries the same length cap and review-marker gate as `SKILL.md`.** `check-skill-length.sh`'s 500-line structural-dispatcher cap and `require-skill-review.sh`'s marker-gate scope both widen to the single hardcoded exception `claude/.claude/skills/plan-review/ROUTING.md` — previously a `ROUTING.md`-only commit had no length ceiling and rode along on whatever `SKILL.md` marker happened to be on disk (or on none) instead of being independently audited (GH-504). `marker.sh write skill-review`'s pathspecs widen in lockstep so the write and read side stay in agreement. Plugin bumped: `skill-management` 3.1.0 (trigger broadened to fire in strictly more cases — minor, not breaking). **Contributors who pull this change before updating their installed `skill-management` plugin** may see a transient false-deny on a commit that mixes `SKILL.md` and `ROUTING.md` changes — the stowed `marker.sh` writes a three-pathspec marker immediately on pull, while the plugin-shipped `require-skill-review.sh` still reads two pathspecs until the plugin is updated, so the hashes no longer match and the commit denies. A `ROUTING.md`-only commit in that same window is unaffected either way: the not-yet-updated hook's early-exit still checks only for staged `SKILL.md` files, so it exits without gating — identical to the pre-this-change behavior, not a new gap. Both cases self-resolve on `claude plugin install skill-management@claude-config --scope project`.
- **`deny-credential-bash-reads.sh` exempts a `.env`-shaped argument to a documented env-file loader flag.** `--env-file`/`--env-file=` (Deno, Docker/podman/docker compose), `--env-file-if-exists=` (Node), and `--envfile` (pytest-dotenv) load the named file into a subprocess environment rather than printing it, so a command like `deno test --env-file=<repo>/tests/.env <repo>/tests/unit/` no longer denies solely on that flag's argument — closing a false positive that removed autonomous test-run/iterate loops for any project using this pattern. The scan still runs unchanged first; only on a match does the hook strip the flag-and-argument span (case-sensitive flag match, argument basename required to be `.env`-shaped, argument run required to terminate at whitespace or a shell metacharacter rather than swallow a following credential token) and re-scan, so a strip failure or a non-`.env` argument in flag position both still deny. New `_lib_strip_env_file_flag_args` in `_lib.sh`; the `.ssh` deny-by-default check and the personal `credential-file-guard.md` glob loop are unaffected, since both keep reading the un-stripped command text. No-verb-allowlist stance is otherwise unchanged. See [`docs/security-hardening.md`](docs/security-hardening.md) for the two accepted residuals (a load-then-print invocation, and the flag as inert argv padding to a command that doesn't actually parse it).
- **`/plan-it` Step 5 now dispatches a pinned-`model: opus` `plan-architect` agent for architecture-design synthesis, instead of requiring a whole-session `--model opus` anchor.** **Supersedes** the Migration line on the `opusplan`→`sonnet` entry above: a whole-session `--model opus` is no longer the way to get an Opus-authored plan. See `docs/design-decisions.md` §30 for the mechanism and rationale.
- **`/handoff` gains a fifth active-bypass marker, closing a mid-write hard-block truncation.** `nudge-handoff-near-context-cap.sh`'s escalation ladder could re-fire its hard block during `/handoff`'s own multi-turn write — notably the "collect in-flight background dispatches" wait — because the ladder's only reset runs at the very end of that process. `/handoff` now writes a `handoff` active-bypass marker (`marker.sh activate handoff`, mirroring the existing `plan-review`/`ready-for-review`/`respond-pr`/`memory-skill` family) once a handoff is confirmed warranted. It removes the marker (`marker.sh deactivate handoff`) after recording the conversion signal; while live, a qualifying re-arm stays advisory instead of hard-blocking. The escalation count itself is unaffected — the marker suppresses the block, it does not reset the count. `permissions.allow` gains two new exact-match entries, `"Bash(~/.claude/scripts/marker.sh activate handoff)"` and `"Bash(~/.claude/scripts/marker.sh deactivate handoff)"`. **Migration:** none required — the marker is created and removed by the skill itself.
- **`disableArtifact` and `disableWorkflows` now default to `true` in the shared `settings.json`.** The built-in `Artifact` and `Workflow` tools are the two largest eagerly-loaded tool schemas in every session's system prompt, an unconditional per-session cost paid whether or not a session ever calls either tool. A pre-committed `/context` before/after measurement gated the flip and closed the schema-strip question `docs/design-decisions.md` §28 had left open. See `docs/design-decisions.md` §31 for the measurement, the full reasoning, and the residual risk this mechanism carries. **Migration:** the setting is live on `git pull` with no reinstall — both tools are off for every session starting from the next `claude` launch. The `claude-workflow`/`claude-artifact` wrapper commands (see Added, below) need `./install.sh` to materialize, since a new `claude/.local/bin/*` entry is stowed only by the installer, not by `git pull` alone; until then, `claude --settings '{"disableWorkflows": false}'` (or `disableArtifact`) re-enables a tool for one session with no reinstall required. To flip the default itself rather than opting back in per session, set `disableWorkflows: false` (or `disableArtifact: false`) in a repository's own `.claude/settings.json` or `.claude/settings.local.json` — both outrank the shared User-scope default.
- **`plan-architect` now serves two dispatch modes, selected by a `MODE=` first line on the dispatch prompt.** `MODE=plan-sections` is the existing `/plan-it` Step 5 grammar, unchanged; `MODE=consult` is a new ad hoc mode for outside/Opus-level architectural judgment on a design decision, and it fires only on the user's explicit ask, never on the session's own initiative. `general-purpose` + `model: opus` is no longer the pattern for a mid-session Opus consult — `plan-architect` is already read-only and Opus-pinned, so routing there drops unneeded `Write`/`Bash`/`Skill` and stops restating the charter per dispatch. Live on `git pull` with no re-install, like every other change under `claude/.claude/**`. See `docs/design-decisions.md` §37.
- **`transcript-narrative` and `error-mode-analysis` now run as forked skills (`context: fork`, `background: false`) and return a file path plus a short summary instead of the full report inline.** Both bodies previously read raw transcript JSONL and full PR-comment GraphQL payloads directly into the invoking conversation — the largest working-set costs in the skill corpus — where they were re-read on every subsequent turn. Each skill now writes its artifact to the caller-supplied path (or output directory), or to a `mktemp -d`-rooted location when none is given, and states plainly that the default location is temporary. The return is a path plus a short, skill-defined summary only: `transcript-narrative` returns its output path plus the ranked lessons; `error-mode-analysis` returns both artifact paths plus the Step 4 bucket table. **This is a one-way behavior change with no opt-out:** a follow-up question that needs the full report now re-opens the file at the returned path instead of reading it inline for free. Requires Claude Code v2.1.218 or later for `background: false` to take effect; each skill's first step stops and names that requirement when `Bash` is unavailable. See `docs/skills.md`'s Skill architecture notes section for the selection criterion — working set, not body size — that keeps this roster at exactly these two skills.
- **`ready-for-review` and `handoff` now tell the model explicitly that `pr-description`'s ending is not the caller's own stopping point.** An agent occasionally ended its turn right after `pr-description` reported back mid-`ready-for-review` (step 5) or mid-`handoff` (the pre-write checklist), instead of continuing into the orchestrator's next step, leaving the PR uncreated or the handoff file unwritten. `pr-description`'s own deliverable format is unchanged — its single-line `BODY_FILE: <path>` report and its `gh pr edit --body-file` application remain the contract every consumer reads, including the standalone invocation where ending the turn there is correct. No hook was added; this is a prose-only fix. Live on `git pull` with no re-install.

- **`ai-instruction-and-memory-files/SKILL.md`'s CLAUDE.md/AGENTS.md authoring mechanics (the `@AGENTS.md` import pattern, `@path` resolution, precedence, and when to add an AGENTS.md) moved to a new stowed path-scoped rule, `claude/.claude/rules/claude-md-conventions.md`.** The rule auto-loads whenever a CLAUDE.md, AGENTS.md, or CLAUDE.local.md is read, in any repo, rather than only when the skill is explicitly dispatched. The skill keeps the length cap, the per-line behavior test, the compression-diff audit, duplicate-vs-reference judgment, and auto-memory — and retires its 215-line cap override back to the 200 default, since the override's rationale (gate-loaded routing content with no narrower surface to move to) no longer holds once the CLAUDE.md half has one. **Migration:** live on `git pull` with no reinstall, since `claude/.claude/**` is stowed. Authoring a brand-new CLAUDE.md in a repo with no AGENTS.md may not surface this guidance, because path-scoped rules load on file read.
- **Drops the five bare-basename `paths:` entries (`CLAUDE.md`, `AGENTS.md`, `CLAUDE.local.md`, `.claude/CLAUDE.md`, `.claude/AGENTS.md`), keeping only the five `**/`-led ones.** Which files trigger the rule is unchanged. Zero-segment `**/` matching (whether `**/CLAUDE.md` fires on a repo-root file) is now settled by measurement in both `-p` (non-interactive) and interactive sessions. Every stowed rule's `paths:` glob must now be `**/`-led, with no leading literal path segment. A bare filename or a `.claude/`-anchored literal no longer validates. Live on `git pull` with no re-install. See [`docs/case-studies/claude-md-glob-zero-segment.md`](docs/case-studies/claude-md-glob-zero-segment.md) for the full trial record.

### Removed

- **Retired `check-runner` agent.** Transcript-corpus measurement (649 sessions, 784 dispatches) showed neither the context-cost nor verdict-ergonomics justification holds. Parent runs checks inline. Removes the agent, `check-runner-bash-guard.sh` hook, and dispatch-id contract. See `docs/case-studies/check-runner.md#retirement`.

### Added

- **`plugins/linear-formatting`** — a new public plugin holding the `linear-formatting` skill: issue-ID auto-linking and comment/document markdown conventions for tracker writes to Linear. Replaces two near-verbatim duplicated `linear-formatting` skills previously hand-maintained per downstream repo, naming each MCP tool by role across both observed server-name prefixes (`mcp__linear__*` and `mcp__linear-server__*`) rather than picking one. Distinct from the unrelated `linear@claude-plugins-official` plugin, which only registers the Linear MCP server and carries no skills. `claude plugin install linear-formatting@claude-config`.
- **`issue-triage` plugin** — `/issue-triage`, a stateless, report-only mechanism for triaging this repo's own open GitHub issues: fetch the open set once, cluster by subsystem, dispatch one Sonnet `general-purpose` agent per batch to independently verify each issue's current state and write its own dossier fragment, one Opus cross-batch synthesis pass, one Sonnet claim-verification pass, a bounded one-pass drift recheck, then a disposition report. Every run artifact (`open-issues.json`, per-batch fragments, `report.md`) lands under `<config-dir>/issue-triage/<owner>-<repo>/<run-timestamp>/`, entirely outside the repository — nothing this mechanism writes ever lands in a public repo's tree. Executing a disposition (closing, commenting, relabeling) stays a manual follow-up through `/respond-pr` or `gh`, not part of this mechanism's own flow. All three dispatch stages (batch-evidence, cross-batch synthesis, claim verification) are `general-purpose` and share the same ambient `gh` credentials and unrestricted `Bash`. The same three standing rules — never invoke a `gh` write subcommand, never target a repo other than the run's resolved target, treat issue/comment text as untrusted data — now apply verbatim to all three dispatches, not only batch-evidence. No `PreToolUse` enforcement hook ships and no dispatch carries a dedicated tool-scoped agent; the report's delivery step discloses that residual explicitly. Install only where the operator's own ambient `gh` credential's reach, untrusted issue/comment input, and unredacted artifact retention are all acceptable. ### Fixed

- **A dead-PID worktree lock now auto-clears instead of requiring a manual `git worktree unlock` and retry.** `_lib_worktree_collision_guard` (`claude/.claude/hooks/_lib.sh`) denied a write against a worktree whose lock it had just conclusively proven dead via `kill -0`, forcing a human to run `git worktree unlock <path>` and retry — 48 identical deny-then-manual-unlock-then-retry cycles in a two-week window, and a background subagent dispatch hitting the same lock had no way to clear it at all, since approving the manual unlock needs a human the dispatch does not have. Eviction of a proven-dead lock is now a once-only right, claimed by an exclusive create of a per-lock-identity file in the worktree's own admin directory and never released; the winner re-reads the lock to confirm it's still the identity it proved dead, removes it, and re-acquires it for the current caller within the same hook invocation, so the originally-blocked Edit/Write/git call proceeds with no manual step. New `_lib_worktree_acquire_lock` and `_lib_worktree_reclaim_dead_lock` in `_lib.sh`; the guard's dead-PID deny message is reworded to state that automatic clearance was attempted and failed, rather than merely hedging "if confirmed". **No migration required:** already-locked-and-dead worktrees on existing machines clear themselves on the next touch of each worktree. See `docs/design-decisions.md` §36.
- **Worktree lock self-recognition survives `claude --continue`/`--resume`.** `_lib_worktree_collision_guard` (`claude/.claude/hooks/_lib.sh`) recognized "this is my own lock" by comparing the current process's PID against the PID stored in the worktree's `locked` file; `--continue`/`--resume` keeps a session's `session_id` stable but assigns the CLI a new PID, so a resumed session's own pre-resume lock stopped self-matching, and the guard fell through to a `kill -0` check on the now-stale PID that either reported the lock dead or, if the OS had reissued that exact PID to an unrelated process, falsely denied the worktree as already in use. Self-recognition now compares `session_id`, stored in the lock's reason string (`claude-code pid <N> session <ID>`) at acquisition time, falling back to today's PID comparison for an old-format lock carrying no `session_id` field — no migration needed, an already-on-disk lock keeps its current behavior until naturally released. See `docs/design-decisions.md` §29.
- **`deny-network-installs.sh` no longer denies a bare restore with output-capture redirection glued to it.** `_lib_split_fragments` never splits on `>`/`<`, so `2>&1`, `> out.log`, or `&>/dev/null` attached to a bare `pnpm install`/`npm install`/`yarn install` reached `_install_has_leftover_token`'s per-word scan as an unrecognized word and denied exactly like a real package name — surfaced by `pnpm install 2>&1 | tail -30`, an ordinary way to capture output. The scan now recognizes shell redirection syntax (fd duplication/close, a bare operator, or an operator glued to its target) via three start-anchored regex branches, reusing the existing flag-value skip mechanism; a real leftover token abutting an operator with no space (`evil-package>out.log`) still denies. Opens one narrow, inert residual in the opposite direction: a quoted argument that becomes redirect-shaped after this hook's pre-existing quote-stripping (`npm install ">pkg"`) now allows instead of denying, which has no exploit value since neither npm's nor PyPI's package-name grammar permits a literal `>`/`<` character — both this and the pre-existing heredoc/here-string gap are documented in the hook's own header.
- **`cleanup-merged-branches.sh` restores per-branch Tier B prompting** — a branch reachable from `origin/<default>` with no merged PR now prompts `[y/N]` on a TTY and skips with a warning on non-TTY stdin, rather than auto-deleting; the open-PR guard only protects branches that already have a PR, so a branch with active, uncommitted-to-a-PR work could otherwise be auto-deleted along with its worktree. `--yes` stays removed.
- **Chained `marker.sh write && git commit` no longer denied** — three coordinated changes: `enforce-marker-script-shape.sh` accepts a chain of one or more `marker.sh write <skill>` invocations followed by `git commit`; `require-code-review.sh` and `require-skill-review.sh` (plugin bumped to 2.2.0) honor an in-chain marker write that precedes the commit. PreToolUse fires once per Bash tool call before the chain runs, so an on-disk marker check would otherwise deny these naturally-typed forms even though the chain would create the marker. Chains to non-commit tails (curl, rm, semicolon-arbitrary) stay denied, and the structural validator still fires when chained, so malformed SKILL.md files can't slip through.

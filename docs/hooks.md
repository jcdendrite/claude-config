# Hook reference

Full descriptions for every hook in `claude/.claude/hooks/`. For the gate summary (which hook blocks which command), see the Hook → Gates → Cleared-by table in the [README](../README.md#workflow). The "Threat-model tiers" table below is the one exception to that main-dir scope: it also covers the 4 plugin gates under `plugins/*/hooks/`.

## Threat-model tiers

This framework covers `hook-class: gate` hooks only. A non-gate hook that stands in a backstop relationship to a gate — e.g. `redact-credential-values.sh`, which its own header calls the value-shape backstop for content `deny-credential-bash-reads.sh`/`deny-credential-file-reads.sh` don't cover — is outside the framework even in that relationship; an absent tier line on it waives nothing and claims nothing.

Three independent axes: (1) agent intent, assumed cooperative — the only thing this framework governs; (2) input trust, never assumed; (3) consequence reversibility, independent of (1). The framework never infers input trust from agent cooperation. Axis (2), `untrusted-input`, is a disposition label: it decides which findings a review may waive on cooperative-agent grounds, not a claim that any gate's matching logic is proven to resist steered input. Adversarial robustness against a determined attacker is out of scope for a text-matching hook and lives, if anywhere, in capability removal or a git-native pre-commit/pre-receive layer, not text matching (see `docs/security-hardening.md`).

**Tier definitions.** A tier applies to a hook by its worst member: a hook whose denied set mixes reversible and irreversible outcomes takes the elevated tier (already how `require-worktree-for-git-writes.sh`, `block-gh-pr-merge.sh`, and `deny-pii-in-commits.sh` are tiered).

- `cooperative` — this gate guards a cooperative agent's honest mistakes. A review finding that requires a command or staged-content shape a cooperative agent would never emit is not a defect in this gate, unless the gate also lists `untrusted-input`. Over-deny on ordinary shapes a cooperative agent does emit stays in scope for every tier.
- `untrusted-input` — a positive test, not a negative one: this gate's header, or its `docs/hooks.md`/`docs/security-hardening.md` entry, states that steered input (prompt injection, adversarial content read from outside the session) is part of what the gate defends against; or another `untrusted-input` gate names this gate as its own backstop against deliberate evasion (the dependency invariant, below). A finding needing a shape a cooperative agent would not emit is live only when the change under review introduces or widens that gap; a pre-existing gap of that shape is accepted debt, recorded on the gate's header or the tracking issue it points to, and is not, by itself, a blocking finding (the regression-only rule, below).
- `irreversible` — bypassing this gate produces an outcome the session cannot retract: published or pushed content, a secret in model context, this session's or another session's uncommitted work destroyed. Over-deny is the correct trade; a false-positive-cost argument alone does not justify relaxing it. A commit-boundary gate is `irreversible` only when the gated content is secret, PII, or private-identifying (i.e. its bypass is publication), not merely because a commit occurred. This tier governs relaxations only; it does not by itself suspend the cooperative waiver for gap findings.
- Precedence rationale: reversibility calibrates deny-versus-allow; intent decides which shapes a gate must catch. Letting `irreversible` suspend the waiver would collapse the intent axis into the reversibility axis and make every gap finding on an elevated hook un-waivable.

**Classification rule.** A hook's own stated threat-model text decides; a posture or false-positive-cost citation does not by itself elevate. Applied in both directions, so the table below is a summary of headers rather than a second opinion. Silence in both the header and the docs entry means no `untrusted-input`; an elevated row's Why cell quotes the single-line source sentence it rests on. Where the tier line and existing prose disagree, resolve it by the positive test above: if the header or docs entry states a steered-input threat but the tier is plain, add `untrusted-input`; if the tier carries `untrusted-input` but the prose is silent and no `untrusted-input` gate names this gate as its backstop, drop that elevation only with the relaxation rationale. A gate elevated through the dependency invariant keeps its elevation even though its own prose is silent.

**Existing debt** is a closed set: a gap enumerated in a gate's own header or in `docs/security-hardening.md`, or named on a tracking issue a header points to, as of the commit that introduces the tier headers. A gap discovered later is a live finding until it, too, is recorded this way.

**The dependency invariant.** If gate X's header names gate Y as X's backstop against evasion, Y carries every elevation X carries. This is a non-relaxation rule, not "every shared function inherits the highest tier of its callers": shared `_lib.sh` code is never changed so that it accepts a shape an `untrusted-input` caller denies today, but a residual gap already present in shared code stays accepted debt and is not, by itself, a licence to demand its closure just because one caller is elevated.

**The symmetric add-side relaxation rule.** Adding `untrusted-input` or `irreversible` to a previously-unelevated gate, backed by header or docs prose introduced in the same change, is a security-classification change exactly like removing one — the commit message or PR body states the rationale either way. This is what keeps the classification mechanism from becoming a lever in either direction.

**The regression-only rule.** A gap a gate's header names, or a tracking issue its header points to, is accepted existing debt — the tier neither licenses it nor reopens it for debate. A change to that gate is reviewed for regressions only: an input the gate denied at the merge-base that it allows after the change, or a new fail-open path the change introduces. A regression is always ADDRESS or stop-and-ask, never deferred. A pre-existing gap a review happens to surface is recorded on the gate's tracking issue, not raised as a blocking finding. Adding a tracking-issue pointer to an elevated gate that had none is itself a scope-narrowing change and takes the same relaxation treatment as any other classification change (above; its commit message states the rationale). Wording is "route the finding, don't raise it as blocking" — never "don't look": "regression" means a behavioral delta against the merge-base, never against the header's own conceded-gaps list, so a diff cannot open a new bypass and legalize it by listing it in the same commit. No `CLAUDE.md` or SKILL.md edit carries this rule; this section is its only home.

**What a waiver accepts, and how it is recorded.** A waived finding against a plain-`cooperative` or `cooperative, irreversible` gate is accepted risk, not covered risk. Treat the waived shape as able to reach the public remote. None of the controls this repo ships inspects, before publication, the content the gate missed:

- The harness ask-prompt, where one fires, shows a human the command, not the diff.
- PR review gates merge, not the push that publishes a branch.
- `require-ready-for-review.sh` checks a review marker, never content, and allows the pushes its own header lists.
- A git-native pre-commit or pre-receive hook would inspect content. This repo does not ship one (see `docs/security-hardening.md`).

A waived finding is recorded on the gate's header or tracking issue in the same change; a PR-body line links any issue comment recording it.

`irreversible` is a term of art scoped to this table, distinct from `CLAUDE.md`'s global confirm-before-destructive-action rule: it governs which findings a review may relax on false-positive-cost grounds, not which actions this session pauses to confirm. It covers the dispatching session's own uncommitted tree, not only another session's.

Repairing a mis-parse — a gate that misreads an ordinary shape it should allow, or misses a shape a cooperative agent does emit — stays in scope for every tier (a gap already in the closed existing-debt set is still governed by the regression-only rule); only a deliberate admission of a shape carrying the gate's denied semantics is what `irreversible` blocks from being waived.

**Header grammar.** The tier line lives at line 3 of the hook file, spelled `# tier-threat-model: <tiers>`, intent tier first, elevations in canonical order (`untrusted-input` before `irreversible`), comma-space separated. Legal forms: `cooperative`; `cooperative, untrusted-input`; `cooperative, irreversible`; `cooperative, untrusted-input, irreversible`.

The header line is the source of truth for a hook's tier; the table below is the rationale record. The tests enforce agreement between the header and the table, not agreement with the hook's actual behavior — a stale tier that both surfaces still agree on passes.

A tier lacking `untrusted-input` — plain `cooperative` and `cooperative, irreversible` alike, not only plain `cooperative` — must not be cited as evidence of an enforced security control against steered input; only `untrusted-input` carries that claim.

**Deliberate scope: commit-boundary disclosure gates.** `deny-pii-in-commits.sh`, `deny-private-project-refs.sh`, and `deny-invisible-commit-content.sh` stay `cooperative, irreversible` by deliberate choice, not by oversight. Under the classification rule above, none of their headers states a steered-input threat, and that silence is intended. A finding against one of them that needs a shape a cooperative agent would never emit — a reworded name, an obfuscated commit invocation — may be waived on cooperative-agent grounds. The residual risk of steered-content disclosure through these gates is accepted risk (see the waiver paragraph above), not something their matching logic covers. A routine encoding a cooperative agent emits, such as a base64 credential in a Kubernetes Secret manifest, is not a waivable shape: such a finding is fixed in the change, or recorded in the gate's header Known-gaps section with the rationale stated in the commit message. Each gate's own header Known-gaps section is its existing-debt closed set and the place a waived finding against it is recorded. No tracking issue is opened for this class.

## Gate hooks

- **`require-plan-review.sh`** — blocks `Write`/`Edit`/`MultiEdit`/`ExitPlanMode` when an uncommitted or modified plan file exists in `.claude/plans/` and no `/plan-review` marker holds the current plan set's hash. Committed, unmodified plan files are treated as historical and pass through. Two-marker pattern: an active marker (`<config-dir>/.plan-review-active.d/<session_id>`) bypasses the gate for the skill's own Write/Edit calls during review (but not `ExitPlanMode`, which stays blocked until review is complete); a completion marker (`<config-dir>/plan-review-markers/<repo-hash>.<session_id>`) allows through once the review is clean. The completion read is two-tier: it scans this worktree's repo-hash prefix first, then — only on a miss — the repo's sibling worktrees, so a plan copied into a fresh worktree inherits the review that already covers its text. `<config-dir>` means `$CLAUDE_CONFIG_DIR` when set, else `~/.claude`. See [Marker keying and gate-release authority](#marker-keying-and-gate-release-authority) and [Gate deadlock recovery](#gate-deadlock-recovery).
- **`deny-invisible-commit-content.sh`** — always on, no arming file, no `if`-condition. Denies a Bash `git commit` whose actually-committed content cannot be described by the `git diff --cached` snapshot every other commit gate reads at PreToolUse time, closing a time-of-check-to-time-of-use gap: a chained `git add <files> && git commit`, or a second `git commit` later in the same chain, leaves `--cached` empty (or already reviewed) at hook time, so a downstream gate's "nothing to review" carve-out fires even though the commit that actually runs is not empty. Three independent checks run.
  - A **wrapper/commit co-occurrence pre-check** denies outright when the command's raw text carries both a git-commit-shaped fragment and an execution-wrapper token (`bash -c`, `sh -c`, `eval`, `xargs`, `source`/bare `.`, `perl -e`, `python -c`, `ruby -e`, `node -e`, or similar) anywhere in the same call, independent of order or quote style — closing the wrapped-invocation bypass structurally, without parsing what runs inside the wrapper. Accepted over-deny cost: a commit message merely mentioning one of these tokens as ordinary text also denies. An unquoted parameter expansion standing in for a required whitespace character (e.g. `${IFS}`) defeats this check — see the hook's own header "Known gaps" list.
  - **Arm 1** walks the command's fragments in order over quote-*stripped* text, denying a non-read-only git subcommand chained ahead of the first commit fragment, or that commit fragment itself carrying `-a`/`--all`, a `--` pathspec separator, or a bare pathspec argument.
  - **Arm 2** counts git-commit-invoking fragments over quote-*masked* text and denies more than one anywhere in the command, since arm 1 alone stops at the first commit fragment and cannot see a second one in the same chain. The same ordered walk over masked fragments also denies a non-read-only git subcommand reached before the first masked commit fragment — masking correctly erases a quote-embedded decoy's content, so a real mutation hidden behind a fake stripped commit fragment in arm 1's quote-stripped walk is still visible here.
    - `_lib_mask_shell_quotes` (defined in `_lib.sh`) runs as a single quote-state-tracking pass over the whole command string, left to right, rather than two independent line-scoped `sed` passes, so a `"` seen while a single-quote span is open is masked as ordinary content and never mistaken for a double-quote delimiter (and vice versa).
    - It reads the entire command as one awk record (`RS` set to NUL, which never appears in shell command text), so a quoted span containing an embedded newline is scanned as a single span. That holds on awks that honor a NUL `RS`; BSD/macOS awk splits the command at each blank line instead. Limits, some of which fail open, are listed in `_lib_mask_shell_quotes`'s header in `_lib.sh`; worked cases are in `docs/security-hardening.md`.
    - It blanks any quoted span whose interior contains whitespace or a shell operator, leaving only its delimiter pair (`"..."` becomes `""`) — except a span whose interior is a single word matching `^[A-Za-z0-9._/-]+$`, which is emitted unquoted instead, so a quoted `git`/`commit` word (`"git" commit`) is still visible to the count.
    - This is the opposite normalization from arm 1's `_lib_strip_shell_quotes`, which treats quoted text as code to strip rather than as inert data to mask.
    - Runs under a 5s `_lib_capped_for` cap — the per-character scan is O(n²) on command length.
  - The sanctioned `marker.sh write <skill> && git commit` chain survives untouched by construction.
  - Every commit gate whose trigger or hash derives from `git diff --cached` depends on this gate for its own empty-diff carve-out to be sound, for the shapes this gate closes — see the hook's own header "Known gaps" list for what still bypasses it (an execution mechanism outside its wrapper-token list, `$(...)` side-effect execution inside a commit's own arguments, and quote/indirection obfuscation of commit detection itself): `require-code-review.sh`, `require-skill-review.sh`, `check-skill-length.sh`, `check-claude-md-length.sh`, `guard-settings-session-keys.sh`, `require-plugin-version-bump.sh`, `require-npm-version-bump.sh`, `deny-pii-in-commits.sh`, `deny-private-project-refs.sh`.
  - Each of those names this dependency in a one-line comment pointing here rather than restating this list.
  - See the hook's own header for the full known-gaps list:
    - bare `--amend` (folds HEAD's tree into the commit; left open because closing it would break the amend-message-only flow every commit gate's empty-diff carve-out exists to permit)
    - whole-word quote obfuscation (`"git" commit`) is closed for both arms; a shell variable, heredoc, or mid-word quote split (`g"it commit"`) remains open
    - `git -C <other-repo> commit` is not a gap: this hook never hashes a `git diff --cached` of its own, so a `-C`-qualified commit is evaluated the same as any other — the cross-repo-target-hash concern belongs to hooks that do hash a diff, already documented in `deny-pii-in-commits.sh`'s own header
    - an unreviewed `$(...)`/backtick side effect inside a commit's own arguments
    - the accepted `_lib_fragment_invokes_git` any-word false positive
    - the ANSI-C multi-character-escape residual (`$'\x67it'`) contains a backslash, so it fails the masker's single-safe-word exception and stays invisible to arm 2's fragment count (see [`docs/security-hardening.md`](security-hardening.md) for the mechanism)
    - an execution mechanism outside the wrapper/commit co-occurrence check's enumerated token list (an `awk` `system()` call, a `make` recipe, `find -exec`, a remote `ssh host <cmd>`) — see `require-respond-pr.sh`'s own "Threat model" comment for why this is accepted
    - a commit fragment embedded as a wrapper-language string literal with no whitespace between the wrapper's own call syntax and the opening quote (e.g. `perl -e "system('git commit -m y')"`), which evades the fast-reject's bare-word `git` match entirely — a piped or interpreter-fed commit fragment with ordinary word spacing (e.g. `printf '%s' 'git commit -m y' | xargs -0 sh -c`) is caught, since the fast-reject's word-walk has no chain-position requirement
    - an unquoted parameter expansion standing in for a required whitespace character (e.g. `${IFS}`, `$IFS`) defeats the wrapper-token regex and `_lib_fragment_invokes_git`'s word-split alike, since neither performs real shell tokenization — e.g. `bash${IFS}-c${IFS}"git add secret && git commit -m y"`, where quote-stripping yields the single glued word `bash${IFS}-c${IFS}git`, recognized by neither check as invoking `bash`/`git`
    - none of this hook's own forks carries an internal timeout, except `_lib_mask_shell_quotes`'s own 5s `_lib_capped_for` cap
    - hoisting `COMMAND_UNQUOTED`'s computation ahead of the fast-reject widened this hook's failure blast radius from commit-shaped Bash calls only to every Bash call in the session on a missing or wedged sed/tr
- **`require-code-review.sh`** — blocks `git commit` (including chained forms like `git add . && git commit`) until `/code-review` has run on the current staged state. Verified via a sha256 marker in `<config-dir>/code-review-markers/<repo-hash>.<session-id>`, which auto-invalidates the moment the staging area changes. The read matches on the marker's stored hash across every session suffix under this repo-hash; the session key in the filename exists so two parallel sessions in the same worktree cannot overwrite each other's markers when staging different diffs. Also appends a non-blocking compliance line (`<iso8601> marker=<matched|unmatched> ledger=<present|absent>`) to `<config-dir>/.review-ledger-compliance.log` at both the allow and deny paths, timeout-guarded via `_lib_capped` — a measured signal for whether `review-ledger.sh append` (see below) is actually keeping pace with `/code-review` runs, never itself affecting the gate's decision. The log is append-only and not rotated automatically. Trim it periodically if disk space is a concern: `> <config-dir>/.review-ledger-compliance.log`.
- **`require-skill-review.sh`** — blocks `git commit` when staged changes, diffed against a novel-content base, include a `SKILL.md` or `claude-skills/skills/plan-review/ROUTING.md`. Mid-merge/cherry-pick/rebase, gated content an already-reviewed upstream commit brought in unchanged does not arm the gate. A trusted in-progress revert is excluded from that base and stays HEAD-relative. See [`docs/design-decisions/skill-review-gate-disarms-on-empty-base-relative-diff.md`](design-decisions/skill-review-gate-disarms-on-empty-base-relative-diff.md). Requires `/skill-review` to have produced a behavioral-equivalence audit for any removed or shortened lines. Marker is keyed to that same base-relative SKILL.md/ROUTING.md-scoped diff (not the full staged diff), so re-staging non-skill files after a clean review does not invalidate the marker. Mid-merge/cherry-pick/rebase, a staged gated file that carries a column-0 conflict-marker line its change touches denies outright, and no marker can release it. A failed conflict-marker scan or path listing also denies, and a retry clears a transient failure such as a cap kill. An unreadable staged blob denies until its cause is fixed, for example by resolving and staging an unmerged path or renaming a path that git lists quoted. See the design doc's "Conflict-marker hard deny" section.
- **`deny-private-project-refs.sh`** — blocks `git commit`, `gh pr create`, `gh pr edit`, `gh issue create`, `gh issue comment`, `gh issue edit`, and mutating `gh api` calls when the staged diff, commit message, or PR/issue title/body/body-source-file contains either (a) tracker-ID tokens (`[A-Z]{2,}-\d+`) outside an OSS-prefix allowlist (`CVE-`, `RFC-`, `GH-`, and similar — see the script for the full list), or (b) a literal substring match against entries in the user's opt-in `<config-dir>/private-projects.md` blocklist. `gh pr`/`gh issue` surface detection resolves positional words via `_lib_tool_argv_from_subcmd`, so any flag interposed before the subcommand — not only a value-taking `-R`/`--repo` flag — cannot separate the surface word from its subcommand, matching gh's own cobra-based subcommand resolution (`gh --repo o/r pr create`, `gh pr --title x create`, `gh issue --repo o/r comment 42`). The same grammar covers `block-gh-pr-merge.sh`. Enforces the mechanical categories of the repo-root `CLAUDE.md` redaction rule; structural fingerprints still require review discipline. See [`docs/private-project-redaction.md`](private-project-redaction.md).
- **`deny-pii-in-commits.sh`** — two tiers, one opt-in and one always on. Blocks `git commit` (every repo, including chained forms) when the added lines of the staged diff, the commit message, or a referenced `-F`/`--file` message file contain personally-identifying/protected-health information or a credential-shaped value. The credential-value sub-check (the same GitHub-token-prefix/PEM-header regex `redact-credential-values.sh` uses) is always on, with no arming file. The SSN/Luhn-checked-credit-card built-ins and every user `<label>: <regex>` line stay dormant unless `<config-dir>/pii-patterns.md` exists as a readable regular file; `exclude: <glob>` lines in that file drop synthetic-fixture paths from the scan for both tiers. When `-a`/`--all`, a `--` pathspec, or a bare pathspec argument is present, also scans `git diff HEAD` (working-tree content committed outside the index) — unconditionally, since the credential-value tier needs it regardless of arming. Robust against `--no-verify`. The deny message names the matched pattern by label only — never the matched value or the user regex. See [`docs/security-hardening.md`](security-hardening.md).
- **`deny-data-file-reads.sh`** — opt-in. PreToolUse `Read` gate that refuses data-shaped files before their content enters Claude's context. Dormant unless `<config-dir>/data-file-read-guard.md` exists as a readable regular file. Once armed, denies `Read` of a data-file extension (`.csv`, `.parquet`, `.sqlite`, `.xlsx`, and similar), a path under a `Downloads/` directory, a file over 5 MB, or any path matching a glob line in the config file. No bypass valve. See [`docs/security-hardening.md`](security-hardening.md).
- **`deny-credential-bash-reads.sh`** — always on, no arming file. PreToolUse `Bash` gate that denies any command whose raw text contains a credential-shaped path token: an SSH private key basename (`id_` followed by `rsa`, `dsa`, `ecdsa`, or `ed25519`, excluding the `.pub` public-key variant), `.netrc`/`_netrc`, `.git-credentials`, a cloud credential store (`~/.aws/credentials`, `~/.docker/config.json`, `~/.kube/config`, `~/.config/gh/hosts.yml`), or a non-template `.env` variant/`credentials.json`. Matches case-insensitively and on the bare basename anywhere in the command, not only when directory-qualified — the case-insensitive match closes a bypass on any case-insensitive-but-case-preserving filesystem (macOS APFS/HFS+, Windows NTFS), where an uppercase-variant basename opens the identical on-disk file as its lowercase form. Carries no content-exposing-verb carve-out — `ssh-add`, `chmod`, and `ssh -i` against a credential path are denied too, the accepted false-positive cost of a path-token-only match with no bypass valve. An optional `<config-dir>/credential-file-guard.md`, same glob grammar as `data-file-read-guard.md`, adds personal/org-specific path tokens, matched case-insensitively too (a scoped `shopt -s nocasematch` around the glob match, since bash `case` has no per-pattern case-fold syntax). See [`docs/security-hardening.md`](security-hardening.md).
- **`deny-credential-file-reads.sh`** — always on, no arming file. PreToolUse `Read` sibling to `deny-credential-bash-reads.sh`, using the same built-in credential-path shapes (case-insensitively matched, same rationale) against `tool_input.file_path`. Resolves symlinks via `readlink -f` before allowing (same fail-closed-on-unresolvable-or-missing-target posture as `deny-env-reads.sh`'s own symlink defense) — since this hook has no allowlist, every symlinked Read target is resolved and checked, not only ones whose own name already looks credential-shaped. Same optional `<config-dir>/credential-file-guard.md` additions file as `deny-credential-bash-reads.sh`. See [`docs/security-hardening.md`](security-hardening.md).
- **`deny-escaped-backticks-in-pr-body.sh`** — blocks `gh pr create` and `gh pr edit` when the PR body (inline `--body` or any body-source file passed via `--body-file`/`-F`/`--template`/`-T`) contains literal backslash-backtick sequences (`\``). Those sequences appear when a `<<'EOF'` single-quoted heredoc writer unnecessarily escapes a backtick — the backslash survives into the rendered GitHub body and breaks code-span formatting. Fails closed when a body-source file is unreadable or a pseudo-file path (`-`, `/dev/stdin`, `/dev/fd/*`, `/proc/*/fd/*`).
- **`block-gh-pr-merge.sh`** — blocks every shape of `gh pr merge` (bare, with flags, `--auto`, `--squash`/`--merge`/`--rebase`, paren-grouped chains, `&&`-chained, trailing-semicolon forms) and instructs the agent to surface the merge intent to the engineer. Enforces the repo-root CLAUDE.md rule **AI agents: don't merge your own PRs** at the tool-call boundary. No bypass marker — the engineer runs `gh pr merge` themselves (or via the `!` shell escape). Matches via `_lib_command_invokes_tool_subcmd` (GH-783): quote-strip, fragment-split, then a command-word-resolved `gh`/`pr`/`merge` word-sequence match. This also matches a full-path invocation (`/usr/bin/gh pr merge`), a quote-split subcommand word (`gh pr "merge"`), and any flag interposed before the subcommand words, matching gh's own cobra-based resolution (`gh --repo o/r pr merge`, `gh pr --title x merge 291`). It does not match `gh pr mergefoo` (word-sequence, not substring) or `echo "gh pr merge"` (the stripped fragment's command word resolves to `echo`, not `gh`).
- **`require-stow-reminder.sh`** — scoped to the `claude-config` repo. Blocks `gh pr create` and `gh pr edit` (when the edit changes the body) if the PR adds a new immediate child of `claude/.claude/` (file or directory) **or** changes `install.sh` (GH-465) — and neither the inline command, a referenced `--body-file`/`--template`, nor any `--fill`-sourced commit message mentions `install.sh` or `stow` (case-insensitive). Reason: GNU Stow links each top-level child of `claude/.claude/` individually, so a brand-new child only appears in `~/.claude/` after re-running `install.sh` — `git pull` alone won't materialize the symlink; `install.sh` itself is not stowed and only takes effect when invoked, so a change to it ships on `git pull` only if it removes stowed behavior, with the replacement landing only after a manual re-run. The reminder lands in the PR body so the post-merge re-run step doesn't get forgotten at merge time. Its `ADDED_PATHS` diff is hardcoded to `claude/.claude/` and cannot see a new immediate child of `claude-skills/`. The hook's own "Known gaps" header section records that gap.
- **`require-respond-pr.sh`** — blocks PR/issue comment reads and posts and redirects to `/respond-pr`, so all three comment types get fetched and replies carry the `[Claude Code]` attribution prefix. The gated surface is `gh api .../pulls|issues/N/{comments,reviews}`, the un-numbered comment-ID endpoint `gh api repos/O/R/pulls|issues/comments/ID`, `gh pr comment`, `gh pr review`, `gh issue comment`, and the GraphQL comment/review mutations plus file-sourced GraphQL bodies. Reads and writes are gated asymmetrically: a command that explicitly names a repo other than the current `origin` is released as external research, but only when it carries no write signal — writes are denied for every repo, because the attribution prefix is owed to readers of any public thread. Honors a per-session bypass marker at `<config-dir>/.respond-pr-active.d/<session_id>` that the skill sets on entry and removes on exit; the hook checks `kill -0` against the stored PID on each gate hit; a dead PID evicts the orphaned marker automatically. Per-session keying (rather than a singleton path) keeps parallel Claude sessions from thrashing on cleanup or leaking bypass to unrelated sessions.
- **`require-ready-for-review.sh`** — gates `git push`, `gh pr ready`, and `gh pr create` on branches with an open PR. Requires `/ready-for-review` to have run and passed since the last commit. Verified via a marker whose content is the HEAD SHA the gate ran against — a new commit invalidates the marker automatically and forces a re-run. Wired on the PreToolUse `Bash` matcher with no `if`-condition, so it fires on every Bash call and self-filters internally. An active-skill bypass marker (`<config-dir>/.ready-for-review-active.d/<session_id>`) prevents the skill's own iteration pushes (fix → push → loop) from self-denying.
- **`require-worktree-for-git-writes.sh`** — opt-in per repo or per machine. When active, denies non-read-only git operations unless the session runs in a linked git worktree. Prevents concurrent Claude Code sessions from racing on the same working tree. A git command that resolves into a linked worktree passes through `_lib_worktree_collision_guard` (`_lib.sh`) whenever that worktree's lock is already held, denying when a *different* live session holds it. Only a write can cause the guard to freshly acquire the lock. When the full-parsing path's own collision-guard call is what freshly acquired the lock (a plain `[ -e ... ]` pre-check on the lock file before the call), the allow carries an `additionalContext` note naming the reacquisition and the `git worktree unlock <path>` remedy if unintended. A self-lock reentry (the lock was already this session's) stays silent, and so does every prior allow. A read never acquires the lock, regardless of which path evaluates it. See the "Worktree enforcement" section of [the README](../README.md).
- **`require-worktree-for-file-writes.sh`** — opt-in per repo or per machine (same sentinel files). When active, denies `Edit`/`Write`/`MultiEdit` on paths in the main working tree; all file edits must land in a linked worktree. Paths under `$HOME/.claude/` are always exempt — the harness and skills write plans, memory, settings, and other infrastructure files there as normal operation, and `~/.claude/` may resolve via stow directory-folding into an opted-in checkout. Also runs the same `_lib_worktree_collision_guard` check as `require-worktree-for-git-writes.sh` before allowing a write into an already-linked worktree, with the same fresh-acquire `additionalContext` note on the same pre-check basis.
- **`deny-reviewer-tree-mutation.sh`** — always on (no worktree-enforcement opt-in required). Denies `Bash`/`Write`/`Edit`/`MultiEdit` from the closed set of review-only agents (`ciso-reviewer`, the seven `staff-*` personas, the non-specialist reviewers `skill-fidelity-reviewer` and `comment-discipline-reviewer`, `Explore`, `Plan`) that would mutate the tree under review: git writes, `Write`/`Edit`/`MultiEdit` outside `/tmp` or an `agent-reviews/` findings path, and a closed in-place-edit-tool family split into two tiers — pure formatters denied on any invocation regardless of flags (`black`, `isort`, `gofmt`, `prettier`, `rustfmt`, `terraform`/`tofu fmt`), and dual-use linters/text tools denied only in their write form (`sed -i`/`perl -i`, `eslint --fix`, `ruff format`/`ruff check --fix`). An `agent-reviews/*` write is exempted only after confirming with `git check-ignore` that the directory is actually ignored in the target repo — a stale worktree-local `info/exclude` or a repo with no ignore entry denies rather than silently allowing an unignored findings file through. GH-751: a `cp`/`mv`/`tee` destination or a `>`/`>>` shell redirect target in a Bash command that is not literally under `/tmp/` denies, when the write is the fragment's sole or first command (`cp scratch src/x`, `sed ... > src/x`, `tee src/x`) — not when the same target is hidden behind a bare `&` background operator in the same fragment, a residual GH-811 tracks. A raw-Bash write to `agent-reviews/*` gets no exemption at all under this check (it has no `git check-ignore` confirmation the Write/Edit/MultiEdit arm's exemption depends on), a stricter default rather than an unchecked one. Every other agent (main session, `code-writer`, `general-purpose`) passes through unconditionally.
- **`deny-repo-relocation.sh`** — always on (no worktree-enforcement opt-in required; not scoped to this repo — it protects whichever claude-config checkout it is stowed from, regardless of which repo the session is working in). Denies a `Bash` `mv` or `rsync --remove-source-files` command whose resolved source argument is this claude-config checkout's root or an ancestor of it — moving or renaming the checkout breaks every stow symlink under `~/.claude/` and `~/.local/bin/` at once, with nothing left running that could detect or explain the failure. Points at `relocate-claude-config` (see [`docs/scripts.md`](scripts.md)) as the supported command instead. Self-locates the protected root from its own physical path (`readlink -f "$0"`), not from cwd, so it fires correctly no matter which repo's Bash call it's evaluating. Best-effort, not a hard security boundary: a source argument reached only through a shell variable, command substitution, or a preceding `cd` in the same command fails OPEN (allow) rather than deny, and equivalent-relocation forms outside the `mv`/`rsync` pattern (`cp -r && rm -rf`, `python3 -c "os.rename(...)"`, a GUI/Finder move) aren't covered at all — see the [README "Repo relocation"](../README.md#repo-relocation) section and the hook's own header for the full known-gaps list and why the destination-side validation in `relocate-claude-config` is where this design's actual security investment goes.
- **`deny-network-installs.sh`** — always on, no arming file, no bypass valve. Denies a `Bash` command that installs a named package via `npm`/`pnpm`/`yarn`/`bun`/`pip`/`pip3`/`uv pip`/`uv add` (a manager and install verb both present, with an unrecognized-as-restore argument left over after removing flags and known restore markers like `-r`/`--frozen-lockfile`), an `npx`/`bunx`/`uvx`/`pipx run`/`npm exec` invocation carrying an explicit `-y`/`--yes` skip-confirmation flag, `pnpm`/`yarn dlx` unconditionally (no local-resolution ambiguity to disambiguate, unlike npx), or a command that hands fetched content to a shell/interpreter (`curl`/`wget` co-occurring with `bash`/`sh`/`zsh`/`python3`/`python`/`node`/`ruby`/`perl` anywhere in the same call, including via `bash -c "$(curl …)"` or process substitution). Matches on token presence, not on resolving "the" leading command — position-based resolution misses pnpm/yarn/bun (its runner-skip list treats them as wrappers), `bash -c "$(curl …)"` (produces a trailing empty fragment), and is sensitive to wrapper/assignment ordering; presence has none of these gaps, since no wrapper removes a token from the command string. Command text is quote-stripped before matching, closing a false-allow (`"npm" install lodash` runs identically to the unquoted form) at the cost of a uniform, accepted over-deny on any text argument merely mentioning an install shape (a `grep` pattern, a commit message). Named residuals: bare `npx`/`bunx`/`uvx`/`pipx`/`npm exec` (no `-y`/`--yes`), and `pip install -e <VCS-URL>`. See [`docs/security-hardening.md`](security-hardening.md) for the full list.
- **`guard-settings-session-keys.sh`** — blocks `git commit` when `claude/.claude/settings.json` has staged changes to `model`, `effortLevel`, `skipAutoPermissionPrompt`, `skipWorkflowUsageWarning`, `theme`, `tui`, or the same `model`/`effortLevel` values written nested under `env.ANTHROPIC_MODEL`/`env.CLAUDE_CODE_EFFORT_LEVEL`. These are session-scoped or Claude-Code-auto-written preferences that should not be committed to the shared config; for `model`/`effortLevel`, use `ANTHROPIC_MODEL`/`CLAUDE_CODE_EFFORT_LEVEL` env vars or `/effort max` mid-session instead.
- **`check-skill-length.sh`** — blocks `git commit` when a staged `SKILL.md` exceeds its line limit (200 by default; `limit_for` in the hook holds the per-skill overrides) and grew vs HEAD, across stowed skills (`claude-skills/skills/`), project-scoped plugins (`plugins/*/skills/`), and repo-root plugin layouts (`skills/<name>/SKILL.md`). Also caps two runtime auxiliary files: `plan-review/ROUTING.md` (500 lines) and `pr-description/DEFAULT_TEMPLATE.md` (200 lines). Nudges toward splitting a growing skill or moving reference material to a co-located `REFERENCES.md`.
- **`check-claude-md-length.sh`** — blocks `git commit` when a staged `CLAUDE.md` or `AGENTS.md` (repo root or any `.claude/`-scoped path) is over its 200-line cap and grew past HEAD in lines. It also blocks when the file is over its 25,600-byte cap and grew past HEAD in bytes. Each dimension is checked independently, so an already-over-limit file can still shrink commit by commit without blocking the work. `check-skill-length.sh` has no byte cap.
- **`require-memory-skill.sh`** — PreToolUse `Edit|Write|MultiEdit` gate on `<config-dir>/projects/*/memory/MEMORY.md` and new memory topic files under that path. Requires an active `/ai-instruction-and-memory-files` per-session marker before allowing writes, ensuring index format and frontmatter rules are applied.
- **`require-routing-read.sh`** — PreToolUse `Agent` gate active during a running `/plan-review` session. Denies subagent spawn until `~/.claude/skills/plan-review/ROUTING.md` has been read (tracked by `log-routing-read.sh`), ensuring reviewer routing consults the full ownership table before any specialist is spawned.
- **`require-architect-consult.sh`** — `PreToolUse` gate on matcher `Agent|Task`, self-filtered to a reviewer-persona spawn (`ciso-reviewer`, the `staff-*` personas, `comment-discipline-reviewer`, `skill-fidelity-reviewer`). Denies the spawn once a branch's `<config-dir>/.reviewer-round-state.d/<repo-hash>.<branch-hash>` state file already holds the resolved cap's worth of distinct `(HEAD sha, staged-diff sha256)` entries and the current state is a genuinely new one beyond that cap, unless `<config-dir>/.architect-consult-latch.d/<repo-hash>.<branch-hash>` already shows a `plan-architect` consult ran recently for this branch. The cap is resolved via `_lib.sh`'s `_lib_reviewer_round_state_cap`. It is 2 by default (entry to the 3rd distinct state trips the gate). It is 1 under the time-boxed round-2 pilot (`round_consult_round2_pilot` config key, falling back to its legacy sentinel `<config-dir>/.round-consult-round2-pilot` when absent — see [`docs/config-file.md`](config-file.md) and [`docs/design-decisions/round2-consult-trigger-pilot.md`](design-decisions/round2-consult-trigger-pilot.md)). Fires once per branch — the latch does not re-arm at round 5, 7, 9. Fast path is cheap-check-first: tool name, then reviewer-persona type, then the disable sentinel `<config-dir>/.round-consult-gate-disabled` (presence-only, machine scope, wins even with the pilot sentinel also present), then a live `/plan-review`/`/ready-for-review` active-bypass marker for the session — every non-reviewer `Agent`/`Task` dispatch exits before the first git call, and the current state's own `git diff --cached` hash is paid only once the state file is already at the cap. The deny message names:
  - the compliance path (`plan-architect MODE=consult`)
  - `code-review/SKILL.md` § "Round-cap architect consult", for routing the consult's return
  - the report-to-engineer escalation if that's not workable in-session
  - a subagent-specific report-to-dispatcher clause

  Never an instruction to touch the disable sentinel itself. This gate ships a genuine off-switch sentinel, unlike the three entries in [Gates with no clean escape](#gates-with-no-clean-escape) below, so it is not filed there.
- **`deny-no-op-dispatch.sh`** — `PreToolUse` gate on matcher `Agent|Task`, unfiltered by `subagent_type` — every dispatch is evaluated, since confirmed no-op occurrences spanned `fork`, `general-purpose`, and no `subagent_type` field at all. Denies a dispatch only when **both** hold: `tool_input.prompt` is shorter than `NOOP_MAX_PROMPT_LEN` (600 characters), and `tool_input.prompt` alone matches a closed, sourced idiom list — either an anchored whole-prompt stub token (`noop`/`placeholder`) or an unanchored phrase (e.g. `just wait`, `report back immediately`, `occupy the turn`, `hold while`; the full list is `NOOP_PHRASE_RE` in the hook). `tool_input.description` is never read; it is a display label, not an instruction surface. A prompt at or above the ceiling is allowed regardless of content, so the gate cannot reach a prompt long enough to specify real work. Reads nothing from disk — no config dir, no git, no transcript, no marker — so it carries no state-failure branch, only the uniform payload-failure deny every gate hook shares. No `subagent_type` filter, no disable sentinel, and no bypass valve of any kind: the escape is rephrasing the dispatch to state its actual work. This is a cooperative guardrail against a self-inflicted cost anti-pattern, not an adversarial-resistant security boundary, so it must not be cited as evidence of an enforced cost or abuse control. See [`docs/design-decisions/no-op-dispatch-hook-gate.md`](design-decisions/no-op-dispatch-hook-gate.md) for the full design rationale and known gaps.

## Utility hooks

- **`capture-session-id.sh`** (SessionStart, SubagentStart) — at session and subagent start, writes the session's `session_id` to `<config-dir>/sessions/<claude-pid>` so skills running as Bash tool calls (which don't see the hook payload) can look up their own session id by walking process ancestors from the bash tool's `$PPID` (`marker.sh`'s `_walk_session`) until it reaches this file. `<claude-pid>` is the hook's own `$PPID`, optionally overridden by `$CLAUDE_PID` when Claude Code exports it and it names the same process or its immediate parent (`_lib_hook_claude_pid`, `_lib.sh`). Used by both `/respond-pr` and `/code-review` to compute per-session marker filenames. Rewritten at every `SessionStart` and `SubagentStart` under the resolved PID (covers `/clear`, where one session ends and another starts in the same process); nothing deletes it on session exit, so a bare-PID file from a session, resume, or one-shot run lingers until its PID is reused. Unlike `nudge-worktree-anchor.sh` and `advance-past-commit-stall.sh` below, this file gets no time-based self-sweep: an mtime sweep can't tell a stale entry from a still-live long-running session's own entry — growth is bounded only by PID reuse.
- **`record-session-end.sh`** (`SessionEnd`) — `SessionEnd` fires once when Claude Code shuts down (the harness's documented `reason` values: `clear`, `resume`, `logout`, `prompt_input_exit`, `other` — none of them denotes a crash). This hook writes `<config-dir>/session-end-records/<claude-pid>` as `{"sessionId": "<id>", "reason": "<reason, or null if absent>"}` on every fire, keyed by `<claude-pid>` the same way `capture-session-id.sh` keys its own lookup file (`_lib_hook_claude_pid`). No timestamp field — the record file's own mtime is the record time. `post-crash-sessions.py` reads these records as a fifth evidence source, reclassifying a dead-pid session into "Confirmed clean exit" once every process instance it tracked for that session has a matching record — see [`docs/scripts.md`](scripts.md) and `.claude/plans/detect-clean-exit-vs-crash.md`. Sweeps records older than 30 days from its own directory on every fire, after the write. Registered with `"timeout": 10` in `claude/.claude/settings.json` to raise its SessionEnd execution budget above the harness's shared default. Two known gaps: `claude -p` (headless) skips `SessionEnd` entirely, so a headless run that exits cleanly never writes a record; and whether `SessionEnd` fires on a hard kill (SIGKILL, OOM, reboot) is undocumented upstream and verified only by manual testing (see `.claude/plans/detect-clean-exit-vs-crash.md`). `SessionEnd` has been observed firing with `reason: "other"` on a SIGTERM/SIGHUP-adjacent hard kill (e.g. an OOM-killer terminating the terminal), not only on a deliberate exit. `SIGKILL` and cross-platform behavior remain unverified. `post-crash-sessions.py` treats `reason: "other"` as inconclusive because it cannot distinguish a hard kill from a deliberate exit.
- **`nudge-handoff-near-context-cap.sh`** (PostToolBatch + Stop, `batch-gate`) — injects an `additionalContext` reminder to consider `/handoff` as carried context nears the compaction cap. PostToolBatch fires during autonomous tool-call stretches so the nudge isn't limited to human-interaction boundaries; Stop stays registered alongside it as a safety net for a toolless final turn. Once a session's estimate reaches `HANDOFF_NUDGE_BLOCK_AT`, a further re-arm hard-blocks (stderr + exit 2, PostToolBatch's own native loop-stop) instead of staying advisory — unless a live `/handoff` active-bypass marker for that session keeps the re-arm advisory instead. Every `nudged` log line also records `ignored=` (the session's ignored-re-arm count) and `skills=` (the active-bypass skill markers live at fire time, or `-`). Opt-out via `<config-dir>/.handoff-nudge-disabled`. Also runs as a read-only query — `nudge-handoff-near-context-cap.sh --check` reports the session's current estimate and threshold as JSON, writing no marker and no log line, which is what `plan-it` Step 7, the `handoff` skill, and `ready-for-review` Step 1 act on. See [`docs/handoff-nudge.md`](handoff-nudge.md) for the threshold, marker mechanics, log format, escalation ladder, and the `--check` contract.
- **`nudge-long-turn-subagent.sh`** (PostToolBatch, `batch-gate`) — injects an `additionalContext` nudge when a **subagent dispatch's own** turn count crosses a measured outlier threshold (340 turns, just above a corpus-measured p99 of 339 — see `docs/design-decisions.md`), so a runaway dispatch surfaces early instead of after tens of hours. Inverted polarity from `nudge-handoff-near-context-cap.sh`: fires only when `agent_type` identifies a subagent, never in the main session. Turn count is tracked incrementally per dispatch via a small state file (resume offset, running total, and a flag marking whether the next scan resumes mid-record), never a full-transcript rescan on every fire. It reuses `_lib_advance_offset_past_complete_lines` (shared with `nudge-handoff-near-context-cap.sh` via `_lib.sh`) for mid-write transcript safety. The scan and threshold check run only on every 10th `PostToolBatch` fire (`LONG_TURN_NUDGE_SAMPLE_CADENCE`); every other fire only appends one byte to a counter file. Fires at most once per dispatch. A fired marker under `<config-dir>/.long-turn-nudge-fired.d/` suppresses repeats. It never blocks or kills the tool call it observes, purely advisory — unlike `nudge-handoff-near-context-cap.sh`'s hard-block escalation ladder. `LONG_TURN_NUDGE_THRESHOLD` and `LONG_TURN_NUDGE_SAMPLE_CADENCE` override the defaults. See [`docs/long-turn-nudge.md`](long-turn-nudge.md) for the lock-directory-orphaning, per-fire-latency, and scan-rate-undercounting known limitations.

## Non-hook opt-in/opt-out sentinels

Not every opt-in or opt-out config key gates a hook. `pr_cost_disclosure` and `pr_description_tighten_prose` each gate a step inside the `pr-description` skill itself (see `claude-skills/skills/pr-description/SKILL.md`'s "Cost section" and "Prose tightening pass") — no `PreToolUse`/`PostToolUse` hook is involved, so neither appears in the lists above. Documented here anyway, since this file is where every config key in this repo is meant to be discoverable — `install.sh`'s `report_sentinel_inventory` surfaces both at install time from the same schema (`claude/.claude/hooks/config-keys.psv`). Both resolve through `<config-dir>/claude-config.toml`, falling back to their own legacy per-key sentinel file only when the key has no row there — see [`docs/config-file.md`](config-file.md) for the file format and full resolution precedence.

Unlike a presence-only key (`worktree_required`, `autonomous_shipping`), `pr_cost_disclosure`'s value is a **mode**, not just a boolean: exactly `dollars` enables the PR body's cost block; `false` or absent disables it. It is also scoped to the Claude account rather than to the repo — cost is an organizational fact, and each account is its own billing entity — so it resolves through exactly one config dir (`$CLAUDE_CONFIG_DIR` when set and absolute, else `$HOME/.claude`), never a union of both the way `worktree_required`/`autonomous_shipping` resolve. Resolving only one path is what keeps one account's opt-in from activating disclosure under another.

The fields it discloses are not neutral even in aggregate form — see `docs/transcript-analysis.md`'s `cost` section, "The disclosed fields are not neutral."

Account scoping has one residual travel path, accepted rather than closed: bootstrapping a new Claude account by copying an existing `$CLAUDE_CONFIG_DIR` tree carries `claude-config.toml`'s `pr_cost_disclosure` row (or its legacy file) forward into the new account with no prompt. `install.sh`'s account row reports the resolved value and source at every run, so an operator inspecting a freshly bootstrapped account sees an inherited value rather than having to suspect one.

### Prose tightening opt-out

`pr_description_tighten_prose` gates the `## Prose tightening pass` section: dispatching `tighten-prose` against a drafted PR body before the reader-coherence and content-claim checks run. Defaults `true` (the pass runs); an explicit `false` row in `claude-config.toml`, or presence of the legacy account-scope `pr-description-tighten-prose-optout` file (kept permanently as a fallback — see `docs/config-file.md`), skips it.

Scoped to the Claude account, not the repo, for the same reason as `pr_cost_disclosure`: a writing-style preference is a personal, cross-repo choice, not a per-project one. Resolves the same way — `$CLAUDE_CONFIG_DIR` when set and absolute, else `$HOME/.claude`, never both.

## Marker keying and gate-release authority

Two properties govern every review gate. They pull in opposite directions and are easy to conflate.

**What a marker's filename means vs. what its content means.** A completion marker lives at `<markers-dir>/<repo-hash>.<session-id>`, and its *content* is a hash of exactly the state that was reviewed — the base-relative staged diff for `/code-review` and `/skill-review`, the active plan set's paths-plus-contents for `/plan-review`, the HEAD sha for `/ready-for-review`, and the cumulative PR-vs-base diff for the `cumulative-review` kind (read back by `ready-for-review` step 3 itself via `marker.sh status`, not gated by a separate `require-*.sh` hook). For the `cumulative-review` kind specifically, that content is the hash of the diff recorded as the review subject at `cumulative-review-subject-markers/<repo-hash>.<session-id>`, captured by `pr-diff-against-base.sh --record` at step 3's entry rather than recomputed at write time.

The base-relative diff is HEAD-relative outside any trusted in-progress state, and mid-revert for `/skill-review` specifically. See each hook's own [Gate hooks](#gate-hooks) bullet.

`--diff-file` writes the cumulative diff to `cumulative-review-diff-markers/<repo-hash>.<session-id>`. `--staged --diff-file` writes the staged diff to `code-review-diff-markers/<repo-hash>.<session-id>`. The two are separate directories so a staged write can never clobber a cumulative artifact the same session is still reading. `enforce-marker-script-shape.sh` protects both directories, plus the subject directory named in the paragraph above, via the same `*-markers/` name-suffix glob that protects every other marker directory, not because it recognizes any of them as holding a review input rather than a completion record.

The completion hash itself still lands in `cumulative-review-markers/`, same as every other kind. The content is the authorization: it is what proves a review covered this state, and it is what re-arms the gate the moment the state changes. The session id in the filename is a *write-side* key only — it keeps two parallel sessions in the same worktree from overwriting each other's markers. Gates therefore match on content across every session suffix under the repo-hash, and a review still covering the current state keeps counting after a resume, a `/clear`, or a handoff to a parallel session. The repo-hash stays part of the read: an identical staged diff or plan text in an unrelated repository was reviewed against different code. A resumed session gets a new session id, so a marker filename quoted from before the resume — e.g. one copied into a handoff brief — no longer names the current session's own marker. To locate the current session's marker file for manual inspection, resolve the id fresh with `marker.sh resolve-session-id` rather than trusting a quoted filename — the gate itself is already unaffected by which session id is current (see above).

`require-plan-review.sh` widens that one step further, to the current repository's own worktrees. A plan's hash covers repo-*relative* paths, so a plan copied into a fresh worktree hashes identically, and the gate honors a review performed in any sibling worktree. Two tiers keep the cost off the common path: the current worktree's repo-hash is checked first (one `sha256sum`), and the worktree enumeration runs only after that misses — i.e. only when the gate is about to deny anyway. A tier-2 hit authorizes content-identity of the plan *text*, not state-identity of the sibling's checkout: two worktrees on divergent branches holding byte-identical plan files do cross-validate.

**Which tree a marker describes.** The repo-hash is derived from a resolved repo root, so one repository checked out at a main tree and at a linked worktree yields two different keys — deliberately, since a review of one tree is not a review of the other. That makes the resolution step load-bearing on both sides of the gate. The reading gates (`require-code-review.sh`, `require-plan-review.sh`, `require-skill-review.sh`) resolve the root from the hook payload's `.cwd` and thread that one root through every subsequent git call, so a hook's marker path and the state it hashes always describe the same tree. `marker.sh` receives no payload and so has no trusted directory to import; it fails closed instead, refusing to write any completion marker while worktree enforcement is active, its resolved root is the repo's main working tree, **and** a linked worktree exists on disk — naming that worktree as the re-anchoring target in the refusal. The worktree-existence check must run symmetrically: with no linked worktree, a main-tree marker is correct by definition (there is no second tree to confuse it with), so denying unconditionally would instead block ordinary main-tree git activity that never passes through these hooks (the worktree hooks gate tool calls, not ambient git state — hand-staged edits and CI checkouts stay unaffected). Symmetry matters because without it, a session anchored in the wrong tree would write and then satisfy a gate describing a tree nobody reviewed.

**Who may release a gate.** Releasing a gate requires having run the review it demands. No agent in `_LIB_NO_GATE_RELEASE_AGENTS` — the review-only personas plus `code-writer` — could have run one: the file-backed personas declare no `Skill` tool and cannot invoke a review skill at all, and the two harness built-ins (`Explore`, `Plan`) are dispatched read-only by mandate — which holds whether or not the harness grants them `Skill`, since this repo ships no frontmatter for either and so cannot check. Either way a marker written by one asserts a review that could not have happened. Because `marker.sh` resolves the session id by walking the process ancestor chain to the Claude main process, such a write is indistinguishable from the parent session's and releases the gate for the whole session, not just the subagent.

`enforce-marker-script-shape.sh` enforces this by keying on **marker state**, not on command text, because marker state is reachable from three tool surfaces and gating any one alone leaves the property false:

- **`Write`/`Edit`/`MultiEdit`** targeting a path under `<config-dir>/*-markers/` or `<config-dir>/.*-active.d/`. This is the load-bearing arm — every agent in the set carries the `Write` tool, so without it a subagent could simply write the marker file directly and never invoke `marker.sh`. It matches the resolved target path (tilde-expanded and normalized), so no shell-level construct evades it.
- **`Bash`** carrying `marker.sh write` or `marker.sh activate`, checked before the hook's own shape validation so wrapped and chained invocations are covered. This arm necessarily matches command text and therefore has a scope limit, stated rather than implied: shell indirection that separates `marker.sh` from the operation keyword — assigning the path to a variable, or wrapping the call in a function — is not matched here, the same carve-out the shape check already documents for wrapped forms. Those forms are not pre-approved in `permissions.allow` either, so they surface as a permission prompt rather than a silent allow.
- **`Bash`** reaching a marker path without ever mentioning `marker.sh` — a `>`/`>>`/`&>`/`&>>`/`<>` redirect, `tee`, `cp`/`mv`/`install` (last-argument form), `dd of=`, or `sed -i` — via a scan that runs before the two checks above, resolving each extracted candidate through the same tilde-expand → realpath → marker-shape match the Write/Edit arm uses. This closes the "arbitrary Bash write-target" gap mechanically, for every agent type, in the cases it covers — narrower in agent scope than `deny-reviewer-tree-mutation.sh`'s own GH-751 fix (a review-only-agent-only, literal-/tmp/-prefix check on the same cp/mv/tee/redirect shapes, with no tilde-expand/realpath resolution), and unlike that hook's still-open residuals (relative-path/symlink resolution, `cp -t DIR`, fd-numbered redirects — see that hook's "Known gaps" section), not dependent on any of them for marker paths specifically. See the hook's own header comment for the current residual-gap list — it is the single source of truth, not restated here.

A subagent that hits a review gate is expected to report the denial upward; the dispatching session runs the skill, or delegates it to a `general-purpose` subagent, which does carry `Skill`. Matching a hash the subagent computed itself is not authorization — an equal hash shows the state is unchanged, not that anyone reviewed it. `test_agent_roster.py` asserts the no-`Skill` property against each file-backed agent's `tools:` frontmatter and pins the harness built-ins as a closed exemption set, so neither grounding can quietly go stale.

## Gate deadlock recovery

With `jq` unavailable (missing from `PATH`, failing, or hung past its 5s timeout backstop), every gate hook hard-blocks by design rather than silently allowing. In an interactive session, the recovery route is the `!` shell escape, which runs outside the tool-call path these hooks gate, to install or repair `jq`. A headless or non-interactive run has no `!` escape, so `jq` must already be installed in the execution environment beforehand.

A `timeout` or `gtimeout` that rejects `-k` is the same kind of hard-block, because `jq` runs under it: `jq` is healthy, yet every gated tool call denies. README.md's Requirements section states which implementations accept `-k`.
Diagnose with `command -v timeout gtimeout` and `timeout -k 1 1 true; echo $?`, which must print 0. The hooks probe `timeout` first and `gtimeout` only when no `timeout` is on `PATH`, so installing GNU coreutils behind a BusyBox `timeout` that still wins on `PATH` changes nothing.
Recovery is one route: put a `-k`-capable `timeout` ahead of the rejecting one on the harness's `PATH`, then restart the harness.
A `PATH` change made in a `!` shell escape is not a recovery route.

A SIGKILL after the grace can strand a git lock file. The symptom is git's "Unable to create '<path>/index.lock': File exists" error. Confirm no git process is running for that repository, then remove the lock path git names in its error message. In a linked worktree it lives under `.git/worktrees/<name>/`.

The skill-review gate's marker recipe spans two halves that update independently: the stowed `marker.sh` (updated by `git pull` in the claude-config checkout) and the installed `skill-management` plugin hook (updated by `claude plugin update`). While the halves disagree, a freshly written skill-review marker can keep denying, because `marker.sh` and the hook hash different diffs mid-merge/cherry-pick/rebase.
- Stowed half newer than the plugin: refresh the plugin. In an interactive session, run `claude plugin update skill-management@claude-config --scope project` through the `!` shell escape, then run `/reload-plugins` (or restart Claude Code) so the open session loads the new hook, then re-run `/skill-review`. A shell-run update does not affect the open session.
- Plugin newer than the stowed half: the user runs `git pull` in the claude-config checkout, then re-run `/skill-review`.

`check-claude-md-length.sh`, `check-skill-length.sh`, `require-code-review.sh`, `block-gh-pr-merge.sh`, `deny-escaped-backticks-in-pr-body.sh`, and `deny-invisible-commit-content.sh` add `sed`/`tr` as further hard-block dependencies beyond `jq`; `require-respond-pr.sh` (GH-801) adds `awk`. Each denies (rather than silently allowing) when its own `sed`/`tr`/`awk` fork fails — missing, killed, or erroring — so a deadlock traced to one of those tools rather than `jq` blocks only that hook's own gated surface, not every Bash call, and recovers the same way: the `!` shell escape to install or repair the missing tool. See each hook's own header comment for the exact status-2 deny message it emits.

Active-bypass markers from sessions that crash before cleanup evict themselves automatically: the hooks check `kill -0` against the stored PID and evict dead entries on the next gate hit. They also evict a marker whose mtime has aged more than 60 minutes past its last gating call even when the PID is still alive, bounding the case of a skill that halts between its activate and deactivate steps without the session process itself dying. This cutoff matches `session-marker-dashboard.sh`'s own staleness threshold (`age_min -ge 60`), so the dashboard's "stale" label and the gate's own eviction agree on the same marker. A capped-out read (the `cat`/`find` calls behind this check exceeding `_lib_capped`'s 5-second timeout, e.g. a stalled NFS mount) is treated the same way: the liveness check returns false and the marker is evicted, identically to a dead PID or an aged-out mtime.

The marker path carries no repo hash, so a live marker releases its gate for every tree the session touches while the skill runs, not only the tree where it was activated. Switching trees inside the idle window carries the release across trees with it, since the window bounds how long the marker has gone idle, not which tree it applies to. This gap predates the touch-on-use refresh below and is unchanged by it.

The four gate hooks that grant the bypass (`require-plan-review.sh`, `require-ready-for-review.sh`, `require-respond-pr.sh`, `require-memory-skill.sh`) refresh a marker's mtime on every gate check that reaches the marker, so this 60-minute window is a touch-on-use idle window, not a hard cap, for as long as the hook's own trigger condition keeps firing. What keeps a given hook's checks firing is the hook's own dispatch condition, not narrowly the owning skill's own progress, and it splits along dispatch class — Bash-dispatched gates refresh far more broadly than Write/Edit-dispatched ones:

- `require-respond-pr.sh` and `require-ready-for-review.sh` are both wired on the PreToolUse `Bash` matcher with no `if`-condition, and both refresh before any command-shape filter, so either one refreshes on every Bash tool call in the session. This includes a call issued by a dispatched subagent, since a subagent's Bash calls carry the parent session's `session_id` (see [PreCompact hook behavior](precompact-hook-behavior.md)).
- `require-plan-review.sh` refreshes only on a Write/Edit/MultiEdit to an in-repo file that is neither a plan file nor under `agent-reviews/`, while a plan is outstanding.
- `require-memory-skill.sh` refreshes only on a Write/Edit/MultiEdit targeting a memory-file path.

A session that goes fully idle for 60+ minutes, with no tool call matching either hook family's trigger condition, loses the bypass. For `require-respond-pr.sh` and `require-ready-for-review.sh`, the trigger condition is broad enough that ordinary session activity keeps the marker alive for the practical duration of the session; `require-plan-review.sh` and `require-memory-skill.sh` keep the narrower, write-scoped residual.

For `require-ready-for-review.sh` specifically, that practical-duration-of-the-session window is not repo-scoped either: the marker carries no repo hash (see above), so a Bash call in any other tree the session touches also counts toward it. An abandoned run's push bypass can therefore stay alive for as long as the session is active across multiple repositories, not only in the repo where the skill was activated. `gh pr ready` and `gh pr create` are excluded from the release in every command shape the hook's detection recognizes, so this exposure is push-only for those shapes — see the design-decision doc [`ready-for-review-bypass-releases-push-only.md`](design-decisions/ready-for-review-bypass-releases-push-only.md) for the rationale and the hook header's Known gaps for the shapes detection misses. This is a wider exposure than `require-respond-pr.sh`'s comment-labeling gate carries for the same reason, since that gate's stakes are a correctable comment rather than a push.

The active-marker check and refresh run before the command-shape scan, and the release decision runs after `_lib_split_fragments`. A partial `sed` failure that breaks the split's invocation shape therefore denies even under a live marker. A total absence of `sed` denies earlier, at the unconditional `_lib_strip_shell_quotes` check. The fragment scan runs on every Bash call; see `require-ready-for-review.sh`'s Known gaps header for its per-fragment rescan cost.

`nudge-handoff-near-context-cap.sh` refreshes only its own `.handoff-active.d` label, on every fire, because the hook firing at all is itself evidence the session is still taking turns — the same signal a long multi-turn `/handoff` write needs to avoid expiring mid-run. Every other marker family it enumerates, and `marker.sh status`'s own enumeration, stays on the unrefreshing base predicate, so reading status can never itself extend a marker's life.

The remaining case is a *live session* whose review skill cannot execute — harness-blocked, failing to load, or unable to produce a completion marker due to a tool error.

For three gates, the gating condition is removable via Bash without destroying work:

**`require-plan-review.sh`** blocks Write/Edit when an uncommitted or modified plan file exists in `.claude/plans/` and no completion marker holds that plan set's hash. Committed, unmodified plan files are treated as historical and do not arm the gate. A Write/Edit/MultiEdit whose own target is one of those plan files is exempt, so authoring the plan itself is never what trips the gate.

```bash
# Option 1: remove the plan file to clear the gate. Copy the content first
# if you need to preserve it. If multiple uncommitted plan files exist, all
# must be removed or committed to clear the gate.
rm .claude/plans/<slug>.md

# Option 2: commit the plan file. A committed, unmodified plan is treated
# as historical and does not arm the gate. Two separate commands, not one
# chained call: deny-invisible-commit-content.sh denies a git commit
# chained after a fragment that stages content in the same Bash call.
git add .claude/plans/<slug>.md
git commit -m "plan: <topic>"
```

**`require-code-review.sh`** blocks `git commit` when no review covers the currently staged diff:

```bash
# Unstage the files. Changes remain in your working tree; re-stage and
# run /code-review once the skill is available.
git reset HEAD -- <files>
```

Alternatively, commit directly from a terminal outside Claude Code — Claude Code PreToolUse hooks only fire for `Bash` tool calls within a session.

**`require-skill-review.sh`** blocks `git commit` under the trigger condition its [Gate hooks](#gate-hooks) bullet states:

```bash
git reset HEAD -- <path-to-SKILL.md>
```

Same terminal-outside-Claude-Code fallback applies.

### Gates with no clean escape

Three skill gates have no safe condition-removal path — the gate's intent is to force the skill:

- **`require-ready-for-review.sh`**: escape paths (close the PR, force-push, hard-reset) are destructive. If the skill cannot run in the current session, spawn a subagent.
- **`require-respond-pr.sh`**: the gate ensures the skill fetches all review-comment types before any `gh` PR comment operation. There is no condition to remove short of closing the PR.
- **`require-memory-skill.sh`**: the gate is path-based (fires on writes to memory files). Writing elsewhere defeats the user's intent. Run the skill in a subagent.

### Orphaned active-bypass markers

If a skill's active-bypass gate refuses to release after the skill has finished, use the manual sweep utility:

```bash
~/.claude/scripts/marker.sh clear-stale          # evict dead-PID entries
~/.claude/scripts/marker.sh clear-stale --dry-run # report without removing
```

`activate` resolves the live PID from the process ancestor tree, so a stale `<config-dir>/sessions/` entry — left behind by any session that has since exited, not only a crash or restart, since nothing deletes the lookup file on exit — cannot be stamped into a freshly written marker. `clear-stale` remains the tool for markers left behind by sessions that ended without `deactivate`.

## What a gate-backed skill's description may promise

Once a review skill acquires a gate hook, its `DO NOT TRIGGER` clauses stop being routing hints and start being predictions about whether an operation will be allowed. A gate decides on what it can compute — tool name, command shape, staged pathspec, marker hash. So every clause must either name a condition under which the hook's own predicate also declines to fire, or explicitly scope itself to a trigger point that has no hook behind it.

Two clause shapes cannot be honored and must not be written:

- **Judgment predicates** — "cosmetic-only changes", "a trivial one-liner". No hook can compute triviality; `require-code-review.sh` gates on staged-diff emptiness and command shape, never on the nature of the change.
- **Conversational state** — "the user has explicitly said to skip review". A PreToolUse hook sees one tool call, not the transcript.

The failure mode is uniform: the session reads the exemption, declines to run the review, and is then denied by the gate. Because the description is what the model reads *before* the skill fires, no amount of correct prose in the skill body can undo it.

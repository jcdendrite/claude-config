# Hook reference

Full descriptions for every hook in `claude/.claude/hooks/`. For the gate summary (which hook blocks which command), see the Hook → Gates → Cleared-by table in the [README](../README.md#workflow).

## Gate hooks

- **`require-plan-review.sh`** — blocks `Write`/`Edit`/`MultiEdit`/`ExitPlanMode` when an uncommitted or modified plan file exists in `.claude/plans/` and no `/plan-review` marker holds the current plan set's hash. Committed, unmodified plan files are treated as historical and pass through. Two-marker pattern: an active marker (`<config-dir>/.plan-review-active.d/<session_id>`) bypasses the gate for the skill's own Write/Edit calls during review (but not `ExitPlanMode`, which stays blocked until review is complete); a completion marker (`<config-dir>/plan-review-markers/<repo-hash>.<session_id>`) allows through once the review is clean. The completion read is two-tier: it scans this worktree's repo-hash prefix first, then — only on a miss — the repo's sibling worktrees, so a plan copied into a fresh worktree inherits the review that already covers its text. `<config-dir>` means `$CLAUDE_CONFIG_DIR` when set, else `~/.claude`. See [Marker keying and gate-release authority](#marker-keying-and-gate-release-authority) and [Gate deadlock recovery](#gate-deadlock-recovery).
- **`require-code-review.sh`** — blocks `git commit` (including chained forms like `git add . && git commit`) until `/code-review` has run on the current staged state. Verified via a sha256 marker in `<config-dir>/code-review-markers/<repo-hash>.<session-id>`, which auto-invalidates the moment the staging area changes. The read matches on the marker's stored hash across every session suffix under this repo-hash; the session key in the filename exists so two parallel sessions in the same worktree cannot overwrite each other's markers when staging different diffs. Also appends a non-blocking compliance line (`<iso8601> marker=<matched|unmatched> ledger=<present|absent>`) to `<config-dir>/.review-ledger-compliance.log` at both the allow and deny paths, timeout-guarded via `_lib_capped` — a measured signal for whether `review-ledger.sh append` (see below) is actually keeping pace with `/code-review` runs, never itself affecting the gate's decision. The log is append-only and not rotated automatically. Trim it periodically if disk space is a concern: `> <config-dir>/.review-ledger-compliance.log`.
- **`require-skill-review.sh`** — blocks `git commit` only when staged changes include a `SKILL.md`. Requires `/skill-review` to have produced a behavioral-equivalence audit for any removed or shortened lines. Marker is keyed to the SKILL.md-scoped diff (not the full staged diff), so re-staging non-skill files after a clean review does not invalidate the marker.
- **`deny-private-project-refs.sh`** — blocks `git commit`, `gh pr create`, `gh pr edit`, and mutating `gh api` calls when the staged diff, commit message, or PR title/body/body-source-file contains either (a) tracker-ID tokens (`[A-Z]{2,}-\d+`) outside an OSS-prefix allowlist (`CVE-`, `RFC-`, `GH-`, and similar — see the script for the full list), or (b) a literal substring match against entries in the user's opt-in `<config-dir>/private-projects.md` blocklist. Enforces the mechanical categories of the repo-root `CLAUDE.md` redaction rule; structural fingerprints still require review discipline. See [`docs/private-project-redaction.md`](private-project-redaction.md).
- **`deny-pii-in-commits.sh`** — two tiers, one opt-in and one always on. Blocks `git commit` (every repo, including chained forms) when the added lines of the staged diff, the commit message, or a referenced `-F`/`--file` message file contain personally-identifying/protected-health information or a credential-shaped value. The credential-value sub-check (the same GitHub-token-prefix/PEM-header regex `redact-credential-values.sh` uses) is always on, with no arming file. The SSN/Luhn-checked-credit-card built-ins and every user `<label>: <regex>` line stay dormant unless `<config-dir>/pii-patterns.md` exists as a readable regular file; `exclude: <glob>` lines in that file drop synthetic-fixture paths from the scan for both tiers. When `-a`/`--all`, a `--` pathspec, or a bare pathspec argument is present, also scans `git diff HEAD` (working-tree content committed outside the index) — unconditionally, since the credential-value tier needs it regardless of arming. Robust against `--no-verify`. The deny message names the matched pattern by label only — never the matched value or the user regex. See [`docs/security-hardening.md`](security-hardening.md).
- **`deny-data-file-reads.sh`** — opt-in. PreToolUse `Read` gate that refuses data-shaped files before their content enters Claude's context. Dormant unless `<config-dir>/data-file-read-guard.md` exists as a readable regular file. Once armed, denies `Read` of a data-file extension (`.csv`, `.parquet`, `.sqlite`, `.xlsx`, and similar), a path under a `Downloads/` directory, a file over 5 MB, or any path matching a glob line in the config file. No bypass valve. See [`docs/security-hardening.md`](security-hardening.md).
- **`deny-credential-bash-reads.sh`** — always on, no arming file. PreToolUse `Bash` gate that denies any command whose raw text contains a credential-shaped path token: an SSH private key basename (`id_` followed by `rsa`, `dsa`, `ecdsa`, or `ed25519`, excluding the `.pub` public-key variant), `.netrc`/`_netrc`, `.git-credentials`, a cloud credential store (`~/.aws/credentials`, `~/.docker/config.json`, `~/.kube/config`, `~/.config/gh/hosts.yml`), or a non-template `.env` variant/`credentials.json`. Matches case-insensitively and on the bare basename anywhere in the command, not only when directory-qualified — the case-insensitive match closes a bypass on any case-insensitive-but-case-preserving filesystem (macOS APFS/HFS+, Windows NTFS), where an uppercase-variant basename opens the identical on-disk file as its lowercase form. Carries no content-exposing-verb carve-out — `ssh-add`, `chmod`, and `ssh -i` against a credential path are denied too, the accepted false-positive cost of a path-token-only match with no bypass valve. An optional `<config-dir>/credential-file-guard.md`, same glob grammar as `data-file-read-guard.md`, adds personal/org-specific path tokens, matched case-insensitively too (a scoped `shopt -s nocasematch` around the glob match, since bash `case` has no per-pattern case-fold syntax). See [`docs/security-hardening.md`](security-hardening.md).
- **`deny-credential-file-reads.sh`** — always on, no arming file. PreToolUse `Read` sibling to `deny-credential-bash-reads.sh`, using the same built-in credential-path shapes (case-insensitively matched, same rationale) against `tool_input.file_path`. Resolves symlinks via `readlink -f` before allowing (same fail-closed-on-unresolvable-or-missing-target posture as `deny-env-reads.sh`'s own symlink defense) — since this hook has no allowlist, every symlinked Read target is resolved and checked, not only ones whose own name already looks credential-shaped. Same optional `<config-dir>/credential-file-guard.md` additions file as `deny-credential-bash-reads.sh`. See [`docs/security-hardening.md`](security-hardening.md).
- **`deny-escaped-backticks-in-pr-body.sh`** — blocks `gh pr create` and `gh pr edit` when the PR body (inline `--body` or any body-source file passed via `--body-file`/`-F`/`--template`/`-T`) contains literal backslash-backtick sequences (`\``). Those sequences appear when a `<<'EOF'` single-quoted heredoc writer unnecessarily escapes a backtick — the backslash survives into the rendered GitHub body and breaks code-span formatting. Fails closed when a body-source file is unreadable or a pseudo-file path (`-`, `/dev/stdin`, `/dev/fd/*`).
- **`block-gh-pr-merge.sh`** — blocks every shape of `gh pr merge` (bare, with flags, `--auto`, `--squash`/`--merge`/`--rebase`, paren-grouped chains, `&&`-chained, trailing-semicolon forms) and instructs the agent to surface the merge intent to the engineer. Enforces the repo-root CLAUDE.md rule **AI agents: don't merge your own PRs** at the tool-call boundary. No bypass marker — the engineer runs `gh pr merge` themselves (or via the `!` shell escape). Word-boundary regex `(^|[[:space:]])gh[[:space:]]+pr[[:space:]]+merge([^a-zA-Z0-9_]|$)` matches verb-anchored, so `gh pr mergefoo` and quoted/commented `gh pr merge` text do not match.
- **`require-stow-reminder.sh`** — scoped to the `claude-config` repo. Blocks `gh pr create` and `gh pr edit` (when the edit changes the body) if the PR adds a new immediate child of `claude/.claude/` (file or directory) and neither the inline command, a referenced `--body-file`/`--template`, nor any `--fill`-sourced commit message mentions `install.sh` or `stow` (case-insensitive). Reason: GNU Stow links each top-level child of `claude/.claude/` individually, so a brand-new child only appears in `~/.claude/` after re-running `install.sh` — `git pull` alone won't materialize the symlink. The reminder lands in the PR body so the post-merge stow step doesn't get forgotten at merge time.
- **`require-respond-pr.sh`** — blocks PR/issue comment reads and posts and redirects to `/respond-pr`, so all three comment types get fetched and replies carry the `[Claude Code]` attribution prefix. The gated surface is `gh api .../pulls|issues/N/{comments,reviews}`, the un-numbered comment-ID endpoint `gh api repos/O/R/pulls|issues/comments/ID`, `gh pr comment`, `gh pr review`, `gh issue comment`, and the GraphQL comment/review mutations plus file-sourced GraphQL bodies. Reads and writes are gated asymmetrically: a command that explicitly names a repo other than the current `origin` is released as external research, but only when it carries no write signal — writes are denied for every repo, because the attribution prefix is owed to readers of any public thread. Honors a per-session bypass marker at `<config-dir>/.respond-pr-active.d/<session_id>` that the skill sets on entry and removes on exit; the hook checks `kill -0` against the stored PID on each gate hit; a dead PID evicts the orphaned marker automatically. Per-session keying (rather than a singleton path) keeps parallel Claude sessions from thrashing on cleanup or leaking bypass to unrelated sessions.
- **`require-ready-for-review.sh`** — gates `git push` and `gh pr ready` on branches with an open PR. Requires `/ready-for-review` to have run and passed since the last commit. Verified via a marker whose content is the HEAD SHA the gate ran against — a new commit invalidates the marker automatically and forces a re-run. An active-skill bypass marker (`<config-dir>/.ready-for-review-active.d/<session_id>`) prevents the skill's own iteration pushes (fix → push → loop) from self-denying.
- **`require-worktree-for-git-writes.sh`** — opt-in per repo or per machine. When active, denies non-read-only git operations unless the session runs in a linked git worktree. Prevents concurrent Claude Code sessions from racing on the same working tree. A git command that resolves into a linked worktree passes through `_lib_worktree_collision_guard` (`_lib.sh`) whenever that worktree's lock is already held, denying when a *different* live session holds it; only a write can cause the guard to freshly acquire the lock. When the full-parsing path's own collision-guard call is what freshly acquired the lock (a plain `[ -e ... ]` pre-check on the lock file before the call), the allow carries an `additionalContext` note naming the reacquisition and the `git worktree unlock <path>` remedy if unintended. A self-lock reentry (the lock was already this session's) stays silent, and so does every prior allow. A read never acquires the lock, regardless of which path evaluates it. See the "Worktree enforcement" section of [the README](../README.md).
- **`require-worktree-for-file-writes.sh`** — opt-in per repo or per machine (same sentinel files). When active, denies `Edit`/`Write`/`MultiEdit` on paths in the main working tree; all file edits must land in a linked worktree. Paths under `$HOME/.claude/` are always exempt — the harness and skills write plans, memory, settings, and other infrastructure files there as normal operation, and `~/.claude/` may resolve via stow directory-folding into an opted-in checkout. Also runs the same `_lib_worktree_collision_guard` check as `require-worktree-for-git-writes.sh` before allowing a write into an already-linked worktree, with the same fresh-acquire `additionalContext` note on the same pre-check basis.
- **`deny-reviewer-tree-mutation.sh`** — always on (no worktree-enforcement opt-in required). Denies `Bash`/`Write`/`Edit`/`MultiEdit` from the closed set of review-only agents (`ciso-reviewer`, the seven `staff-*` personas, the non-specialist reviewers `skill-fidelity-reviewer` and `comment-discipline-reviewer`, `Explore`, `Plan`) that would mutate the tree under review: git writes, `Write`/`Edit`/`MultiEdit` outside `/tmp` or an `agent-reviews/` findings path, and a closed in-place-edit-tool family split into two tiers — pure formatters denied on any invocation regardless of flags (`black`, `isort`, `gofmt`, `prettier`, `rustfmt`, `terraform`/`tofu fmt`), and dual-use linters/text tools denied only in their write form (`sed -i`/`perl -i`, `eslint --fix`, `ruff format`/`ruff check --fix`). An `agent-reviews/*` write is exempted only after confirming with `git check-ignore` that the directory is actually ignored in the target repo — a stale worktree-local `info/exclude` or a repo with no ignore entry denies rather than silently allowing an unignored findings file through. Every other agent (main session, `code-writer`, `general-purpose`) passes through unconditionally.
- **`deny-repo-relocation.sh`** — always on (no worktree-enforcement opt-in required; not scoped to this repo — it protects whichever claude-config checkout it is stowed from, regardless of which repo the session is working in). Denies a `Bash` `mv` or `rsync --remove-source-files` command whose resolved source argument is this claude-config checkout's root or an ancestor of it — moving or renaming the checkout breaks every stow symlink under `~/.claude/` and `~/.local/bin/` at once, with nothing left running that could detect or explain the failure. Points at `relocate-claude-config` (see [`docs/scripts.md`](scripts.md)) as the supported command instead. Self-locates the protected root from its own physical path (`readlink -f "$0"`), not from cwd, so it fires correctly no matter which repo's Bash call it's evaluating. Best-effort, not a hard security boundary: a source argument reached only through a shell variable, command substitution, or a preceding `cd` in the same command fails OPEN (allow) rather than deny, and equivalent-relocation forms outside the `mv`/`rsync` pattern (`cp -r && rm -rf`, `python3 -c "os.rename(...)"`, a GUI/Finder move) aren't covered at all — see the [README "Repo relocation"](../README.md#repo-relocation) section and the hook's own header for the full known-gaps list and why the destination-side validation in `relocate-claude-config` is where this design's actual security investment goes.
- **`deny-network-installs.sh`** — always on, no arming file, no bypass valve. Denies a `Bash` command that installs a named package via `npm`/`pnpm`/`yarn`/`bun`/`pip`/`pip3`/`uv pip`/`uv add` (a manager and install verb both present, with an unrecognized-as-restore argument left over after removing flags and known restore markers like `-r`/`--frozen-lockfile`), an `npx`/`bunx`/`uvx`/`pipx run`/`npm exec` invocation carrying an explicit `-y`/`--yes` skip-confirmation flag, `pnpm`/`yarn dlx` unconditionally (no local-resolution ambiguity to disambiguate, unlike npx), or a command that hands fetched content to a shell/interpreter (`curl`/`wget` co-occurring with `bash`/`sh`/`zsh`/`python3`/`python`/`node`/`ruby`/`perl` anywhere in the same call, including via `bash -c "$(curl …)"` or process substitution). Matches on token presence, not on resolving "the" leading command — position-based resolution misses pnpm/yarn/bun (its runner-skip list treats them as wrappers), `bash -c "$(curl …)"` (produces a trailing empty fragment), and is sensitive to wrapper/assignment ordering; presence has none of these gaps, since no wrapper removes a token from the command string. Command text is quote-stripped before matching, closing a false-allow (`"npm" install lodash` runs identically to the unquoted form) at the cost of a uniform, accepted over-deny on any text argument merely mentioning an install shape (a `grep` pattern, a commit message). Named residuals: bare `npx`/`bunx`/`uvx`/`pipx`/`npm exec` (no `-y`/`--yes`), and `pip install -e <VCS-URL>`. See [`docs/security-hardening.md`](security-hardening.md) for the full list.
- **`guard-settings-session-keys.sh`** — blocks `git commit` when `claude/.claude/settings.json` has staged changes to `model`, `effortLevel`, `skipAutoPermissionPrompt`, or the same `model`/`effortLevel` values written nested under `env.ANTHROPIC_MODEL`/`env.CLAUDE_CODE_EFFORT_LEVEL`. These are session-scoped or Claude-Code-auto-written preferences that should not be committed to the shared config; for `model`/`effortLevel`, use `ANTHROPIC_MODEL`/`CLAUDE_CODE_EFFORT_LEVEL` env vars or `/effort max` mid-session instead.
- **`check-skill-length.sh`** — blocks `git commit` when a staged `SKILL.md` exceeds 200 lines and grew vs HEAD. Nudges toward splitting a growing skill or moving reference material to a co-located `REFERENCES.md`.
- **`check-claude-md-length.sh`** — blocks `git commit` when a staged `CLAUDE.md` or `AGENTS.md` (repo root or any `.claude/`-scoped path) exceeds 200 lines and grew vs HEAD. Same shape as `check-skill-length.sh`, but also covers `AGENTS.md`.
- **`require-memory-skill.sh`** — PreToolUse `Edit|Write|MultiEdit` gate on `<config-dir>/projects/*/memory/MEMORY.md` and new memory topic files under that path. Requires an active `/ai-instruction-and-memory-files` per-session marker before allowing writes, ensuring index format and frontmatter rules are applied.
- **`require-routing-read.sh`** — PreToolUse `Agent` gate active during a running `/plan-review` session. Denies subagent spawn until `~/.claude/skills/plan-review/ROUTING.md` has been read (tracked by `log-routing-read.sh`), ensuring reviewer routing consults the full ownership table before any specialist is spawned.
## Utility hooks

- **`capture-session-id.sh`** (SessionStart, SubagentStart) — at session and subagent start, writes the session's `session_id` to `<config-dir>/sessions/<claude-pid>` so skills running as Bash tool calls (which don't see the hook payload) can look up their own session id by walking process ancestors from the bash tool's `$PPID` (`marker.sh`'s `_walk_session`) until it reaches this file. `<claude-pid>` is the hook's own `$PPID`, optionally overridden by `$CLAUDE_PID` when Claude Code exports it and it names the same process or its immediate parent. Used by both `/respond-pr` and `/code-review` to compute per-session marker filenames. Rewritten at every `SessionStart` and `SubagentStart` under the resolved PID (covers `/clear`, where one session ends and another starts in the same process); nothing deletes it on session exit, so a bare-PID file from a session, resume, or one-shot run lingers until its PID is reused. Unlike `nudge-worktree-anchor.sh` and `advance-past-commit-stall.sh` below, this file gets no time-based self-sweep: an mtime sweep can't tell a stale entry from a still-live long-running session's own entry — growth is bounded only by PID reuse.
- **`nudge-handoff-near-context-cap.sh`** (PostToolBatch + Stop, `batch-gate`) — injects an `additionalContext` reminder to consider `/handoff` as carried context nears the compaction cap. PostToolBatch fires during autonomous tool-call stretches so the nudge isn't limited to human-interaction boundaries; Stop stays registered alongside it as a safety net for a toolless final turn. Past `HANDOFF_NUDGE_BLOCK_AFTER` ignored re-arms in one session, a further re-arm hard-blocks (stderr + exit 2, PostToolBatch's own native loop-stop) instead of staying advisory — unless a live `/handoff` active-bypass marker for that session keeps the re-arm advisory instead. Opt-out via `<config-dir>/.handoff-nudge-disabled`. Also runs as a read-only query — `nudge-handoff-near-context-cap.sh --check` reports the session's current estimate and threshold as JSON, writing no marker and no log line, which is what `plan-it` Step 7 and the `handoff` skill act on. See [`docs/handoff-nudge.md`](handoff-nudge.md) for the threshold, marker mechanics, log format, escalation ladder, and the `--check` contract.
- **`nudge-error-mode-analysis.sh`** (UserPromptSubmit, advisory, opt-in) — injects a one-shot `additionalContext` suggestion to run `/error-mode-analysis` once in-session friction signals cross a threshold. Dormant unless `<config-dir>/.error-mode-nudge-enabled` exists. See [`docs/error-mode-nudge.md`](error-mode-nudge.md) for the threshold, signal composition, and marker mechanics.
- **`nudge-worktree-anchor.sh`** (UserPromptSubmit, advisory) — reports via `additionalContext` when the session's working directory is the **main** working tree of a repo with worktree enforcement active while a linked worktree exists on disk. Silent in every other state, including an opted-in repo with no worktree yet (the normal state just before `git worktree add`). Re-arms rather than firing once per session: anchor state is not monotonic, so its per-session state file records the tree last reported and is cleared whenever the condition stops holding, letting a genuine drift-back-out be reported again. Advisory only — a hook cannot change a session's working directory, so re-anchoring is left to the agent's `EnterWorktree` call. Exits 0 on every path and bounds every git call with `_lib_capped`, since a `UserPromptSubmit` hook runs on the per-turn hot path. Sweeps entries older than 30 days from its own state dir on every transition into the drifted state — a non-atomic per-file `find -delete` loop, so an interruption mid-sweep leaves only the not-yet-visited stale entries behind, retried harmlessly on the next transition.
- **`nudge-unexpanded-skill-mention.sh`** (UserPromptSubmit, advisory) — reports via `additionalContext` when a prompt names an installed skill (`/<name>`) outside the leading command run, asking the agent to check with the engineer before invoking it. Slash-command expansion is anchored to message start — as of v2.1.199 the harness expands a leading chain of up to six skills — so a skill named later in the prompt is inert text that loads nothing unless the agent notices unaided. Resolution never runs `git`, `find`, `ls`, a glob, or `eval`: the project skills root comes from a pure-bash ancestor-directory walk from `cwd`, and each candidate is tested with an exact `[[ -f "$dir/$token/SKILL.md" ]]`. A captured token is re-validated against `^[A-Za-z0-9_-]+$` immediately before it builds a path, mirroring `_lib_valid_session_id_component`'s re-check at point of use, so partly-untrusted prompt text (pasted issues, logs, web content) can neither traverse outside the two resolution roots nor reach a shell built-in; only the validated token is ever echoed back. The scanned prompt is truncated to a fixed byte cap so a multi-megabyte paste cannot slow the per-turn hot path. Fenced code blocks and inline backtick spans are stripped before scanning, using POSIX-portable constructs so BSD and GNU userlands behave identically. Keeps no dedup state and no enable/disable sentinel — every qualifying mention fires and the only kill switch is editing `settings.json`, both deliberate engineer decisions. Exits 0 on every path, including missing `jq`, an unreadable `_lib.sh`, an unresolvable config dir, and malformed stdin. Known gaps it does not close: plugin skills (`plugin:skill`) never resolve, and unquoted prose that merely discusses a skill still fires as an accepted false positive.
- **`nudge-transcript-toolkit.sh`** (PostToolUse, `Edit|Write|MultiEdit`, advisory) — reports via `additionalContext` when the content just written to a `.py`/`.sh` file looks like a hand-rolled transcript-corpus glob (a `projects/*/*.jsonl` shape), naming `transcript-analysis.py` and its union-across-declared-roots default (`~/.claude/transcript-config-dirs`). Inspects post-write content only — `Write`'s `content` verbatim, `Edit`'s `new_string` alone, or a single-entry `MultiEdit`'s lone `edits[0].new_string` (a glob split across multiple `edits[]` entries is a documented residual, not reconstructed). Suppressed on this toolkit's own tree in both the repo-source shape (`claude/.claude/scripts|hooks|tests/`) and the stowed shape (tied to `_lib_config_dir`'s resolved `scripts/hooks/tests`, not a bare `.claude/scripts/` substring, so an unrelated project's own `.claude/scripts/` isn't suppressed too). Documented residuals: path components assembled via `os.path.join(...)`, a glob shape built from variable/f-string interpolation rather than written as a literal path segment, and any extension other than `.py`/`.sh` (deliberate — 13 `.md` files in this repo discuss the pattern and must never fire). Never denies; a miss costs nothing and a false positive costs one line of context.
- **`advance-past-commit-stall.sh`** (Stop, `turn-gate`) — opt-in. Forces forward progress past a commit/push/PR-open permission-question stall (GH-526) when `_lib_autonomous_shipping_active` holds for the resolved repo. Fires only on the main session (never a subagent), only once per user turn (re-arms on a new `prompt_id`), and only when the final sentence of the last assistant message asks permission to commit/push/open a PR (phrasing-matched, case-insensitive) without also carrying an exclusion phrase (`merge`, `--force`, `failing`, etc.), and work is actually pending (a dirty tree, HEAD ahead of its configured upstream, or — the common state before a branch's first push — no upstream configured at all). Emits `{"decision": "block", "reason": …}` to force the same turn to continue rather than end. Kill switches: `<config-dir>/.commit-stall-block-disabled` (always-effective) and `<repo>/.claude/autonomous-shipping-optout` (repo-scoped). Sweeps entries older than 30 days from its own state dir on every fire, since `claude -p` one-shot invocations never fire `SessionEnd` to clean up their own state file. See [`docs/commit-stall-block.md`](commit-stall-block.md) for the fire predicate's design history, known limitations, and log format.
- **`ask-review-permissions.sh`** — asks before `Edit`/`Write`/`MultiEdit` to `.claude/settings*.json`, nudging toward `/review-permissions` when the edit touches `permissions.allow`.
- **`ask-new-dependency-disclosure.sh`** — asks before an `Edit`/`Write`/`MultiEdit` to a recognized manifest (`package.json`, `requirements*.txt`, `go.mod`, `Gemfile`, `Cargo.toml`, `pyproject.toml`) adds a dependency not already declared, naming each `name@constraint` pair — backs `claude/.claude/CLAUDE.md`'s "Name every new package before it is fetched" duty. Reconstructs the post-write manifest text from `tool_input` (`Edit`'s `old_string`→`new_string`, `MultiEdit`'s `edits` applied sequentially against a running buffer, `Write`'s `content` verbatim) and diffs its declared dependency names against the on-disk pre-state via `parse-manifest-dependencies.py` (Python >= 3.11 floor, since `Cargo.toml`/`pyproject.toml` parsing needs stdlib `tomllib`), and caps the listed names at 10 with an "…and N more" marker. Silent allow when the tool isn't `Edit`/`Write`/`MultiEdit`, the basename isn't one of the six recognized manifest names (case-sensitive), the path sits under `node_modules/`/`fixtures/`/`__fixtures__/`/`test-data/`, `python3` is absent or unusable (e.g. the Xcode Command Line Tools shim), or the diff is empty. Degrades to a generic ask naming no packages — rather than silent allow — when the on-disk manifest is over 5 MB, the helper errors/times out/emits unparseable output, or a present-but-usable `python3` falls below the 3.11 floor (a broken install, not an expected runtime state), since a too-large or malformed manifest is agent-authored content and silence there would be a one-step-suppressible reminder. A `requirements*.txt`'s `-r`/`-c` include is not followed — only the edited manifest's own text is diffed, never a file it references. Best-effort and `informational`, not a deny-class gate; no repo-scoped opt-out. See [`docs/security-hardening.md`](security-hardening.md).
- **`session-marker-dashboard.sh`** (SessionStart, matcher `startup|clear|compact|resume`) — at session start, emits a summary of any active bypass markers (`/respond-pr`, `/ready-for-review`) into the resumed session's context so stale bypasses are visible. Also folds in a review-narrative ledger summary (finding/addressed/deferred counts) when the resuming session's `review-narrative-ledger/<repo-hash>.<session-id>.jsonl` (see `review-ledger.sh` under `claude/.claude/scripts/`) is non-empty — resolved from the payload's `.cwd` field, keyed the same way `review-ledger.sh` keys writes. Gated on `~/.claude/.review-narrative-ledger-disabled`; the marker-status half of this hook stays always-on and ungated. The `resume` matcher value covers a genuine `--resume`/`--continue` session resume, the case the CLAUDE.md fallback instruction (see Safety section) names.
- **`restore-authorization-boundary-on-compact.sh`** (SessionStart, `matcher: compact`) — re-states the irreversible-action authorization boundary as `additionalContext` after compaction discards it, so the harness-generated summary's "Optional Next Step" section isn't misread as engineer sanction. Advisory only — it gates nothing. Names an illustrative, non-exhaustive subset of `handoff/SKILL.md` §3.5's shapes. Does not fire on `clear`, since an emptied context asserts no next step. Kill switch: `~/.claude/.authorization-boundary-disabled`.
- **`check-branch-divergence.sh`** (SessionStart, `matcher: startup`) — surfaces feature-branch divergence from `origin/<default>` as `additionalContext`. Skips silently when not in a repo, on the default branch, on detached HEAD, with no `origin` remote, or with `origin/HEAD` unresolvable. Runs a bounded `git fetch` (`timeout 2 git fetch …` with `GIT_TERMINAL_PROMPT=0` to suppress credential prompts), then `git rev-list --count HEAD..origin/<default>` for the behind count and `git merge-tree --write-tree` for the trial-merge prediction. Falls back to the locally-cached `origin/<default>` ref with a stale-ref suffix when the fetch fails, times out, or no portable timeout wrapper is available (macOS without `gtimeout`). Quiet-on-success — emits nothing when behind = 0. Advisory only; never blocks, never acts. Resolution is delegated to `/git-feature-branch-sync`. Matcher is `startup` only (not `startup|clear|compact`) because divergence is on-disk state, not session-scoped.
- **`set-session-title-from-branch.sh`** (SessionStart, `matcher: startup`) — sets the terminal tab title (`hookSpecificOutput.sessionTitle`) to `<repo>/<branch>` from git state, replacing the auto-titler's summary of the first prompt on feature-branch and detached-HEAD sessions. Emits nothing (auto-titler runs as today) when: not a git repo; on the repo's default branch; the default branch is undeterminable (no `origin` remote, `origin/HEAD` unset, or a dangling `origin/HEAD` symref); the main worktree is bare; or either the repo-directory or branch component fails the `^[A-Za-z0-9._/@+-]+$` allowlist, matched under `LC_ALL=C` specifically (outside the C locale, bracket-range matching is collation-order and admits non-ASCII characters and C1 control bytes into `[A-Za-z]`). Detached HEAD titles as `<repo>/@<short-sha>`; the branch component truncates to 32 chars. Reads the payload's `.cwd`, not process cwd, so a session anchored in a linked worktree titles from that worktree's branch. Resolves `<repo>` from the basename of `git worktree list --porcelain`'s first (always main, per `git-worktree(1)`) record — not skipped for `--separate-git-dir` layouts (no `bare` attribute), though on git 2.55.0 that record names the relocated git-dir rather than the working directory in that layout; skipped for bare ones. Kill switches: machine-global `<config-dir>/.session-title-disabled` and per-repo `<main-worktree-root>/.claude/session-title-disabled`. A repo with no `origin` remote, or a stale `origin/HEAD` (e.g. after a `master`→`main` rename), never resolves a default branch correctly — remedy with `git remote set-head origin -a`.
- **`enforce-marker-script-shape.sh`** — PreToolUse gate wired on both the `Bash` and `Edit|Write|MultiEdit` matchers, with two jobs. First, it denies writes to review-marker state from any agent type in `_LIB_NO_GATE_RELEASE_AGENTS` — the review-only personas plus `code-writer` — since none of them could have run the review a gate demands. Marker state is reachable three ways and all three are gated: a `Write`/`Edit`/`MultiEdit` targeting a path under `<config-dir>/*-markers/` or `<config-dir>/.*-active.d/` (matched on the resolved path, so shell indirection does not apply); a `Bash` call carrying `marker.sh write`/`activate`; and a `Bash` call reaching a marker path via `>`/`>>`/`&>`/`&>>`/`<>`, `tee`, `cp`/`mv`/`install` (last-argument form), `dd of=`, or `sed -i` without ever mentioning `marker.sh` — a dedicated scan that runs before the `marker.sh`-shape check, resolving each candidate through the same tilde-expand → realpath → marker-shape match the Write/Edit arm uses. `deactivate` and `clear-stale` stay available because they re-arm gates rather than release them. Second, on the `Bash` surface only, it denies any `marker.sh` invocation not exactly matching the allowlisted shape pattern (`~/.claude/scripts/marker.sh <subcommand> <skill>`). Chains of individually-valid marker.sh operations joined by `&&` are permitted (capability-neutral — each op is independently allowlisted or harmless); chains to any other command (except the blessed `git commit` tail), `||`/`;` separators, redirects, and extra arguments remain denied. Defense-in-depth against prompt-injection escalation through the `marker.sh` allow rules. See [Marker keying and gate-release authority](#marker-keying-and-gate-release-authority).
- **`deny-env-reads.sh`** — PreToolUse `Read` gate that allows `.env.example`, `.env.template`, and `.env.sample` (including symlink-resolved targets) while denying all other `.env`/`.env.*` paths. Extends the static `permissions.deny` entries documented in [`docs/auto-mode.md`](auto-mode.md) to cover `.env.*` variants not listed there.
- **`log-routing-read.sh`** — PostToolUse `Read` companion to `require-routing-read.sh`. Writes a per-session routing-read marker when `~/.claude/skills/plan-review/ROUTING.md` is read during an active `/plan-review` session.
- **`consume-durable-continuity-file-on-read.sh`** — PostToolUse `Read` hook that moves a `/handoff` or `/brief` continuity file (`<config-dir>/handoffs/*-handoff.md`, `<config-dir>/briefs/*-task.md`) out via `resume-context.sh --consume-only` whenever it's read directly — the same-session resume path (`/clear` then manually reading the file) that never invokes `resume-context.sh`'s own launch mode. Fail-open (never blocks; a crashed or timed-out consume just leaves the file in place). The `resume-context.sh` call is wrapped in a 5s `timeout` (falls back to a bare call when `timeout(1)` is absent) since it runs synchronously inside the triggering `Read` call — guards against a hung network-backed `$HOME`. On a successful consume the destination is reported on two channels: a `systemMessage` for the human, and `hookSpecificOutput.additionalContext` for the model — the agent that just had its own file moved has no other way to learn where it went, since `systemMessage` reaches the user only. On-by-default; opt out per-machine by touching `<config-dir>/.consume-durable-continuity-disabled`, mirroring `nudge-handoff-near-context-cap.sh`'s kill-switch convention. See [`docs/scripts.md`](scripts.md) for `resume-context.sh` itself.
- **`redact-credential-values.sh`** — always on, no arming file. PostToolUse hook on `Bash|Read|WebFetch|Grep|Task` that scans each tool's own result for credential-*value* shapes with a vendor-fixed format (a GitHub token prefix, a full PEM private-key block) and replaces every match with `[REDACTED-CREDENTIAL]` via `updatedToolOutput` before the model's next turn consumes it — the backstop for a credential entering context through a path neither `deny-credential-bash-reads.sh` nor `deny-credential-file-reads.sh` anticipates (a `WebFetch` body, a `Grep` match, subagent-returned text). This is narrower than the path gates' credential coverage: it does not recognize a `.netrc` plaintext password, a `.git-credentials` URL, an AWS `credentials` file's secret key value, a Docker `config.json` auth blob, or a Kubernetes `config` bearer token/cert — none of those have a fixed, vendor-documented shape to match against. The path gates are what actually stop those credential families from entering context. Redaction is shape-agnostic: a recursive `jq walk` rewrites every string leaf of `tool_response` regardless of its structure, so it works uniformly across tool shapes without needing a hardcoded field name per tool. Content over the 5 MB size cap (shared with `deny-data-file-reads.sh`) is left unscanned. Fails open on any parse failure — an informational hook, it never emits a deny decision. An optional `<config-dir>/credential-value-patterns.md`, same `<label>: <regex>` grammar as `pii-patterns.md`, adds personal/org-specific value patterns. See [`docs/security-hardening.md`](security-hardening.md).
- **`track-permission-prompts.sh`** (`Notification`, matcher `permission_prompt`) — opt-in. Appends the raw `Notification` payload — run through the same credential-value redaction walk as `redact-credential-values.sh` (extracted to the shared `_lib_redact_credential_shaped_strings`), plus one added `logged_at` field — to `<config-dir>/.permission-prompt-log.jsonl`, so a developer running in `auto` permission mode can see which commands still trigger an interactive prompt. Dormant unless `<config-dir>/track-permission-prompts` exists. Self-checks `hook_event_name == "Notification"` rather than relying solely on the settings.json matcher. `chmod 600`s the log file on every append, since a plain `>>`-created file would otherwise inherit the checkout directory's `755`/`644` permissions. No per-repo opt-out — see [`docs/permission-prompt-tracking.md`](permission-prompt-tracking.md) for the log format and known limitations, including the undocumented `Notification` payload schema this hook works around by logging the payload verbatim rather than an assumed field list.

## Non-hook opt-in/opt-out sentinels

Not every opt-in or opt-out sentinel gates a hook. `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/pr-cost-disclosure` and `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/pr-description-tighten-prose-optout` each gate a step inside the `pr-description` skill itself (see `claude/.claude/skills/pr-description/SKILL.md`'s "Cost section" and "Prose tightening pass") — no `PreToolUse`/`PostToolUse` hook is involved, so neither appears in the lists above. Documented here anyway, since this file is where every opt-in/opt-out sentinel in this repo is meant to be discoverable — `install.sh`'s `report_sentinel_inventory` surfaces both at install time from the same inventory.

Unlike a presence-only sentinel (`worktree-required`, `autonomous-shipping-required`), `pr-cost-disclosure`'s content is a **mode**, not just a presence check: exactly `dollars` enables the `## Cost` section; absent, empty, or any unrecognized value disables it. It is also scoped to the Claude account rather than to the repo — cost is an organizational fact, and each account is its own billing entity — so it lives outside any repo's working tree at `$CLAUDE_CONFIG_DIR` (when set and absolute) or `$HOME/.claude`, resolved to exactly one of those paths and never both. Resolving only one path is what keeps one account's opt-in from activating disclosure under another.

The fields it discloses (session count, priced-turn count, per-class token volume, per-model-ID dollars) are not neutral even in aggregate form — see `docs/transcript-analysis.md`'s `cost` section, "The disclosed fields are not neutral."

Account scoping has one residual travel path, accepted rather than closed: bootstrapping a new Claude account by copying an existing `$CLAUDE_CONFIG_DIR` tree carries the sentinel forward into the new account with no prompt. `install.sh`'s account row reports the resolved path and mode at every run, so an operator inspecting a freshly bootstrapped account sees an inherited file rather than having to suspect one.

### Prose tightening opt-out

`pr-description-tighten-prose-optout` gates the `## Prose tightening pass` section: dispatching `tighten-prose` against a drafted PR body before the reader-coherence and content-claim checks run. Presence-only, like `worktree-required` — but where every other sentinel in this inventory is opt-in (absent = off, present = on), this one is opt-out: absent means the pass runs, present means it's skipped.

Scoped to the Claude account, not the repo, for the same reason as `pr-cost-disclosure`: a writing-style preference is a personal, cross-repo choice, not a per-project one. Resolves the same way — `$CLAUDE_CONFIG_DIR` when set and absolute, else `$HOME/.claude`, never both.

## Marker keying and gate-release authority

Two properties govern every review gate. They pull in opposite directions and are easy to conflate.

**What a marker's filename means vs. what its content means.** A completion marker lives at `<markers-dir>/<repo-hash>.<session-id>`, and its *content* is a hash of exactly the state that was reviewed — the staged diff for `/code-review` and `/skill-review`, the active plan set's paths-plus-contents for `/plan-review`, the HEAD sha for `/ready-for-review`. The content is the authorization: it is what proves a review covered this state, and it is what re-arms the gate the moment the state changes. The session id in the filename is a *write-side* key only — it keeps two parallel sessions in the same worktree from overwriting each other's markers. Gates therefore match on content across every session suffix under the repo-hash, and a review still covering the current state keeps counting after a resume, a `/clear`, or a handoff to a parallel session. The repo-hash stays part of the read: an identical staged diff or plan text in an unrelated repository was reviewed against different code. A resumed session gets a new session id, so a marker filename quoted from before the resume — e.g. one copied into a handoff brief — no longer names the current session's own marker. To locate the current session's marker file for manual inspection, resolve the id fresh with `marker.sh resolve-session-id` rather than trusting a quoted filename — the gate itself is already unaffected by which session id is current (see above).

`require-plan-review.sh` widens that one step further, to the current repository's own worktrees. A plan's hash covers repo-*relative* paths, so a plan copied into a fresh worktree hashes identically, and the gate honors a review performed in any sibling worktree. Two tiers keep the cost off the common path: the current worktree's repo-hash is checked first (one `sha256sum`), and the worktree enumeration runs only after that misses — i.e. only when the gate is about to deny anyway. A tier-2 hit authorizes content-identity of the plan *text*, not state-identity of the sibling's checkout: two worktrees on divergent branches holding byte-identical plan files do cross-validate.

**Which tree a marker describes.** The repo-hash is derived from a resolved repo root, so one repository checked out at a main tree and at a linked worktree yields two different keys — deliberately, since a review of one tree is not a review of the other. That makes the resolution step load-bearing on both sides of the gate. The reading gates (`require-code-review.sh`, `require-plan-review.sh`, `require-skill-review.sh`) resolve the root from the hook payload's `.cwd` and thread that one root through every subsequent git call, so a hook's marker path and the state it hashes always describe the same tree. `marker.sh` receives no payload and so has no trusted directory to import; it fails closed instead, refusing to write any completion marker while worktree enforcement is active, its resolved root is the repo's main working tree, **and** a linked worktree exists on disk — naming that worktree as the re-anchoring target in the refusal. The worktree-existence check must run symmetrically: with no linked worktree, a main-tree marker is correct by definition (there is no second tree to confuse it with), so denying unconditionally would instead block ordinary main-tree git activity that never passes through these hooks (the worktree hooks gate tool calls, not ambient git state — hand-staged edits and CI checkouts stay unaffected). Symmetry matters because without it, a session anchored in the wrong tree would write and then satisfy a gate describing a tree nobody reviewed.

**Who may release a gate.** Releasing a gate requires having run the review it demands. No agent in `_LIB_NO_GATE_RELEASE_AGENTS` — the review-only personas plus `code-writer` — could have run one: the file-backed personas declare no `Skill` tool and cannot invoke a review skill at all, and the two harness built-ins (`Explore`, `Plan`) are dispatched read-only by mandate — which holds whether or not the harness grants them `Skill`, since this repo ships no frontmatter for either and so cannot check. Either way a marker written by one asserts a review that could not have happened. Because `marker.sh` resolves the session id by walking the process ancestor chain to the Claude main process, such a write is indistinguishable from the parent session's and releases the gate for the whole session, not just the subagent.

`enforce-marker-script-shape.sh` enforces this by keying on **marker state**, not on command text, because marker state is reachable from three tool surfaces and gating any one alone leaves the property false:

- **`Write`/`Edit`/`MultiEdit`** targeting a path under `<config-dir>/*-markers/` or `<config-dir>/.*-active.d/`. This is the load-bearing arm — every agent in the set carries the `Write` tool, so without it a subagent could simply write the marker file directly and never invoke `marker.sh`. It matches the resolved target path (tilde-expanded and normalized), so no shell-level construct evades it.
- **`Bash`** carrying `marker.sh write` or `marker.sh activate`, checked before the hook's own shape validation so wrapped and chained invocations are covered. This arm necessarily matches command text and therefore has a scope limit, stated rather than implied: shell indirection that separates `marker.sh` from the operation keyword — assigning the path to a variable, or wrapping the call in a function — is not matched here, the same carve-out the shape check already documents for wrapped forms. Those forms are not pre-approved in `permissions.allow` either, so they surface as a permission prompt rather than a silent allow.
- **`Bash`** reaching a marker path without ever mentioning `marker.sh` — a `>`/`>>`/`&>`/`&>>`/`<>` redirect, `tee`, `cp`/`mv`/`install` (last-argument form), `dd of=`, or `sed -i` — via a scan that runs before the two checks above, resolving each extracted candidate through the same tilde-expand → realpath → marker-shape match the Write/Edit arm uses. This closes the "arbitrary Bash write-target" gap mechanically, for every agent type, in the cases it covers — narrower than `deny-reviewer-tree-mutation.sh`'s instruction-following-dependent backstop for the general write-anywhere case (see that hook's "Known gaps" section), but not dependent on it for marker paths specifically. Its own named residuals: `>|` (clobber-override, since the fragment splitter this scan reuses severs the literal `|` from the operator before extraction sees a whole token); `python3 -c "open(...).write(...)"` and here-doc bodies handed to an interpreter; a `$(...)`-computed target path; shell-function/variable indirection around the write utility itself; `cp`/`mv`/`install -t DIR`/`--target-directory=DIR` (destination isn't the last argument, so the last-argument heuristic misses it); a symlink whose own path text carries no literal `.claude`; beyond the first 10 `.claude`-mentioning candidates in one command (`MARKER_WRITE_REALPATH_BUDGET`), a `..`-traversal or stow-fold-physical-path obfuscation (candidates past the budget are tested against their raw tilde-expanded form only, not realpath-normalized); and a `CLAUDE_CONFIG_DIR` resolving with no `.claude` path segment, since the scan's own pre-filter requires that literal substring before a candidate is ever extracted. See the hook's own header comment for the authoritative, current list.

A subagent that hits a review gate is expected to report the denial upward; the dispatching session runs the skill, or delegates it to a `general-purpose` subagent, which does carry `Skill`. Matching a hash the subagent computed itself is not authorization — an equal hash shows the state is unchanged, not that anyone reviewed it. `test_agent_roster.py` asserts the no-`Skill` property against each file-backed agent's `tools:` frontmatter and pins the harness built-ins as a closed exemption set, so neither grounding can quietly go stale.

## Gate deadlock recovery

With `jq` unavailable (missing from `PATH`, failing, or hung past its 5s timeout backstop), every gate hook hard-blocks by design rather than silently allowing. In an interactive session, the recovery route is the `!` shell escape, which runs outside the tool-call path these hooks gate, to install or repair `jq`. A headless or non-interactive run has no `!` escape, so `jq` must already be installed in the execution environment beforehand.

Active-bypass markers from sessions that crash before cleanup evict themselves automatically: the hooks check `kill -0` against the stored PID and evict dead entries on the next gate hit. The remaining case is a *live session* whose review skill cannot execute — harness-blocked, failing to load, or unable to produce a completion marker due to a tool error.

For three gates, the gating condition is removable via Bash without destroying work:

**`require-plan-review.sh`** blocks Write/Edit when an uncommitted or modified plan file exists in `.claude/plans/` and no completion marker holds that plan set's hash. Committed, unmodified plan files are treated as historical and do not arm the gate. A Write/Edit/MultiEdit whose own target is one of those plan files is exempt, so authoring the plan itself is never what trips the gate.

```bash
# Option 1: remove the plan file to clear the gate. Copy the content first
# if you need to preserve it. If multiple uncommitted plan files exist, all
# must be removed or committed to clear the gate.
rm .claude/plans/<slug>.md

# Option 2: commit the plan file. A committed, unmodified plan is treated
# as historical and does not arm the gate.
git add .claude/plans/<slug>.md && git commit -m "plan: <topic>"
```

**`require-code-review.sh`** blocks `git commit` when no review covers the currently staged diff:

```bash
# Unstage the files. Changes remain in your working tree; re-stage and
# run /code-review once the skill is available.
git reset HEAD -- <files>
```

Alternatively, commit directly from a terminal outside Claude Code — Claude Code PreToolUse hooks only fire for `Bash` tool calls within a session.

**`require-skill-review.sh`** blocks `git commit` when no audit covers the currently staged `SKILL.md` diff:

```bash
git reset HEAD -- <path-to-SKILL.md>
```

Same terminal-outside-Claude-Code fallback applies.

### Gates with no clean escape

Three skill gates have no safe condition-removal path — the gate's intent is to force the skill:

- **`require-ready-for-review.sh`**: escape paths (close the PR, force-push, hard-reset) are destructive. If the skill cannot run in the current session, spawn a subagent.
- **`require-respond-pr.sh`**: the gate ensures the skill fetches all review-comment types before any `gh` PR comment operation. There is no condition to remove short of closing the PR.
- **`require-memory-skill.sh`**: the gate is path-based (fires on writes to memory files). Writing elsewhere defeats the user's intent. Run the skill in a subagent.

### Orphaned active-bypass markers

If a skill's active-bypass gate refuses to release after the skill has finished, use the manual sweep utility:

```bash
"${CLAUDE_CONFIG_DIR:-$HOME/.claude}/scripts/marker.sh" clear-stale          # evict dead-PID entries
"${CLAUDE_CONFIG_DIR:-$HOME/.claude}/scripts/marker.sh" clear-stale --dry-run # report without removing
```

`activate` resolves the live PID from the process ancestor tree, so a stale `<config-dir>/sessions/` entry — left behind by any session that has since exited, not only a crash or restart, since nothing deletes the lookup file on exit — cannot be stamped into a freshly written marker. `clear-stale` remains the tool for markers left behind by sessions that ended without `deactivate`.

## What a gate-backed skill's description may promise

Once a review skill acquires a gate hook, its `DO NOT TRIGGER` clauses stop being routing hints and start being predictions about whether an operation will be allowed. A gate decides on what it can compute — tool name, command shape, staged pathspec, marker hash. So every clause must either name a condition under which the hook's own predicate also declines to fire, or explicitly scope itself to a trigger point that has no hook behind it.

Two clause shapes cannot be honored and must not be written:

- **Judgment predicates** — "cosmetic-only changes", "a trivial one-liner". No hook can compute triviality; `require-code-review.sh` gates on staged-diff emptiness and command shape, never on the nature of the change.
- **Conversational state** — "the user has explicitly said to skip review". A PreToolUse hook sees one tool call, not the transcript.

The failure mode is uniform: the session reads the exemption, declines to run the review, and is then denied by the gate. Because the description is what the model reads *before* the skill fires, no amount of correct prose in the skill body can undo it.

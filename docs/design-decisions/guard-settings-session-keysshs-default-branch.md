# `guard-settings-session-keys.sh`'s default-branch diff accepts up to 5 extra `_lib_capped` git calls on its staged path

*2026-09-04. Formerly `docs/design-decisions.md` §54.*

`guard-settings-session-keys.sh` diffs staged `claude/.claude/settings.json` against the repo's resolved default branch, so an unresolvable default branch must deny rather than silently comparing nothing. This is the one fail-closed exception to the hook's otherwise fail-open posture. Resolving that branch via the shared `_lib_default_branch_or_guess` (`_lib.sh`) adds up to 5 more `_lib_capped` git calls on the settings.json-staged path:
- one for the symbolic-ref probe
- one more to verify a resolved-but-dangling target before falling through to the candidate probe (added when `_lib_default_branch_from_origin_head` gained that verification)
- up to three more for the `main`/`master`/`develop` candidate loop

Each call is capped at `_lib_capped`'s default 5s. This diff raises the sequential-call count on the settings-staged path from 4 pre-existing calls to up to 10: 3 of the 4 pre-existing calls are unchanged, the old single-call default-branch resolution is replaced by the 5-call shared helper counted above, and the pre-existing existence-check-then-refetch pair of `git show` calls against the identical target (see the "Correction" paragraph below) adds 2 more. So the theoretical worst case — every call independently timing out — is now ~50s (10 × 5s). That is well past the hooks' <100ms/fire budget. On a machine lacking both `timeout(1)` and `gtimeout(1)`, each of these calls instead runs uncapped and can hang indefinitely rather than for a bounded 5s, so that uncapped-timeout exposure compounds against more calls, not just a longer one.

This is an accepted tradeoff scoped to the narrow settings.json-staged path, not a general latency regression. The hook's earlier staged-file check exits before reaching this diff on every commit that doesn't touch `claude/.claude/settings.json`, which is what keeps the cost scoped to that one path. The new `.cwd`-extraction `jq` call this diff also adds, however, runs unconditionally on every gated `git commit`, not only the settings.json-staged path. `require-ready-for-review.sh`'s default-branch bypass check pays a similar but smaller call-count shape: up to 9 calls, ~45s, one less than the count above, because it has no analogous existence-check-then-refetch duplication. It resolves the default branch through this same shared helper.

**Why the helper reads local refs only, never the network.** `_lib_default_branch_from_origin_head` and `_lib_default_branch_or_guess` both read only `refs/remotes/origin/HEAD` and locally-tracked `origin/<candidate>` refs — neither shells out to `gh` nor fetches. Two network-touching alternatives were considered and rejected for this shared read path specifically:
- `gh api repos/{owner}/{repo}` resolves through `origin`'s own GitHub repo record, so on a fork it answers with the fork's default branch rather than the upstream one — wrong for every caller that means "the branch I'm normally compared against."
- `git remote set-head origin --auto` is the authoritative repair for an unset or dangling `origin/HEAD`: it queries the remote and rewrites the local ref to match. It writes, though, so it belongs in an interactive script that owns that consent question, not in a shared read-path helper every hook and script calls.

**Accepted false-negative narrowing after `_lib_default_branch_from_origin_head` gained target verification.** Before this diff, a dangling `origin/HEAD` made `_lib_default_branch_from_origin_head` return its raw, unverified target name directly, so `guard-settings-session-keys.sh`'s own line-87 `git show` existence check on `origin/$DEFAULT_BRANCH` failed too (`origin/<that raw name>` was never a real ref), and the hook fell back to the safest empty-baseline comparison — every guarded key read as changed, unconditionally. After this diff, `_lib_default_branch_from_origin_head` verifies its own target before returning it, so a dangling symref now fails at that narrow layer instead, and `_lib_default_branch_or_guess` falls through to the candidate probe, which can land on a real, verified-but-wrong branch (a "wrong-but-verified guess" — the repo's true default branch stays unknown). The hook then compares staged content against that branch's real settings.json instead of an empty baseline, so a guarded key whose staged value happens to match the wrong-guessed branch's stored value is now silently treated as unchanged and allowed — where the prior dangling-`origin/HEAD` behavior denied unconditionally.

This is an accepted tradeoff, not a regression to close here. `_lib_default_branch_or_guess`'s own contract does not exclude wrong-but-verified names — the hook already had to tolerate that category for the pre-existing "origin/HEAD entirely unset" case, which has reached the same candidate probe since PR 863. This diff only widens which dangling-symref conditions reach that already-accepted candidate probe; it does not introduce a new class of risk. It cannot detect, and was never able to detect, a wrong guess whose settings.json happens to carry a matching value.

**Correction, found during this diff's own review: line-87's `git show` existence check never affected `MAIN_CONTENT`'s value, on any input.** The subsequent unconditional assignment (`MAIN_CONTENT=$(git show origin/$DEFAULT_BRANCH:$SETTINGS_REPO_PATH 2>/dev/null)`) already yields an empty string on the identical set of failures the explicit check tests for — a nonexistent ref and a file absent from a real ref both make `git show` fail and produce no stdout, with or without the preceding boolean probe. Confirmed empirically: every existing "file absent from the resolved branch" test in this file still passes with the check's existence-probe half deleted. This predates this diff; it was already true of the check as PR 863 wrote it. It is not fixed here, per this project's scope-discipline convention for pre-existing issues in unchanged code. Tracked as a follow-up simplification, not a correctness gap: removing the redundant probe would also drop one `_lib_capped` git call from this hook's per-fire count.

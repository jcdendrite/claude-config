# Dispatch prompts mark relayed text by path, source and blockquote, not by fence

*2026-10-20.*

`claude/.claude/CLAUDE.md` § "Agent Briefing" states the convention, in its bullet on keeping relayed text apart from a dispatcher's own words. Its receiving side is the bullet in `claude/.claude/CLAUDE.md` § "Agent Core" that begins "Only the harness, the user's messages". This file records why the dispatching side takes this form, which sites it reaches, and its limits.

- **A path is the strongest boundary for attribution.** The harness, not the dispatcher, marks where a file's text starts and ends, so no miscopy or dropped marker can make that text read as the dispatcher's own words. A path also spares the dispatcher a transcription that can drop or distort a claim. It lets the agent form its own view of a plan file, a review's findings file or the files a fix would touch. Once read, a file's text steers as much as a blockquote does, because Agent Core makes both data.
- **A skill or the user can still call for a paste.** Two skills paste part of a file the agent could read, for reasons a path cannot serve. `/plan-review` copies one check's exact wording into a reviewer's prompt rather than sending the whole routing file. `subagent-delegation` sends `code-writer` only a review round's ADDRESS rows (the findings the round fixes). The round's findings files also hold its DEFER rows (the findings it leaves unfixed under a named criterion).
- **A skill's own wording is the dispatcher's instruction.** Agent Core sorts text by whose instruction it is, not by who typed it. A skill the dispatcher runs is configuration loaded for it. Marking that wording as relayed text would turn the dispatcher's configuration into data. `/plan-review`'s copied check is one case. `/code-review`'s judgment standard and DEFER criteria for a `plan-architect` consult are another. `plan-architect` does not count a verdict set or standard that appears only in quoted or read text as its caller's. The bullet says "own" because a skill also has the dispatcher carry text that others wrote, such as reviewers' ADDRESS rows. The bullet says "if you are running that skill" because a skill file can also reach a prompt as material. One case is another skill's diff that `/code-review` hands a reviewer inline when it has no diff file. Limits covers the running skill's own file.
- **A blockquote marks where inline relayed text ends.** A blank line ends the quote, and the dispatcher's own words resume after it. Under CommonMark, a line that continues the quoted paragraph stays inside the quote without a `>` (lazy continuation). Because the dispatcher prefixes every LF-delimited line, a quoted line that already starts with `>` reads as `> >`, and content cannot end the quote early. The boundary holds only where every such line carries the marker.
- **Quotation marks suit only a short phrase.** The quoted text can contain a quotation mark. Quotation marks are therefore kept for phrases too short to hide much past a misplaced end.
- **The lead-in names a source and a form.** It names a source rather than an author, because one relayed block can gather findings from several agents. The lead-in sits outside the blockquote, in the dispatcher's own voice. A title or other third-party label in it would therefore put third-party text in that voice. An identifier of a fixed shape, or one the session chose, carries no such text. Examples are a ticket or PR number, the name of an agent the session dispatched or a path the session wrote. The form keeps an excerpt from passing for a whole plan and a summary from passing for someone's own words. A summary counts as relayed text because it reports what a source said. An instruction says what the agent should do, so it is the dispatcher's own words.
- **A blockquote is plain Markdown.** A receiving agent reads code, a diff or a nested `> >` line inside one without a convention of its own. Its cost is a two-character prefix on every line, which shifts a diff's columns. A diff that a file holds therefore goes by path, and a diff with no file still takes the prefix.
- **No delimiter or fence.** A delimiter the dispatching model picks can also appear inside the text it encloses, and nothing checks for that before the prompt is sent. `evals/review_bench/adjudicate.py` fences safely only because its code picks a marker and checks that every fenced text lacks it. A code-built fence on every dispatch path would need a new script and an allow rule.
- **The task statement names what to follow.** Saying what the agent should do already covers what it should follow, such as the ADDRESS rows quoted below the task or an approved plan at a path. A separate clause asking the dispatcher to name what to follow would repeat that duty and check nothing.
  - A prompt with no task fails visibly. A task that leaves out an item the agent needed does not, as Limits notes.
  - For a `plan-architect` consult, the verdict set and the standard are in the dispatcher's own words. The skill running the consult has its prompt carry them, so they stay in the prompt rather than going by path. The bullet's sentence "A skill's own wording that you pass on counts as your own words if you are running that skill" makes them the dispatcher's words. The consult counts a verdict set or standard as its caller's only in the caller's own words.
  - A task statement may name any item, whoever wrote it. The dispatcher can state the same text as its own instruction, so a limit by author has nothing to bind. A limit by author would also make the dispatcher re-type the ADDRESS rows and approved plans, which a paste or a path keeps exact.
  - The dispatching skill's own decision step settles which item a dispatcher adopts, such as which findings a review round addresses or which plan the engineer approved. It does not vet what sits inside the item.
- **The rule addresses the dispatcher.** A rule in an agent's own definition reaches only that agent, never the session writing its dispatch prompt. `review-orchestrator`, the one agent here that dispatches others, is pointed at Agent Briefing by its own definition. A rules file would not serve either: the rules here are path-scoped, and no file path marks the moment a prompt is written. Every dispatching session loads the global `CLAUDE.md`, and nothing narrower is loaded when it writes a prompt. The rule therefore sits there, together with the limits a dispatcher must apply while writing.
- **Sites.** Every dispatch site follows the bullet without a copy of its own.
  - `/review-pr` Step 3 puts a ticket's or a `diff-only` PR's plan in context, and `/plan-review` relays it to each reviewer under a lead-in naming the ticket or the PR. That plan is third-party text. It can reach a reviewer only in that reviewer's prompt, because a spawned reviewer cannot see the session that read it. In `diff-only` mode, the relayed text is the plan, not its diff: the `+` side of its hunks with each line's first-column diff marker dropped. It is whole when the PR adds the plan and an excerpt when the PR modifies it.
  - These sites say what to carry, often "verbatim", and none says how to set it apart, so they follow the convention only when the dispatcher applies the bullet:
    - `/code-review`'s `plan-architect` consults (round-cap, heavier-mechanism, contradiction and fix-plan pilot) and its diff fallback.
    - `subagent-delegation`'s `code-writer` dispatches, for a review round and for a plan, and `review-orchestrator`'s.
    - `/respond-pr` step 6. Its sweep sentence states a reviewer's point, so it is a summary.
    - `/plan-review`'s spawn prompts.
    - `/ready-for-review`'s dispatches.
    - `/plan-it` Step 5.
  - `/plan-it` Step 5 keeps pasting the plan's Context paragraph, because no file holds it at the first dispatch and it is the session's own brief.
    - Limits covers the summaries inside it.
    - An engineer quote of a sentence or more in it is past the quoted-phrase bound, so it takes a blockquote. That changes its layout, not its words, so Step 5's "verbatim" still holds.
    - Honoring each engineer decision is part of what the agent should do. This record therefore reads the sentence "Outside any blockquote, say in your own words what the agent should do" as reaching Step 5's relayed answers too.
    - A decision stated as an instruction in the dispatcher's own sentence directs the agent. The engineer's words or label, quoted in a blockquote beside it, record where the decision came from.
    - A sentence that only reports the engineer's choice is a summary of the answer. It is relayed text and only informs the agent.
  - `issue-triage` passes issue text on disk and carries its own receiving-side rules. `claude-hook-review` dispatches agents that the same stow package as the global `CLAUDE.md` installs.
  - A plugin skill whose dispatch inlines relayed text and can run without the global `CLAUDE.md` carries its own copy. It does so under the exception for instructional prose that must stand alone in `claude/.claude/CLAUDE.md` § "Engineering Judgment".
- **Limits.**
  - Six `_PLACEMENTS` rows in `claude/.claude/hooks/tests/test_global_claude_md_groups.py` pin the presence of six clauses and the Main session group of `claude/.claude/CLAUDE.md` as their placement, and other text in the bullet is unpinned. No pin checks the Agent Briefing section, and nothing tests adherence. No test or eval measures whether dispatchers follow it or receivers honor it. That includes whether a `plan-architect` consult counts a skill's standard passed on as its caller's and declines one in a blockquote.
  - It reduces boundary ambiguity and transcription loss. It does not limit what relayed text can steer. It does not guard against a steered dispatcher either, whose own words instruct whatever steered them.
  - A dropped `>` silently returns that line to the dispatcher's voice. A quotation mark inside a quoted phrase can end that phrase early. Nothing checks for either.
  - A line break other than LF inside relayed text (a bare CR, U+2028 or U+0085) can start a line in a receiver's reading that carries no `>`. The prefix does not cover it, and nothing checks for it.
  - A quoted phrase takes no lead-in. Nothing asks the dispatcher to name its source or form. Its quotation marks are what mark it as relayed text. A phrase short enough to read as an imperative is covered by the Limit that the convention does not limit what relayed text can steer.
  - The bullet's "identifier you can check" does not exclude a name a third party chose, such as a `diff-only` PR's plan-file path. A dispatcher that puts one in a lead-in puts that text in its own voice. `/review-pr`, the one site that relays a ticket's or a `diff-only` PR's plan text, names the ticket or the PR instead, in the sentence of its Step 3 that begins "Have `/plan-review` relay". No test pins that sentence.
  - A task that leaves out an item the agent needed leaves that item as data, and nothing signals the miss. One such case is an engineer answer at `/plan-it` Step 5 that the dispatcher sets in a blockquote and names in no sentence of its own. The plan can then drift from the engineer's choice until someone reads it. `/plan-it` Step 5 prescribes no sentence that states each decision as an instruction. The Step 5 form rests on reading the sentence "Outside any blockquote, say in your own words what the agent should do" to ask for one. Nothing shows that a Step 5 dispatcher reads it that way.
  - Summaries of a source's text inside `/plan-it`'s Context paragraph take no blockquote. `/plan-it` has the session compose that paragraph as its own brief and paste it into the Step 5 prompt. A ticket or finding the session restates there therefore reaches `plan-architect` in the dispatcher's voice, with no lead-in naming its source. This exception rests on `/plan-it`'s mandate, not on the reason a summary counts as relayed text, and the bullet does not state it. Only an engineer quote of a sentence or more in Context takes a blockquote.
  - A dispatcher that takes third-party text for a skill's own wording passes it on unmarked, in its own voice.
    - The bullet's "own" and its "if you are running that skill" are the only guards.
    - They pick a skill, not a span of its text.
    - A running skill's own file can reach a prompt as material, not as the skill's own wording. One case is a change to `/code-review` that `/code-review` hands a reviewer inline when it has no diff file.
    - Only the dispatcher's judgment marks that text as relayed.
  - Naming an item adopts all of it, any command included. The bullet gives a dispatcher no rule to cite for declining to name third-party text. Where a skill has a decision step, such as a review round's disposition, `/respond-pr`'s triage or the engineer's approval of a plan, that step is the only gate on which item is adopted. Elsewhere only the dispatcher's judgment is.
  - Marking does not survive an agent's return that a file holds and a later dispatch names. `/plan-it` inserts a `plan-architect` return into the plan file, and a plan phase hands `code-writer` that file by path.
  - Marking adds no bound on a steered recipient and removes none. The recipient keeps the reach it has without this convention, and this record neither restates that reach nor rates its risk. It defers to the sources that state it, among them:
    - Each agent's `tools:` line under `claude/.claude/agents/`.
    - [The gate-release record](review-orchestrator-gate-release-decoupling.md)'s accepted residuals.
    - `docs/hooks.md`'s per-hook entries.
    - For a `plan-architect` consult's return, `/code-review`'s `DISPOSITION_RULE` regions and [the pilot record](architect-authored-fix-plan-pilot.md)'s Known gaps.
  - The convention assumes the receiving agent loads Agent Core. An agent that skips the startup load of the global `CLAUDE.md`, as the built-in `Plan` agent does ([`/plan-it` Step 5 dispatches a custom agent instead](plan-it-step5-pinned-opus-dispatch.md)), sees the lead-in and blockquote without that rule behind them.
  - `/review-pr` still relays a ticket's plan inline. Its ticket read has no file backstop, so a cut-off body can look whole. As of this record's date, GH-1280 tracks passing that plan by a path that code writes.
- **Revisit** in either of two cases:
  - A dispatched agent is seen acting on relayed text its task did not name, ignoring text its task named, or treating a skill's wording its dispatcher passed on as data.
  - A dispatcher is seen passing third-party text on unmarked as a skill's wording, or leaving out an engineer decision its agent needed.

  In either case, edit the dispatch text of the site that sent the prompt, or hand the text over by a path that code writes.

# CI stays an unconditional full-suite backstop

*2026-09-10.*

Three options were weighed for CI's test-execution strategy in `.claude/plans/test-suite-boundary-and-selective-ci.md`: keep CI running the full suite unconditionally (the status quo), make CI selective by routing `.github/workflows/tests.yml` through `select-tests.py`'s own rule table or an equivalent path filter, or a hybrid that runs a fast selective pre-check alongside the existing full gate. The first was kept; the other two were rejected on primary-source grounds, not on cost. A related decision, `full-suite-pytest-drift-traced-to.md`, forecloses a narrower version of the same idea — mechanically checking whether an agent's chosen verification command matches the selective default — on the grounds that CLAUDE.md's full-suite exception is a condition on intent, not a machine-readable predicate. The same foreclosure underlies why a hand-authored path table cannot safely hold CI's gating position either: neither a human nor a machine can cheaply tell, from the diff alone, whether the table's selection was actually sufficient.

Making CI selective would put that path table — one with documented precision-not-recall gaps — in the position that today catches those gaps. Every credible affected-test system researched for this decision either declines that position, needs a fundamentally stronger correctness primitive to hold it safely, or is itself calibrated to over-run rather than under-run. pytest-testmon is the closest analogue: selection over a Python suite via coverage.py-measured per-test dependencies, a stronger signal than a path table. Its own docs state its reliability limits mirror coverage.py's, naming untracked static files and external services as blind spots. Its docs also state it has no CI-specific behavior — it runs the same locally and in CI. A companion hosted product exists because sharing per-runner dependency data across CI's ephemeral machines is otherwise impractical. A tool whose own vendor treats multi-runner CI as an unsolved practical problem, on top of a signal it admits inherits coverage.py's own reliability limits, does not license a weaker path-heuristic taking the merge-gate role.

Bazel's `--cache_test_results` is the one researched system that does skip work in a gating position. It earns that position with a content/action-hash primitive rather than a diff heuristic. Bazel's own docs still name a live race condition — an input file modified during a build can upload invalid results to the remote cache — closed only by an experimental, not-yet-default `--experimental_guard_against_concurrent_changes` flag. This repo has no content-hash primitive, and building one is out of scope here.

The diff-heuristic systems that exist are calibrated to over-run rather than to correctness. Turborepo's own docs state that a too-shallow checkout means "all packages will be considered changed" (fail open). Nx's own docs name over-triggering on a widely-depended-on file as the acknowledged cost of `affected` — "you might end up running tasks for almost all the projects in the workspace" — not a correctness defect. `select-tests.py` already matches that calibration, and CI is already the thing it over-runs into.

The repo-specific argument is sharper. GitHub's own docs name an explicit fail-*closed* edge case for `paths:` filters: a diff over 3,000 changed files, where the matching files aren't among the first 3,000 returned, causes the workflow not to run at all. GitHub's docs separately warn that a required check gated by path filtering can leave a PR blocked forever, since a skipped workflow reports no status and no branch-protection setting treats a missing check as passed. The `tests` job id is exactly the status-check context branch protection requires on `main`. The workflow already avoids the paths-filter deadlock deliberately, by gating *steps* rather than the job (`if: steps.detect.outputs.changed == 'true'`). The job therefore always runs and always reports, so a docs-only PR reports green instead of reporting nothing. A workflow-level `paths:` filter is precisely the shape GitHub's docs warn about, and it's already avoided here. Any selectivity added on top would have to preserve that step-level shape: a PR whose changes actually trigger the test steps still pays the runner, the checkout, `pip install -r requirements-dev.txt`, and the apt `stow` install regardless of how narrow the selected test subset is — the fixed per-run cost, not the test wall-clock, is what a selective CI would leave untouched.

The hybrid — a fast selective pre-check job plus the existing full gate — is rejected on top of that. It produces no information the full gate doesn't already produce, it can't fail a merge on its own, and it pays a second job's fixed cost to learn a subset of what the first job learns. It's also the compounding-defensive-layer shape: a second layer whose only job is to compensate for the first layer being slow.

**Revisit** if any of:

- An end-to-end wall-clock measurement of the current two-pass split (parallel `-m "not timing"`, serial `-m timing`) lands and shows CI is the binding constraint on merge latency.
- The repo gains a content-hash-based test cache, closing the gap Bazel's `--cache_test_results` needs to skip work correctly.

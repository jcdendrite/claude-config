# `/code-review`'s Fix-route unifies [§42](code-review-fix-route-plan-architect.md)'s two dispatch arms into one

*2026-09-06. Formerly `docs/design-decisions.md` §59.*

[§42](code-review-fix-route-plan-architect.md) routed a mechanism-inventing fix through `plan-architect` on one of two arms chosen by plan-file existence: a direct `MODE=consult` dispatch with no plan file, or `plan-it` Step 5's revision re-dispatch carrying `MODE=plan-sections` when one existed. That second literal is exactly what both `log-reviewer-round.sh`'s latch writer and `_is_architect_consult_dispatch` define as *not* a consult, so a fully [§42](code-review-fix-route-plan-architect.md)-compliant escalation on a plan-file branch wrote no latch and emitted no `review-trace` row. `code-review/SKILL.md`'s Fix-route step now collapses the fork: always dispatch `plan-architect` first with `MODE=consult` as the prompt's first line, carrying the finding, the fix, the paths it would touch, and the plan file's path when one exists on the branch. The return decides what follows — endorsed with a plan file re-dispatches `plan-it` Step 5's existing revision re-dispatch against that path to insert the sections; endorsed with no plan file enters through `/plan-it` on its own terms, unchanged; rejected produces no second dispatch and no plan edit. The `Fix route:` line's two recorded values collapse to the single `plan-architect — consult`, since it is written at disposition time, before the return is known, and so can never record which branch of the follow-up fires.

**No hook-layer change.** `log-reviewer-round.sh:_maybe_write_consult_latch` fires for any `plan-architect` dispatch and returns early only when the prompt's first line is literally `MODE=plan-sections` — under the unified route the first dispatch's first line is always `MODE=consult`, so the latch is written unconditionally, with no edit to the hook. The conditional second dispatch, when it fires, carries `MODE=plan-sections` and correctly writes nothing, which is harmless because the latch already exists. `require-architect-consult.sh` tests only the latch file's existence and is mode-unaware, so its behavior is unchanged either way.

**[§42](code-review-fix-route-plan-architect.md)'s "hook-backed in practice" claim narrows to the endorsed branch.** [§42](code-review-fix-route-plan-architect.md) read the plan-file route as converting an advisory rule into a hook-backed one, because the compliance act edits the plan file and re-arms `require-plan-review.sh`. That re-arm now happens only when the consult is endorsed and a plan file exists — a rejected consult produces no plan edit and no re-arm, so the rule stays advisory on that branch, as it always was on the no-plan-file arm. [§42](code-review-fix-route-plan-architect.md) itself is not edited; this entry states the narrower scope its "hook-backed in practice" claim now carries.

**Supersedes [§48](review-trace-fifth-event-kind.md)'s SILENT-SKIP verdict-ceiling sentence, on reason 1 only.** [§48](review-trace-fifth-event-kind.md) held the architect-consult check could never legitimately emit `[SILENT-SKIP]`, for three reasons:

1. `review-trace` never loading subagent records (reason 1).
2. [§37](plan-architect-consult-mode.md)'s user-ask gate and [§42](code-review-fix-route-plan-architect.md)'s Fix-route narration both being non-evidence (reason 2).
3. [§45](round3-plan-architect-consult-gate.md)'s deny-latch correlation being a rejected duplicate detective layer (reason 3).

[§58](review-trace-and-cost-ledger-widen.md) closed reason 1's scan-visibility half; this entry's unified route closes its plan-file-misclassification half. Together, a `plan-architect` consult prescribed anywhere on the branch's timeline is now observable regardless of route or thread. `skill-fidelity-reviewer.md`'s "The architect-consult check" section is restructured into two cases. The no-deny sub-heading keeps the original zero-rows → *Dismissed as undecidable* rule, reasoned "absence of a row is not evidence of absence," never `[SILENT-SKIP]`. A new gate-deny sub-heading is the one case that now earns `[SILENT-SKIP]`: a `denial` row whose `msg=` text opens `Blocked by architect-consult gate:` with no later `architect-consult` row on the same branch's timeline, decidable because the preventive gate's own deny message reaches the timeline as tool-call metadata, never the deviating session's rationale. **[§48](review-trace-fifth-event-kind.md) reasons 2 and 3 stand untouched** — neither [§37](plan-architect-consult-mode.md)'s user ask nor [§42](code-review-fix-route-plan-architect.md)'s Fix-route narration is observable from the reviewer's evidence surfaces, and this entry narrows the ceiling on reason 1 alone.

**Revert-order coupling with [§58](review-trace-and-cost-ledger-widen.md), stated canonically here.** [§58](review-trace-and-cost-ledger-widen.md) and this entry must be reverted together: [§58](review-trace-and-cost-ledger-widen.md)'s widened `review-trace` scan and this entry's narrowed `[SILENT-SKIP]` ceiling depend on each other (see the two scenarios below). Reverting this entry alone is safe — the ceiling reverts to its [§48](review-trace-fifth-event-kind.md) shape and `review-trace`'s widened scan ([§58](review-trace-and-cost-ledger-widen.md)) keeps running unused by this narrower check. Reverting [§58](review-trace-and-cost-ledger-widen.md) alone while this entry's narrowed ceiling stays live is not: `review-trace` goes blind again to a subagent-dispatched consult, and the narrowed check would then flag a fully [§42](code-review-fix-route-plan-architect.md)-compliant subagent-dispatched consult as `[SILENT-SKIP]` — the exact false positive this entry exists to eliminate. The two entries must be reverted together.

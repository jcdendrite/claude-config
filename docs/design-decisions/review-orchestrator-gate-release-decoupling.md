# `review-orchestrator`: a thin, explicit-request-only agent that runs one `/code-review` round and writes its own marker

*2026-10-09.*

The decision is a minimal dedicated `review-orchestrator` agent. It runs one `/code-review` round per dispatch in its own context, so a dirty round's skill body, findings read-back, and fix churn stay out of the main session. The bar for its guardrails is that it must be no weaker than an unconstrained `general-purpose` dispatch, not that it be airtight. Its tree and marker rules are therefore a prose contract, backed only by hooks that already fail loudly. The cost premise is that a subagent-wrapped round saves main-session context, so the agent pays for itself on rounds that end without a `HALT:` entry and costs one extra round on a halted one, because that review then continues inline. The premise is unmeasured, and the post-merge dogfood does not measure it.

**The agent is a Sonnet agent with `Skill`, `Agent`, `Read`, `Grep`, `Glob` and `Bash`, and no `Edit` or `Write`.** It pins `model: sonnet` and `effort: high`. Leaving out `Edit` and `Write` steers every fix to `code-writer`. `Bash` can still write, which the accepted residuals below record. Body item 2 points the agent only at the `Agent Briefing` and `Model & Effort Routing` sections of CLAUDE.md's Main session, so its charter excludes a commit and a `/code-review` re-run after its own fix.

**One round per dispatch, and the parent sequences the rounds.** A fix is never re-reviewed in the dispatch that made it. The next dispatch reviews it. Nothing in this design bounds the parent's stage-and-dispatch loop. The round-cap consult fires once per branch and has a machine-wide kill switch (`require-architect-consult.sh`), so the parent or the human stops the loop, as with inline `/code-review`. That consult gate fires on any reviewer spawn and never checks the caller, so it can fire from inside the agent.

**The agent covers `/code-review` only.** `/plan-review` stays inline. `/ready-for-review` is out of scope because it pushes and opens a PR.

**The agent writes its own code-review marker, and only on a clean round in which it dispatched no `code-writer` and has no `HALT:` entry.** `code-writer` leaves its fixes unstaged, so the staged-diff hash the marker keys on still matches after a fix. The skill's own check that it reviewed a different state than the one currently staged therefore never fires after a fix, and the no-fix condition stands in for it. The no-`HALT:` condition exists because a halted review continues inline, and inline Step 0.1 would skip on a marker that round left.

**A marker the agent writes releases the parent's commit gate, and the gate hooks treat the agent as any subagent absent from `_LIB_NO_GATE_RELEASE_AGENTS`.** The stored staged-diff hash is the authorization, whichever session wrote it. `enforce-marker-script-shape.sh` denies `marker.sh write` and `activate` to agent types in `_LIB_NO_GATE_RELEASE_AGENTS`, and the agent may write only because it is absent from that roster. That absence is skill-agnostic, the same as `general-purpose`'s. The hook's deny covers every `marker.sh write` and `activate` for roster members and none for anyone else. The agent can therefore run, with no prompt, each `marker.sh` invocation that `permissions.allow` pre-approves, among them the plan-review and ready-for-review markers and the memory-skill and handoff bypasses. Only its charter holds it to the code-review marker. A marker-name deny keyed on this agent's identity would not narrow that reach, because its `Agent` tool can dispatch a `general-purpose` agent that runs the same `marker.sh` invocations. Closing that hop needs the dispatch-target hook rejected below. `test_absent_from_no_gate_release_agents` in `test_agent_roster.py` and the `GATE_RELEASE_ALLOWED_AGENTS` list in `test_enforce_marker_script_shape.py` pin that absence.

**The parent relays, persists, stages, checks and decides after every dispatch, and `subagent-delegation/SKILL.md` § "Exception: gate/review loops stay orchestrator-driven" is the protocol's one home.** The parent acts on what the return reports and does not fingerprint the tree. This record holds only the reasons behind the steps:
- Persist: with a PR open, the parent runs `claude-skills/skills/code-review/SKILL.md` § "Review-findings persistence", which the agent skips. The public PR body therefore changes only in the session the user is watching, where a gate denial on the edit can be recovered. `render` builds the block's rows from the ledger, so a return that stops before this step loses nothing: the next inline round or `/ready-for-review` publishes them.
- Check runs after every dispatch, a staged fix included. `check` matches any session's marker under the repo hash within its freshness bound, so a match means a marker covers the staged state, not that this dispatch wrote one.
- A `match` that accompanies a `HALT:` entry or a staged fix stops for the user, because the marker then covers a state the review did not finish and inline Step 0.1 would skip on it.

Every stop in the protocol fails closed. The parent runs no `check` before the first dispatch. Without one, an already-reviewed state still ends as done, because Step 0.1 sees the match and skips the round. Dispatching anyway also keeps Step 0.1's CLEAN ledger row.

**No hook names the agent's dispatch target.** A dispatch-target allowlist hook would deny `plan-architect`, which `/code-review` dispatches. With no `Bash` allowlist, getting past it would reach nothing the agent's own `Bash` cannot. Keeping it would also need a tier line and a tiers-table row. If a `Bash` restriction for the agent ever returns, the dispatch-target hook returns with it.

**The agent fires only on an explicit user request until the post-merge dogfood passes.** A `TRIGGER` matching every `/code-review` would send every stow consumer's reviews through an agent nobody has dogfooded, which is rewiring under another name. The description's only `TRIGGER` clause is `TRIGGER only when the user explicitly asks to run /code-review through review-orchestrator`, and the `subagent-delegation` paragraph states the same condition as `only when the user explicitly asks`. Until the follow-on rewiring (the CLAUDE.md, README and `TRIGGER` changes held back below), no session is told to use the agent unless the user asks.

**The protocol lives in the skill, and the agent description stays a thin shell.** The description says what the agent does, when it fires, and where the dispatching session's protocol lives. It carries no protocol. The `subagent-delegation` skill's own `TRIGGER` already covers delegating a multi-step gate/review loop, and its exception section already prescribes separate bounded per-step dispatches that the orchestrator sequences between. Two tripwires pin the contract's ends and nothing else:
- `test_agent_roster.py` pins the description's explicit-request `TRIGGER`, its `subagent-delegation` pointer, and that no second `TRIGGER` clause stands outside `DO NOT TRIGGER`.
- `test_skills.py` pins that the protocol section carries the exact allowlisted marker-check command as a whole code span, `:(top,literal)`, `no single or double quote`, `Review-findings persistence` and `only when the user explicitly asks`, that the section and the agent body both name `Fix paths:`, `Marker:` and `HALT:`, and that the `code-review` headings and `Spawn decisions:` line the agent body relies on still exist.

Every other rule in the protocol is deliberately unpinned. Under the bar above, a dropped rule surfaces in dogfood or review, not in a test.

**Existence test (`claude-skills/skills/agent-review/SKILL.md` § "7. Existence test: should this be an agent at all?").** The agent's one dispatch site is one skill's one step, so it is presumed wrong unless both questions hold.
- Is the privilege cap load-bearing? Not by itself. No hook names the agent. `enforce-marker-script-shape.sh` keys marker and ledger writes on agent identity, and the agent's absence from `_LIB_NO_GATE_RELEASE_AGENTS` lets it write the marker as a `general-purpose` dispatch can. The tools cap only steers. The existence case rests instead on the model pin, which a `general-purpose` dispatch prompt cannot impose (and which is a request rather than a guarantee, per CLAUDE.md § "Model & Effort Routing"), and on context isolation.
- Does the call site fire often enough to amortize an always-loaded description? Not yet. Until rewiring, the agent runs only on an explicit request, so its always-loaded description is a standing cost for rare use. The follow-on rewiring, which routes `/code-review` rounds through it, is the amortization path, and a failed dogfood removes the agent.

**Two deliberate departures from `claude-skills/skills/agent-review/SKILL.md` § "8. Review checklist".**
- The description's `TRIGGER only when` and `DO NOT TRIGGER for` clauses stand in for the checklist's literal `TRIGGER when:` and `DO NOT TRIGGER when:` blocks, because the agent fires on no situation, only on an explicit request.
- Body item 4 names the `Skill` tool as its invocation verb, because this repo-specific agent invokes `code-review` through the `Skill` tool its frontmatter grants.

**An agent named for orchestration runs on Sonnet although CLAUDE.md § "Model & Effort Routing" lists "parent-dispatcher orchestration" under Opus.** The agent runs one round of a skill it follows verbatim. The round's open judgment calls go to the human as `HALT:` entries or to the Opus-pinned `plan-architect` that the skill spawns. The follow-on rewiring reconciles the Model & Effort Routing line with this pin.

**Rejected alternatives.**
- Running `/code-review` inline in every session: this is the cost the agent removes.
- A closed `Bash` allowlist hook, a dispatch-target allowlist hook and a checkpoint store: each would make the agent stricter than a `general-purpose` dispatch. With one round per dispatch, the parent is how a run resumes, so nothing reads a checkpoint.
- `general-purpose` with `model: sonnet`: a dispatch prompt cannot impose a tools cap or a model pin that holds when the parent runs on another model.
- `context: fork` on `code-review`: it applies to every call and forfeits `AskUserQuestion`. It would also reverse the `_FORKED_SKILLS` pin in `claude-skills/skills/tests/test_skills.py`.
- A marker written by the parent, with the agent added to `_LIB_NO_GATE_RELEASE_AGENTS`: `claude-skills/skills/code-review/SKILL.md` § "Step — Record review completion" says the marker is written only by the skill, and the parent would write it for a round it did not run. The roster's grounding is that its members can neither run a review nor dispatch an agent that can, and this agent does both. Adding it would also narrow nothing, for the reason the gate-release paragraph above gives.
- A script that fingerprints the tree before and after each dispatch: it catches changes the return leaves out, but needs a model-copied token that no exact `permissions.allow` rule matches.
- The parent's protocol in the agent description: the description loads into every session, and the protocol is the dispatcher's concern.
- An `Agent(agent_type)` allowlist in the agent's `tools:` frontmatter, to close the `general-purpose` hop without a hook: the vendor applies that syntax only to an agent running as the main thread with `claude --agent` and ignores the type list in a subagent, so it is inert here (https://code.claude.com/docs/en/sub-agents).

**Staged rollout, gated on a post-merge dogfood.** The agent ships additive-only: explicit-request-only, with the CLAUDE.md rewiring, the README agent paragraph and gate-table row, and any widening of `TRIGGER` held back. The rollout mechanism for the follow-on rewiring is a boolean config key, `review_orchestrator_routing`, default `false`, with a SessionStart hook that emits one `additionalContext` line only when the key is on. The key gates routing, not use, so an explicit-request dispatch works either way. The dogfood gates flipping the default.

The dogfood is two real `/code-review` rounds through the agent, on explicit request, from a session that has not loaded this record, and at least one round must include a fix, because the no-fix marker condition and the check-after-fix rule only come into play when a fix happens. A pre-merge dogfood is declined: a pre-merge session loads a `subagent-delegation` skill that lacks the protocol, and it would need a temporary second copy of the agent that can drift from the reviewed file. A dispatch passes only if all of these hold:
- The agent ran on Sonnet, read from its transcript, since the pin is a request, not a guarantee.
- Reviewers and `code-writer` spawned beneath it, plus `plan-architect` if the round cap fired, with no nested-dispatch failure, and the return's `Spawn decisions:` line matches what spawned.
- The return followed the format, and `Fix paths:` named every file the fix touched and nothing else, checked against `git status --porcelain --untracked-files=all` captured before and after the dispatch.
- `review-ledger.sh show` lists the round's rows in the branch's ledger.
- The dispatching session's action followed from the agent description and the `subagent-delegation` section alone.
- After done, `git commit` passes `require-code-review.sh` on the agent's own marker.

Two consequences follow. Any miss means no rewiring: the decision the miss names reopens as an engineer decision before the follow-on rewiring, and a nested-dispatch failure sends the design back for revision. A marker over a fix no round reviewed reopens the marker-ownership decision above, because an identity deny on `marker.sh write` cannot tell a clean round from a post-fix one and so would amount to the parent writing the marker.

If the dogfood fails, a forward change removes the agent, the test entries that name it, the protocol paragraph with its test and the CHANGELOG Added entry, and records the withdrawal here. It leaves the `docs/skills.md` bullet on forking skills that run their reviewers as subagents in place, because that bullet is accurate without the agent.

**Unverified until the dogfood observes it.**
- Whether `Skill` inside a custom subagent runs `/code-review` and the skills it calls.
- Whether the session-id walk behind `marker.sh` and `review-ledger.sh` (`_lib_resolve_claude_pid` in `_lib.sh`) succeeds from inside a subagent.
- Whether nested dispatch from the agent works. The vendor documents a spawn-depth limit, a default nesting depth of 3 past which the harness withholds `Agent` from a subagent, which then does the delegated work itself. That documentation reaches this record only second-hand.
- Whether the harness resolves the new agent file under the active config dir: a consumer whose `agents/` directory is not a folded directory symlink re-runs `./install.sh` after pulling.

**Accepted residual: prompt injection from reviewed content.** The agent can fix and release, with no human turn in between, any gate whose marker it can write or activate, which is not only code-review's. Content the agent reads during a review (a malicious comment in the diff under review) is a threat class this repo already accepts for the top-level session running these skills. What changes here is blast radius. Staging a reported fix retires a marker written before it. Nothing catches a change the return leaves out of `Fix paths:`, a path the return lists that the fix never touched (the parent stages any listed path that porcelain status shows, dirty for another reason or not), a commit made during the dispatch, or a steered clean verdict. Staging a fixed file also stages any edits it held before the dispatch, as staging after an inline round does. An unconstrained `general-purpose` dispatch is checked no better, so this meets the bar.

**Accepted residual: gaps in the marker protocol, each needing the agent to break a written rule and none closed here.**
- A fix staged before the marker is written. The marker then covers the staged fix, and staging retires nothing, because `marker.sh` has no revoke for completion markers. The parent's `check` stops the loop on it when the return reports the fix.
- `Fix paths: none` after a fix, together with a marker written in that round. The commit then carries the reviewed state without the fix. Either mistake alone is safe: the missing paths stop at `no-match`, and a marker after a reported fix is retired by staging.
- A marker written in a round that also returned a `HALT:` entry and named no fix. The parent's `check` can only report it, so the protocol stops there for the user's decision, and the marker stays live.

**Accepted residual: routes past `enforce-marker-script-shape.sh`'s engineer-quote deny.** The hook's header lists them as residuals: variable and function indirection, brace expansion, `$'\x..'` escapes, a script name or op supplied at run time, and a renamed copy or link of `review-ledger.sh`. It also lists a nested `claude -p` or `claude --print` session started through `Bash`, whose payload carries no `agent_id`. Through any of them the agent can log a ledger row attributed to the engineer, which the PR body then publishes, with no engineer turn. A `general-purpose` dispatch has the same reach. The header names one whole-class control for the nested session only: a permission-layer `ask` or `deny` entry for those two spellings. That entry would change every session's `Bash` for every stow consumer, so it needs its own review of the spellings it catches and of the direct `claude -p` uses the repo documents. It is the named follow-on that closes that one route. The header names no control for the rest.

**Accepted residual: the agent's `Bash` and `Agent` calls face only the hooks every session runs.** A `general-purpose` dispatch's calls face the same hooks. Beyond what those hooks deny, nothing in this design bounds the agent's network egress, `git push`, `gh pr edit` or `gh pr comment`, its dispatch of an agent that holds `Edit` and `Write`, or `rm` and `truncate` on marker and ledger files, which `enforce-marker-script-shape.sh`'s header lists as unscanned.

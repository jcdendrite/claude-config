# `review-orchestrator`: gate-release/Bash-restriction decoupled into a new array, not folded into the existing roster

*2026-08-21.*

The review-pipeline orchestrator plan (`.claude/plans/review-pipeline-orchestrator-subagent.md`) adds a dedicated `review-orchestrator` agent that runs `/code-review` or `/plan-review` to completion inside its own disposable context, substituting a nested `code-writer` dispatch for any fix step instead of editing directly. Three roster decisions fell out of making that substitution genuine rather than nominal.

**Scope limited to `code-review` and `plan-review`; `ready-for-review` support deferred.** `ready-for-review` pushes and opens a PR, which conflicts with `review-orchestrator`'s zero-mutation/zero-egress invariant — a structural gap, not a missing case arm. `require-review-orchestrator-bash.sh`'s allowlist also doesn't yet cover `ready-for-review`'s own step 1 (`gh pr view`, `git fetch`, several helper-script calls, `gh pr create`, and more). Both gaps are left for a follow-on design covering the push/PR-creation boundary rather than closed here.

**A new `_LIB_BASH_MUTATION_RESTRICTED_AGENTS` array, not an addition to `_LIB_REVIEW_ONLY_AGENTS`.** `review-orchestrator` carries `Bash` but no `Edit`/`Write`, so without a Bash restriction it could mutate the tree directly (`echo > file`, `sed -i`, `git commit`) and make the "fixes route through `code-writer`" design false as built. The natural home for that restriction looked like `_LIB_REVIEW_ONLY_AGENTS` — every existing member is already Bash-mutation-restricted via `deny-reviewer-tree-mutation.sh`. But that array also drives `_LIB_NO_GATE_RELEASE_AGENTS` (`enforce-marker-script-shape.sh`'s deny list), and `review-orchestrator` genuinely runs the review skill it's dispatched for, so it must keep the ability to write that skill's completion marker — the opposite of what `_LIB_NO_GATE_RELEASE_AGENTS` membership would grant. Whether an agent may release a gate and whether its Bash calls are mutation-restricted are two independent properties that happen to coincide for every `_LIB_REVIEW_ONLY_AGENTS` member today; a new, separate array keeps them independent instead of accidentally re-coupling them for the one agent that needs them split.

**A separate hook (`require-review-orchestrator-bash.sh`) with a closed allowlist, not an addition to `deny-reviewer-tree-mutation.sh`'s blocklist shape.** The existing reviewer hook denies a closed set of known-mutating patterns and allows everything else — correct for a persona that only ever reads and writes findings files, wrong for an agent whose legitimate Bash surface (verification commands, three specific helper scripts, read-only git) is itself small and enumerable. This new hook's allowlist is deliberately closed rather than an open "whatever the running skill needs" bucket: no `PreToolUse` hook payload exposes which skill is currently running for such a bucket to key on, and an open bucket has no fixture coverage by construction.

**`require-review-orchestrator-agent-target.sh` closes the one-hop-around gap the Bash restriction leaves open.** `review-orchestrator` is also granted `Agent` (needed to dispatch `code-writer` for fixes and reviewer personas for the skill's own routing), and a Bash restriction alone does nothing to stop it from nest-dispatching an unrestricted `general-purpose` or `claude` to do the mutating and gate-releasing on its behalf — reopening the Bash gate's own gap one hop away, with zero `Bash` call from `review-orchestrator` itself. The allowlist reuses `_LIB_REVIEW_ONLY_AGENTS ∪ {code-writer}` rather than inventing a third roster: every member is already non-gate-releasing, and `code-writer` is fully mutation-restricted, but a reviewer persona's own Bash calls route through `deny-reviewer-tree-mutation.sh`, whose header documents an accepted, unclosed gap on raw Bash write-target resolution (`cp`/redirect/`tee` onto a tracked file). This hook and the Bash restriction above close the *direct* one-hop path (which agent may be dispatched, and what `review-orchestrator` itself may run); a review-orchestrator instruction that misleads an allowed reviewer persona into exploiting that pre-existing gap is a residual two-hop path this design does not mechanically close, consistent with the cooperative-agent threat model the rest of this repo's review-only-agent hooks already accept.

**Staged rollout, gated on dogfooding.** Whether a custom agent type's `Agent` grant can reliably nest-dispatch further subagents was, at authoring time, verified only for one dispatch from a throwaway spike agent — the single highest-risk unverified assumption in the plan. The orchestrator ships additive-only first — reachable only by explicit manual `Agent` dispatch — with the top-level-session-forcing hook (`require-review-orchestrator-dispatch.sh`), the CLAUDE.md rewiring, and the docs update held back until `review-orchestrator` has been manually dispatched at least twice per skill against real work with no nested-dispatch failure. That two-dispatch bar applies separately to each of `code-review` and `plan-review`. Staying additive-only until then means a nested-dispatch reliability problem discovered during dogfooding costs nothing beyond that follow-on work never landing.

**Retry cap: 3 total attempts (2 automatic retries), grounded in AWS Step Functions' `Retry` field defaulting `MaxAttempts` to 3** (https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html). The orchestrator's Resume protocol enforces this by counting a checkpointed step's `started` entries before redispatching it, rather than retrying without bound.

**Accepted residual: prompt injection from reviewed content, blast radius raised.** Content `review-orchestrator` reads during a review (a malicious comment in the diff under review) is a threat class this repo already accepts for the top-level session running these skills today. What changes here is blast radius: `review-orchestrator` can nest-dispatch `code-writer` or a reviewer persona and then release the commit gate itself. No human turn sits in between. Only a synthesized summary is surfaced. A successful injection therefore now reaches a gate-released change, not merely a written diff. No control beyond the two hooks above is added for this; it stays consistent with this repo's stated local-tooling, cooperative-agent threat model.

**Accepted residual: `_fragment_invokes_canonical_git`'s two match arms both trust PATH, unlike the realpath-resolved checks on the three helper scripts.** The bare-word arm accepts a fragment command word that equals the literal string `git` with no resolution at all, and the `CANONICAL_GIT` arm accepts a match against `command -v git`'s output resolved once via PATH at hook-eval time — both resolve through the same PATH lookup the eventual `git` invocation itself resolves through at exec time, so PATH poisoning ahead of this hook's own invocation defeats either arm identically, and no comparison this hook could run would detect it (the realpath-resolved helper-script comparison isn't immune either, since `_lib_realpath_m`'s own `realpath`/`grealpath`/`basename`/`dirname` calls are themselves bare PATH-resolved command names). Accepting this gap is consistent with `SECURITY.md`'s "Out of scope" boundary, which already places an attacker with write access to `<config-dir>` — a prerequisite for poisoning PATH ahead of this hook's own invocation — outside the hook system's protection.

**Closed: the ANSI-C/brace-expansion/command-substitution bypass class no longer reaches either hook's dangerous-flag checks.** `_lib_strip_word_quotes` itself still does not decode a `$'...'` region's own `\xHH` hex, `\NNN` octal, or `\uHHHH`/`\UHHHHHHHH` Unicode escapes, nor resolve a `${var:-flag}` parameter-expansion default. So a fragment word spelling a dangerous flag through ANSI-C escaping (e.g. `$'--tex\x74conv'` decoding to `--textconv`), brace expansion (`--te{x,}tconv`), or command/backtick substitution (`$(printf -- --textconv)`) still passes through the function unrecognized. Both hooks now close this class with a closed character-class check rather than a growing set of individually-matched escape patterns. `require-review-orchestrator-bash.sh` denies any command containing a character outside the allowlist `[A-Za-z0-9_./=:,@+~^%'"<>|&; -]` before any fragment splitting or word matching runs. That check runs against the whole raw command text, since the hook's entire legitimate command surface needs none of `$`, backtick, `{`, or `}` at all. `deny-reviewer-tree-mutation.sh` cannot use a whole-command allowlist the same way, because its twelve pre-existing reviewer personas (`ciso-reviewer`, the seven `staff-*` agents, `skill-fidelity-reviewer`, `comment-discipline-reviewer`, `Explore`, `Plan`) legitimately run arbitrary read-only shell commands outside git. It instead splits the raw command on true command-chaining operators only (`_top_level_command_segments`, deliberately coarser than `_lib_split_fragments`'s own `$(...)`/backtick sub-splitting, which would delete the very bytes this check looks for), and denies any resulting git-invoking segment whose own raw text carries `$`, a backtick, `{`, or `}`. Both checks run ahead of `_lib_strip_word_quotes`'s own stripping, so an escape-bearing fragment is denied before this gap in the shared helper can matter.

**Accepted residual: a glob-obfuscated command word can still resolve to a same-named local `git` at real bash execution time, bypassing `deny-reviewer-tree-mutation.sh`'s entire git-specific enforcement.** `_lib_fragment_invokes_git` (`_lib.sh`, unmodified by this diff) recognizes a git invocation by literal word-equality only — a fragment word like `g?t` or `g*t` never equals the literal string `git` or matches `*/git`, so this hook's git-anchored checks (the command-invoking-flag check, the write-target-flag check, the env-assignment-before-git check, and the read-only-subcommand allowlist) never fire on it, and the fragment falls through to this hook's default allow. Real bash, executing the command afterward, still performs its own filename-generation on the unquoted `g?t`/`g*t` word and resolves it to whatever file matching that glob sits in the reviewer's cwd — if that file is literally named `git`, the fragment executes as a full git invocation with none of this hook's git-specific denials ever having applied. The precondition is a file named exactly `git`, reachable via the glob pattern, in the reviewer's own working directory. Confirmed empirically this round: `g?t commit -am pwned` and `g*t log --textconv` are both allowed by `deny-reviewer-tree-mutation.sh`. `require-review-orchestrator-bash.sh` is not reachable the same way: its character-class allowlist above excludes `?`, `*`, `[`, and `]` from the raw command text outright, so a glob pattern of this shape can never appear in an accepted payload there at all. Accepted under the same cooperative-agent threat model the two residuals above already invoke; no fix planned.

# `attribution.sessionUrl: false` ships in both settings files, reversing [§40](attribution-in-skill-prose-and-hook.md)'s `sessionUrl` paragraph

*2026-09-05. Formerly `docs/design-decisions.md` §63.*

Set `attribution.sessionUrl` to `false` in both the stow-source `claude/.claude/settings.json` and the repo-local `.claude/settings.json`. This public repo's `main` carries a `Claude-Session: https://claude.ai/code/session_<id>` trailer on 113 of the 116 commits merged since 2026-08-21 (533 across all branches). The stow-source entry covers every repo and every session on this machine — the population that produced all 113 trailers — unconditionally. The repo-local entry is **expected**, pending the open question below, to cover a clone made by an outside contributor or a cloud container, since neither has the stow package and neither therefore has any of this repo's hooks or its stow-source settings.

**The #77830 account [§40](attribution-in-skill-prose-and-hook.md) shipped is wrong on two counts, and the correction is the reason this reversal exists at all.** [§40](attribution-in-skill-prose-and-hook.md) cited anthropics/claude-code #77830 as reproducing a bug where the `Claude-Session:` trailer is injected via the Bash tool description and ignores `attribution`, and left `sessionUrl` at its default of `true` on that basis. Reading the full comment thread rather than the rendered issue page shows the reporter set `attribution.commit: ""`, not `sessionUrl`, and the issue is closed as *completed*, not left open as a live bug. An Anthropic collaborator names `attribution.sessionUrl` as the trailer's actual control, and a reader of the shipped 2.1.231 bundle quotes the early return that implements it: setting it to `false` short-circuits before the trailer is built. The key has existed since v2.1.182; this machine runs 2.1.261. That maintainer reply also addresses a question [§40](attribution-in-skill-prose-and-hook.md)'s body leaves open: the trailer is reported to fire only from a web or Remote Control session, never a plain local terminal one. This repo's own history fits that account only partially — see the unresolved tension below. Because the wrong account was the stated basis for [§40](attribution-in-skill-prose-and-hook.md)'s `sessionUrl` conclusion, correcting it removes that conclusion's foundation rather than adding a competing one.

**`commit` and `pr` stay unset, as established in [§40](attribution-in-skill-prose-and-hook.md), unchanged here.** The one new fact this entry adds: `attribution.commit: ""` is counterproductive, not merely ineffective. An empty string is falsy, so the session trailer becomes the *sole* trailer instead of being suppressed — the reporter's own reproduction in #77830 hit exactly this. `CLAUDE_CODE_SUPPRESS_SESSION_ATTRIBUTION=1`, a separate environment variable documented in the same thread to short-circuit ahead of the settings check, is not shipped: it is machine-local and uncommittable for other consumers, and redundant with a setting already confirmed to work. It is the fallback if `sessionUrl` regresses.

**The blast-radius test this repo applies elsewhere, run here and its mismatch accepted rather than dissolved.** [§39](claudemdexcludes-nested-discovery-duplicate.md) and [§40](attribution-in-skill-prose-and-hook.md) both weigh a "wider than any condition this repo has" test before putting repo-specific policy at stow scope, and [§40](attribution-in-skill-prose-and-hook.md) declined `attribution.commit` there on exactly that mismatch. This change does not pass that test either: the threat model is one public repo, the fix lands at user scope, and it changes behavior in every other repo every consumer works in, including a private repo where an internal AI-authorship trail may be wanted. Removing a link invents nothing, where setting `commit` would have imposed an invented trailer format — a real distinction, but one about the *kind* of change, not about blast radius exceeding the problem's scope, so it does not on its own answer the test. What actually makes the wider default acceptable is that the removal is per-repo reversible by a consumer editing their own tracked stow-source file — and that leg is entirely contingent on the open project-scope question below. If that question resolves false, this decision takes exactly the shape [§40](attribution-in-skill-prose-and-hook.md) rejected for `commit`: a non-reversible wider-than-the-condition default imposed on every private repo to fix a public-repo-specific problem. In that case the blast-radius justification itself needs revisiting, not only the coverage and opt-back-in claims below.

**Whether project-scope `attribution` is honored is unverified, and it is load-bearing.** It is the entire basis for saying the repo-local file protects an outside contributor's clone or a cloud container, and for the reversibility leg above. No CLI subcommand on Claude Code 2.1.261 reports a resolved settings value — the full command set is `agents`, `attach`, `auth`, `auto-mode`, `doctor`, `gateway`, `import`, `install`, `logs`, `mcp`, `plugin`, `project`, `respawn`, `rm`, `setup-token`, `stop`, `ultrareview`, `update`, and `claude doctor` reads settings files but never surfaces a key's resolved value — so this question is answered less rigorously than [§43](ui-notification-defaults-in-stow-source.md)'s own scope question: no cheap CLI probe exists here, and the only route is a live emitting session. Shipping the entry regardless costs one line and is harmless if project scope turns out to be ignored, since that population is then exactly where it was before this change. The risk is not in the key, it is in overclaiming the coverage in a durable record before verification — so every surface stating this coverage (this entry, the CHANGELOG) uses "expected," not "confirmed," until a session with no user-scope `attribution` key present has been run through the same before/after check the stow-source entry got.

**An unresolved tension, not a resolution: the "web or Remote Control" scoping may cover only the PR-description surface.** One hypothesis: the maintainer's qualifier scopes the PR-description clause only, leaving commit trailers unconditional across every session type — consistent with 113 of 116 commits on `main` carrying one regardless of how the authoring session started, and with the engineer's own recollection that the PR-body leaks they manually caught coincide with a recent increase in their own Remote Control session usage — an approximate, unaudited recollection, not a confirmed count. Against it: a dispatched subagent session on this machine, not a web or Remote Control session, carried the identical unconditional PR-description instruction in its own system prompt. Both the correlation and the counter-evidence are recorded here as unresolved so a future reader does not treat this as more settled than it is.

**The rollout window is expected, not established.** Config-adjacent state in this harness appears to be session-start-scoped rather than hot-reloaded, so a consumer with a session already open when they `git pull` is expected to keep emitting the trailer until they start a new one. The nearest supporting evidence, `.claude/plans/engagement-lessons-fixes.md:130`, is about skill registration — a different subsystem — so this stays qualified as "expected" rather than confirmed for the attribution settings layer specifically.

**No opt-back-in path is confirmed.** The natural candidate — a per-repo `.claude/settings.json` or `.claude/settings.local.json` entry setting `attribution.sessionUrl: true` — is the same open project-scope question above. This repo's CHANGELOG publishes that shape for `disableWorkflows`/`disableArtifact` ([§31](artifact-workflow-disabled-by-default.md)), which is suggestive but is exactly the cross-key analogy [§43](ui-notification-defaults-in-stow-source.md) warns against: [§43](ui-notification-defaults-in-stow-source.md) found `tui`, `theme`, and `agentPushNotifEnabled` *not* honored at a scope engineers assumed worked. The only confirmed recourse today is editing the tracked stow-source file directly, re-clobbered on the next `git pull` unless carried forward — the same disclosure [§49](schedulewakeup-denied-by-bare-tool-name.md)'s CHANGELOG entry makes for its own reversal path. This entry is the canonical, Revisit-tracked home for this status; the CHANGELOG points here rather than freezing a claim that may go stale.

**A content-shape detector was considered and rejected, twice.** A repo-wide mechanical gate on session identifiers in committed content — a commit message, PR body, issue comment, `gh api` payload, or plan file — was declined by the engineer in favor of the setting alone. The residual is real: the only existing control is the advisory line at `claude-skills/skills/plan-it/SKILL.md:139`, added 2026-08-10, and it still failed to prevent the one tracked-file instance found in this repo (`.claude/plans/redact-hook-uuid-detection-gap.md:49`, committed 2026-08-23, 13 days after the advisory line shipped). That control also never covered the PR-body surface at all — the engineer recalls — an approximate, unaudited recollection — catching two or three bare session-URL lines in PR bodies by manual review within roughly the past two weeks. A second, narrower option was also weighed: extending `pr-description/SKILL.md`'s own `## Checks` step to flag an extra bare `claude.ai/code/session_` line beyond its own prescribed trailer. Declined on the same reasoning as the broader detector — `attribution.sessionUrl: false` is expected to suppress the harness's PR-description injection at its source, the same mechanism already fixing the commit-trailer surface, and the disclosed PR-body leaks predate that fix.

**Merge is a second surface, closable by configuration but not closed here.** This repo permits only squash merges and sets `squash_merge_commit_message` to `COMMIT_MESSAGES` (`allow_squash: true`, `allow_merge: false`, `allow_rebase: false`) — GitHub concatenates each branch commit's message into the squash commit body, which is the precise, verified mechanism by which all 113 trailers reached `main`. `squash_merge_commit_message` also accepts `PR_BODY` or `BLANK`; setting it to `PR_BODY` would stop commit-message bodies, and any trailer they carry, from reaching `main`'s history at all — mechanically, independent of whether project-scope `attribution` is honored. That change is not made here: it rewrites this repo's history format (commit bodies become frozen PR descriptions instead of the current per-commit narrative), which is a decision on its own terms, recommended to the engineer separately rather than folded into this PR. Until it ships, the only control on the merge surface is clearing the concatenated commit bodies from the squash-merge message box by hand at merge time.

**The 533 published pointers are a permanent public index, not 533 independent low-value leaks.** Together they map commit metadata to session identifiers; in any account-compromise scenario reached by an unrelated channel, an attacker's search cost for the highest-value private-project sessions is already zero, because this repository published the target list. Rewriting history to purge them is declined, with the engineer's explicit sign-off, as disproportionate to a metadata leak against a token whose entropy rules out enumeration and whose owning sessions are private by default. Two owner-side levers remain, both actions on the owner's Claude account rather than a repository change, and neither belongs in this diff: auditing whether any of the 533 published sessions was ever explicitly shared, and purging transcript content behind published IDs known to carry private-project material. Neither has an established mechanism today, and both are accepted as an indefinite residual rather than left as an oversight: no next step is scheduled, and this entry is where a future audit of either lever should be recorded.

**Revisit** if any of:

- Project-scope `attribution` turns out not to be honored — this reopens the repo-local file's coverage claim, the opt-back-in status, *and* the blast-radius justification above, not only the two narrower claims.
- A second agent-authored session identifier reaches a commit, PR body, issue comment, `gh api` payload, or plan file.
- A fourth attribution channel ships enabled by default (three have already reached histories with attribution turned off: #77830, #82690, #83226).
- `attribution` gains a property covering PR or issue review comments.
- The range-scoped audit below ever returns non-zero.
- A PR body is ever found to carry a session URL after this fix ships. The range-scoped `git log` audit cannot detect that — it only ever sees commit-message content, never PR-description text — so this surface has no automated regression signal and depends on continued manual review until the unresolved tension above is independently resolved.

Record the fix's merge SHA here once this change merges, together with the range-scoped audit `git log <fix-sha>..origin/main --format=%B | grep -c 'claude.ai/code'`, expected to return 0. The unscoped form, `git log origin/main --format=%B | grep -c 'claude.ai/code'`, returns 403 as of 2026-09-05 and can only grow, since the 113 pre-existing trailers stay in history by design — a counter that starts saturated can never distinguish clean from regressed.

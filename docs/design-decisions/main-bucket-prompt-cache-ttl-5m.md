# Set `promptCacheTtl: "5m"` for the main-conversation prompt-cache bucket

*2026-09-20.*

**The lever and its two-bucket structure.** Claude Code sorts every request into one of two prompt-cache TTL buckets — the main conversation, and "everything else" (subagents, workflows, forks, compaction) — each with its own settings key, `promptCacheTtl` and `subagentPromptCacheTtl`, accepting only `"5m"` or `"1h"`. `claude/.claude/settings.json` now sets `promptCacheTtl: "5m"`, the stow-source file that maps onto every consumer's `~/.claude/settings.json`. `subagentPromptCacheTtl` stays absent; see below. This verdict is scoped to this machine's own transcript corpus and billing regime, unlike a universal privacy/security default such as `attribution.sessionUrl` that benefits every contributor regardless of profile — this key, by contrast, is a cheap, self-checkable, tunable cost lever with a documented reversal path. It is therefore not mirrored into this repo's own project-scope `.claude/settings.json`, which would impose one engineer's billing-regime-specific, single-corpus verdict on every contributor. The stow-global mechanism actually chosen carries the same single-corpus generalization risk at comparable or wider reach — every stow consumer, not just this repo's own contributors — but that reach is an acceptable tradeoff here, and the per-machine escape hatch below tells a reader with a different traffic pattern exactly how to re-verify it for themselves.

**Why 5m for main.** `cache-rebuild --ttl-verdict` scores each project's own transcript corpus separately rather than pooling them, against a pre-registered decision rule:

- A root's dominant tier must clear a dominance-share gate before it contributes to either direction's verdict at all.
- A consistent root's own net-dollar margin must clear two independently-grounded idle-band boundary points rather than one.
- A consistent 1-hour root additionally runs a zero-price raw-token tiebreaker that must agree with the dollar accounting's own direction.

A run against this machine's corpus returned `adopt` for the `main` bucket in the 1h→5m direction:

- The 1h→5m recommendation held in every project the gate admitted to the verdict.
- Every admitted project cleared both boundary points.
- The raw-token tiebreaker agreed.

A project the gate holds back as a near-tie or as carrying no data contributes to the verdict in neither direction, by construction — it is not evidence against the recommendation, it is simply silent. The underlying figures, the per-project decomposition, and the number of projects involved are all withheld here under this repo's CLAUDE.md § "Redact private-project-identifying content" and `docs/private-project-redaction.md` § "Publishing a tooling measurement." A reader whose own session pattern differs materially from this machine's corpus should run `cache-rebuild --ttl-verdict` against their own transcripts before assuming this default is a saving rather than a regression for them.

**Why `subagentPromptCacheTtl` stays unset.** The vendor's TTL-selection precedence chain is one ordered fallback list, not a pair of mutually exclusive mechanisms: `FORCE_PROMPT_CACHING_5M=1`, then the bucket's own environment variable, then the bucket's *setting*, then — for a subagent's own requests only — the `cacheTtl` value in that subagent's `experimental` frontmatter field, then `ENABLE_PROMPT_CACHING_1H=1`, then the vendor's own default for the request's bucket. Because the setting rung precedes the frontmatter rung, setting `subagentPromptCacheTtl` to any value — including `"5m"`, which the settings reference documents as the subagent bucket's current default and is *expected*, not confirmed, to change no behavior today across every billing regime — would silently outrank and disable per-agent `experimental.cacheTtl` for every subagent dispatch on this machine. The verdict for the subagent bucket was `decline`, so there is no measured basis to write any value there, and leaving the key absent keeps the per-agent lever reachable for a future, more targeted decision.

**The corpus's billing regime bounds the verdict's reach.** The main bucket's *default* TTL is billing-regime-conditional: one hour on a Claude subscription within plan usage, five minutes under usage credits, an API key, or a cloud provider. The measured corpus is subscription-billed, inferable from its main-bucket writes landing on the one-hour tier at all — not proof of it, since `ENABLE_PROMPT_CACHING_1H=1` can force that tier under any regime and would not be visible to an in-tree grep, but consistent with subscription billing and with this repo's own existing qualifier at `docs/transcript-analysis.md:939`. A consumer already on metered, API-key, or cloud billing was already on the five-minute tier by vendor default; for that consumer, this change pins a value their harness already used and is a no-op, not a behavior change.

**Reversing this change does not restore `"1h"`.** Deleting the `promptCacheTtl` key restores whichever default the vendor currently applies to the reader's own billing regime — conditional, per the paragraph above, and free to move on a vendor-side change with no edit to this repo. A reader who specifically wants the one-hour tier has to set `promptCacheTtl: "1h"` explicitly; reverting this diff does not get them there.

**Version floor.** `promptCacheTtl` requires Claude Code v2.1.242 or later (`https://code.claude.com/docs/en/settings-reference`). The `experimental.cacheTtl` subagent-frontmatter mechanism the "Why `subagentPromptCacheTtl` stays unset" section above relies on carries a stricter floor, v2.1.248 (`https://code.claude.com/docs/en/prompt-caching`). How an older CLI treats an unrecognized top-level settings key is not stated by any source read for this change; the expectation — not a confirmed fact — is that it is ignored, leaving a below-floor consumer at their prior behavior rather than a regression. SchemaStore's `claude-code-settings.json` sets top-level `additionalProperties: true` and lists neither cache-TTL key, which is real evidence that the *documented schema* tolerates an unrecognized top-level key; it says nothing about what validation the CLI itself performs at load time, so it narrows this uncertainty without closing it.

**Consumer recourse, in precedence order.** The vendor's own ordered list (above) guarantees that an environment variable outranks a settings-file value, so the bucket's own environment variable, `CLAUDE_CODE_PROMPT_CACHE_TTL` (accepting `5m` or `1h`; any other value is ignored), is the mechanically certain override for a consumer with a different traffic mix. A higher-precedence settings file (project or project-local scope) is a second, weaker option: it is only *documented*, not observed to work, in this repo's own experience. Two prior entries in this directory found a documented settings scope not holding for a sibling key in this same file. [ui-notification-defaults-in-stow-source.md](ui-notification-defaults-in-stow-source.md) found `theme`, `tui`, and `agentPushNotifEnabled` not honored at `~/.claude/settings.local.json`. [schedulewakeup-denied-by-bare-tool-name.md](schedulewakeup-denied-by-bare-tool-name.md) found that neither project nor project-local scope re-enabled a denied tool when tried. The only *confirmed* recourse today is editing the tracked `claude/.claude/settings.json` directly, re-clobbered on the next `git pull` unless carried forward.

**When the key takes effect is not established.** Config-adjacent state in this harness appears to be session-start-scoped rather than hot-reloaded, so a consumer with a session already open when they `git pull` is *expected* — not confirmed — to keep the prior tier until their next launch, the same hedge [attributionsessionurl-false-ships-in-both-settings.md](attributionsessionurl-false-ships-in-both-settings.md) records for this same file. This is checkable directly: run `claude -p "hello" --output-format json` and read `usage.cache_creation` — a one-hour write reports under `ephemeral_1h_input_tokens`, a five-minute write under `ephemeral_5m_input_tokens` (`https://code.claude.com/docs/en/prompt-caching`). A follow-up `cache-rebuild` scan confirming post-rollout main-origin writes land under the 5m field is the indirect alternative.

**Revisit** if any of:

- A later `cache-rebuild --ttl-verdict` run inverts the `main`-bucket verdict.
- The `subagent`-bucket verdict changes from `decline`.
- The vendor changes the 1.25x/2x price multipliers or the six-rung precedence chain.
- The vendor changes either bucket's *default* value — a distinct trigger from the multiplier and precedence cases above, because it silently changes what reverting this change actually restores (see "Reversing this change" above).
- This machine's own billing regime changes.
- `docs/cost-levers-considered.md`'s Cache-TTL row gets its full register update, at which point this entry's pointer there is superseded.
- Pre-v2.1.242 CLI compatibility is confirmed empirically or by the vendor.

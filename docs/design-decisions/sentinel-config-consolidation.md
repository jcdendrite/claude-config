# Fourteen sentinel files consolidated into one schema-driven config file

*2026-09-07.*

Replaced 14 machine- and account-scope sentinel files — 13 already tracked in `install.sh`'s own `SENTINEL_INVENTORY`, plus `.authorization-boundary-disabled`, a working kill switch that predated this migration but had never been added to that inventory — with one hand-editable state file per config dir (`<config-dir>/claude-config.toml`) plus one in-repo schema (`claude/.claude/hooks/config-keys.psv`) that declares every key's type, default, resolution mode, and legacy-file mapping. Each of the 14 had been a standalone presence- or content-checked file, with its own resolution logic re-derived by every consumer. One reader per language runtime (`_config.sh`, `_config.py`) replaces what had been three independent config-dir resolvers (`_lib.sh`, `_config_dir.py`, and `install.sh`'s own inline copy) and 12 independent presence/content checks. See [`docs/config-file.md`](../config-file.md) for the file format, schema, per-key table, and migration mechanics — this entry covers only why the shape was chosen, not how to use it.

**The motivating bug was a content-grammar divergence, not a missing feature.** `install.sh:531-547`'s `[:space:]` trim and `pr-cost-section.sh:20-26`'s `[:blank:]` trim disagreed on a CRLF-authored `pr-cost-disclosure` file — one reported it `ENABLED`, the other published nothing. Patching that one trim call would have left every other sentinel's independent re-derivation of "what does this file mean" in place, an unpatched instance of the same bug class waiting to recur. The schema declares each key's grammar once (`type: bool` or `enum:<value>`); every reader asks `_config_value`/`config_value()` rather than re-parsing raw file content itself.

**A dedicated state-file format was chosen over two lighter alternatives.** Keeping one file per key and adding only shared readers would have closed the parser divergence but left `install.sh`'s writer creating N files whose names are a duplicated constant across a dozen hooks, with no single surface for a query CLI. Storing the keys in Claude Code's own `settings.json` was rejected as vendor-schema-owned (a future first-party key could collide) and comment-free, which would have killed the hand-editable `docs-anchor` convention the sentinel files already carried and this file preserves.

**Key polarity flips to positive sense.** A kill-switch sentinel's `*-disabled` framing existed only because file-absence can't express "on by default" — a key-value file can, so `pr-description-tighten-prose-optout` becomes `pr_description_tighten_prose = true` (default `true`), and every other kill switch becomes a positively-named capability defaulting `true`. The old polarity survives only as a `legacy-polarity` schema column describing what the superseded file's presence meant, load-bearing for reading a legacy file that predates this migration, never for anything new.

**The legacy fallback is permanent, not time-boxed.** `claude/.claude/**` goes live on `git pull` with no guaranteed `install.sh` re-run, so there is no point at which every stow consumer has demonstrably migrated — a removal date for the legacy-file read path would be unverifiable, and its arrival would silently disable enforcement for whoever hadn't. Every schema row keeps its `legacy-filename`/`legacy-polarity` columns for as long as this scheme exists.

**Consolidating 15 toggles into one file raises write-path blast radius.** A single agent-mediated write can now touch any of the 15 keys, including the five enforcement-critical ones (`worktree_required`, `autonomous_shipping`, `round_consult_gate`, `commit_stall_block`, `authorization_boundary_restore`).

**Write-gate enforcement for `claude-config.toml` was descoped after review did not converge.** A dedicated write-gating hook (`enforce-config-write-shape.sh`) was built to mitigate the blast radius above, sharing `enforce-marker-script-shape.sh`'s shape-matching engine. Across 56 review rounds over 6 days, each fix opened a new bypass the next round found. One of those findings was HIGH-severity: the legacy-filename protection collided with this repo's own, unrelated `worktree-required` per-project opt-in convention. A `plan-architect` consult concluded that reimplementing bash's word-expansion semantics from outside, over adversarial command text, does not converge, and recommended shipping only the migration. Dropping the shared `_lib.sh` engine also meant a brace-expansion hardening developed in-branch for `enforce-marker-script-shape.sh`'s own Bash arms, independent of `claude-config.toml`, was never shipped to `origin/main`. The commit that built it, `e7105d21`, never reached `origin/main`, so no stow consumer's real protection regresses; see that hook's own header for the disclosed brace-expansion gap. The self-authorization gap the hook was meant to close predates this migration and is unchanged by it. The user explicitly decided not to track it as a separate follow-up, relying on Claude Code's existing ask-by-default permission prompt instead.

**`migrate-legacy-config.sh`'s import step is direction-aware for the five enforcement-critical keys specifically, not TTY-gated.** Promoting a legacy value into a state-file row makes it *harder* to reverse than the raw legacy file was, since the row then becomes authoritative and nothing gates a later Claude-Code-tool-mediated attempt to flip it back, beyond the harness's own ask-by-default permission prompt.

- **`[ -t 0 ]` is not a security boundary:** a single Bash call can self-allocate a pseudo-terminal (`script -qc "..." /dev/null`) and satisfy the check with no human involved, since the check runs inside the very subprocess it is meant to constrain. A TTY check cannot mechanically prove a human is at the other end of a prompt — every enforcement-critical write path must therefore be one where impersonating the human buys nothing, or must not exist.
- **Fail-closed-direction import:** the import step compares each enforcement-critical key's legacy-derived value against that key's fail-closed value (`worktree_required=true`, `autonomous_shipping=false`, `round_consult_gate=true`, `commit_stall_block=true`, `authorization_boundary_restore=true`) and writes it with no gate at all when the two match, since that can only make the machine more restrictive. A permissive-direction value is never written — it is deferred (recorded the same way an unreadable legacy file already was) and printed for a human to hand-paste into `claude-config.toml` instead.

**`install.sh`'s own interactive opt-in prompts carry the same `[ -t 0 ]` pattern used elsewhere in this migration (see the paragraph above) and are equally pty-spoofable — accepted and disclosed, not fixed, here.** `configure_machine_level_opt_ins`'s `_prompt_sentinel_opt_in` gates `worktree_required`/`autonomous_shipping` (and every other promptable key) behind the same TTY check; a self-allocated pty satisfies it the same way, and needs no legacy file planted first. This is pre-existing, unchanged from `main`'s sentinel-file-based prompts, not a regression this migration introduces, and is intentionally left as-is: these prompts serve real first-run onboarding UX — a human deciding, on first install, whether to enable worktree enforcement or autonomous shipping — that removing interactivity would eliminate.

# Fourteen sentinel files consolidated into one schema-driven config file

*2026-09-07.*

Replaced 14 machine- and account-scope sentinel files — 13 already tracked in `install.sh`'s own `SENTINEL_INVENTORY`, plus `.authorization-boundary-disabled`, a working kill switch that predated this migration but had never been added to that inventory — with one hand-editable state file per config dir (`<config-dir>/claude-config.toml`) plus one in-repo schema (`claude/.claude/hooks/config-keys.psv`) that declares every key's type, default, resolution mode, and legacy-file mapping. Each of the 14 had been a standalone presence- or content-checked file, with its own resolution logic re-derived by every consumer. One reader per language runtime (`_config.sh`, `_config.py`) replaces what had been three independent config-dir resolvers (`_lib.sh`, `_config_dir.py`, and `install.sh`'s own inline copy) and 12 independent presence/content checks. See [`docs/config-file.md`](../config-file.md) for the file format, schema, per-key table, and migration mechanics — this entry covers only why the shape was chosen, not how to use it.

**The motivating bug was a content-grammar divergence, not a missing feature.** `install.sh:531-547`'s `[:space:]` trim and `pr-cost-section.sh:20-26`'s `[:blank:]` trim disagreed on a CRLF-authored `pr-cost-disclosure` file — one reported it `ENABLED`, the other published nothing. Patching that one trim call would have left every other sentinel's independent re-derivation of "what does this file mean" in place, an unpatched instance of the same bug class waiting to recur. The schema declares each key's grammar once (`type: bool` or `enum:<value>`); every reader asks `_config_value`/`config_value()` rather than re-parsing raw file content itself.

**A dedicated state-file format was chosen over two lighter alternatives.** Keeping one file per key and adding only shared readers would have closed the parser divergence but left `install.sh`'s writer creating N files whose names are a duplicated constant across a dozen hooks, with no single surface for a query CLI. Storing the keys in Claude Code's own `settings.json` was rejected as vendor-schema-owned (a future first-party key could collide) and comment-free, which would have killed the hand-editable `docs-anchor` convention the sentinel files already carried and this file preserves.

**Key polarity flips to positive sense.** A kill-switch sentinel's `*-disabled` framing existed only because file-absence can't express "on by default" — a key-value file can, so `pr-description-tighten-prose-optout` becomes `pr_description_tighten_prose = true` (default `true`), and every other kill switch becomes a positively-named capability defaulting `true`. The old polarity survives only as a `legacy-polarity` schema column describing what the superseded file's presence meant, load-bearing for reading a legacy file that predates this migration, never for anything new.

**The legacy fallback is permanent, not time-boxed.** `claude/.claude/**` goes live on `git pull` with no guaranteed `install.sh` re-run, so there is no point at which every stow consumer has demonstrably migrated — a removal date for the legacy-file read path would be unverifiable, and its arrival would silently disable enforcement for whoever hadn't. Every schema row keeps its `legacy-filename`/`legacy-polarity` columns for as long as this scheme exists.

**Consolidating 14 toggles into one file raises write-path blast radius, mitigated by a dedicated write-gating hook rather than a permissions.allow/deny rule.** A single agent-mediated write can now touch any of the 14 keys, including the five enforcement-critical ones (`worktree_required`, `autonomous_shipping`, `round_consult_gate`, `commit_stall_block`, `authorization_boundary_restore`). `enforce-config-write-shape.sh` is a guardrail against ordinary and accidental agent writes, not a boundary that closes every path a determined adversary could reach: it denies a Claude-Code-tool-mediated `Write`/`Edit`/`MultiEdit` targeting the resolved `claude-config.toml` path and a `Bash` command invoking `_config_set` by name or whose redirect/utility-write candidates resolve to the same path, sharing `enforce-marker-script-shape.sh`'s shape-matching and redirect-candidate-extraction engine (moved into `_lib.sh` as shared primitives) rather than a second, independently maintained copy of that security-critical logic — the TTY-spoofing finding two paragraphs below is one documented example of a path this kind of guardrail does not close. A `permissions.deny` glob was rejected: it matches file-write tool calls only, never Bash command text, so it can't close a `source _config.sh && _config_set ...` or a plain `printf ... >> claude-config.toml` vector. A human editing the file directly, outside Claude Code's own tool calls, is unaffected — that is the file's whole hand-editable design goal.

**`migrate-legacy-config.sh`'s import step is direction-aware for the five enforcement-critical keys specifically, not TTY-gated.** Promoting a legacy value into a state-file row makes it *harder* to reverse than the raw legacy file was, since the row then becomes authoritative. The write-gating hook becomes a guardrail against every later Claude-Code-tool-mediated attempt to flip the row back, not a boundary that closes every path to it — a legitimate remediation session conducted through Claude Code's own tools is blocked the same as an illegitimate one, while a human editing the file directly, or one of the residual write shapes the hook discloses but does not close, is not. Because no hook gates writes to the legacy kill-switch files themselves, an agent could otherwise plant one (`touch ~/.claude/.round-consult-gate-disabled`) and, on any machine that has pulled this migration's hook code but not yet run `install.sh`, entrench it in one script call. `[ -t 0 ]` is not a security boundary here: a single Bash call can self-allocate a pseudo-terminal (`script -qc "..." /dev/null`) and satisfy the check with no human involved, since the check runs inside the very subprocess it is meant to constrain. This repo can mechanically deny an agent a write; it cannot mechanically prove a human is at the other end of a prompt. Every enforcement-critical write path must therefore be one where impersonating the human buys nothing, or must not exist. The import step compares each enforcement-critical key's legacy-derived value against that key's fail-closed value (`worktree_required=true`, `autonomous_shipping=false`, `round_consult_gate=true`, `commit_stall_block=true`, `authorization_boundary_restore=true`): a value matching the fail-closed direction imports with no gate at all, since it can only make the machine more restrictive. A permissive-direction value is never written — it is deferred (recorded the same way an unreadable legacy file already was) and printed for a human to hand-paste into `claude-config.toml` instead.

**`install.sh`'s own interactive opt-in prompts carry the identical `[ -t 0 ]` pattern the migration script's import step used to rely on, and are equally pty-spoofable — accepted and disclosed, not fixed, here.** `configure_machine_level_opt_ins`'s `_prompt_sentinel_opt_in` gates `worktree_required`/`autonomous_shipping` (and every other promptable key) behind the same TTY check; a self-allocated pty satisfies it the same way, and needs no legacy file planted first. This is pre-existing, unchanged from `main`'s sentinel-file-based prompts, not a regression this migration introduces, and is intentionally left as-is: these prompts serve real first-run onboarding UX — a human deciding, on first install, whether to enable worktree enforcement or autonomous shipping — that removing interactivity would eliminate.

This consolidation went through six rounds of `/plan-review` (`staff-platform-engineer`, `staff-backend-engineer`, `staff-sdet`, `ciso-reviewer`) plus two `plan-architect` design consults before implementation; `.claude/plans/sentinel-config-migration.md`'s own assumption ledger records each round's findings and how they were resolved.

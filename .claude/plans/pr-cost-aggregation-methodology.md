# Combine two machines' pr-cost exports into one aggregate

## Context

Goal: define and run a one-off methodology that combines this machine's and a second machine's `pr-cost-export` files into one correct aggregate: PR count, token counts, cost, and models used. The result informs `docs/case-studies/handoff-threshold-impact.md`'s "Cross-account component" around the 2026-08-22 handoff-nudge-cap retune (360,000 → 150,000 tokens).

Why now: `pr-cost-export` (#948) just merged, and both machines have run it for real. Both exports carry `corpus_override=0` and the DO-NOT-PUBLISH marker. The second export's coverage was fixed before this plan runs. Its provenance line also flags legacy hand-chosen machine labels. The two `corpus=` digests differ, which is expected for different account sets.

Intended outcome:
- A reviewable combining procedure, committed as the canonical consumer procedure in `docs/pr-cost.md`.
- A one-off script, kept outside git, that implements it.
- A private result for the owner.
- A case-study update that the redaction policy permits.
- A tracked follow-up for a durable subcommand once the methodology is validated.

## Approach

**Design.** A standalone one-off script, kept outside git, combines the two exports. It:
- reads columns by name;
- tags every identity token with its input file;
- groups rows into real PRs, keeping the latest row when one account captured a PR twice, and applying the union rule when the same PR appears in different accounts or on different machines;
- reports dollars as recorded, labeled by whether a git-history check proves every row's pricing state comparable, and compares dollars across eras only when it does.

The procedure itself is committed to `docs/pr-cost.md`, replacing two rules there that the schema can't support. Every era-split figure stays private to the owner. The case-study update records only that the read happened; its result, direction included, stays with the owner (row 28).

**Root problem.** Two redacted exports can't be combined correctly by simple concatenation:
- Account tokens collide across the two exports.
- One real PR can appear in several rows.
- Rows were priced under more than one pricing state, with no model split to re-price from.
- The combined corpus is wider than a single account, so its figures can be published only under per-figure owner authorization.

**Threat.** A combined figure that double-counts, silently blends pricing states, or leaks a per-account, per-machine, or per-row figure into a public artifact or a session transcript.

**Givens:**
- **G1.** Rows already in both ledgers carry no per-model split, and they stay that way. The ledger is append-only, and the export copies non-identity cells byte-for-byte (`docs/pr-cost.md:60, :82, :135`). Reason: pr-cost's write contract owns this. A migration would apply only to future rows, and re-deriving old rows needs transcripts that may have aged out (row 23).
- **G2.** The vendor sets per-model rates, and they differ across the models in this corpus. Reason: vendor-imposed.
- **G3.** Account ordinals and `account-K/<kind>-N` tokens are valid only within one export run. Reason: the shipped export's redaction contract. A cross-run anchor would change a contract other call sites share (`.claude/plans/pr-cost-redacted-export-subcommand.md:17`).
- **G4.** Redaction policy bars publishing a before/after split of a wider-than-single-account corpus, even under owner authorization (`docs/private-project-redaction.md:239-242`). Reason: this is the owner's policy, and changing it is the owner's decision (see Open decision).
- **G5.** The second machine's export coverage is fixed as exported. Reason: that machine's local state was fixed before this plan runs.

**Mechanisms.**

**M1: The engineer transfers the file.** `anchors: row1, row2, row24, row26`
- Land the file into a 0700 input directory on this machine. That directory must sit outside every git work tree and every cloud-sync folder.
- Before the transfer runs, the engineer resolves the destination directory's realpath and checks it against both gaps `docs/pr-cost.md:181-191` documents the git-tree check missing: a cloud-sync provider path (iCloud, Dropbox, OneDrive, or similar) and a bare-repo dotfile manager's `--work-tree` (e.g. yadm). Neither gap is mechanically checked; this is a manual pre-flight the engineer performs and confirms, not merely a property the directory is assumed to have.
- Compare SHA-256 digests of the file on both ends, each in a separate terminal.
- This is operational, not a repo change. It is in scope because the method's inputs depend on it.
- The engineer runs it, never an agent — method A's SSH key is gated off agent use (CLAUDE.md §Safety), and method B's manual upload is a third-party-service action CLAUDE.md's Engineering Judgment section already treats as an engineer's own call, not an autonomous one (its blast-radius rule: flag the risk and confirm the approach before an action with reach beyond the immediate change).

Two transfer methods satisfy the properties above; the engineer picks Method A when both machines' network policy allows mutual SSH, and Method B otherwise.

- **Method A (default): direct SSH.** Copy the second machine's export directly over SSH into the 0700 destination directory. Use this method when both machines allow outbound/inbound SSH to each other. Never route the file through a git remote, chat, or a Claude session.
- **Method B (fallback, when either machine's network policy blocks SSH): the engineer's existing manual, temporary cloud-upload channel.** Upload the file, unencrypted, to the cloud-storage folder the engineer already uses for manual, one-off file moves (row 26). Download it into the 0700 destination directory on this machine. Once the SHA-256 match against the second machine's digest confirms the transfer (per the shared step above), the engineer deletes the file from cloud storage. This is a known, accepted residual, not a closed gap, for the same reason row 26 already accepts it elsewhere: the provider's own trash retention (commonly on the order of 30 days) and any file-version history can keep the file recoverable past the delete action, and a cloud-sync client on another device can propagate a copy before the delete step runs.

**M2: A one-off script kept outside git.** `anchors: row3, row21, row22`

The script lives at `<analysis-dir>/combine_pr_cost_exports.py`, with `fixtures/` beside it. `<analysis-dir>` is a placeholder: any directory outside every git work tree and sync folder works. It is not committed, for three reasons:
- Anything under `claude/` ships to every stow consumer, and the repo expects scripts to be tested. The engineer deferred that step (row 3).
- The script needs nothing from the repo. It reads columns by name. The consult suggested importing `pricing._model_rates`, but that can't re-price mixed-model rows (rows 5-6).
- Last time the script was lost, but the spec was the part that mattered (row 22). M10 commits the spec.

Lighter options set aside:
- An interactive pandas session can't be re-run.
- Shell or `awk` over the TSVs: the provenance line shifts `cut`/`awk` columns (`docs/pr-cost.md:126`), and the grouping logic isn't a one-liner.

Heavier option set aside: a durable subcommand (row 3, G1).

**M3: Validate the inputs.** `anchors: row15, row16`
- Line 1 of each input must be the `# pr-cost-export DO-NOT-PUBLISH` provenance line.
- Refuse an input with `corpus_override=1`.
- Refuse two inputs that share a `corpus=` digest or are byte-identical. The same corpus fed twice would double every figure.
- Read columns by header name, and refuse an input missing a required column.
- Refuse a row whose numeric columns (token and dollar counts) don't parse as numbers, or whose `captured_at`/`merged_at` don't parse as dates. This is a per-row refusal (skip that row, count it in `diagnostics.tsv`), not a whole-input refusal, since one malformed row elsewhere in a large ledger shouldn't discard every other row's data.
- Each output file's own provenance line combines both inputs' fields, not copies them: `exported_at` is the later (max) of the two, `declared`, `opted_in`, `skipped_not_opted_in`, and `legacy_machine_value_rows` are each summed across the two inputs, `corpus` is the two inputs' digests joined with `+`, and `corpus_override` is always written as 0 — an input with `corpus_override=1` already triggers the whole-input refusal above before any output is written. Plus DO-NOT-PUBLISH — not only `bucket.tsv` (M11).

**M4: Tag tokens by input.** `anchors: row12`
Prefix every token with its input's label. Within an input, a PR's identity is its input, account, host, repo, and pr tokens.

**M5: Same-account recaptures keep the latest row (layer 1).** `anchors: row10`
- Within one input and account, rows that share host, repo, and pr tokens but differ in machine token are two captures of one corpus.
- Keep the row with the latest `captured_at` date.
- On a same-date tie, keep the row with the larger total tokens, and count the tie as ambiguous.
- `diagnostics.tsv` also reports what summing both rows would have given.

**M6: The union rule across accounts and inputs (layer 2).** `anchors: row11, row13, row14`
- Take two layer-1 PRs from different input/account groups. If their row-13 fingerprints match exactly and both are `ok`, treat them as one real PR: count it once and sum its dollar and token columns.
- Degraded rows never match (row 14). Their zeroed `gh` columns would otherwise match each other. This is the only role the old "drop degraded rows only for `gh`-sourced columns" rule plays here, because the bucket reports no `gh`-sourced field.
- If one fingerprint belongs to two PRs within one group, that proves a collision, and no PR with that fingerprint is merged.
- If a PR matches two PRs of another group, it is not merged.
- Three PR counts are reported privately: rows (an upper bound), layer-1 PRs, and layer-1+2 PRs. The last is the estimate the bucket uses.

Simpler options set aside: counting rows overcounts by construction (row 11), and layer 1 alone misses the cross-ledger duplicates the published study found (row 11). Both are kept as bounds.

**M7: A pricing classification that labels dollars and gates the dollar era comparison.** `anchors: row4, row5, row6, row8, row9`

Steps:
1. The script writes `rate_stamps_present.txt`, which lists the distinct stamp values beneath the provenance line M3 defines.
2. An agent reads `git log -p` over `claude/.claude/scripts/transcript_analysis/pricing.py`. The range runs from the first commit carrying the earliest stamp present to the last commit carrying the latest. To detect whether the earliest present stamp predates `pricing.py`'s own file history (e.g. because that code was extracted from `transcript-analysis.py`), compare the earliest present stamp's date against `pricing.py`'s first-commit date via `git log --follow --diff-filter=A -- claude/.claude/scripts/transcript_analysis/pricing.py`. If the earliest present stamp predates that first-commit date, the search extends into `transcript-analysis.py`'s history using the same `--follow` mechanism; a plain `git log -p` with no `--follow` is not sufficient, since it stops at the commit that created the file at its current path.
3. Every change to pricing code is classified as either an added model row or a rate/logic change. Pricing code means the rate constants, the multipliers, the overrides, `_model_rates`, `_price_turn`, `_token_counts`, and `_cache_write_split`.
4. The reference state is the latest pricing state present. Each stamp is then classified:
   - **Identical:** every commit carrying the stamp has the reference pricing.
   - **Addition-only:** every such commit, for every model it prices, yields the same `_model_rates` output as the reference, and has unchanged `_price_turn`, `_token_counts`, `_cache_write_split`, and model-independent multipliers. A model it leaves unpriced may be priced in the reference, along with any override entry that model needs.
   - **Changed:** anything else.
5. The script takes `--comparable-stamps` and `--addition-only-stamps`.

A row **passes the dollar rule** in only two cases:
- Its stamp is identical.
- Its stamp is addition-only and its `unpriced_tokens` is 0, which means every turn was priced at rates the reference shares.

A layer-1+2 PR (M6) **passes the dollar rule** iff every row whose dollar and token values were summed into its total individually passes the row-level rule above. A row M5 discarded as a same-account recapture loser contributes neither value nor stamp to this determination, since M5 never sums the discarded row into anything.

Every row's dollars are summed as-recorded into `bucket.tsv`'s pooled total regardless of whether it passes the dollar rule — `docs/pr-cost.md:86` bars *comparing* two rows' dollars across pricing states, not *summing* them, so a labeled pool is well-defined even before this classification runs.

The bucket carries a `pricing_basis` label:
- `unclassified`: neither gate flag was passed.
- `comparable`: at least one gate flag was passed, and every PR in the bucket passes the dollar rule.
- `mixed`: otherwise, including a stamp named by neither flag.

The dollar era direction word (M11) is gated separately, and more strictly than the pooled total: it prints only when every PR on both sides of the before/after split passes the dollar rule, with at least two PRs per side. Per-row inclusion in the pooled total doesn't suffice for the era comparison, because the pricing reference is always the latest state, so a non-comparable row always sits in an earlier stamp — filtering only the non-comparable rows out of one side's median while leaving the other side untouched concentrates the exclusion in the before era and biases the comparison exactly the way `docs/pr-cost.md:86` warns against.

Options set aside:
- (i) Full withholding of every dollar field until the gate runs was set aside: `docs/pr-cost.md:86` bars *comparing* two rows' dollars across pricing states, not *summing* them, and a `pricing_basis`-labeled pooled sum is well-defined, not silently blended — withholding therefore has no correctness basis for the pooled total, only for the era comparison M11 gates separately.
- (ii) Re-deriving under today's `pricing._model_rates` can't be done (rows 5-6). That was the consult's route, and the one `docs/pr-cost.md:86` prescribed before Phase 1 replaced it (pre-edit text).
- (iii) A worst-case bound on the re-pricing change would, with no model split, span every priced model's rate for a class, a 10× spread (row 6). That is too wide to say anything about an era difference.
- (iv) Recapturing every PR with `--record --force` is an irreversible append on two machines. It also understates PRs whose transcripts have aged out (row 23).

**M8: Token totals are the comparison that doesn't depend on price.** `anchors: row7`
Every token figure reports the per-class tokens, `unpriced_tokens`, and their sum. Era comparisons use the sum.

**M9: "Models used" means the Opus-family share of dollars.** `anchors: row5`
Compute it from summed `opus_dollars` over summed class dollars, over the same as-recorded population as the bucket's pooled dollar total (M7), as `docs/pr-cost.md:153` requires. Label it "Opus-family share of dollars". No other model dimension exists (G1). When summed class dollars are zero (no rows in the bucket, or every turn unpriced), the denominator is zero: the script must write an explicit sentinel (e.g. `n/a`) for this field rather than dividing, and must not emit a bare `0`, which would misread as "no Opus usage" rather than "undefined — no priced rows."

**M10: The spec is committed to `docs/pr-cost.md`.** `anchors: row6, row7, row10, row22`
The doc edits in Critical files make the procedure the canonical consumer procedure. They also correct the three places where current text prescribes something the schema can't do or that double-counts.

**M11: Output handling.** `anchors: row17, row19`

`--out-dir` rules:
- It must not already exist. It is created with mode 0700.
- It is refused inside a git work tree, meaning when `git -C <parent> rev-parse --is-inside-work-tree` exits 0 with stdout `true`. This check mirrors `_ledger_path_is_git_tracked`'s fail-closed hardening (`transcript_analysis/ledger_common.py`), even though the script imports nothing from the repo (M2): strip `GIT_DIR`/`GIT_WORK_TREE`/`GIT_INDEX_FILE` from the subprocess environment before the call, and decode subprocess output with `encoding="utf-8", errors="replace"` under `LC_ALL=C` to avoid a locale-dependent crash.

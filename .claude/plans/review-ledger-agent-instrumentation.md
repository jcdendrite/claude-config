# Instrument review-narrative ledger with an authoring-agent/effort field and dispatch join key

## Context

This plan instruments the review-narrative ledger (`claude/.claude/scripts/review-ledger.sh`) and `transcript-analysis.py` so a later analysis can compute what share of `code-writer` subagent dispatches fail their own downstream `/code-review` check — the numerator GitHub issue #800 (`priority:high`) says is currently unreachable, blocking cost-guide audit row 9 ("re-run failures at higher effort" in `docs/cost-levers-considered.md`) from closing. Because issue #800 frames this as the concrete, buildable next step once a prior investigation (documented in the issue body and in `.claude/plans/escalate-effort-on-code-writer-failure.md` on a separate, unmerged branch) established that the ledger's schema and `transcript-analysis.py` both currently lack any signal tying a review finding back to the `code-writer` dispatch that authored the reviewed diff. The intended outcome is the three parts issue #800 specifies: (1) an authoring-agent/effort field added to the ledger's `append` schema, written at review time; (2) a join key from a ledger entry back to the specific `code-writer` dispatch that authored the diff under review; (3) a new `transcript-analysis.py` subcommand that reports the failure share.

This plan does **not** compute or publish an actual failure-share number (no historical corpus carries the new fields yet — accumulation starts once this ships), does **not** close cost-guide audit row 9, and does **not** edit `docs/cost-levers-considered.md` — the register was deliberately left untouched by the prior session and everything routed to this issue instead.

**This revision supersedes the plan's original join mechanism.** The first version added a `repo_identity` field (derived from `git rev-parse --path-format=absolute --git-common-dir`, stable across every worktree of one repo) so a ledger *file* could be attributed to a repository despite the ledger's `$REPO_HASH.$SESSION_ID.jsonl` naming hashing one worktree's own path. Implementation proceeded on that design through two `code-writer` dispatches, then a `plan-architect` consult run during this branch's second `/code-review` round (mandatory after one recorded review round with no consult) found the mechanism unnecessary and identified two correctness defects it introduced:

- **The ledger file was never the primary record for this join.** Every field the classifier needs — the finding's disposition, the declared authoring agent — is already a literal argv token in the `review-ledger.sh append code-review ...` Bash command, which is itself a `tool_use` record in the same transcript that carries the `code-writer` dispatch. Reading the ledger file added a second, lossier copy of data the transcript already holds directly: the ledger deduplicates identical findings whole-line (so a re-raised finding produces no new line), silently no-ops under the kill switch, silently drops over-cap findings, and sweeps at 30 days while transcripts persist longer. Each of those under-counts `ADDRESS` findings relative to reading the command text directly.
- **The join scoped its two sides inconsistently.** `_read_ledger_corpus` built one finding-text-keyed map across every in-scope session and repo, so two sessions raising textually identical findings (plausible against a stable rulebook) could attribute one session's disposition to another's round. Separately, the transcript side defaulted to `--projects '*'` (every repo) while the ledger side was always scoped to the invoking process's own repo, so under the default invocation every other repo's failing rounds were structurally unable to match a ledger line and fell through to PASS or UNATTRIBUTED — deflating the failure share in the direction opposite to what the measurement exists to catch.

**This also supersedes an `[engineer-verified]` constraint from the first `/plan-review` round** (that round's assumption-ledger row 2: "Losing ledger data tied to deleted worktrees is unacceptable; a heuristic better than live-worktree enumeration was explicitly requested"). That constraint existed only because the superseded design attributed ledger *files* to a repository; this design attributes classifications from transcript command text directly and never attributes a ledger file to anything, so the constraint's premise — that a file-attribution heuristic is needed at all — no longer holds. The engineer re-confirmed dropping the mechanism in the session that authored this revision, after being shown exactly what dropping it removes (repo_identity, the hash helper, and the ledger-file read path) — this is not a unilateral resolution of that earlier row. The underlying human concern (worktree-deletion data loss) does not resurface here: nothing in this design reads a ledger file, so there is nothing left for a deleted worktree to make unattributable.

This revision removes `repo_identity`, `_lib_repo_identity_hash`, the ledger-file read path, and every fixture/test/docs paragraph specific to that mechanism. It keeps the `--authoring-agent`/`--authoring-effort` flags on `review-ledger.sh append` — those flags are still required, not for a file the classifier reads, but so their values appear as argv tokens in the command the classifier reads directly. Classification now derives every signal from the transcript alone: round windows, dispatch completion ordering, and the literal flag values on each round's own `review-ledger.sh append code-review` and `marker.sh write code-review` Bash commands. No ledger directory is globbed, no ledger file is opened, and no cross-worktree attribution problem exists to solve, because there is no second, worktree-partitioned artifact left in the join.

## Approach

Bridge the numerator issue #800 describes by reading, for each `code-writer` dispatch, the `review-ledger.sh append code-review` and `marker.sh write code-review` Bash commands that fall inside the `code-review` round that judged its diff — both are themselves `tool_use` records inside a round window `review_rounds.py`'s round detector already computes, so no new hook, no captured `tool_use_id`, and no ledger file read are needed. Two new argv flags (`--authoring-agent`, `--authoring-effort`) on `review-ledger.sh append`, still written into the ledger line for the ledger's own human-facing `show`/audit purposes, but read by the analysis directly off the command text rather than off the file those flags land in. A new `transcript-analysis.py author-outcome` subcommand reports a failure share with every bias it cannot remove printed alongside it as a named counter.

**Root problem.** For each `code-writer` dispatch, nothing today classifies whether the `code-review` round that judged its diff recorded a must-fix finding, even though every signal the classification needs — the review's disposition, its authoring-agent declaration, and a clean-marker write — already exists as literal Bash command text in the same transcript that records the dispatch itself.

Three structural findings shape this design:

**The join key, and the disposition it needs, both already exist in the transcript.** #800 treats "a join key from a ledger entry back to the specific `code-writer` dispatch" as missing. It is missing *from the ledger file*, but every `review-ledger.sh append` invocation is a Bash `tool_use` record at a known position, inside a round window `detect_round_windows` already computes, in the same transcript that carries the `Agent`/`Task` dispatch records — and that Bash command's own argv already carries `--disposition` and (with this plan's two new flags) `--authoring-agent` as literal text. So round attribution, dispatch ordering, clean-round detection, and the finding's disposition are all recoverable from the transcript with no ledger read at all.

**A clean round already emits a positive transcript signal, so no round outcome has to be inferred from the round that follows it.** `/code-review` runs two independent per-round steps: it appends one ledger line per finding *on every invocation, clean or not* (`code-review/SKILL.md:381`), and it runs `marker.sh write code-review` *exactly once and only when the review is clean* (`:449-460`). A zero-finding round is therefore not ambiguous — the marker-write call distinguishes "clean" from "the append step was skipped" directly, inside the round's own span.

**A per-call timestamp field would have silently broken ledger dedup.** `_lib_append_line_locked` (`claude/.claude/hooks/_lib.sh:2638`) dedups with `grep -qFx -e "$line"` — whole-line verbatim, inside the lock, shared with `log-reviewer-round.sh`. This constrains the ledger's *own* schema (Dispatch 1's fields must be round-stable, or a retried identical finding would regress `test_review_ledger_script.py:159-182`); it no longer constrains the classifier, which never reads the ledger file and so is unaffected by its dedup behavior either way.

**Givens** (fixed beyond this plan's reach):

- `effort` is subagent-definition frontmatter, not a per-dispatch `Agent`-tool parameter, so `authoring_effort` will log the constant `high` until a future issue builds an override — Anthropic owns the dispatch schema.
- The ledger sweeps at 30 days (`review-ledger.sh:87`) while transcripts persist longer. Under this design that asymmetry no longer bounds the classifier (which reads only the transcript), but it does mean the ledger's own new fields have no historical corpus and the ledger's `show` output for old lines has neither field.
- `/code-review`'s append is orchestrator prose (`code-review/SKILL.md:381`), not a hook, so append compliance is a model behavior this plan can measure but not enforce. The marker write it is cross-checked against is *partly* enforced — `require-code-review.sh` denies `git commit` without a matching marker — but a session that never commits is under no such pressure.

**Mechanism justifications:**

- **A round's outcome is read directly off its own `review-ledger.sh append code-review` and `marker.sh write code-review` Bash commands, with no ledger file read.** `anchors: row3, row14` — the ledger file is a write path, not a second copy the classifier needs: every value the three-test walk below consumes (`--disposition`, `--authoring-agent`) is already a literal token in the append command itself. This removes the entire ledger-attribution problem the superseded design solved: there is no file to attribute to a repository, because no file is read.
- **The command-parsing helper scans the token list `corpus.split_command_segments` already returns, rather than re-tokenizing.** `anchors: row12, row15` — operator segmentation is required, not optional: `enforce-marker-script-shape.sh` explicitly *permits* `marker.sh write code-review && git commit …` (row 6), so the marker signal is routinely inside a chain, and an append call can equally appear alongside other chained commands. `split_command_segments` already performs the one whole-command `shlex.split` and returns each operator-split segment as a `list[str]`; `_parse_ledger_append_flags(segment: list[str]) -> dict[str, str] | None` walks that list looking for `--disposition`/`--authoring-agent` tokens, matching the same pattern its two sibling matchers (`_ledger_append_finding`, `_is_clean_marker_write`, both being removed by this revision) already use — a second `shlex.split()` call against an already-tokenized list would be a type error, not an alternative implementation.
- **`_parse_ledger_append_flags` returns `None` only when a segment matches `review-ledger.sh append code-review` by `basename(argv[0])` + literal subcommand pair but fails to yield `--disposition`, never for an ordinary segment that isn't an append call at all.** `anchors: row14, row15` — the distinction matters for `_DQ_UNPARSEABLE_APPEND` below: the counter exists to surface a genuine parse failure on an identified append attempt, not to count the (overwhelming, and meaningless) majority of unrelated Bash commands in a round's span. A segment that doesn't match the append shape at all is simply not an append call — it contributes nothing to either the classification or the data-quality counter.
- **A matched append call is only counted toward Test 2/3 if its paired `tool_result` is not `is_error`.** `anchors: row3` — `review-ledger.sh append` can be invoked and rejected at runtime (invalid `--disposition`/`--authoring-agent` enum, an over-cap `--finding`/`--rationale`/`--source`), and `code-review/SKILL.md`'s own append prose explicitly anticipates a reject-then-retry pair inside one round ("summarize more tightly and retry, not skip"). Without this check, a rejected attempt — which wrote nothing to the real ledger — would still satisfy Test 3's "≥1 append call" PASS criterion. A rejected append call is excluded from classification and counted under a new `_DQ_REJECTED_APPEND` data-quality key instead. A matched call with no paired `tool_result` at all (the Bash call never completed) is treated as accepted rather than rejected, since every append call inside an already-closed round span has necessarily completed by the time that round opened.
- **The dispatch-to-round ordering key is the dispatch's paired `tool_result` record index (completion), not its `Agent`/`Task` `tool_use` record index (start), computed over the same deduped main-thread record list the round windows come from.** `anchors: row3, row4` — a round can legitimately open while a dispatch is still running, and a start-keyed join would then charge that round's findings to a diff not yet on disk. Completion-keyed, that is impossible. A dispatch whose paired `tool_result` is absent from the main-thread records is left **UNDECIDABLE** and counted, mirroring `reviewer_yield._build_tool_result_ts_map`'s own documented posture for the same shape of gap, rather than falling back to the start index.
- **The round's *outcome span* is `[open_idx(r), open_idx(next code-review round))`, not `detect_round_windows`'s own `window_end`.** `anchors: row11` — a user interjection between the review and its marker write ends `window_end` but does not end the round's outcome, and nothing but a `/code-review` run emits either signal, since the append is gated to `append code-review` and the marker call to `write code-review`, so a wider span cannot capture an unrelated event.
- **No new hook.** `anchors: row3, row5` — the lighter primitives that make one unnecessary are already in place: the transcript's own `Agent`/`Task` records joined via `corpus._index_subagent_dispatches`, the `marker.sh write code-review` call as the clean-round signal, and the command's own `--authoring-agent` token as the one signal a purely-structural transcript read cannot always resolve (a handoff, where the dispatch ran in session A and the review in session B, still needs the declared value). A `PostToolUse`/`Agent|Task` hook mirroring `log-reviewer-round.sh` would add only a `tool_use_id` the transcript already carries, at the cost of a new state file and sweep.
- **`authoring_agent` as an optional flag over a closed enum (`code-writer` | `inline` | `mixed` | `unknown`, default `unknown`), not free text.** `anchors: row3` — kept from the original design unchanged: the transcript-derived value (was a `code-writer` dispatch's completion inside this round's span?) is authoritative for the join; the declared flag covers cross-session authorship and is cross-checked against the transcript-derived determination rather than trusted blindly. An **absent** flag never aborts the append (the ledger's primary purpose — preserving the disposition — outranks the secondary one); an **invalid** value does abort, consistent with `--disposition`.
- **`authoring_effort` as a validated flag over `low`/`medium`/`high`/`xhigh`, not read from `code-writer.md` frontmatter by the script.** `anchors: row13` — unchanged from the original design: a frontmatter read would couple the ledger to the very assumption this measurement exists to overturn (that effort is a static per-file constant). `max` is deliberately excluded per CLAUDE.md's "`xhigh`, not `max`", so a `max` value aborts loudly. Drift in the prescribed literal is caught by a test: `claude-skills/skills/tests/test_skills.py` asserts the literal in `code-review/SKILL.md` equals `claude/.claude/agents/code-writer.md`'s own frontmatter value, which `test_agent_roster.py`'s `EXPECTED_EFFORT` independently pins to `high`.
- **Output carries no per-project, per-branch, or per-session dimension.** `anchors: root` — one aggregate table plus counters, by construction, so there is nothing for `redaction` to pseudonymize and no figure that could carry the per-engagement dimension CLAUDE.md § "Also redact structural fingerprints and provenance" forbids absolutely.

**Failure definition** (the subcommand's correctness rests on this; stated explicitly since it is a design call, not an engineer-supplied one):

A dispatch's **attributed round** is the `code-review` round with the smallest `open_idx` strictly greater than that dispatch's completion index. Its **outcome span** is `[open_idx, open_idx of the next code-review round)`, or `[open_idx, end of records)` for the last round in the session. Within that span, scan every Bash `tool_use` command: an **append call** is one whose command text, once split into `&&`/`||`/`;`/`|` segments, contains a segment invoking `review-ledger.sh append code-review` — extract its `--disposition` and `--authoring-agent` argv values directly from that segment; a **clean-marker call** is one containing a segment matching the hook-allowlisted `marker.sh write code-review` shape.

Each dispatch classifies by walking three tests against its attributed round, in order:

1. No attributed round exists → **UNRESOLVED**.
2. The span contains ≥1 append call with `--disposition ADDRESS` → **FAILURE**. `ADDRESS` means "must be fixed in this diff," which is exactly "the dispatch's output did not survive review." `ADDRESS` presence decides this regardless of whether a clean-marker call also appears in the same span.
3. Otherwise, the round concluded clean and the dispatch is a **PASS** iff the span contains either ≥1 append call (necessarily all `DEFER`) or a clean-marker call; **UNATTRIBUTED** if it contains neither.

All five DEFER criteria (`code-review/SKILL.md:358-365`) describe findings that are not the dispatch's fault, so a DEFER-only round is a PASS, and no per-criterion split is added.

A precondition sits before Test 1: a dispatch whose paired `tool_result` record is absent from the main-thread records is classified **UNDECIDABLE**.

Two non-failure buckets and one fan-out case, each of which would bias the share if collapsed into PASS:

- **UNRESOLVED** — no `code-review` round after the dispatch at all (typically the last dispatch of a session). Excluded from the denominator.
- **UNATTRIBUTED** — a round ran and left neither an append call naming a disposition nor a clean-marker call. Excluded from the denominator and reported, so the operator sees the compliance rate rather than absorbing it as a passing grade. One known residual lands here: `/code-review`'s Step 0.1 short-circuit (`code-review/SKILL.md:25`) exits before both steps when the staged diff already matches a fresh clean marker.
- **Co-authored rounds** — when several dispatches precede one round, the round's outcome fans out to each, the conservative reading. Counted as its own data-quality counter.

Proposed output shape, one headline number with an explicit denominator plus one counter per named bias:

```
AUTHOR OUTCOME SOURCES (this repo (N project dirs); 1 root)
agent=code-writer  window=last 30d

Dispatches in scope                             20
  FAILURE      (round had >=1 ADDRESS)          10
  PASS         (round concluded clean)           6
  UNRESOLVED   (no subsequent round)             3
  UNATTRIBUTED (round ran, no append, no marker)  1
Failure share: 10 of 16 resolved dispatches (62.5%)

Data quality
  rounds co-authored by >1 dispatch                    3
  append calls with unparseable flags (skipped)        0
  append calls rejected by review-ledger.sh (skipped)  0
  dispatches with no paired tool_result (undecidable)  0
  authoring_agent inconsistent with the transcript join 1
```

The `authoring_agent inconsistent` counter compares each append call's own `--authoring-agent` token (when present — an append call from a pre-migration transcript, or from a `code-writer.md` version older than this ships, may omit the flag entirely, which is treated identically to an explicitly-empty value: skipped, not miscounted) against the transcript-derived determination for that round — a `code-writer` dispatch attributed to the span or not — using an **unfiltered** dispatch count, distinct from the count that gates "Dispatches in scope." Today's `round_entry["dispatch_count"]` serves both roles from one `--since`-filtered pass over `_agent_dispatch_tool_use_ids`, which is the bug: deriving `transcript_side` from that same filtered count reports every round whose authoring dispatch falls just outside a `--since` cutoff as spuriously inconsistent, even though the round's own append/marker signals are evaluated without regard to `--since` at all. The fix is two separate per-round counts, not one field read two ways: a `--since`-filtered dispatch count (unchanged, gates which dispatches enter "Dispatches in scope" and the reported outcome buckets) and a second, unfiltered dispatch count (every `code-writer` dispatch whose completion falls in the span, regardless of `--since`) that `transcript_side`/the inconsistency check reads instead. Both are produced from the same `_agent_dispatch_tool_use_ids` pass; only the accumulation target differs per dispatch depending on whether it also passes the filter.

## Out of scope

- **Computing or publishing an actual failure-share number.** No historical corpus carries the new fields; accumulation starts at merge.
- **Closing cost-guide audit row 9, and editing `docs/cost-levers-considered.md`** — the register stays untouched, per the deliberate prior routing of everything to issue #800.
- **Any mechanism making `code-writer`'s effort vary per dispatch.** #800 asks only to log the current constant.
- **A `PostToolUse`/`Agent|Task` hook capturing `code-writer` dispatch identity.** Deliberately not built — the transcript already carries it.
- **A `CLEAN` disposition value or any zero-finding sentinel append.** It would make clean rounds directly visible instead of inferred, but it changes the `ADDRESS|DEFER` enum every consumer knows (`session-marker-dashboard.sh:104-108`) and adds an append to a path that currently writes nothing. The UNATTRIBUTED bucket surfaces the same gap as an observable counter instead.
- **Per-file attribution of a finding to the specific co-authoring dispatch that touched its file.** Buildable — `reviewer_yield._index_session_edits` is the precedent — but `--source` defaults to `n/a` (`review-ledger.sh:140`), so coverage would be partial. Revisit once `--source` population is measured.
- **Changing the ledger's 30-day sweep, its file naming, `_marker_lib_repo_hash`, or `_lib_append_line_locked`.** None of these are touched by either the original or this revised design.
- **Extending the join across sessions using anything beyond the declared `authoring_agent` field.** A handoff splits the dispatch and its review into two transcripts; the transcript-only join cannot span them, which biases the share low. Stated as a documented limitation, not fixed here.
- **A data-quality counter observing `corpus.split_command_segments`'s silent `shlex`-failure fallback.** A `plan-architect`-adjacent review noted the fallback (naive `command.split()` on unbalanced quoting) degrades with no signal to the caller, and this design is its first consumer feeding a published metric rather than a boolean check. Not built: every realistic nested-quoting shape inside `--finding`'s own value (escaped quotes, the POSIX single-quote-escape idiom, embedded `$(...)` text, embedded newlines) tokenizes correctly and leaves the surrounding `--disposition`/`--authoring-agent` tokens unaffected regardless of what's inside `--finding`'s quoting — verified directly against `shlex`'s actual behavior. The one real gap (genuinely unbalanced quoting, or bash's `$'...'` ANSI-C form) is rare, and building a new signal for it means changing `split_command_segments`'s return contract for its other consumer (`_bash_command_is_mutating_git`) too, disproportionate to a case that doesn't change this design's classification correctness in any case that matters. Revisit if the real corpus ever shows it firing.
- **A dedicated `shell_commands.py` module for the promoted command tokenizer.** `plan-architect`'s consult noted `corpus.py` is a loose categorical fit for a shell-command tokenizer and suggested a small dedicated module. Worth doing, not required for this plan's correctness, and already-written call sites would need updating; left as a follow-up rather than bundled into this revision's already-substantial rework.
- **Refactoring `reviewer_yield._build_tool_result_ts_map` to share the promoted tokenizer's scan.** It answers a different question (a wall-clock threshold, not a within-list position), and `reviewer_yield.py` is outside this plan's file scope.

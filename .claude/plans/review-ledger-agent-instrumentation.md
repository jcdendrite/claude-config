# Instrument review-narrative ledger with an authoring-agent/effort field and dispatch join key

## Context

This plan instruments the review-narrative ledger (`claude/.claude/scripts/review-ledger.sh`) and `transcript-analysis.py` so a later analysis can compute what share of `code-writer` subagent dispatches fail their own downstream `/code-review` check.

That failure share is the numerator GitHub issue #800 (`priority:high`) says is currently unreachable, blocking cost-guide audit row 9 ("re-run failures at higher effort" in `docs/cost-levers-considered.md`) from closing. A prior investigation (documented in the issue body and in `.claude/plans/escalate-effort-on-code-writer-failure.md` on a separate, unmerged branch) established that the ledger's schema and `transcript-analysis.py` both currently lack any signal tying a review finding back to the `code-writer` dispatch that authored the reviewed diff. Issue #800 frames closing that gap as the concrete, buildable next step.

The intended outcome is the three parts issue #800 specifies:

1. An authoring-agent/effort field added to the ledger's `append` schema, written at review time.
2. A join key from a ledger entry back to the specific `code-writer` dispatch that authored the diff under review.
3. A new `transcript-analysis.py` subcommand that reports the failure share.

This plan does not:

- Compute or publish an actual failure-share number — no historical corpus carries the new fields yet, so accumulation starts once this ships.
- Close cost-guide audit row 9.
- Edit `docs/cost-levers-considered.md` — the register was deliberately left untouched by the prior session and everything routed to this issue instead.

An earlier `repo_identity`-based join was dropped: it added a field (derived from `git rev-parse --path-format=absolute --git-common-dir`) to attribute a ledger *file* to a repository despite the ledger's `$REPO_HASH.$SESSION_ID.jsonl` naming hashing one worktree's own path. A `plan-architect` consult found it unnecessary — the ledger's own session-id filename component already gives a 1:1 point lookup — and identified two defects:

- A whole-line-keyed cross-session collision in `_read_ledger_corpus`'s finding-text-keyed map.
- An inconsistent scope default (transcript side `--projects '*'` vs. ledger side scoped to the invoking repo) that could deflate the failure share.

An earlier `/plan-review` round's assumption-ledger constraint requiring a worktree-deletion heuristic in place of live-worktree enumeration was dropped along with it, since the shipped design never attributes a ledger file to a repository at all.

A subsequent design read every classification signal directly off transcript Bash-command argv text instead of the ledger file, because the ledger looked lossy relative to the transcript:

- Whole-line dedup collapses a re-raised finding into no new line.
- The ledger silently no-ops under the kill switch.
- The ledger silently drops over-cap findings.
- The ledger sweeps at 30 days while transcripts persist longer.

That design is superseded by the one shipped here, once the ledger schema added in this session closed the first two of those gaps and the third (the sweep-window claim) was verified false — see the Givens bullet on retention, below. The fourth (over-cap findings) remains an accepted residual, covered at the end of this section.

**Shipped design: the classifier reads each session's own ledger file directly, matching rows to rounds by a new `round` field.**

- **A new `round` field defeats the whole-line-dedup collapse.** `review-ledger.sh append` now requires `--round <N>` (`review-ledger.sh:24, 210-219`) and writes it into the ledger line alongside a `schema_version: 2` marker (`review-ledger.sh:302-303`). The append no longer calls `_lib_append_line_locked`'s whole-line `grep -qFx`; a new sibling primitive, `_lib_append_json_line_locked` (`_lib.sh:2742-2774`), shares that function's lock-acquisition/eviction/retry logic — factored out into `_lib_acquire_append_lock` (`_lib.sh:2697-2721`) — but projects each candidate and existing line through a caller-supplied `jq` filter before comparing. `review-ledger.sh` passes `{round, finding, disposition, rationale, source, authoring_agent, authoring_effort}` (`review-ledger.sh:316-317`), deliberately excluding the now-per-call-varying `event_time` and the constant `schema_version`. Two rounds raising a textually identical finding now both land as separate rows, because `round` differs between them.
- **A new `CLEAN` disposition makes the kill-switch gap an explicit, counted fallback rather than a silent miss.** `review-ledger.sh append` gained a `CLEAN` disposition value (`review-ledger.sh:233-236`; `--finding`/`--rationale` are rejected, not merely optional, for `CLEAN`), which both `code-review/SKILL.md`'s Step 0.1 short-circuit and its own zero-finding path now call once per round-open regardless of outcome (`code-review/SKILL.md:25-27, 383-390`), in addition to, not instead of, the `marker.sh write code-review` call. A round with the kill switch on for its entire lifetime still leaves zero ledger rows for that round, but `author_outcome.py`'s `_classify_round` (`author_outcome.py:208-239`) now treats "no matching ledger row, but a `marker.sh write code-review` Bash call inside the round's own span" as an inferred-clean PASS, counted under the named `_DQ_KILL_SWITCH_INFERRED_CLEAN` counter (`author_outcome.py:57`) instead of falling through unnoticed.
- **The assumed retention asymmetry was verified false.** This file's Givens bullet below confirms transcripts and the ledger both default to the same ~30-day `cleanupPeriodDays` window, not an asymmetric one.

Reading the ledger directly is therefore no longer the lossier option: it is the direct source for exactly the fields (`disposition`, `authoring_agent`) the classifier needs, with no argv-tokenization layer required to recover them from Bash command text. The lookup stays a simple session-id glob, never a repo-hash or worktree join: `_ledger_path_for_session` (`author_outcome.py:143-154`) globs `<config_dir_root>/review-narrative-ledger/*.<session_id>.jsonl` directly off the transcript's own session id, since session ids are globally unique (UUIDs). `repo_identity`/`_lib_repo_identity_hash` stay dropped; nothing here attributes a ledger *file* to a repository, only to the one session whose id names it.

One gap remains open: an append rejected for an over-cap `--finding`/`--rationale` (`review-ledger.sh:255-260`, unchanged by this schema pass) still lands zero ledger rows for that attempt, indistinguishable on its own from "nothing happened." This is not silent to the reviewing agent in the moment (the script exits 2 with an error the calling skill sees and is instructed to retry on, `code-review/SKILL.md:392`), but a corpus-wide read of the ledger file alone still can't tell a rejected-then-abandoned attempt apart from a round that raised nothing at all. The `UNATTRIBUTED` bucket — a round that ran and left neither a matching ledger row nor a marker write — is the same safety net a transcript-argv-only design would also need for this shape of gap: it excludes the round from the failure-share denominator rather than counting it as a false PASS, so the residual biases the denominator down, not the numerator up.

## Approach

Bridge the numerator issue #800 describes by reading, for each `code-writer` dispatch, its own attributed `code-review` round's disposition directly off that session's own review-narrative-ledger file — located by a session-id glob, not a repo-hash join — and falling back to the transcript's `marker.sh write code-review` Bash command only when the round produced no ledger row at all (the kill-switch case). The transcript alone still supplies the dispatch's completion ordering, the round-open positions `review_rounds.detect_round_windows` already computes, and each round's 1-indexed ordinal; the ledger alone supplies the disposition and the declared authoring agent for the round at that ordinal, matched by an explicit `--round` field the schema now carries rather than by scanning Bash argv text. A new `transcript-analysis.py author-outcome` subcommand reports a failure share with every bias it cannot remove printed alongside it as a named counter.

**Root problem.** For each `code-writer` dispatch, nothing today classifies whether the `code-review` round that judged its diff recorded a must-fix finding, even though the signal the classification needs — the round's own disposition sequence, one row per finding-or-clean-event — now lives directly in that session's own ledger file, joined to the transcript's dispatch/round structure by nothing more than the session id both artifacts already share.

Three structural findings shape this design:

**The ledger file is a direct, per-session point lookup, not a repo-scoped join.** #800 treats "a join key from a ledger entry back to the specific `code-writer` dispatch" as missing. It is recoverable with no new join field: a transcript file's own session id is the same session id the ledger's `$REPO_HASH.$SESSION_ID.jsonl` filename embeds, so `_ledger_path_for_session` finds one session's ledger file by a `*.<session_id>.jsonl` glob (`author_outcome.py:143-154`) — a 1:1 point lookup, never a repo-hash or worktree join. The transcript still supplies the dispatch's completion ordering, the round-open positions (`review_rounds.detect_round_windows`), and each round's own 1-indexed ordinal; the ledger supplies the disposition and the declared authoring agent for that ordinal.

**A `round` field makes ledger-row-to-round matching exact instead of inferred from text.** Before this schema, a ledger row carried a finding but nothing tying it to which numbered `/code-review` invocation raised it — exactly the ambiguity the first-supersession design's whole-line-keyed, cross-session join got wrong (above). `review-ledger.sh append` now requires `--round <N>` (`review-ledger.sh:24, 210-219`); `code-review/SKILL.md`'s Step 0.1 tracks a per-session round counter and passes the same number on every append made during that round (`code-review/SKILL.md:25, 383`). `_classify_round` (`author_outcome.py:208-239`) matches ledger rows to a round by exact `round`-field equality against that round's own ordinal position in the transcript's round-open sequence — no finding-text matching, no whole-corpus scan.

**A clean round now emits a positive ledger signal of its own; the transcript's marker write is a fallback only for the kill-switch gap.** `review-ledger.sh append` gained a `CLEAN` disposition (`review-ledger.sh:233-236`), which both Step 0.1's short-circuit and the normal zero-finding path call once per round-open (`code-review/SKILL.md:27, 390`) — in addition to, not instead of, the `marker.sh write code-review` call at the end of a clean review. A round is a ledger-backed PASS whenever a `CLEAN` or all-`DEFER` row set matches its ordinal. Only when the round has *no* matching row at all (the ledger kill switch was on for the round, or every append attempt failed before landing) does `_classify_round` fall back to checking whether the round's own span contains a `marker.sh write code-review` Bash call — and even then, it counts the fallback under `_DQ_KILL_SWITCH_INFERRED_CLEAN` (`author_outcome.py:57, 231-238`) rather than reporting it identically to a genuine ledger-backed PASS.

**Givens** (fixed beyond this plan's reach):

- `effort` is subagent-definition frontmatter, not a per-dispatch `Agent`-tool parameter, so `authoring_effort` will log the constant `high` until a future issue builds an override — Anthropic owns the dispatch schema.
- The ledger sweeps at 30 days (`review-ledger.sh:112`, `_sweep_stale_ledger_files`'s own `-mtime +30`), and under vendor defaults transcripts sweep on the same ~30-day window (`cleanupPeriodDays`, default 30d — `docs/cost-ledger.md`, `docs/pr-cost.md`), not an asymmetric one. This design's own read path does not depend on either window's length, since it reads a session's ledger file directly rather than reconstructing disposition from transcript text — but it does mean neither artifact carries a corpus older than ~30 days by default, and the ledger's own new fields (`round`, `schema_version`, `event_time`) have no historical rows at all until this schema ships.
- `/code-review`'s append is orchestrator prose (`code-review/SKILL.md:383, 390`), not a hook, so append compliance is a model behavior this plan can measure but not enforce. The marker write it is cross-checked against is *partly* enforced — `require-code-review.sh` denies `git commit` without a matching marker — but a session that never commits is under no such pressure.

**Mechanism justifications:**

- **A round's outcome is read directly off its own review-narrative-ledger rows, located by a session-id glob, with the transcript's `marker.sh write code-review` call as a fallback signal used only when the round produced no ledger row at all.** `anchors: row1, row3, row14, row15` — the ledger file is the primary record again, not a second copy: every value the three-test walk below consumes (`disposition`, `authoring_agent`) is a field on the row itself, requiring no argv-parsing or command-tokenizing layer to recover. The `repo_identity`/file-attribution mechanism described in Context above stays dropped: the session-id glob is a direct point lookup, never a repo-scoped or worktree-scoped join.
- **The one remaining command-parsing helper, `_is_clean_marker_write`, still scans the token list `corpus.split_command_segments` returns rather than re-tokenizing.** `anchors: row6, row12` — operator segmentation is still required, not optional: `enforce-marker-script-shape.sh` explicitly *permits* `marker.sh write code-review && git commit …` (row 6), so the marker signal is routinely inside a chain. A second matcher that would have parsed `--disposition`/`--authoring-agent` off `review-ledger.sh append` argv was never built in this revision, since the classifier reads the ledger row directly instead — `split_command_segments` now has one classifier consumer, not two.
- **The dispatch-to-round ordering key is the dispatch's paired `tool_result` record index (completion), not its `Agent`/`Task` `tool_use` record index (start), computed over the same deduped main-thread record list the round windows come from.** `anchors: row3, row4` — a round can legitimately open while a dispatch is still running, and a start-keyed join would then charge that round's findings to a diff not yet on disk. Completion-keyed, that is impossible. A dispatch whose paired `tool_result` is absent from the main-thread records is left **UNDECIDABLE** and counted under `_DQ_UNDECIDABLE`, mirroring `reviewer_yield._build_tool_result_ts_map`'s own documented posture for the same shape of gap, rather than falling back to the start index.
- **The round's *outcome span* is `[open_idx(r), open_idx(next code-review round))`, not `detect_round_windows`'s own `window_end`.** `anchors: row11` — a user interjection between the review and its marker write ends `window_end` but does not end the round's outcome, and nothing but a `/code-review` run emits either signal, since the marker call is gated to `write code-review`, so a wider span cannot capture an unrelated event.
- **A round with zero matching ledger rows but a marker-write call is inferred clean, and counted as inferred rather than reported identically to a genuine ledger-backed PASS.** `anchors: row5, row15` — this is the design's explicit answer to the kill-switch-silent-no-op gap that motivated the earlier transcript-argv-only design (see Context above): the gap is real (a round with the kill switch on for its whole lifetime leaves no ledger row), but it is now a named, counted fallback (`_DQ_KILL_SWITCH_INFERRED_CLEAN`) rather than an unmarked miss.
- **A round-number-sequence check flags a session whose ledger `round` values don't form the transcript's own exact `1..N` sequence, as a data-quality signal, not a correctness gate.** `anchors: row16` — this does not block or alter any dispatch's own classification; it surfaces a session where the ledger and the transcript's own round-open count have drifted (a gap, an out-of-order round, or an orphaned ledger round number), for an operator auditing the corpus rather than for the classifier itself.
- **No new hook.** `anchors: row3, row7` — the lighter primitives that make one unnecessary are already in place: the transcript's own `Agent`/`Task` records, the `marker.sh write code-review` call as the kill-switch fallback signal, and now the ledger's own `disposition`/`round` fields as the primary signal. A `PostToolUse`/`Agent|Task` hook mirroring `log-reviewer-round.sh` would add only a `tool_use_id` the transcript already carries, at the cost of a new state file and sweep.
- **`authoring_agent` as an optional flag over a closed enum (`code-writer` | `inline` | `mixed` | `unknown`, default `unknown`), not free text.** `anchors: row3, row18` — kept from the original design unchanged: the transcript-derived value (was a `code-writer` dispatch's completion inside this round's span?) is authoritative for the join; the declared flag covers cross-session authorship and is cross-checked against the transcript-derived determination rather than trusted blindly (row 17's two-count bifurcation). An **absent** flag never aborts the append (the ledger's primary purpose — preserving the disposition — outranks the secondary one); an **invalid** value does abort, consistent with `--disposition`. `test_skills.py`'s `TestReviewLedgerAuthoringAgentEnum` mechanically pins `review-ledger.sh`'s accepted enum to `author_outcome.py`'s own comparison constants, so the two cannot drift apart silently.
- **`authoring_effort` as a validated flag over `low`/`medium`/`high`/`xhigh`, not read from `code-writer.md` frontmatter by the script.** `anchors: row13, row18` — unchanged from the original design: a frontmatter read would couple the ledger to the very assumption this measurement exists to overturn (that effort is a static per-file constant). `max` is deliberately excluded per CLAUDE.md's "`xhigh`, not `max`", so a `max` value aborts loudly. Drift in the prescribed literal is caught by `test_skills.py`'s `TestReviewLedgerAuthoringEffortLiteral`, which asserts the literal in `code-review/SKILL.md` equals `claude/.claude/agents/code-writer.md`'s own frontmatter value, which `test_agent_roster.py`'s `EXPECTED_EFFORT` independently pins to `high`.
- **Output carries no per-project, per-branch, or per-session dimension.** `anchors: root` — one aggregate table plus counters, by construction, so there is nothing for `redaction` to pseudonymize and no figure that could carry the per-engagement dimension CLAUDE.md § "Also redact structural fingerprints and provenance" forbids absolutely.

**Failure definition** (the subcommand's correctness rests on this; stated explicitly since it is a design call, not an engineer-supplied one):

A dispatch's completion index is the record index of its paired `tool_result` block, not its `Agent`/`Task` tool_use's own start position — a round that opened before the dispatch's own output existed cannot have reviewed that output. A dispatch's **attributed round** is the `code-review` round with the smallest `open_idx` strictly greater than that completion index; that round's **round ordinal** is its 1-indexed position in the transcript's own code-review-open sequence for that session. A ledger row is **matched** to a round when its own `round` field equals that round's ordinal exactly; a row with no `round` key at all (predating this field) never matches any round, since `None` can't equal an int.

Each dispatch classifies by walking three tests against its attributed round, in order:

1. No attributed round exists → **UNRESOLVED**.
2. The round has ≥1 matching ledger row with `disposition: ADDRESS` → **FAILURE**. `ADDRESS` means "must be fixed in this diff," which is exactly "the dispatch's output did not survive review." `ADDRESS` presence decides this regardless of whether a marker write or another matching row also exists in the same span.
3. Otherwise, the round concluded clean and the dispatch is a **PASS** iff the round has ≥1 matching row (necessarily all `DEFER`/`CLEAN`) or a `marker.sh write code-review` Bash call inside its own outcome span; **UNATTRIBUTED** if it has neither.

All five DEFER criteria (`code-review/SKILL.md:362-366`) describe findings that are not the dispatch's fault, so a DEFER-only round is a PASS, and no per-criterion split is added.

A round with zero matching ledger rows but a marker-write call is inferred clean rather than treated as a genuine ledger-backed PASS — this covers the review-narrative-ledger kill switch (on for that round, so nothing was appended) and any append that errored before landing — and is counted separately under `_DQ_KILL_SWITCH_INFERRED_CLEAN`.

A precondition sits before Test 1: a dispatch whose paired `tool_result` record is absent from the main-thread records is classified **UNDECIDABLE** rather than entering the three-test walk at all, counted only under Data quality, never in "Dispatches in scope."

Two non-failure buckets and one fan-out case, each of which would bias the share if collapsed into PASS:

- **UNRESOLVED** — no `code-review` round after the dispatch at all (typically the last dispatch of a session). Excluded from the denominator.
- **UNATTRIBUTED** — a round ran and left neither a matching ledger row nor a marker write. Excluded from the denominator and reported, so the operator sees the compliance rate rather than absorbing it as a passing grade. **Accepted regression, per `docs/transcript-analysis.md`'s author-outcome section:** a round that both had the ledger kill switch on and raised a genuine `ADDRESS` finding leaves no ledger row (kill switch) and no marker write (the review wasn't clean), so it reads identically to a round nothing happened in at all — accepted as narrow (the kill switch is a manual, rare operator toggle) rather than solved by re-deriving disposition from Bash argv text, which this design deliberately moved away from. A second, self-expiring accepted risk — a round straddling a live mid-session schema flip reading as a false PASS — is documented alongside it in that same doc section.
- **Co-authored rounds** — when several dispatches precede one round, the round's outcome fans out to each, the conservative reading. Counted under `_DQ_CO_AUTHORED_ROUNDS`.

A separate, non-classification data-quality check runs per session, not per dispatch: a session's ledger `round` values (restricted to rows carrying the key) must form the transcript's own exact `1..N` round-open sequence, or the session is counted under `_DQ_ROUND_NUMBER_MISMATCH`.

Output shape, one headline number with an explicit denominator plus one counter per named bias (verbatim from `docs/transcript-analysis.md`'s author-outcome section):

```
AUTHOR OUTCOME SOURCES (this repo (N project dirs); 1 root)
agent=code-writer  window=last 30d

Dispatches in scope                                 20
  FAILURE      (round had >=1 ADDRESS)              10
  PASS         (round concluded clean)               6
  UNRESOLVED   (no subsequent round)                 3
  UNATTRIBUTED (round ran, no ledger row, no marker)   1
Failure share: 10 of 16 resolved dispatches (62.5%)

Data quality
  rounds co-authored by >1 dispatch                                                 3
  rounds with a marker write but no ledger row (kill-switch inferred clean)         0
  sessions whose ledger round sequence doesn't match the transcript's round-opens   0
  dispatches with no paired tool_result (undecidable)                               0
  authoring_agent inconsistent with the transcript join                             1
```

The `authoring_agent inconsistent` counter compares each matching ledger row's own `authoring_agent` field (when present and not `unknown` — a row from a pre-migration transcript, or from a `code-writer.md` version older than this ships, may omit the flag entirely, which is treated identically to an explicitly-empty value: skipped, not miscounted) against the transcript-derived determination for that round — a `code-writer` dispatch attributed to the span or not — using an **unfiltered** dispatch count, distinct from the count that gates "Dispatches in scope." Two separate per-round counts come out of one `--since`-filtered pass over `_agent_dispatch_tool_use_ids`: a `--since`-filtered dispatch count (gates which dispatches enter "Dispatches in scope" and the reported outcome buckets) and a second, unfiltered dispatch count (every `code-writer` dispatch whose completion falls in the span, regardless of `--since`) that the inconsistency check reads instead — deriving both from one filtered count would report every round whose authoring dispatch falls just outside a `--since` cutoff as spuriously inconsistent, even though the round's own ledger rows are read without regard to `--since` at all.

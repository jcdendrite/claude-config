# Instrument review-narrative ledger with an authoring-agent/effort field and dispatch join key

## Context

This plan instruments the review-narrative ledger (`claude/.claude/scripts/review-ledger.sh`) and `transcript-analysis.py` so a later analysis can compute what share of `code-writer` subagent dispatches fail their own downstream `/code-review` check — the numerator GitHub issue #800 (`priority:high`) says is currently unreachable, blocking cost-guide audit row 9 ("re-run failures at higher effort" in `docs/cost-levers-considered.md`) from closing. Now, because issue #800 frames this as the concrete, buildable next step once a prior investigation (documented in the issue body and in `.claude/plans/escalate-effort-on-code-writer-failure.md` on a separate, unmerged branch) established that the ledger's schema and `transcript-analysis.py` both currently lack any signal tying a review finding back to the `code-writer` dispatch that authored the reviewed diff. The intended outcome is the three parts issue #800 specifies: (1) an authoring-agent/effort field added to the ledger's `append` schema, written at review time; (2) a join key from a ledger entry back to the specific `code-writer` dispatch that authored the diff under review; (3) a new `transcript-analysis.py` subcommand that reads the ledger, joins it against `subagent-mix`'s per-dispatch `code-writer` identification, and reports the failure share.

This plan does **not** compute or publish an actual failure-share number (no historical ledger data carries the new fields yet — the corpus only starts accumulating once this ships), does **not** close cost-guide audit row 9, and does **not** edit `docs/cost-levers-considered.md` — the register was deliberately left untouched by the prior session and everything routed to this issue instead.

A clarifying question was resolved with the engineer before design: `review-ledger.sh`'s ledger files are named `$REPO_HASH.$SESSION_ID.jsonl`, where `$REPO_HASH` hashes the *worktree's own path* — a value that changes per branch worktree in this repo's worktree-per-branch convention. Ruled out up front, per the engineer's explicit answer: changing `_marker_lib_repo_hash` itself (shared by the whole `marker.sh` gate system, whose completion markers are deliberately worktree-scoped) and accepting permanent data loss for since-cleaned-up worktrees (the engineer: "I don't like option 1 though because that greatly limits our data... we can't use a different heuristic?"). `plan-architect` was asked to find a third heuristic; its answer — a per-line `repo_identity` field derived from `git rev-parse --path-format=absolute --git-common-dir` (stable across every worktree of one repo, unlike `$REPO_HASH`) — is in the Approach section below.

This plan went through one `/plan-review` round. `staff-sdet` and `staff-platform-engineer` returned two blockers and five concerns; every item is resolved in the Approach, Critical files, and Verification sections below (see the assumption-ledger rows and mechanism justifications, which now cite the fixes directly).

## Approach

Bridge the numerator issue #800 describes by making each ledger line self-describing about its repository and its diff's author, and by joining the ledger to the transcript through the `review-ledger.sh append` Bash calls that `/code-review` already emits — those calls are themselves `tool_use` records inside a round window `review_rounds.py`'s round detector already computes, so no new hook and no captured `tool_use_id` are needed. Three additive JSON fields (`repo_identity`, `authoring_agent`, `authoring_effort`), none of which varies between two calls inside one review round, plus a new `transcript-analysis.py author-outcome` subcommand that reports a failure share with every bias it cannot remove printed alongside it as a named counter.

The three structural findings that shape this design, all of which move it away from what #800 prescribes:

**The join key already exists in the transcript.** #800 treats "a join key from a ledger entry back to the specific `code-writer` dispatch" as missing. It is missing *from the ledger*, but every `review-ledger.sh append` invocation is a Bash `tool_use` record at a known record position, inside a round window `_detect_round_windows` already computes, in the same transcript that carries the `Agent`/`Task` dispatch records. So round attribution, dispatch ordering, and clean-round detection are all recoverable today; the ledger's unique contribution is the *structured* disposition and any field a human deliberately declares. That collapses the dispatching session's own follow-up questions — a captured marker would need invalidating so a stale dispatch identity isn't charged to a later human-only edit, and a transcript window has nothing to invalidate: a window containing no `code-writer` dispatch is attributed to `inline` by construction.

**A clean round already emits a positive transcript signal, so no round outcome has to be inferred from the round that follows it.** `/code-review` runs two independent per-round steps: it appends one ledger line per finding *on every invocation, clean or not* (`code-review/SKILL.md:381`), and it runs `marker.sh write code-review` *exactly once and only when the review is clean* (`:449-460`). A zero-line round is therefore not ambiguous — the marker-write call distinguishes "clean" from "the append step was skipped" directly, inside the round's own span. This replaces an earlier draft's "did a dispatch intervene before the *next* round" inference, which had no answer for a zero-line round that was itself the session's last round (row 10, row 11).

**A per-call timestamp field would have silently broken dedup.** `_lib_append_line_locked` (`claude/.claude/hooks/_lib.sh:2638`) dedups with `grep -qFx -e "$line"` — whole-line verbatim, inside the lock, and shared with `log-reviewer-round.sh`. Any per-call-varying field turns a retried identical finding into a second line, regressing the behavior `test_review_ledger_script.py:159-182` pins. All three chosen fields are constant across a round, so the primitive is untouched and dedup keeps working unchanged. This is the property that makes the design additive rather than layered, and it is why no `ts` field appears below.

**Root problem.** For each `code-writer` dispatch, nothing today can answer "did the review round that judged its diff record a must-fix finding" — the disposition lives only in a ledger whose files cannot be attributed to a repository (its `$REPO_HASH` names one worktree path, so two live worktrees of one repo are already indistinguishable from two unrelated repos), and whose lines carry no round or authorship signal.

**Givens** (fixed beyond this plan's reach):

- `effort` is subagent-definition frontmatter, not a per-dispatch `Agent`-tool parameter, so `authoring_effort` will log the constant `high` until a future issue builds an override — Anthropic owns the dispatch schema.
- The ledger sweeps at 30 days (`review-ledger.sh:87`) while transcripts persist longer, so no historical corpus exists for the new fields and the measurement starts accumulating only at merge.
- `/code-review`'s append is orchestrator prose (`code-review/SKILL.md:381`), not a hook, so append compliance is a model behavior this plan can measure but not enforce. The marker write it is cross-checked against is *partly* enforced — `require-code-review.sh` denies `git commit` without a matching marker — but a session that never commits is under no such pressure.

**Mechanism justifications:**

- **`repo_identity` = `_marker_lib_repo_hash` applied to the validated `--git-common-dir` value, embedded per line; the subcommand globs each root's ledger directory and filters on it.** `anchors: row2, row4` — its everyday value is not the orphan case: `$REPO_HASH` hashes one worktree path, so without this field two *live* worktrees of one repo are already indistinguishable from two unrelated repos and cannot be unioned at all. It additionally keeps an orphaned file attributable as long as the *main* checkout exists, a far weaker condition than the authoring worktree existing. Over-powered check, three lighter/alternative primitives weighed: (a) `git worktree list` live-worktree enumeration — rejected, it is precisely what row 2 rules out and `docs/transcript-analysis.md:38` documents this exact silent-exclusion failure; (b) a sidecar hash→identity map file in the ledger directory — rejected, it adds a second artifact needing its own lock, sweep, and consistency invariant to answer a question one field answers; (c) hashed `git remote get-url origin` — rejected, absent for a local-only repo, differs between SSH and HTTPS forms of one repo, and identical across forks. Root-commit SHA rejected separately: it is a private-repo commit SHA, which `CLAUDE.md` § "Redact private-project-identifying content" names as reviewer-discipline-redactable, and `transcript-analysis.py` output is routinely quoted into public PR bodies (`scope.py:47-56`). The value is stored hashed, never as a raw path, for the same reason `_marker_lib_repo_hash` hashes.
- **`_lib_repo_identity_hash` validates the captured value's shape before hashing, and deliberately does *not* pipe through `tr -d '\n'`.** `anchors: row5, row6` — the two-outcome contract (`exit 1`, empty stdout) is only real if the pre-2.31 echo-back reaches it as a *failure* rather than as a longer string. `_lib_repo_root` is not a like-for-like precedent: `--show-toplevel` takes no `--path-format` flag, so it has no echo-back mode to guard. Required shape, one `case` over the captured value, both arms load-bearing: reject if it contains a newline (row 6's echo-back discriminator), reject if it does not begin with `/` (an absolute path is the only shape whose hash means anything here). Rejecting on either arm returns exit 1 with empty stdout; nothing is hashed. The single-check-of-one-value form is deliberate over layering a second guard elsewhere. The failure is then *observable* rather than silent: `review-ledger.sh` omits the `repo_identity` key entirely on a helper failure (never an empty string, which would union unrelated repos under one identity) and still writes the line, so a pre-2.31 contributor's lines land in the existing "ledger lines with no `repo_identity`" counter instead of being hashed wrong. A helper result is stable for a session's lifetime, so row 7's round-stability requirement still holds.
- **A new `_lib_repo_identity_hash` helper in `_lib.sh`, calling the untouched `_marker_lib_repo_hash` with a different input.** `anchors: row1, row6` — inlining the recipe in `review-ledger.sh` is lighter but the Python side must reproduce it byte-for-byte, and `_lib_reviewer_round_state_key`'s own "Determinism contract" comment (`_lib.sh:2518-2523`) establishes `_lib.sh` as this repo's home for a cross-consumer hash recipe. Purely additive: no existing caller changes.
- **The Python side re-derives the same hash and applies the same shape validation.** `anchors: row4, row5` — asymmetric validation would be worse than none: Python hashing garbage that bash refuses makes the two sides disagree exactly where the field is least trustworthy. `scope._repo_scoped_project_slugs` is the in-package precedent for shelling out to git and failing closed (`sys.exit(1)`) rather than degrading to a wider scope. One `git rev-parse` call serves both the identity hash and row 20's project-slug prefix.
- **The dispatch-to-round ordering key is the dispatch's paired `tool_result` record index (completion), not its `Agent`/`Task` `tool_use` record index (start), computed over the same deduped main-thread record list the round windows come from.** `anchors: row8, row9` — a round can legitimately open while a dispatch is still running (two dispatches issued back-to-back, or main-thread work triggering a review mid-dispatch), and a start-keyed join would then charge that round's findings to a diff not yet on disk. Completion-keyed, that is impossible. Both keys must be indices into one list, so `author_outcome.py` runs `pricing.dedup_turns_by_request_id` first and derives both keys from the result — mixing a pre-dedup index with a post-dedup one silently misorders. A dispatch whose paired `tool_result` is absent from the main-thread records is left undecidable and counted, mirroring `_build_tool_result_ts_map`'s own documented posture, rather than falling back to the start index.
- **The round's *outcome span* is `[open_idx(r), open_idx(next code-review round))`, not `_detect_round_windows`'s own `window_end`.** `anchors: row18` — a user interjection between the review and its marker write ends `window_end` but does not end the round's outcome; and nothing but a `/code-review` run emits either signal, since `review-ledger.sh append` is gated to `append code-review` and the marker call to `write code-review`, so a wider span cannot capture an unrelated event. `_detect_round_windows` is still the source of `open_idx`/`skill`; only its `window_end` is unused here.
- **No new hook.** `anchors: row8, row10` — the lighter primitives that make one unnecessary are already in place: the transcript's own `Agent`/`Task` records joined via `corpus._index_subagent_dispatches`, the `marker.sh write code-review` call as the clean-round signal, and the orchestrator-declared `authoring_agent` field for the one case the transcript cannot cover (a handoff, where the dispatch ran in session A and the review in session B). A `PostToolUse`/`Agent|Task` hook mirroring `log-reviewer-round.sh` would add only a `tool_use_id` the transcript already carries, at the cost of a new state file, a new sweep, and a marker-invalidation problem.
- **`authoring_agent` as an optional flag over a closed enum (`code-writer` | `inline` | `mixed` | `unknown`, default `unknown`), not free text.** `anchors: row8` — the transcript-derived value is authoritative for the join; this field covers cross-session authorship and doubles as the over-accept/under-accept cross-check the corpus needs during its first accumulation period. The CLI's `--agent NAME` governs the transcript-side join only, so the cross-check counter is meaningful only at its `code-writer` default. An **absent** flag never aborts the append (that would sacrifice the ledger's primary purpose — preserving the disposition — for its secondary one); an **invalid** value does abort, consistent with `--disposition`, because the value is prescribed as a literal in `code-review/SKILL.md` and an invalid one means that prose drifted. `code-review/SKILL.md`'s existing "summarize more tightly and retry, not skip" instruction extends to cover the two new flags, so a loud abort is recoverable inside the same turn.
- **`authoring_effort` as a validated flag over `low`/`medium`/`high`/`xhigh`, not read from `code-writer.md` frontmatter by the script.** `anchors: row23, row on Givens/effort` — a frontmatter read is deterministic but couples the ledger to the very assumption this measurement exists to overturn (that effort is a static per-file constant), and it would break the moment a per-dispatch override ships. `max` is deliberately excluded per CLAUDE.md's "`xhigh`, not `max`", so a `max` value aborts loudly rather than being recorded — the correct signal that the routing rule changed. Drift in the prescribed literal is caught by a test instead: `claude-skills/skills/tests/test_skills.py` asserts the literal in `code-review/SKILL.md` equals `claude/.claude/agents/code-writer.md`'s own frontmatter value, which `test_agent_roster.py`'s `EXPECTED_EFFORT` independently pins to `high` — one chain, no test-to-test import.
- **A `Bash`-command-to-ledger-line matcher as its own named, independently tested unit, joining on the `--finding` value.** `anchors: row8, row21` — this is the load-bearing boundary between two independently-evolvable representations (a shell command line and a `jq`-emitted JSON object), and `review-ledger.sh:201-203` binds `--finding`'s value verbatim into the line's `finding` field with no transformation, and rejects rather than truncates an over-cap value (`:172-175`), so exact string equality on that one field is the whole contract. The match is deliberately **many-to-one**, not one-to-one: row 7's dedup means an identical finding re-raised in a later round produces *no* new ledger line, so one line is legitimately attributed to every round whose span contains an append call naming it. Binding each line to its first matching call instead would leave the later round looking line-less. Both directions of failure get a counter — a line no call names, and a call no line matches (the shape a `$VAR` or heredoc-built command produces).
- **The tokenizer moves into `corpus.py` and the shim imports it, rather than being reimplemented in `author_outcome.py`.** `anchors: row21` — a second `shlex.split`-plus-operator-split copy is a duplicated parser, which the single-source-of-truth rule treats as a defect absent a named exception; and shim-imports-package is the migration direction the architecture doc already states (row 17). Operator segmentation is not defensive here: `enforce-marker-script-shape.sh` explicitly *permits* `marker.sh write code-review && git commit …` (row 11), so the marker signal is routinely inside a chain. `corpus.py` is a looser categorical fit than `render.py` (whose documented scope — "small display-formatting and text-normalization helpers with no state of their own" — reads closer to a tokenizer than `corpus.py`'s "JSONL transcript read/parse and session iteration"), but no consumer-scope test pins either module's docstring, so this is a naming judgment call rather than a correctness one; `corpus.py` is chosen only because it is already this plan's other new dependency for `author_outcome.py`, keeping the new import surface to one module rather than two.
- **The clean-marker matcher accepts only the hook-allowlisted shape.** `anchors: row11` — matching `basename(argv[0]) == "marker.sh"` plus exactly `write code-review` is stricter than a substring search and strictly weaker than reimplementing `MARKER_SHAPE`, and it inherits the gate's guarantee that no wrapper or variable form of the call can exist in the transcript. One residual, named rather than layered against: a call that passed the gate but failed at runtime (`marker.sh` could not resolve `SESSION_ID`) reads as clean. Its `tool_result` is not inspected — the skill instructs the session to abort and report on that path, and it cannot then commit, so the case is rare and self-limiting.
- **A new `author-outcome` module under `transcript_analysis/`, not an extension of an existing subcommand.** `anchors: row12, row17` — extending `subagent-mix` is nominally lighter but lands new code in the 12k-line un-migrated shim against the direction `docs/transcript-analysis-architecture.md` documents, and `subagent-mix` discards per-dispatch identity after aggregation; extending `reviewer-yield` is barred by row 12. Naming follows the existing two-word domain-first set (`reviewer-yield`, `review-trace`, `review-round-cost`), with `--agent NAME` defaulting to `code-writer` so the mechanism is not agent-hardcoded in the CLI surface. Scope resolution follows `cmd_review_round_cost` exactly (`scope.resolve_scan_roots` then `scope._resolve_project_scope`), and the ledger directories derive per-root as `root.parent / "review-narrative-ledger"` (row 19) so a multi-root run reads every account's ledger rather than only the active one.
- **Full-glob-then-filter over each root's ledger directory, with the cost bound stated rather than inferred.** `anchors: row2, row19` — ledger files are flat and carry no per-repo partition in their names, so unlike the transcript corpus (whose per-project subdirectories `scope.py` narrows *before* scanning) there is nothing to narrow up front. What bounds the cost is `_sweep_stale_ledger_files` (`review-ledger.sh:68-87`), which deletes every ledger and lock file older than 30 days by mtime on every append, across every repo hash. So the glob is bounded by 30 days of `/code-review` activity **account-wide** — every repo the account has reviewed in — not by the target repo's own activity, and it multiplies by the number of resolved roots. With each line capped near 700 bytes and dedup keeping files small, that is tens to low hundreds of files for an active multi-project account. Stated as an accepted tradeoff in the new docs section, the same way the rejected alternatives above are stated.
- **Output carries no per-project, per-branch, or per-session dimension.** `anchors: root` — one aggregate table plus counters, by construction, so there is nothing for `redaction` to pseudonymize and no figure that could carry the per-engagement dimension CLAUDE.md § "Also redact structural fingerprints and provenance" forbids absolutely. This is a design constraint on the output shape, not a post-hoc filter.

**Failure definition** (the subcommand's correctness rests on this; stated explicitly since it is a design call, not an engineer-supplied one):

A dispatch's **attributed round** is the `code-review` round with the smallest `open_idx` strictly greater than that dispatch's completion index. Its **outcome span** is `[open_idx, open_idx of the next code-review round)`, or `[open_idx, end of records)` for the last round in the session. A ledger line is **attributed** to a span when some `review-ledger.sh append code-review` call inside that span names its `finding` value.

Each dispatch classifies by walking three tests against its attributed round, in order:

1. No attributed round exists → **UNRESOLVED**.
2. The span has ≥1 attributed line with `disposition == "ADDRESS"` → **FAILURE**. ADDRESS means "must be fixed in this diff," which is exactly "the dispatch's output did not survive review." ADDRESS presence decides this regardless of whether a marker write also appears in the same span — the finding was raised against that diff, and a same-span fix does not undo that.
3. Otherwise, the round concluded clean and the dispatch is a **PASS** iff the span contains either ≥1 attributed line (necessarily all DEFER) or a `marker.sh write code-review` call; **UNATTRIBUTED** if it contains neither.

All five DEFER criteria (`code-review/SKILL.md:358-365`) describe findings that are not the dispatch's fault — orthogonal scope, cross-PR coordination, gold-plating past the declared surface, a contract pinned elsewhere, an edge case below scale — so a DEFER-only round is a PASS, and no per-criterion split is added (the criterion lives in free-text `rationale`, and mining it would need a sixth field for no gain here).

Test 3 is what makes the classification total. It asks only about the round's *own* span, so a zero-line round that is the session's last round has the same determinate answer as any other zero-line round — an earlier draft's "did a dispatch intervene before the next round" rule had no answer there, and is gone rather than patched with a third case. UNATTRIBUTED now means both prose steps were skipped, which is a stronger non-compliance signal than the append alone.

A precondition sits before Test 1, not among the three tests: a dispatch whose paired `tool_result` record is absent from the main-thread records has no completion index to compute an attributed round from, and is classified **UNDECIDABLE** rather than entering the three-test walk at all — mirroring `reviewer_yield._build_tool_result_ts_map`'s own documented omission behavior for the same shape of gap. This is stated here, not only in the mechanism justifications above, because a reader implementing strictly from this section needs the short-circuit named where the rest of the classification lives.

Two non-failure buckets and one fan-out case, each of which would bias the share if collapsed into PASS:

- **UNRESOLVED** — no `code-review` round after the dispatch at all (typically the last dispatch of a session). Counting these as PASS biases the share low; they are excluded from the denominator.
- **UNATTRIBUTED** — a round ran and left neither a ledger line nor a clean-marker write. Excluded from the denominator and reported, so the operator sees the compliance rate rather than absorbing it as a passing grade. One known residual lands here rather than getting its own counter: `/code-review`'s Step 0.1 short-circuit (`code-review/SKILL.md:25`) exits before both steps when the staged diff already matches a fresh clean marker. It is rare by construction — the marker is content-addressed on the staged diff, so any dispatch that changed a staged byte invalidates the match.
- **Co-authored rounds** — when several dispatches precede one round, the round's outcome fans out to each (each contributed bytes to a diff that failed), which is the conservative reading. The count of such rounds prints as its own counter so the operator can see how often fan-out mattered. Finer per-file attribution via the `--source` field is out of scope below.

Proposed output shape, one headline number with an explicit denominator plus one counter per named bias:

```
AUTHOR OUTCOME SOURCES (this repo (N project dirs); 1 root)
agent=code-writer  window=last 30d

Dispatches in scope                             20
  FAILURE      (round had >=1 ADDRESS)          10
  PASS         (round concluded clean)           6
  UNRESOLVED   (no subsequent round)             3
  UNATTRIBUTED (round ran, no line, no marker)   1
Failure share: 10 of 16 resolved dispatches (62.5%)

Data quality
  rounds co-authored by >1 dispatch                        3
  ledger lines with no repo_identity                       0
  ledger lines matching no append call                     2
  append calls matching no ledger line                     1
  ledger files whose session names no in-scope transcript  0
  dispatches with no paired tool_result (undecidable)      0
  authoring_agent inconsistent with the transcript join    1
```

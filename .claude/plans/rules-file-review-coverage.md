# Rules-file review coverage

## Context

`.claude/rules/*.md` path-scoped rule files have no review coverage at
code-review time. `/skill-review` is scoped to SKILL.md, `/agent-review` to
agent files, and `/ai-instruction-and-memory-files` to
CLAUDE.md/AGENTS.md/auto-memory — so a rules-file edit reaching commit is
reviewed only by generic `/code-review`. Why now: rule files carry real
behavioral authority (they auto-load into any session that opens a matching
file), the stowed `claude/.claude/rules/` set applies in *every* repo a stow
consumer opens, and a live latent defect of exactly the uncaught class already
exists in the repo (S19, below). Intended outcome: rule files get the same
review coverage at code-review time that they already have at plan time, plus
a mechanical check for the glob-correctness failure mode that no human review
reliably catches.

The asymmetry has a known origin. PR #721 (`ad1f199`, "Plan it consider
rules") added `.claude/rules/` awareness to `plan-it`, `plan-review`, and
`ai-instruction-and-memory-files` — and touched `code-review/SKILL.md`
nowhere. This is an unfinished sibling arm, not an undesigned area.

### Decisions taken this session

- **Scope** — "dispatch fix + glob test," over prose-only and over authoring a
  new `rules-review` skill. `[engineer-verified]`
- **S19 fix is in scope** — composite-action globs added to
  `claude/.claude/rules/github-actions-workflows.md`. `[engineer-verified]`
- **Stowed-glob portability is enforced** (row3d) — a stowed rule's `paths:`
  globs must carry no leading literal segment. `[engineer-verified]`
- **Both architect-added items are kept** — the `ai-instruction-and-memory-files`
  scoping note (row4a) and the `review-pipeline-dispatch.md` body bullet
  (row2). `[engineer-verified]`

## Approach

Close the rules-file review gap by adding one dispatch clause to `/code-review` (mirroring the clause `/plan-review` already carries), pointing `review-pipeline-dispatch.md`'s own `paths:` at rule files so the dispatch guidance loads when you edit one, and extending the existing `test_rules_frontmatter.py` with a **literal-prefix / portability** check on each `paths:` glob. That glob check is what makes the S19 fix safe to ship in the same PR: it validates each glob's *non-wildcard leading segments* against the corpus that glob actually targets, which catches a misspelled path root while leaving a fully-portable forward-looking pattern like `**/.github/actions/**/action.yml` untouched. No new skill, no new hook, no new test module.

**row3 — extend `rule_frontmatter_violations()` in the existing `claude/.claude/skills/tests/test_rules_frontmatter.py` with a per-glob literal-prefix check.** `anchors: root`. Algorithm, per glob string:

1. Extract the literal prefix in a named module-level helper, `_literal_prefix_segments(glob: str) -> tuple[str, ...]` — the algorithm needs a paragraph to explain, which is CLAUDE.md's own signal to extract and name it. Parse with `PurePosixPath(glob).parts` rather than `glob.split("/")`: `paths:` globs are `/`-separated regardless of host, and `PurePosixPath` absorbs `//`, trailing `/`, and leading `./` for free. Take the longest leading run of segments containing no glob metacharacter (`itertools.takewhile` reads as its own name) — the **full run**, not the first segment, so a typo in a later literal segment (`claude/.claude/skils/**`) is still caught. Build error messages from the original string, since normalization means the parsed segments may not be a verbatim substring of the file's text.
   - `_GLOB_METACHARACTERS = frozenset("*?[{")` as a module constant, carrying one grounding line: `{` is included because brace expansion **is** supported (see row3e), and `glob.has_magic` is deliberately not used because its magic set omits `{` — it would call `{skills,agents}` literal, extend the prefix, find no such directory, and emit a false positive. `[verified: `glob.has_magic('{a,b}')` returns `False` and `glob.escape('a{b,c}d')` leaves the braces unescaped, both run this session]`
2. **Empty or whitespace-only glob entry** is a violation in both classes. `paths: [""]` currently passes the existing all-strings check and would otherwise be silently exempted as "portable."
3. **Stowed rule** (file under `claude/.claude/rules/`): a non-empty literal prefix is a violation. Its referent corpus is every consumer repo (G2), so a leading literal either is a typo or wrongly assumes this repo's layout.
4. **Project rule** (file under `.claude/rules/`): a non-empty literal prefix must resolve to an existing **directory** under `_REPO_ROOT`. An empty prefix (a fully-portable `**/…` glob) is exempt — its referent is any path in this repo, which stays meaningful.
   - Use `.is_dir()`, not `.exists()`: a prefix naming an existing *file* followed by a wildcard segment (`docs/rules-references.md/**`) is nonsensical and must flag.
   - **Reject escaping prefixes lexically, before touching the filesystem.** Two separate predicates on the parsed pattern, each naming its own defect: flag if `PurePosixPath(glob).is_absolute()`, and flag if `".."` appears anywhere in the **whole glob's** parts — not merely within the extracted literal prefix. Scanning the whole pattern also rejects a post-wildcard escape such as `docs/**/../secret/**`, which a prefix-only scan would miss. Do **not** reach for `joinpath` plus `.is_relative_to()` — `is_relative_to` is purely lexical and does not collapse `..`, so `Path("/a/b").joinpath("..","x").is_relative_to(Path("/a/b"))` is `True` and a `../`-walking prefix passes the guard, after which `.is_dir()` follows the real filesystem outside the repo. `[verified: both expressions evaluated this session]` Checking lexically avoids consulting the filesystem at all for input that is malformed on its face, and yields a specific message per case.
5. Reuse the module's existing `_discover_rule_files()`, `_REPO_ROOT`, and parametrized-test scaffolding — add no second parametrized test. **There is no accumulator to append to:** `rule_frontmatter_violations()` currently returns a single-item list from each guard branch and ends with a bare `return []`. Replace that terminal `return []` with the glob-check results. The existing early returns do not mask the new check — they are mutually-exclusive structural prerequisites (absent/invalid frontmatter, wrong `paths` type, non-string entries) that cannot co-occur with a well-formed-but-badly-globbed list.
6. **Take the classification as a parameter; do not infer it from the path.** Change the signature to `rule_frontmatter_violations(rule_file: Path, *, is_stowed: bool)` and have `_discover_rule_files()` return `(path, is_stowed)` pairs — it already knows the class in its own two-directory loop and currently discards it for a downstream ancestry test to reconstruct. `[verified: `rule_frontmatter_violations` has no callers outside its own module]` **"No external callers" is not "free"** — an earlier draft said free, which overclaimed. Three in-module sites must change, and the implementer should not have to infer them:

   1. `_RULE_IDS = [str(f.relative_to(_REPO_ROOT)) for f in _RULE_FILES]` — `f` is now a `(path, is_stowed)` tuple; unpack it.
   2. The `@pytest.mark.parametrize("rule_file", _RULE_FILES, ids=_RULE_IDS)` decorator — needs a two-name argument string and a matching test signature.
   3. All 8 existing call sites inside `TestRuleFrontmatterViolations` — each needs the new `is_stowed=` keyword, which is required and has no default.

   None of these fail silently: each raises `AttributeError` or `TypeError` at collection or call time. The cost is implementer friction, not a masked defect.

   This replaces an earlier draft that grew `_write_rule` with a `stowed: bool` writing into a fabricated `tmp_path/"claude"/".claude"/"rules"/` tree. That shape was wrong three ways: it fabricates a directory tree for fixtures that care about nothing but a glob string and a class; it forces a *second* hand-rolled path routine into production code (a relative-suffix test, since the check could no longer be `is_relative_to(_STOWED_RULES_DIR)`) purely to make fixtures work; and that suffix test carries a silent ordering bug — `claude/.claude/rules/x.md` also ends with `.claude/rules/x.md`, so a project-first classifier labels every stowed rule a project rule, with no symptom except row3d quietly never firing.

   With the explicit parameter, `_write_rule` stays byte-identical, every unit fixture is `(tmp_path/"rule.md", is_stowed=True|False)`, and the function becomes pure with respect to classification. The only remaining filesystem touch is the project-rule `.is_dir()` resolution against `_REPO_ROOT`, which is inherently filesystem-grounded and belongs. Keep it a keyword-only `bool` rather than an enum — there are exactly two classes, both already named in the module, and `*, is_stowed:` removes the boolean-trap objection at each call site. Do not also parameterize `_REPO_ROOT`; it has exactly one production value.

**row3e — the `paths:` contract is documented upstream; a new stowed rule records it and `docs/rules-references.md` carries the citations.** `anchors: root`. `[engineer-verified: fill the documentation gap and cite sources]` An earlier draft called brace semantics "undocumented in-repo, so exclude conservatively rather than guess." - **Brace expansion is supported.** *"You can specify multiple patterns and use brace expansion to match multiple extensions in one pattern"*; `src/*.{ts,tsx}` expands to two patterns. So treating `{` as a metacharacter in row3 is **required for correctness**, not a conservative guess.
- **Brace expansion is budget-bounded, and overflow fails silently.** A rule's whole `paths` list shares a budget of 1,000 expanded patterns and 4 MiB; *"Claude Code uses any pattern that would exceed the budget unexpanded, and its literal braces match no files."* A silent-no-match class, same shape as a typo'd glob.
- **A malformed bracket expression also fails silently.** *"A pattern with a `[` that can't be read as a bracket expression, such as `photos [2024/**`, is invalid: it matches nothing, and the rule's other patterns keep working."* Escape a literal `[` as `\[`.
- **A rule with no `paths:` key loads unconditionally at launch**, *"with the same priority as `.claude/CLAUDE.md`"* — so a missing key is a context-budget event, not merely a scoping slip. This grounds the existing test's assertion that `paths:` must be present.
- **`?` support, leading-`/` anchoring, and trailing-`/` semantics are `[unverified]`** — not stated at primary source. Record them as unknown; do not fill them by inference.

# GH-748: Fix recurring `git commit -F -` habit tripping the PII-commit gate

## Context

Fix the recurring `git commit -F -` (or `-F /dev/stdin` / `-F /dev/fd/*`) habit that trips the PII-commit gate. Weekly denial counts for this exact gate grew 16x over four consecutive weeks (2 → 6 → 17 → 33, 2026-07-30 through 2026-08-26), with the same exact mistake recurring verbatim across two sessions six days apart (source: error-mode-analysis run 2026-08-27, finding A8). `code-review/SKILL.md` is the sole repo-wide place that instructs sessions how to construct a `git commit` message; it tells sessions to use `-F <file>` for multi-line messages but never shows how to safely create `<file>`, so sessions fall back to the generic heredoc-to-stdin shell idiom that every commit gate denies. Fixing now closes that guidance gap before the recurrence grows further.

## Approach

Rewrite the commit-message paragraph in `code-review/SKILL.md` (currently line 408) from a bare shape reference into a complete authoring recipe — Write tool into an `mktemp` file, then `git commit -F <literal path>` — that names the four denial traps explicitly, including `-F -` / `/dev/stdin` / `/dev/fd/*` in the gate's own wording. This is a prose-only change to one file. The root problem is that the line names the required *shape* (`-F <file>`) without the *reason* the shape is required and without any recipe for producing `<file>`; a model that must emit a multi-line message and has been told `-m` is unavailable then reaches for the nearest shape-compatible shell idiom — a heredoc piped to `-F -`. Teaching the reason (both gates must read the message off disk *before* git runs, and neither can read the stdin of a process that has not started) makes `-F -` self-evidently wrong rather than arbitrarily blocked, and giving the Write-tool recipe removes the need to reach for a heredoc at all.

**Alternatives set aside.** *Changing the gate to accept `-F -`* — rejected: `deny-pii-in-commits.sh` cannot statically verify what git will later read from a pseudo-file, so accepting it would route unscanned content into a public repo; the fail-closed posture is the gate's purpose, not a defect. *A `~/.claude/scripts/commit-with-message.sh` wrapper taking the message on stdin* — rejected as strictly worse than the status quo: hooks gate the Bash tool-call boundary, so a wrapper's internal `git commit` never reaches `require-code-review.sh`, `deny-pii-in-commits.sh`, or `deny-private-project-refs.sh`, silently disabling all three. *A PreToolUse hook rewriting `-F -` into a temp file* — rejected for the same unscannable-content reason, plus it mutates tool input to work around guidance that costs nine lines to fix. *A CLAUDE.md rule* — rejected per `ai-instruction-and-memory-files/SKILL.md:130`: a rule that applies only while a specific skill runs belongs in that skill's body, since CLAUDE.md spends every session's attention budget. *A `.claude/rules/*.md` path-scoped rule* — rejected: rules activate on the path of an open file, and this one must fire on a Bash command shape regardless of what file is open. *Amending the gate's denial message* — rejected: the denial only teaches inside the session that already paid for it, and the observed recurrence is across sessions, so a post-hoc message cannot reach the next one.

**Two accuracy corrections are folded into the rewritten sentence** (in-file scope, Axis 2 — the sentence is being rewritten anyway, and carrying a known-false claim forward is worse than dropping it). First, the current clause "not `-m` with a heredoc or command substitution, which the invocation-shape gate rejects" is half wrong: `enforce-marker-script-shape.sh:599-602` states outright that "Backticks and `$` (command substitution) remain permitted" in the chained-commit form. Second, the real hazard with `-m "$(cat …)"` is not denial but silence — `deny-private-project-refs.sh` appends only the literal `$COMMAND` string to its scan target, so a command-substituted message reaches the commit entirely unscanned (documented as a known gap in that hook's own header, lines 74-77). The replacement prose warns against that shape on the accurate grounds.

### Assumption ledger

**Root problem:** `code-review/SKILL.md` prescribes `git commit -F <file>` for multi-line commit messages without a recipe for creating `<file>`, so sessions fill the gap with the generic heredoc-to-stdin idiom (`git commit -F - <<EOF`), which every commit gate denies.

**Givens** (fixed, outside this plan's reach):
- **G1.** The commit gates reject pseudo-file `-F` sources and fail closed on unreadable ones. A protocol constraint, not a policy choice: the hook runs before git does and cannot read a not-yet-started process's stdin (`deny-pii-in-commits.sh:287-292, 360-367`).
- **G2.** Skills cannot share partials — `SKILL.md` has no `includes:`/`import:` field, so any overlap between this recipe and `pr-description`'s is duplicated by design. Fixed by the repo's own authoring rule (`.claude/rules/skill-and-agent-self-review.md`).
- **G3.** The only pre-emission teaching channel is text already loaded into the session's context. Everything else in the system (hooks, gates) can only react after the model has emitted the command. Fixed by the harness's execution model.

**Assumptions:**

1. The recurrence is a guidance gap, not a gate bug — the gate's behavior is correct and intentional. `[verified: deny-pii-in-commits.sh:68, 103, 287-292, 360-367 — pseudo-file rejection is documented as a deliberate fail-closed posture, gated independently of arming]`
2. `code-review/SKILL.md` is a *sufficient* single home, because every `git commit` routes through it. `[verified: require-code-review.sh:64 gates any Bash command matching git commit at a chain boundary; code-review/SKILL.md:3 self-describes as "Also the gate on git commit"]`
3. `pr-description/SKILL.md:164-190` is a working exemplar for the identical problem class (mktemp + Write tool + literal path, never a shell argument), and its constraint set is provably the same — both command strings land in the same `SCAN_TARGET` and face the same six structural detectors. `[verified: deny-private-project-refs.sh:462 (git commit path) and :500 (gh pr path) both append $COMMAND; detectors at :623-630]`
4. A `$HOME`-rooted message-file path is *also* denied — a trap the current line does not mention. `[verified: _LIB_HOME_ROOTED_PATH_REGEX at _lib.sh:1336 matches /Users/<name> or /home/<name>, scanned against the command string per row 3]`
5. A `$VAR` message-file path fails closed — the second trap the current line does not mention, and the one a session hits if it writes `MSG=$(mktemp …); git commit -F "$MSG"`. `[verified: deny-pii-in-commits.sh:364 — the unexpanded literal is not a readable regular file, so the unreadable-source branch denies]`
6. The current line's command-substitution attribution is false and must not be carried forward. `[verified: enforce-marker-script-shape.sh:599-602]`
7. `-m "$(cat …)"` is permitted by every gate yet reaches the commit unscanned, making it a worse outcome than the denial it appears to solve. `[verified: deny-private-project-refs.sh:74-77 known-gap note; SCAN_TARGET holds only the literal command text]`
8. No test, eval fixture, or hook pins the current wording of line 408, so this is a pure prose edit with no test-file changes. `[verified: no match for "commit -F" / "UUID-shaped" / "long-hex" / "scratchpad" across claude/.claude/**/*.py outside the hooks' own shell-parsing tests]`
9. There is line-count headroom: the file is 419 lines against a 500-line cap for structural-dispatcher skills. `[verified: check-skill-length.sh:71 assigns 500 to code-review; the file's last line is 419]`
10. The denial counts (2 → 6 → 17 → 33 across 2026-07-30 to 2026-08-26) and the verbatim cross-session recurrence come from the error-mode-analysis run of 2026-08-27, finding A8. `[unverified]` — not re-derivable with read-only tools this session. Load-bearing for *priority* only; the design does not depend on the magnitude.
11. Absent a recipe, the heredoc-to-stdin idiom is what a model reaches for. `[unverified]` — a causal inference from the recurrence shape, not an observed decision trace. The fix does not depend on it being the sole cause: supplying a complete recipe removes the need for *any* substitute idiom, correct or not.

**Mechanisms:**

- **Replace one paragraph in `code-review/SKILL.md` with a three-paragraph recipe.** The lightest primitive that closes the gap — prose is the only channel that reaches the model before it emits the command (G3), and this is the one file loaded on every commit path. `anchors: root, row2`
- **Recipe body: `mktemp` + `Write` tool + literal path in `-F`.** Reuses the sibling recipe already proven on an identical constraint set rather than inventing a second pattern for the same problem. `anchors: row3`
- **Name `-` / `/dev/stdin` / `/dev/fd/*` verbatim as the prohibited `-F` argument.** Echoes the gate's own denial wording so a session recognizes the shape before emitting it, not only after being denied. `anchors: root, row1`
- **Name the `$HOME` and `$VAR` traps in the same block.** These are the two nearest wrong answers once the heredoc route is closed; leaving them out would trade one denial round-trip for another. `anchors: row4, row5`
- **Drop the false command-substitution attribution; warn against `-m "$(cat …)"` on unscanned-content grounds instead.** Corrects a claim the source contradicts, and closes the one alternative idiom that fails *silently* rather than loudly. `anchors: row6, row7`

**Proposed replacement text** for `claude/.claude/skills/code-review/SKILL.md` line 408 (implementer may tighten wording under `/skill-review`, but each of the four named traps and the "gates read the file before git runs" rationale must survive):

> **Authoring the commit message.** A single-line message goes inline with `-m`. For a multi-line message, create the file with `mktemp "${TMPDIR:-/tmp}/commit-msg.XXXXXX"`, populate it with the **`Write` tool**, then pass that path to `git commit -F <path>` as literal text — a `$VAR` is opaque to the gates, which resolve the argument statically and fail closed on it.
>
> Never author the message with a shell heredoc, and never point `-F` at `-`, `/dev/stdin`, `/dev/fd/*`, or any other pseudo-file. Both the PII gate and the redaction gate read the `-F` file before git runs, and neither can read the stdin of a process that has not started — a pseudo-file source is denied outright rather than scanned. Do not substitute file contents into `-m` either (`-m "$(cat …)"`): the gates scan the literal command string, so the real message would reach the commit unscanned.
>
> Keep the file out of `$HOME` and out of any UUID-shaped or 32-plus-hex-character path — e.g. not the session scratchpad. The redaction gate scans the commit command string itself, and its home-rooted-path and long-hex-identifier detectors match on the `-F` argument.

**Dispatch split:** one `code-writer` dispatch, one file, no split — the edit is a single contiguous paragraph replacement.

4. **The recipe actually passes the gates it describes** — the point of the change is that the prescribed command is *not* denied, so exercise it once end to end in a scratch commit: `mktemp "${TMPDIR:-/tmp}/commit-msg.XXXXXX"`, `Write` a two-paragraph message to the returned path, then `git commit -F <that literal path>`. It must not be denied by `deny-pii-in-commits.sh` or `deny-private-project-refs.sh`.
5. **The four named traps still deny, with the messages the prose promises** — the existing hook tests already cover three of them, so re-running them (step 1 picks up the hooks domain only if hook files changed; run `.venv/bin/pytest claude/.claude/hooks/tests/test_deny_private_project_refs.py` directly if not) is sufficient evidence for: pseudo-file `-F -` denies (`test_deny_private_project_refs.py:1202`), a nonexistent/unexpanded path denies (`:1221`, which is the `$VAR` case's mechanism), and a quoted path is still extracted (`:2728`). The `$HOME`-rooted-path trap has no test asserting it fires via the *command string* on a git-commit call — spot-check it manually by attempting `git commit -F /Users/<name>/msg.txt` in the scratch repo and confirming the deny names the `home-rooted path` detector.
6. **Review gates** — `/skill-review` is hook-enforced for any `SKILL.md` change (`require-skill-review.sh`), and `/code-review` gates the commit. Run `/skill-review` on the diff itself: this edit is prose about how to construct a safe command, so it is exactly the class of change that can violate the rules it documents.
7. **Read the rewritten block cold** — the standalone test from CLAUDE.md's prose rules: a contributor who has never seen this issue or PR should be able to produce a compliant commit from the block alone, with no reference to a gate's source or a denial transcript.

## Out of scope

- **Any change to `deny-pii-in-commits.sh` or `deny-private-project-refs.sh`, including their denial messages.** The gates are correct; a denial message teaches only within the session that already paid for the round-trip, and the observed recurrence is *across* sessions.
- **A commit-message wrapper script, or a hook that rewrites `-F -`.** Both move `git commit` behind a boundary the Bash-tool hooks cannot inspect, disabling the PII and redaction scans. Named here rather than silently omitted because it is the tempting "just make the friction go away" answer.
- **`pr-description/SKILL.md`.** Structural-sibling audit outcome: the `gh pr create --body-file` arm faces the identical pseudo-file gate (`deny-escaped-backticks-in-pr-body.sh:81-99`, `deny-private-project-refs.sh:505-511`) but is *not* affected by the same bug shape — its recipe already supplies the complete file-creation path, which is precisely what `code-review` lacks. It is the exemplar, not a second defect. If `--body-file -` denials ever appear in an error-mode-analysis run, the same one-clause pseudo-file warning applies there.
- **`respond-pr/SKILL.md`.** Its `<<'RESPOND_PR_BODY_EOF'` heredoc feeds a repo script's own stdin; the script name carries no `--input`/`-F key=@` flag, so `deny-private-project-refs.sh`'s `gh api` pseudo-file checks (`:540`, `:563`) never engage. Different shape, not a sibling of this bug.
- **The `gh api --input` / `-f key=@PATH` arm generally.** No skill instructs a body-from-file form for `gh api`, so there is no guidance surface to fix and no observed denials.
- **New tests.** The behaviors the prose describes are already asserted by the hooks' own suites (Verification step 5); adding tests that assert skill *wording* would pin prose the next revision should be free to improve.
- **Why models prefer heredocs for multi-line text generally.** A real question, but a research one — this plan closes the one surface where that preference collides with a gate.

# Opus-as-main-session cost/review-rounds A/B analysis

## Context

The engineer has an informal practice of anchoring some Claude Code main sessions on Opus via an explicit `--model opus` override, leaving others on the account default (Sonnet). Determine, with measured evidence, whether that split has correlated with two outcomes: lower total dollar cost (main session plus every subagent it spawned), and fewer `/code-review`/`/plan-review` rounds. The corpus is machine-wide — every repo/project the engineer works in on this machine, not just `claude-config`.

Enough sessions have now accumulated under this informal split that a retrospective read might show something. The intended outcome is a rigorous, pre-registered-gate analysis **report** — delivered to the engineer directly, in-session, never committed to this repo or published anywhere — built entirely from this repo's own already-shipped `transcript-analysis.py` toolkit, with no new subcommand and no new ledger column. This design and its gates are adapted from a structural sibling, referred to throughout as **the sibling study**: `.claude/plans/opus-frontload-review-rounds.md` and its published write-up, `docs/case-studies/opus-frontload-review-rounds.md`, which ran the same gated-verdict methodology on a different treatment variable — whether front-loading Opus into code authoring reduces review rounds — scoped to this repo alone.

**Amendment (2026-09-08).** A prior run of this design hit a bias in admission rule 1 — a repo's main checkout and its own linked worktree counted as two distinct projects, systematically biasing `Proj == 1` admission downward — delivered an Inconclusive report, and was retracted (PR #929, which also fixed the bug). This amendment re-runs the corrected-classifier design and extends the corpus from one machine to two, pooling at the `(account, repo)` stratum. See the Approach section's "Amendment" subsection, the Assumption ledger's amendment rows, and the amended Critical files / Verification / Out of scope sections below. Every mechanism above this notice is unchanged and still applies; the amendment states only what is added or altered.

## Approach

Classify each **branch** in the machine-wide 30-day transcript corpus as Opus-anchored, Sonnet-anchored, or mixed, using the opus share of only its *earliest-touching session's own* main-thread turns — not the branch's aggregate turn counts from `buckets`, which merges every session that ever touched the branch into one row and so dilutes a deliberate session-1 anchor by however much default-Sonnet `/handoff` continuation work followed it. Then compare the two poles on total dollars for the *whole branch* (`cost --branches`, which prices subagent turns by default and folds in every continuation session) and on `/code-review` round counts (`review-trace --skill`) for the whole branch, within `(account, repo)` strata, against gates fixed in this file before the first scan. The mixed band is not noise to be smoothed — it is where harness plan-mode-forced Opus lands by construction, so excluding it is how this design separates deliberate `--model opus` anchoring from plan-mode forcing without needing a signal `message.model` cannot carry.

### Why a branch, why its first session, and why a share rather than a first turn

The repo's own canonical predicate for "Opus-anchored" is `plan-boundary`'s: a session whose **first main-thread turn** is Opus (`docs/transcript-analysis.md:1020`). That predicate is unusable as this study's classifier, for a reason specific to this question: under harness plan mode the first turns are Opus whether or not the engineer anchored anything, so the canonical predicate returns true for both mechanisms and cannot tell them apart. It stays in the design as a **feasibility and contamination instrument** (G0/G1 below), not as the classifier.

The discriminating signal within one session is the *trajectory*, not any single turn: deliberate `--model opus` anchoring produces a main thread that is Opus end to end, while plan-mode forcing produces an Opus prefix followed by Sonnet work after the boundary. So the classifier is a **share** — but a share of *which* session's turns is itself a decision, and the branch aggregate gets it wrong. The engineer's actual practice is Opus only for a branch's first session's main agent (`claude --model=opus`); every `/handoff`-resumed continuation on the same branch runs Sonnet by default. A branch's `buckets` row merges every contributing session's turns into one total (`transcript-analysis.py:276-285`), so a deliberately Opus-anchored first session on a branch that later grew several Sonnet-run continuation sessions dilutes toward the excluded mixed band exactly as often as it doesn't — the aggregate classifier would be measuring how many continuation sessions a branch happened to need, not whether it was anchored. The classifier is therefore the opus share of **only the branch's earliest-touching session's own main-thread turns**. Everything the branch aggregate is still good for — the primary dollar and round-count *outcomes* — stays at branch level, across every contributing session; only the *classification label* moves to session granularity.

`buckets`' own CLI output cannot supply that: it prints only the post-merge branch row, with no per-session breakdown and no ordering (`transcript-analysis.py:291-304`). Getting the earliest-touching session's own tally means reading what `buckets` computes internally and discards — for each session, a `file_branches` dict of per-branch family counts and a `ts_min`/`ts_max` (`transcript-analysis.py:261-285`), built before the merge into `branch_data` throws the per-session boundary away. `resolve_scan_roots`, `_resolve_project_scope`, `_branch_filter` (`transcript_analysis/scope.py`) and `_fam` (`transcript_analysis/render.py`) are plain functions with no argparse or CLI side effects, importable from a standalone script exactly as `cmd_buckets` itself imports and calls them (`transcript-analysis.py:39,142-160`) — this replicates `cmd_buckets`'s own per-session loop and keeps what that loop already computes before discarding it, rather than parsing anything differently. This is a **shipped-module import, not a new subcommand**: nothing in `transcript-analysis.py` changes, nothing new is registered in its CLI, and the resulting script is ephemeral — written and run once by the feasibility dispatch, never committed, deleted with the scratch directory (see Critical files and Dispatch split).

A branch is **admissible** when all of these hold:

1. It appears under exactly one declared root and shows `Proj == 1` in that root's `buckets` output. `buckets` keys its accumulator on the bare branch string, so a name occurring in two repos or two accounts merges into one row (`transcript-analysis.py:253-277`); `Proj` is the count of distinct contributing project dirs and is what makes that collision detectable rather than silent. This also makes "earliest-touching session" well-defined: once a branch name is confirmed unique to one root, every session that touches it lives in that same root's corpus, so comparing their `ts_min` values to find the earliest is a within-root comparison, never a cross-root one. A tie in `ts_min` at the transcript's timestamp resolution — a parent session and a subagent dispatch sharing a start time, for instance — breaks toward the lexicographically smaller session ID, a fixed rule with no dependency on scan order.
2. Its name is not `main`, `master`, `HEAD`, or empty — generic names pool unrelated work under one label.
3. The earliest-touching session's own main-thread turn total on that branch is ≥ 20. Floor derived, not borrowed: the classification margin below is 10 percentage points, so under 20 turns a single stray turn sits inside the margin and a mixed session is indistinguishable from a pure one. A branch's aggregate turn count is always ≥ its first session's own count, so a floor stated at first-session granularity admits no more branches than the same floor would at branch-aggregate granularity, and very likely fewer — G0 tests the resulting population rather than assuming it clears 20 per arm.
4. `haiku + other` ≤ 10% of that same earliest session's own main-thread turns — a first session mostly unclassified-family turns cannot be assigned to either arm.
5. The earliest-touching session's own turns fall inside the analysis window.

An admissible branch is **Opus-anchored** at `opus / total ≥ 0.90`, **Sonnet-anchored** at `≤ 0.10`, and **mixed → excluded and counted** in between — all three read off the earliest-touching session's own main-thread turns, never the branch aggregate.

`buckets` is the right instrument for this and `subagents` is not, despite `subagents` being the subcommand documented as splitting main from sidechain. `buckets` counts only `type == "assistant" and not isSidechain` (`transcript-analysis.py:272-274`). That makes it main-thread-only in fact, regardless of what its doc entry calls it ("assistant-turn counts"). It also prints raw branch names at any root count. `subagents` prints the same split but is in `_SUBCOMMANDS_WITH_OWN_CONFIG_DIR` (`scope.py:480-485`), which forecloses the narrowing top-level `--config-dir` and leaves its branch names redacted to run-local `account-K/branch-N` labels machine-wide. A redacted label cannot be fed back to `cost --branches`. This is the same redaction wall that blocked the sibling study's G2, met at a different subcommand.

**The classification thresholds are sensitivity-tested, not asserted.** The primary reading is 0.90/0.10; the same tables are recomputed at 0.80/0.20 and 0.95/0.05 and all three are reported. A direction that flips across the three is reported as threshold instability, which converts an arbitrary cut point from a hidden assumption into a measured quantity.

### Machine-wide collection: per-root loop, not the union

The declared-roots union is the wrong default here for a reason unrelated to redaction. Under the union, `buckets` pools same-named branches across accounts into one row, and `review-trace` gives no per-account attribution at all. Looping an explicit single top-level `--config-dir <root>` once per declared root collapses `roots` to exactly one per invocation, which both attributes every row to an account and removes cross-account name collisions. That loop works for `buckets`, `review-trace`, and `struggle` — all three funnel through `_resolve_scan_roots` and none of them redacts anything at any root count (`docs/transcript-analysis.md:47`).

It does **not** work for `cost`, `subagents`, `subagent-mix`, `plan-boundary`, or `pr-cost`: `main()` exits 2 on a top-level `--config-dir` for those five (`transcript-analysis.py:11854-11868`), and their own `--config-dir` is additive-only — `_resolve_cost_roots` always starts from the default config dir plus every declared root (`scope.py:488-492`). On this machine those five are permanently 6-root. The practical consequences are load-bearing and worth stating plainly. `cost --no-redact` exits 2 unconditionally here, so no per-session dollar figure carries a real session ID. `plan-boundary`'s output is aggregate-only anyway, so its multi-root scope costs nothing.

A per-account `--config-dir` loop is not an escape hatch around `subagent-mix`'s redaction — that subcommand refuses the flag unconditionally. The loop is available precisely where redaction was never the problem, and unavailable precisely where it was.

`cost --branches` is therefore run against the 6-root union, with a real branch name supplied as *input*. Admission rule 1 is what makes that safe: a name unique to one project dir across all six roots cannot silently pull a foreign account's spend into an arm total. That uniqueness is verified by an explicit cross-referencing step, not asserted from a single root's `Proj` field alone — the feasibility dispatch (Dispatch split item 1) compares the six per-root `buckets` branch-name sets against each other and drops any name occurring in more than one root's output before it is treated as admissible, regardless of what `Proj` reports for that one root.

### Outcomes and their instruments

**Primary — total dollars per branch.** `cost --branches <arm's branch list>`, once per arm per stratum. It prices sidechain turns by default and folds `worktree-agent-*` subagent spend back onto the dispatching session's branch (`docs/transcript-analysis.md:586,607`), so "main session plus every subagent it spawned" is what the figure already means, with nothing hand-summed. Capture `## Cost by thread` and `## Cost by model ID` from each run: the thread split answers whether the arms differ in delegated spend, and the model-ID split is an independent corroboration that the Opus arm really is Opus-dominated in dollars and not just in turn counts.

**A per-branch dollar figure is deliberately not collected.** `cost` reports totals for a branch set, and a per-branch value would need one full corpus rescan per branch — measured at ~18s for a redacted single-root `--since 30d` run against a smaller corpus (`docs/transcript-analysis.md:706`), against six roots and hundreds of branches. So the cost outcome is a ratio of aggregates and carries no within-stratum bootstrap; its stability check is cross-stratum consistency instead (G3). Stating this in advance is what stops a later session from quietly reporting a mean it could not compute.

**Primary — `/code-review` rounds per branch.** `review-trace --skill code-review`, looped per root, grouping `skill` events by each event's own resolved branch. Per-branch values come free here, so this outcome does carry the bootstrap. Its overcount bias is known and verified once (PR #613: 3 counted invocations against 2 commits and one `"lgtm"` review). The bias applies to both arms through the same instrument, so it moves the comparison only if it correlates with the arm — which is unmeasured, and named as a residual limit rather than argued away. `--skill plan-review` is collected on the same pass as a descriptive covariate.

**Secondary — correction-phrase density per branch.** `struggle` per root, summed across families rather than read by family: the per-family split is near-collinear with the arm by construction, but the per-branch total is a live in-session friction signal sharing no code path with either primary instrument. Reported, never gate-bearing.

**Negative control, with a value predicted before the scan.** Opus-5's base input rate is $5.00/MTok against Sonnet-5's $2.00/MTok, and every other class derives from that one base by the same multipliers (`pricing.py:50-54,150-162`), so a turn with an identical token profile prices at exactly **2.5×** on Opus. Because the classifier now reads off each admitted branch's earliest-touching session alone, the negative control is computed on that same population rather than on `cost --branches`' whole-branch aggregate: the ephemeral extraction script (Approach § above) also runs `_extract_rearm_session_turns` (`transcript-analysis.py:9982`, loaded via `importlib.util.spec_from_file_location` the same way the test suite already loads this hyphenated-name module) against each admitted branch's earliest session, resolves each turn's branch via `_session_branch_index`/`_attributed_branch` (`transcript_analysis/cost.py:40-94`), and sums `actual_dollars` over that session's own main-thread turns on that branch. Dividing that sum by the same session's own main-thread turn count — already computed by the classifier's `buckets`-mirroring pass — gives a real per-session dollars-per-turn figure for each admitted branch, averaged per arm. That ratio should come out near 2.5× between arms. Near 2.5× means the classifier is selecting what it claims to. A large deviation is a diagnostic, not automatically an error: it most likely means the arms differ in per-turn context depth, and it must be reported either way.

That same 2.5× is the frame for reading the headline. An Opus-anchored branch breaks even on cost if it consumes ≤40% of the tokens the Sonnet arm needed. So a *favorable* cost result has cleared both the price premium and the difficulty confound and is strong evidence; an *unfavorable* one is nearly uninformative, being what price alone predicts.

### Cross-repo pooling: checked, and the answer is stratify

Pooling turned out to be more defensible than expected on the cross-repo work-comparability axis, and still not defensible on another. The `/code-review` gate is **machine-level, not repo-level**: `require-code-review.sh` gates every `git commit` in every git repository, resolving the repo from the payload's own cwd, with no repo opt-in sentinel anywhere in its path (`require-code-review.sh:57-95,104-151`) — unlike worktree enforcement, which does have one. It is registered in `claude/.claude/settings.json:200`, which stows to `~/.claude/settings.json`, and every git-tracked entry under the stow packages resolves into the same shared checkout for all six accounts (`~/CLAUDE.local.md`, the engineer's own private machine-notes file). `require-plan-review.sh` is registered the same way (`:318,353`). So the round-count generating process is structurally uniform across every repo on this machine.

What is *not* uniform is what a round costs in a different codebase. Hence: strata are `(account, repo)`, compared within, never pooled raw across. G2 sets the admission bar for a stratum empirically rather than assuming the gate fires everywhere.

One consequence of gate uniformity worth carrying into the write-up: because the marker matches on a hash of the reviewed state, each new committed state needs its own review, so round counts and commit counts are mechanically coupled machine-wide. That is context for reading the sibling study's G1 pass, not a finding of this one.

### The ledger arm is dropped, and this is a deliberate departure

The sibling study's powered arm ran on the `pr-cost` ledger because a single row carried treatment, outcome, and covariates together, sidestepping every redaction-blocked join. That property does not transfer. This study's treatment is main-thread model anchoring, and **no ledger column separates main-thread Opus spend from subagent Opus spend** — `opus_dollars` / `opus_dollar_share_pct` is one number over both (`docs/pr-cost.md:25`, full column list `:9-33`). Worse, the validation that would license using it as a proxy is foreclosed: `head_branch` is written to the ledger already scrubbed to an opaque `account-K/branch-N`, with deliberately no `--no-redact` escape hatch (`docs/pr-cost.md:95-96`), so no row can be joined to the `buckets` ground truth that would test the proxy.

An unvalidatable proxy for the exact variable a study is about is worse than a smaller n. The ledger arm is excluded and recorded in Out of scope with this reason. The cost is that the study is confined to the ~30-day retention window; machine-wide across six accounts, that window is expected to carry more branches than the sibling's single-repo scan found (120 with ≥1 invocation), and G0 checks rather than assumes it.

### Pre-registered gates

**G0 — anchored-population feasibility.** Two readings, both required.

- `plan-boundary --since 30d` (machine-wide, aggregate-only) reports `Sessions scanned` and `Opus-anchored` under the repo's own canonical predicate. Because that predicate counts plan-mode-forced sessions too, its `Opus-anchored` count is an **upper bound** on deliberate anchoring — the right shape for a feasibility floor.
- The per-root `buckets`-plus-ephemeral-extraction-script pass yields ≥ 20 admissible Opus-anchored branches **and** ≥ 20 admissible Sonnet-anchored branches, admissibility now decided at each branch's earliest-touching session (Approach § rule 3) rather than the branch aggregate. The 20 floor is `plan-boundary`'s own documented 20-session floor, the same precedent the sibling study's G2 used.

Fail → **stop before the measurement dispatch runs.** Report the census, and raise to the engineer the one option that would resolve it, which only he can authorize because it spends his own future working time: a forward-looking pre-registered pilot in which he randomizes his own anchor choice over N sessions. Do not start that here.

**G1 — contamination bound and scope disclosure.** Not pass/fail; a mandatory disclosure with a pre-committed consequence. Report (a) `plan-boundary`'s ground-truth `Sessions with a real model change observed at boundary+1: X of Y` with its `cache_miss_reason` breakdown — a direct machine-wide count of the opusplan/plan-mode signature among Opus-anchored sessions — and (b) the count and share of admissible branches landing in the excluded mixed band. If the mixed band exceeds the two poles combined, the study's claim is **pre-committed to re-scope** from "Opus-anchored versus Sonnet-anchored sessions" to "the minority of branches carrying an unambiguous whole-branch anchor," and the report must say so in those words. Fixing that re-scoping in advance is cheaper than inventing a threshold whose only justification would be that it was crossed.

The engineer states his Opus-anchored sessions came from his own `--model opus` override. G1 does not test that statement and cannot contradict it — it bounds how much *other* Opus main-thread work is in the corpus alongside it. Note that G1(a) also fires on a deliberate mid-session `/model` switch, which for this design is fine: both mechanisms break a whole-session anchor, and both are excluded by the same rule.

**G2 — stratum admission.** An `(account, repo)` stratum enters the round-count arm only when ≥ 10 of its in-window branches carry ≥ 1 `/code-review` invocation, and it holds ≥ 10 admissible branches in each arm. The 10 floor is `reviewer-yield`'s own documented `insufficient` threshold — "`insufficient` in `Rate` means `Active` fell below 10" (`docs/transcript-analysis.md:268`). A stratum failing only the first leg is excluded from the round arm but stays in the cost arm, which does not depend on the gate firing. All strata failing → the round-count outcome is withdrawn and the verdict rests on cost alone.

**G3 — verdict rule, and its asymmetry.**

- **Adopt-candidate** requires, within an admissible stratum, the Opus arm to show the *lower* value, and: for rounds, the direction survives a 2,000-resample bootstrap in ≥ 95% of resamples (both figures from `plan-boundary`'s precedent, as the sibling used); for dollars, the direction holds in a majority of admissible strata with no admissible stratum contradicting it. Cross-stratum consistency is the cost arm's substitute for a bootstrap it structurally cannot run.
- **Inconclusive** if the direction is unstable, threshold-sensitive across the three cut points, or the strata are thin.
- **Reject is not reachable from this design.** The engineer chose Opus for work he judged harder, and Opus prices at 2.5×. "More expensive, more rounds" is what the assignment mechanism and the rate table jointly predict, so reading it as refutation would be reading the confound twice over. A reject verdict would need a randomized arm this study does not have.

### Corpus freeze

The sibling study measured same-day re-derivation drift on this corpus minutes apart (106 vs 107 zero-round PRs; 24 vs 26 censored branches). Two dispatches scanning independently would inherit that drift as an internal inconsistency between the gate evaluation and the measurement. So the feasibility dispatch redirects every scan's raw stdout to a scratch directory outside any git tree — created via `mktemp -d` with mode `0700`, never a predictable or reused path — and the measurement dispatch reads those frozen files instead of rescanning, given the directory's absolute path from the feasibility dispatch's own return (Dispatch split items 1–2). This also removes the cost of a second six-root pass.

### Alternatives considered and set aside

*A new `transcript-analysis.py` subcommand joining per-session anchor model, total dollars, and round count.* The heavier primitive, and set aside. `_extract_rearm_session_turns` already builds exactly this per session — ordered `main_thread_models`, per-turn dollars, `sidechain_dollars_total` — but only for `rearm-backtest` and `plan-boundary`, whose CLI output is aggregate-only by design. Two lighter primitives were checked before reaching for it:

- Exposing that existing internal structure as a shipped CLI subcommand or flag — rejected because doing so *is* the new-subcommand change, not an alternative to it, and it would ship a durable per-session identity-bearing report to every stow user for one personal retrospective.
- The `pr-cost` ledger — rejected for the two reasons in the dropped-arm section above.

What this study does instead is a third, lighter option distinct from both: an ephemeral, uncommitted script imports that same internal structure directly (`_extract_rearm_session_turns`, `resolve_scan_roots`, `_resolve_project_scope`, `_fam`, `_session_branch_index`/`_attributed_branch`) for this one retrospective's classifier and negative control, then is deleted with the scratch directory (Approach §, Dispatch split). That is not the CLI-subcommand option: nothing is exposed to any other stow user, nothing is registered in the CLI, and no durable per-session report ships. The shipped composition `buckets` + `cost --branches` + `review-trace` still covers every figure that reaches the *report*; the import only supplies the classifier's and negative control's session-level intermediate values, which never appear in the report body above the pseudonymized, branch-level tables Critical files already requires.

*Session as the unit of analysis, for the outcomes.* The natural unit for the *classifier*, since `--model opus` is a per-session choice — and now used for exactly that (Approach §). It stays unavailable as the unit for the *outcomes*: `cost --branches` and `review-trace` both report at branch granularity, and re-deriving a full session-level round-count or cross-session dollar allocation for every admitted branch would mean building the second joining instrument the bullet above already declines. So the branch remains the outcome unit, and the mixed-band exclusion still absorbs branches where sessions of different anchors overlapped; only the *label* a branch carries into that outcome is now a session-level fact.

*`--this-repo` scope, as the sibling used.* Set aside on the engineer's own scope answer, and independently: the sibling found only 4 Opus-attributed correction-signal hits in the whole of claude-config's history and stated directly that this repo's corpus does not contain enough Opus-authored main-thread work to compare against. Repeating that scan would re-derive a known negative.

*Stratifying on main-thread turn count as a difficulty proxy.* Set aside as endogenous — dollars scale with turns, so conditioning on turns partly conditions away the effect being measured. Turn count appears only as the negative control's denominator.

### Amendment: corrected classifier and cross-machine pooling

Every mechanism above carries over unchanged except where a numbered delta below says otherwise.

#### Delta 1 — what PR #929 fixed, and the residual it did not close

Admission rule 1's `Proj` test previously biased `Proj == 1` admission downward, because a repo's main checkout and its own linked worktree presented as two distinct project directories. `buckets` now collapses a linked worktree's project-dir slug into its main checkout's slug before counting `Proj`, so a branch worked in both shows `Proj == 1` — `_WORKTREE_SUFFIX_RE` strips a trailing `--claude-worktrees-<branch>` from the slug (`redaction.py:29,32-44`), a pure string operation that depends only on the worktree living at `<repo>/.claude/worktrees/<name>`, the convention this repo's own worktree enforcement creates, so it behaves identically on any machine regardless of local git state.

That fix does not make admission rule 1 unbiased. A session started in a repo *subdirectory* still gets its own project-dir slug that does not collapse into the main repo's slug, so it still counts as a second project for the same repo (`docs/transcript-analysis.md:77-79`). The residual pushes the same direction as the fixed bug — it drops branches out of admission — and is not closeable by prefix-matching slugs, because `-` is both the path separator and a literal character in real directory names, the same lossy-slug collision `scope.py:54-61` warns against. Disposition: measure it rather than assert it away. Each machine's feasibility phase reports its count of branches dropped by rule 1 with `Proj > 1`, and that count is a required Limits-section item. Admission rule 1 itself is otherwise unchanged, including its cross-root branch-name dedup step, which still runs within each machine's own declared-roots union before any cross-machine step.

#### Delta 2 — the cross-machine join key, and the failure it cannot self-detect

Strata are `(account, repo)` merged across machines, joined on `stratum_hash = HMAC-SHA256(key=window_start + "|" + window_end, msg=account_slug + "\n" + repo_label)[:12]`, computed independently on both machines and matched hash-to-hash, never inverted. The HMAC key is the pre-registered window's own start/end dates (Delta 4) — both machines already hold a checkout of this plan file (X0), so the key is identically available on both sides at zero added coordination cost, unlike a salt (which would need a synchronous exchange the design otherwise avoids). Keying on the window scopes this plan's own disclosed, public hashing algorithm to one run: a candidate-pair table built once from this file's committed spec could otherwise be replayed against every future run's payload; window-keying forces a fresh table per run instead. Two inputs to the hashed message, each pinned:

- `account_slug` comes from the account-slug column of the git-versioned account roster shared by both machines, so the same account yields the same string wherever both machines have pulled a reasonably current checkout of that roster.
- `repo_label` is `_project_family(_derive_proj_label(<session jsonl path>))` — the shipped functions, not a hand-rolled parser. `_derive_proj_label` (`redaction.py:21-23`) drops the slug's first two `-`-separated tokens, and the slug is the session cwd with `/` and `.` mapped to `-` (`scope.py:36-44`). The net effect: the repo label is the repo's path relative to `$HOME`, with `/` and `.` mapped to `-` — provided `$HOME` is exactly two path components deep, which holds for the conventional home-directory layout on both machines involved.

That derivation is the whole join's load-bearing premise, and it fails silently. If a repo sits at a different path relative to `$HOME` on the two machines, its two labels differ, its stratum hashes differ, and the stratum splits into two half-size strata — each then likely failing G2's ≥10 floor and yielding "thin strata → Inconclusive." That failure mode is indistinguishable from the study's own null result, which is precisely the shape of defect that produced the retraction this amendment exists to correct.

The branch-level fingerprint (below) cannot catch it — it also hashes `repo_label`, so a label mismatch makes branch fingerprints differ too, and the disjointness detector's pass condition ("no collision") is exactly what a broken join also produces. The detector only detects unexpected *overlap*; the dangerous new failure is expected overlap being *absent*. This is why X1 below adds a positive control for the join, not just a negative one.

Keep one branch-level fingerprint too — `HMAC-SHA256(key=window_start + "|" + window_end, msg=account_slug + "\n" + repo_label + "\n" + branch)[:12]`, keyed the same way as the stratum hash and for the same reason — used only as a disjointness/desync detector in the same role `_corpus_fingerprint` already plays (`redaction.py:166-174`), never as a label or a join key. Because a branch is never worked from two machines (the engineer's own stated invariant: a single PR is never split across machines), the two machines' admissible-branch lists are disjoint by construction, so a fingerprint appearing on both machines falsifies that premise for that branch — meaning it genuinely was worked from both, invalidating its earliest-touching-session classification (the true earliest session may be on the other machine). Disposition: drop that branch from both lists, count the collision, and escalate to the engineer rather than resolve it silently. This is distinct from admission rule 1's cross-account raw-branch-name collision check, which still applies unchanged within each machine first.

Bare branch names do not cross machines at all — because the lists are disjoint by construction, merging them is a concatenation, not a join, so no branch-level key is needed. Where a row must be referenceable in prose, it carries an opaque `machine-<M>/branch-<N>` label, the same `account-<K>/<kind>-<N>` shape `_assign_root_scoped_redact_label` already uses (`redaction.py:197-229`), with one namespace level added for machine. Machine labels are `machine-1`/`machine-2`, fixed by the engineer before the run.

**The hash is keyed by the run's own window, not by a shared secret, and the payload is pseudonymized rather than anonymized.** Both machines must compute an identical hash with no synchronous channel between them beyond the plan file itself, so a per-run *secret* salt would have to exist in both sessions' transcripts and would not be a secret — the window-key above is the strongest binding available without one. With both message inputs low-entropy, anyone already holding a candidate `(account_slug, repo_label)` pair, for the same pre-registered window this run used, can confirm its presence in the payload — and, having confirmed it, also reads off that engagement's **turn/cost/review-round profile**: its turn counts, dollars-per-turn, and review-round counts (Payload A's own fields), not merely its presence. Consequence, not just disclosure: the cross-machine payload gets the same handling and deletion discipline as the raw scratch data (Critical files, amended below), and this residual — presence plus turn/cost/review-round profile, scoped to one run's window — is what the report's Limits section states, not "presence" alone. 12 hex chars (48 bits) is enough — birthday-collision probability ≈4×10⁻¹⁰ at 500 items, and the stratum count is far below the branch count.

#### Delta 3 — three phases, two sync points, and no message-borne data

Data crosses machines as **files the engineer moves himself**, never as message content. `SendMessage` is acceptable only as a content-free status ping ("freeze done, file at `<path>`") — never as the transport for a payload, since every figure must be re-derivable from a re-readable frozen file at write time, a chat message body is an undisclosed extra transcript hop on both machines, and pooled G0 needs both censuses evaluated together before either measurement runs, which a fire-and-forget message cannot synchronously gate.

1. **Phase 1 — feasibility and freeze, run independently on each machine.** Each machine runs the original design's Dispatch split item 1 in full against its own declared-roots union, then emits **payload A** (schema below). Sync point 1: both payloads reach the pooling machine (the machine holding this plan's implementation branch and worktree).
2. **Phase 2 — pooling and gate evaluation, on the pooling machine only.** Merges the two payload A files, runs X1's join controls (below), drops fingerprint collisions, and evaluates pooled G0, G1, and G2. On a pass, emits a small **go-list** per machine: a go/no-go flag plus the branch fingerprints to drop. Sync point 2: the go-list reaches the other machine.
3. **Phase 3 — measurement, run independently on each machine, only on a pooled G0 pass.** Each machine reads its own frozen files, builds arms at all three threshold pairs, runs `cost --branches` per arm per stratum per threshold against its own 6-root union, and emits **payload B**. Sync point 2's return leg carries payload B to the pooling machine.
4. **Write-up — on the pooling machine, not delegated**, for the same reason the original gave.

Measurement cannot be centralized: `cost --branches` and `review-trace` need each machine's own local corpus, and the frozen scan files deliberately do not cross machines. Collapsing this to one round trip by having both machines measure unconditionally in phase 1 was considered and rejected — the original design's rule that the measurement dispatch "does not run at all if G0 fails" is a disclosure control, not a compute optimization.

#### Delta 4 — window alignment, which the cost instrument cannot fully honor

The two machines freeze at different wall-clock times, so a relative window would cover two different absolute windows. The analysis window is therefore pre-registered as absolute `YYYY-MM-DD` start and end dates, fixed in this file before either machine's first scan: **2026-08-09 through 2026-09-08**, chosen because waiting does not grow the corpus (retention is a rolling ~30-day window, not a cumulative one) and because both machines already show comparable, non-sparse Opus-anchored activity in this window (this machine alone: 32 Opus-anchored sessions of 615 scanned in the trailing 30 days, per `plan-boundary --since 30d` run at authoring time). If execution has not started within roughly two days of this date, re-confirm and update this window before either machine's first scan rather than scanning against a stale pre-registration.

The instruments split on whether they can express the window: `review-trace` takes absolute `--since DATE`/`--until DATE` (`docs/transcript-analysis.md:415-416`), so the round-count outcome is exactly aligned across machines. `buckets` takes no window flag at all, so the window is enforced post-hoc from its per-branch `Date range` column, unchanged from the original design. `cost` takes only relative `--since Nd`, so each machine sets `N` so that its own run time minus `N` days lands on 2026-08-09, aligning the window's *start*; the window's *end* is each machine's run time and cannot be bounded, since `cost` has no `--until`. Residual, disclosed rather than engineered away: the later-freezing machine's branches carry up to one extra day of post-window tail spend. Both freezes must fall within one calendar day of each other. The effect is non-differential by arm — it applies equally to both arms on the same machine — so it lands only on the cross-machine dollar *level*, not on the within-stratum arm comparison the verdict rests on.

#### Delta 5 — the pooled report cannot use account ordinals

`account-K` ordinals come from `scope._redaction_ordinals`, which is per-run and resolved-path-sorted, and labels built from *different* declared-roots files are explicitly not comparable ("a changed root set can renumber every ordinal", `redaction.py:128-133`; `docs/transcript-analysis.md:45`). The two machines regenerate their declared-roots files independently from their own local account rosters, so `account-3` on machine 1 and `account-3` on machine 2 may be different accounts. Fix: pooled strata carry their own report labels — `stratum-1`, `stratum-2`, … assigned in sorted-stratum-hash order at the pooling machine. Per-machine `account-K` ordinals stay local to each machine's own session and never appear in the pooled report body. Pooled labels are comparable only within this run.

#### Delta 6 — the cross-machine payload schemas

New, smaller schemas than the original design's 7-field-or-`SKIP` stdout schema, which continues to govern each machine's local extraction script unchanged. Tab-separated, one record per line, no header. Full field lists and Deny/Allow rules are in the amended Critical files section below.

#### Delta 7 — new pre-registered gates

Named `X0`–`X2` so they cannot be confused with the original's `G0`–`G3`, which are unchanged and still apply to the pooled population.

**X0 — toolkit and window parity.** Evaluated on each machine before any scan runs. Both machines must execute a `transcript-analysis.py` whose behavior includes the collapse fix from PR #929 — resolve the stowed `~/.claude/scripts/transcript-analysis.py` symlink to its real path, take that file's git root, and confirm `git merge-base --is-ancestor d1ea79a6 HEAD` there. Each machine records that checkout's HEAD SHA in payload C. Both machines must also hold a checkout containing this plan file, and must use the same pre-registered absolute window (Delta 4). **Also evaluated here (Delta 8): both machines' `.round-consult-round2-pilot` sentinel presence/absence states must match at freeze time** — a desync would silently reintroduce the asymmetric machine × arm confound X2 exists to catch. Fail any of the above → stop; run no scans on either machine.

**X1 — join-key control.** Evaluated at the pooling step, before pooled G0. Three readings, all required:

- A *positive control* — for each account slug present in both machines' payloads, at least one stratum hash must appear on both sides (`claude-config` itself, the one label the toolkit's own redact map passes through unredacted, is the natural canary).
- An *overlap census* — the count of stratum hashes on both machines, and on each alone.
- The *fingerprint-collision count*, with every colliding branch dropped from both lists and escalated.

Fail (an account present on both machines with zero shared strata) → do not proceed to pooled G0 on the affected accounts; pre-committed remedy is an engineer-supplied stratum alias table, applied before hashing, then re-checked.

**X2 — machine/arm confound disclosure.** Evaluated after G2, before G3's verdict. Report a machine × arm contingency table per admitted stratum. A stratum whose arms are machine-segregated — one arm drawn wholly or near-wholly from one machine — has its comparison reported as between-machine as much as between-arm, in those words, and cannot support an adopt-candidate reading on its own.

Pooling is decided **per stratum**. A stratum present on only one machine stays in the study as a single-machine stratum, evaluated against G2's floors on that machine's counts alone. When no stratum is admissible on both machines, the report says so explicitly and presents two independent single-machine runs, rather than presenting a pooled n it did not obtain.

#### Delta 8 — the round2-consult-trigger pilot's brief regime-change tail (disclosed, not gated)

An unrelated, concurrent pilot (PR #934) changes `/code-review` round-count generation by firing the `plan-architect MODE=consult` gate at round 2 instead of round 3, via a machine-scoped, opt-in sentinel (`<config-dir>/.round-consult-round2-pilot`; stop condition 20 firings or 4 calendar weeks from activation). This threatens the round-count outcome specifically if it runs asymmetrically across machines — X0 and X2 above exist partly for that reason. Verified at authoring time (2026-09-08): the sentinel is active on **both** machines, activated within the same few hours, with **zero firings recorded on either machine** before this plan's pre-registered freeze window closes. Because it is symmetric across machines, it does not reintroduce the machine × arm confound X2 targets; the residual is a brief regime-change tail — any code-review round counted after each machine's own activation timestamp reflects the round2 regime rather than the round3 regime the rest of the window reflects, on both arms equally. Because retention is a rolling window, this tail can only grow the longer the freeze is delayed, so freezing promptly minimizes it; delaying until the pilot concludes would instead maximize it, since the entire trailing window would then fall inside the pilot's active period. Disposition: report each machine's own sentinel activation timestamp and firing count as of freeze time in the Limits section; if either machine's firing count is material or the sentinel states have desynced by freeze time, that machine's round-count outcome carries a stated regime-mix caveat rather than being silently treated as clean.

#### Alternatives considered and set aside (amendment)

*A message-borne payload via `SendMessage`.* Set aside — see Delta 3.

*Splitting strata by machine — `(machine, account, repo)`.* Set aside on the engineer's stated invariant that a single PR is never split across machines, which makes the two branch sets disjoint and machine a nuisance dimension (X2) rather than a stratifying one.

*A weighted meta-analysis of independently-computed per-machine aggregates.* Set aside; branch-level lists merge by concatenation, so the combined bootstrap runs over the full merged branch set exactly as the original single-machine mechanics do.

*Resolving each project dir back to a checkout and hashing its git remote URL, instead of the path-relative-to-`$HOME` label.* Rejected as the heavier option: it shells out to git per project dir, fails for local-only repos, breaks when a checkout is deleted while its transcript survives, and would put private remote URLs into the hashing path.

*Syncing each machine's frozen scan files rather than a derived payload.* Set aside — it would move raw branch names and config-dir paths across machines, a disclosure regression against the minimization the payload schema exists to enforce. Consequence, accepted: the pooling session takes machine 2's per-branch rows on the payload's schema check plus machine 2's own local re-derivation attestation, not on its own read of machine 2's raw scan (Verification, amended).

The script's stdout and stderr are together redirected (`> ... 2>&1`) to a dedicated file inside the scratch directory, per root (Corpus freeze) — never left on the Bash tool's own captured output as a side effect of the run itself, regardless of content. Item 1 does read that frozen file back afterward, deliberately, to build the census (Report disclosure discipline item 4, below) — the redirection prevents incidental capture during execution, not the later, deliberate read. That redirection is still the containment layer for the run itself; the script's only valid print path within that redirected stream is still one schema-validated line per branch — no other `print` call exists anywhere in it — because `_extract_rearm_session_turns`' `"deduped"` return value, held in memory for all six declared roots (five client accounts), is the full record list, complete `message.content`, not only the fields this study needs. That validating function's only valid output is one tab-separated line per surviving branch, processed in the same sorted-by-branch-name order `buckets` itself enumerates them in, in this fixed 7-field schema:

- Field 1: a bare branch name string.
- Fields 2–5: four non-negative integers (opus/sonnet/haiku/other turn counts).
- Field 6: one float (dollars-per-turn).
- Field 7: one ISO-8601 timestamp (`ts_min`).

Never a `deduped` value, never a raw record, and never an unguarded exception traceback. The exception boundary covers the script's entire per-branch computation, not record parsing alone, since branch attribution (`_session_branch_index`/`_attributed_branch`), earliest-session selection, and the dollars-per-turn division can each raise with a record in scope. Any failure anywhere in that computation emits the fixed line `SKIP` in that branch's own position, never a traceback or a branch identifier — emitting `SKIP` in place, rather than omitting the line, is what lets Verification item 5 tell a designed skip from a silently dropped branch. A SKIP'd branch is excluded from G0, G1, and G2 entirely. It is also dropped from the admissible-branch list before item 2 consumes it, since none of those figures can be computed without the per-branch classification the failure prevented. Admissibility (Approach § conditions 1–5) is itself only decidable once that classification succeeds — conditions 3–5 read the earliest session's own turn counts and window, which a SKIP'd branch's failed computation never produced. A SKIP'd branch is therefore not counted as inadmissible on the data; its true admissibility is simply unknown. That is why its incidence is a disclosed quantity (Verification item 4) rather than a silent exclusion. This document uses "admitted" and "admissible" interchangeably for the same population; "surviving" names the broader, pre-admissibility population the extraction script actually emits a line for (Dispatch split; Verification item 5's Allow-check).

The script is also developed and validated against synthetic fixture records, before it is ever run against a real transcript file, so no draft-stage exploratory output touches real per-session data before the final version exists. Each fixture is checked against an independently-computed expected value:

- A single-session branch and a multi-session branch (to exercise earliest-session selection), each checked against its expected opus share and dollars-per-turn.
- Two sessions on one branch sharing an identical `ts_min` (to exercise the tie-break rule above), checked against the independently-known expected winner.
- A branch on each side of the turn floor — 19 turns excluded, 20 admitted — checked against the admissibility decision itself, not only the counted turns.
- A record shaped to trigger the `SKIP` path, checked only for emitting the literal token `SKIP` in that branch's position, since no share or ratio value exists to compute for it.

## Out of scope

- **The `pr-cost` ledger arm.** Excluded, not deferred, for two independent reasons: no column separates main-thread from subagent Opus spend, so the only in-row treatment signal is contaminated by the `plan-architect` dispatch that fires on every `/plan-it` run; and `head_branch` is stored already-scrubbed with no escape hatch, so the branch join that would validate that proxy against `buckets` ground truth does not exist. The sibling study's ledger frame worked because `plan_file_added` was a clean in-row indicator; this study has no equivalent. The cost is the ~30-day horizon, stated as a limit.
- **`pr-cost --record` backfill on any account.** Read-only ledger use is not needed at all once the arm is dropped; recording would be a durable out-of-repo write across up to six accounts, each behind its own consent sentinel, to feed an arm this plan does not run.
- **Any change to `transcript-analysis.py`** — a new joining subcommand, a per-session anchor report, a new `pr-cost` column, or a redaction escape hatch on `subagents`/`subagent-mix`. If a gate fails for want of an instrument, that gap is reported as a named finding, not built here. It would also ship a durable change to every stow user for one personal retrospective.
- **A forward-looking randomized pilot.** Not designed here. If G0 fails it is raised to the engineer at that point as the one remaining option, because it spends his own future working time and only he can authorize that. Do not start it inside this plan on a G0 failure.
- **Any routing, `model:` pin, or configuration change**, whichever way the data falls. This plan ends at the report; a change ships as its own scoped `/plan-it` run.
- **Committing or publishing the report**, in this repo or anywhere else — including as a `docs/case-studies/` entry, a `docs/cost-levers-considered.md` row, or a GitHub issue. The corpus spans five client accounts, so the machine-wide figures are not this public repo's own history the way the sibling study's `--this-repo` figures were.
- **`gh` enrichment for non-`claude-config` repos** — PR size, commit counts, review comments. Cross-account `gh` credential routing needs `direnv exec` per directory and the repos may not be cloned at reachable paths; the study therefore carries no exogenous work-size covariate outside the local corpus, which is a stated limit rather than a gap to fill.
- **Re-litigating the sibling study's inconclusive verdict**, its blocked G2, or its follow-up round-3-consult recommendation. This study asks a different question with a different treatment variable.
- **`subagent-mix`'s model-mix table.** It is the natural home for a declared-versus-observed pin comparison and it is unusable machine-wide: it refuses the narrowing top-level `--config-dir` and redacts `subagent_type` as well as branch names above one root — the documented wall that blocked the sibling's G2, unchanged.
- **A within-session analysis of when the anchor was chosen or switched.** `plan-boundary`'s boundary+1 ground truth is used only as a contamination count; re-pricing arms, plan-boundary switching, and mid-session handoff economics are that subcommand's own settled question.

**Amendment — additional items excluded by the cross-machine extension:**

- **Re-deriving or republishing the retracted run's figures.** They were produced under the pre-fix, biased admission-rule-1 classifier (Delta 1), so a side-by-side invites a comparison that is not meaningful. If the retracted run's admission census is available to the write-up session without a new scan, its delta against this run's may be reported as a one-line disclosure; chasing it otherwise is not in scope.
- **Closing the subdirectory-session arm of the `Proj` bias** (Delta 1). Not fixable here without prefix-matching project-dir slugs, which the lossy slug grammar makes unsafe. Measured and disclosed; a real fix belongs in `transcript-analysis.py` under its own scoped plan.
- **Any general cross-machine transcript sync, replication, or shared-corpus mechanism.** None exists in this repo today, and this amendment deliberately builds none: the cross-machine payload is a hand-moved, single-purpose, deleted-on-delivery file, not a transport. `cost-ledger`'s and `pr-cost`'s `--machine-label` flags are cited as a naming precedent only — neither provides a pooling mechanism, and both document having no built-in cross-machine replication of their own.
- **Sending any payload, branch list, or figure through `SendMessage` or any chat channel.** Cross-machine transfer is file-borne; messaging is limited to a content-free status ping (Delta 3).
- **Mechanically enforcing or auto-expiring the round2-consult-trigger pilot's sentinel, or otherwise modifying that pilot.** Delta 8 only reads and discloses its state; changing its behavior is that pilot's own plan's concern (PR #934), not this one's.

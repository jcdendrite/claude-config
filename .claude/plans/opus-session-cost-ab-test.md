# Opus-as-main-session cost/review-rounds A/B analysis

## Context

The engineer has an informal practice of anchoring some Claude Code main sessions on Opus via an explicit `--model opus` override, leaving others on the account default (Sonnet). Determine, with measured evidence, whether that split has correlated with two outcomes: lower total dollar cost (main session plus every subagent it spawned), and fewer `/code-review`/`/plan-review` rounds. The corpus is machine-wide — every repo/project the engineer works in on this machine, not just `claude-config`.

Enough sessions have now accumulated under this informal split that a retrospective read might show something. The intended outcome is a rigorous, pre-registered-gate analysis **report** — delivered to the engineer directly, in-session, never committed to this repo or published anywhere — built entirely from this repo's own already-shipped `transcript-analysis.py` toolkit, with no new subcommand and no new ledger column. This design and its gates are adapted from a structural sibling, referred to throughout as **the sibling study**: `.claude/plans/opus-frontload-review-rounds.md` and its published write-up, `docs/case-studies/opus-frontload-review-rounds.md`, which ran the same gated-verdict methodology on a different treatment variable — whether front-loading Opus into code authoring reduces review rounds — scoped to this repo alone.

## Approach

Classify each **branch** in the machine-wide 30-day transcript corpus as Opus-anchored, Sonnet-anchored, or mixed, using the opus share of only its *earliest-touching session's own* main-thread turns — not the branch's aggregate turn counts from `buckets`, which merges every session that ever touched the branch into one row and so dilutes a deliberate session-1 anchor by however much default-Sonnet `/handoff` continuation work followed it. Then compare the two poles on total dollars for the *whole branch* (`cost --branches`, which prices subagent turns by default and folds in every continuation session) and on `/code-review` round counts (`review-trace --skill`) for the whole branch, within `(account, repo)` strata, against gates fixed in this file before the first scan. The mixed band is not noise to be smoothed — it is where harness plan-mode-forced Opus lands by construction, so excluding it is how this design separates deliberate `--model opus` anchoring from plan-mode forcing without needing a signal `message.model` cannot carry.

### Why a branch, why its first session, and why a share rather than a first turn

The repo's own canonical predicate for "Opus-anchored" is `plan-boundary`'s: a session whose **first main-thread turn** is Opus (`docs/transcript-analysis.md:1020`). That predicate is unusable as this study's classifier, for a reason specific to this question: under harness plan mode the first turns are Opus whether or not the engineer anchored anything, so the canonical predicate returns true for both mechanisms and cannot tell them apart. It stays in the design as a **feasibility and contamination instrument** (G0/G1 below), not as the classifier.

The discriminating signal within one session is the *trajectory*, not any single turn: deliberate `--model opus` anchoring produces a main thread that is Opus end to end, while plan-mode forcing produces an Opus prefix followed by Sonnet work after the boundary. So the classifier is a **share** — but a share of *which* session's turns is itself a decision, and the branch aggregate gets it wrong. The engineer's actual practice is Opus only for a branch's first session's main agent (`claude --model=opus`); every `/handoff`-resumed continuation on the same branch runs Sonnet by default. A branch's `buckets` row merges every contributing session's turns into one total (`transcript-analysis.py:276-285`), so a deliberately Opus-anchored first session on a branch that later grew several Sonnet-run continuation sessions dilutes toward the excluded mixed band exactly as often as it doesn't — the aggregate classifier would be measuring how many continuation sessions a branch happened to need, not whether it was anchored. The classifier is therefore the opus share of **only the branch's earliest-touching session's own main-thread turns**. Everything the branch aggregate is still good for — the primary dollar and round-count *outcomes* — stays at branch level, across every contributing session; only the *classification label* moves to session granularity.

`buckets`' own CLI output cannot supply that: it prints only the post-merge branch row, with no per-session breakdown and no ordering (`transcript-analysis.py:291-304`). Getting the earliest-touching session's own tally means reading what `buckets` computes internally and discards — for each session, a `file_branches` dict of per-branch family counts and a `ts_min`/`ts_max` (`transcript-analysis.py:261-285`), built before the merge into `branch_data` throws the per-session boundary away. `resolve_scan_roots`, `_resolve_project_scope`, `_branch_filter` (`transcript_analysis/scope.py`) and `_fam` (`transcript_analysis/render.py`) are plain functions with no argparse or CLI side effects, importable from a standalone script exactly as `cmd_buckets` itself imports and calls them (`transcript-analysis.py:39,142-160`) — this replicates `cmd_buckets`'s own per-session loop and keeps what that loop already computes before discarding it, rather than parsing anything differently. This is a **shipped-module import, not a new subcommand**: nothing in `transcript-analysis.py` changes, nothing new is registered in its CLI, and the resulting script is ephemeral — written and run once by the feasibility dispatch, never committed, deleted with the scratch directory (see Critical files and Dispatch split).

A branch is **admissible** when all of these hold:

1. It appears under exactly one declared root and shows `Proj == 1` in that root's `buckets` output. `buckets` keys its accumulator on the bare branch string, so a name occurring in two repos or two accounts merges into one row (`transcript-analysis.py:253-277`); `Proj` is the count of distinct contributing project dirs and is what makes that collision detectable rather than silent. This also makes "earliest-touching session" well-defined: once a branch name is confirmed unique to one root, every session that touches it lives in that same root's corpus, so comparing their `ts_min` values to find the earliest is a within-root comparison, never a cross-root one.
2. Its name is not `main`, `master`, `HEAD`, or empty — generic names pool unrelated work under one label.
3. The earliest-touching session's own main-thread turn total on that branch is ≥ 20. Floor derived, not borrowed: the classification margin below is 10 percentage points, so under 20 turns a single stray turn sits inside the margin and a mixed session is indistinguishable from a pure one. A branch's aggregate turn count is always ≥ its first session's own count, so a floor stated at first-session granularity admits no more branches than the same floor would at branch-aggregate granularity, and very likely fewer — G0 tests the resulting population rather than assuming it clears 20 per arm.
4. `haiku + other` ≤ 10% of that same earliest session's own main-thread turns — a first session mostly unclassified-family turns cannot be assigned to either arm.
5. The earliest-touching session's own turns fall inside the analysis window.

An admissible branch is **Opus-anchored** at `opus / total ≥ 0.90`, **Sonnet-anchored** at `≤ 0.10`, and **mixed → excluded and counted** in between — all three read off the earliest-touching session's own main-thread turns, never the branch aggregate.

`buckets` is the right instrument for this and `subagents` is not, despite `subagents` being the subcommand documented as splitting main from sidechain. `buckets` counts only `type == "assistant" and not isSidechain` (`transcript-analysis.py:272-274`). That makes it main-thread-only in fact, regardless of what its doc entry calls it ("assistant-turn counts"). It also prints raw branch names at any root count. `subagents` prints the same split but is in `_SUBCOMMANDS_WITH_OWN_CONFIG_DIR` (`scope.py:480-485`), which forecloses the narrowing top-level `--config-dir` and leaves its branch names redacted to run-local `account-K/branch-N` labels machine-wide. A redacted label cannot be fed back to `cost --branches`. This is the same redaction wall that blocked the sibling study's G2, met at a different subcommand.

**The classification thresholds are sensitivity-tested, not asserted.** The primary reading is 0.90/0.10; the same tables are recomputed at 0.80/0.20 and 0.95/0.05 and all three are reported. A direction that flips across the three is reported as threshold instability, which converts an arbitrary cut point from a hidden assumption into a measured quantity.

### Machine-wide collection: per-root loop, not the union

The declared-roots union is the wrong default here for a reason unrelated to redaction. Under the union, `buckets` pools same-named branches across accounts into one row, and `review-trace` gives no per-account attribution at all. Looping an explicit single top-level `--config-dir <root>` once per declared root collapses `roots` to exactly one per invocation, which both attributes every row to an account and removes cross-account name collisions. That loop works for `buckets`, `review-trace`, and `struggle` — all three funnel through `_resolve_scan_roots` and none of them redacts anything at any root count (`docs/transcript-analysis.md:47`).

It does **not** work for `cost`, `subagents`, `subagent-mix`, `plan-boundary`, or `pr-cost`: `main()` exits 2 on a top-level `--config-dir` for those five (`transcript-analysis.py:11854-11868`), and their own `--config-dir` is additive-only — `_resolve_cost_roots` always starts from the default config dir plus every declared root (`scope.py:488-492`). On this machine those five are permanently 6-root. The practical consequences are load-bearing and worth stating plainly. `cost --no-redact` exits 2 unconditionally here, so no per-session dollar figure carries a real session ID. `plan-boundary`'s output is aggregate-only anyway, so its multi-root scope costs nothing.

A per-account `--config-dir` loop is not an escape hatch around `subagent-mix`'s redaction — that subcommand refuses the flag unconditionally. The loop is available precisely where redaction was never the problem, and unavailable precisely where it was.

`cost --branches` is therefore run against the 6-root union, with a real branch name supplied as *input*. Admission rule 1 is what makes that safe: a name unique to one project dir across all six roots cannot silently pull a foreign account's spend into an arm total. That uniqueness is verified by an explicit cross-referencing step, not asserted from a single root's `Proj` field alone — the feasibility dispatch (Dispatch split item 1) compares the six per-root `buckets` branch-name sets against each other and drops any name occurring in more than one root's output before it is treated as admissible, regardless of what `Proj` reports for that one root.

### Outcomes and their instruments

**Primary — total dollars per branch.** `cost --branches <arm's branch list>`, once per arm per stratum. It prices sidechain turns by default and folds `worktree-agent-*` subagent spend back onto the dispatching session's branch (`docs/transcript-analysis.md:586,607`), so "main session plus every subagent it spawned" is what the figure already means, with nothing hand-summed. Capture `## Cost by thread` and `## Cost by model ID` from each run: the thread split answers whether the arms differ in delegated spend, and the model-ID split is an independent corroboration that the Opus arm really is Opus-dominated in dollars and not just in turn counts.

**A per-branch dollar figure is deliberately not collected.** `cost` reports totals for a branch set, and a per-branch value would need one full corpus rescan per branch — measured at ~18s for a redacted single-root `--since 30d` run against a smaller corpus (`docs/transcript-analysis.md:706`), against six roots and hundreds of branches. So the cost outcome is a ratio of aggregates and carries no within-stratum bootstrap; its stability check is cross-stratum consistency instead (G3). Stating this in advance is what stops a later session from quietly reporting a mean it could not compute.

**Primary — `/code-review` rounds per branch.** `review-trace --skill code-review`, looped per root, grouping `skill` events by each event's own resolved branch. Per-branch values come free here, so this outcome does carry the bootstrap. Its overcount bias is known and verified once (PR #613: 3 counted invocations against 2 commits and one `"lgtm"` review). The bias applies to both arms through the same instrument, so it moves the comparison only if it correlates with the arm — which is unmeasured, and named as a residual limit rather than argued away. `--skill plan-review` is collected on the same pass as a descriptive covariate.

**Secondary — correction-phrase density per branch.** `struggle` per root, summed across families rather than read by family: the per-family split is near-collinear with the arm by construction, but the per-branch total is a live in-session friction signal sharing no code path with either primary instrument. Reported, never gate-bearing.

**Negative control, with a value predicted before the scan.** Opus-5's base input rate is $5.00/MTok against Sonnet-5's $2.00/MTok, and every other class derives from that one base by the same multipliers (`pricing.py:50-54,150-162`), so a turn with an identical token profile prices at exactly **2.5×** on Opus. Because the classifier now reads off each admitted branch's earliest-touching session alone, the negative control is computed on that same population rather than on `cost --branches`' whole-branch aggregate: the ephemeral extraction script (Approach § above) also runs `_extract_rearm_session_turns` (`transcript-analysis.py:9982`, loaded via `importlib.util.spec_from_file_location` the same way the test suite already loads this hyphenated-name module) against each admitted branch's earliest session, resolves each turn's branch via `_session_branch_index`/`_attributed_branch` (`transcript_analysis/cost.py:40-94`), and sums `actual_dollars` over that session's own main-thread turns on that branch. Dividing that sum by the same session's own main-thread turn count — already computed by the classifier's `buckets`-mirroring pass — gives a real per-session dollars-per-turn figure for each admitted branch, averaged per arm. That ratio should come out near 2.5× between arms. Near 2.5× means the classifier is selecting what it claims to. A large deviation is a diagnostic, not automatically an error: it most likely means the arms differ in per-turn context depth, and it must be reported either way.

That same 2.5× is the frame for reading the headline. An Opus-anchored branch breaks even on cost if it consumes ≤40% of the tokens the Sonnet arm needed. So a *favorable* cost result has cleared both the price premium and the difficulty confound and is strong evidence; an *unfavorable* one is nearly uninformative, being what price alone predicts.

### Cross-repo pooling: checked, and the answer is stratify

Pooling turned out to be more defensible than expected on the cross-repo work-comparability axis, and still not defensible on another. The `/code-review` gate is **machine-level, not repo-level**: `require-code-review.sh` gates every `git commit` in every git repository, resolving the repo from the payload's own cwd, with no repo opt-in sentinel anywhere in its path (`require-code-review.sh:57-95,104-151`) — unlike worktree enforcement, which does have one. It is registered in `claude/.claude/settings.json:200`, which stows to `~/.claude/settings.json`, and every git-tracked entry under the stow packages resolves into the same shared checkout for all six accounts (`~/CLAUDE.local.md`, the engineer's own private machine-notes file). `require-plan-review.sh` is registered the same way (`:318,353`). So the round-count generating process is structurally uniform across every repo on this machine.

What is *not* uniform is what a round costs in a different codebase. Hence: strata are `(account, repo)`, compared within, never pooled raw across. G2 sets the admission bar for a stratum empirically rather than assuming the gate fires everywhere.

One consequence of gate uniformity worth carrying into the write-up: because the marker matches on a hash of the reviewed state, each new committed state needs its own review, so round counts and commit counts are mechanically coupled machine-wide. That is context for reading the sibling study's G1 pass, not a finding of this one.

### The ledger arm is dropped, and this is a deliberate departure

The sibling study's powered arm ran on the `pr-cost` ledger because a single row carried treatment, outcome, and covariates together, sidestepping every redaction-blocked join. That property does not transfer. This study's treatment is main-thread model anchoring, and **no ledger column separates main-thread Opus spend from subagent Opus spend** — `opus_dollars` / `opus_dollar_share_pct` is one number over both (`docs/pr-cost.md:25`, full column list `:9-33`). Worse, the validation that would license using it as a proxy is foreclosed: `head_branch` is written to the ledger already scrubbed to an opaque `account-K/branch-N`, with deliberately no `--no-redact` escape hatch (`docs/pr-cost.md:95-96`), so no row can be joined to the `buckets` ground truth that would test the proxy.

An unvalidatable proxy for the exact variable a study is about is worse than a smaller n. The ledger arm is excluded and recorded in Out of scope with this reason. The cost is that the study is confined to the ~30-day retention window; machine-wide across six accounts, that window is expected to carry more branches than the sibling's single-repo scan found (120 with ≥1 invocation), and G0 checks rather than assumes it.

### Pre-registered gates

**G0 — anchored-population feasibility.** Two readings, both required.

- `plan-boundary --since 30d` (machine-wide, aggregate-only) reports `Sessions scanned` and `Opus-anchored` under the repo's own canonical predicate. Because that predicate counts plan-mode-forced sessions too, its `Opus-anchored` count is an **upper bound** on deliberate anchoring — the right shape for a feasibility floor.
- The per-root `buckets`-plus-ephemeral-extraction-script pass yields ≥ 20 admissible Opus-anchored branches **and** ≥ 20 admissible Sonnet-anchored branches, admissibility now decided at each branch's earliest-touching session (Approach § rule 3) rather than the branch aggregate. The 20 floor is `plan-boundary`'s own documented 20-session floor, the same precedent the sibling study's G2 used.

Fail → **stop before the measurement dispatch runs.** Report the census, and raise to the engineer the one option that would resolve it, which only he can authorize because it spends his own future working time: a forward-looking pre-registered pilot in which he randomizes his own anchor choice over N sessions. Do not start that here.

**G1 — contamination bound and scope disclosure.** Not pass/fail; a mandatory disclosure with a pre-committed consequence. Report (a) `plan-boundary`'s ground-truth `Sessions with a real model change observed at boundary+1: X of Y` with its `cache_miss_reason` breakdown — a direct machine-wide count of the opusplan/plan-mode signature among Opus-anchored sessions — and (b) the count and share of admissible branches landing in the excluded mixed band. If the mixed band exceeds the two poles combined, the study's claim is **pre-committed to re-scope** from "Opus-anchored versus Sonnet-anchored sessions" to "the minority of branches carrying an unambiguous whole-branch anchor," and the report must say so in those words. Fixing that re-scoping in advance is cheaper than inventing a threshold whose only justification would be that it was crossed.

The engineer states his Opus-anchored sessions came from his own `--model opus` override. G1 does not test that statement and cannot contradict it — it bounds how much *other* Opus main-thread work is in the corpus alongside it. Note that G1(a) also fires on a deliberate mid-session `/model` switch, which for this design is fine: both mechanisms break a whole-session anchor, and both are excluded by the same rule.

**G2 — stratum admission.** An `(account, repo)` stratum enters the round-count arm only when ≥ 10 of its in-window branches carry ≥ 1 `/code-review` invocation, and it holds ≥ 10 admissible branches in each arm. The 10 floor is `reviewer-yield`'s own documented `insufficient` threshold — "`insufficient` in `Rate` means `Active` fell below 10" (`docs/transcript-analysis.md:268`). A stratum failing only the first leg is excluded from the round arm but stays in the cost arm, which does not depend on the gate firing. All strata failing → the round-count outcome is withdrawn and the verdict rests on cost alone.

**G3 — verdict rule, and its asymmetry.**

- **Adopt-candidate** requires, within an admissible stratum, the Opus arm to show the *lower* value, and: for rounds, the direction survives a 2,000-resample bootstrap in ≥ 95% of resamples (both figures from `plan-boundary`'s precedent, as the sibling used); for dollars, the direction holds in a majority of admissible strata with no admissible stratum contradicting it. Cross-stratum consistency is the cost arm's substitute for a bootstrap it structurally cannot run.
- **Inconclusive** if the direction is unstable, threshold-sensitive across the three cut points, or the strata are thin.
- **Reject is not reachable from this design.** The engineer chose Opus for work he judged harder, and Opus prices at 2.5×. "More expensive, more rounds" is what the assignment mechanism and the rate table jointly predict, so reading it as refutation would be reading the confound twice over. A reject verdict would need a randomized arm this study does not have.

### Corpus freeze

The sibling study measured same-day re-derivation drift on this corpus minutes apart (106 vs 107 zero-round PRs; 24 vs 26 censored branches). Two dispatches scanning independently would inherit that drift as an internal inconsistency between the gate evaluation and the measurement. So the feasibility dispatch redirects every scan's raw stdout to a scratch directory outside any git tree — created via `mktemp -d` with mode `0700`, never a predictable or reused path — and the measurement dispatch reads those frozen files instead of rescanning, given the directory's absolute path from the feasibility dispatch's own return (Dispatch split items 1–2). This also removes the cost of a second six-root pass.

### Alternatives considered and set aside

*A new `transcript-analysis.py` subcommand joining per-session anchor model, total dollars, and round count.* The heavier primitive, and set aside. `_extract_rearm_session_turns` already builds exactly this per session — ordered `main_thread_models`, per-turn dollars, `sidechain_dollars_total` — but only for `rearm-backtest` and `plan-boundary`, whose CLI output is aggregate-only by design. Two lighter primitives were checked before reaching for it: (a) exposing that existing internal structure as a shipped CLI subcommand or flag — rejected because doing so *is* the new-subcommand change, not an alternative to it, and it would ship a durable per-session identity-bearing report to every stow user for one personal retrospective; (b) the `pr-cost` ledger — rejected for the two reasons in the dropped-arm section above. What this study does instead is a third, lighter option distinct from both: an ephemeral, uncommitted script imports that same internal structure directly (`_extract_rearm_session_turns`, `resolve_scan_roots`, `_resolve_project_scope`, `_fam`, `_session_branch_index`/`_attributed_branch`) for this one retrospective's classifier and negative control, then is deleted with the scratch directory (Approach §, Dispatch split). That is not option (a): nothing is exposed to any other stow user, nothing is registered in the CLI, and no durable per-session report ships. The shipped composition `buckets` + `cost --branches` + `review-trace` still covers every figure that reaches the *report*; the import only supplies the classifier's and negative control's session-level intermediate values, which never appear in the report body above the pseudonymized, branch-level tables Critical files already requires.

*Session as the unit of analysis, for the outcomes.* The natural unit for the *classifier*, since `--model opus` is a per-session choice — and now used for exactly that (Approach §). It stays unavailable as the unit for the *outcomes*: `cost --branches` and `review-trace` both report at branch granularity, and re-deriving a full session-level round-count or cross-session dollar allocation for every admitted branch would mean building the second joining instrument the bullet above already declines. So the branch remains the outcome unit, and the mixed-band exclusion still absorbs branches where sessions of different anchors overlapped; only the *label* a branch carries into that outcome is now a session-level fact.

*`--this-repo` scope, as the sibling used.* Set aside on the engineer's own scope answer, and independently: the sibling found only 4 Opus-attributed correction-signal hits in the whole of claude-config's history and stated directly that this repo's corpus does not contain enough Opus-authored main-thread work to compare against. Repeating that scan would re-derive a known negative.

*Stratifying on main-thread turn count as a difficulty proxy.* Set aside as endogenous — dollars scale with turns, so conditioning on turns partly conditions away the effect being measured. Turn count appears only as the negative control's denominator.

### Assumption ledger

**Root problem.** The engineer has run an informal Opus-anchored-versus-default A/B across every repo on this machine and has no measurement of it; the corpus is the only evidence, it ages out on a rolling window, and no shipped report joins a session's anchor model to its cost and its review-round count. The deliverable is a gated verdict with named limits, not a routing or configuration change.

**Givens** (fixed, beyond this design's reach):

- Local transcript retention is a rolling ~30-day window (`cleanupPeriodDays`) — harness-owned; nothing here restores an aged-out transcript, and dropping the ledger arm means the window is the study's hard horizon.
- Treatment was assigned historically by the engineer's own session-by-session choice and cannot be randomized after the fact — the past is not reachable by any design available here.
- The vendor rate table sets Opus-5 at 2.5× Sonnet-5 per identical token profile — vendor-imposed, and the reason the cost verdict is asymmetric.
- The corpus is the six roots declared in `~/.claude/transcript-config-dirs`, a file managed by `setup-claude-accounts.sh` in a separate repository — changing the account set is outside this plan.

**Mechanisms.**

- *Earliest-touching-session Opus-share classification via an ephemeral per-session extraction script* — `anchors: root, row1, row2, row9, row19`. Replicates `cmd_buckets`'s own internal per-session `file_branches` tally (discarded after its merge into the printed branch row) by importing the same shipped, side-effect-free functions `cmd_buckets` itself calls; the share form is what separates deliberate anchoring from plan-mode forcing, and reading it off one session rather than the branch aggregate is what keeps a deliberately-anchored session-1 from diluting into the mixed band as `/handoff` continuations accumulate.
- *Same ephemeral script also prices the negative control at session granularity* — `anchors: row20`. Runs `_extract_rearm_session_turns` against each admitted branch's earliest session and resolves each turn's branch via `_session_branch_index`/`_attributed_branch`, giving a real per-session dollars-per-turn figure instead of the branch-aggregate ratio a session-level classifier would otherwise be checked against.
- *Per-root `--config-dir` loop for `buckets`/`review-trace`/`struggle`* — `anchors: row2, row9`. Supplies account attribution and eliminates cross-account branch-name collisions; not a redaction workaround, since none of the three redacts.
- *`cost --branches <arm>` per arm per stratum* — `anchors: root, row10`. Prices subagent turns by default and reattributes worktree-isolated subagent spend to the dispatching branch, so the engineer's "main session plus every subagent" definition needs no hand-summing, and stays the instrument for the branch-level *outcome* even though the classifier itself has moved to session granularity.
- *`plan-boundary` as feasibility-and-contamination instrument, never as classifier* — `anchors: row5, row6`. Aggregate-only output makes its permanent multi-root scope harmless, and its canonical predicate's inability to exclude plan-mode forcing is exactly what makes its count the right *upper* bound for a floor gate.
- *Pre-registered G0–G3 fixed in this file before the first scan* — `anchors: root`. Without a bar fixed in advance, an observational screen with a known-direction confound yields a narrative.
- *Frozen scan snapshot shared between the two dispatches* — `anchors: row8`. Same-day drift is measured on this corpus, so an independent second scan would put the gate evaluation and the measurement on different data.
- *Composition of shipped read-only subcommands and functions, rather than a new joining subcommand* — `anchors: root`. See Alternatives for the two lighter primitives checked before rejecting the heavier one, and for why the ephemeral import script is a third option distinct from both.

## Critical files

**This plan file itself, and nothing else.** This study changes no other repository file: no new `transcript-analysis.py` subcommand, no new ledger column, no `model:` pin edit, no doc, no register row, no case study. The ephemeral per-session extraction script (Approach §, Reuse) is not an exception to this — it imports shipped functions but is itself never written to this repository at any point; it lives only in the scratch directory for the life of the two dispatches and is deleted with it. The plan file is committed and kept — a deliberate departure from `plan-it` Step 7's default names-no-files branch, on the engineer's own instruction, so the design is on record if a later session turns a finding here into a durable script change (a redaction escape hatch, a new subcommand, whatever a fresh scoped `/plan-it` run would decide). It ships as its own standalone pre-implementation-review PR, carrying no code — the `/plan-review` skill's own PR-packaging checklist names a standalone plan-only PR opened before implementation begins as an accepted case, not a defect.

The deliverable is a **report returned to the engineer in-session as markdown** — verdict against each pre-registered gate, the tables, every command shown with its scope flags and run date (any `--config-dir` path replaced by its account ordinal, never shown raw; a `cost --branches` branch-list argument omitted and described as "that arm's admitted branches for that stratum" instead, per Verification item 3), and a Limits section. Unlike this plan file, the report itself is never committed, never published, and never filed under `docs/case-studies/` — the corpus spans five client accounts, so the machine-wide figures are not this public repo's own history the way a `--this-repo`-scoped case study's figures would be (see Out of scope).

**Report disclosure discipline.** Nothing here reaches a public commit, so the repo's redaction rules do not bind mechanically — but the corpus spans five client accounts, so the report body uses `account-1`…`account-6` ordinals and `repo-A`… pseudonyms, and carries no branch name, session ID, ticket ID, or config-dir path. Those ordinals are comparable only against a report built from the same declared-roots file (`docs/transcript-analysis.md:45`), which the report states. The ordinal/pseudonym rule applies to every in-session reference to account or config-dir identity while writing the report, not only to the final table — the write-up session narrates in ordinals throughout, even though Verification item 3 requires it to read real branch names and config-dir paths from the frozen files to re-derive each figure.

Retention and commingling, stated as separate facts:

1. Raw scan output stays in the scratch directory and is deleted when the report is delivered, or immediately by the orchestrating session if either dispatch errors or is interrupted first (Dispatch split's shared cleanup rule, above the numbered items).
2. This analysis session's own transcript, and each of the two dispatched subagents' transcripts (items 1 and 2 below), will durably retain the real branch names, config-dir paths, and derived figures behind the pseudonymized tables — including each admitted branch's earliest-session dollars-per-turn, which the negative control's extraction script computes and is the only new figure this revision adds to what's retained. The per-turn model sequence `_extract_rearm_session_turns` returns (Row 20) is consumed internally by the extraction script to select which turns are main-thread and priced; it is never part of the script's own emitted output (Dispatch split's fixed schema) and so is not itself retained in any transcript.
3. Item 1's transcript is the widest point of cross-account commingling in this design, since it holds all six roots' raw branch-name sets at once to perform the cross-root dedup.
4. The extraction script's stdout allowlist (Dispatch split) is the control that keeps that transcript's actual content to bare branch names, counts, and figures, rather than the full raw records the script's own process holds in memory to compute them.
5. That data — from five distinct clients — sits in artifacts outside any of their own accounts for as long as each account's own transcript retention window holds it. Nothing here reaches or redacts those transcripts — the harness's own retention mechanism is outside this plan's reach (see the assumption ledger's Givens) — so the report's Limits section names this retention, across all three sessions, as a disclosed constraint rather than treating report-body redaction as the sole safeguard.

**Dispatch split.** Two `general-purpose` dispatches, `model: sonnet`, sequenced — the second consumes the first's frozen output and does not run at all if G0 fails. Neither writes a repository file. Both redirect every scan to the scratch directory and read back only tabulated summary lines and the admissible-branch-name list itself — never a raw per-session or per-record scan listing into their own context or their return.

That constraint is a stated technical requirement on the ephemeral extraction script, not only an intent, because of what the script necessarily holds in memory: `_extract_rearm_session_turns`' `"deduped"` return value is the full deduped record list — complete `message.content` (thinking/text/tool_use blocks), not only the model/dollar/branch/timestamp fields this study needs — held sequentially for all six declared roots (five client accounts) inside one subagent process. Detecting a leak after the script has already run is too late: a print reaches the dispatch's own transcript the instant it executes, and that transcript is durably retained outside this plan's reach (Report disclosure discipline) — a later "corrected and re-run clean" cannot un-retain an earlier run's leak. So the constraint is enforced at emission time, inside the script, not only checked after the fact: every line the script prints goes through one formatting function that validates shape before printing, and raises — printing nothing — on anything else; no other `print` call exists anywhere in the script. That function's only valid output is one tab-separated line per branch, in this fixed 7-field schema:

- Field 1: a bare branch name string.
- Fields 2–5: four non-negative integers (opus/sonnet/haiku/other turn counts).
- Field 6: one float (dollars-per-turn).
- Field 7: one ISO-8601 timestamp (`ts_min`).

Never a `deduped` value, never a raw record, and never an unguarded exception whose default traceback could embed one. That guarantee is not scoped to record parsing alone — branch attribution (`_session_branch_index`/`_attributed_branch`), earliest-session selection (comparing `ts_min` across a branch's contributing sessions), and the dollars-per-turn division itself can each raise with a session or turn record in scope, so the script wraps its entire per-branch computation in one top-level exception boundary, not a parsing-only one: any exception raised anywhere in that computation emits only `"error, branch skipped"` with no field content, never a default traceback. The script is also developed and validated against synthetic fixture records before it is ever run against a real transcript file, so no draft-stage exploratory output touches real per-session data before the final, allowlist-enforcing version exists. Under that constraint, the underlying per-session raw records are never printed or read into either dispatch's context, by construction — Verification item 5 below confirms the constraint held for this run, since a design intent is not itself evidence to the report's reader.

The admissible-branch list is the classifier's own output, not raw scan noise: item 1 must hold all six roots' per-root branch-name sets at once to perform the cross-root dedup below, and item 2 needs the resulting list verbatim to build each `cost --branches` call — neither means reading a per-session or per-record detail through. If either dispatch errors or is interrupted before returning, the orchestrating session deletes the scratch directory itself rather than deferring to the happy-path cleanup named in Critical files.

1. *Feasibility and freeze.* Verifies the interpreter path, creates the scratch directory (`mktemp -d`, mode `0700`, outside any git tree), runs `plan-boundary` once and the per-root `buckets` / `review-trace` / `struggle` loops, writes and runs the ephemeral per-session extraction script once per declared root (Approach §, Reuse), freezes all stdout there, and cross-references the six per-root `buckets` branch-name sets against each other — dropping any name occurring in more than one root's output before it is treated as admissible, regardless of that root's own `Proj` value. For each surviving branch, the extraction script's per-session output identifies the earliest-touching session by `ts_min` and computes that session's own opus share and dollars-per-turn. Returns: the scratch directory's absolute path, the G0 census (admissible branches per arm per stratum, post-dedup, at session-level admissibility), the G1 contamination figures, the G2 stratum-admission table, per-account coverage, and a pass/fail per gate. Small return.
2. *Measurement.* Runs only on a G0 pass, given the scratch directory's absolute path from item 1's return as an input. Reads the frozen files from that path, builds the arms at all three threshold pairs from the post-dedup, session-level admission list, runs `cost --branches` per arm per stratum for the branch-level dollar outcome, computes the negative control from the extraction script's own frozen per-session dollars-per-turn figures, bootstraps the round-count direction at 2,000 resamples, and returns the tables plus a per-gate evaluation with the exact command and run date behind every figure.
3. *Write-up.* **Not delegated** — it runs in the session holding the measurement. Same reason the sibling gave: every quantitative claim must be re-derived from its source at the moment it is written, which a subagent handed a table of numbers cannot do. The report is also a single coherent artifact that does not partition into independently specifiable dispatches.

## Verification

The only repository change is this plan file's own commit — no toolkit code, so `select-tests.py` has no code diff to scope to and running it would verify nothing about this deliverable. `/plan-review` on this plan still applies and is hook-enforced; `/code-review` applies to the plan-file commit itself, per its own no-file-type-exception scope (Row 5). Verification of the actual analysis has five parts below, none of them a test run.

1. **Gate-conformance check, before any verdict sentence is written.** Read this file's G0–G3 text and confirm each stated verdict matches the bar as written — including G3's asymmetry, specifically that no "reject" reading is drawn from the observational arm, and including G1's pre-committed re-scoping if the mixed band exceeded the two poles. Confirm too that the feasibility dispatch's G0 census reflects branches *after* the cross-root branch-name dedup and at the earliest-touching-session admissibility rule 3 now uses, never the branch aggregate (Approach § "Why a branch, why its first session, and why a share rather than a first turn", Dispatch split item 1) — a census run before dedup, or one still keyed to branch-aggregate turn counts, is not the population this plan defines as admissible. A verdict not matching a stated gate means the gate or the verdict is wrong; resolve that before writing, not after.

2. **Negative-control check.** Confirm the earliest-touching-session dollars-per-turn ratio between arms is reported — from the ephemeral extraction script's own per-session figures, not `cost --branches`' whole-branch aggregate — and that its distance from the predicted 2.5× is stated with both readings (classifier behaving versus arms differing in per-turn context depth). A report that omits this, or that substitutes the branch-aggregate ratio for the session-level one, is not publishable to the engineer, because it has no evidence its classifier selected what it claims.

3. **Claim re-derivation at write time.** Every figure reaching the report is re-derived by the writing session from the frozen snapshot at the moment it is written, and shipped alongside the command, scope flags, and run date that produced it, with any `--config-dir` path replaced by its account ordinal — the same substitution item 4 below requires of the report body, never the raw value. `cost --branches` is the one command carrying raw branch names as CLI input; no per-branch pseudonym scheme exists for that argument, so it is omitted from the shown command and described instead as "that arm's admitted branches for that stratum." Scan-derived figures re-read the frozen file rather than rescanning — rescanning would reintroduce the drift the freeze exists to remove.

4. **Disclosure check, extended past the report body.** No hook covers any of this, because nothing here reaches a commit: no raw branch name, ticket ID, session ID, config-dir path, or repo name in the report body; every account referenced by ordinal with the same-roots-file comparability caveat stated; in-session narration en route to the report used the same ordinals rather than naming real accounts or config-dir paths, even while re-deriving figures from the frozen files under item 3 above; the report's Limits section names all three sessions' transcript retention (the write-up session and both dispatched subagents) as a disclosed constraint; and the scratch directory was deleted, whether by the successful-delivery path or the early-termination cleanup named in Dispatch split's shared cleanup rule.

5. **Extraction-script emission-schema check.** The ephemeral extraction script's in-memory data includes `_extract_rearm_session_turns`' full `"deduped"` record list, not only the model/dollar/branch/timestamp fields this study needs (Dispatch split) — so a leak, once printed, is durably retained in dispatch item 1's own transcript before this check ever runs, and a later clean re-run cannot un-retain it. The primary control is therefore emission-time (Dispatch split's single validating print function); this check confirms it held for this run rather than substituting for it. Inspect dispatch item 1's own transcript file — the per-session JSONL record of its Bash tool calls, directly accessible the same way any dispatched subagent's transcript is, independent of its deliberately small structured return — for two properties, both required:
   - **Deny.** Every printed line matches the fixed 7-field schema exactly (Dispatch split) and nothing else: no `{`, `[`, or the substrings `deduped`, `Traceback`, `"role":`, `"content":`, `"tool_use"`, `"thinking"`, or a `.jsonl` path; no line with more than 7 tab-separated fields.
   - **Allow.** The count of schema-conformant lines equals the count of admissible branches in that root's G0 census — a shortfall means a branch's summary was silently dropped (an early return, a swallowed exception) rather than printed as a schema violation, and this catches that failure mode rather than letting it pass silently.

   A violation of either property is a disclosable event, not a silently-resolved one: name it in the report's Limits section, or escalate to the engineer directly if the report is not otherwise produced this run, since the offending run's transcript already retains what it printed and no later fix reaches it. Re-running is scoped to the extraction script alone, against the same frozen scratch-directory inputs — not the whole feasibility dispatch, since the G0/G1/G2 figures it also produced are separable from the script's own stdout. The report is not publishable until a clean run's deny and allow checks both hold.

# post-crash-sessions: recognize non-reboot crashes, cap the legacy dead-pid list

## Context

`post-crash-sessions` (`claude/.claude/scripts/post-crash-sessions.py`,
installed to every stow user) is supposed to hand back resume commands for
sessions orphaned by an unclean shutdown, but a real ghostty crash on this
machine today produced zero resumable sessions and a 1400-line dump of
unrelated stale PIDs — surfaced during a live diagnosis session, not a
hypothetical.

Two independent defects, both in the same file:

1. **The crash classifier is anchored to machine boot time, not to "a
   process died."** `_classify_session`'s `dead_before_boot`/`dead_after_boot`
   split and `_near_boot_transcript_only_ids`'s fallback window both require
   evidence to predate `boot_time`. A terminal-emulator crash (ghostty) does
   not reboot Linux, so every genuinely orphaned session from today's crash
   has registry/transcript timestamps *after* the last boot — and by the
   time the user reruns the tool, Claude Code's own startup sweep has
   already pruned the crashed sessions' registry entries entirely (confirmed
   empirically: only 2 registry JSON files existed across 4 scanned
   accounts, both for sessions that are still alive). The transcript
   fallback's own upper bound (`last_activity <= boot_time`) then also
   excludes them, so they vanish from every report bucket, including
   Unknown. A manual cross-reference of transcript mtimes against live pids
   (this session) confirmed the orphaned sessions exist and are locatable —
   the tool just has no signal shaped to find them when there's no reboot.
2. **The "Legacy bare-pid lookup files with a dead pid" section has no
   cap.** It printed all 1400 stale `capture-session-id.sh` lookup files
   (accumulated since May) with zero truncation, making the report
   unreadable and burying the two real sections above it.

Intended outcome: `post-crash-sessions` surfaces a same-day, non-reboot
crash's orphaned sessions as resumable (or at least flagged, with
appropriate hedging) without requiring a machine reboot to have occurred,
and the legacy-dead-pid section stays readable regardless of how many stale
files have accumulated.

## Approach

Three fixes to one module, unified by a single reframing: **a dead pid is crash evidence in proportion to whether its source deletes the entry on a clean exit.** The scheduled-task lock is released by a clean run and the session registry is pruned at Claude Code startup, so a surviving dead entry in either is anomalous; this repo's own `sessions/<pid>` pid-lookup corpus is never swept, so a dead entry there is routine and only bounds *when* the session ended. The plan (1) stops discarding registry evidence merely because no reboot separates it from now, (2) admits the never-swept lookup corpus as a fourth, recency-bounded evidence source — which is what makes a non-reboot crash findable at all once Claude Code has pruned its own registry — and (3) makes `procStart` comparison work on Linux, where the stored value is a raw `/proc` tick count rather than a `ps -o lstart=` date string.

**Direct answer to the open question raised in Context.** The `dead_after_boot` demotion should be promoted to `CLASS_POSSIBLE_CRASH`, not `CLASS_RESUMABLE` — equally actionable (same resume command, same section shape as the tier PR #595 already built) without overclaiming. And the investigation's conclusion is right on its own terms but the guard is not useless: the `boot_time` split's *stated* pid-reuse rationale is misattributed, but the split does real work under a different name.

- The pid-reuse rationale is indeed already covered elsewhere, confirmed by re-reading: `_read_registry` keys each entry by the file's own `sessionId` field (`post-crash-sessions.py:474`) and `build_report` groups on it (`:887-889`), so a pid-reusing *Claude* session's overwrite replaces the sessionId and the crashed session's id leaves the registry entirely rather than persisting as a mis-attributed dead row; a pid-reusing *non-Claude* process never writes `sessions/<pid>.json` at all, and `_entry_liveness`'s `_same_process` mismatch already returns `"dead"` for it (`:336-341`).
- What the split *actually* distinguishes is **whether the process's death is explained**. `mtime < boot_time` means the reboot killed it — a death that is definitively not a clean exit. `mtime >= boot_time` means it died while the machine stayed up, which is equally consistent with the user closing the session on purpose. Both are dead; only one is *unclean*. The current code encodes this as "explained death = actionable, unexplained death = Unknown," which inverts the tool's purpose, since an application-level crash is exactly what an unexplained death looks like. The fix is to keep the comparison and change what the after-boot arm emits.
- **The case not ruled out in the investigation, named explicitly so it is not lost:** the pid-reuse concern becomes live *again* once the Linux-`procStart`-ticks fix lands, at a different site. A Linux `procStart` is an offset from *a* boot; comparing it against a currently-live process's offset from *this* boot is only meaningful when both refer to the same boot. So the guard relocates from the classification split (where it does no work) onto the identity comparison (where it does) — see row3/row5.

**Root problem:** the tool models "unclean shutdown" as "the machine went down," so a crash that kills a terminal emulator without rebooting Linux leaves no signal the classifier is shaped to find; separately, the one evidence source that *does* survive such a crash is treated as garbage to be listed for deletion rather than read, and Linux `procStart` values never parse, so even live sessions classify as Unknown.

**Givens:**

- **G1** — Claude Code's session registry, its `procStart` field format, and the timing of its own prune sweep are undocumented first-party state owned by Anthropic and can change per platform and per CLI version without notice. Anthropic owns it; this plan can only read defensively, never pin it. `[verified: post-crash-sessions.py:26-30, :85-89]`
- **G2** — `capture-session-id.sh` will keep writing `<config-dir>/sessions/<pid>` at every SessionStart and SubagentStart with no self-sweep. That absence is a deliberate, documented property (`capture-session-id.sh:38-42`), and changing it would renegotiate the `require-respond-pr.sh` bypass contract — a decision outside this plan. `[verified: capture-session-id.sh:38-42, :106]`
- **G3** — `claude --resume <id>` is assumed to accept main-session ids only, not subagent session ids. Harness-owned CLI behavior this plan cannot change; it bounds the worst case for row7 rather than gating it. `[unverified]`
- **G4** — multi-account auto-discovery stays out of scope, per the merged plan behind PR #582 which assigned account-name-to-config-dir resolution to `workstation-setup`. Reach genuinely stops at that ownership boundary. `[verified: .claude/plans/post-crash-sessions-report-fixes.md G1]`

**Per-mechanism:**

- **row1 — Registry `dead_after_boot` + main transcript emits `CLASS_POSSIBLE_CRASH` instead of `CLASS_UNKNOWN`** (`_classify_session:790-798`); with no main transcript it stays `CLASS_UNKNOWN` (nothing to resume). `anchors: root`. `CLASS_RESUMABLE` was the alternative and is rejected: this file installs to every stow consumer, and the "registry holds only live sessions" observation is one machine at one CLI version — on a consumer whose Claude Code does not prune, every cleanly-exited session with a surviving `<pid>.json` would render Resumable. `CLASS_POSSIBLE_CRASH` is robust under either prune behavior, prints the same resume command, and PR #595 already built the section. `[engineer-verified: 2 registry JSON files across 4 scanned accounts this session, both for live sessions]`
- **row2 — Keep the `mtime`/`boot_time` comparison; restate its rationale in the module docstring and the detail strings as explained-vs-unexplained death, not pid reuse.** `anchors: row1`. Deleting the comparison was considered and rejected: it is the only signal separating "the reboot killed this" (Resumable) from "this died for an unknown reason" (Possible crash), and collapsing them would either overclaim the second or discard the first. `[verified: post-crash-sessions.py:19-24, :759-798]`
- **row3 — A numeric `procStart` is compared only when the entry's own `mtime >= boot_time`; otherwise the comparison yields `None` (indeterminate).** `anchors: row5`. This is not a defensive layer, it is the precondition that makes the comparison well-typed — a since-boot offset carries no meaning across a reboot. It is also where the docstring's pid-reuse rationale becomes true, so row2's restatement relocates rather than deletes it. Degradation is safe: `boot_time is None` or `mtime is None` yields indeterminate, which is exactly today's Linux behavior. **Plan-review finding, named here:** `mtime >= boot_time` is a proxy for "the stored ticks were captured under the current boot," not a guarantee — it holds only if nothing rewrites the file's mtime without refreshing `procStart` from a pre-boot value, which is undocumented Claude Code write-cadence behavior (a second G1-class assumption, not a closed type-theoretic precondition). Accepted risk, not a design change: row4's exact-integer-equality comparison (no tolerance) makes a coincidental match against a stale ticks value practically impossible. `[verified: post-crash-sessions.py:384-393 (_safe_mtime's None-means-unknown contract), :300-326]`
- **row4 — `procStart` dispatches on the stored value's shape, not on `platform.system()`: an all-digits value is a Linux `/proc/<pid>/stat` field-22 tick count compared for exact integer equality against the live process's own field 22; anything else takes the existing `_LSTART_FORMAT` path unchanged.** `anchors: root`. Shape-dispatch keeps Darwin's path byte-identical and degrades to today's indeterminate result if a future version changes format again. Field 22 is `starttime`, documented in `proc(5)` as "The time the process started after system boot... expressed in clock ticks (divided by `sysconf(_SC_CLK_TCK)`)" — parsed as `text.rpartition(")")[2].split()[19]`, since splitting after the final `)` skips the `comm` field, which may itself contain spaces and parentheses. Two lighter primitives were checked and both fail:
  - Convert the stored ticks to wall clock via `/proc/stat` btime and `_SC_CLK_TCK`, then compare to `ps -o lstart=` with the existing tolerance — **rejected on the session's own measurement.** Re-deriving from the numbers gathered this session: boot `2026-08-29T21:42:03Z` + `13017318/100` s = `2026-08-31T09:51:36Z`, against `ps`'s `Mon Aug 31 02:52:29 2026` local (UTC offset -7) = `09:52:29Z`. That is a **53-second** gap, 26× `_PROC_START_TOLERANCE_SECONDS = 2.0` (`:66`) — procps derives lstart from `/proc/uptime` rather than btime, and the two diverge with suspend and NTP adjustment. Matching would need a tolerance loose enough to void the pid-reuse guard entirely. Comparing raw ticks to raw ticks needs no conversion, no tolerance, and no boot time.
  - `ps -o etimes=` converted to a start instant — rejected: 1-second resolution, and it is derived from the same uptime clock, so it inherits the divergence above rather than removing it.
  - Widening `_PROC_START_TOLERANCE_SECONDS` and keeping the string compare — rejected: the stored value is not a date string, so no tolerance makes `strptime` parse it. `[verified: post-crash-sessions.py:66, :101, :300-326; arithmetic re-derived from the Context's own measured values]`
- **row5 — New injectable seam `_proc_starttime_ticks(pid, *, proc_root=Path("/proc")) -> int | None`, consulted only for pids `ps` has already reported alive.** `anchors: row4`. Mirrors the existing `_ps_lstart` / `boot_time_fn` seam convention so tests inject a fake proc root instead of touching the real one; `ps` stays the sole liveness oracle, so a dead pid triggers zero `/proc` reads and the batched `_ps_lstart_batch` call (`:894-905`) is unchanged. Missing or unreadable file returns `None` → indeterminate. **Plan-review finding, fixed here:** the seam is incomplete unless it's threaded all the way to the public entry points, matching how `boot_time_fn`/`ps_lstart` are already threaded — `build_report` gains a `proc_starttime_ticks_fn=_proc_starttime_ticks` keyword (default the real implementation, mirroring `boot_time_fn=_boot_time`) and passes it through to `_classify_session`/`_entry_liveness`, so the Bug-3 headline test (Critical files, test file bullet) injects a fake ticks function instead of reading the real `/proc` of a live test pid. `[verified: post-crash-sessions.py:233-297, :861-868]`
- **row6 — `_parse_lstart` gains an `isinstance(raw, str)` guard.** `anchors: row4`. `RegistryEntry.proc_start` is populated from raw `data.get("procStart")` with no type check (`:484`), and `_parse_lstart`'s `if not raw` passes a nonzero int straight into `raw.strip()` (`:306-307`) — an uncaught `AttributeError` if any CLI version ever stores `procStart` as a JSON number rather than a numeric string. Now that the field is known to hold a number-shaped value on Linux, that is a plausible next drift, and row4's shape predicate has to type-check the value anyway. `[verified: post-crash-sessions.py:300-309, :482-490]`
- **row7 — Source D: parse `<config-dir>/sessions/<pid>` bare lookup files into a new `LookupEntry` dataclass (session_id, pid, proc_start, mtime, path, config_dir) and feed them through the existing liveness and grouping machinery, admitted only when `now - mtime <= crash_window_seconds`.** `anchors: root`. `capture-session-id.sh:106` writes exactly two lines — session id, then `TZ=UTC LC_ALL=C ps -o lstart=` output — so the stored start time is already in the format `_parse_lstart` expects and needs none of row4's dispatch. This is the only first-party-adjacent source that survives Claude Code's own prune, which is what makes a non-reboot crash findable after the user has restarted Claude. The mtime filter is a source-admission rule, not a crash heuristic: the corpus never forgets (1400 files since May on this machine), so without a horizon every session ever run would classify. Three lighter primitives were checked:
  - Rely on the registry alone — rejected: empirically already pruned by the time the user runs the tool, which is the reported symptom.
  - A transcript-mtime recency listing with no pid — rejected: with no pid there is nothing to check liveness against, so the listing cannot exclude currently-live sessions, which is the dominant noise source (the tool is typically run *from* a live session).
  - Scan `ps` for live `claude` processes — rejected: `ps` output carries no session id, so it can neither attribute nor exclude per session.

  This adds no new scan: `_read_registry` already enumerates these paths (`:459-464`) and `_ps_lstart_batch` already queries their pids (`:901-904`). Files are mtime-filtered before their contents are read. `[verified: capture-session-id.sh:96-109; post-crash-sessions.py:438-491, :894-905]`
- **row8 — Source D dead-pid + main transcript emits `CLASS_POSSIBLE_CRASH`; dead-pid with no main transcript emits `CLASS_UNKNOWN`.** `anchors: row7`. Never `CLASS_RESUMABLE`: because this source is never swept (G2), a dead entry is the normal end state of every session that ever ran, including cleanly-exited ones, so it bounds *when* a session ended but says nothing about *how*. The no-transcript case routes to Unknown rather than `CLASS_CRASHED_NO_TRANSCRIPT` because that label overclaims for a never-swept source and there is nothing to resume — this also absorbs G3's worst case, where a `SubagentStart`-written file names a subagent session id that has no main transcript, degrading into a non-actionable bucket instead of emitting an unusable resume command. `[verified: capture-session-id.sh:26-27, :38-42; post-crash-sessions.py:629-649 (subagent ids are never main-transcript keys)]`
- **row9 — `_near_boot_transcript_only_ids` becomes `_recent_transcript_only_ids`, matching on either disjunct: `boot_time is not None and boot_time - window <= last_activity <= boot_time`, or `last_activity >= now - window`. The `boot_time is None -> []` early return is dropped** (`:664-671`). `anchors: root`. Both bounds in the current predicate exclude every non-reboot-crash session — `last_activity <= boot_time` is the one that makes them vanish from every bucket including Unknown. Adding a separate tier for the now-anchored case was rejected: `CLASS_POSSIBLE_CRASH` already means "the process is gone and this was recently active, but a clean exit is not ruled out," which is exactly true for this feeder too. Only the detail string differs, naming which anchor matched so the operator knows whether a reboot is implicated. **Plan-review finding, fixed here:** dropping the early return while leaving the first disjunct's arithmetic unguarded raises `TypeError` on `None - window_seconds` whenever `boot_time` is `None` and `now` is provided (ps-unusable or boot-time-undeterminable platforms) — the explicit `boot_time is not None and ...` guard above is required, not optional, and the now-disjunct must still evaluate on its own. `[verified: post-crash-sessions.py:654-671, :844-854]`
- **row10 — One window governs both anchors and both sources: rename `_NEAR_BOOT_TRANSCRIPT_WINDOW_SECONDS` to `_CRASH_EVIDENCE_WINDOW_SECONDS` (value unchanged at 14400.0) and give the flag a second option string: `parser.add_argument("--crash-window-hours", "--near-boot-hours", ...)`.** `anchors: row7, row9`. The quantity is the same in all three uses — how far back the crash's blast radius reaches — and 14400 is already grounded on the measured 29min–2h45m gap range from PR #595, so a second constant with the same value would be duplication. A rename alone would break a flag documented at `docs/scripts.md:43`; argparse accepts multiple option strings for one argument at zero code cost, so the documented spelling keeps working with `dest="crash_window_hours"`. `[verified: post-crash-sessions.py:77-83, :1208-1216; docs/scripts.md:37, :43]`
- **row11 — `main()` captures `now = time.time()` once and passes the same scalar to both `build_report(now=...)` and `render_report(now=...)`; `build_report`'s parameter defaults to `None`, which admits no Source D entries and skips row9's now-disjunct.** `anchors: row9`. A scalar rather than a `now_fn` callable, because `boot_time_fn` is a *capability* (a platform probe tests replace) while `now` is a value, and `render_report(now=...)` already established the scalar convention in PR #595. One capture rather than two prevents the window decision and the age annotation disagreeing. - **row12 — The legacy cleanup section excludes any dead-pid file inside the crash window, sorts oldest-first, caps the listing and the `rm --` line at `_LEGACY_DEAD_LIST_CAP = 20`, and prints an explicit "showing N of M" note whenever it truncates.** `anchors: root`. - **row13 — `lookup_entries` is a keyword-only parameter with default `()` on `_classify_session`, not a fourth positional alongside `registry_entries`/`lock_entries`.** `anchors: row7`. The asymmetry mirrors a real one: registry and lock are self-pruning first-party sources admitted unconditionally, while Source D is this repo's own never-swept side-channel admitted only under a recency filter. It also leaves every existing `_classify_session(...)` test call unchanged. Collecting the run-wide seams (`boot_time`, `now`, `ps_lstart`, `ps_usable`, `proc_starttime_ticks`, window) into a frozen context dataclass would read better at eleven parameters but rewrites every existing call site — deferred to Out of scope rather than bundled. `[verified: post-crash-sessions.py:700-710]`

**Dispatch split.** One `code-writer` dispatch for the whole change, with the rows ordered row4→row6→row5→row3 (liveness seam), then row7→row8→row13→row9→row10→row11→row1→row2 (classification), then row12, then row14. Splitting is only warranted for non-overlapping file sets; this change has none.

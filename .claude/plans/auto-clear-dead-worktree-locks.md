# Auto-clear dead-PID worktree locks

## Context

Fix the shared root cause behind GH-754 and GH-747: `_lib_worktree_collision_guard` (`claude/.claude/hooks/_lib.sh:976-1089`) always denies a write when it finds an existing worktree lock — even when it has just conclusively proven, via `kill -0`, that the locking PID is dead — requiring a human to run `git worktree unlock <path>` and retry manually. On this machine right now, 70 worktrees are locked and 61 of 66 unique locking PIDs are dead; GH-754 counted 48 identical deny-then-manual-unlock-then-retry cycles in a single two-week window (2026-08-13 to 2026-08-26), 42 via Edit and 6 via Write. GH-747 is the same mechanism hit via the session-resume angle specifically. The intended outcome: when the guard has just conclusively proven a lock's PID is dead, it safely evicts that lock and re-acquires it for the current caller within the same hook invocation — eliminating both the manual `git worktree unlock` step and the manual retry, since both callers treat a guard return of 0 as "proceed" and the originally-blocked tool call goes through in that same `PreToolUse` invocation.

A prior iteration of this exact design was already tried and explicitly rejected, with a live-reproduced counterexample, in `.claude/plans/worktree-collision-guard.md:86-108`: `git worktree unlock` has no ownership check, so an evict-then-relock sequence is racy against a second evictor — one session can unlock-and-relock while a second session's stale `unlock` call, issued from an earlier read, lands afterward and silently strips the first session's fresh, legitimate lock. PR #730 (merged 2026-08-23) reaffirmed this as a known gap and added explicit tests asserting "guard must not auto-evict" as an invariant. This plan reverses that invariant deliberately, closing the specific race the prior design proved rather than reopening it.

## Approach

Auto-evict a dead worktree lock inside the hook by making eviction a **once-only right, claimed by an exclusive create and never released** — the same `noclobber` primitive the guard already uses to acquire the lock itself. Before a caller may remove a lock it has proven dead, it must win an `O_EXCL` create of a per-lock-identity claim file in the worktree's own admin directory (`<wt-git-dir>/claude-evicted-lock-<dead-pid>-<dead-session>`). The winner re-reads the lock inside that claim, removes it only if it is byte-for-byte the same holder it proved dead, and re-acquires through the existing atomic acquisition path. Every loser denies with today's message and today's manual remedy. The guard returns 0 on a successful reclaim, so the Edit/Write/git call that triggered the hook proceeds in the same `PreToolUse` invocation with no manual `git worktree unlock` and no retry.

**Why this answers the prior rejection.** `.claude/plans/worktree-collision-guard.md:86-108` rejected in-hook eviction because "git's `worktree lock` is exclusive-create but `worktree unlock` is not compare-and-swap, there is no race-safe way to auto-evict inline without adding a second coordination layer on top of the first." That is correct, and this design accepts it rather than arguing with it: it *does* add a second coordination layer, and the layer is **exclusive-create-only — it has no unlock half at all**. The rejection's own reasoning ("the danger is in the unlock half of the sequence, not the relock half", `:191-210`) is what makes a release-free claim sound: there is no second unlock to be raced. A conventional acquire/release mutex — the shape one might reach for first — would reintroduce exactly the rejected problem one level up, because a mutex that leaks (hook SIGKILLed mid-section) needs staleness handling, and stale-mutex reaping is itself an unconditional unlink racing a second reaper. That is the recursion, and it is why this returns a variant of the prescribed approach rather than the prescribed approach: **never releasing is strictly simpler than releasing safely.**

**Bounded worst case.** A claim that is burnt without completing (permission error, harness kill mid-section) permanently disables auto-eviction *for that one lock identity in that one worktree* — every other worktree and every other dead lock is unaffected, and a conventional mutex's leak would instead disable eviction for the whole worktree forever. Most interruption points still leave today's deny-and-manual-unlock fallback intact; the one exception (a kill between lock removal and reacquisition confirmation) is named in the `_lib.sh` Known-gaps update below, not glossed over here. There is no retry loop and no `sleep`: one claim attempt, then fall through to deny. Per-subprocess latency stays bounded by the existing `_lib_capped` 5s budget, but the reclaim path chains roughly 8-10 such calls sequentially — the aggregate bound and the uncapped fallback on `timeout`-less machines are also named in the Known-gaps update.

### Assumption ledger

**Root problem.** `_lib_worktree_collision_guard` (`claude/.claude/hooks/_lib.sh:976-1089`) denies a write against a worktree whose lock it has just proven dead via `kill -0` (`:1080-1084`), forcing a human `git worktree unlock` plus a manual retry on every occurrence; making it self-heal requires a confirm→remove→re-acquire sequence that is not atomic as a unit, because file unlink is unconditional while file create is exclusive.

**Givens** (fixed, outside this design's reach):

- **G1 — git's `worktree unlock` has no ownership check, and its own lock write is not atomic.** Vendor behavior; the repo already bypasses the write half for the same reason. [verified: `.claude/plans/worktree-collision-guard.md:89-96`; `.claude/plans/atomic-worktree-lock-acquisition.md:100-104`]
- **G2 — `kill -0` cannot distinguish a dead PID from a reused one or one owned by another user.** OS semantics; already a documented gap. [verified: `_lib.sh:966`; `require-worktree-for-git-writes.sh:72-78`]
- **G3 — the harness owns the hook process's lifetime and can kill it at any instruction boundary.** `_lib_capped` caps children, not the hook itself; no bash construct survives SIGKILL. [unverified — the harness's hook timeout was not measured this session; the design is correct either way because it treats an interrupted claim as permanently burnt]
- **G4 — `session_id` is harness-assigned and stable across `--continue`/`--resume`.** [verified: `docs/design-decisions.md` §29 and its Sources entry]
- **G5 — the threat model is a single-developer machine with cooperating sessions, not an adversarial boundary.** Set by the committed prior design; widening it is a decision outside this plan. [verified: `_lib.sh:964-965`]

This narrows but does not eliminate the race — a manual `git worktree unlock` plus a third party's fresh acquisition landing within that one subprocess's own read-then-unlink instructions could still in principle race it. A session whose crashed lock is auto-evicted by a *different* session, and which is then resumed, will be denied on that worktree as "in use by a live session" where it previously self-recognized. [engineer-verified: implied by the ticket's stated intent that a dead lock be reclaimable by whoever touches the worktree]

14. The eviction path costs roughly three `worktree list --porcelain` reads (self-lock check, diagnosis, post-reacquire confirm) plus four `bash -c` calls (the failed first write attempt, the claim create, the merged read-compare-unlink, and the successful re-acquire write) — paid only on the rare dead-lock path, never on the self-lock fast path or the ordinary acquisition path. [verified: traced `_lib.sh:1093, 943, 1132, 979, 985, 943, 946` this round]
15. `wt_git_dir` is already resolved and in scope at the dead-PID arm (`_lib.sh:1113-1117`), and the main-working-tree refusal at `:1118-1121` runs before it, so the claim path can never target the main tree's admin dir. [verified: `_lib.sh:1113-1121`]

**Mechanism justifications:**

- **M1 — per-lock-identity claim file created with `set -o noclobber` in `<wt-git-dir>`, never removed** (anchors: root). This is the only new coordination and it is a heavier primitive than "just unlink and relock," so the lighter options were enumerated first: **(a)** no coordination at all — live-reproduced double-holder in `.claude/plans/worktree-collision-guard.md:89-101`; **(b)** the existing `O_EXCL` create on `locked` alone — exclusive for creation, but eviction must unlink first and unlink is unconditional, leaving the unlink→create window unprotected; **(c)** the existing post-write verification re-read alone (`_lib.sh:1035-1049`) — two evictors can each verify their own lock at different instants and both return 0, which is why `TestCollisionGuardRereadRace` exists as a *fail-closed* test rather than a mutual-exclusion one; **(d)** `git worktree unlock` plus a new ownership token written into the reason string — the token must be checked and then acted on in two separate steps, so it is the same non-atomic sequence with an extra field, and G1 means git will still honour any unlock from anyone; **(e)** a long-lived daemon or watcher that reaps dead locks out of band — a far more privileged and invasive execution context (a persistent process, its own lifecycle, its own crash story) for a problem solvable with one file create, and it would still race a live session acquiring a lock it is mid-reap; **(f)** OS-level `flock`/`lockf` — row 13: neither CLI exists on both platforms, and reaching `flock(2)` from bash needs a `python3` spawn, which would make this guard depend on `python3` where today only the git-writes *slow* path does (`require-worktree-for-git-writes.sh:217-218`). The claim file uses the same `_lib_capped bash -c 'set -o noclobber; …'` idiom as `_lib.sh:1034`, and the same critical-section idiom `review-ledger.sh:100-137` already establishes in this repo — whose own header names `_lib_worktree_collision_guard` as its source. It deliberately does **not** copy that function's two behaviors: its dead-PID reaping of the lock file (unsafe here per the recursion argument above) and its fall-through-to-unlocked-append after N retries (fail-open, which is the wrong direction for a mutual-exclusion gate).
- **M2 — the in-claim check must show the lock file's raw content still matches the diagnosed-dead identity before removal, read and unlinked in one merged subprocess** (anchors: row8, row9). Closes the stale-observation window between the pre-claim diagnosis read and winning the claim, and does so with no command-dispatch boundary between confirming the content and removing it — narrower than a separate reread-then-delete call pair would leave open. `kill -0` is deliberately *not* re-run inside the claim: a dead PID cannot resurrect, and re-running it would only add a way to spuriously abort when the OS has reissued that PID number (G2).
- **M3 — remove the lock via a raw-file read-compare-unlink (`_lib_capped bash -c 'content=$(cat "$1" 2>/dev/null); [ "$content" = "$2" ] && rm -f "$1"' _ "$wt_git_dir/locked" "$expected_reason"`), not `git worktree unlock`** (anchors: row9). Strictly the lighter primitive: no subprocess indirection, no git path resolution, and symmetric with the raw-file write the guard already performs at `_lib.sh:1034`, whose interoperability with git's own tooling is verified at `.claude/plans/atomic-worktree-lock-acquisition.md:57-66`. The function's header claim that it "never calls `git worktree unlock`" stays literally true.
- **M4 — extract `_lib_worktree_acquire_lock` from the existing `_lib.sh:1034-1049` block and call it from both the ordinary path and the reclaim path** (anchors: row10). Without it the write-then-verify-then-fail-closed sequence would be duplicated verbatim, which is a defect under the single-source-of-truth rule. Three outcomes: 0 = acquired and verified, 1 = write failed (caller falls through to diagnosis), 2 = wrote but could not confirm (caller emits the existing "could not be confirmed after acquiring it" message). Message ownership stays in the guard, so no deny string moves.
- **M5 — one claim attempt, no retry and no sleep; any non-reclaim outcome falls back to the existing deny** (anchors: root, G3). Guarantees the worst case is bounded-but-not-small rather than unbounded — no retry/sleep loop, but the reclaim path's aggregate latency across ~8-10 sequential `_lib_capped` calls is not itself capped; see the `_lib.sh` Known-gaps bullet on aggregate latency.
- **M6 — deny message reworded to `this worktree is locked by pid %s, which is no longer running, and could not be cleared automatically — clear it with \`git worktree unlock %s\` and retry`** (anchors: M5). The current wording's "if confirmed" hedge no longer describes reality: the guard has now confirmed *and* attempted. Both substrings the three test files assert on (`no longer running`, `git worktree unlock`) are preserved, so the change is a rewording, not a contract break.

6. **Manual end-to-end on a real stale lock (non-destructive, and the only step that touches live state):** pick one linked worktree whose lock names a PID that `kill -0` reports dead, `cd` into it, make a trivial Edit, and confirm the hook allows without a deny round-trip and that `git worktree list --porcelain` now names the current session. Verify the PID is dead *first* — this step removes a real lock. When recording the result anywhere that lands in the repo, use placeholder paths and session ids: this plan and its PR ship to a public repository under the repo's redaction rules.
7. **Git interop:** with a claim file present in a worktree's admin dir, confirm `git worktree list --porcelain`, `git worktree unlock`, `git worktree prune`, and `git worktree remove` all behave identically to a worktree without one (row 12 is the only `[unverified]` row that gates correctness rather than ergonomics).

## Out of scope

- **`cleanup-merged-branches.sh:730-747`'s own dead-PID auto-eviction** (`git worktree unlock` at `:744`, with a re-lock on remove failure at `:753`). Structural-sibling audit result: it is the same unconditional-unlock shape, and `.claude/plans/worktree-collision-guard.md:381-383` already flagged it. Left out because its threat model differs materially — a human-initiated batch cleanup that immediately *removes* the worktree, not an automatic per-tool-call gate — so the fix there is a different question (should it evict at all, or skip?) rather than the same one. A follow-up can reuse `_lib_worktree_reclaim_dead_lock`'s claim idiom; bundling it here would mix a hook fix with a CLI-script policy change.
- **Unparseable-reason locks (`state=2`), including the truncated-session-token shape.** No parseable PID means deadness cannot be established, so the claim's precondition is unreachable by construction. Row 7.
- **Live-foreign locks.** Unchanged deny, unchanged message, no claim file created. Must-not-regress #2.
- **Claim-file garbage collection.** Bounded by worktree lifetime (removed with the admin dir) and ~80 bytes each; adding a sweeper would reintroduce an unconditional-unlink race for no measured benefit.
- **Bulk-clearing the worktrees already locked by dead PIDs on existing machines.** They clear themselves on the next touch of each worktree, so no migration command ships.
- **`.claude/plans/worktree-collision-guard.md` and `docs/design-decisions.md` §29.** Both are dated records of decisions that were correct when made, protected by CLAUDE.md's Axis 3 preserved-content rule. §29's "degrade-not-auto-evict posture" sentence also remains literally true of the malformed-lock cases it describes, which this change does not touch. Supersession is recorded in the new §32, not by editing either.
- **`kill -0`'s inability to distinguish a dead PID from a reused or other-user PID** (G2), and **`O_EXCL` atomicity on older NFS-mounted git-dirs** (`_lib.sh:973-975`). Pre-existing documented gaps, unchanged in both directions by this design.
- **A `SessionEnd` unlock hook.** Explicitly rejected in the prior design (`.claude/plans/worktree-collision-guard.md:263-267`) and orthogonal: it would reduce how often dead locks appear, not make eviction of the ones that do appear race-safe.

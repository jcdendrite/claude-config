# skill-fidelity-reviewer zero-finding cited-path edit rate: correct the record

## Context

`skill-fidelity-reviewer`'s low zero-finding cited-path edit rate — a documented, real signal per the corrected `reviewer-yield` measurement (GH-762, PR #764) — does not warrant a routing, trigger-prose, or demotion change; instead, the repo's decision record needs to correctly state why, since GH-762's issue text currently cites `docs/design-decisions.md` §9 for a rationale §9 doesn't actually contain.

GH-762 fixed a reviewer-yield measurement defect and explicitly deferred deciding what to do about any post-fix gap to a separate follow-up (its item 4). A post-fix re-run showed `skill-fidelity-reviewer`'s zero-finding-bucket cited-path edit rate at 6.2% (343 dispatches), a clear outlier against every peer reviewer's zero-finding edit rate (22-33% range). GH-762's issue body asserted this is "the expected shape for a per-branch compliance gate, already discussed in `docs/design-decisions.md` §9" — but §9 contains no such discussion; that framing is GH-762's own unverified gloss.

Intended outcome: `docs/design-decisions.md` gains a new dated section recording the actual mechanism-based reasoning for why this rate is expected and benign, and GH-762's issue body is corrected to cite that section accurately instead of over-citing §9. No routing, trigger-prose, or dispatch-condition change to `skill-fidelity-reviewer` — the user chose "conclude no action + fix docs" over pursuing trigger-prose refinement or a full demotion analysis.

## Approach

Record the actual reason `skill-fidelity-reviewer`'s zero-finding cited-path edit rate is low in a new dated section of `docs/design-decisions.md` (`## 32.`), index it as a closed lever in `docs/cost-levers-considered.md`, and rewrite GH-762's issue body to cite that new section instead of §9. No code, skill, agent, or routing file changes — the deliverable is a correct decision record plus one corrected tracker artifact.

**Why a new dated section rather than an edit to §9.** `docs/design-decisions.md` is an append-only ledger of dated conclusions: §13 through §31 each carry their own date and their own evidence, and later entries reverse or narrow earlier ones by reference (§31 opens by naming what §28 measured and why the trade-off shape changed) rather than by rewriting them. Appending §32 puts this conclusion in the genre the file already uses. §9 is a different genre — an undated statement of standing roster *operations* (extend / split / spawn) whose `skill-fidelity-reviewer` paragraphs establish the agent's charter and its cost-and-effectiveness re-measurement instruction. Folding a dated, evidence-bearing conclusion about one column of one measurement into that entry would give §9 two kinds of claim under one heading, and would leave a reader with the impression that §9 held this reasoning all along — which is exactly the misstatement being corrected.

**What the new section must actually say — and the precision correction it carries.** GH-762's issue body asserts the low rate is "the expected shape for a per-branch compliance gate, already discussed in `docs/design-decisions.md` §9." Both halves fail. §9 discusses no such thing. And "per-branch gate" is not on its own an explanation: dispatch cadence alone does not predict a low *cited-path* edit rate. Two verifiable mechanisms do, and §32 must state those instead:

1. **The join key is lexical and hashed, so the one branch shape where the citation *is* the work surface still cannot register.** `skill-fidelity-reviewer` resolves each skill by reading `~/.claude/skills/<name>/SKILL.md` (its Name resolution step), so the paths it names are config-dir paths. A branch in this repo that edits that same skill edits it through the stow source, `claude/.claude/skills/<name>/SKILL.md`. `_normalize_cited_path` is deliberately lexical — no `Path.resolve()`, no `realpath`, no `stat`, for reasons its own docstring gives — and hashes the normalized string to a sha256 prefix. Two spellings of one file therefore produce two different keys and never join.
2. **On a clean pass the agent cites the specifications it read, not the branch's work surface.** Citations are drawn from the last assistant text *plus every `Write` blob*, so with `findings_path` set the scanned substance is the findings file, whose clean-pass content is a dismissal list naming skills and skill bodies. A branch is not normally editing the skill it invoked. This is what makes the numerator structurally small.

Dispatch timing then inflates the denominator without touching the numerator: `/ready-for-review` spawns this agent once per branch at the last gate before handoff, where the ship path still produces real edits (fixing other reviewers' findings), so `Active` — defined as "the session recorded any code edit at all," a null control, not a path-specific one — is easily satisfied while the cited spec paths stay untouched.

Together these give the section's actual conclusion: **the cross-reviewer comparison is not like-for-like.** A `staff-*` reviewer carries `Bash`, re-fetches the diff inside its own context, and cites the diff's own files — the very files the session edits next. `skill-fidelity-reviewer` carries `Read, Grep, Glob, Write` and no `Bash`, and cites the specifications it was checking against. `Rate` answers "did the session act on a path this reviewer named"; the two agents' named-path populations are different kinds of object, so ranking them against each other measures citation genre, not reviewer value. That is why no routing, trigger-prose, or dispatch-condition change follows.

**Three writing constraints on §32.**

- **No percentages, and no per-bucket counts.** Claude Code deletes transcripts on a rolling `cleanupPeriodDays` window, so any figure written into a durable decision doc becomes unre-derivable within about a month — an unverifiable claim in the file this repo treats as authoritative. §32 records the mechanism and names the command that reproduces the observation; the numbers stay in this plan and in the issue, which are dated artifacts.
- **No claim about this agent's findings rate.** §9 already owns that claim and carries its own re-run instruction. §32 is about one column of the second table; asserting anything about how often the agent finds something — in either direction — would put two homes on one fact and would be doing it from a measurement that does not answer that question.
- **Name the falsifier.** The entry rests on mechanism 2 being true of real clean-pass output. Cited paths are held only as sha256 digests and never surface as raw paths, so this is *not* checkable from the tool's own output — §32 must say so and point at the checkable surface instead: the agent's own findings files under `agent-reviews/` in existing worktrees. If clean-pass findings files routinely name the branch's diff paths, mechanism 2 is wrong and the low rate becomes a real "the session ignored what it was told" signal; the same applies if the agent's Output format later gains a required enumeration of files checked. Either observation re-opens this entry.

**Drop "compliance gate."** The phrase appears nowhere in this repo outside GH-762's own prose (grep across the worktree returns only this plan's Context). It is PR-defined terminology with no definition a future reader can resolve, and its apparent authority is part of what made the §9 over-citation read as grounded. §32 states the two mechanisms and the dispatch cadence in plain terms instead.

**Alternatives considered and set aside.** (a) Appending a paragraph to §9 — genre mismatch and the misleading-provenance problem above. (b) Correcting only the GH-762 issue body and writing nothing in-repo — the lightest option, but it leaves no in-repo home, so the next cost investigation re-derives the same conclusion from scratch, and a tracker issue is not where this repo records decisions. (c) A comment beside the `Rate` column in `reviewer_yield.py` — the reasoning is agent-specific and roster-dependent, CLAUDE.md caps a comment at one non-obvious sentence, and a per-agent caveat inside a general-purpose measurement module would imply the tool special-cases this agent, which it does not. (d) Changing the measurement itself (symlink-aware normalization, or excluding spec-path citations) — a real option, but it needs its own plan and its own before/after measurement, and it would break comparability with the ledger rows already recorded; see Out of scope.

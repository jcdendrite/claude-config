# Delegate review-feedback fixes to `code-writer`

## Context

**Goal:** make sessions reliably delegate the code changes that fix
reviewer-flagged findings (`code-review` ADDRESS items, `ready-for-review`
steps 3/4, `respond-pr` `FIXED` items) to the `code-writer` subagent, instead
of the main thread applying them inline.

**Why now.** The engineer's anecdotal read of transcripts is that after a
plan is approved, sessions reliably dispatch `code-writer` for the initial
implementation — a prior plan (`.claude/plans/handoff-code-writer-delegation.md`,
merged as PR #723) measured and fixed exactly that gap for the
approved-plan-implementation case. But that same prior plan's own scope
section deliberately treated "fixing a [returned] diff" as one of the
legitimate-inline-edit cases a hard rule *can't* distinguish from plan
implementation, and left the general question of delegating post-review
fixes unaddressed. The engineer now observes the same inline-edit pattern
recurring specifically in the fix loop that follows reviewer feedback: after
`code-review` or `ready-for-review` returns findings, the main session tends
to apply the fix itself via `Edit`/`MultiEdit` rather than dispatching
`code-writer`, even though the reviewer has already named the file, line, and
often a concrete suggested fix — the same "decision already made" shape that
grounds the approved-plan mandate. The engineer's own instinct is to add an
explicit instruction to `code-review`'s and `ready-for-review`'s invoker, but
wants `plan-architect`'s independent judgment on the mechanism and its
placement before committing to that shape.

**Intended outcome:** a grounded, transcript-evidenced decision on whether
and how to extend delegation-by-default to the post-review fix loop —
including whether the prior plan's rejected "trivial fix" exception should
stay rejected here, given that a review finding's location is normally
already named — landing in the same DRY location the prior plan
established (`subagent-delegation`) with concrete pointers from every
call site, not a restatement in each.

## Approach

Delegate the fix, once per review round, using the finding set each review skill already produces as the dispatch specification — and reject the trivial-fix carve-out again, but on new grounds, because the prior plan's reason for rejecting it does not survive here. The canonical rule lands in `subagent-delegation`; `code-review`, `ready-for-review`, and `respond-pr` each get a pointer, and `code-review` additionally emits a one-line `Fix route:` record so the call is auditable rather than silent.

Three findings drive the shape, and each overturns something in the dispatch's framing:

**Condition (2) genuinely fails here, and the case for delegation does not rest on it.** A `/code-review` finding arrives with file, line, and a concrete suggested fix — the Output format section mandates all five fields (`code-review/SKILL.md:234-240`). Locating the target therefore costs the parent one ranged `Read`, not a discovery sweep, so the decision-made test's context-cost condition often is not met for a single finding. I am not force-fitting it. What justifies the default instead is that the fix is itself review-bearing work: `ready-for-review` step 3 already requires the fix commit to go through its own staged-diff `/code-review` + marker gate (`ready-for-review/SKILL.md:79-84`), which is precisely the after-the-fact feedback sensor `docs/design-decisions.md` §11 says `code-writer`'s in-agent self-review exists to move earlier. An inline fix gets no `staff-*`-angle pass before that gate; a dispatched one does. The secondary axis is aggregate, not per-fix: section C's block-level ratio (10,734 inline edit blocks across 2,410 rounds, ~4.5 per round, vs. 376 dispatches) is what actually sits in the parent, and it accumulates late in a session when parent context is most expensive.

**The trivial-fix exception stays rejected — for a reason #723's does not supply.** #723 rejected it because condition (2) already handled the small case; that reasoning does not transfer, per the paragraph above. The reason it stays rejected here is that `code-review`'s own adjacent step already declares this axis invalid: "Disposition turns on complexity/risk/test coverage, never fix size" and lists *small / quick / cosmetic / non-blocking / advisory* among the invalid rationales (`code-review/SKILL.md:320,338`). Introducing a size test at fix-application, one step after the disposition step forbids it, would put two contradictory rules in one file. The structural fix is to change the unit rather than add an exception: **one dispatch per review round carrying every ADDRESS row**, which dissolves the per-finding "is this one worth a dispatch?" question that produces the cherry-picking failure. Two honest carve-outs remain, neither size-based — a finding whose fix is not code (a `## Deferred review findings` block, a `respond-pr` reply body, a plan-file edit), and a finding you are still re-deciding rather than applying, which fails condition (1) and is the existing test doing its job.

**Section C cannot serve as #723's remeasurement, so its stated trigger for reconsidering the nudge hook has not fired.** The #723 narrowing is dated 2026-08-21 (`docs/design-decisions.md:143`) and today is 2026-09-01, so roughly 11 of the 90 measured days postdate the change. A 90-day aggregate dominated by 79 pre-change days cannot detect an 11-day post-change effect even if the fix were fully effective, so "the number has not moved" is not yet a supportable reading. I therefore do not escalate to a hook. #723's hook-rejection reasoning also still applies on its own terms: the `Edit`/`Write` payload carries a path and content, not "this applies a reviewer finding." One nuance has changed — #723 named "applying a review finding" as a *false positive* a nudge hook would fire on, and after this plan it is a true positive — but the remaining false positives (plan-file edits, PR-body drafts, reply bodies, DEFER persistence) are unchanged, and a far more precise trigger point exists: the session is already *inside* the disposition step when the decision is made.

That precision is what the mechanism exploits. Rather than a third bare prose pointer, the route is folded into the artifact each skill already emits — `code-review`'s ADDRESS/DEFER disposition output gains a `Fix route:` line, mirroring the existing `Spawn decisions:` line whose stated purpose is that "empty rationale is the under-spawn failure mode this format closes; visible rationale is reviewable" (`code-review/SKILL.md:228`). One line per round, not a per-row column, so it matches the round-as-unit choice instead of re-inviting per-finding cherry-picking. It also leaves a greppable text signal, which the next remeasurement needs and which section C conspicuously lacked (it had to infer from tool-call adjacency and a nearest-preceding-`Skill` heuristic, by its own caveats).

`respond-pr` is in scope: its `FIXED` classification is by construction the already-decided subset — a comment only lands there after step 5 assigns `disposition` and `rationale`, with everything ambiguous routed to `EXPLAIN-DESIGN` / `OUT-OF-SCOPE` / `DEFERRED` / `AGREE-NO-CHANGE`, which produce no code at all — so excluding the one arm whose specification is *cleanest* would be exactly the narrow scoping CLAUDE.md's audit-structural-siblings rule bars.

### Assumption ledger

**Root problem:** the fix that follows reviewer feedback is applied by the main thread inline, so it receives no `staff-*`-angle self-review before the parent's own re-review gate, and its read-and-edit load accumulates in parent context across many findings — because no site states who applies an ADDRESS/`FIXED` fix or how.

**Givens:**

- **G1 — `Edit`/`Write` payloads carry a path and content, not a semantic label for edit-kind.** Beyond reach: this is a property of the harness tool schema, owned by Anthropic, and nothing in this repo changes it. It is the same given #723 recorded.
- **G2 — `code-writer` does not commit, push, stage, or open PRs, cannot run review skills, and is denied marker writes.** In reach (the agent's own charter file is editable in this repo) but deliberately unchanged — recorded in **Out of scope**, not treated as beyond-reach; kept here only as the fact that sets what the parent must keep (the commit, the `/skill-review` run, the marker).

**M1 — `subagent-delegation`: state the rule once.** `anchors: root, row1, row2, row4, row5`. Single source of truth, and the file already owns the delegate-vs-inline decision, so M2–M4 point rather than restate. Must say explicitly that condition (2) is not the basis, or a later reader will "correct" the rule back to the two-condition test. *Lighter primitives rejected:* (a) extending the existing approved-plan paragraph instead of adding a sibling — rejected, that paragraph reserves "applying a correction whose content is already decided" to the parent, so folding this in silently would leave the file self-contradictory; the new paragraph must instead narrow that clause to the parent's own line-by-line read of a returned diff, distinct from a dispositioned finding set; (b) relying on the existing two-condition test unchanged — rejected per row 1, condition (2) fails on the common single-finding case, so the general test returns "stays inline."

**M2 — `code-review` Finding disposition: route plus a `Fix route:` line.** `anchors: row2, row3, row11`. The ADDRESS rows *are* the dispatch spec (row 2), so the marginal cost is near zero; the emitted line makes the skip auditable, including by `skill-fidelity-reviewer`. *Lighter primitives rejected:* (a) a bare prose pointer with no artifact (#723's mechanism) — leaves the next remeasurement on the same tool-call-adjacency heuristics section C's own caveats flag as weak; (b) a `Fix route` column on the disposition table — rejected, per-row routing re-invites the per-finding cherry-picking the round-as-unit choice exists to close; (c) a `handoff`-style pre-write checklist item — neither `code-review` nor `respond-pr` has a checklist, so this invents new structure in two files to carry one line. *Heavier alternative rejected:* a `PreToolUse` nudge or deny hook — G1 stands, and row 10 shows #723's own stated trigger for reconsidering it has not actually fired.

**M3 — `ready-for-review` steps 3 and 4: zero-net-line pointer.** `anchors: root, row8`. This is the most inline-skewed origin in section C (82% / 7%) and simultaneously the one file with no line budget (row 8), so both additions are paid for by rewrapping the sentences they attach to. Step 4 needs its own clause because its findings come from `skill-fidelity-reviewer`, not from a `/code-review` disposition table, and are often fixed by stating a rationale — prose, not code. *Lighter primitive rejected:* pointing only from step 3 and letting step 4 inherit — rejected, step 4 produces no ADDRESS rows, so nothing there would carry the route.

**M4 — `respond-pr` step 6: one dispatch for the batch.** `anchors: row6, row7`. Structural sibling with the cleanest specification of the three (row 6), and row 7 independently argues for the batch unit. *Lighter primitive rejected:* leaving `respond-pr` to a follow-up — rejected under CLAUDE.md's audit-structural-siblings rule; the identical bug shape in a third arm with the same one-line fix is not a separate ticket.

**M5 — `docs/design-decisions.md` §11: a second dated annotation.** `anchors: row10, row13`. The existing 2026-08-21 paragraph names "fixing a diff" as an example of a *legitimate* inline edit a hard deny cannot distinguish; after this change that example is itself a delegated-by-default case, so leaving it unqualified makes §11 self-contradictory. The new paragraph supersedes that one example explicitly rather than rewriting a dated record (CLAUDE.md scope Axis 3). It must also correct the remeasurement framing per row 10, so the next reader does not cite a rolling-window number as evidence about #723.

**No `CLAUDE.md` edit.** Row 13 — the existing pointer already routes the delegate-or-not call to `subagent-delegation`, which is where both defaults now live. Zero net lines answers the engineer's standing bloat concern.

**Dispatch split: one `code-writer` dispatch for all five files.** M2–M5 are pointers to and documentation of M1's canonical wording, so splitting would require restating M1's content in every prompt — the case `plan-it` Step 5 names as a do-not-split. The parent runs `/skill-review` afterward (G2).

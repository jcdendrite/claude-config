# Did moving the handoff hard block from a re-arm count to an absolute token position cut cost?

## Context

The goal is to determine whether replacing the count-based handoff hard-block (`HANDOFF_NUDGE_BLOCK_AFTER`, tightened in PR #708 to fire after 1 ignored re-arm) with an absolute-token hard block (`HANDOFF_NUDGE_BLOCK_AT`, default 470000) — merged in PR #782 on 2026-08-31 12:06:15 -0700 — has reduced overall handoff-related cost since it shipped. This is a follow-up to the existing `docs/case-studies/handoff-threshold-impact.md` case study, which evaluated a different, earlier mechanism change (the advisory-nudge absolute cap drop from 360,000 to 150,000 in PR #727, plus the BLOCK_AFTER count tightening in PR #708) using a four-tier before/after instrument battery — but that study was captured 2026-08-28/29, before PR #782 merged, so it does not cover the count→absolute hard-block switch. It's now about a week after PR #782 shipped (today: 2026-09-06), and the engineer has plenty of local corpus plus a second machine's corpus reachable via a peer Claude Code session on that machine.

Scope decisions confirmed by the engineer: full case-study rigor (mirroring the precedent's four-tier methodology, confounds section, statistical framing, and publication-scope discipline), proceeding now rather than waiting for more after-era data, with the second machine's corpus folded in via cross-session coordination rather than direct file access.

## Approach

Design the study as a **matched counterpart to the precedent**, not a copy of it. `handoff-threshold-impact.md` measured a *tightening* (advisory cap 360,000 → 150,000) and found "gate tighter, overhead grew." PR #782 moves the same subsystem in the opposite direction at a different lever: it replaces a count-based hard block whose effective floor sat at **230,000 tokens** with a flat **470,000-token** position, and makes the block unreachable on 200k-window models entirely. So this study's question is not "did a tighter gate save money" but "did *loosening* the forced-handoff gate give back the overhead the precedent measured, and did the deep-context tail eat the savings." Two consequences follow, and they are the plan's two real design calls: **Tier 0 is rebuilt on hard-block position/rate** (`spend-over-threshold` has no `BLOCK_AT` term and cannot be a mechanism-engagement gate for this change — it demotes to a Tier 3 mediator arm with a *reversed* expected direction), and **era attribution for `.handoff-nudge.log` lines uses block-time, not session-start**, because the blocking population is by construction long sessions and the two eras are one week apart.

### The mechanism, re-derived

The pre-782 block floor is arithmetic, not an assumption, and it validates twice against independent statements:

- Regime live 2026-08-24..08-30: `ABS_CAP=150000`, `REARM_SPACING=80000`, `BLOCK_AFTER=1`. Fire 1 at ≥150,000 (1M-window) with ignored counter 0; fire 2 at ≥230,000 with counter 1 → block. Floor **230,000** (1M-window) / **160,000** (200k-window).
- Validation A: the same arithmetic under the pre-#727 cap of 360,000 at `BLOCK_AFTER=3` gives 360,000 + 3×80,000 = **600,000** — the exact figure the PR #708 commit message states.
- Validation B: `docs/handoff-nudge.md:26` says 470,000 sits "past a session's fifth crossing under today's shipped 150000 cap and 80000 spacing" — 150k → 230k → 310k → 390k → 470k is the fifth crossing. The same model reproduces the doc's own claim.

**PR #782 therefore raised the hard-block floor by ~240,000 tokens and inserted three additional advisory re-arms ahead of it.** The expected directions this study tests: `action=block` rate collapses (Tier 0), forced-handoff overhead falls (Tier 3 arm A), deep-tail spend past the unchanged 150,000 advisory threshold rises (Tier 3 arm B), and Tier 1 lands somewhere between.

### Pre-registered decision rule (fixed before any number is pulled)

Tier 0 confirming the block point moved is **expected by construction and carries no cost verdict.** Given that confirmation:

- **Reversal candidate (deep-tail dominance).** Trigger if *either*: the after-era Tier 1 median exceeds the before-era interquartile range's upper bound (the precedent's own rule, reused verbatim at `handoff-threshold-impact.md:79` so the two studies stay comparable); **or** both Tier 2 instruments decline in the same direction — reviewer-spawn intensity per branch falls *and* user-facing-friction events per branch rise. Either fires, and the report names `HANDOFF_NUDGE_BLOCK_AT=470000` a candidate for lowering.
- **Clean win.** Tier 1's after-era median is at or below the before-era median, Tier 3 arm A (sessions-per-branch, startup-burn share) falls, and Tier 2 shows no decline.
- **Real trade** (the predicted outcome). Arm A falls, arm B (`spend-over-threshold` share) rises, Tier 1's median stays inside the before-era IQR. Reported as a trade, not a win.
- **Falsification test, pre-registered.** If Tier 0 confirms hard blocks collapsed but Tier 3 arm A does *not* fall, then hard blocks were never a material driver of handoff volume. That is a publishable negative finding on its own terms: it would mean `HANDOFF_NUDGE_BLOCK_AT`'s value is neither helping nor hurting at this corpus's session shapes, and `docs/handoff-nudge.md:32`'s revisit trigger should be relaxed rather than tightened.
- **Small-n ladder for Tier 1** (row 14 makes this likely to bind). After-era captured n ≥ 10 → mean/median/IQR as the precedent reports. 3 ≤ n < 10 → raw per-PR values plus a point delta on the median, labelled directional-not-decisive, **no percentage headline** (this repo's existing floor, `handoff-threshold-impact.md:137`). n < 3 → report the count, decline a Tier 1 verdict entirely, and rest the study's verdict on Tiers 0 and 3 with "primary outcome not measurable at this elapsed time" stated in the short answer, not buried.
- **Peer-data fallback.** If the peer reply does not arrive, is unusable (stale checkout per row 12), shows a late deploy (row 7), **or contributes a negligible share of a pooled bucket's n** (e.g. Machine A n=9, peer n=1, both clearing the small-n ladder's n≥10 total only in combination), the study ships single-installation with that stated as a scope limit. Pre-registered here so it is not a post-hoc convenience. Whenever a figure is presented as "pooled," the doc states each side's share of *n* (count only, never values) alongside it, so a lopsided split reads as what it is rather than as genuinely joint data.

### Sensitivity arm

The precedent's sensitivity arm narrowed its before era, which spanned four threshold regimes. This before era is one ISO week under one regime, so that arm buys nothing. **Substitute an attribution-method sensitivity arm instead:** report Tier 0 under both era-attribution rules (block-time per row 8, and session-first-timestamp per the precedent) and show the verdict does not flip. That targets this study's actual robustness risk rather than importing the precedent's.

### Sequencing

Do **not** block the whole doc on the peer reply. Machine A alone has 375 after-era sessions (measured this session), which powers Tier 0 without pooling. Draft against machine A first with every table shaped to accept a pooled column, then fold the peer's numbers in. The one hard constraint: the pre-registered rule above must be committed **in this plan file** before machine A's numbers are pulled — writing it into the doc after the first capture is not pre-registration.

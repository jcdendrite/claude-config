# Handoff-nudge threshold/block impact analysis

## Context

The user wants to know, across all PRs and all Claude Code accounts on this
machine, whether pushing the handoff-block escalation (PR #691, tightened in
PR #708) and lowering the handoff-nudge absolute-token cap from 360,000 to
150,000 (PR #727) actually reduced dollar/token cost and whether it preserved
or improved review quality — using review-round counts and reviewer-findings
counts as the quality proxy. This is being asked now because both changes have
been live long enough to form an initial read, but the mechanism itself has
kept moving (five distinct threshold/block revisions between 2026-05-26 and
2026-08-23), so no single clean before/after comparison has ever been run
against the current settled state. The intended outcome is a precise,
evidence-grounded verdict — not a redesign of the mechanism — reporting actual
$/token deltas and quality-proxy deltas between a defined "before" era and the
current "after" era, with sample sizes and confidence stated honestly rather
than glossed over.

## Approach

Run a fixed, date-bounded instrument battery across all six declared accounts and report **share of spend earned above the nudge's own fire threshold** as the primary cost metric — it is the one quantity the mechanism acts on directly — with `$`/tokens per merged PR from the durable `pr-cost` ledger as a deliberately-labelled confounded secondary; pair those with review-round, hook-denial, and reviewer-findings counts for quality, verify the treatment actually fired before interpreting any delta, and publish the result as a case study. One CLI change ships with it: `reviewer-yield` gains an absolute `--until DATE`, because it is the only instrument in the battery that cannot currently be bounded to a fixed historical window.

**Root problem.** Two threshold/block changes (PR #691 → #708 hard-block escalation, PR #727 cap 360,000→150,000) shipped on cost-and-quality reasoning that was never re-measured after the fact; `docs/handoff-nudge.md`'s Known-limitations bullet records that gap in the repo itself. This plan produces the measurement that closes it, at the precision the data actually supports.

### Mechanisms

- **Primary cost metric: `spend-over-threshold`, run twice.** `--since 2026-08-23` yields the after era exactly (session first-timestamp filter, so its W34 row contains Aug 23 alone); an unfiltered run's weekly rows sum to the before era for weeks ≤ 2026-W33. Both runs print raw above-$ and total-$ per week, so the era share is recomputed from summed raws, never from averaged percentages. *Justification: it isolates the quantity the hook acts on — spend earned past the fire threshold — so it moves for mechanism reasons where total spend moves for any reason.* `anchors: root`, `anchors: G4`
- **Secondary cost metric: the `pr-cost` ledger, tokens first.** Report per-class **token** counts per PR as the headline (rate-invariant), and dollars only after confirming a single `rate_stamp` across compared rows; if stamps differ, re-derive dollars from token columns under one table. Report median and IQR alongside the mean, and list the after-era per-PR values individually. *Justification: G1 makes dollars conditional and tokens unconditional; at single-digit n a mean is dominated by one PR, so the values themselves are the honest presentation.* `anchors: G1`, `anchors: A15`
- **Corroborating series: `cost-trend`.** Weeks ≤ W33 as before, W35+ as after, with the after window explicitly one day narrower than the exact-date instruments (A9). Era-level Opus% and ≥200k% are recovered as `Σ(pct_w × $_w) / Σ$_w`, with the printed-percentage rounding error stated. *Justification: the only instrument giving a *shape* of spend over time, which is what distinguishes a step change at the era boundary from a pre-existing trend.* `anchors: A8`, `anchors: A9`
- **Rounds: one `review-trace` scan per era, `--this-repo`, counted not read.** `--since`/`--until` bound each era exactly; each event line carries its own `(branch=…)`, so a single scan per era yields all (branch, skill) pairs — redirect once to a temp file outside the repo, then count per skill. *Justification: `--skill` takes one value from a six-name set, so filtering in-tool would cost three corpus scans per era instead of one.* `anchors: A6`
- **Denial friction: `review-trace --deny-summary`, date-bounded per era.** Grouped counts only, no per-session listing. *Justification: it is the one review-trace mode whose output carries no transcript path.* `anchors: A6`
- **Findings: `reviewer-yield` run three times — `--until 2026-08-16`, `--until 2026-08-22`, unbounded — and differenced, all three runs with `--this-repo`.** Table-1 columns are additive counts, so before / transition / after fall out exactly, with every bound an absolute date. Report findings only as an era-level aggregate normalized by that era's merged-PR count. `--this-repo` on every run is not optional: the merged-PR denominator is `claude-config`-only by G3, and `reviewer-yield` is machine-wide by default (A12) — an unscoped numerator over that denominator is a cross-scope ratio, not a directional approximation. **Do not** claim a per-PR findings figure regardless of scope. *Justification: `reviewer-yield` has no `--branches` and the join would need per-record branch attribution the module doesn't carry — the era ratio, correctly scoped, answers the question without it.* `anchors: A5`, `anchors: G5`, `anchors: G3`
- **Treatment-applied check: count `action=block` and `handoff session=` lines in each account's `.handoff-nudge.log`.** If zero hard blocks are attributable to after-era sessions, the report says so and reframes the after era as cap-only. *Justification: `docs/handoff-nudge.md`'s own Known-limitations bullet names exactly this log signal as the way to detect that the block never fired; interpreting a cost delta without it would attribute an effect to a mechanism that never ran.* `anchors: root`, `anchors: A11`

**The one code change, and the lighter primitives rejected for it.** `reviewer-yield` gains `--until DATE` (inclusive, mirroring `review-trace`'s semantics), wired to the `until_ts` parameter `compute_reviewer_yield_data` already accepts. `--since` keeps its existing `Nd` contract untouched — three runs plus differencing cover all three buckets without it. Lighter alternatives weighed and set aside: (1) **relative `--since Nd` differencing with fractional days** — arithmetically valid, but the window is defined by the invocation instant (`scope.py:674`, `time.time() − days*86400`), so a published figure is not reproducible and a re-run silently measures a different window; (2) **`cost-ledger --record`'s per-week windowing** — `--record` appends only the current ISO week and needs a sentinel plus a durable write, so it cannot produce a historical era row at all `[verified: transcript-analysis.py:6354-6373 read mode lists week *labels* only; :10853-10856]`; (3) **post-filtering `reviewer-yield` output** — impossible, the output is pre-aggregated with no per-dispatch timestamps; (4) **a throwaway local script calling `compute_reviewer_yield_data(until_ts=…)` directly** — genuinely lighter, but the case study's figures must be re-derivable from a committed subcommand by any stow consumer and by the revisit trigger's future re-run. Heavier alternative also rejected: adding `--branches` to `reviewer-yield`.

**Extract before adding the fourth copy.** The six-line inclusive-day conversion is already duplicated at three production sites — `transcript-analysis.py:519-526` (`cmd_user_input`), `:1751-1757` (`cmd_review_trace`), `:1856-1863` (`cmd_judgment_pair`) — plus a test helper at `tests/test_transcript_analysis.py:2229-2234`. Adding a fourth is the locally-valid patch CLAUDE.md's "abstract into a shared helper once two or more share it" rule fires on. Extract `_parse_absolute_window_args(args, subcommand) -> (since_ts, until_epoch)` into `transcript_analysis/scope.py` beside its exact sibling `_parse_since_nd_arg` (`scope.py:661`) — `scope.py` already imports from `transcript_analysis.corpus` at line 32, so pulling `_parse_ts` in adds no cycle — and route all three existing sites plus the new one through it. Pure extraction, no behavior change.

**The cross-account reach gap, stated not silently narrowed.** G3 means the per-PR arm covers **claude-config's own PR history across all six accounts**, not each account's separate private-project repos — this session holds neither their paths nor their credentials. The session-level arm has no such limit: A12's root union plus the default `--projects *` scope already spans every repo on every declared account, and the hook itself is machine-global. So the honest framing is: *aggregate spend movement is measured machine-wide; the per-PR denominator is claude-config-only.* Extending the per-PR arm later needs one `cd <repo> && direnv exec . python3 …/transcript-analysis.py pr-cost --record …` per repo under that account's own credentials (`CLAUDE.local.md`'s cross-account pattern) — recorded as a named follow-up, not attempted here.

**Publication scope.** Both arms are committed (A17), so the primary cost metric — which is machine-wide by construction — ships as a figure rather than as an in-session-only number. Aggregation across all six accounts, not repo-scoping, is what makes a figure publishable, so the derivation discipline for every machine-wide number is *sum first, publish second*: the per-account `.handoff-nudge.log` block counts, the per-root retention floors, and the Phase 0 root census all arrive per-account and are collapsed to a single figure before any of them reaches the draft. Because the report now mixes scopes across metrics, every committed figure names its own scope in situ, and no ratio divides a figure of one scope by a figure of the other — where a denominator is claude-config-only by G3 (anything per-merged-PR, including the findings ratio), its numerator is produced with `--this-repo` as well (A12, and see the Findings mechanism above); everywhere else both sides are machine-wide.

**Statistical framing.** Report raw counts everywhere (PRs, sessions, dispatches, denials per bucket) alongside every ratio, and the *observed* date window per bucket rather than the nominal one. Adopt A13's floor: any bucket whose denominator is under 10 is reported as raw values plus a point delta labelled **directional, not decisive** — no percentage headline, no confidence interval, no p-value, no bootstrap (the repo's bootstrap precedent in `opus-plan-boundary-handoff.md` ran 2,000 session-level resamples on a large arm; at single-digit n it manufactures precision). Every ratio prints its numerator and denominator. Close with a **numeric revisit trigger** — a stated after-era PR count at which the battery is re-run — matching the convention the case-study index already uses.

**Confounds the report must name explicitly, in this order:** (1) G4 co-intervention, the dominant threat; (2) G2's retention floor, measured not assumed; (3) A10's as-of window, held uniform across eras so the after arm isn't flattered by early capture; (4) within-era heterogeneity — the before era spans four threshold regimes (flat 120,000 → 60% → 40% → 40%∧360,000), so it is a *no-hard-block* baseline, not a *360,000-cap* baseline; a secondary sensitivity arm restricted to 2026-08-08..2026-08-16 gives the true immediately-prior comparison; (5) A9's one-day granularity mismatch; (6) volume — era totals are not comparable, only per-PR / per-session / per-priced-turn normalizations are.

### Phases and dispatch split

- **Phase 0 — Preconditions census (read-only).** Measure, don't assume: resolved root count and each root's oldest surviving transcript (the before-era floor); the existing ledgers' `machine` label and the set of `rate_stamp` values; whether `PR_COST_LEDGER_PATH` or `GH_REPO` is set (both would break Phase 2); which accounts hold `.pr-cost-enabled`, and the resolved `~/.local/state/claude-accounts/<account>/` config-dir path for each of the 3 that don't yet, so Phase 2 has the exact sentinel target per account; per bucket (before/excluded/after), how many of the 6 accounts hold at least one contributing session or ledger row, flagging any bucket at 1 contributing account (A17's aggregation floor) or fewer than 10 (A13's volume floor); total session and file count across the 6-account union, as a rough duration signal for how long Phase 3's battery will take. Output: the exact before-era start date every later command uses. **Not this phase:** A14's cross-account duplicate-`pr_number` check — Phase 2's backfill is the mutation that could introduce the duplicate, so that check runs after Phase 2, not before it.
- **Phase 1 — CLI change.** One `code-writer` dispatch (`model: sonnet`). Extraction + new flag + tests + doc. Must land before Phase 3 consumes it.
- **Phase 2 — pr-cost enablement and capture.** Create `.pr-cost-enabled` as a **regular file per account, never a symlink** to another account's (a symlinked sentinel silently opts both accounts in, `docs/pr-cost.md:84`), at each of the 3 config-dir paths Phase 0 resolved. Then run `pr-cost --all-accounts` in **read mode first** — its uncaptured-PR listing is the preview — and only after the operator has seen that listing run `--record --all-accounts --machine-label <the label already in the ledger>`. Reusing the existing label matters: the ledger key is `(host, repo, pr_number, machine)`, so a new label appends parallel rows rather than colliding. **A per-account ledger-parse failure (`_PrCostLedgerParseError`) aborts the whole `--all-accounts` loop via `sys.exit(1)`, even though rows already recorded before the failing account persist:** treat a nonzero exit code as the retry signal — re-run the identical command, which recovers idempotently against the rows already written. **Do not** use the run's printed `recorded X of N` summary as a completeness check: it counts only rows newly written in that invocation, not cumulative ledger state, so it legitimately reads below 6 on a fully-recovered ledger once earlier accounts' rows are already present and skipped. The completeness signal is the one already named in Verification: the read-mode preview's uncaptured-PR listing must go empty (or contain only rows explicitly deferred), not this summary line. **A `degraded_*`-status row (absent gh-sourced columns) is resolved here, as part of the run, not deferred to Verification:** recapture it with `--force --pr N`, or exclude it and record the exclusion in Phase 4's raw counts. **Accepted cost, not a bug:** if A14 turns out true, `gh pr view` enrichment re-fetches a shared PR once per contributing account — unbudgeted but bounded by pr-cost's existing backoff. **After the backfill completes across all 6 accounts, check A14 empirically** — whether any `pr_number` appears in more than one account's ledger; a pre-backfill check would be a false negative. Not a code-writer dispatch — durable writes plus live `gh` calls stay in the operator-visible session.
- **Phase 3 — Instrument battery.** Deterministic command list, all runs back-to-back in one sitting so every instrument sees the same corpus. **Pause other Claude Code activity on all 6 accounts for the battery's duration** — corpus growth mid-battery breaks the corpus-stability check in Verification and forces redoing the whole battery; Phase 0's session/file count signal estimates how long that window needs to be. Each command is a single Bash statement; where output must be counted rather than read, redirect once to a temp path outside the repo and count in a second call. Before trusting the `reviewer-yield` differencing, count dispatch records with a missing or unparseable timestamp: `compute_reviewer_yield_data` only filters a record when a bound is actually passed (`reviewer_yield.py:462-469`), so an untimestamped dispatch is silently counted in the unbounded run and excluded from every bounded run — a real risk to the differencing, not just a test gap. Capture the raw pass/fail number for each of the six internal-consistency checks (Verification, below) into the same temp path as the counted output, rather than reading them off the terminal and discarding them — Phase 4 cites them. No new script under `~/.claude/scripts/` — that is the over-powered primitive for a one-time battery.
- **Phase 4 — Author the artifacts.** Kept in the session that holds the measurement output; not split across dispatches, since every dispatch would need the same measurement context restated and could reach a different verdict on the same numbers.

# Worktree lock self-recognition across `/clear`

## Context

Goal: stop the worktree collision guard from denying a session's writes into a worktree whose lock it acquired itself before a `/clear`, without letting two live processes hold one worktree.

Ask: "I think this points to another bug in the system in how the clear thing works. When I worked on the resume handoff changes, it said it was compatible with the PID stuff, but it looks like the work tree lock thing is an oversight." and "can you pivot towards planning that bug fix". On design: "checking the PID seems good enough, but it almost strikes me as, like, too simple. I wonder if there's a catch there." and "it seems like you figured out the problem with using the PID, but the solution seems over-engineered."; the selected labels "Yes, plan F (Recommended)" and "Adopt process-first (Recommended)"; and "I don't think we should increase the scope to this PR aggregate."

After `/clear`, the harness issues a new `session_id` inside the same Claude Code process (same pid). The lock file `<git-dir>/locked` still carries the pre-`/clear` `session_id` plus this process's own live pid. `_lib_worktree_collision_guard` fails its `session_id` self-check, falls through, and `kill -0 <own pid>` succeeds. The guard then prints "this worktree is already in use by a live Claude Code session (pid N)" naming the session's own pid.

Why now: the same-session `/clear` + `/resume-context` flow shipped in #1303 makes `/clear` mid-worktree routine. A session that cannot write into its own worktree is stuck, because `EnterWorktree` errors when the path is the cwd. #1303's pid-compatibility claims covered only `sessions/<PID>`, active markers, and nudge state, not the worktree lock.

Intended outcome: a session recognises its own lock across `/clear` with a regression test, a lock held by another live Claude Code process is still denied, and `--continue`/`--resume` self-recognition still works when the old process is gone.

## Approach

A worktree lock is the caller's own when it records the caller's own pid, because `/clear` keeps the process and so the pid is the identity that survives it. A lock from another pid is the caller's own only when it carries the caller's session_id (a `--continue`/`--resume`) and the old pid is not a live Claude Code process. One shared read-only predicate replaces the guard's two identical self-check blocks. Nothing new is persisted, the guard writes nothing new, and `capture-session-id.sh` is unchanged.

**The rule** (`_lib_worktree_lock_is_mine`, new in `claude/.claude/hooks/_lib.sh`):

```bash
_lib_worktree_lock_is_mine() {
  local locked_pid="$1" locked_session_id="$2" my_pid="$3" my_session_id="$4"
  local config_dir
  [[ -n "$locked_pid" && -n "$my_pid" ]] || return 1
  [[ "$locked_pid" == "$my_pid" ]] && return 0
  [[ -n "$locked_session_id" && "$locked_session_id" == "$my_session_id" ]] || return 1
  config_dir=$(_lib_config_dir) || return 1
  _lib_registered_live_sid "$config_dir" "$locked_pid" >/dev/null && return 1
  return 0
}
```

- **Pid arm.** The same process owns the lock whatever its current session_id. It covers `/clear`, `/compact`, and parallel subagents, which run inside the parent's process. It also absorbs today's old-format fallback, which compared pids already.
- **Session arm.** A lock from another pid with the caller's session_id is a resume. It stays the caller's when the old pid is dead, has no registry entry, has a stale start time, or the registry read cannot confirm it. A live, start-time-valid, registered Claude Code process at the old pid makes it "not mine", whatever session that process runs. The guard then falls through to its `kill -0` path and denies naming that pid.
- **Empty-pid guard.** An empty pid on either side is never the caller's. The guard cannot reach it, because `_lib_worktree_lock_pid` returns state 0 only for a `[0-9]+` pid and the resolver prints a pid only when non-empty. It protects direct callers. The old-format fallback treated two empty pids as equal (`_lib.sh:3281`), and the predicate now returns 1 there, in the fail-closed direction.
- **Config-dir failure.** A `_lib_config_dir` failure returns "not mine". It is unreachable through the guard, because `_lib_resolve_claude_pid` resolved the same config dir earlier (`_lib.sh:2983`). A direct predicate test pins it.
- **Registry-read polarity.** `_lib_registered_live_sid` returns 1 for every case it cannot confirm, so the session arm reads each as "mine" (the merge-base outcome for a resumed session).

`_lib_registered_live_sid CONFIG_DIR PID` is the registry validation at `_lib.sh:2988-2999`, extracted. It reads `sessions/<pid>`, requires both lines non-empty, and compares `TZ=UTC LC_ALL=C ps -o lstart=` against line 2, keeping the `_lib_capped ps ... -p` call as it is. On a match it prints the session_id and returns 0. Otherwise it prints nothing and returns 1. The predicate discards the printed id. `_lib_resolve_claude_pid`'s loop calls the helper with byte-identical output.

The first-read block (`_lib.sh:3278-3284`) and the contention-reread block (`_lib.sh:3317-3323`) each become `if [ "$state" -eq 0 ] && _lib_worktree_lock_is_mine "$locked_pid" "$locked_session_id" "$my_pid" "$my_session_id"; then return 0; fi`.

The sibling-arm audit found a third lock-identity comparison, acquire-verify (`_lib.sh:3117-3123`). It stays exact, because it confirms the caller's own just-written content and does not decide whether someone else's lock is the caller's. The reclaim content check (`_lib.sh:3148-3152`) is a byte-exact compare against a diagnosed-dead identity and stays exact too.

**Behavior against the merge-base.** S = session_id, N/M = pid, W = the worktree.
- Lock `pid N session S1`, caller (N, S2) after `/clear`: denied before, allowed after, lock untouched. This is the fix.
- Resumed S1@M, N dead, unregistered, or with a stale start time: allowed before and after.
- Resumed S1@M, N live and registered (to S1, to S2 after a `/clear`, or to an unrelated Claude Code process that reused N's pid): allowed before, denied after, naming N. See the over-deny residual.
- Foreign live, foreign dead (reclaim), old-format foreign, unparseable, and truncated locks: unchanged. A lock the regex at `_lib.sh:3061` rejects is `state` 2 and never reaches the predicate. A truncation the regex still accepts (cut inside the pid digits or the session id) is a parsed lock covered by the other rows.
- Caller whose pid equals the lock's pid while carrying another session_id, from pid reuse, a different PID namespace, or the caller's own lock write cut off inside the session id: denied before, allowed after. The first two are the false-allow residuals. The third is the caller's own lock, recognized correctly.
- No input newly reaches the reclaim path, except one: the registered pid exits between the predicate's `ps` and the guard's `kill -0`. That input is allowed before and after, and one claim file is burnt.

**Two-writer closure.** S1 locks W in process N and `/clear` gives S2@N. S2@N writes W, allowed by the pid arm. `claude --resume S1` then starts M, and S1@M is denied because N is live and registered. In the other order, S1@M writes first only while N is not a live registered process, so S2@N cannot exist yet. While the lock's pid is a live process registered under the caller's own config dir, only that process writes. The closure holds when the registry read succeeds (see the incomplete-read residual) and one config dir serves the worktree (decision 6). Once the lock's pid is not live, every process carrying the lock's session_id passes (see the reclaim residual).

**Residuals.** Each is one input sequence. This section is the design record, and the known-gaps bullets in `_lib.sh` are their durable home. Every other site points to one of the two. In each, the newly affected process is named.
- **Over-deny (allowed to denied).** A resumed conversation is denied while the lock's old pid is a live Claude Code process, whatever session it runs. It has three shapes. The old process was cleared and still runs. The old process still runs the same conversation. The old process exited and an unrelated Claude Code process now holds its pid, which needs no `/clear` and no write by that process. The third shape is most likely after a reboot, because pids restart low and the lock survives in the git-dir (`post-crash-sessions.py:53-55`). The deny clears once that pid is gone from the process table, which an exited but unreaped process is not, or when someone runs `git worktree unlock W`, which is safe only after confirming no live process is working in W. The live-holder text stays unchanged. It is accurate for the first two shapes and inexact for the third, where it names a process that never held W. Advising unlock inside it would hand W to a second writer while a live process still holds it, and a case-specific message would turn the predicate into a three-way result for rare shapes.
- **Pid reuse (denied to allowed).** S0@N0 locks W and N0 exits. `claude --resume S0` starts M, and S0@M writes W (allowed; the lock names dead N0). The OS reissues N0 to a new Claude Code process running S9, which writes W and is allowed by the pid arm. It can clobber S0's uncommitted work. The lock records no process start time, and `sessions/<pid>` is rewritten at every SessionStart, so no single-pid read of the lock text or `sessions/<pid>` tells "this process locked before `/clear`" from "an earlier process with this pid locked". Closing it takes one of three options. The first is a lock-format change that carries the holder's start time. The second is a `sessions/*` scan in the pid arm, which denies both processes in the two-writer sequence above. The third is an elapsed-time comparison of the process against the lock file's age, which is untraced and unverified on BSD.
- **Equal pids across PID namespaces (denied to allowed).** Two live Claude Code processes in different PID namespaces share one worktree directory and hold the same pid. The pid arm treats the other namespace's lock as the caller's own. The guard assumes one PID namespace per worktree. Merge-base denied this input only because `kill -0` succeeds in the caller's own namespace.
- **Incomplete registry read (conditional).** `ps` fails or times out, or `sessions/N` is read between N's own truncate and write. A third trigger is a live holder whose recorded start time no longer equals the current `ps -o lstart=` output, for example after a wall-clock step, which the session arm also reads as "mine". [unverified: the derivation of `lstart` was not traced, so this trigger is not confirmed.] The session arm then reads "mine" for a resumed S1@M while N is live. S1@M is then at merge-base parity, and the newly allowed process is S2@N, which the pid arm allows unconditionally, so both can write. The first two triggers need a transient failure at the moment S1@M's call reaches the guard. Under the third trigger, N's own calls fail the same start-time check inside `_lib_resolve_claude_pid` (`_lib.sh:2988-2999`, the check the extracted helper keeps), and the guard denies them ("could not resolve this session's own process identity", `_lib.sh:3258-3261`) until N's next SessionStart or SubagentStart rewrites `sessions/N` with a fresh start time (`capture-session-id.sh:96`). S1@M writes W in that window, and after the rewrite the pid arm lets S2@N in, so S2@N can overwrite S1@M's uncommitted work.
- **Reclaim of a resumed session's worktree (pre-existing, unchanged).** S1@N locks W and N exits. A resume starts S1@M and writes W (allowed; the lock names dead N). A third session S3 then writes W, `kill -0 N` fails, and the guard reclaims at `_lib.sh:3335`, so S3 takes W while S1@M works there. Two resumes of S1 started after N exits (for example from a crash-recovery listing) both pass the session arm on every call, because nothing re-stamps the lock. A resumed S1@M that then runs `/clear` becomes (M, S2) and matches the lock by neither pid nor session, so the guard falls to `kill -0 N`: a dead N is reclaimed (one claim file burnt), and a live N that was not a registered Claude process denies S2@M with the live-holder text, cleared by `git worktree unlock W` after confirming no live process works in W. The shapes are at merge-base parity and share the cause that a session-arm hit never re-stamps. See Out of scope.

**Alternatives set aside.**
- **Pid equality alone** (pid arm plus today's unchanged session arm). Ordering the two-writer closure's sequence the other way allows both S2@N and S1@M, and the same holds after pid reuse by a Claude process. Merge-base denied one of them, so it is a regression under docs/hooks.md:26.
- **Session arm that reads registry session equality** (deny only when the old pid is registered to a different session). It leaves two live processes on one conversation allowed, and the cleared-process takeover with it. The engineer chose to deny whenever the old pid is a live registered process.
- **`kill -0` on the old pid in the session arm.** It denies a resumed session whose old pid was reused by an unrelated non-Claude process, and flips `test_resumed_session_reused_live_pid_self_recognized_via_session_id` (test_lib_worktree_collision_guard.py:751). The registry tells "a live Claude process" apart from "some live process".
- **Re-stamping the lock in the guard on a pid-arm hit.** The git-writes fast path hands every git command, reads included, to the guard once the lock exists (`require-worktree-for-git-writes.sh:257-271`). A re-stamp would turn the first-write-wins tiebreak (`docs/design-decisions/worktree-lock-fast-path.md:7`) into first-touch-wins.
- **Re-stamping from `capture-session-id.sh` on `SessionStart` with source `clear`.** It writes where a read suffices, runs in an informational fail-open hook (`capture-session-id.sh:2`, `:29-36`), cannot find locks in a second repo the session wrote into, and reverses the cohesion reason at `docs/design-decisions/worktree-lock-session-id.md:9`.
- **Registry-based session liveness in place of `kill -0`.** After `/clear` no process runs S1, so a foreign session could reclaim a live process's worktree. That outcome is irreversible.
- **Closing pid reuse by comparing the lock file's mtime with the process start time.** It needs `lstart` parsed into epoch seconds across GNU and BSD `date`, which is hand-rolled date logic, and `lstart` has one-second resolution. An elapsed-time comparison (`ps -o etimes=` against the lock file's age) needs no date parsing, but its BSD availability is unverified, so it joins the follow-up design space as an unverified option.

**Root problem:** `_lib_worktree_collision_guard` checks self-recognition by session_id alone whenever the lock carries one. After `/clear` gives the same process a new session_id, the guard misreads the process's own lock as a live foreign holder and denies every write into the process's own worktree.

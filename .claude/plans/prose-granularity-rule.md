# Prose granularity rule

## Context

Goal: stop review-round churn on docstrings, comments, and durable docs that are written at the wrong granularity, meaning they restate what the code already says, or feature docs that drift into implementation detail.

Ask: "Docstrings are only supposed to explain what is non-obvious from the code, and docs about features should be higher level." / "agents ask me about whether or not to fix inaccuracies in the prose without realizing - which requires my direct input - that the prose is written at the wrong level of granularity in the first place." The session drafted a three-part fix: a granularity rule in CLAUDE.md §Durable text applied at authoring time, an existence check by reviewers before raising accuracy findings on prose, and a delete-or-raise-altitude verdict on code-review's contradiction route. It was accepted via "yep, start that please". Widened: "Also there should probably be prose for the code writer to indicate this rule as well". Supplied stress-test data: "You may want to use this as data to stress test the heuristics your PR adds and/or use as fixtures". Narrowed after review: "Your plan seems very scattered if I'm going to be honest. I think you understand what we're trying to accomplish, but you have a list of guidelines that feels like compounding defensive engineering." The engineer accepted an architect consult's smaller design ("Yeah, this sounds good."), with revisions: "I think what you mean to say is if it's non-obvious"; "What is behavior at its reader's level? I think you need to explain that to the agent."; for the code-writer bullet, "Don't restate what can be gleaned from the code"; on a published-API exception, "I'm not so certain about the public API one because that's so rare, and when it happens, that can just be another pass of adding doc strings for public API documentation." / "it's easy to add it afterwards in the cases where something is a public API, and it's hard for the agent to tell whether that's the case, and it's disruptive to ask every single time." / "I actually think it should be removed entirely"; and "that plus the research that you did, it needs to be stored in some references file". Widened after `/code-review` round 3: "R4 is correct actually"; "Putting what is effectively guidelines for "bad prose" shouldn't be in the same bullet point as "prose that is fine but in the wrong place or at the wrong level of detail""; "I also don't want to overengineer things"; "The carveout for prose at the wrong altitude feels like a bandaid on a foundational problem."; "CLAUDE.md defines the broad rules of what is acceptable and what isn't, and ai-instruction-files skill defines where to put the prose that is currently in the wrong place according to more specific guidelines for the domain of the files that it is responsible for."; and, on the session's proposal to split restatement into its own angle and drop the instruction-file exemption, "yup amend that way and take it through plan-review." Widened at `/plan-review` round 3: "skills or rules that load when particular files are loaded. need to be responsible for the entirety of that file", confirmed for the session's proposed placement-table row with "yes that matches what I meant"; and "i might be inclined to move effort to high", confirmed with "yes" and again with "high (Recommended)"; and "Edit both phrases (Recommended)".

Why now: in later review rounds, prose that restates the code drifts every time the code changes. Each drift becomes an accuracy finding, and each finding is posed to the engineer as fix-or-keep. Neither option removes the prose, so it keeps drifting. A local audit of the session corpus confirmed this pattern. Its figures are not reproduced here because the corpus spans private projects. Nothing in `claude/.claude/CLAUDE.md` §Durable text, `code-writer`, `comment-discipline-reviewer`, or `/code-review` currently says that prose restating the code should not exist. The contradiction route's consult can only return *Keep current text*, *Apply this round's fix*, or *Cannot choose*.

Intended outcome: prose that restates the code is not written in the first place. When a reviewer finds it, the fix the session relays is deletion, not a corrected rewrite.

Counter-evidence the design must respect: many accuracy findings on prose are real user-facing doc errors where correction is right. In one branch, deletion caused its own churn as later reviewers flagged the removal. The rule must target restatement of code, not prose in general.

## Approach

Make prose that restates the code a named defect with one home: a new **Don't restate the code** bullet in `claude/.claude/CLAUDE.md` §Durable text, whose remedy is deletion. `/code-review`'s per-finding suggested fix, a new `comment-discipline-reviewer` angle and `code-writer`'s authoring baseline point at that bullet. Restatement gets its own angle because it is prose that should not exist, while the altitude angle covers sound prose in the wrong place. The same change ends `comment-discipline-reviewer`'s exemption of instruction files from the altitude angle: CLAUDE.md's prose rules apply to every file, and `ai-instruction-and-memory-files` decides only which surface misplaced instruction-file content moves to, gaining a row for content that isn't a rule. A design record keeps the reasons and the primary-source research behind it.

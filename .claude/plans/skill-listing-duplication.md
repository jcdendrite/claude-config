# Fix GH-849: duplicated skill listing from claude-config's stow source path

## Context

Fix GH-849: claude-config sessions load the full skill listing twice — ~28 skill
descriptions appear once at user scope (`~/.claude/skills`) and a second time,
directory-qualified as `claude:<name>`, because Claude Code's nested
project-skill-discovery mechanism tests the literal path `<ancestor>/.claude/skills`
for existence on every Read/Edit/Write, and this repo's stow source happens to be
spelled exactly `claude/.claude/skills` — an ancestor of every file under `claude/`.
Why now: the duplication just reproduced live in this session (two `/plan-it`
dispatches, one bare-scoped and one `claude/`-scoped, returned byte-identical skill
bodies from the two discovery paths), it costs real tokens on every session working
in this repo, and a scoped, design-reviewed fix now exists. Intended outcome: no
path in the repo is literally `<ancestor>/.claude/skills` after this PR;
`install.sh` auto-migrates existing installs; the shared stow-package enumeration
is published as a script so the downstream private `workstation-setup` repo can
adopt it ahead of the layout change; and `CLAUDE.md` gains a rule ruling out future
hard dependencies on other repositories.

GH-845 (the analogous `.claude/rules` double-load, via the same discovery
mechanism) is explicitly out of scope — it has a cheaper likely fix
(`claudeMdExcludes`, which already exists for the CLAUDE.md-duplication sibling
problem) and is tracked separately.

## Approach

Move the skills tree out from under `claude/.claude/` into a new top-level stow package `claude-skills/`, so no path in this repo is spelled `<ancestor>/.claude/skills` and Claude Code's nested project-skill discovery has nothing to find. `claude-skills/skills/` mirrors today's subtree one level down and is stowed with a second invocation, `stow -t "$HOME/.claude" claude-skills`, alongside the existing `stow -v "${stow_ignore_args[@]}" -t "$HOME" claude`. `install.sh` gains an idempotent migration that removes the old `~/.claude/skills` symlink when — and only when — it still resolves into `claude/.claude/skills`, and refuses anything else. Every behavioral reference to the old path (three copies of the skill-review pathspec set, the skill-length gate regex, the test-selection table, CI's collection roots, two path-scoped rule globs) moves with it, because each is a literal string that silently matches nothing after the move rather than failing loudly.

The change is roughly 35 files, and almost all of it is mechanical path rewriting. Four pieces are not: the stow-package manifest seam, the migration predicate, the new CLAUDE.md dependency rule, and the decision about which stale prose to rewrite versus preserve. The dispatch split below puts the mechanical churn behind the designed pieces it depends on.

## Verification

**Manual pre-flight, before Dispatch 1 writes anything.** Discovery is lazy (ledger row 1): it fires on the first `Read`/`Edit`/`Write` in a session that touches a file under the ancestor path, not on session start. A pre-flight that never performs that trigger step returns a false-clean reading regardless of whether the tree is fixed — this happened three times before the trigger step was identified. Discovery is also, as far as this fix's own reproduction has shown, additive within a session rather than re-evaluated per Read — so the positive control and the real check must run as two separate fresh sessions, never as two Reads inside one session, or a stale in-session discovery flag from the control could mask (or falsely confirm) the real check's result:

1. **Positive control, unmodified tree.** In a throwaway worktree of this branch, before moving anything, start a fresh session and `Read` any file under `claude/.claude/` (e.g. `claude/.claude/scripts/marker.sh`) and confirm the available-skills listing now carries `claude:`-prefixed duplicates.

# Fix reviewer-yield gap measurement (GitHub issue #762)

## Context

`reviewer-yield` measures, per specialist reviewer agent, the edit-rate gap between dispatches that found something and dispatches that found nothing (`docs/cost-ledger.md`'s `reviewer_gap_pp`). A prior investigation into PR #760's review-pipeline cost proposed demoting any reviewer with a non-positive gap from auto-routing to explicit-request-only, based on a 30-day pull showing `staff-frontend-engineer` at a −3.1pp gap (16-dispatch zero-finding arm) and `skill-fidelity-reviewer` at an 84% zero-finding rate. A second, more careful pass showed both numbers are artifacts: `staff-frontend-engineer`'s gap comes from an underpowered 16-dispatch arm (95% CI ~±21pp) that the tool's own review never checked against its documented floor, and `skill-fidelity-reviewer`'s +21.8pp gap is actually the strongest discrimination in the roster, not a weak signal. The measurement tool itself has two real defects, and this issue is scoped to fixing those two defects only — not to touching either reviewer's routing. Fix now because demoting a reviewer on a spurious signal would silently degrade review coverage, and the flawed proposal has already been through one issue-body rewrite. Intended outcome: the two measurement defects below are closed, the measurement is re-run, and only a persisting gap (if any) becomes a candidate for a future, separate demotion-or-refinement decision.

## Approach

Close the two measurement defects in `reviewer-yield` so the findings-found-vs-zero-finding edit-rate gap means what its column name claims, without touching any reviewer's routing. **Defect 1:** the corpus walk behind both `reviewer-yield` and `cost-ledger --record` opts into `include_subagents=True`, and the edit index stops discarding `isSidechain` records, so an edit made inside a `code-writer` (or any) subagent transcript reaches the Active/Edited counts — but the original design's `subagent_type`-keyed exclusion for reviewer-subagent writes is restored alongside it, so `Active` keeps functioning as a null control for real fix work rather than converging toward `Cited` on routine review bookkeeping. **Defect 2:** `_reviewer_gap_pp` gains an under-floor guard that returns the same `"insufficient"` sentinel `reviewer-yield`'s own per-bucket rate already uses, carried through the existing `reviewer_gap_pp` cell rather than a new column.

**Defect 1 mechanics.** Four coordinated edits plus a drift canary:

1. Both consumers flip together. `cmd_reviewer_yield`'s scope call (`claude/.claude/scripts/transcript_analysis/reviewer_yield.py:582`) and `cost-ledger --record`'s reviewer iterator (`claude/.claude/scripts/transcript-analysis.py:6439`) each gain `include_subagents=True`, matching `cost.py:280`'s existing form. Flipping only one would silently break the property `compute_reviewer_yield_data`'s own docstring exists to guarantee — that the report and the ledger's `reviewer_gap_pp` "can never drift apart" (`reviewer_yield.py:574-576`).
2. `_index_parent_edits` (`reviewer_yield.py:333-366`) drops `or bool(rec.get("isSidechain"))` from its record filter, gains a required keyword-only `reviewer_write_tool_use_ids: frozenset[str]`, and is renamed `_index_session_edits`. The name is load-bearing: leaving "parent" on a function that indexes subagent edits is the stale-label failure CLAUDE.md's "a narrowly-scoped label pushes up to the canonical name" rule names. The new parameter takes no default — one production call site exists (`reviewer_yield.py:456`), and a default would let it regress to the unfiltered index silently. The rename touches the named import at `transcript-analysis.py:122`, the test class at `test_transcript_reviewer_yield.py:1346-1400`, and its five `_mod._index_parent_edits` call sites.
3. **The restored reviewer-write exclusion** — detailed below.
4. The dispatch-detection loop keeps its `isSidechain` filter (`reviewer_yield.py:459-460`). Defect 1 is an edit-attribution bug, not a dispatch-detection one; dropping that filter would newly count reviewer dispatches nested inside other subagents, changing the `Dispatches`/`Cited` denominators and contradicting the documented "each main-thread reviewer-agent dispatch" definition (`reviewer_yield.py:530-533`, `docs/transcript-analysis.md:229`).
5. `cmd_reviewer_yield` and the `--record` path call `pricing._warn_if_subagent_format_drift(spawns, sidechain_turns)`, matching every other `include_subagents=True` reader in this toolkit (`cost.py:531`, `transcript-analysis.py:899`, `:2746`, `:5483`).

**The restored exclusion, in detail.** The original design's rule is stated literally at `.claude/plans/gh558-reviewer-yield-cited-path.md:184-188`: "any `Write` tool_use inside a subagent transcript whose dispatch `subagent_type` is in the reviewer set … is excluded from the edit index outright — not only writes matching a specific path." Three properties of that rule govern the implementation:

- **It is neither self-write suppression nor cross-reviewer-type suppression.** The edit index is session-scoped and `Active` asks "did the session record any code edit after this dispatch returned," so the harm is structural: in a review fan-out, a zero-finding dispatch is followed by *sibling* reviewers each writing its own findings file, satisfying `Active` with zero fix work (`gh558:170-174`). A reviewer's own findings write cannot satisfy its own `Active` — it precedes its own `tool_result` timestamp, which is the threshold. The predicate is therefore uniform: every code-write recorded inside any reviewer-typed subagent transcript leaves the index, self and sibling alike.
- **It keys on the dispatch's `subagent_type`, not on the write's target path.** Path matching was considered and rejected there (`gh558:176-182`) because the findings path exists only inside the parent's free-text prompt. Keying on the dispatch type keeps the two exclusions structurally separate, as `gh558:287-294` requires: the cited-side exclusion is a path-normalized set-membership check, the edit-side one is a `subagent_type` classification, "because they answer different questions." Path-key subtraction is also independently wrong here: the edit index maps a path key to its *latest* edit timestamp, so dropping a key would also erase a genuine `code-writer` edit to that same path.
- **What keeps a `code-writer` fix edit safe is the roster, not a per-write heuristic.** `_is_reviewer_subagent_type` (`reviewer_yield.py:288-293`) matches the `staff-` prefix plus `_REVIEWER_EXACT_NAMES`; `code-writer` has neither, so its edits can never enter the exclusion set. gh558's soundness argument was the reviewer agents' documented review-only tool contract, and that contract still holds on the current, larger roster: all ten reviewer agents grant `Write` and none grants `Edit` (`claude/.claude/agents/*.md` frontmatter), while `code-writer` is the only writing agent that grants `Edit` (`code-writer.md:4`). The exclusion therefore covers every `corpus._CODE_WRITE_TOOLS` name rather than `Write` alone, so a future reviewer granted `Edit` does not silently start counting as fix work.

The merge is what makes the mechanism non-obvious. `corpus.read_session_file` flattens each subagent file's records into one list with no per-record back-reference to its source file (`corpus.py:70-85`), and a subagent record carries the *parent* session's `sessionId`, not its own agent id (`corpus.py:44-52`). So the exclusion cannot be applied as a record-level filter, and it is applied as a **tool_use-id set** instead:

- A new per-session pre-pass `_scan_reviewer_transcripts(records, dispatch_index)` walks assistant records for spawn blocks with `_is_reviewer_subagent_type(subagent_type)`, resolves each through `dispatch_index` (`reviewer_yield.py:449`), and scans that transcript once, deduplicating by dispatch id. It applies neither the `isSidechain` filter nor `since_ts`/`until_ts`: a reviewer dispatched from inside another subagent, or one straddling a window boundary, still writes into the session's merged records, so an exclusion bounded by the scoring loop's own filters would fail open exactly where the bias is.
- `_scan_reviewer_transcript` gains a `code_write_tool_use_ids` field and returns a `_ReviewerTranscriptScan` NamedTuple rather than a sixth positional element — it already has five, and the pre-pass reads fields by name at two sites. Its `Write`-only branch stays `Write`-only: `write_content_blobs` and `write_target_paths` feed cited-path extraction and must not broaden; only the id collection uses the wider `corpus._CODE_WRITE_TOOLS` test.
- `_reviewer_write_tool_use_ids(scans)` unions those ids; `_index_session_edits` skips any code-write block whose `id` is in the set. Session-wide tool_use-id uniqueness is the join this file already relies on twice — `_build_tool_result_ts_map` and `_index_subagent_dispatches` both key session-wide dicts on it.
- The dispatch loop reads its scan from the pre-pass cache by direct indexing instead of calling `_scan_reviewer_transcript` itself, so no reviewer transcript is parsed a third time. The pre-pass's filter is a strict superset of the loop's, so a lookup miss is a programming error and should raise rather than silently unscore a dispatch. `transcript_read_errors` keeps incrementing inside the loop, from the cached `read_error` flag, so the printed "excluded from Cited" line keeps counting scored dispatches only.

Fail-open cases are named rather than closed: a reviewer dispatch with no resolvable `meta.json` is absent from `dispatch_index`, so its writes stay in the index — the same population `reviewer_yield.py:482` already excludes from scoring entirely, and closing it would mean guessing at agent identity with no sidecar to read.

**Defect 2 mechanics.** `_reviewer_gap_pp` returns `float | str | None`, where the only possible string is a new `_REVIEWER_YIELD_INSUFFICIENT = "insufficient"` constant defined next to `_REVIEWER_YIELD_ACTIVE_FLOOR` in `reviewer_yield.py:48` and also substituted for the bare literal at `reviewer_yield.py:635`. Guard order inside the function is `None` first, then the floor: a zero denominator stays the existing empty/"unmeasured" cell, while 1–9 becomes the sentinel.

The union return is forced, not preferred: `_format_cost_ledger_read_row` and `_format_cost_ledger_row` receive parsed row dicts read back from the ledger file, where `agg2` no longer exists, so a caller-side re-derivation of low confidence is impossible on the read path. Three call sites adapt:

- `_parse_cost_ledger_row_cells` (`:6059-6070`) tests for the sentinel before the `endswith("pp")` validation and passes it through unchanged.
- `_format_cost_ledger_row` (`:6122-6132`) and `_format_cost_ledger_read_row` (`:6226-6238`) share one new `_format_reviewer_gap_cell(gap, *, unmeasured)` helper.
- `_COST_LEDGER_READ_HEADER`'s `GapPP` column and `_format_cost_ledger_read_row`'s `{gap_s:>11}` widen to `>12` — `"insufficient"` is 12 characters and would overflow an 11-wide field by one. 12 matches the width `reviewer-yield`'s own Table 2 already uses for this token (`reviewer_yield.py:616`, `:640`).

**Cross-phase sequencing constraint (plan-review finding, B11):** Phase 1 and Phase 2 must land in the same PR and merge together — never Phase 1 alone. `cost-ledger --record` is a manual, human-triggered weekly command with no backup and no correction path short of `--force` (`_upsert_cost_ledger_row` refuses to overwrite an existing week's row). If it runs after Phase 1 merges but before Phase 2 does, it durably records a row with Defect 1 fixed but Defect 2's floor guard absent — reproducing, uncorrectably, the exact false-precision failure this issue exists to prevent.

The floor and the sentinel enter `transcript-analysis.py` through the existing named-import block (`:110-129`).

**Alternatives set aside.** A `Literal["insufficient"]` type alias was rejected — the toolchain runs `ruff` and `shellcheck`, no type checker (CLAUDE.md Commands), so the alias would buy no enforcement while duplicating the literal. Restating the zero-active caveat a third time in `docs/transcript-analysis.md:813` was rejected in favor of making that line defer to `docs/cost-ledger.md`, which is where the caveat is canonical. A targeted "only read code-writer subagent transcripts" alternative for Defect 1 was considered and rejected in favor of full `include_subagents=True` (engineer decision) — but that decision's side effect (Active converging toward Cited via sibling reviewer writes) is what the restored exclusion above neutralizes, reinstating the original design's own answer to the same problem rather than accepting the regression. Keying that exclusion on `meta.json`'s `agentType` was rejected in favor of the dispatch's `subagent_type` (ledger row 10), and applying it via `_read_session_file_partitioned`'s per-file grouping was rejected on a verified defect in that grouping (ledger row 2). A new schema column for Defect 2's low-confidence signal was considered and rejected in favor of a same-column sentinel (engineer decision).

### Assumption ledger

**Root:** `reviewer-yield`'s per-reviewer edit-rate gap is not trustworthy enough to act on — it cannot see edits made inside subagent transcripts, and it reports a gap computed from an under-powered arm as an ordinary number with no distinguishing signal.

**Givens** (fixed conditions beyond this design's reach):

- **G1.** Claude Code writes subagent transcripts to `<session_id>/subagents/*.jsonl` with `isSidechain: true` on assistant records and a `*.meta.json` sidecar carrying `toolUseId` and `agentType`.

# Hook performance foundational issue (GH-1024)

Line numbers are at the branch's original fork point `e307b9e6` unless marked post-change. Main has since moved, so a cite may sit a line or two off at the current base. The tree carries the shipped comment, doc, and test wording; this plan records decisions and the evidence behind them.

## Context

A `/doctor` run reported hooks running past their coded caps, `redact-credential-values.sh` (which fires on nearly every event) among them. GH-1024 asks whether this is noise or a foundational defect in the hooks themselves. The measurements are withheld here under `docs/private-project-redaction.md`.

This plan closes a confirmed SIGTERM-only gap in the shared wrapper `_lib_capped_for` (`claude/.claude/hooks/_lib.sh:56-66`, reached through `_lib_capped`/`_lib_jq`), plus a fail-open in the commit-time credential gate that the fix would otherwise widen (M6). The wrapper invokes `timeout "$seconds" "$@"` (or `gtimeout`) with no `-k`, so a child that outlives its SIGTERM holds the caller's `$(...)` open. The gap's contribution to the observed overruns is UNPROVEN:

- `-k` only changes children that catch or ignore SIGTERM, such as git's cleanup handlers and trap-holding shells.
- The jq-only hooks (`redact-credential-values.sh`, `nudge-unexpanded-skill-mention.sh`) are killed by SIGTERM at their cap with or without `-k`, so step 7 cannot confirm or refute `-k` for them.
- Only `nudge-worktree-anchor.sh` has git children.

Whether "missing binary, silently uncapped" (the wrapper's documented uncapped fallback, `docs/long-turn-nudge.md:24`) contributed to the overruns is not established by this plan. The mechanism behind the observed overruns is UNPROVEN and UNATTRIBUTED: this plan does not measure it and names no cause.

Two observations are out of this change and are recorded on GH-1024, routed by step 7: two SessionStart hooks (`set-session-title-from-branch.sh`, `check-branch-divergence.sh`) leave most of their git calls uncapped on the documented assumption that a one-shot call is safe, and `nudge-handoff-near-context-cap.sh` spawns many subprocesses per fire, including a nested `bash -c` that re-sources `_lib.sh`.

## Approach

Pass `-k 2` to the `timeout`/`gtimeout` invocations inside `_lib_capped_for`, so a child that outlives its SIGTERM gets a SIGKILL two seconds later instead of holding the hook open until the harness's own timeout fires. The two-token change carries required companions: the scaled test shim parses `argv[1]` as the duration and silently stops scaling once an option precedes it; the same function is duplicated in `plugins/skill-management/hooks/_lib.sh` under a parity test; several comments and docs state the absence of `-k` as fact; and `-k` gives `timeout` a second cap-kill exit status, which some consumers read as a literal, one of them a commit-time credential gate that treats every status but 124 as safe to skip.

**Root:** `_lib_capped_for` sends SIGTERM and then waits for a child that may never honor it, so a stalled call is unbounded, not capped. Other SIGTERM-only `timeout` copies exist (Out of scope) and stay open.

**Givens:**

- **G-a.** The harness's per-event hook timeout is vendor-controlled: `command` hooks default to 600s, and `docs/handoff-nudge.md:137` (sourced from the hooks reference) says only `UserPromptSubmit` and `MessageDisplay` lower it. That "only" is `[unverified]`: `record-session-end.sh:30-34` cites the same reference for a 1.5s shared `SessionEnd` default, and `settings.json:178` sets `"timeout": 10` for it. Step 7 therefore looks up each relevant event's budget rather than assuming 600s, `PreToolUse` included since the commit-time gates run there.
- **G-b.** A process in genuine kernel-level uninterruptible sleep honors no userspace signal, SIGKILL included, so this fix narrows the stall and does not guarantee a bound.
- **G-c.** Plugin hooks ship standalone and cannot source the stowed `_lib.sh`, so their helper copies stay duplicates (each plugin `_lib.sh` header records this).

Support for the flag is not uniform across its spellings, and the difference is not cosmetic. `-k 2` — short, two tokens, space-separated — runs on GNU coreutils and on BusyBox 1.35.0 or newer; BusyBox 1.34.1 and earlier have no `-k` and reject it with a usage error. `--kill-after=2` is rejected by BusyBox at any version with a usage error and exit 1, so the wrapped command never runs. **Mechanisms:**

- **M1 — `-k 2` on both branches of `_lib_capped_for`.** `anchors: root, row1, row2, row10, row11` — The grace is grounded in this repo's own cap vocabulary, exactly `{2, 5, 10, 15}`: 2s is the floor tier, already judged sufficient for an entire external operation to *complete* in normal operation (`_lib.sh:138,148,151` for `tail -c` over a transcript slice, `nudge-handoff-near-context-cap.sh:199` for `jq -s`, `:287`/`:532`/`:541` for `mkdir`, `activate-handoff-bypass.sh:88` for a whole `marker.sh activate` run, `record-session-end.sh:97` for a `find -delete` sweep). Post-SIGTERM teardown is less work than any of those, so a grace bounded by the smallest whole-operation cap is justified rather than picked, and it introduces no new constant. Worst case per call becomes cap+2 (2→4, 5→7, 10→12, 15→17), under the scope stated in "What this does not buy"; the healthy path is unchanged, because the grace timer only runs once SIGTERM has already failed.
  - Lighter primitives weighed and rejected: (a) **rely on the harness timeout alone** — G-a puts that at 600s for `PostToolUse`/`PostToolBatch`, so it bounds nothing useful; (b) **shorten the existing caps** — the failure is the cap firing and the child surviving it, so a smaller number changes when SIGTERM is sent and nothing about the hang; (c) **`timeout -s KILL`** — worse, not lighter: it denies every child a clean exit, and `mkdir`, `git fetch`, and `marker.sh` writes are among the wrapped commands, so it trades an availability bug for a torn-state bug.
  - Short form `-k 2`, not `--kill-after=2`: BusyBox rejects the long form (row 10). The one hazard of the two-token form — a reader that skips one token lands on the grace and mis-scales it as the duration — is confined to the test shim this repo owns; M2 strips the pair explicitly and M3's argv-contract test pins the shape.

- **M2 — teach the scaled shim the new argv prefix.** `anchors: row3, row10` — Only when `$1` is literally `-k`, strip that leading two-token pair into an array before the existing duration-scaling branch; a bare invocation with no `-k` prefix is left untouched.
  - The scaling branch passes `-k <scaled-n>` ahead of the scaled duration, so a shim-mediated test sees a grace proportional to its scaled cap.
  - The unscaled `exec` fall-through re-attaches the same pair.
  - Only a grace matching `^[1-9][0-9]*$` is scaled. Any other grace is forwarded verbatim, so a value bash arithmetic would reject never reaches it.

**What this does not buy, stated plainly:**

- a bound on a process in kernel-level uninterruptible sleep (G-b);

    - For the jq-only hooks (`redact-credential-values.sh`, `nudge-unexpanded-skill-mention.sh`) a pass means the stall was not reproduced in that run. It is not attributable to `-k`, which cannot change a child that dies at SIGTERM (Context).
    - For `nudge-error-mode-analysis.sh` a pass carries no attribution either.
    - A pass is not evidence that an allow-on-failure control ran (see "What this does not buy").

    A worst case above the bar means the excess is not a capped stage behaving as bounded. The plan cannot say in advance which explanation holds:
    - kernel-level uninterruptible sleep (G-b), which no userspace change reaches;
    - a descendant that ignores SIGTERM and holds a captured pipe, or that left the wrapper's process group, which `-k` does not bound ("What this does not buy");
    - exec latency in the uncapped stages — sourcing the large `_lib.sh`, one exec per spawned process, and, for `nudge-worktree-anchor.sh` on the drift-report path, uncapped state-directory I/O (`cat` at `:152`, `mkdir -p` at `:162`, `find -delete` at `:167`), which neither `-k` nor any cap touches;
    - the wrapper running uncapped because neither `timeout` nor `gtimeout` resolves, so `_lib_capped_for`'s uncapped `else` fallback runs the command bounded only by the harness hook timeout (`docs/handoff-nudge.md`). This is a checkable precondition: resolve both names from the hook process's own inherited PATH, not an interactive shell's, since a GUI-launched harness need not inherit a profile-added directory. A binary that resolves rules this explanation out. A pass or fail here says nothing about `-k`;
    - for the jq-only hooks, the SIGTERM-only-gap hypothesis not applying to their children at all (Context).

    Uncapped-stage latency points at fewer spawns and a lighter source path; D-state at the uncapped SessionStart calls. The owner decides what those explanations imply, and only the verdict lands on GH-1024.

## Out of scope

Follow-up issues are two, each scoped here by rule and not designed:

- **A — status-blind allow sites and one home for the cap-kill status set.** Extend M6's allowlist rule to every capped call whose nonzero or empty path reaches an allow, seeded by a mechanical sweep at A's start rather than by row 14's named list (`redact-credential-values.sh` is informational and stays fail-open by design). Consolidate the cap-kill exit-status set into one named home. Today that set is stated in `_lib.sh`'s two enumerations, `deny-pii-in-commits.sh`'s predicate, `require-skill-review.sh`'s `case` arm, and the shim predicate at `helpers.py:1610`. A shared predicate reaches none of them cleanly: G-c bars the plugin copy from sourcing `_lib.sh`, and the shim is Python-generated bash. A also gives the invariant "no capped child installs a TERM handler that exits 0" an owner and a check. On the two probed implementations, GNU coreutils reports 124 for such a child and BusyBox passes its own status through, so a handler that exits 0 would read as a clean success there. A owns the invariant, and its check covers any handler (shell `trap` or a non-shell signal handler) in a capped child, run at A's start.
- **B — `deny-pii-in-commits.sh` scans the hook's repo rather than the commit's, and scans git's rendered diff rather than the committed bytes.** Two defect classes, one issue. Scope by rule for the first: the scanned repo, index, or work tree comes from the hook's cwd and environment, not the commit's effective ones. That covers both probes and both diff sites, and the `-C`, `cd <repo> &&`, `--git-dir`/`--work-tree`, `GIT_DIR`/`GIT_WORK_TREE`/`GIT_INDEX_FILE`, and `-c safe.directory` forms. It also covers the unborn-HEAD gap, where worktree-vs-index content is unscanned for a worktree-target commit. The second class is the scanned text depending on git's output classification and on `grep`'s locale instead of the commit's bytes: binary-classified files, the `++`-prefixed added-line drop, the invalid-byte line drop, and any further diff-config or diff-structure route found later. Extending the flag list one config at a time is not the intended fix, since each sweep found another route. The fix shape is to acquire the index blobs and the worktree bytes and not parse rendered diff, and to fix the matcher's locale separately (for example `LC_ALL=C`, which also re-scopes the user-pattern tier's `grep`). Deciding whole-blob versus added-lines-only scanning is B's first task, since it changes which commits a consumer's gate blocks.

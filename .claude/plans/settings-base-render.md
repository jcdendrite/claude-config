# settings.base.json + render split: migration remediation

## Context

**Goal:** land PR #744 (settings-base-json-and-render split) with the migration correct, by replacing its inert shell-rc detector with a repair, fixing the installer ordering bug that makes the detector unreachable, and closing five defects in the render itself — so that every stow consumer's default `$HOME` profile keeps its `permissions.deny` floor and hook registrations across the rename. (Scoped to the default profile explicitly, official-`/plan-review` finding, `staff-product-engineer` — a consumer running additional non-default `CLAUDE_CONFIG_DIR` profiles is not protected by this PR at all, not merely during a closable window; see Out of scope's "Per-profile render recipe" entry. Carry this same scoping into the PR body's own opening paragraph, not only the Out-of-scope section.)

PR #744 renames the tracked `claude/.claude/settings.json` to `settings.base.json` and generates the live `~/.claude/settings.json` from it via `render-settings.sh`, merged with an optional untracked per-machine `settings.overlay.json`. The split is the right foundation: it closes a real write-through bug (Claude Code's session-local writes landing through the stow symlink into a public repo's tracked file) and gives per-profile `autoMode` trust declarations a home that a shared tracked file cannot provide.

The migration scaffolding bolted onto that foundation is not right. Renaming a file that a live stow symlink points at leaves `~/.claude/settings.json` dangling on every consumer's next `git pull`, and Claude Code treats a dangling settings symlink as silent absence — zero deny rules, zero hooks, no diagnostic. The PR's mitigation, `check-settings-render.sh` wired into `~/.bashrc`/`~/.zshrc`, cannot fire in either state it exists for: the rc block is installed by `install.sh` itself (so a not-yet-installed machine has no block), and the render call at `install.sh:330` aborts under `set -e` 635 lines before `ensure_settings_render_check` at `install.sh:965` ever runs (so the render-failure case never installs its own detector). That is a detector for a cliff the same PR creates, layered on a foundation that can be fixed instead.

Separately, review surfaced five defects in the render and its installer integration that would ship silently: a merge-direction bug that becomes catastrophic the moment carry-forward is widened, a `model` key collision between the tracked base and Claude Code's own writes, a BSD `chmod` portability failure that inverts the PR's own warning semantics, a `mv`-into-directory failure that exits 0 claiming success, and a stow migration-library blind spot that treats the render's own output as `stow --adopt` leftovers.

**Intended outcome:** a single PR that ships the render foundation with a repairing rc block instead of a warning one, an overlay boundary that leaves no per-machine setting homeless, a carry-forward rule that cannot resurrect removed keys, and documentation that does not contradict itself. The degradation window between `git pull` and the next `install.sh` is not closable by any mechanism available to this repo, and the PR body must say so plainly rather than imply the rc block closes it.

## Approach

Keep the base/overlay/render foundation; delete the detector and make the shell-rc block *run the render* instead of warning about it; fix the installer ordering so the block is installed before the render can abort; redefine the overlay's allowed key set as a closed allowlist (`autoMode`, `env`, `skillListingBudgetFraction`, with `env` guarded by a vendor-prefix namespace rule, plus a narrow nested exception for `permissions.defaultMode`); and replace the two-key carry-forward with a shallow carry-forward split across base-owned, overlay-allowed, and every-other top-level key — which removes `model` from `settings.base.json` entirely, giving it no explicit home in either base or the overlay so the general carry-forward rule preserves Claude Code's own `/config` writes to it.

The migration window itself stays open. No mechanism reachable from this repo can act on a machine that has pulled but not re-installed, so the plan shortens the window and documents it rather than pretending to close it.

### Mechanisms

**M1 — Replace `check-settings-render.sh` with `ensure-settings-render.sh`, which runs the render instead of warning about it.** `anchors: root` — this converts the compounding defensive layer into a fix: the same rc trigger that could only observe the broken state now repairs it, and warns only when the repair itself fails. Lighter primitives rejected: (a) a Claude Code `SessionStart` hook that renders — fails on given 1, since the registration lives in the missing file; (b) a `post-merge` git hook shipped in the repo — fails on given 1, git distributes no hooks by clone, so it needs `install.sh` to install it and inherits the identical bootstrap; (c) keeping the warn-only detector — fails on the root line's two circularity findings, and given 2 means the warning it prints is the *only* signal a consumer gets while an unprotected session runs anyway; (d) a staleness check (mtime or hash of base+overlay compared against the last successful render, skipping the `jq` pipeline when unchanged) — deferred rather than rejected: this plan has no latency measurement to justify the added state and complexity, and M1 makes this pipeline run unconditionally on every new interactive shell forever, a permanent architectural fact the plan already leans on elsewhere (M3 rule 4's rejection of a second subprocess call, M5's residual paragraph's change-triggered disclosure, the Concurrent-render race entry). **Required at implementation time:** measure the render's wall-clock cost on a representative machine; if it is not negligible, add a staleness check as a follow-up rather than shipping an unbounded per-shell cost with no accountability (official `/plan-review` finding, `staff-platform-engineer` — M1's other three rejected alternatives are each named with reasoning; this fourth one was previously absent entirely, with no stated latency budget anywhere in Verification). All ingredients for M1 already exist: `~/.claude/scripts/render-settings.sh` survives the rename (only `settings.json` moved), `render-settings.sh:98-110` already self-heals a dangling symlink via mktemp+`mv`, and `$HOME/.claude-config-source` (written `install.sh:340`, already read `check-settings-render.sh:27`) supplies the checkout path for the failure message.

**M2 — Relocate the rc-block installation's definitions, not just its call site, above the render call in `install.sh`.** `anchors: root` — `install.sh:330` is a hard unguarded statement under `set -e`, and bash does not hoist function definitions: a function must already be *defined* by the time execution reaches its call. `ensure_settings_render_check` (`:896`, renamed under M1) and its dependency `_ensure_rc_block` (`:803`) both sit after `:330` today, so moving only the call site at `:965` would still fail with "command not found" on the very first run it's meant to protect. The fix moves the *definitions* of `_file_has_active_reference` (`:770`), `_undo_rc_append` (`:779`), and `_ensure_rc_block` (`:803`) — plus the renamed rc-invocation function itself — above `:330`, and moves that function's call site there too.

`ensure_local_bin_on_path` (`:872`) shares the `local-bin-path` fixture block and the `_ensure_rc_block` dependency with the functions above, but has no ordering relationship to the render — it decouples rather than moving with them. The three shared helpers extract into a new `rc-block-helpers` `INSTALL_TEST_FIXTURE` block positioned before `:330`; `local-bin-path` shrinks to just `ensure_local_bin_on_path`'s own definition and keeps its existing call site (`:964`) unchanged. Reordering the settings-render half is strictly cheaper than the alternative (wrapping the render in `|| { install block; exit 1; }`), which duplicates the installation call site.

**M3 — Carry forward top-level keys the merge doesn't own, shallowly; never carry forward an overlay-allowed key's own top level; always re-apply app-written state, top-level or nested.** `anchors: row5, row9, row24, row25` — given 5 makes enumeration unwinnable, and row 9 makes the current direction unsafe at any width. Lighter primitives rejected: (a) extend the enumerated list to the five currently-documented keys — fails on given 5, the set is vendor-versioned and already grew once unnoticed; (b) enumerate plus warn on unrecognized keys — same failure, and it discards the user's setting while warning about it. `plan-architect` (consulted this round on the `env` guard, whose reasoning applies here too) surfaced a defect in the plan's prior single-rule version: carrying forward *every* top-level key absent from the merged result also resurrects a key a consumer deliberately deleted from the overlay — e.g. removing `autoMode` from `settings.overlay.json`, M6's own prescribed way to turn autoMode off, would do nothing, because the deleted key is now "absent from the merged result" and the prior render's stale value carries forward forever. The fix splits carry-forward into three rules applied in order, none of them a re-introduced enumeration:

1. **Base-owned top-level keys** (`permissions` — subject to M11's narrow `defaultMode` exception, `hooks`, `statusLine`, `enabledPlugins`, `extraKnownMarketplaces`, `skillOverrides`) — base always wins, no carry-forward, no nested exceptions beyond M11's. Unaffected by this revision. (`skillOverrides` added round-13, `staff-platform-engineer` — row 11 already classifies it as part of "base's remaining top-level key set... none of which Claude Code writes," the same never-app-written rationale rule 1 exists for; this enumeration had omitted it, leaving it to fall under rule 3's general carry-forward by default and giving it weaker resurrection protection than its row-11 siblings.)
2. **Overlay-allowed top-level keys** (M5's `autoMode`, `env`, `skillListingBudgetFraction`) — **not** carried forward at the top level. If the overlay doesn't set one, it is simply absent from the merged result and stays absent — this is what makes deleting an overlay key (or the overlay file itself) actually take effect, closing the M6 regression above.
3. **Every other top-level key** — carried forward from the prior rendered file when absent from the merged result, base/overlay winning when present. This is the open-ended, row-5-motivated fallback: it needs no enumeration because it applies to whatever key isn't claimed by rules 1 or 2, present or future. `theme`, `tui`, and (after M4) `model` all fall here and need no special-casing anymore — the hardcoded `theme`/`tui` carry-forward this plan's predecessor code already has (`render-settings.sh:91-92`) is subsumed by this general rule, not kept alongside it.

All three rules are **top-level only, never a deep `*`** — a deep merge would resurrect a nested path base deliberately removed, so dropping a hook event from `settings.base.json:97` would silently reinstate it from every consumer's stale rendered file forever. This is what keeps `permissions`, `hooks`, and `statusLine` (`settings.base.json:448`, command-executing) base-owned with no nested exceptions beyond M11's.

Rule 3 alone would still lose the two dotted paths nested *inside* an overlay-allowed top-level key (`env.CLAUDE_CODE_EFFORT_LEVEL`, `env.ANTHROPIC_MODEL` — row 24, machine-local and possibly app-written): `env` itself is rule 2's territory, so an overlay that sets `env` without those two paths (a realistic shape — a consumer adds `DISABLE_TELEMETRY` to their overlay but never touches the paths `/effort` writes) drops them on the next render. A fourth step closes this, narrowly: **after rules 1–3 produce the merged result, re-apply the prior rendered file's value for `env.CLAUDE_CODE_EFFORT_LEVEL` and `env.ANTHROPIC_MODEL` only where the merged result does not already contain that path.** Presence is decided by path traversal rather than a non-null test, matching `guard-settings-session-keys.sh:111-119`'s own `guarded_value` semantics for these same two paths, and the parent `env` object is created when the merged result has none — a consumer with no overlay at all still needs the value preserved. This is deliberately *not* the unconditional "prior file wins" shape `render-settings.sh:91-92` uses for `theme`/`tui`. That shape's precondition, stated at row 9 — the prior file holds keys base and overlay can never set — does not hold here: M5's namespace rule accepts `CLAUDE_CODE_`- and `ANTHROPIC_`-prefixed names, so both paths are legal overlay content, and an unconditional re-apply would silently overwrite an overlay-authored value with a stale rendered one on every render after the first (round-3 finding, `staff-sdet` BLOCKER, corroborated independently by `staff-platform-engineer`; direction confirmed by `plan-architect` consult). Rule 4's precedence is rule 3's precedence: base and overlay win where they set the path; the prior file fills only where they don't. This list is exactly the *dotted* entries of `GUARDED_KEYS_JSON` (row 25), so it doesn't reintroduce an enumeration — it's testable drift against the same SSOT Phase 1's M4 disjointness test already reuses, via the print-mode interface below, rather than a second hand-typed copy.

Rule 4's own premise — whether any Claude Code version actually writes either dotted path into user-scope settings — is unverified (row 24, `[unverified]`), on the same footing as M11's `defaultMode` enum and M5's `env`-prefix set, both of which this plan already re-derives from live vendor docs at implementation time rather than trusting a planning-time citation. The re-derivation method differs from M11's/M5's, though, and must be named explicitly rather than assumed analogous (round-6 finding, `staff-platform-engineer`): M11 and M5 check a *documented* enum/prefix set, so re-reading the current vendor docs is a real, terminating check. Whether Claude Code writes either dotted path is a *runtime-behavior* question row 24 already found the docs silent on — re-reading the same docs at implementation time cannot resolve it. The actual check: trigger `/effort` (or whatever command currently sets these) on a clean profile and inspect the resulting `~/.claude/settings.json` for either path. If Claude Code does not write either path, rule 4 is not defensive preservation but the sole cause of the stickiness it exists to guard against, and it should be deleted along with Verification cases 6–8 and the dotted-path equality test in Verification's "`--print-guarded-keys` mode and its reuse" entry specifically (not the test in Verification's "Base/app-written disjointness" entry, which is unrelated to rule 4). **Fail-safe default if unresolved by implementation time: keep rule 4** — the asymmetry runs opposite to `dontAsk`'s (M11): dropping a preserved `/effort` value on ambiguous evidence is a visible regression, while keeping a stale one on ambiguous evidence is a nicety. Whichever outcome is reached, record it in a one-line comment next to rule 4 in `render-settings.sh` itself (confirmed-write / confirmed-absent / fail-safe-default-applied), mirroring M11's identical requirement for its own implementation-time-decided enum members (round-6 finding, `staff-platform-engineer`; scoped to `dontAsk` specifically round-9, `staff-product-engineer`, since M11's text at that point named only `dontAsk`; restored to "enum members" round-10, `staff-product-engineer`, since M11's own text was extended that same round to require the identical recording for `auto` too — see M11's `dontAsk` paragraph) — otherwise a future maintainer has no way to tell whether rule 4 is load-bearing or a permanently-unverified defensive artifact. This check and its outcome-recording requirement are also restated in Phase 1's `render-settings.sh` critical-files bullet itself, not left only in this mechanism narrative, so a `code-writer` dispatch scoped to that bullet doesn't implement rule 4 unconditionally and skip the check entirely (round-6 finding, `staff-platform-engineer`).

`GUARDED_KEYS_JSON`'s value has no existing invocation path a caller can execute (row 25) — regex-extracting it from source would be the source-scanning anti-pattern `staff-sdet` flagged. `guard-settings-session-keys.sh` gains a direct-invocation mode: called as `guard-settings-session-keys.sh --print-guarded-keys` (not via the hook's stdin tool-input protocol), it prints `GUARDED_KEYS_JSON` to stdout as JSON and exits 0. This check must run before the script's *stdin read and `_lib.sh` source* — not merely before the named tool-name/commit-command/git-repo/staged-file guards, which are already downstream of both (`claude-hook-review` invocation, this round: the script's actual first substantive step is `_lib_parse_tool_input_or_deny`, itself fail-closed on missing/malformed stdin — a CLI invocation with no piped tool-input JSON would be swallowed by that fail-closed parse, deny/error out, and never reach a check placed only ahead of the tool-name guard; a `_lib.sh`-sourcing failure elsewhere would also break this mode for no real reason, since printing a literal bash constant needs none of `_lib.sh`'s functions). Concretely: check `$1` against `--print-guarded-keys` as the very first statement in the script — before the `_lib.sh` source attempt and before any stdin is touched — with `GUARDED_KEYS_JSON`'s definition moved earlier if needed so the print path never depends on code that runs after it today. If a caller wants the value JSON-canonicalized rather than printed as the literal bash constant, route that through `_lib_jq`, not bare `jq`, matching this file's existing timeout-backstop discipline everywhere else — though a bare `printf '%s\n' "$GUARDED_KEYS_JSON"` suffices, since the constant is already valid JSON. This is a test-time and drift-check interface only — `render-settings.sh` does not shell out to it on every render; the two dotted paths it preserves are a small literal constant in `render-settings.sh` itself (performance: M1 makes renders run on every new shell, and a subprocess call to a second script is not warranted for two names), and a test asserts that constant equals `--print-guarded-keys`'s dotted-path subset, catching drift the moment the two lists diverge rather than silently.

The plan's earlier fix — moving `model` into the overlay instead — reproduced the identical regression one layer up (row 10, `staff-sdet` BLOCKER): `/config` writes into the live file, not the overlay, so an overlay that seeds `model` always wins over the merged result. This is not a preference: the repo already classifies `model` as machine state at `guard-settings-session-keys.sh:84`, and "a key Claude Code writes belongs to carry-forward, not the overlay" is now the organizing rule for the whole allowlist (row 20), not a `model`-specific exception. It also establishes row 11's disjointness for the *merged result*, not only for base, which is the property that keeps M3 special-case-free.

**M5 — Define the overlay's allowed top-level key set as a closed allowlist: `autoMode`, `env`, `skillListingBudgetFraction`.** `anchors: row4, row17, row20` — the original two-key set (`enabled`, `autoMode`) left `env` and `skillListingBudgetFraction` with no private home in a public repo, which is what falsified the doc sites in row 17. `model` was considered and excluded — see M4, row 10. A same-session denylist refusing only `permissions`/`hooks` overcorrected: it would leave `statusLine` (executes a command per prompt render), `enabledPlugins`/`extraKnownMarketplaces` (registers hooks additive to base's own — a parallel execution path base never reviews), and an unconstrained `env` reachable from any overlay, and M1 makes renders automatic on every new shell. The allowlist stays closed rather than denylist-shaped because the overlay is human-authored and bounded, unlike carry-forward's vendor-written, unbounded set (M3) — the two mechanisms solve different problems and should not share a shape. (Round-2 finding, `ciso-reviewer` S2: the threat this control is actually sized for is a consumer who can write `settings.overlay.json` specifically — e.g. hand-pasting an untrusted "helpful settings" snippet — not a general home-directory-write-capable adversary, who has strictly easier schema-blind paths available already — a shell rc file, `crontab`, LaunchAgents, or an SSH client config's `ProxyCommand` directive among them — none of which route through this allowlist at all. The mitigation isn't oversold by that narrower framing; it just needs to be named accurately rather than implied to close a wider gap it cannot reach.)

`env`'s value guard is a **namespace rule, not a denylist**, per the `plan-architect` consult this round: an overlay `env` key is accepted only if its name matches `^(CLAUDE_CODE|ANTHROPIC|DISABLE)_[A-Z0-9_]+$` (the prefix set attested in-repo — `guard-settings-session-keys.sh:90-91` guards `env.CLAUDE_CODE_EFFORT_LEVEL`/`env.ANTHROPIC_MODEL`, `docs/security-hardening.md:537-545` documents five `DISABLE_*`/`CLAUDE_CODE_ENABLE_TELEMETRY` telemetry vars as `env`'s actual sanctioned use — but re-derived from the live Claude Code settings docs at implementation time, since the set is vendor-versioned and this citation could be stale by then) and its value is a string. That same implementation-time re-derivation step must also check whether any vendor-documented `env` var in this prefix space has a permission-mode- or prompt-suppression-equivalent effect, and refuse it under M11's rule if so — otherwise the namespace rule could admit, through the `env` channel, exactly the prompt suppression M11 hard-refuses `bypassPermissions`/`acceptEdits` for achieving through `permissions.defaultMode` (official `/plan-review` finding, `ciso-reviewer` — no such variable is confirmed to exist today; this is a gap in the plan's own cross-channel coverage, not a confirmed exploit). The reasoning M3/row 5 already used to reject an *enumerated* carry-forward allowlist ("the set is versioned by the vendor and already grew once unnoticed") applies just as strongly to a denylist of dangerous names — the originally-planned four-name denylist (`BASH_ENV`, `NODE_OPTIONS`, `LD_PRELOAD`, `PATH`) was exactly that shape, and `ciso-reviewer` (S1, round-2) confirmed it was already incomplete on this plan's own primary-verification platform (missing macOS's `DYLD_INSERT_LIBRARIES`/`DYLD_LIBRARY_PATH`, plus `PYTHONPATH` and `GIT_SSH_COMMAND` from the same class). Widening the denylist with more names — the obvious patch — repeats the same shape rather than fixing it. The namespace rule closes the problem structurally instead: an environment variable's name is chosen by the *program that reads it* (dyld, node, git, a shell), never by the config-writer, so nothing outside the vendor's own configuration-prefix convention can carry a code-execution or credential-redirection effect, present or future, on any platform. The originally-denylisted names, plus the macOS dyld-hijack vectors `ciso-reviewer` additionally found missing, become regression-pin test fixtures under the new rule — see Verification's "Overlay allowlist (M5)" entry for the full fixture list, not restated here to avoid the count drift a round-9 finding (`staff-sdet`) found between this sentence, row 20, and Verification itself — not guard logic; a hand-typed name check is no longer in the render path at all.

**Residual the namespace rule doesn't close, and why no second control is added for it:** any `ANTHROPIC_`- or `CLAUDE_CODE_`-prefixed name accepted by the namespace rule can, in principle, carry the vendor's own future meaning — not just the two currently-known examples (`ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`) that redirect the API endpoint or swap credentials, an open class rather than an enumerated pair, per the same row-5/M3 standard that rejected an enumerated carry-forward list (round-3 finding, `ciso-reviewer`, Medium). The blast radius is broader than credential exfiltration alone: an adversary-controlled `ANTHROPIC_BASE_URL` redirects every subsequent tool-use turn to a backend of the attacker's choosing, bounded only by whatever `permissions.deny` rules remain in force — not solely a data-exfiltration path (round-3 finding, `ciso-reviewer`, Medium, correcting this paragraph's prior "not code execution, but exfiltration" framing). This is reachable via the same hand-pasted-snippet path S2 names above (e.g. "use this gateway, add these two vars"). Per CLAUDE.md's compounding-defensive-layers principle, this doesn't get a second validation layer (`ciso-reviewer` S3's proposed independent rendered-output audit is declined for the same reason — the guard already fails closed under the namespace rule, so a bug in it fails toward refusing the render, loud, not toward a silent bypass a backstop would need to catch). Instead the overlay-authored side of this residual gets a matching disclosure, specified once as a single Phase 1 deliverable and Verification entry (see Phase 1's stderr-disclosure bullet) rather than restated here: a per-render stderr announcement, triggered only when the rendered output changes from the prior render, names which overlay `env` keys were newly applied or changed value at the render where the overlay sets them. Change-triggered rather than unconditional-every-render, because M1 makes renders run on every new shell and an unconditional line trains the blindness it exists to prevent (round-3 finding, `ciso-reviewer`, Medium). Also add `DISABLE_`-prefixed names to this residual's open-class acknowledgment: the same "value chosen by the vendor, not the config-writer" reasoning that motivates concern about `ANTHROPIC_`/`CLAUDE_CODE_`-prefixed names applies identically to `DISABLE_`-prefixed ones, which the namespace rule accepts on the same footing (round-4 finding, `ciso-reviewer`, Medium — the residual paragraph named only two of the three accepted prefixes).

This disclosure is deliberately **not** attributed to M3's rule 4 itself, correcting this paragraph's own earlier wording (round-4 finding, `staff-sdet`, top-priority): rule 4's whole job is to reproduce the prior rendered file's value exactly at `env.CLAUDE_CODE_EFFORT_LEVEL`/`env.ANTHROPIC_MODEL`, so its action produces no diff against the prior render and a diff-based oracle is structurally blind to it — claiming rule 4 "gains a matching disclosure" was false, not just underspecified. The real gap that leaves open: an overlay author who sets one of these two paths gets disclosed once, correctly, by the mechanism above; if they later remove it from the overlay expecting the value to disappear, rule 4 silently keeps reapplying the old value forever, with no output change and therefore no further disclosure — a "did my edit take effect" mismatch, not a new attacker-injection path (rule 4's scope is those two paths only, both legitimate app-written state, not the open `ANTHROPIC_BASE_URL`-class residual this paragraph is actually about). This mismatch is accepted and documented rather than announced at render time: building a fourth disclosure category — a provenance-transition oracle requiring new persistent state (a sidecar file, its own atomicity, corrupt-content tolerance, and stow-exclusion treatment) — to close a "did my overlay edit take effect" nicety on two non-secret, non-attacker-controlled paths would itself be the second validation layer this paragraph's own next clause already argues against building (round-5 finding via `plan-architect` consult, resolving a round-4/round-5 reviewer split — `staff-sdet` recommended dropping it as disproportionate, `staff-platform-engineer` found it appropriately scoped if built at all; the consult's independent read sided with dropping it, on grounds neither reviewer's disagreement reached: rule 4's own premise, row 24, is itself `[unverified]`, so hardening a disclosure mechanism for rule 4's side effect commits to a second layer before the first is confirmed load-bearing). Applied to itself, this paragraph's closing clause — "the value is always visible to direct inspection of the rendered file regardless" — is dispositive against building anything new here, not only against building something wider than one transition disclosure. Phase 3's `docs/auto-mode.md` rewrite states the carry-forward behavior in prose instead (see Phase 3's file list): removing `env.CLAUDE_CODE_EFFORT_LEVEL`/`env.ANTHROPIC_MODEL` from the overlay does not remove either from the rendered file while rule 4 is in effect — edit or delete the value directly in `~/.claude/settings.json` (or re-run `/effort`) and re-render.

Refusal of any key outside the closed top-level set, or any `env` name outside the namespace rule, stays a hard error rather than a silent strip, matching `render-settings.sh:54-58` — a consumer who puts an unrecognized key in an overlay should be told. `permissions` is **conditionally admissible** at the top level rather than simply absent from the allowlist: the check accepts an overlay `permissions` object only when its key set is exactly `{defaultMode}` — M11's nested exception — and refuses it with a hard error naming every other key it carries, `deny` included. This conditional is part of `render-settings.sh:54-58`'s replacement itself, not a separate check layered after it; implementing that replacement as a straight key-list swap would hard-refuse the exact overlay shape M11 exists to accept (round-3 finding, `staff-product-engineer`, BLOCKER; wording confirmed by `plan-architect` consult). The `permissions.deny` array-union logic previously flagged is still **not** needed: no overlay can supply a `permissions.deny` array at all under this conditional, so `render-settings.sh:68-70`'s wholesale array replacement stays unreachable.

**A golden-fixture round-trip test for the full rendered output.** The per-behavior tests above cover each rule; a fixture pinning the entire rendered `settings.json` would catch interaction bugs the per-rule tests miss, but it would also churn on every legitimate base change and needs its own update discipline decided first.

**`permissions.deny` array-union logic in the merge.** Considered and rejected: `render-settings.sh:68-70`'s wholesale array replacement is reachable only via an overlay-supplied `permissions.deny`, which M5's conditional admissibility check refuses outright since only an exact `{defaultMode}` key set is accepted (round-10 finding, `staff-product-engineer` — the prior wording said `permissions` was "outside M5's allowlist entirely," stale against M5's own later-introduced conditional admissibility; M11's "does not reopen `permissions` generally" closing paragraph already states the correct, narrower version of this claim, and this entry now matches it; structural label used instead of a bare line number per round-11 finding, `staff-product-engineer` — matching this document's own convention, established round 8, against exactly this drift risk). Adding union logic would guard a case that cannot occur.

**An enumerated carry-forward allowlist, and a strip list of dangerous vendor keys.** Considered and rejected per given 5 — the set is versioned by the vendor and already grew unnoticed once, and Phase 1's own backfill of `modelSettings`/`fastMode`/`disableBypassPermissionsMode` into `GUARDED_KEYS_JSON` is this plan's evidence that the enumeration had already fallen three keys behind (round-14 finding, `ciso-reviewer`, resolved via `plan-architect` consult). Sourcing rule 3's carry-forward set from `GUARDED_KEYS_JSON` would therefore delete every vendor key absent from that list on every render, including whichever of `agentPushNotifEnabled`/`disableArtifact`/`disableWorkflows` Phase 0 routes to general carry-forward — the "nowhere" answer Phase 0's own bullet names as valid. Re-scoping `BASE_OWNED_KEYS_JSON` to name dangerous-if-planted vendor keys fails differently: rule 1 means "base wins," so a key base never sets is deleted rather than owned, making it a strip list wearing rule 1's name, and it removes the only home a per-machine vendor key has post-M5 — the same homeless-key defect row 17 catalogues.

The residual cost of carry-forward-all is that the live `settings.json` becomes durable state the render never resets: a top-level key written into it by anything other than this pipeline persists across every future render, so re-rendering is not a remediation step. The change-triggered stderr disclosure names the full carried-forward set, but only on a render whose output differs from the prior one — a key carried forward with base and overlay unchanged leaves the output byte-identical, so the steady state is silent. Writing a top-level key into the live `settings.json` needs the same general home-directory-write capability M5's residual paragraph places outside this design's threat model. M1 sharpens that: the render is invoked from `~/.bashrc`/`~/.zshrc`, which carry the same write permissions as its own output, so an adversary who can plant a settings key can instead rewrite the line that runs the render. No rule inside `render-settings.sh` bounds a writer who owns its trigger. An install-time-only unconditional carried-set announcement was considered and declined: it adds a flag, a call-site change, and a test to gain visibility only on the narrow slice of `install.sh` runs where base did not change, against a threat model this entry places out of scope — the same reasoning that declined the independent rendered-output audit and the category (d) provenance oracle.

**The two-phase migration split.** Considered and rejected; reasoning recorded under Alternatives set aside.

**Interactive TUI startup behavior against a dangling symlink** (given 3). Verifying it needs a real login for a throwaway config directory. It would refine how the migration window is described, not what this plan does about it — given 1 makes the window unavoidable either way.

**Concurrent-render last-write-wins race.** The realistic pairing is not two renders racing each other — two renders in isolation read identical inputs and produce byte-identical output, so that framing alone doesn't lose anything (round-5 finding, `staff-product-engineer`, verified directly against `render-settings.sh:90-92,98-110`). The actual race is a render (triggered by any new shell opening, which M1 makes constant) against a **live-file write from `/config` or `/effort` in a different, already-running session** — that write lands directly in `$target` between the render's read and its own write-back, so the render's carry-forward can silently lose it. Pre-existing for `theme`/`tui` alone before this PR; M3 widens the set of keys exposed to it (every top-level key plus two dotted paths), and M1 raises the frequency (round-3 finding, `staff-platform-engineer`, FYI). Not fixed here — a lock or atomic compare-and-swap around the render is more mechanism than this plan's scope warrants for a race whose window is a few hundred milliseconds and whose worst case is the same as today's: one write loses to the other, not data loss or a security-relevant bypass. Concretely, this can silently revert a user's `/config` model or effort-level choice, and unlike a cosmetic `theme` flip that reversion isn't noticed on sight and persists across every subsequent render until the user re-runs `/config` (round-4 finding, `staff-platform-engineer`, Low — names the concrete case the abstract description above only implied). Worth one sentence in the PR body, describing the actual trigger (a new-shell render racing a concurrent `/config`/`/effort` write) rather than two shells colliding.

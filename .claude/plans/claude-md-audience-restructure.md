# Restructure the global CLAUDE.md: compress the post-#741 delta, install a ratchet

## Context

Trim `claude/.claude/CLAUDE.md` back toward the size it held after PR #741 and add
a mechanism that makes the next regrowth visible, without losing any load-bearing
instruction. The file is 178 lines / 31,143 bytes today against 141 lines / 27,332
bytes at #741 plan's post-rebase baseline — a 3,811-byte, 37-line delta accrued across
many individually-reviewed PRs, none of which showed a reviewer a cumulative total.

Why now: an external critique (Gemini) argued the file is a "monolithic rulebook"
whose full weight is paid by every dispatched subagent. Its premise is partly
sound — ~12,181 bytes (39%) is orchestrator-only content with no reader in a
subagent, and Anthropic's docs confirm no per-agent opt-out exists. Its proposed
remedies are not: every skill-based extraction it names is unloadable, because no
custom agent in this repo carries the `Skill` tool, and its "12KB / 1,500–2,000
word" budget has no primary source. The genuine problem it surfaced indirectly is
the absence of a ratchet, not the absence of decomposition — #741 already ran the
decomposition experiment and largely exhausted that lever.

Intended outcome: a smaller, better-ordered global CLAUDE.md; one relocation to a
path-scoped rule file; a shared-hook byte-size gate that denies the next commit
that grows the file past a vendor-sourced threshold without an offsetting cut;
and a decision record so the next pass does not re-derive the harness semantics
or re-propose the deferral this plan declines.

## Approach

Phase 1 compresses `claude/.claude/CLAUDE.md` in place along five moves — a behavior-test audit of everything the file gained since PR #741, one exact-trigger relocation to a new user-scope `.claude/rules/` file, moving the Safety section to the head of the file for attention, a shared-hook byte-size gate that makes the next regrowth visible, and a compact correction pass to the governing skill's own sizing guidance. Phase 2 is a written recommendation, not an implementation: **do not build the `SessionStart` + `additionalContext` deferral**, and record why in `docs/design-decisions.md` so the next pass does not re-derive it.

The framing shift from #741 matters. #741 asked "which surface does this rule's load trigger match?" and largely exhausted that lever — its own trigger audit and armed-and-complete check are still valid and this plan does not re-litigate them. This pass asks a different question: **the file gained 3,811 bytes across 37 lines since #741 with no gate noticing**, so the target is the delta and the absence of a ratchet, not another surface sweep.

### Why Gemini's framing is partly right and partly wrong

Right: the per-subagent multiplier is real, and no mechanism exists to avoid it. Wrong on three counts, each load-bearing for what this plan does and does not do:

1. Its proposed "12KB / 1,500–2,000 word" budget has no primary source. The only published Anthropic-first-party threshold for CLAUDE.md itself is **under 200 lines** (`claude/.claude/skills/ai-instruction-and-memory-files/SKILL.md:45`), and the file is at 178. A byte cap is still justified — but on Anthropic's own sibling-file precedent (`MEMORY.md`'s 25KB load window, `docs/instruction-file-sizing-evidence.md` §1), never on that invented 12KB figure.
2. "Halving it chops token weight in half across all sessions" does not follow. CLAUDE.md sits in the cached prefix, and this repo's dominant spend driver is idle-gap cache rebuilds at 92.9% (`docs/cost-levers-considered.md:194-215`), with the main thread carrying 71.4% of dollar cost (`docs/design-decisions.md:283-289`) — the exact place the orchestrator block would remain under any deferral scheme.
3. "Monolithic rulebook" implies the fix is decomposition. The repo already ran that experiment: #741 decomposed what could be decomposed and found the residue genuinely un-relocatable, because its firing event is a dispatch, which reads no file.

### Phase 1 — the five moves

**1A. Delta behavior-test audit.** Locate #741 plan's landing commit (`git log --oneline -- .claude/plans/trim-global-claude-md.md`), then `git diff <that-commit>..HEAD -- claude/.claude/CLAUDE.md`. Apply the behavior test (`ai-instruction-and-memory-files/SKILL.md:54-60`) per added line: does removing it change behavior on at least one realistic input? Compress or cut what fails; keep rationale that arms the model for an unenumerated edge case. Two specific delta regions to look at hardest, because both are recent additions with sibling homes: the prose rules promoted from `output-preferences.md` (`docs/design-decisions.md` §38, 2026-08-31) now spanning L138-153, and the Model & Effort Routing block (L100-113) whose own closing sub-bullet at L112 already declares `EXPECTED_EFFORT` in `test_agent_roster.py` the source of truth over itself. This is an audit, not a fixed cut list — the byte saving is whatever fails the test, reconciled in Verification.

When a Safety bullet is backed by a hook, the cut is per-clause, not per-bullet: split the bullet into the sub-clause the hook actually enforces (a candidate for compression) and any sub-clause it does not (must stay verbatim). Two concrete cases where a whole-bullet cut would be wrong: `deny-credential-file-reads.sh` enforces the Read prohibition on credential paths but has no visibility into "never route around the denial," which governs behavior *after* the hook has already fired; and `ask-new-dependency-disclosure.sh` is ask-class (`# Gate: ask (never deny)`) and mechanically names `name@constraint` pairs, but supplies no rationale, so the CLAUDE.md duty's "and rationale" clause has no hook backstop at all.

**1B. Settings-scoped relocation — L136 only.** L136 (`settings.json` vs `settings.local.json` scoping) fires on exactly one event — editing a settings file — which is a file read a glob can name: it answers "which of these two files does my rule go in," a question that only arises once a settings file is already open. L135 (`permissions.allow` globs) does not share that trigger: it fires when *composing* a permission rule, which precedes opening the file, and three sequences reach an authored `permissions.allow` entry with no file-open event at all — conversational advice given with no settings file open, a subagent asked what permission a dispatch needs, and a `Write` to a `settings.json` that does not yet exist (rule injection is a post-tool-result system-reminder, so for a `Write` the content is chosen before the reminder could arrive). So **only L136 relocates; L135 stays in CLAUDE.md.** `ai-instruction-and-memory-files/SKILL.md` §2 names "the content is genuinely critical and one delivery mechanism could fail silently" as a reason to duplicate rather than relocate, and that reasoning cuts the same way here for the line that stays: `ask-review-permissions.sh` fires on settings-file edits but does not check glob shape, so CLAUDE.md's prose is the sole carrier of the glob-specific rule regardless of which file it lives in. Create `claude/.claude/rules/settings-json-conventions.md` with `paths: ["**/settings.json", "**/settings.local.json"]`, and **fold the existing project-scope `.claude/rules/settings-json-conventions.md` into it, deleting the project file**. That file's two bullets (`enabledPlugins` only takes effect in `settings.json`; `false` versus removing an entry) plus the relocated L136 are harness facts that generalize to every repo, so user scope is their correct home. The alternative — a differently-named global file leaving the project file in place — loses: two rule files on the identical glob covering the same subject is precisely the "reader can't tell which is canonical" failure the Single-source-of-truth rule targets.

**Pre-merge window for 1B.** `~/.claude/rules` is a directory symlink to the **main** tree, so the new user-scope rule file is unreachable from any session — including one whose cwd is this branch's worktree — until this PR merges and a contributor pulls. The project-scope file's deletion, by contrast, takes effect the moment it lands in the worktree, because project-scope `.claude/rules/` loads from cwd, not through the symlink. Between those two events there is a window where **neither** copy of the L136 rule is in effect, and the population most likely to hit it is this PR's own reviewers editing a `settings.json` while reviewing it. This is advisory content, narrow, and self-resolves at merge — document it here, do not re-sequence the relocation around it. CLAUDE.md's own edit (moving L136 out) does not share this problem: `claude/.claude/CLAUDE.md` is itself stowed through the same symlink as the rules directory, so its old and new content transition through that one symlink at the same merge event — there is no second, differently-timed copy to create a gap.

**1C. Safety to the head of the file.** `ai-instruction-and-memory-files/SKILL.md:49-50` directs critical rules to the start or end of the file, but its own stated reason — "attention decays in the middle ('lost in the middle')" — over-cites: "Lost in the Middle" (Liu et al., TACL 2024) measures multi-document-QA and key-value-retrieval accuracy over document position, and contains no instruction-adherence task; citing it for *rule placement* is an extrapolation the paper does not make (`docs/instruction-file-sizing-evidence.md` §3-4). The correctly-scoped justification for this move is one first-party vendor statement, **asserted, not measured**: OpenAI's GPT-4.1 prompting guide ("ideally place your instructions at both the beginning and end of the provided context, as we found this to perform better than only above or below") (`docs/instruction-file-sizing-evidence.md` §1). Anthropic's own structure guidance ("organized sections are easier to follow than dense paragraphs," same section) is deliberately not cited alongside it — that statement supports headers-and-bullets structure, not start/end positional placement, and pairing it with OpenAI's quote would repeat the same over-citation shape this move is correcting, just smaller in scope (`ai-instruction-and-memory-files` plan-review, 2026-09-03). The move itself is unchanged — only the rationale is corrected; SKILL.md's own over-citation is fixed separately, per the new scope item below. Safety currently sits at L114-137, mid-file. Move that section to immediately after the `# Global Instructions` title as a **pure line move**, no content edit, in its own commit. Deliberately *not* a full reshuffle: the tail (Prose and Output Format → Code Comments → Shipping) stays exactly as-is, because `test_output_preferences_layering.py:92` extracts the Prose section by heading and a full reorder buys little over the single highest-value move. Cross-references survive because they are by name, not position (L88 "Safety's marker bullet"; L102 "the Agent Briefing section's..."), with one exception: L130's "the confirm-before-destructive-action rule **above**" refers positionally to Engineering Judgment's L8, and the Safety move inverts that ordering — Engineering Judgment moves from before Safety to after it. Add a follow-up one-line content commit, after the pure-move commit, rewording L130 to name the rule by section ("Engineering Judgment's confirm-before-destructive-action rule") rather than by position, matching the file's own name-based practice at L88 and L102. A sweep of the file's other positional phrases (L102, L106, L107, L140, L152) found each section-internal — referring to a bullet earlier or later in the *same* section, which the Safety move does not reorder — so this is one line to fix, not a class.

**1D. The byte-size gate.** **2026-09-03 engineer decision, superseding the design below** `[engineer-verified]`: the ratchet measures **bytes and rule count**, dropping tokens as a dimension entirely — no vendor publishes a token-denominated budget for this file family (`docs/instruction-file-sizing-evidence.md` §1), so converting through a reverse-engineered bytes-per-token ratio would add tokenizer-specific variance for no gain over the byte figures Anthropic already publishes directly. Only the **bytes** dimension ships in this plan; **rule count does not** — see the open-question callout below.

*Bytes dimension — implemented, as a shared-hook extension, not a new pytest module.* Extend `claude/.claude/hooks/check-claude-md-length.sh` with a byte-size check alongside its existing 200-line check, using the same ratchet-with-relief semantics `_lib_staged_length_gate` already provides for lines: deny a commit only when the staged file is *already over* the byte limit *and* longer than the previously committed version, so a file already over the limit can still shrink commit by commit with no denial. This applies to **every stow consumer**, not just this repo — the same scope the existing 200-line check already has.

- *Where the byte figure comes from.* Anthropic states no byte figure for CLAUDE.md itself. The nearest in-family precedent is `MEMORY.md`'s own stated load window — "the first 200 lines or 25KB, whichever comes first" (`docs/instruction-file-sizing-evidence.md` §1) — used here as an **extrapolation from a sibling file**, not a measurement of this repo's file. `claude/.claude/CLAUDE.md` is currently 178 lines / 31,143 bytes: already over 25KB while still under the 200-line cap. That gap — a file that reads as "under budget" by the only cap `check-claude-md-length.sh` currently enforces, while already exceeding the nearest sourced byte figure — is the exact motivation for this addition, not an incidental fact.
- *Why the shared hook, not a repo-scoped pytest ratchet (reverses the design below).* The earlier objection to extending `check-claude-md-length.sh` — a cap derived from *this repo's own file* would fire on unrelated projects' CLAUDE.md files — does not apply to a figure sourced from Anthropic's own docs: 25KB is not derived from this repo's file, so applying it to every stow consumer's CLAUDE.md is correct, not incidental over-reach. The remaining part of the original objection still holds and still shapes the implementation: widening `_lib_staged_length_gate` itself (used by both `check-claude-md-length.sh` and `check-skill-length.sh`) to bytes would change `check-skill-length.sh`'s behavior too, which this plan does not intend. The byte check must therefore be added as logic scoped to `check-claude-md-length.sh` alone — a sibling helper or an opt-in parameter `check-skill-length.sh` does not pass — not as a blind widening of the shared function. The exact shape (new `_lib.sh` helper vs. an additional parameter) is an implementation-time call for the code-writer dispatch, constrained only by "does not change `check-skill-length.sh`'s observed behavior."
- *Bytes, not lines, and not tokens.* Lines are already gated at 200 by `check-claude-md-length.sh:63-74`, and line count does not measure context cost in this file: L102 is a single unwrapped ~1,200-char line costing one line, while the plan-mode bullet at L80-85 is one rule hard-wrapped across six. Under a line-only gate, unwrapping is free and wrapping is penalized — the metric is backwards for the thing it proxies. Bytes are not a token proxy either — see the dropped-tokens decision above; the byte figure is used because it is the figure a vendor publishes, not as a stand-in for a token count.
- *Failure message.* Match the existing hook's message shape (`check-claude-md-length.sh`'s over-limit line, `_lib_staged_length_gate`'s `$messages` format): name the actual and budgeted byte counts alongside the existing line-count report, then the two legitimate resolutions in order — offset the addition with a cut of equal size in the same file, or note in the PR that the byte limit itself needs revisiting (this repo cannot raise a vendor-sourced constant unilaterally the way it could raise a self-measured one; see the open-question callout for what a future revision to this figure would need). `GATE_LABEL` (parsed verbatim by `transcript-analysis.py`'s `_denial_hook_label`) must not change — extend the message body only, never the label prefix. The lead-in sentence ("Reduce to the limit or fewer lines before committing") also needs rewording so it stays accurate when only the byte dimension, not the line dimension, is violated.
- *Single combined deny.* `_lib_staged_length_gate` accumulates every over-limit file into one `$messages` string and calls `_lib_emit_deny` exactly once per invocation. The byte check must resolve into that same single call — not a sequentially-invoked sibling function that calls `_lib_emit_deny` a second time. A commit violating both the line and byte dimensions would otherwise print two JSON objects to stdout, which most harnesses parsing `PreToolUse` output as one JSON document would mis-parse or silently truncate to the first, dropping the second denial reason. This is why the `_lib.sh` change (below) is an opt-in parameter threaded into the existing single-pass loop, not a sibling helper invoked afterward (`claude-hook-review`, 2026-09-03).

*Rule-count dimension — declined, not deferred.* `plan-architect` (consult, 2026-09-03) resolved this rather than leaving it open. No source in `docs/instruction-file-sizing-evidence.md` gives a defensible rule-count threshold: §2's peer-reviewed instruction-count-degradation studies (FollowBench, ComplexBench, "When Instructions Multiply," SIFo, InfoBench, CELLO) establish that adherence falls as instruction count rises, but their independent variable is instructions *all live on the one task being scored*, not dormant rules sitting in an always-loaded file — a large majority of this file's rules are dormant on any given turn, so the measured direction does not transfer to a file-level count at all. The one source with a quantified curve (IFScale) is an unreviewed preprint on a narrow, non-transferable task. Both candidate ways to mechanically count "a rule" are perverse in opposite directions: counting top-level bullets (`^- `, 67 in the current file) lets an author add a rule with no counter movement by appending a clause to an existing bullet via a semicolon; counting all bullets/sub-items (104) rewards a dense paragraph and penalizes an author who complies with this file's own "one idea per sentence" / "split multi-fact comments" rules by pushing the counter up when they comply. **No absolute threshold may be asserted without a source that states one, and none exists** — so gating is foreclosed, and a self-measured floor (freeze at today's count) reintroduces exactly the invented-threshold problem the engineer already moved away from for bytes. Report-only is also declined: an uninterpretable number has no consumer and invites someone downstream to invent the threshold this plan declines to invent. The byte gate already covers the real risk — rules and bytes co-move, so accreting rules without accruing bytes isn't possible, and the one divergence case (more rules, fewer bytes) is a desirable compression this plan doesn't want to discourage. What ships instead: one sentence in 1E's SKILL.md §2 edit, pointing at `docs/instruction-file-sizing-evidence.md` §5, stating that no source supports a rule-count threshold for an instruction file. Recorded as a closed decision in §44, with a re-opener condition: a source measuring adherence over the count of dormant rules in an always-loaded file that states a threshold or per-rule marginal cost, or a vendor publishing a rule-count figure for CLAUDE.md/AGENTS.md analogous to Anthropic's 200-line figure. Absent one of those, this stays declined — not re-derived by the next planning pass.

*Superseded design (kept for history, not followed):* the original plan for this section built a new pytest module, `claude/.claude/hooks/tests/test_claude_md_budget.py`, asserting `len(claude/.claude/CLAUDE.md bytes) <= GLOBAL_CLAUDE_MD_BUDGET_BYTES` with the constant set to the measured post-Phase-1 byte count at zero headroom — reasoning: every candidate allowance was invented, so the measured size was the only figure in the design that was itself a measurement, and the accepted friction was that any byte-increasing edit must pair with an offsetting cut or raise the constant in the same commit, with a dated log of prior values in the constant's docstring so a reviewer could see the accrued trend rather than only a single-PR delta. That reasoning is superseded by the engineer decision above: the constant is no longer self-measured (removing the zero-headroom framing), and the ratchet is no longer this-repo-scoped (removing the reason pytest was chosen over the shared hook). The dated-log-of-prior-values requirement carries forward unchanged to the shared hook's own docstring/comment, for the same reason it was needed here — a single-PR delta is not a trend.
- *Two precedents considered — superseded framing.* `SKILL_LISTING_BUDGET_CHARS` (8,000, `claude/.claude/skills/tests/test_skills.py`) remains correctly **distinguished, not followed**: it is derived from an independent harness truncation constant, not from the skill corpus's own current size or from any vendor-published figure, so it doesn't answer how a reviewer would notice accrued drift and isn't a model for a vendor-grounded byte cap either. `check-claude-md-length.sh`'s 200-line cap and its `_lib_staged_length_gate` ratchet-with-relief semantics were originally listed as a rejected precedent for the reason above (unrelated-repo blast radius); that rejection is now reversed for the byte dimension specifically — see "Why the shared hook" above — while the underlying ratchet-with-relief *mechanism* (deny only when already-over-and-growing) is adopted, not merely distinguished.
- *Why pytest and not the existing hook — reversed.* The original text here argued a pytest test in this repo's suite scopes to this repo's file correctly, using `select-tests.py:332`'s existing `GLOBAL_CLAUDE_MD` → `HOOKS_TESTS_DIR` + `SKILLS_TESTS_DIR` routing to pick the ratchet up automatically. That argument no longer applies: the mechanism is not this-repo-scoped once its threshold is vendor-sourced rather than self-measured, so scoping enforcement to this repo's own test suite is the wrong shape — every stow consumer's CLAUDE.md should get the same check, which only the shared hook delivers.

### Phase 2 — recommendation: do not build the `SessionStart` deferral

The proposal is structurally attractive: inject the ~12,181-byte orchestrator-only block at session start, before any delegation decision, with none of the dispatch-time friction the engineer rejected. It should still be declined, for four reasons in descending weight:

1. **It converts a vendor-guaranteed load into a locally-scripted one whose failure is silent.** A missing, non-executable, or erroring `SessionStart` hook drops 12 KB of instructions with no denial, no tool error, and no user-visible symptom — the session simply behaves as if Agent Briefing and Model & Effort Routing were never written. CLAUDE.md loading has no such failure mode. This lands on every stow consumer in every repo.
2. **It moves rules onto a surface of unmeasured adherence in order to improve adherence.** `additionalContext` enters as conversation-position text, not the memory block. No measurement exists comparing the two. Phase 1's own goal makes this trade self-defeating unless measured first.
3. **The saving lands in the smaller cost slice.** The block stays in the main thread — 71.4% of dollar cost (`docs/design-decisions.md:283-289`) — and is removed only from the 28.6% subagent slice, against a spend profile dominated 92.9% by idle-gap cache rebuilds whose *frequency* is unrelated to byte count (`docs/cost-levers-considered.md:194-215`).
4. **Its premise is unverified.** The whole design depends on `SessionStart` not firing for subagents. The evidence is strong but circumstantial (`capture-session-id.sh:26-27` dual-registers on `SubagentStart` "in addition to" `SessionStart`, and is the only one of five `SessionStart` hooks to do so). Building on it before an empirical check inverts the order.

Compaction durability and fork inheritance are **not** blockers — `SessionStart` fires with `source: compact` and `restore-authorization-boundary-on-compact.sh` is working precedent, and a fork carries the parent's context. Those were the two objections worth checking that turned out answerable; the four above are not.

**What to do instead, if Phase 1's reconciliation still shows a gap** — each lighter than the rejected mechanism, listed in the order they should be attempted:

- **Trim the CLAUDE.md restatements out of the agent files.** `code-writer.md:56-65` and `:99-109` restate §Engineering Judgment / §Scope Discipline / §Code Comments twice, and `staff-backend-engineer.md:67` once. Since every subagent already receives the full CLAUDE.md, these are redundant *today* — cutting them reduces per-dispatch context with zero adherence risk to the main thread and no new mechanism. This is the correctly-shaped fix for the per-subagent-cost problem.
- **A narrow `PreToolUse`-on-`Agent` validation hook** — not the Read-gate the engineer rejected. A hook that inspects the dispatch's `subagent_type` and `model` and denies only a violation (e.g. `general-purpose` with no explicit `model`, per L106) is silent when a skill has already prescribed the dispatch correctly, so the friction objection does not apply. Success would let L106 shrink to denial-shape under #741 plan's armed-and-complete check.
- **Move dispatch mechanics into the dispatching skills** (`subagent-delegation`, `plan-it`, `code-review`). Covers prescribed dispatches only, not ad-hoc ones — partial, so it ranks last.

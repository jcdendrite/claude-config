# Let /ready-for-review run for a stacked PR

## Context

Goal: a branch stacked on another open PR's branch can complete `/ready-for-review` against its stack base instead of the default branch.

Ask: cited to the engineer-attached brief "Brief: let /ready-for-review run for a stacked PR (base is not the default branch)", on which the engineer invoked `/plan-it`. Widened during implementation review by the engineer's selections: "conftest.py shared builder", "respond-pr/SKILL.md:24 clause", "docs/skills.md:10 phrase", "respond-pr: retry once, then stop", "Add the 2 hook deny strings", "docs/skills.md: 'PR-vs-base diff'", plus "Have the architect adversarially review those choices", and later "ready-for-review L77 clause", "git-feature-branch-sync L28-32", "Comment-only edit (Recommended)" for the hook header, "Use the documented path (Recommended)", "Add one clause (Recommended)" for the sync failed-recipe arm, and "Both sound good to me but what does the architect think?" for the `docs/skills.md` L17 phrase, then "Keep, log as SETTLED (Recommended)" for the unscanned key-read base gap, "Keep, authorize a plan edit" for the hook header and "Add it, list both files in the plan (Recommended)" for the `docs/private-project-redaction.md` sentence, then "Trim it, keep accepted wording (Recommended)" and "Merge into one bullet (Recommended)" in the cumulative review, "Keep one bullet, log SETTLED (Recommended)" for the merged hook bullet, "Supersede, stop accepted (Recommended)" for the round-22 row, "One clause in docs/hooks.md (Recommended)" for the armed-marker remedy, "Yes, edit the plan for both (Recommended)" for these plan edits, "Build the real fix now" for the divergence script reading an open PR's base, and "No, leave it as today (Recommended)" for leaving a set key that disagrees with the PR as it is. The engineer's earlier "Yes I think so" to a step-1 key write is superseded (row 73).

Problem: `pr-diff-against-base.sh` resolves the base from `gh pr view --json baseRefName` and falls back to the default branch when no PR exists. `/ready-for-review` opens the PR last (step 8), so for a stacked branch the cumulative diff is taken against the default branch and includes the whole base PR's work, which has already had its own cumulative review. The push gate requires the ready-for-review marker, so the PR cannot be opened first to fix the base. `marker.sh status` re-runs `pr-diff-against-base.sh` with no arguments to recompute the `cumulative-review` hash, so any base override must be visible to that no-arg call as well. Step 8's `gh pr create` passes no `--base`.

Intended outcome: the engineer states a stack base once, every base-dependent step (divergence check, cumulative diff, fidelity-review diff file, behind-base recheck, `gh pr create`) uses it, and a stale base fails closed.

## Approach

The engineer names a stack base once, in gh's own per-branch key `branch.<branch>.gh-merge-base`. With the key set, every base-dependent step uses its value or stops with one line: an unusable value gets the key fix, a git read failure says to retry the command, and a fetch failure says to retry before changing the key. With no key set, every step resolves its base as on main, with the three hardening changes Design item 4 lists, except that `branch-divergence-status.sh` also measures against an open PR's base (row 75).

**Design.**

1. **Source of truth.** `git config branch.<branch>.gh-merge-base <stack-base>`, called "the key" below.
   - `gh pr create` already reads it when `--base` is absent (row 15), and gh's checkout and create code never write it (row 16).
   - `ready-for-review` step 1 sets it only from the engineer's own words, never by inference. For an existing open PR with no key set, `branch-divergence-status.sh` itself reads the PR's base, measures against it, and writes nothing (engineer's "Build the real fix now", rows 75 and 76).
2. **One rule: with the key set, use its value or stop.** The gate stops when the value:
   - cannot be read, meaning any `git symbolic-ref`, `git config` or `git check-ref-format` status other than 0 and 1 (for `check-ref-format`, 1 means "not a valid branch name"), a cap kill included (row 26);
   - is not a usable branch name: empty, starting with `-` or `origin/`, rejected by `git check-ref-format "refs/heads/<value>"`, holding a character outside `[A-Za-z0-9._/-]`, `HEAD`, or this branch's own name (rows 18, 48, 50). The character set keeps shell metacharacters, quotes and bidi controls out of stop lines and out of commands the engineer copies;
   - cannot be fetched from origin, checked by `branch-divergence-status.sh` at steps 1 and 6. A timeout and a deleted branch fail alike there (row 11), so the reason reads "fetch failed (network, or the stack base is gone from origin)", tells the engineer to retry the command before changing the key, and, if the retry fails again, names `git ls-remote origin refs/heads/<base>` as the discriminator (nothing printed means the base is gone, an error means network or auth);
   - differs from the base of this branch's OPEN PR, checked by `pr-diff-against-base.sh` at step 3. A merged or closed PR's base is ignored (row 30).

   Every stop exits non-zero with one stderr line. A read failure prints the helper's own line, which names the failed git call and its status and says to retry the command and, if it fails again, to run that git call by hand, because the failure is git's, not the value's, and a key edit would not fix it (row 48). Every other stop takes its line from one formatter, which `%q`-quotes the branch and the value. That line names the script, the key, its value and the reason, gives the fix, and says the engineer runs it, not the agent:
   - `git config --replace-all branch.<branch>.gh-merge-base <stack-base>` corrects the value.
   - If the stack base merged, the engineer rebases this branch's own commits onto the branch it merged into, `git rebase --onto origin/<merged-into> <old stack-base commit>`, then runs `git config --unset-all branch.<branch>.gh-merge-base`. The line names no fork point (Out of scope).
   - The open-PR reason also offers `gh pr edit --base <value>`.

   Steps 1 and 6 halt when the divergence script fails, and `respond-pr`'s precheck stops after one re-run (item 7). A failed `status` recompute never reads `live`, so step 3 runs `pr-diff-against-base.sh` itself and halts on its failure (row 34). Every stop therefore lands before step 7's marker, on the CI-watch path too. `pr-diff-against-base.sh` never fetches (row 7), so it can read a deleted stack base's stale local ref. Step 1's fetch is what catches a deleted stack base, and the design doc records that ordering dependency.
3. **Helpers in `claude/.claude/hooks/_lib.sh`**, beside the default-branch layers (row 23):
   - `_lib_configured_stack_base STDERR_PREFIX REPO_ROOT` derives the branch from `git symbolic-ref -q HEAD` with `refs/heads/` stripped, reads the key with `git config --get`, and validates the value. Only `git config` exit 1 means unset.
     - Exit 0 prints `<branch> <value>` on one line. Branch names cannot hold a space, so the split is unambiguous.
     - Exit 1 means no key or a detached HEAD, with no output.
     - Exit 2 means a stop, with empty stdout and one stderr line: the formatter's for an unusable value, the helper's own retry line for a read failure.
     - All three git calls (`symbolic-ref`, `config`, `check-ref-format`) go through `_lib_stack_base_git`, which runs `_lib_capped`, returns git's 0 or 1, and for any other status prints the one read-failure line and returns 2. `check-ref-format` status 1 stays the "not a valid branch name" stop. Each status is tested explicitly. Callers capture with `rc=0; out=$(...) || rc=$?`, which suspends `set -e` inside the function (row 28), and treat every status other than 0 and 1 as a stop.
   - `_lib_print_unusable_stack_base STDERR_PREFIX BRANCH VALUE REASON` prints the stop line. It is the one home of the fix text. It `%q`-quotes BRANCH and VALUE, because VALUE reaches it before validation.
   - `_lib_stack_base_git STDERR_PREFIX CALL_LABEL REPO_ROOT ARGS...` is the read-failure line's one home (above).
   - `_lib_open_pr_base REPLY` takes `pr-diff-against-base.sh`'s two-line `gh pr view` reply, exits 0 and prints the base only for a first line `OPEN` and a non-empty second line, and exits 1 otherwise. It holds the parse that `pr-diff-against-base.sh` would otherwise inline (`.claude/rules/shell-script-conventions.md`).

**Alternatives set aside.**

- **A `--base` flag on `pr-diff-against-base.sh`.** `marker.sh status` calls it with no arguments (row 8), so the flag would still need a persistent store.
- **An environment variable.** It does not survive across Bash tool calls or sessions, so a later `status` call would not see it (row 8).
- **A new key such as `branch.<name>.rfr-base`.** Same mechanism as the chosen key, but gh ignores it (row 15), so a hand-run `gh pr create` would target the default branch.
- **Pointing the branch's upstream (`branch.<name>.merge`) at the stack base.** Steps 6 and 8 rely on the branch's own `origin/<branch>` tracking (row 33).
- **Auto-detecting the base from open PR heads.** It needs a network scan and a heuristic the engineer would confirm anyway.
- **One resolver with a precedence chain (open PR, key, closed PR, default) and PR-lookup and default-layer parameters.** `pr-diff-against-base.sh` reads a PR on every path, and the divergence script reads one only with no key (row 75). The two read it for different questions and with different failure handling, so a shared precedence chain would couple them.
- **A named trigger per cause, each with its own remedy text.** The causes differ only in the reason clause, so one formatter holds the fix text once.
- **A check that the stack base's own PR merged** (`gh pr list`, a tip comparison and an acknowledgement key). Dropped per row 6, and its case goes to Out of scope.
- **Letting an open PR's base silently override a disagreeing key.** It hides a retarget or a wrong base, against row 2's posture (row 4).
- **Folding the base ref into the `cumulative-review` hash.** It contradicts the recorded decision in row 9.
- **Treating a key equal to the default branch as unset.** Such a key measures against the same branch, so only the output label would differ.
- **Relying on gh's key read at step 8.** It keeps the base out of the command text the redaction hook scans (row 31).
- **`git fetch origin <base>` under the configured refspec.** A narrowed `remote.origin.fetch` leaves `origin/<base>` missing or stale while the fetch succeeds (row 27).
- **Printing a fork point in the stop line, or adding a `git rebase --onto` recipe to the sync skill.** The line names `--onto` and leaves the old base commit to the engineer, who runs the rebase, and Out of scope records the gap.
- **Routing a failed recipe in `respond-pr` to `/git-feature-branch-sync`.** That skill's detection runs the same script (row 42), so it repeats the failure, and a stack-base stop's fix is the engineer's key edit.
- **Stopping `respond-pr` without a re-run, or re-running only a fetch failure.** The fetch stop's own line says to retry before changing the key. Telling a fetch failure from a key stop would mean parsing stderr to save one 2-second-bounded run.
- **Widening the sync skill's frontmatter trigger to name a stack base.** Its TRIGGER clause reads "syncing a feature branch with the default branch", but the entry points this plan touches invoke `/git-feature-branch-sync` by name (`ready-for-review/SKILL.md` L44 and `check-branch-divergence.sh` L123 and L128), `respond-pr/SKILL.md` L24's CONFLICT arm only routes the user to it, and the skill is not user-invocable, so that path and any ad-hoc stacked-branch request rest on the description's first line, "Rebase vs merge a feature branch; force-push safely." An ad-hoc stacked-branch request still meets the description's first line, "Rebase vs merge a feature branch; force-push safely." Widening it would gate no flow this plan adds, and the description loads for every stow consumer (row 69).
- **Keeping both stacked-repo builders, or making the shared one a pytest fixture.** The two copies already differ in commit file, push and parameters (row 39). Callers pass per-test arguments, as callers of the plain function `_make_repo_with_remote` do.

**Assumption ledger.**

Root. `/ready-for-review` takes every base-dependent fact from an open PR's base or the default branch: the sync check, the cumulative diff, the fidelity diff file, the behind recheck, and the PR's target. It has no way to learn a stack base before the PR exists, so a stacked branch is reviewed against the default branch, the base PR's work included.

Givens.
- G1. GitHub sets each PR's `baseRefName`, deletes or keeps a merged base branch, and decides whether to retarget a stacked PR. Reason: GitHub and each repository's admins own these.
- G2. gh defines what the `gh-merge-base` key means, which gh commands read or write it, and which gh versions read it. Reason: the vendor owns it.
- G3. `ready-for-review/SKILL.md` stays within the 200-line cap. Reason: `check-skill-length.sh` sets the cap repo-wide (`docs/skills.md` L155), and changing it needs a decision outside this plan.

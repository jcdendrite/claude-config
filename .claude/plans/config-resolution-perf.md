# _config.sh: cut per-lookup schema re-reads and subprocess forks

## Context

Cut the per-call filesystem/subprocess cost of `claude/.claude/hooks/_config.sh`'s config-key resolution path without changing any resolution semantics, grammar, or Python parity. A single `_config_value`/`_config_enabled` call for one key today re-parses `config-keys.psv` up to seven times — `_config_value` calls `_config_schema_field` separately for `resolution` and `legacy-probe-on-resolution-failure`, and (for a `config-dir-or-home` union key with a diverged `$HOME`) also calls `_config_schema_known_keys` and three more `_config_schema_field` calls for `type`/`legacy-filename`/`legacy-polarity` — each a full re-read of the same 15-row schema file, plus `_config_line_key_value`/`_config_location_value` each fork a `tr` subprocess per state-file line for case-folding. This repo's `PreToolUse` hooks run this path on every `Edit`/`Write`/`MultiEdit` and every git write (11+ call sites), so the per-call overhead compounds against the documented <100ms-per-fire hook budget (`docs/config-file.md`'s Performance section measures ~22ms added per `_config_enabled` call). GitHub issue #998 prescribes three fixes, all confirmed against `docs/design-decisions/sentinel-config-consolidation.md`'s own performance paragraph as the design doc's intended remediation: (1) one schema pass per `_config_value` lookup instead of up to seven, (2) replace the `tr` subprocess fork with a bash-3.2-safe `case` statement, (3) per-process memoization so a repeated lookup of the same key within one process's lifetime skips re-resolution. This is a pure implementation-efficiency change — the file format, config schema, and per-call (not per-session) resolution model are all explicitly out of scope per that design doc.

## Approach

Collapse `_config.sh`'s per-lookup schema re-reads into one pass, gate the `tr` fork behind a `case` test so it never runs for an all-lowercase file, and memoize `_config_value`/`_config_enabled`'s final per-key result in a single delimited-string cache that `_config_set`/`_config_scaffold` reset. Every public contract — exit codes, arity-guard texts, stderr wording, resolution order — stays byte-identical, so the existing behavioral suites are the proof.

Three findings shift the design away from the issue's literal prescription, all verified this session:

**The `tr` fork does not need replacing — it needs a guard.** `_config_read_key_from_file` walks every state-file line, and `_config_line_key_value` forks one `tr` per line: ~15 forks per location read, up to ~30 for a `config-dir-or-home` union key. Wrapping the existing call in `case "$value" in *[A-Z]*) <existing tr> ;; esac` drops that to zero for every machine-written state file (`_config_set` writes `true`/`false`/a lowercase enum literal), and to at most two on a machine carrying a hand-authored `TRUE`. A hand-rolled 26-arm ASCII folder would buy those last two forks at the cost of ~35 lines of new string-manipulation code inside the file that decides whether worktree enforcement is armed — the heavier primitive for a rounding error. It is also the option CLAUDE.md's hand-rolled-logic rule argues against while `tr` remains available. Set aside; if the engineer wants the fork gone unconditionally, that is a follow-up with its own review surface.

The guard is fail-safe in either direction for the call site that already scopes its locale. `_config_line_key_value` already holds `local LC_ALL=C`, so `[A-Z]` there is exactly the 26 ASCII bytes, confirmed by reading the function — this call site needs no further change. `_config_location_value`'s `content-matches` branch (the only key using that legacy-polarity today is `pr_cost_disclosure`, not one of the five enforcement-critical keys) has no such `local` today, so its `[A-Z]` guard would otherwise rest on an unverified assumption about every collation on every platform this file targets — including macOS/Darwin bash 3.2, which this file's own header names as its binding constraint and which a same-machine probe in this session (glibc/Linux bash 5.2 only) cannot confirm. Rather than accept that assumption, this function gains its own `local LC_ALL=C` — the same one-line scoping `_config_line_key_value` already carries — so the guard's correctness no longer depends on an unverified cross-platform claim. With that scoping in place, over-matching still costs a fork (the `tr` branch keeps its own `LC_ALL=C` prefix and reproduces today's exact output) and under-matching cannot occur (ASCII `A`-`Z` is unconditionally matched by `[A-Z]` under `LC_ALL=C`, the same guarantee `_config_line_key_value`'s existing guard already relies on).

**The single-pass helper collapses seven passes to two, not to one.** A new `_config_schema_row KEY` does one `IFS='|' read` walk of `config-keys.psv`, populating `_CONFIG_ROW_TYPE`/`_DEFAULT`/`_RESOLUTION`/`_LEGACY_PROBE`/`_LEGACY_IMPORT`/`_LEGACY_FILENAME`/`_LEGACY_POLARITY`/`_HUMAN_NAME`/`_DOCS_ANCHOR`/`_PROMPT_DESCRIPTION` plus `_CONFIG_ROW_KNOWN_KEYS` (the `" k1 k2 "` membership list, free in the same pass). It follows `_config_trim`/`_config_quote_value_for_write`'s established global-result idiom rather than printing for `$(...)` capture, because a capture fork is the cost this change exists to remove and bash 3.2 has no `local -n`. It captures fields from the **first** matching row while scanning to end-of-file for `known_keys` — `test_config_parser_parity.py:444` pins schema-row first-match-wins against `_config_schema_field`'s in-loop `return`.

`_config_value` then calls `_config_schema_row` once and threads the result down through the already-existing 6-arg `_config_location_value` / 4-arg `_config_read_key_from_file` precomputed forms on **every** path, not just the union-active one. What remains is `_config_location_value`'s closing `_config_schema_field "$key" default`, one further pass, reached only when neither a state-file row nor a legacy file resolved the key. Threading `default` as a seventh argument would remove it, but `TestPrecomputedArgsArityGuard` pins the literal `"expected 2 or 6 args, got %d"` text with `got 3` and `got 5` assertions. Set aside: at most two passes per lookup (three for a union key falling through at both locations), down from seven-plus, is the whole win, and it costs no contract.

Truncation semantics forbid validating eagerly. `_config_schema_field` returns 4 only for the *specific* resolution-critical column a caller asked for, so `_config_value` must check `resolution` empty, then `legacy_probe` empty, in that order — that ordering is what makes `autonomous_shipping|bool` and `worktree_required|bool|false|config-dir-or-home` both return 4 at their two different pinned points. Validating all four resolution-critical columns inside `_config_schema_row` would name the wrong field in the warning and would turn a hand-corrupted-but-resolvable row (`key|bool||config-dir|...`, empty `default`, state-file row present) into a spurious exit 4. A one-line `_config_warn_truncated_row KEY FIELD` helper keeps the warning text in one place and is called at each consumption point.

`_config_schema_field` is rewritten to delegate to `_config_schema_row` and map FIELD onto the right global, preserving its name, signature, exit codes, and the ordering that makes an unrecognized FIELD return 1 only when KEY's row was found (and 4 otherwise). `_config_read_key_from_file`'s 2-arg self-deriving branch keeps calling `_config_schema_known_keys` **by name** and is deliberately left uncollapsed — that is the path `_migrate_process_key` uses, and `test_migrate_legacy_config.py:293` overrides that function as a bash stub. It is not on the hot path, because `_config_value` now always reaches the 4-arg form.

No caching at the schema-read level, per the session's resolved constraint: `config-get.sh:53-71` performs two deliberate independent schema reads to close a TOCTOU window, and a row cache shared across them would silently retire the second `[ -r ]` check. Each `_config_schema_row` call re-reads and re-checks readability, exactly as `_config_schema_field` does today.

**Memoization needs invalidation, and the repo has a real cache hit the Step 4 answer missed.** `advance-past-commit-stall.sh` resolves `autonomous_shipping` twice in one process: line 77 (`_lib_autonomous_shipping_sentinel_present`, the pre-`REPO_ROOT` fast path) and line 181 (`_lib_autonomous_shipping_active`, which calls the same helper again). Both are bare commands in the top-level shell, not `$(...)` captures, so a parent-frame memo hits. That second lookup is the most expensive shape in the repo — a `config-dir-or-home` union key walking two locations — and it lands on exactly the machines where autonomous shipping is on. `nudge-handoff-near-context-cap.sh` calls `_config_enabled handoff_nudge` at lines 396 and 508, but those are the `--check` and fire paths, mutually exclusive in one process.

The staleness hazard is in `install.sh`, not `_lib.sh`. `_prompt_sentinel_opt_in` reads `_config_value "$key"` (line 438), writes `_config_set "$key" false` (448), then re-reads `_config_value "$key"` (458) and *must* see the write — `test_install_sh_machine_level_opt_ins.py:459` asserts `"→ disabled"` on that second read. `report_sentinel_inventory`'s own header (install.sh:646-649) documents the same invariant across functions. Both reads happen inside `$(...)`, so a naive memo survives by luck. The design does not rely on that: `_config_set` and `_config_scaffold` each call a one-line `_config_memo_reset` before returning, closing the class by construction. `migrate-legacy-config.sh` is unaffected either way — it uses `_config_read_key_from_file`, never `_config_value`.

Memo shape: a single delimited string, `_CONFIG_MEMO_CACHE`, formatted `" key1=value1 key2=value2 "` and queried with the same space-padded `case " $list " in *" $key "*)` idiom `_config_schema_known_keys` (lines 409-445) already establishes in this file, extended one step further with parameter-expansion extraction of the value half. This reuses an already-precedented pattern rather than introducing a new one, and it has no two-structure desync failure mode the way a pair of parallel indexed arrays would (an append to one array with no matching append to the other, silently misaligning index-based lookups with no error). No delimiter-collision risk: a memoized key is always schema-declared snake_case (`config-keys.psv`'s own documented grammar), and — because only exit 0 is ever memoized (see below) — a memoized value is always drawn from `true`/`false`/`[a-z0-9_-]+`, the same grammar `_config_line_key_value` already enforces and which can never contain a space or `=`. Two alternatives were weighed and set aside:

- **Dynamic variable names via `printf -v` plus `${!name}` indirect expansion.** Two distinct hazards, only one of which is actually decisive. Indirect expansion of an unset target under `set -u` is not decisive: the guarded idiom `${!name:-SENTINEL}` sidesteps an unset indirect target without tripping `set -u` at all (confirmed on a bash 5.2 probe this session; not independently confirmed on bash 3.2, so this doesn't resolve whether the guarded form itself behaves identically there, but it does mean this hazard alone would not have ruled the approach out even if it had). The actually decisive hazard is `printf -v` rejecting a hyphenated variable name outright — every current `config-keys.psv` key is schema-documented snake_case, so no live key trips this today, but a future hyphenated key would silently break the scheme with no compile-time signal. Forward-compatibility hardening, not a live bug, but real enough to prefer the string-based approach below.
- **Two parallel indexed arrays (`_CONFIG_MEMO_KEYS`, `_CONFIG_MEMO_VALUES`) with a linear, `${#arr[@]}`-guarded scan.** Bash-3.2-safe and legitimate, but carries the desync failure mode the single-string design avoids, and duplicates a "is X a member of this list, and if so what's its paired value" query shape this file already solves once via `_config_schema_known_keys`'s idiom. Set aside in favor of reusing that idiom directly.

Three rules keep it correct:

- **Memoize only when `config_dir_override` is empty.** An override is an arbitrary filesystem path and would have to become part of the cache key; no bash caller passes one (only `_config.py`'s `config_dir_override` parameter, a separate reader), and every hook call site is zero-override. This dissolves the composite-key problem instead of defending it.
- **Memoize only exit 0.** Exits 2, 3, and 4 are transient-environment failures; re-resolving them costs nothing on a cold path and keeps every readability and resolution check live on each call.
- **`_config_enabled` checks the memo before calling `_config_value`,** so a hit skips the `$(...)` fork too, and stores on a miss in its own frame — `_config_value`'s own store is lost to the subshell when it is called that way. Reading before storing means a duplicate entry cannot be appended.

Cost when the memo never hits (nine of the eleven call sites): one case-glob scan of the (typically empty or single-entry) memo string and one append. No forks, no file I/O.

**Global-return scoping needs an explicit invariant, not just correct call-site tracing.** `_config_schema_row`'s ~10 `_CONFIG_ROW_*` globals and the single `_CONFIG_MEMO_CACHE` global are safe as designed — tracing the call shape, `_config_value` copies the fields it needs into its own locals immediately after calling `_config_schema_row` and never re-reads `_CONFIG_ROW_*` after a later call (inside `_config_location_value`'s closing `default` fallback) overwrites them for the same key. But bash `local` is dynamically, not lexically, scoped: a `local` declaration sharing one of these names *anywhere* up the call stack — now or in a future edit — would silently intercept the plain assignment and redirect it into that shadow, with no error. This is a materially larger surface than this file's two existing global-return helpers (`_config_trim`'s `_CONFIG_TRIM_RESULT`, `_config_quote_value_for_write`'s `_CONFIG_QUOTE_RESULT`), both single-name leaf functions with no nested calls, because the new design threads ~10 names through a 3-level call chain. The invariant — copy into a plainly-named local immediately, never declare a `local` shadowing a `_CONFIG_ROW_*`/`_CONFIG_MEMO_*` name anywhere in this file — is stated as a comment on the global declarations and enforced by a static grep-based test (Critical files, below), closing the class by construction rather than by review discipline.

**The design doc's inline figure becomes a pointer.** `docs/design-decisions/sentinel-config-consolidation.md`:17 restates the `~22ms` figure that `docs/config-file.md`'s Performance section owns, so re-measuring in this PR would update one copy and leave the other stale. The figure is deleted there and the existing parenthetical pointer kept, per CLAUDE.md's single-source-of-truth rule for prose. Nothing else in that paragraph moves: its argument (the cost is implementation, not file format) and its conclusion (fixable inside `_config.sh` alone) are what this PR implements, so they are confirmed rather than revised. The two verbs that carried the deleted figure shift to past tense, because the same sentence's present-tense mechanism claim — seven schema passes, one `tr` fork per state-file line — stops describing `_config.sh` the moment this change lands.

### Assumption ledger

**Root:** one `_config_value`/`_config_enabled` lookup re-parses the 15-row `config-keys.psv` up to seven times and forks one `tr` per state-file line, so every `PreToolUse` gate in this repo pays ~22ms of avoidable work per fire against a documented <100ms budget.

**Givens:**

1. macOS system bash is 3.2 — no associative arrays, no `${var,,}`, no `local -n`. Vendor-imposed; `_config.sh`:19-23 and 121-135 already pin both consequences. `[verified: claude/.claude/hooks/_config.sh:19-23,121-135]`
2. Hook processes are independent, short-lived, and share no memory, so no cross-invocation cache exists to reach for. Owned by the Claude Code hook runtime. `[verified: docs/design-decisions/sentinel-config-consolidation.md:13-15]`
3. `config-get.sh`'s two independent schema reads are a deliberate TOCTOU defense that no lower-level cache may collapse. `config-get.sh` is a repo-owned file this plan could technically edit, but weakening its race-detection behavior is a separate, separately-decidable question (is the detection worth its current cost?) that this issue's own "no resolution-semantics change" scope doesn't authorize deciding here — the reason this counts as a given is that dissolving it needs a decision outside this plan, not that the file is unreachable. `[engineer-verified]`, corroborated at `claude/.claude/scripts/config-get.sh:53-71`

5. `_config.py` needs no change: `schema()` already does one pass per call, folds with in-process `str.lower()`, and documents no-caching as deliberate. `[engineer-verified]`

## Critical files

One `code-writer` dispatch.

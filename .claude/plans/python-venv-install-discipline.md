# Python environment install discipline

## Context

Stop Claude Code agents from installing Python requirements into the machine's system interpreter instead of a project-local venv. The engineer has observed this anti-pattern twice, in two different repos, under two different accounts, and it just recurred — the fix is guidance, not a runtime gate, that reliably steers an agent toward a project environment whenever it installs or restores Python dependencies. The intended outcome: `claude/.claude/CLAUDE.md`'s existing restore carve-out names the right interpreter, and a new stowed rule carries the actual detection-then-defer recipe, so the guidance reaches every repo a contributor's stowed `~/.claude/` touches — not just this one.

## Approach

Two documentation surfaces, no hook. `claude/.claude/CLAUDE.md`'s Safety line 116 gains a clause naming *which* interpreter a Python restore must land in (it currently blesses a bare `pip install -r requirements.txt`, which is the proximate cause of the observed anti-pattern), and a new stowed path-scoped rule at `claude/.claude/rules/python-environment-conventions.md` carries the detect-then-defer recipe, the PEP 668 explanation, and the anti-patterns. The rule auto-loads on Python-file-shaped touches; the CLAUDE.md clause covers the ad hoc case where no matching file was ever opened. External citations go in `docs/rules-references.md` via a `verify-sources` pass at implementation time, and `docs/design-decisions.md` §47 records why this is guidance and not a gate.

**Root problem.** An agent restoring Python dependencies has no instruction naming which interpreter the restore must land in, and the one always-loaded line that mentions the case (`claude/.claude/CLAUDE.md:116`) blesses the interpreter-ambiguous form — so packages land in the system interpreter. Observed twice, across two repos and two accounts.

**Givens** (fixed conditions outside this design's reach):

- **G1 — A Bash gate cannot see which interpreter `pip` will resolve to.** The shared PreToolUse parser exposes exactly `tool_name` and `tool_input.command`; nothing in the payload describes the environment the command's shell will inherit (`PATH`, an active `VIRTUAL_ENV`, a direnv-activated layout). The harness owns that input contract. `[verified: claude/.claude/hooks/_lib.sh:211-248]`
- **G2 — The two surfaces have opposite cost models, both fixed by Claude Code's loading model.** `claude/.claude/CLAUDE.md` loads in every session and every subagent against a hook-enforced 200-line cap; `claude/.claude/rules/*.md` load only when a matching file is opened. `[verified: claude/.claude/hooks/check-claude-md-length.sh:63-74; README.md:248-249]`
- **G3 — Everything under `claude/.claude/` stows into every contributor's `~/.claude/`,** so both surfaces fire in repos this repo never sees. Settled by the repo's packaging layout, not by this plan. `[verified: CLAUDE.md (repo root) "Repo layout"; README.md:249]`

**Ledger rows:**

1. **Two documentation sites, no hook — new or nudging.** `anchors: root`. `[engineer-verified]` — "deny hook is super overkill… this is best practice discipline when running python repos specifically. where does that live?" Lighter-and-heavier primitives weighed against G1: (a) a **deny hook** on `pip install` — cannot discriminate, so it denies the CI-runner and direnv-activated cases that are already correct; (b) a **non-blocking `ask`/nudge hook** — same blindness, so it fires on every already-correct repo and stays silent on the failing one, training the reader to dismiss it; (c) an **auto-memory entry** — per-user, per-working-tree, and this failure crossed two accounts and two repos, so it cannot reach the sites that need it (`ai-instruction-and-memory-files/SKILL.md` §3). The documentation pair is the lightest primitive that reaches all the affected sites.
2. **The CLAUDE.md line must actually change; adding only a rule leaves the cause in place.** `anchors: root`. `[verified: claude/.claude/CLAUDE.md:116]` — the line names `pip install -r requirements.txt` unqualified, so an agent that hits an `ImportError` and recalls it is following instructions correctly as written.
3. **CLAUDE.md gets one clause and a pointer; the rule carries the recipe.** `anchors: row2, G2`. `[verified: ai-instruction-and-memory-files/SKILL.md §1 and §3 routing table]` — altitude split, not duplication: CLAUDE.md states the constraint (which interpreter), the rule states the procedure (detect, defer, fall back). Precedent for an always-loaded surface pointing at a lazily-loaded stowed rule: `ai-instruction-and-memory-files/SKILL.md:39-42` ("It auto-loads whenever one of those files is open. Read it directly when reviewing a diff with neither open.").
4. **Stowed rule (`claude/.claude/rules/`), not repo-scoped (`.claude/rules/`).** `anchors: root, G3`. `[engineer-verified]` — the failure recurred across repos and accounts. Structural precedent: `claude/.claude/rules/shell-script-conventions.md`, a stowed cross-repo conventions rule with its own citation-attribution paragraph. `[verified: README.md:249]`
5. **`paths:` is four `**/`-led globs — `**/*.py`, `**/requirements*.txt`, `**/pyproject.toml`, `**/Pipfile`.** `anchors: row4`. `[verified: claude/.claude/skills/tests/test_rules_frontmatter.py:222-263]` — a `**/`-led glob has an empty literal prefix, the only shape that clears the stowed-portability check without invoking the bare-filename or two-segment-`.claude/` exemption. No bare-basename sibling entries are needed for the root-level `pyproject.toml` / `requirements.txt` case: a leading `**/` matching zero path segments is confirmed empirically (five instrumented one-shot sessions, GH-844). `[verified: docs/rules-references.md:252-261]`
6. **Lockfiles and `**/environment.yml` are deliberately not globs.** `anchors: row5`. `[unverified]` — resting on the judgment that an agent rarely opens a lockfile before installing, while every added glob widens a body that costs context on each fire. The failure shape observed (test run → `ImportError` → install) has a `.py` read in front of it, and the CLAUDE.md clause backstops any trigger miss.
7. **Fallback creator is stdlib `venv`.** `anchors: root`. `[engineer-verified]` — `python3 -m venv .venv`, not `uv`. Corroborated in-repo: `install-dev.sh:96,103` and `plugins/skill-management/hooks/provision-validator-venv.sh:58-59` both run create-then-`<venv>/bin/pip`. `[verified: both files]`
8. **Detection order puts the declared tool ahead of a bare `.venv/`.** `anchors: row7`. `[verified: reasoning from the tools' own ownership model]` — a repo can carry both `uv.lock` and a `.venv/`, and `uv sync` is still the right command because uv manages that directory. Checking for `.venv/` first inverts it and desyncs the lock. Order: declared tool (`uv` → `poetry` → `pipenv` → conda) → existing `$VIRTUAL_ENV` or `.venv/`/`venv/` → create `.venv`.
9. **Prescribe explicit interpreter paths, never `source .venv/bin/activate`.** `anchors: root`. `[engineer-verified]` — activation state does not survive across separate Bash tool calls.
10. **Prescribe `<venv>/bin/pip`, and specifically not `<venv>/bin/python -m pip`.** `anchors: row9`. Two independent reasons. Durable one, for the rule body: an explicit `<venv>/bin/pip` already pins the interpreter through its shebang, so `-m` buys nothing. Situational one, for §47 and the follow-up issue: `.venv/bin/python -m pip install -r requirements.txt` is **denied today** by this repo's own stowed gate — `_install_check_pip_family` matches the bare `pip` word as the manager, `-m` is absent from `_INSTALL_VALUE_TAKING_MARKERS` so it consumes no value, and the interpreter word `.venv/bin/python` survives `_install_has_leftover_token` and reads as a named package. `[verified: claude/.claude/hooks/deny-network-installs.sh:136-215 and 241-264 — static read; no test covers this shape, so Verification re-runs it empirically]` This is a distinct gap from the grep false-positive filed as #850 and is not in the hook header's Known-gaps list.
11. **Every command the rule prescribes must clear `deny-network-installs.sh`.** `anchors: row10`. `[verified: static read of the same hook + claude/.claude/hooks/tests/test_deny_network_installs.py:307-330]` — `.venv/bin/pip install -r requirements.txt` is already pinned as allowed by that test; `python3 -m venv .venv`, `uv sync`, `uv pip install -r requirements.txt`, `poetry install`, and `pipenv install` each read as allowed (no manager+leftover match; `pipenv` fails the `pip`/`*/pip` word test, and `uv sync` exits the uv branch at the missing `pip` token). A recipe this repo's own gate denies would be a defect, so Verification runs each one.
12. **The rule body carries an explicit CI/container carve-out.** `anchors: G1`. `[verified: .github/workflows/tests.yml:142]` — this repo's own CI runs a bare `pip install -r requirements-dev.txt` on an `actions/setup-python` interpreter, which is correct: an ephemeral single-project environment already *is* the project environment. Without the carve-out stated, the first agent to read the new rule "fixes" that line. This is also the concrete instance of the false-positive class that rules out a hook (G1).
13. **`docs/rules-references.md` gets a new section; the plan asserts no PEP 668 content itself.** `anchors: row3`. `[verified: docs/rules-references.md:1-5]` — "One section per rule file; one entry per claim within a section," and the file carries sections only for rules that cite external documentation. **Verbatim replacement for `claude/.claude/CLAUDE.md:116`** (one line, replacing one line):

```
- Installing new software autonomously is strictly prohibited — a general go-ahead ("try X", "see if Y works") does not authorize it; restoring already-declared dependencies (`.venv/bin/pip install -r requirements.txt`, bare `npm install`) is unaffected. Point the user to the `!` shell escape for a genuine new install. A Python restore names the project environment's own interpreter, never the machine's system one — `~/.claude/rules/python-environment-conventions.md` carries the detection order and the fallback.
```

**Intended shape of the new rule** (bullet content, not verbatim prose — the citation pass fills the attribution paragraph):

```
---
paths:
  - "**/*.py"
  - "**/requirements*.txt"
  - "**/pyproject.toml"
  - "**/Pipfile"
---

## Python environment conventions
```

One attribution paragraph (pattern: `shell-script-conventions.md:9-12`) naming which claims are sourced and pointing at `docs/rules-references.md` **in the claude-config repo** — the qualifier is required, since the rule resolves in consumers' repos where that path does not exist. Then one scoping sentence ("Applies when installing or restoring Python dependencies"), then bullets:

- Never install into the machine's system interpreter; name the project environment's interpreter explicitly in every command (row 9).
- Detect before creating, in the order at row 8; run the tool the repo already declares (`uv sync`, `poetry install`, `pipenv install`, the conda env from `environment.yml`).
- Nothing declared → `python3 -m venv .venv`, then `.venv/bin/pip install -r requirements.txt` (or `.venv/bin/pip install -e .` for a `pyproject.toml`-only project). `.venv` is the name to use because it is the conventionally gitignored one.
- `<venv>/bin/pip`, not `<venv>/bin/python -m pip` — the explicit path already pins the interpreter (row 10).
- `python3 -m venv` can exit 0 and produce no pip where the distro splits `python3-venv`; probe `python3 -c "import ensurepip"` first (`install-dev.sh:44-75` is the worked guard).
- An "externally managed environment" error (PEP 668) means the command is pointed at the system interpreter — re-point it, never reach for `--break-system-packages`.
- Carve-out (row 12): an ephemeral single-project environment — a CI runner's `setup-python`, a container built for one project — already is the project environment; this rule targets a developer machine's shared system interpreter.

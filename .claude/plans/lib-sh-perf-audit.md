# `_lib.sh` performance and structure audit

## Context

The goal is to determine whether two recently-deferred PR findings against `claude/.claude/hooks/_lib.sh` are symptomatic of broader undiagnosed performance or structural debt, and to remediate whatever real issues that audit surfaces.

`_lib.sh` is the shared bash library sourced by every hook script in the claude-config harness (48 consumers). A recent PR deferred two findings against it: an untested typical-case latency benchmark gap for `_lib_staged_length_gate`'s doubled per-staged-file `git show` cost, and a request to extract its ratchet comparison into a pure, git-independent function — both rated DEFER (edge case below current scale / orthogonal scope), not blocking. The file has also grown sharply — from 13 lines on 2026-05-06 to 2804 lines / 73 functions on 2026-09-10, with +802 lines (+40%) in just the 8 days before this audit — and the user is worried the two deferred findings are "the tip of the iceberg" of undiagnosed performance and structural debt, since this file is essential to every hook invocation in the harness.

Intended outcome: a prioritized audit of `_lib.sh`'s actual runtime-cost and structural-organization risk (not limited to the two deferred findings), landed as a concrete, proportionate remediation plan and PR — or a clear, evidenced statement of what does *not* need fixing, where the evidence says so.

## Approach

**Conclusion first:** the "tip of the iceberg" worry is half-right, and the half that's right is not where the two deferred findings pointed. Both deferred findings target `_lib_staged_length_gate`, which the caller map confirms is **cold** — it runs only when a Bash command invokes `git commit`, behind an `if` gate in `settings.json`, over a bounded set of staged `SKILL.md`/`CLAUDE.md` paths, with every git call independently 5s-capped. Its per-file fork cost is not a defect and gets no optimization here. Meanwhile the audit surfaced one genuinely hot unbounded-fork site nobody had flagged — `_lib_redact_credential_shaped_strings` forks one `jq` per line of the user's `credential-value-patterns.md` on every `Bash|Read|WebFetch|Grep|Task` PostToolUse — and one correctness defect that the perf lens exposed by accident. So: fix the one real hot-path cost, close the deferred findings on their structural/testing merits rather than their latency merits, collapse two in-file duplications, and explicitly reject splitting the file.

The plan is three sequenced phases, one commit each, one PR.

**Phase 1 — byte-ratchet: structure and characterization, not optimization.**

Extract the second deferred finding's comparison as `_lib_length_ratchet_exceeded NEW OLD LIMIT` (exit 0 iff `NEW > LIMIT` and `NEW > OLD`). The justification is not purity for its own sake: today the boundary logic is reachable *only* through a real git repo, and `test_lib.py` already establishes the one-fork harness for a pure `_lib` function at 30+ call sites (`["bash", "-c", f'. {_LIB_SH}; <fn> "$1"', ...]` — e.g. lines 1093, 2037, 2600, 3296). Extraction moves the boundary matrix onto that harness.

Close the first deferred finding's *testing* half, decline its *benchmark* half. The two `git show` calls have no cap-engagement coverage, which the function's own header comment at `_lib.sh:1211-1215` admits. The existing `git_timeout_shim` + `assert_cap_engaged` mechanism covers this exactly; the two shows are distinguishable by `$2` (`:<path>` vs `HEAD:<path>`). Writing these tests is what surfaced the defect below, which is the argument that they aren't ceremony.

**Defect found by reading, not previously reported:** `_lib.sh:1203-1209` claims the capped git calls "degrade to allow (not just to not-hanging) on timeout." That is true for `rev-parse`, `diff --cached`, and the `git show ":$f"` call, but **false for `git show "HEAD:$f"`**. A timeout there yields empty stdout, `awk 'END{print NR}'` prints `0`, so `old=0` — and an over-limit file that is *shrinking* (new=250, old=300, limit=200) flips from allow to a false deny reading `was 0, limit 200`. Disposition: characterize it in the new cap tests and correct the comment; do **not** change the gate's behavior in this plan. Severity is low (a style gate, a visibly-wrong message, an obvious retry) and the fix needs `PIPESTATUS` handling to tell exit 124 from a genuinely-new file — which `test_new_claude_md_over_limit_denies` (`test_check_claude_md_length.py:179`) pins as a legitimate `old=0` deny. A gate-behavior change belongs in its own PR; the characterization test is what makes that later fix a visible, intentional test edit rather than a silent flip. The characterization test must assert on the deny-reason text itself (e.g. that it names the zeroed `old` value, matching `test_sed_absent_from_path_denies`'s reason-text-assertion precedent at `test_check_claude_md_length.py:155-166`) rather than only the verdict — a bare `deny` assertion is satisfiable by any ordinary over-limit case and would silently stop functioning as a tripwire — and must be named and documented as a known-bug pin with a forward reference to the deferred fix PR.

Test-time reduction is a **measured secondary benefit, not a promise.** 9 of the 16 matrix methods in `test_check_claude_md_length.py` were inspected; only ~3 reduce purely to the line triple (`at_exactly_200_allows`, `new_over_limit_denies`, and one of the growing-to-201 pair). The rest each carry a second dimension — tool name, command parsing, repo detection, path pattern, `sed`-absent fail-closed — and must stay end-to-end. So the migration is materially smaller than "45 tests," and the implementer classifies each case rather than bulk-deleting. Measure before/after on the same invocation shape and report the actual number.

**Phase 2 — the one real hot-path fix.** Batch `_lib_redact_credential_shaped_strings`' per-pattern validation from N `jq` forks into one, preserving today's exact skip-and-warn semantics (two tests pin the per-line diagnostic: `test_lib.py:4486` and `test_redact_credential_values.py:265-292`, the latter asserting `"credential-value-patterns.md line 1"` in stderr). This is the only site where cost scales with a dimension that *grows as the feature is used correctly* — a security-conscious user is encouraged to add patterns, and each one currently taxes every tool call. The validation is load-bearing, not decorative: `redact-credential-values.sh:44` fails open (`[ -n "$REDACTED" ] || exit 0` → the unredacted response reaches the model), so one uncompilable pattern entering the combined alternation would disable *all* redaction including the built-ins. On batched-call failure, fall back to today's exact per-line validation loop to attribute and skip only the malformed pattern(s), rather than skipping all user additions — this reuses the pre-existing, already-correct per-line logic as the failure-path fallback (paying its per-pattern fork cost only in the rare failure case, not on the hot path this phase optimizes) and eliminates the blast-radius regression a naive all-or-nothing fallback would introduce (one bad line would otherwise silently drop protection for every other custom pattern, re-evaluated on every tool call, until fixed).

**Phase 3 — two in-file duplications, both correctness-adjacent.**

The sha256 text-hash recipe has **two competing canonical homes**: `_lib_hash_diff_text` (`_lib.sh:604-609`) and `_marker_lib_repo_hash` (`_lib.sh:363-365`) — and the file papers over the split, with `_lib.sh:2564-2567` citing the *latter* as the reference recipe while the former's own header claims to be "the shared sha256 recipe every cumulative-review value must use." Two more sites hand-copy it (`586`, `2576`). Every one of these carries a comment saying the read and write sides "must agree byte-for-byte, or the gate wedges," so this is a drift-wedges-a-gate risk, not tidiness. Collapse to one definition. `_lib.sh:575` (`_lib_capped sha256sum -- "$path"`) and `2617` (hashing a pipeline's stdout) are *different* recipes and stay as they are.

The three membership scans (`_lib_is_review_only_agent` 2430, `_lib_is_no_gate_release_agent` 2479, `_lib_is_reviewer_persona` 2511) are byte-identical bodies over three derived arrays — the literal case CLAUDE.md's sibling-audit bullet names ("abstract into a shared helper once two or more share it"). Add `_lib_list_contains VALUE ITEM...`, following `_lib_words_start_with`'s established flatten-as-positional-args idiom (`_lib.sh:1101-1130`), because `_lib.sh:1114` states outright: "No local -n/declare -n: this repo targets macOS system bash 3.2."

Also add three one-line trigger-frequency comments across the three phases that touch the relevant functions. The audit's most reusable output is the hot/cold map, and its absence is *why* two reviewers spent findings on a cold path. `_lib_active_plan_files`' header already carries exactly this annotation ("this runs on every Write/Edit/MultiEdit/ExitPlanMode", `_lib.sh:464-465`), so extend that existing in-file convention to the three functions where frequency governs a cost decision, rather than creating a hand-maintained doc table that drifts out of sight. Each comment lands in the phase that already owns and edits that function's header — `_lib_staged_length_gate`'s in Phase 1, `_lib_redact_credential_shaped_strings`'s in Phase 2, `_lib_active_plan_hash`'s (the only genuinely independent one) in Phase 3 — rather than batching all three into Phase 3, which would otherwise land two of them inside header blocks the earlier phases already rewrote and create a manual-conflict risk on any later isolated revert of Phase 1 or Phase 2.

**Rejected: splitting or reorganizing `_lib.sh`.** This is the over-powered-primitive check, and the evidence runs against it on four counts. Growth is consolidation-driven — the +802 lines came from Hook family standardization Phase 1-4 pulling duplicated logic *out of* 48 hooks, which is the correct direction. Zero of 60 commits touching the file discuss its size. The clusters are contiguous and heavily documented, with no regrouping opportunity found. And both split mechanics are net-negative *for this plan's own stated goal*: a `_lib.sh`-as-shim that sources sub-files adds per-invocation `source` I/O on literally every tool call, making the hot path slower; per-hook multi-sourcing is a 48-file change that must replicate the fail-closed `emit_deny` bootstrap per sub-library and breaks the source form `test_hook_alignment.py:1030` pins verbatim. The lighter primitives that address the actual complaint — targeted extraction (Phase 1), a shared helper (Phase 3), and recording invocation frequency at the point of cost (Phase 3) — all exist and none require touching the file's shape.

**Resolving the sibling-audit vs. Axis-4 tension explicitly.** The sibling-audit principle binds arms of one multi-arm structure and requires that a fix landing in one arm land in all arms sharing the bug shape. Three unrelated functions that happen to share a coding idiom are not arms of one structure — the membership trio *is* that case, and gets the shared-helper treatment in Phase 3. For the fork-in-a-loop shape, the principle's operative requirement is that the audit be done, and it has been: `_lib_active_plan_hash`'s loop is bounded by the *active* plan count (untracked or modified), not the plans directory — which has now grown past 100 files while the active set stays at 0-1, and the function returns early at `_lib.sh:570` with zero forks when nothing is active. `_lib_staged_length_gate`'s is bounded and cold. Neither instance is a defect. Because the byte-ratchet is not getting the fork fix either, there is no asymmetric fix to propagate, and Axis 4 governs what changes: only the one arm where the shape *is* a defect. The audit result is recorded as a comment so the next reviewer doesn't re-derive it and misprioritize again.

### Assumption ledger

**Root:** `_lib.sh` accumulated a hot-path fork cost that scales with a user's security config, a mis-documented timeout behavior, and two duplicated recipes — none of which prior review caught, because no record of which entry points are hot versus cold exists anywhere.

**Givens** (fixed, beyond this plan's reach):
- The harness invokes each hook as a fresh process per tool call, so per-invocation process startup is not something this plan can amortize. *Reason: harness-owned.*
- macOS ships `/bin/bash` 3.2, so `local -n`/`declare -A`/`mapfile` are unavailable. *Reason: OS vendor; `_lib.sh:1114` and `test_no_bash4_constructs.py` already state and enforce it.*
- `_lib_capped`'s uncapped fallback when neither `timeout(1)` nor `gtimeout(1)` is on PATH stays as-is. *Reason: documented at `_lib.sh:13-15` and warned at install time; changing it is a separate decision about install-time requirements.*

**Mechanisms:**
- Extract `_lib_length_ratchet_exceeded` as a pure predicate and test it on `test_lib.py`'s existing `. $_LIB_SH; <fn>` harness — the lightest primitive that makes the boundary logic reachable without a git repo. `anchors: row5`
- Add two `@pytest.mark.timing` cap-engagement tests via the existing `git_timeout_shim`/`assert_cap_engaged` pair rather than a new fixture. `anchors: row2`
- Correct the timeout comment; leave gate behavior unchanged. `anchors: row2`
- Batch pattern validation into one `jq` call preserving per-line diagnostics; on batched-call failure, fall back to the existing per-line loop to attribute and skip only the malformed pattern(s) — strictly safer than admitting unvalidated patterns, and avoids the blast-radius regression a naive skip-all fallback would introduce (identified in plan-review). `anchors: row3, row4`
- Collapse the text-hash recipe to one definition and add `_lib_list_contains` in `_lib_words_start_with`'s positional-args idiom. `anchors: root`, bash-3.2 given
- Three one-line frequency comments extending `_lib_active_plan_files`' existing in-file convention, not a new doc table. `anchors: row1, row7`
- **Over-powered-primitive check against a file split:** lighter primitives that solve the stated complaint without restructuring — (a) targeted single-function extraction, already the Phase 1 mechanism; (b) a shared helper for the duplicated arms, already Phase 3; (c) recording invocation frequency at the point of cost, already Phase 3. All three exist; the split is strictly heavier and, per the Approach, slower on the hot path. `anchors: root`

## Out of scope

- **Fixing the `HEAD:` timeout false-deny (row 2).** A gate-behavior change needs `PIPESTATUS` handling to separate exit 124 from a legitimately-new file, and belongs in its own PR with its own review. This plan pins the current behavior so that fix is a visible test edit.
- **Splitting `_lib.sh` or changing the `. "$(dirname "$0")/_lib.sh"` source contract.** The plan could change this and deliberately won't — rationale in the Approach; it would slow the hot path or force a 48-file change.
- **Optimizing `_lib_active_plan_hash`'s per-file `sha256sum`.** Bounded by the active-plan count, zero forks in the common case; the audit result is recorded as a comment instead.
- **Optimizing `_lib_staged_length_gate`'s per-file `git show`/`awk` forks.** Cold, bounded, individually capped; a `git cat-file --batch` rewrite would add a fiddly stream parser to a shared library for unmeasured gain.
- **A wall-clock latency benchmark for the byte-ratchet (the first deferred finding's benchmark half).** Declined, not deferred: no latency budget exists anywhere in the repo to assert against, the path is cold, and `pyproject.toml:26` documents such tests as contention-flaky. If a regression guard is ever wanted, the deterministic form is a subprocess-count assertion via a counting PATH shim, not wall-clock.
- **`_lib_worktree_collision_guard`'s 9-item known-gaps list and `_lib_reviewer_round_state_value`'s 5s-per-call ceiling.** Both are fixed-cost, both are already documented in-file; correctness debt in a lock protocol is a different plan.
- **`_lib.sh:575` and `:2617` sha256 sites.** Genuinely different recipes (capped file-path hash; pipeline-stdout hash), not copies of the text recipe.
- **`select-tests.py`'s rule table.** A dedicated `_lib.sh` rule is that file's own concern per this repo's CLAUDE.md.
- **`cleanup-merged-branches.sh:210`'s own linear membership scan.** Different stow package, does not source `_lib.sh`.

# Bound code-review reviewer responsibility to the diff under review — uniformly, with a boundary that bounds the sweep, not the causal reach

## Context

GH-752 (PR #759, "exclude forwarded task-notification text from phrase matching") was a one-regex-plus-one-helper-function change the engineer expected to be trivial. It instead took 9 sessions, 38 subagent dispatches, and ~$57 in API spend across 4 `/code-review` rounds. Root-cause investigation (an Opus agent, a prior session) found the production code was correct after the first commit — all 4 rounds' churn was comment-discipline and test-coverage findings, and round 4 literally **reverted round 2's own fix**: `comment-discipline-reviewer` rewrote the same test docstring in round 2 (splitting a multi-fact sentence per CLAUDE.md §Split multi-fact comments), then round 4 rewrote the identical site back to the flagged wording.

**Design history.** An initial plan (still in this file's earlier revisions, see PR history) narrowed exactly two Change-type rows — `comment-discipline-reviewer` and `staff-sdet` — to a computed delta-since-last-commit. The engineer objected: *"Why are we only applying this change to comment-reviewer-discipline and staff-sdet agent? ... Treating each agent differently makes me think we're not solving the right problem."* Two independent model consults (Opus and Fable) reconsidered from scratch and converged on the design below, which the engineer approved, including an added default-branch guard. GitHub issue [#763](https://github.com/jcdendrite/claude-config/issues/763) tracks this work.

**What this design does and does not close.** It does not claim to reconstruct the exact causal chain of GH-752's round 2→4 revert — whether commits actually landed between those rounds is unconfirmed (assumption row 15 below is `[unverified]`, carried over unchanged). What it delivers regardless: a uniform, testable responsibility boundary for every reviewer row instead of an ad hoc two-row carve-out, one real correctness fix to the original mechanism (§ Approach), and an explicit safety guarantee that `ready-for-review`'s cumulative sweep is never narrowed. The within-round, no-commit case — arguably the more likely shape of the original incident — is named as an open residual, not fixed (Out of scope).

## Approach

**Core mechanism: the boundary bounds the exhaustive sweep, not the causal reach.** Every `/code-review` spawn is already handed a diff to review — for a commit-gate pass this is the currently staged diff, the same one `require-code-review.sh:100` hashes via `git diff --cached`. Step 0.6 gains one uniform clause, applying to **every** Change-type row, not a subset: a spawn must enumerate that boundary exhaustively, but a defect *outside* the boundary that the change causes, activates, or newly reaches stays in scope. This is what makes uniform treatment safe — `ciso-reviewer`, `staff-sdet`, `staff-backend-engineer`, and every other row keep their cross-change reasoning; none of them lose the ability to flag "this delta makes an untouched file's behavior wrong now." No per-agent exemption list is needed to protect that reach.

**One correctness fix versus the prior mechanism.** The prior draft computed a new ref, `git diff HEAD`, to isolate "what's changed since the last commit." That ref is wrong: it pulls in unstaged working-tree content, which is neither under review nor covered by the commit-gate marker. The fix here computes **no new ref at all** — the boundary is simply the diff a spawn is already being handed. It is restated in the spawn prompt as file paths with added/modified line ranges only because `comment-discipline-reviewer` carries no `Bash` and cannot resolve a ref expression itself (unchanged from the prior draft's reasoning).

**One carve-out: comment/prose review gets an *additional* match-narrowing on top of the uniform responsibility rule.** `comment-discipline-reviewer` does not spawn at all when the boundary (plus its causal reach) contains no comment/durable-doc prose. This is unique to that row because, per its own charter, it is exclusively textual-form rules computable from the changed text plus its containing file (`docs/design-decisions.md` §9: closed-form, "no shell needed," which is also why it carries no `Bash`), with no cross-file reach and no accuracy/staleness angle of its own. Staleness of an *existing, untouched* comment — code changed out from under a docstring — is a different, unnarrowed lane: Step 1.5's inline "Non-durable comment" tripwire and checklist item 12 run unconditionally regardless of this change. Note the overlap this carve-out has with the reviewer's own existing charter: `comment-discipline-reviewer.md:82-86` already excludes pre-existing violations outside the diff under review, so this mostly restates that charter against an explicit, tested boundary rather than removing a finding class the agent would otherwise report. The one genuine new savings is the spawn itself — a boundary with zero prose skips the dispatch outright.

**`ready-for-review`'s cumulative pass gets zero narrowing, enforced by a positive precondition, never an opt-out flag.** Narrowing applies only when (a) the diff under review is the currently-staged diff — the commit-gate pass — **and** (b) `HEAD` is not the repo's default branch. This reuses the discriminator `code-review/SKILL.md:397` already states for the completion-marker decision ("you reviewed the currently staged changes") — sharing only the *scope* half of that condition, not its *cleanliness* half: a staged-diff review that finds blockers writes no marker but still narrows correctly, since narrowing and marker-writing are independent facts about the same diff. Every context that fails the precondition enumerates in full, automatically, with no exclusion list to maintain: the cumulative PR-vs-base pass (`ready-for-review/SKILL.md:67-73`, which explicitly reviews "the cumulative PR-vs-base diff, not per-commit deltas"), a presentation-path review with no commit pending, an ad-hoc user-scoped review, and a direct commit to the default branch. (Grep of `claude/.claude/skills/**/SKILL.md`, `plugins/**/skills/**/SKILL.md`, and `claude/.claude/hooks/*.sh` finds exactly two literal `/code-review` call sites outside its own file: `ready-for-review/SKILL.md` step 3, and `require-code-review.sh`'s own denial message pointing back at the commit-gate pass. The presentation-path and ad-hoc contexts are not separate call sites in code — they're the other two invocation shapes named in `code-review/SKILL.md`'s own frontmatter TRIGGER clause and in this repo's CLAUDE.md §Code Review ("the terminal act is the commit... or the presentation"). No other skill or hook invokes `/code-review`.)

**Default-branch guard.** Narrowing additionally requires `HEAD` is not `main`/`master`/`develop` — the same list `ready-for-review/SKILL.md:36` already checks. Rationale: the "per-commit rounds feed the final unnarrowed sweep" justification silently assumes that final sweep happens — but a direct commit to the default branch is followed by no `ready-for-review` cumulative pass at all, so narrowing there would remove the branch's only real review with nothing restoring it. Worktree enforcement makes this rare in *this* repo specifically, but `claude/` installs to every stow consumer and not every consumer opts into worktree enforcement — this protects the wider install base. Engineer-approved this session.

**`ready-for-review/SKILL.md` gets its own mirrored declaration, not just reliance on `code-review`'s precondition.** A session mid-way through several re-review rounds on a branch is exactly the case most likely to misclassify RFR's cumulative pass as "just another round." The mirror states only the applicability fact for RFR's own invocation ("this pass reviews the cumulative diff with no narrowing") and defers the rule's content to `code-review` — single-source-of-truth, not a restatement. It **replaces** `ready-for-review/SKILL.md:75`, which today already near-duplicates `:67-68` ("Review the cumulative PR-vs-base diff, not per-commit deltas — that's what reviewers actually see; per-commit findings feed in as inputs, not substitutes."), so the edit is length-neutral rather than additive.

**Anchor scheme.** Two independent anchor-comment regions, `SCOPE_RULE:code-review-staged-diff-only` (wraps the applicability paragraph in `code-review/SKILL.md`) and, nested inside it, `SCOPE_EXEMPT_ROW` (wraps just the comment/prose row's shorthand) — plus `SCOPE_RULE:ready-for-review-cumulative-unnarrowed` in `ready-for-review/SKILL.md` for the mirror. This deliberately does **not** reuse the existing `DISPOSITION_RULE:` namespace at `code-review/SKILL.md:319-321`: `extract_governing_rule()` (`evals/run_skill_evals.py:766`) hard-codes the `DISPOSITION_RULE:` prefix into its marker strings (`f"<!-- DISPOSITION_RULE:{anchor_name} start -->"`), and `test_disposition_rule_anchors_present` (`test_skills.py:1505`) feeds every anchor under that prefix into the disposition-fidelity eval — a scope rule is not a disposition rule, and reusing the prefix would silently enroll it in that eval. The new `SCOPE_RULE:`/`SCOPE_EXEMPT_ROW` anchors need their own small extraction helper in `test_skills.py`, mirroring `extract_governing_rule`'s presence-and-minimum-length shape rather than calling that function directly.

**Efficiency-claim discipline for the `docs/design-decisions.md` entry.** Responsibility-narrowing (the uniform, all-rows mechanism) saves fix-loop churn, not reviewer reads — every non-prose reviewer still opens whole files for context, unchanged. Only the prose row's match-narrowing removes a spawn outright — the one genuine token-read saving. Separately, "per-commit rounds make `ready-for-review` more efficient" is correct in outcome, not mechanism: RFR step 3 does full fan-out over the whole branch diff regardless of what preceded it. What prior rounds buy is earlier detection and fewer surviving findings at the final gate, not a cheaper final gate.

**Deliberately not done.** `comment-discipline-reviewer.md:76`'s "Read every changed file fully" instruction is not softened, even though it is arguably the most direct trigger for whole-file re-mining. The boundary is a per-invocation fact the dispatcher supplies, not something to bake into the reviewed charter; softening it here would also pull the change into the *Reshapes reviewer ownership* row's full persona fan-out for an agent-charter edit, widening blast radius for no added benefit over stating the boundary in the dispatch prompt. Named as a revisit trigger in Out of scope.

### Assumption ledger

**Root problem.** Nothing in Step 0.6 states an explicit, uniform responsibility boundary — each reviewer's own charter implicitly bounds what it flags (where one exists at all), so the boundary is undocumented at the dispatch layer and untestable as a cross-cutting invariant. A prior narrow fix (two specific rows) drew an engineer objection that it was solving the wrong-shaped problem.

**Givens** (conditions this design treats as fixed, beyond its own reach):

- **G1 — `require-code-review.sh` gates only commits made through the Claude Code Bash tool.** PreToolUse hook keyed on `TOOL_NAME == "Bash"` (`:55-57`); a `git commit` typed into a terminal never reaches it. `[verified: hooks/require-code-review.sh:55-57]`
- **G2 — `comment-discipline-reviewer` carries no `Bash`** (`agents/comment-discipline-reviewer.md:6`, `tools: Read, Grep, Glob, Write`), so it cannot resolve a ref itself and must be handed the boundary as literal file paths and line ranges. The omission is deliberate design, not an oversight this plan should revisit: `docs/design-decisions.md` §9 establishes the agent as closed-form, "reads a diff and a fixed rule set, no shell needed." `[verified: agents/comment-discipline-reviewer.md:6; docs/design-decisions.md §9]`
- **G3 — Neither `marker.sh` nor `review-ledger.sh` retains cross-invocation history**, and this design needs none: it reuses the diff already being reviewed rather than computing or persisting a new one. `[assumed — carried from the prior draft's G3, not re-verified this session against marker.sh/review-ledger.sh source]`
- **G4 — `code-review/SKILL.md` is 427/500 lines; `ready-for-review/SKILL.md` is 196/200 lines (the plain default cap — it is not in `check-skill-length.sh`'s 500-line override list); `plan-it/SKILL.md` is 141/200 lines.** The RFR edit has a strict 4-line net budget and is met by replacing line 75 (a near-duplicate) rather than inserting new content. `[verified: wc -l against all three files, and hooks/check-skill-length.sh:70-72 for the override list, this session]`
- **G5 — `code-writer` never stages or commits; its output sits in the working tree until the parent stages it** (`agents/code-writer.md:21-22`). Git records no authorship for uncommitted hunks, so no ref expression can isolate "what this dispatch wrote" from what was already in the tree. `[verified: agents/code-writer.md:21-22]`
- **G6 — Exactly two literal `/code-review` invocation call sites exist outside `code-review/SKILL.md` itself: `ready-for-review/SKILL.md` step 3 and `require-code-review.sh`'s own gate.** The presentation-path and ad-hoc-review contexts are behavioral triggers named in `code-review/SKILL.md`'s frontmatter and this repo's CLAUDE.md §Code Review, not separate call sites in code. `[verified: grep of claude/.claude/skills/**/SKILL.md, plugins/**/skills/**/SKILL.md, claude/.claude/hooks/*.sh for "/code-review", this session]`

**Mechanisms:**

- **M1 — The boundary is the diff already handed to a spawn; no new ref is computed.** For the commit-gate pass this is `git diff --cached` (the same basis `require-code-review.sh:100` hashes), restated as file paths + added/modified line ranges for reviewers without `Bash` (G2). Corrects the prior draft's `git diff HEAD`, which would have pulled in unstaged content outside both the review and the marker's coverage. `[verified: hooks/require-code-review.sh:100 hashes git diff --cached]`
- **M2 — Responsibility narrowing is uniform across every Change-type row.** A spawn's exhaustive-enumeration duty is bounded to the boundary; its flagging duty extends to any defect outside it that the change causes, activates, or newly reaches. No per-row exemption list (e.g., a `ciso-reviewer`-specific carve-out) is needed or added: `SKILL.md:319-321`'s "enforcement-invariant findings are never DEFER-eligible" is a *disposition* rule firing downstream of a finding existing, while the causal-reach clause is what keeps such findings reachable upstream — a separate per-agent exemption would protect the wrong seam.
- **M3 — Only the comment/prose row is *additionally* match-narrowed** (does not spawn at all when the boundary and its causal reach carry no comment/durable-doc prose), because it alone is closed-form with no cross-file reach (G2). Every other row's match condition is unchanged — this plan does not alter when `staff-sdet`, `ciso-reviewer`, or any `staff-*` row is spawned, only what a spawned reviewer is responsible for flagging.
- **M4 — Narrowing (both M2's responsibility bound and M3's prose match-narrowing) applies only under a positive precondition: the diff under review is the currently-staged diff, AND `HEAD` is not the default branch.** Every context failing either half enumerates in full automatically — no opt-out flag or exclusion list per context.
- **M5 — `ready-for-review/SKILL.md` carries its own mirrored applicability statement, replacing line 75, deferring the rule's content to `code-review`.** Single-source-of-truth: RFR states only that its own pass is unnarrowed, not why.
- **M6 — The `Spawn decisions:` line states whether narrowing applied to this invocation and why (or why not).** A silent narrowing is the same under-spawn-adjacent failure mode `:210` already treats visible rationale as the fix for.
- **M7 — Two independent anchor regions gate the new prose**: `SCOPE_RULE:code-review-staged-diff-only` around the applicability paragraph, nested `SCOPE_EXEMPT_ROW` around the prose row's shorthand, and `SCOPE_RULE:ready-for-review-cumulative-unnarrowed` around the RFR mirror. Deliberately not `DISPOSITION_RULE:` — see Approach's Anchor scheme paragraph; `extract_governing_rule()` (`evals/run_skill_evals.py:766`) is hard-coded to that prefix, and a scope rule enrolling in the disposition-fidelity eval would be a category error, not a convenience. `[verified: evals/run_skill_evals.py:766-798]`
- **M8 — A drift test in `test_skills.py` pins the anchored row list against real Change-type table rows**, using a small local extraction helper mirroring `extract_governing_rule`'s presence-and-minimum-length pattern (`test_skills.py:1505-1536`) rather than calling that function directly, since it is namespace-locked to `DISPOSITION_RULE:`.
- **M9 — `code-writer`'s self-review scopes to the paths this dispatch edited, read with `git diff -- <paths>` — explicitly *not* `git diff HEAD`.** Unaffected by the responsibility-boundary redesign above; carried forward unchanged from the prior draft. On a fix re-dispatch, the prior round's work is staged-but-uncommitted in the same tree (the review that triggered the fix ran on staged content and the gate blocked the commit), so `git diff HEAD` would return that prior work *plus* this dispatch's new edits — widening the self-review, the opposite of intent. Two lighter alternatives were considered and rejected before adding this clause: (a) rely on the existing Charter bullet (`:29-30`, "only defects in your own diff") — rejected because that bounds what may be *fixed*, not what gets *re-read and re-mined* at `:76-90`; (b) rely on `:88-90`'s "scale the pass to the change" — rejected because it under-fires exactly when "the change" is read as the whole working-tree diff. `[verified: agents/code-writer.md:21-22, :29-30, :76-90]`

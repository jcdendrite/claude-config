# Cache-TTL tuning analysis

## Context

Decide, from measured transcript data rather than intuition, which prompt-cache TTL each Claude Code request bucket should use under this harness — and whether the answer is safe enough to ship as a `claude-config` default. Claude Code sorts every request into one of two TTL buckets: the main conversation, and "everything else" (subagents, workflows, forks, compaction). Cache writes bill at 1.25x base input for a five-minute TTL and 2x for a one-hour TTL, while cache reads bill at a flat 0.1x whichever TTL wrote the entry. Picking the wrong TTL for a bucket costs on every turn: too short and long idle gaps expire the prefix and force a fresh write; too long and every incremental write pays a premium it never earns back.

This harness makes the trade sharp: review pipelines dispatch many specialist agents in parallel, and the main session then idles through those dispatches and through long test suites — gaps that routinely exceed five minutes — but the same session also takes long runs of fast turns where a five-minute TTL never expires and the one-hour write premium is pure loss. Which effect dominates is an empirical question.

Why now: no TTL is configured anywhere on this machine, so every root is running Claude Code's defaults. The vendor documents two billing modes with different defaults for the main-conversation bucket, and `claude/.claude/settings.json` stows to every consumer who runs `./install.sh` — so a shipped default must be safe under whatever tier a consumer's root is actually running, not only the tiers this machine happens to exercise. Intended outcome: a durable, re-runnable analyzer that models the counterfactual cost of each TTL configuration per bucket, reports it per root rather than pooled, and ships a shared default only when every root's evidence agrees. The settings change itself lands in a follow-up PR. This change ships the measurement and its documented run.

## Approach

Extend the existing `cache-rebuild` subcommand with a `--ttl-verdict` mode that:

- adds the missing half of the TTL counterfactual (the 1h→5m direction) alongside the existing 5m→1h one,
- accumulates per root instead of pooling across roots, and
- reports one verdict per root per bucket against a decision rule pre-registered in this plan before the run: ship a shared default only when every consistent root agrees.

`transcript-analysis.py` already ships `cache-rebuild` — "idle-gap prompt-cache TTL-expiry measurement" — which:

- classifies every large cache write by gap band (`idle 5m-1h`, `idle >1h`, `model switch`, `unexplained`, `excluded (timestamp anomaly)`),
- prices the excess against a counterfactual warm read (`_cache_rebuild_excess_dollars`),
- accumulates a signed 5m→1h `cacheTtl` switch delta with a per-model break-even (`_cache_rebuild_switch_delta_dollars`),
- splits accumulators main-vs-subagent,
- tables idle-gap excess per account ordinal, and
- carries an ex-post oracle bound on whether a selective per-dispatch lever is excluded.

Its own design plan (`.claude/plans/subagent-idle-gap-cache-rebuild-split.md`) derives the break-even algebraically and pre-registers a decision rule. Roughly 70% of what was asked for already exists and is tested; building a new subcommand or a standalone script would fork the gap classifier, the per-group chain scoping, the pricing path, the account-ordinal redaction, and the TTL model itself into a second copy that drifts — a single-source-of-truth defect, not a design choice. **What is genuinely missing:** the existing work covers one lever (`experimental.cacheTtl` in subagent frontmatter) and therefore one direction (5m→1h) and one bucket (subagents). `promptCacheTtl` and `subagentPromptCacheTtl` — the settings that reach the main-conversation and everything-else buckets — appear nowhere in this repo. Two gaps follow. First, **no 1h→5m accumulator**: on a root whose main conversation defaults to 1h, the only actionable move is down, and the existing `W5m`/`X` accumulators are blind to it by construction — they sum 5-minute-tier write tokens, and the report's own docs note the `main` row's `W5m` measured zero on the corpus it was run against. Second, **a stale lever note**: the docs' narrative prose states the `main` row "has no corresponding lever" because `experimental.cacheTtl` cannot reach main-conversation traffic, but `promptCacheTtl` can. The docs' narrative prose is corrected at `:968`. The tool's own print statement making the same stale claim (`transcript-analysis.py:6584-6587`) is left untouched, because fixing it would be a default-path output change that M1's regression guard exists to forbid. The docs' captured-output sample at `:911-913` is annotated in place as stale rather than hand-edited to show output the tool doesn't produce. Per-agent-type attribution — a further, finer-grained lever this analysis could support — is a follow-up, not this change: it is only actionable when a global setting is deliberately not shipped, since the vendor's precedence list makes the per-agent frontmatter lever and a global setting mutually exclusive, not layered, which is the opposite of this plan's goal of a single default every root agrees on.

**The counterfactual model — where it is exact and where it is not.** The 5m→1h direction is near-exact and already implemented. Its rescued tokens `X` are *directly observed*: a call whose prior-call gap fell in [300, 3600) and which wrote 5m-tier `cache_creation` tokens is a rebuild the 1h tier would have prevented. The uplift term is exact because the vendor states automatic caching writes only the increment — "Each new request caches everything up to the last cacheable block, and previous content is read from cache" — so `W5m` is warm incremental write volume, not repeated full prefixes. Break-even: status quo `1.25·W5m` versus `2·(W5m − X) + r·X`, so adoption pays only when `X / W5m > 0.75 / (2 − r)` ≈ 0.3947 at the default cache-read multiplier.

The 1h→5m direction is its algebraic mirror but is **inferred, not observed** — the single most important honesty point in the design. Under a live 1h tier, a gap in [300, 3600) produces a *warm read*, not a write, so the counterfactual loss is a quantity the transcript never records as a loss. Modelling it claims that `cache_read_input_tokens` served after such a gap is exactly the prefix that would have missed: status quo `2·W1h + r·R`; after dropping to 5m, `1.25·(W1h + Z) + r·(R − Z)`, where `Z` is read tokens on calls whose prior-call gap fell in [300, 3600); delta = `0.75·W1h − (1.25 − r)·Z`, so dropping to 5m pays when `Z / W1h < 0.75 / (1.25 − r)` ≈ 0.6522 at the default rate. `Z` is a good estimator but not exact, for three reasons the report prints rather than buries:

- `cache_read_input_tokens` carries no tier split, so a read behind a 5m breakpoint in a mixed-TTL request is indistinguishable from one behind the 1h breakpoint.
- Partial-prefix survival (the shorter TTL expiring only the tail) is not representable at all, so `Z` assumes all-or-nothing.
- Shared with the 5m→1h direction, the invalidator may not have been the TTL — effort-level switches also invalidate the entire cache and are not classified (model switches are), so some `Z` and some `X` are misattributed to TTL expiry.

A fourth caveat is directional and applies to both directions, which is why the verdict needs margin rather than a bare break-even crossing. The vendor measures TTL lifetime "from the start of the request that writes or reads the cache entry, not from the end of its response," and warns that a response taking 4 minutes to stream leaves a follow-up request "about 1 minute" to reuse the prefix within a 5-minute TTL. The transcript's own record timestamp is not documented as a request-start time; if it is nearer response completion, every measured gap understates the true start-to-start gap, which understates `X` (biasing against 1h) and understates `Z` (biasing toward 5m) — both push the verdict toward 5m. The design checks this at two boundary points rather than a single estimate — 300s and 60s, the vendor's own illustrative unit for the bias this check bounds — and a verdict must hold at both to count. One instrument already in the corpus is wired in as a validator, not the primary path: `pricing._cache_miss_reason` reads a vendor-emitted, per-request miss signal with a token count, and cross-tabulating the gap-derived cause against it is the cheapest available check on whether the gap heuristic is attributing rebuilds correctly; a mismatch is a disclosed discrepancy row, never a silent override.

**Per-root reporting and the ship rule.** Each of the two buckets (main, everything-else) gets one verdict per in-scope root, never pooled. A root's own accumulators already show which tier it is actually paying for that bucket — nonzero `W5m` or nonzero `W1h` — whichever tier that is, and for whatever reason (subscription default, a subscription root over its plan limit, or API billing), so the report applies whichever break-even direction that root's single nonzero accumulator supports without ever asking why the root sits in that tier. A root with both `W5m` and `W1h` simultaneously nonzero in the same window contributes no verdict for that bucket, the same as a root with no data in either — the break-even algebra assumes a single tier per root for the window, and mixed activity within it breaks that assumption. A consistent root with `W5m` nonzero gets the 5m→1h test; a consistent root with `W1h` nonzero gets the 1h→5m test; in both cases the verdict-decision function compares a dollar accumulator resolved call-by-call from `_model_rates`' own per-call `r` — never the single printed default-rate constant — against zero with margin, so a root running a non-default cache-read rate is handled correctly by construction, not by caveat. The printed ≈0.3947 (5m→1h) and ≈0.6522 (1h→5m) figures are human-readable break-even context for the default rate only, not the literal ratio the decision function checks. Since G4 (the vendor publishes nothing on how cache writes weigh against subscription rate limits) leaves dollars possibly not binding on a root currently paying the 1h tier — the tier a rate-limit-driven downgrade would move it off of — every consistent 1h root also runs a raw-token tiebreaker with no price weights: a zero-tolerance sign check, `Z` against `W1h` directly — never a margin — that favors dropping to 5m when `Z < W1h`, disfavors it when `Z > W1h`, and counts as a disagreement (never a wash) when `Z == W1h`. A consistent 5m root has no meaningful raw-token comparison in the opposite direction and runs no tiebreaker at all; its `clears` is decided by the dollar margin alone. Per M5, a 1h-tier root whose dollar-accounting direction and raw-token-tiebreaker direction disagree declines for that root regardless of how comfortably the dollar margin cleared. The rule has four outcomes per bucket:

- **adopt** — every consistent root's verdict points the same direction, every consistent root's own dollar margin independently clears ≥0.10 of that root's own dollar-equivalent volume (a per-root AND, not a single bucket-wide pooled threshold — a dollar-priced margin and a raw-token sign check have no defensible combining formula into one shared denominator), and the direction holds at both boundary points (300s and 60s) for every consistent root.
- **decline** — every consistent root agrees on direction but at least one fails its own margin or boundary check, or a 1h-tier root's dollar and raw-token accountings disagree.
- **roots disagree** — consistent roots point in different directions, so ship nothing — the design never needs to know why they disagree, since it never grouped roots by a reason in the first place.
- **no verdict** — the bucket has zero consistent roots for both directions in the 30-day window, a distinct fourth state (not `adopt`, not `decline`, not `roots disagree`) that `adopt`'s conditions can never reach vacuously, since `adopt` requires at least one consistent root by construction.

Redaction inherits `cache-rebuild`'s existing contract unchanged for the tool's own local report output — `DO NOT PUBLISH` banner, `--no-redact` refused once more than one root is in scope, per-root rows labelled by `scope._redaction_ordinals` ordinal only — with no new disclosure policy for that local output; Phase 3 layers a separate, stricter disclosure rule on top of it for the `docs/cost-levers-considered.md` artifact specifically, since that artifact is published rather than local (see Phase 3). **Over-powered-primitive check, on the configuration lever:** the heavy option is `subagentPromptCacheTtl`/`promptCacheTtl` in the committed `claude/.claude/settings.json`, which changes behaviour for every stow consumer and, per G2, revokes a knob a consumer may already be using; a per-account `CLAUDE_CODE_PROMPT_CACHE_TTL` env var is sufficient whenever roots disagree, since it is the only primitive that can hold a different value per machine, which a committed settings file cannot (G5). The committed setting is expressible at all only when every root agrees, which is precisely the condition this analyzer tests — why the analyzer ships before the settings change.

### Assumption ledger

### Root problem

Two prompt-cache TTL buckets are running on vendor defaults, at a 1.25x/2x/0.1x price structure where the wrong default costs money on every turn; the choice must be made from measured transcript data, per bucket and per root, and shipped as a default to every stow consumer only when every root agrees.

### Givens (fixed beyond this design's reach)

- **G1 — The vendor owns the multipliers, the two-bucket split, and the per-mode defaults.** The design chooses within them and cannot introduce a third bucket or a per-request TTL. `[verified: https://code.claude.com/docs/en/prompt-caching and .../build-with-claude/prompt-caching, quoted in this plan]`
- **G2 — The vendor owns the six-level control precedence, and it is not composable the way it looks.** The bucket's *setting* (level 3) outranks a subagent's `experimental.cacheTtl` frontmatter (level 4), so a global `subagentPromptCacheTtl` silences every per-agent override. The two levers are mutually exclusive, not layered. `[verified: precedence list quoted verbatim from https://code.claude.com/docs/en/prompt-caching]`
- **G3 — Claude Code owns the transcript record format.** No request-start timestamp is documented, gap measurement inherits whatever the record timestamp means, and billing mode is not recorded as a field at all — one more reason the design never tries to infer it. `[verified: schema field list confirmed empirically against real transcript files during exploration]`
- **G4 — The vendor publishes nothing on how cache writes weigh against subscription rate limits.** Dollars may not be the binding metric on a root whose main bucket runs 1h, and no amount of local measurement resolves it. `[verified: absence across both cited vendor pages]`
- **G5 — `claude/.claude/settings.json` is one committed file stowed to every consumer.** It cannot hold two values, which is why disagreement across roots means shipping nothing rather than a per-root split. `[verified: CLAUDE.md "Plans in this repo affect all stow users"; repo layout section]`
- **G6 — Claude Code deletes transcripts.** The 30-day window is what exists, and this measurement cannot be re-derived later from the same data. `[verified: docs/transcript-analysis.md's cost-ledger section states this as the reason the ledger exists]`

### Mechanisms

- **M1 — Extend `cache-rebuild` behind an additive `--ttl-verdict` flag rather than adding a subcommand or a script.** The existing flat `w5m_by_origin`/`x_by_origin`/`switch_delta_by_origin` accumulators, and every default-path site that reads them (`transcript-analysis.py:6593-6595`, `:6625`, `:6641`), stay untouched; a second, parallel accumulator is added alongside them and incremented from the same per-call loop, so the two can never drift out of sync. `anchors: root, row1`
- **M2 — Add the mirror 1h→5m accumulator (`W1h`, `Z`) alongside the existing `W5m`/`X`, in the same scan pass.** Without it the main-conversation question on a root whose main bucket defaults to 1h is unaskable. `anchors: row3`
- **M3 — Key the new accumulator on `(origin, root_ordinal)` only, never on a billing-mode label.** A root's own nonzero accumulator already shows which tier it is paying, for whatever reason. `anchors: row2`
- **M4 — Report the boundary-sensitivity check at two points (300s and 60s) instead of a single point estimate.** The record-timestamp endpoint is undocumented and its bias is directional; two points bound it without a longer ladder's added surface. `anchors: row4`
- **M5 — Print per-class token volumes beside dollars for a root whose main bucket runs 1h, and decline that root when the two accountings disagree.** The raw-token comparison is a zero-tolerance sign check (`Z` vs `W1h`, with `Z == W1h` counted as disagreement), never a margin; G4 is unresolvable, so the verdict must survive either accounting, independent of how comfortably the dollar margin cleared, or that root doesn't contribute a usable verdict. `anchors: G4, row12`
- **M6 — Cross-tabulate the gap-derived cause against `pricing._cache_miss_reason` as a disclosed validator, never as an override.** The vendor's own per-request miss signal is the only independent check available on the classifier. `anchors: row5`
- **M7 — Over-powered-primitive check on the settings lever.** A committed default is expressible only once every root agrees; until then the per-account env var is the correct primitive, not the committed setting. `anchors: G2, G5`

- Regression and reconciliation guards: a committed test asserts `cache-rebuild` output without `--ttl-verdict` is byte-identical to the pre-change output, re-run on every future change rather than checked once by hand, and a separate committed test asserts the sum of the per-`(origin, root_ordinal)` `W5m` cells equals the existing pooled per-origin `W5m` row exactly.
- The per-root diagnostic output states the consistent-root count for each bucket/direction plainly and unambiguously, confirmed in the test suite rather than by eyeballing the live Phase 3 run.
- The live Phase 3 run is a measurement, not a check. Its output must not be quoted in the PR body, the commit message, or any committed file.

## Out of scope

- **The settings change itself.** Engineer-decided: this PR ships the analyzer and a documented run; `promptCacheTtl` / `subagentPromptCacheTtl` / `experimental.cacheTtl` land separately, per the over-powered-primitive check above.
- **Per-agent-type attribution.** Deferred as a follow-up: it is only actionable when a global setting is deliberately not shipped, which cuts against this plan's goal of a single default every root agrees on (see "What is genuinely missing").
- **Migrating the `cache-rebuild` command group into `transcript_analysis/`.** A whole-group move riding along with a measurement change would violate the change-size axis and obscure the diff that matters.
- **Resolving how cache writes weigh against subscription rate limits (G4).** Unpublished by the vendor. The design prints both accountings and declines where they disagree rather than modelling a weighting it cannot source.
- **Effort-switch cache invalidation as a classified cause.** Named as a known misattribution source and disclosed in the report; adding it as a cause needs a corpus survey establishing whether effort is recorded at all.
- **Re-litigating already-inherited mechanics.** The TTL-refresh reset semantics, the read-collapse cold classifier, wire-level/API-side validation of the counterfactual, and the account-ordinal scheme's cross-account fingerprint tradeoff (`_build_redact_map`, `docs/transcript-analysis.md:54`) are all pre-existing, shipped, and tested; this change does not reopen any of them.

# Stop stow-source rules from double-loading in claude-config worktrees

## Context

Every contributor session working in a claude-config worktree loads each matching `claude/.claude/rules/*.md` file into context twice, because that directory is simultaneously the stow *source* for the user-scope `~/.claude/rules/` install and a nested project-scope rules directory under the worktree. Now: GH-845 reported it; this session reproduced and characterized it, and the cost lands on exactly the contributors most likely to be editing files under `claude/`. Intended outcome: exactly one copy of each stow-source rule loads per session in a worktree, with the repo-root project rules (`.claude/rules/*.md`) and every non-contributor stow consumer left untouched.

The issue's own reading was incomplete in one way that changes the fix. The duplication is **worktree-specific**: in the main checkout the user-scope symlink target and the nested project path are the same absolute path and only one copy loads, while in a worktree they are different absolute paths and both load. Worktree enforcement is armed in this repo, so the worktree case is the ordinary contributor session rather than an edge case.

## Approach

Add a second `claudeMdExcludes` entry to this repo's **project-scope** `.claude/settings.json` — `**/.claude/worktrees/**/claude/.claude/rules/**` — so nested discovery skips the worktree's copy of each stow-source rule file while the user-scope copy reached through the `~/.claude/rules` symlink still loads. The entry is the whole behavior change; three supporting parts are forced by it rather than attached to it: the existing guard test asserts `claudeMdExcludes` holds *exactly one* entry and fails the moment a second is added, a `claudeMdExcludes` entry has no runtime failure signal so the guard has to be real, and the accepted cost in row1 has no durable home outside `docs/design-decisions.md` §46.

The tail is `/**`, matching the vendor's own example for a rules directory; this session's headless verification trial confirmed a trailing `/**` matches a direct child under Claude Code's matcher. No flatness guard and no `select-tests.py` table entry are needed as a result (M2 item 3): the cross-domain read that would have motivated the table entry is removed in M2 rather than registered. Four files, four mechanisms.

**Root problem.** A contributor session anchored in a `claude-config` worktree loads every matching stow-source rule file twice — once at user scope through the `~/.claude/rules` directory symlink, whose target is the *main* checkout, and again through nested `.claude/rules/` discovery of the *worktree's* own `claude/.claude/rules/`, which is a different absolute path. Worktree enforcement is armed in this repo, so this is the ordinary contributor session, not an edge case.

**Givens**

- **G1.** Nested rules-directory discovery walks the physical filesystem tree and does not deduplicate two distinct absolute paths that resolve to identical content. Vendor behavior in Claude Code; nothing in this repo can change it.
- **G2.** The rule files must stay at `claude/.claude/rules/*.md`. Stow links each immediate child of `claude/.claude/` into `~/.claude/`, so relocating the directory breaks the 1:1 install mapping every consumer runs (`docs/design-decisions.md` §5, restated at §39).
- **G3.** `claudeMdExcludes` patterns match against absolute file paths using vendor-defined glob syntax, arrays merge across settings layers, and a pattern matching **either** a rules file's own path or its symlink target excludes it. Restated in M1: the `large-codebases.md` example is quoted verbatim there, the `memory.md` example paraphrased.

**Mechanisms**

- **M1 — add the second `claudeMdExcludes` entry to `.claude/settings.json` (repo root).** `anchors: root, row1, row2, row16`. Merged as a second array element beside the existing pattern, preserving `enabledPlugins` and `permissions.allow` byte-for-byte:

  ```json
  "claudeMdExcludes": [
    "**/claude/.claude/CLAUDE.md",
    "**/.claude/worktrees/**/claude/.claude/rules/**"
  ]
  ```

  Every segment earns its place: the leading `**/` absorbs the per-contributor checkout root (row4), `.claude/worktrees/` keeps the pattern off the user-scope copy's link target (row3), and the middle `**` covers a slug containing `/` (row6).

  **The tail is `/**`.** This matches the vendor's own worked example for a rules directory: `memory.md` excludes one with a bare `.claude/rules/**` tail, and `large-codebases.md` gives `"claudeMdExcludes": ["**/packages/web/**"]` — "This skips every CLAUDE.md and rules file under that package." Four facts support the choice:

  1. Row16 confirmed `/**` matches a direct child, so `/**` and `*.md` are now equally grounded on observation.
  2. `/**` additionally covers a rule file later placed in a subdirectory, and needs no test constraining this repo's own directory layout to stay flat.
  3. The wider match is inert in practice: `claudeMdExcludes` governs instruction-file loading, so a non-`.md` file under that path is not loaded either way, and the directory holds only `.md` files today (row7).
  4. Under G3 the pattern still cannot reach the main checkout (no `.claude/worktrees/` segment) or the repo-root `.claude/rules/` (no `claude/` segment before `.claude/rules/`) — the prefix does that discrimination, and the tail change does not touch it.

  *Lighter primitives considered.* (a) Rely on Claude Code deduplicating identical content across scopes — fails: not documented in any source read this session, and row2's control shows 5 loads for 3 files. (b) `.claude/settings.local.json`, genuinely lighter in blast radius and the scope the vendor's own example uses — fails because the duplicate is a property of this repo's layout that every contributor in a worktree hits, and `claude/.claude/CLAUDE.md`'s settings-scoping rule routes a change every engineer on the project needs to committed `settings.json`. (c) Narrow each stow-source rule's own `paths:` frontmatter so the worktree copy never fires — fails twice over: those files install to every consumer's `~/.claude/rules/`, so a repo-local problem would be paid for by every stow consumer, and whether `paths:` globs resolve project-root-relative or rules-dir-relative for a *nested* rules directory is unknown. (d) An ignore-file exclusion — no documented mechanism gates nested rule discovery on ignore files, and it is a wider instrument than a per-path settings entry. `claudeMdExcludes` at project scope is the narrowest documented lever that reaches this; the heavier options (restructuring the stow layout, relocating the rules directory) are the ones G2 rules out.

- **M2 — update `claude/.claude/hooks/tests/test_claude_md_excludes.py`.** `anchors: root, row8, row10, row15`. Forced by row8, and the module's own docstring states why it must be a real guard rather than a mechanical widening: "The exclusion fails silently: nothing in a running session reports that the glob stopped matching. The only observable symptom is a larger context that nobody notices." Four changes:

  1. Add a module constant for the new pattern and an expected-list constant; assert equality against that list, keeping the existing "an extra entry would silently accumulate unrelated excludes" intent. Rename the method away from `..._contains_exactly_one_entry`, which the change falsifies, and extend the module docstring to name the second entry's purpose alongside §46.
  2. Add **negative** `fnmatch` assertions only, for the new pattern: it must not match any real file under `claude/.claude/rules/` given a main-checkout absolute path, and must not match a synthetic `<repo>/.claude/worktrees/<slug>/.claude/rules/<file>.md`. Negatives are sound here where positives are not:

     - Every `**` in this pattern compiles to an unrestricted `.*` under `fnmatch.translate`, so `fnmatch` is strictly more permissive than a segment-aware matcher, and a non-match under the permissive matcher implies a non-match under the real one.
     - State that asymmetry in one comment, scoped to patterns built only from `**` tokens and literal segments — a future pattern using `?` or `[...]` would not automatically inherit the guarantee, so the comment must not read as a general law.
     - Do not assert the positive direction with `fnmatch` and do not introduce a second matcher (row15); point at §46 for the authoritative empirical check, matching the module's three existing caveat comments.
     - The negative-only constraint leaves the pattern's *positive* match behavior — including row6's two-segment worktree slug, the one case in the ledger with a previously-observed regression shape (`worktrees/*/` silently missing it) — with no automated regression coverage anywhere in this suite. V3's one-time, manually-run interactive check is the only thing that would catch a future edit silently narrowing the pattern; state that residual explicitly in the module docstring alongside the existing caveats, not just in §46.
  3. **Replace the hardcoded `dockerfile-conventions.md` at line 42 with an `rglob("*.md")` over the stow-source rules directory** — not `glob`, since M1's own tail-choice rationale (row7 + row16) argues `/**` over `*.md` specifically so the production pattern needs no test constraining this repo's directory layout to stay flat, and a non-recursive `glob` would silently reintroduce that flatness assumption at the test layer for any rule file later placed in a subdirectory. Shared by the existing CLAUDE.md-pattern negative and item 2's new one. **Parametrize the negative assertions over every file the glob returns** — following `test_rules_frontmatter.py`'s `_RULE_FILES`/`_RULE_IDS` shape — rather than picking a representative file: the whole point of the change is removing a single-filename pin, and asserting against one arbitrarily-chosen file would replace one hardcoded name with another while dropping the coverage breadth. Guard the glob as non-empty so it cannot degrade to a vacuous pass. This is a one-level-up fix, not an opportunistic tidy: row10's live mis-selection is entirely a name pin, and removing the pin removes the dependency instead of registering it in `select-tests.py`. Afterward no rules-file rename can break this module, so the audit that `select-tests.py:255-258` demands concludes "no entry needed" rather than being skipped. That non-empty guard is the **only** thing catching an emptied `claude/.claude/rules/` — `test_rules_frontmatter.py:112` does not backstop it, because `_discover_rule_files()` (lines 57-62) builds one union across both rules directories, so emptying the stow-source directory alone still leaves the repo-root files and that assertion still passes. Carry one durable comment line at the glob site stating that it globs the directory rather than naming a rule file so a rename cannot break the module.
  4. Leave `test_stow_source_settings_has_no_claude_md_excludes_entry` unchanged — it already guards both entries by construction.

  *Why not the `select-tests.py` table entry instead.* Widening `RULES_DIR`'s exception to `(SKILLS_TESTS_DIR, HOOKS_TESTS_DIR)` would make every one-line rules-prose edit pull in the whole 5084-test hooks suite, and would force row11's test-expectation edit. Narrowing it to a single file-path target avoids that cost but runs into row17: a second file target fails `test_every_directory_target_exists_on_disk` and requires generalizing two fidelity-test methods. Both variants register a dependency that item 3 deletes for less code, and "the gap is pre-existing" is not the argument — the plan modifies this exact file, so walking past a four-line fix would need a better reason than that.

- **M3 — add `docs/design-decisions.md` §46.** `anchors: root, row1, row13`.

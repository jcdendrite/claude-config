# Round-3-triggered, hook-enforced `plan-architect MODE=consult` dispatch

## Context

29 of 213 merged claude-config PRs (14%) in the 2026-08-01+ window needed 3+ rounds of `/code-review` rework, and the shape of that tail is a discontinuity, not a gradient: mean `commit_count` moves 2.33 → 2.54 → 2.86 through rounds 0–2 (a roughly linear ~0.27-commit marginal cost per round), then jumps to 6.31 at round 3+. A prior `plan-architect` consult and a 29-PR failure-mode classification (both already merged, in `docs/case-studies/opus-frontload-review-rounds.md`'s "Follow-up diagnostic" section) established the design direction: dispatch an **unspecialized** `plan-architect MODE=consult` ("is the foundation wrong?") at **entry to round 3** specifically — not round 1 (round 1 would catch ~50% of PRs to address a 14% tail) and not mode-tailored (no single failure mode reached ≥half: plan-quality 39%, oscillation 29%, context-loss 29%, scope-growth 4% — the "spread evenly" branch of the pre-registered decision rule). The trigger must be **hook-enforced, not instruction-enforced**, per this repo's own convention that memory/skill instructions cannot fulfill an automatic-trigger request and every comparable gate here (`require-code-review.sh`, `require-plan-review.sh`, `require-ready-for-review.sh`) is a hook.

The goal of this plan is to design and implement that trigger: a new round counter, a new hook pair that gates entry to round 3, and the CLAUDE.md / `docs/design-decisions.md` wording updates needed so the new auto-trigger doesn't read as contradicting the existing "never dispatch `MODE=consult` on your own initiative" rule.

Full grounding (already merged, on `main`): `docs/case-studies/opus-frontload-review-rounds.md` lines 158–269 ("Follow-up diagnostic"), `docs/cost-levers-considered.md`'s 4th register row.

**Open decision resolved this session:** the gate ships on-by-default for every stow consumer, with a presence-only disable sentinel (`<config-dir>/.round-consult-gate-disabled`) matching the `handoff-nudge` on-by-default-with-disable-escape precedent — not the opt-in `track-permission-prompts`/`nudge-error-mode-analysis` precedent. `[engineer-verified]`

## Approach

Add a two-hook pair on the subagent-dispatch surface: a `PreToolUse` gate that denies a reviewer-persona spawn on a branch entering its third distinct reviewed state, and a `PostToolUse` recorder that appends round state and writes a content-free release latch when it observes a `plan-architect` consult dispatch. On-by-default for every stow consumer, with a presence-only disable sentinel at `<config-dir>/.round-consult-gate-disabled`.

**Root problem.** A PR entering a 3rd `/code-review` round is a non-converging review loop rather than a quality gradient — mean `commit_count` moves 2.33 → 2.54 → 2.86 across rounds 0–2 and then jumps to 6.31 at round 3+ (`docs/case-studies/opus-frontload-review-rounds.md`, G1 table) — and nothing in the pipeline interrupts the loop to ask whether the foundation is wrong.

**Givens** (conditions this design treats as fixed, each with its qualifying reason):

**Mechanism 1 — round counter: a per-branch state file of distinct `(HEAD sha, staged-diff sha)` pairs, capped at 2.** `[anchors: root; rows 1, 15, 16]` The file `<config-dir>/.reviewer-round-state.d/<repo-hash>.<branch-hash>` holds one `<head-sha> <staged-diff-sha256>` line per state a reviewer fan-out was launched against, and never grows past the cap. The pair is the right unit for two reasons: a whole parallel fan-out at one state collapses to one entry, so five reviewers in one batch are one round; and including HEAD disambiguates a committed fix (HEAD moves, staged diff empties) from a staged one, which a staged-diff hash alone would not.

Four lighter counters were checked and rejected:

- **Branch commit count** — the case study's own bucket table shows commit count and round count are correlated but not equal (round-1 mean 2.54, round-2 mean 2.86), so a 3-commit branch at round 1 would fire the consult on a converging PR. `[anchors: row 15]`
- **Overloading `review-narrative-ledger`** — it is session-keyed, disable-able, and swept at 30 days, and `require-code-review.sh` ships a compliance log specifically because whether it keeps pace with `/code-review` is an open measurement question, not an established one. `[anchors: row 12]`
- **Counting `agent-reviews/` findings files** — a reviewer writes there only via the optional `findings_path` convention and only after `deny-reviewer-tree-mutation.sh` confirms the directory is git-ignored, so the file count tracks reviewer output opt-in, not rounds. `[anchors: row 2]`
- **Appending round rows to `code-review-markers/`** — `_lib_marker_value_present` reads those files with `grep -qFx`, where the stored hash *is* the commit gate's authorization; adding non-hash rows risks releasing that gate, and the repo CLAUDE.md forbids hand-writing `*-markers/*` outright. `[anchors: row 13]`

**Mechanism 2 — gate point: a new `PreToolUse` hook on `Agent|Task`, not on `git commit`.** `[anchors: root; rows 2, 6, 7]` `require-architect-consult.sh` denies a reviewer-persona spawn when the state file already holds 2 distinct entries, the current state is not one of them, and no latch exists. Gating the spawn — not the commit — is what makes the interruption land *before* the third fan-out is paid for, which is the whole point: reviewer fan-out is the expensive act.

The heavier-primitive check, since a new gate hook is the most invasive option available:

- **An instruction in `code-review/SKILL.md` Step 1** — rejected because the repo's own convention holds that "memory and skill instructions cannot fulfill an automatic-trigger request" (repo `CLAUDE.md`, "Should this be a hook?"), and the case study names the trigger as hook-enforced for exactly that reason. `[anchors: row 15]`
- **A `UserPromptSubmit` advisory nudge** — rejected because the round-3 boundary is crossed inside an autonomous `/code-review` stretch, not at a human-interaction boundary, so a prompt-time hook fires either too early or after the fan-out already ran. `[anchors: root]`
- **Reusing `require-code-review.sh`'s existing `git commit` surface** — rejected because it fires after every reviewer of round 3 has already been spawned and paid for, converting a preventive interruption into a retrospective one. `[anchors: root]`
- **A session-scoped active-bypass marker (`_lib_active_bypass_marker_live`)** — rejected because 29% of the tail is `context-loss`, whose signature is a session boundary; a session-keyed mechanism resets exactly where the failure mode concentrates. `[anchors: row 4]`

**Mechanism 3 — scoping the count to code-review fan-out via existing active markers.** `[anchors: row 4]` Both hooks exit early when a live `.plan-review-active.d/<session_id>` or `.ready-for-review-active.d/<session_id>` marker exists for the session, using `_lib_active_bypass_marker_live`. Without this, `/plan-review`'s own fan-out would consume one of two slots on every plan-driven branch — 115 of them in the measured window — dropping the effective trigger to code-review round 2 and contradicting the pre-registered trigger point. This is the lighter primitive than the alternative considered (a third hook on the `Skill` surface recording `/code-review` invocations): it reuses a `_lib.sh` helper four existing gates already call and adds no new observation surface.

**Mechanism 4 — recurrence: fires once per branch; the latch does not re-arm.** `[anchors: rows 3, 15]` Grounded in the case study's own "entry to round 3" (singular) and in this repo's compounding-defensive-layers convention: a latch re-arming at rounds 5, 7, … would be a second layer closing a gap the first created. A branch still active 30 days after its consult can re-fire once, because the latch directory is swept on the same 30-day interval as every other self-sweeping state directory in this repo — a named residual, in the conservative direction. Matching `nudge-worktree-anchor.sh`'s and `review-ledger.sh`'s own sweep placement, the `find -mtime +30 -delete` for both new state directories runs only inside the recorder's write-transition branches (the append and the latch-write), not unconditionally on every `Agent|Task` `PostToolUse` firing — the overwhelming majority of dispatches are `code-writer`/`general-purpose`/`Explore`/`Plan`, which take neither branch, and an unconditional sweep would reintroduce, on the recorder side, exactly the per-dispatch tax Mechanism 7 works to avoid on the gate side, across the whole install base.

**Mechanism 5 — release condition: a content-free latch.** `[anchors: rows 1, 13]` `<config-dir>/.architect-consult-latch.d/<repo-hash>.<branch-hash>` is presence-only, deliberately unlike every completion marker in this repo, whose content is a hash of the reviewed state so the gate re-arms the moment that state changes. Here re-arming on state change is precisely wrong: rounds 3+ exist because the diff keeps changing, so a content-addressed latch would re-deny on the first post-consult fix — the compounding-layers failure again. The state file's `<repo-hash>.<branch-hash>` keying (not `<session-id>`) follows the same reasoning `docs/hooks.md`'s "Marker keying" section already applies to completion markers: the session id is a write-side key only, and a review that still covers the current state keeps counting across a resume.

**Mechanism 6 — the recorder as a separate `PostToolUse` hook.** `[anchors: rows 5, 8]` `log-reviewer-round.sh` registers on `PostToolUse` matcher `Agent|Task` (mirroring the new gate's own matcher, Mechanism 2) and self-filters to reviewer-persona/`plan-architect` dispatches internally, per this repo's hook defense-in-depth convention. It appends round state on a reviewer-persona dispatch, and writes the latch on a `plan-architect` dispatch whose prompt's first line is not `MODE=plan-sections` — the `MODE=` convention `plan-architect.md` and §37 already establish, read the fail-safe way (any non-`plan-sections` first line, including an absent one, is a consult). `PostToolUse` rather than folding the write into the gate's allow path: the latch must mean *a consult ran and returned*, not *a consult was requested*, so a dispatch aborted mid-flight leaves the gate armed. Lighter alternatives rejected: having the gate write on its own allow path (loses the ran-vs-requested distinction above), and having `/code-review`'s SKILL.md call a recording script (an instruction-enforced write backing a hook-enforced gate — the mismatch the "Should this be a hook?" rule exists to prevent). There is no existing same-surface `PostToolUse Agent|Task` hook in this repo to mirror — `log-routing-read.sh` fires on `PostToolUse` matcher `Read` (an unrelated trigger, reading `ROUTING.md`), not on a subagent dispatch, so its shape is not a precedent for this recorder's matcher or self-filter and the two are not otherwise alike.

**Mechanism 6a — the round-state append is lock-guarded.** `[anchors: root; row 17]` Mechanism 1 treats a whole parallel reviewer fan-out (up to 5 dispatches) as the normal case, so `log-reviewer-round.sh`'s check-then-append at the shared per-branch state file is a genuine concurrent race, not a theoretical one. The recorder reuses the same `noclobber`-lock discipline as `review-ledger.sh`'s `_append_ledger_line_locked` (row 17) — a same-directory lock file, acquired before the read-check-append, released after — implemented as a new `_lib.sh` helper (`_lib_append_line_locked`, Critical files) rather than sourcing `review-ledger.sh` itself, since that script is not currently sourced by any hook. `_append_ledger_line_locked`'s params are already generic (`LEDGER_FILE LOCK_FILE LINE`, not hardcoded to the ledger), so genericizing it into `_lib.sh` is a direct translation, not a redesign — but the translation must carry the full shape, not just the acquire/release skeleton: `_lib_append_line_locked` replicates `_append_ledger_line_locked`'s dead-PID eviction (`kill -0` check on the lock's holder, immediate retry on a dead one) and its bounded-retry fallback to an unlocked append after `_LEDGER_LOCK_RETRIES` failed acquisitions. This matters more here than at `review-ledger.sh`'s own call site: `log-reviewer-round.sh` is a `PostToolUse` hook subject to this repo's harness-imposed hook timeouts, so it is more exposed to being killed mid-lock than a skill-invoked CLI script — without eviction, a single killed hook process leaves a permanent lock file that silently blocks every future round-state append for that branch, under-counting rounds with no signal. The lock file takes the same `<state-file>.lock` naming `review-ledger.sh` uses, so it falls inside the state directory's own 30-day `find -mtime +30 -delete` sweep (Mechanism 4) rather than needing a separate sweep pattern. Consolidating the two call sites onto one shared helper in `_lib.sh` is a reasonable follow-up but is not this plan's job (see Out of scope). Without the lock, N concurrent same-state dispatches could each observe "not yet present, under cap" and each append, inflating the count the gate's cap-check reads and causing a false-positive deny on a converging PR — the exact failure this design exists to prevent.

**Mechanism 7 — hot-path cost bound.** `[anchors: rows 2, 7]` The gate resolves nothing expensive until it must, in this order: tool-name check, then reviewer-persona check, then the disable sentinel, then Mechanism 3's `_lib_active_bypass_marker_live` check for a live `.plan-review-active.d`/`.ready-for-review-active.d` marker — all fork-free (the marker check short-circuits at a single `[ -f "$marker" ]` test before any `cat`/`tr`/`kill` in the common no-marker case). Only past those does it pay two `_lib_capped` git calls (repo root, branch name) to locate the state file, and only when that file is already at the cap does it pay `git diff --cached | sha256sum` plus `rev-parse HEAD`. Every non-reviewer `Agent`/`Task` dispatch exits before the first git call.

**Mechanism 8 — shared state recipe in `_lib.sh`.** `[anchors: rows 1, 3]` The key and value recipes go in `_lib.sh` as `_lib_reviewer_round_state_key` and `_lib_reviewer_round_state_value`, with an explicit determinism contract in the header — read side (gate) and write side (recorder) must agree byte-for-byte or the gate wedges, the same contract `_lib_active_plan_hash` already documents. The reviewer-persona predicate derives from `_LIB_REVIEW_ONLY_AGENTS` by excluding the two harness built-ins its own header already names, rather than adding a third enumeration of the reviewer roster.

**Mechanism 9 — `enforce-marker-script-shape.sh` is deliberately not extended.** `[anchors: rows 13, 14, 18]` The latch sits outside that hook's protected path shapes, and leaving it there is the call rather than an oversight. Extending the hook would defend a path with no traversal from any agent that could reach it via the latch write itself, which is the compounding-layers tell: no agent in `_LIB_NO_GATE_RELEASE_AGENTS` ever writes the latch, because none of them dispatches `plan-architect` (a `Skill`-less identity can't run `/code-review`'s reviewer fan-out that would trip the gate in the first place). This is narrower than claiming the deny itself never reaches a subagent — it can (row 18): `general-purpose` and `claude` are deliberately absent from `_LIB_NO_GATE_RELEASE_AGENTS` as the documented delegation escape hatch, and this repo's own CLAUDE.md safety section prescribes delegating a harness-blocked review skill to exactly such a subagent — which then fans out reviewers and can receive this deny, as a party that (per §37/G2) cannot verify why it was dispatched. Mechanism 10's deny message accounts for this directly (see its added subagent clause) rather than resting on a claim that the case never arises. The residual this mechanism defends against — a main-session or delegated-subagent `touch` of the latch instead of dispatching — sits at the same enforcement tier as §37's explicit-user-ask gate, and carries no efficiency incentive since the sanctioned path is a single dispatch; it is not in `permissions.allow`, so it surfaces as a prompt.

**Mechanism 10 — failure direction: deny on payload failure, allow on state failure.** `[anchors: rows 7, 4]` The gate denies on malformed/empty/non-object payload, missing `_lib.sh`, and missing `jq`, because `TestGateHookBehavior` requires it uniformly of every gate. It exits 0 (allow) when the session id is unusable, the config dir is unresolvable, the repo root is unresolvable, or HEAD is detached — following `require-routing-read.sh`'s stated posture that "the marker is what turns enforcement ON, so an unusable id must not turn it on." This is a cost-and-quality interruption, not a security control, and an over-firing deny on unresolvable git state would block reviewer fan-out on legitimate work. Per this repo's hook-review convention that "reviewers shouldn't have to re-derive [the fail posture] from the code," both new hooks' headers state this split explicitly, plus the other known-gaps this plan reasons through elsewhere: reviewer-persona-only scope (Mechanism 7 — a `code-writer`/`general-purpose`/`Explore`/`Plan` dispatch is never gated or recorded), the once-per-branch non-rearm behavior (Mechanism 4), and the zero-start residual for branches already in flight at merge time (G4).

**Mechanism 10a — deny-message content: discoverability, not just reachability.** `[anchors: root; row 18]` The design never structurally deadlocks (`plan-architect` is never itself gated, and Mechanism 10 allows on every state-resolution failure), but an agent hitting the deny sees exactly one prescription in isolation. If it is infeasible in that session, a well-behaved agent has no sanctioned next move — and, per this repo's own safety rules, is *more* likely to get stuck than a careless one, because it has correctly internalized "never hand-write marker state" and "don't self-authorize a broad, persistent config change." The message therefore states three things, in this order: (1) run `plan-architect MODE=consult` — the compliance path; (2) if that is genuinely not workable in this session, **report the block to the engineer rather than resolving it unilaterally** — the disable sentinel (Mechanism 11) exists for a human to flip deliberately, and an agent is never instructed to touch it itself, since that is a persistent, machine-wide behavioral change with no per-repo or per-session scope, and CLAUDE.md's own blast-radius-confirmation rule applies to exactly this shape of action; (3) **a subagent specifically**: report the denial to your dispatcher rather than resolving it yourself — mirrors the general escalation instruction but names the concrete reporting path a dispatched subagent actually has, since (per Mechanism 9) a `general-purpose`/`claude` subagent delegated a review skill can receive this deny and cannot itself verify why it was dispatched (§37, G2).

**Mechanism 11 — on-by-default with the disable sentinel.** `[anchors: G5, rows 9, 10]` `<config-dir>/.round-consult-gate-disabled` is presence-only, read via `_lib_config_dir`, checked before any git call. Its `SENTINEL_INVENTORY` row is `machine` scope with an empty prompt-description and default-state `disabled` — the `.handoff-nudge-disabled` shape exactly, which reports "the suppression is disabled" (i.e. the gate is on) and prints both paths when `CLAUDE_CONFIG_DIR` and `$HOME/.claude` diverge. It is documented inside the gate's own `docs/hooks.md` bullet, matching where `.handoff-nudge-disabled` and `.consume-durable-continuity-disabled` are documented; the "Non-hook opt-in/opt-out sentinels" section is reserved for sentinels that gate no hook.

**Mechanism 12 — routing prose points the existing clause at a condition, not an event.** `[anchors: G2, row 11]` `claude/.claude/CLAUDE.md`'s Model & Effort Routing Opus bullet currently ends "…and never dispatch it this way on your own initiative (see `docs/design-decisions.md` §37…)". Reworded in place, without growing the file, to name two carve-outs: a hook deny prescribing the dispatch, or **the dispatching session's own recognition that this branch is entering a third `/code-review` round** — the condition Mechanism 13 authorizes, not the deny that would otherwise force it. The carve-out is deliberately **condition-shaped, not event-shaped**: wording it as "unless a hook deny prescribes it" would reward the worse outcome (a session that self-triggers early and correctly is technically in violation, while one that blunders into the deny is compliant) and would let the disable sentinel silently revoke the *option* along with the *enforcement* — since no deny would ever prescribe it, "on your own initiative" would once again be flatly forbidden the moment a stow consumer disables the gate. Conditioning on the precondition itself keeps the standing option alive independent of whether the mechanical gate is on. §37's text is untouched — it is a dated decision record and preserved content. New §41 records what changed and, critically, what did not: §37's claim was that the *explicit-user-ask* gate is not mechanically detectable, and that claim survives intact, because this gate mechanizes a different precondition (round count) and leaves the user-ask question exactly where §37 left it. That distinction is why no edit to §37 is warranted.

**Mechanism 13 — a standing proactive option for the dispatching session, with the hook as backstop, not substitute.** `[anchors: G1, G2, rows 15, 16]` The dispatching session — unlike a subagent (G2) and unlike the hook itself (G1: tool-call payloads only, never the conversation) — has direct visibility into how many real `/code-review` rounds have run on this branch. Mechanism 12's carve-out lets it act on that visibility: dispatch `plan-architect MODE=consult` on its own recognition of entering round 3, before the reviewer fan-out that would otherwise trip the gate.

This is not a second enforcement layer for the same trigger — the Out-of-scope section's rejection of an "instruction-enforced `/code-review` Step-1 fallback" is a different proposal and stays rejected (see Out of scope, revised). Tested against this repo's own compounding-layers rule ("each layer closing a gap the prior layer created"): this option closes no gap the hook created, is strictly weaker on enforcement, and never denies anything on its own — it cannot be a layer, because it is not one. What it buys: the hook's counter is an admitted proxy (G1; row 16 concedes it is "closer to the real quantity," not equal to it), and Mechanism 4's non-rearm means the hook goes **permanently silent** after a branch's one consult — exactly the non-converging case this design exists for, at rounds 5, 7, 9. The two signals disagree harmlessly in both directions: the session over-counts → one extra Opus dispatch on a converging PR, at the cost §37 already accepted for the unbounded explicit-user-ask case; the session under-counts or never acts → the hook still catches it at the precise, mechanical count. Neither signal dominates; there is no path where the disagreement produces a wrong *deny*.

This composes with Mechanisms 5 and 6 with **no code change**: the recorder writes the latch on *any* `plan-architect` dispatch whose prompt's first line is not `MODE=plan-sections` (Mechanism 6), unconditional on whether a deny preceded it. A session that self-triggers before the round-3 fan-out simply writes the latch through the existing door, and the subsequent fan-out is never denied. Verification step 5 gets one added sentence pinning this composition claim directly.

One consequence to state rather than patch, since it predates this mechanism and is not newly created by it: the latch is content-free and condition-blind (Mechanism 5), so an explicit-user-ask consult (§37's original case) at round 1 also writes the latch and spends the branch's one firing — after which Mechanism 4's non-rearm means rounds 3, 4, 5 get nothing, ever, from either path. Patching this would require content in the latch, which Mechanism 5 already rejects for good reason (a content-addressed latch re-denies on the first post-consult fix). §41 states the latch's actual meaning plainly — "an architect consult ran on this branch recently," not "the gate's prescribed consult ran" — so a future reader treats the early-consult case as intended coverage, not a hole.

## Out of scope

- **The instruction-enforced `/code-review` Step-1 fallback.** A hook-enforced counter is confirmed feasible on this design, so the fallback the case study left open — a substitute enforcement mechanism inside `code-review/SKILL.md`, aimed at whoever runs the review (often a delegated subagent lacking the round-count visibility the whole idea depends on) and trying to independently guarantee the same invariant the hook already guarantees — is unnecessary and would be a second layer for the same trigger. **This is a different proposal from Mechanism 13's standing proactive option**, which lives in CLAUDE.md (read by the dispatching session, not a delegated subagent), enforces nothing on its own, and composes with the existing hook mechanism rather than duplicating it — see Mechanism 13 for why that one is not a compounding layer.

# Prevent runaway subagent-dispatch cost

## Context

Prevent a subagent dispatch from silently burning unbounded time and money the way one did on the `pr-review-skill` branch: a single `general-purpose` subagent was handed a compound "review, commit, push, ready-for-review — loop until clean" instruction; every time it was interrupted (machine-contention stalls, and finally a kill), it re-dispatched a fresh full CISO+staff-* specialist panel from scratch instead of resuming or converging. It ran 20+ hours, cost roughly $301 of a $480 total branch spend (2,524 turns in that one dispatch, verified from the actual transcript), and never reached a commit — even though the underlying code diff was fine the whole time. Nobody noticed until asked to investigate after the fact.

This is happening now because two things are true at once: nothing in this repo's skills stops an orchestrator from delegating an entire open-ended, multi-step, loop-until-converged gate sequence as one opaque dispatch: and nothing surfaces a signal — to the dispatch itself or to anyone — when a single dispatch has grown far outside the size any legitimate review or fix pass takes.

## Approach

Three independent mechanisms, each closing a different gap the incident exposed: (1) stop delegating the whole review→commit→push→ready-for-review loop as one opaque dispatch, so an interruption only loses one bounded step instead of the whole pipeline; (2) let a fresh review dispatch check whether the current diff/HEAD was already reviewed clean before re-spawning a full specialist panel, reusing this repo's existing marker infrastructure; (3) add a measured, informational nudge — modeled directly on the existing handoff-nudge pattern — that fires when a single dispatch's own turn count crosses a data-grounded outlier threshold, so a runaway is surfaced early instead of after 20 hours. A blunt per-dispatch turn/time cap was considered and rejected for the review/fix work itself (see G2) — the fix targets how dispatches are composed and observed, not a hard ceiling on open-ended work.

### Assumption ledger

**Root problem:** an orchestrator can delegate an unbounded, multi-step "loop until clean" gate sequence to one subagent dispatch with no way for a restarted dispatch to know what a prior, interrupted attempt already established, and no signal to anyone that the dispatch has grown far outside normal size.

**Givens:**

| # | Given | Reason |
|---|---|---|
| G1 | A hook can observe and act on a *running* session's own state (its own transcript, its own token/context usage) from inside that same session's execution. | `[verified: existing behavior]` — the handoff-nudge hook (`nudge-handoff-near-context-cap.sh`) does exactly this today, and fired mid-conversation in this very session (PostToolBatch hook reporting this session's own context percentage). A dispatched subagent is a real Claude Code session in its own right (it has its own `.jsonl` transcript and `.meta.json`), so the same hook surface applies to it. |
| G2 | A hard per-dispatch turn or time cap on open-ended review/fix work would repeat a failure mode this repo already tried and retired. | `[verified: docs/design-decisions.md §10-11, docs/case-studies/check-runner.md]` — `check-runner`'s `maxTurns: 20` was justified only because its charter was narrow and deterministic, and it was still retired 2026-06-23 after continuing to misbehave; `code-writer` deliberately carries no turn cap because its charter (like a review/fix loop) is open-ended, and is backstopped by a downstream pass instead. |
| G3 | Backgrounding local verification commands (`run_in_background` instead of foreground) was already measured and rejected as a cost lever, for a reason unrelated to this incident. | `[verified: docs/cost-levers-considered.md, background-slow-bash-calls.md]` — the rejection is that `run_in_background` governs detachment, not approval-wait time, which is what actually dominates duration; re-proposing it here would re-litigate a settled measurement. |
| G4 | True stall/liveness detection — distinguishing "this dispatch has hung due to machine contention" from "this dispatch is still legitimately working" — is not something any hook or script in this repo currently does, and building it is out of this plan's reach. | `[verified: research this session found no heartbeat/liveness mechanism anywhere in hooks/, scripts/, or docs/]` — the closest analogs (`advance-past-commit-stall.sh`, `hook-timeout-guard.md`) target a different problem (a needless permission question at turn-end; hook-script execution time) and explicitly disclaim this scope. This given is why M3 is a turn-count nudge (something a hook *can* observe), not a stall detector. |

**Mechanisms:**

- **M1 — Don't delegate the whole gate loop as one dispatch.** `anchors: root`. Add explicit guidance that a "review → commit → push → ready-for-review, repeat until clean" sequence must be driven by the orchestrating session itself, or split into separate bounded per-step dispatches the orchestrator sequences between — never handed to one subagent as an internal loop. This bounds the blast radius of any interruption to the current step, and restores per-step visibility to the human (each step's result returns to the orchestrator's own, human-visible conversation, rather than disappearing inside one subagent for hours). `[engineer-verified]` — confirmed with the user as the preferred direction over a blunt cap, in prior discussion this session.
  - Lighter primitives considered: (a) leave the compound dispatch as-is and just cap its turns — rejected per G2, and it doesn't stop the redundant-full-panel-restart behavior, only bounds how large one restart can get; (b) have the dispatched subagent checkpoint its own pipeline progress to disk so a restart can resume mid-pipeline — rejected as heavier: it requires a new persistence format and a resume-parser, when orchestrator-driven sequencing already gets checkpointing for free (each completed step's result lands in the orchestrator's own conversation, which the harness already persists).
- **M2 — Idempotency check before re-spawning `/code-review`'s panel.** `anchors: root`. `code-review` checks the existing `marker.sh` staged-diff-hash marker before dispatching specialists; a marker that already matches the current staged diff short-circuits to "already reviewed clean, skip the panel" instead of re-running it. This is the mechanism that directly serves the incident scenario: a restarted loop re-running `/code-review` on a staged diff nothing has touched since the last clean pass. `ready-for-review` is scoped OUT of M2 — `[verified: claude/.claude/skills/ready-for-review/SKILL.md]` its own step-8 completion marker is keyed on post-resync HEAD SHA and already covers whole-gate idempotency for the cumulative PR diff; `/code-review`'s marker is keyed on the *staged* diff and cannot answer the same question for `ready-for-review`'s different diff scope (`ready-for-review`'s own text confirms this: step 3 explicitly does not write the staged-diff marker because "the reviewed diff is not the staged diff"). Applying one shared short-circuit to both would either be inert in `ready-for-review` (nothing staged at that point) or silently skip a needed review — no gap has been shown that `ready-for-review`'s existing marker doesn't already close, so no new mechanism is added there.
  - Lighter primitives considered: (a) a new, separate "review result cache" — rejected, it would duplicate state `marker.sh` already owns (single source of truth); (b) `review-ledger.sh`'s finding-level log — rejected, it records individual finding dispositions, not whether the whole panel reached a clean, marker-worthy state, so it can't answer "was this already fully reviewed."
- **M3 — Turn-count nudge on individual dispatches, adapted from the existing handoff-nudge pattern.** `anchors: root`. A hook fires inside a subagent's own execution (per G1) when that dispatch's own turn count crosses a measured outlier threshold, surfacing a recommendation to stop and report rather than continue — informational, not a kill. `[verified: corpus measurement this session]` — scanned every `subagents/*.jsonl` transcript across this machine's personal-account corpus (4,058 dispatches with recorded turns): p50 = 28 turns, p90 = 82, p95 = 136, p99 = 339, max = 4,178. The incident dispatch ran 2,524 turns — far beyond p99. A threshold near p99 (~300–350 turns) would have surfaced this dispatch after a small fraction of its eventual cost.
  This is an *adaptation*, not a direct reuse, of `nudge-handoff-near-context-cap.sh` — three respects in which the new hook must differ, each `[verified: claude/.claude/hooks/nudge-handoff-near-context-cap.sh]`:
  - **Inverted polarity.** The existing hook explicitly no-ops for any subagent (`if [ -n "$AGENT_TYPE" ]; then exit 0; fi`) — it only nudges the main session, because a context-percentage nudge is about *that session's* next handoff decision, which a subagent about to return doesn't have. M3 nudges *only* when `AGENT_TYPE` is a subagent type — the opposite condition — because turn-count runaway is specifically a subagent-dispatch problem; the main orchestrating session doesn't need this signal about itself.
  - **Incremental counting, not a full-transcript rescan.** The existing hook's cheap read only works because it needs the *latest* usage record. Turn count needs a running total; re-scanning the whole transcript on every fire grows with transcript size across one long dispatch. The hook instead maintains a small per-dispatch counter (e.g., a state file keyed on the dispatch's own session id, incremented per fire) and reuses the existing hook's offset/line-tracking helpers for mid-write transcript safety — never a naive full-file `jq -s` pass.
  - **Bounded firing cadence.** Given the measured distribution is a coarse, monotonic outlier signal (not one needing per-batch resolution the way context-percentage does), the hook checks on a sampled cadence (e.g., every Nth `PostToolBatch`) rather than every single one — still catches a multi-thousand-turn runaway within a small fraction of its eventual cost, at a fraction of the fixed overhead multiplied across every subagent dispatch system-wide.
  - Lighter primitives considered: (a) a hard kill at the threshold — rejected per G2, same reasoning as M1(a); (b) rely on the human noticing via billing/usage dashboards — rejected, that is exactly the failure that let this run 20+ hours unnoticed.

Plus its `claude/.claude/settings.json` registration.

## Out of scope

True stall/liveness detection for a dispatched subagent — distinguishing "hung due to machine contention" from "still legitimately working" in real time — is a harness-level capability gap (G4), not something a repo-level hook can close today. M3's turn-count nudge catches a runaway *loop* (many turns, unusually large dispatch) but would not by itself catch a dispatch that is simply hung and producing no turns at all; that half of the incident (machine-contention stalls needing manual resume) is noted here as a known gap, not silently dropped.

# Plan: hook threat-model directive and per-gate tier marker (GH-1073)

## Context

Goal: give this repo's hooks one citable statement of their default threat model, and enforce it mechanically.

No single place says the hooks default to guarding a *cooperative* agent's honest mistakes. `require-respond-pr.sh` (cooperative) and `require-ready-for-review.sh` (adversarial input) each state a position in their own header, but nothing generalizes it. `deny-reviewer-tree-mutation.sh` has absorbed five work sessions of review rounds, each finding a new command shape a cooperative review-only agent would never emit, and its header carries ~115 lines of conceded gaps with no scope statement.

Why now: GH-1067's tokenizer rewrite of `_lib_fragment_invokes_tool`/`_lib_fragment_invokes_git` will otherwise relitigate the boundary without a stated scope.

Outcome:
1. A short `## Hook threat model` section in the repo-root `CLAUDE.md`, after `## Review pipeline`.
2. A `## Threat-model tiers` section in `docs/hooks.md` holding the axes, tier definitions, dependency invariant, and per-hook classification.
3. A `# tier-threat-model: <tiers>` header line on every `# hook-class: gate` hook, plus tests in `test_hook_alignment.py`.

Review rounds after this plan was written revised several pieces of this plan's quoted "exact"/"verbatim" text (the CLAUDE.md section, M14's header lines, M15's deny-network-installs sentence, and others) for accuracy or clarity. The shipped files are authoritative for final wording; this plan's quotes are the design intent, not a byte-for-byte diff target. The waiver paragraph in `docs/hooks.md` now states accepted risk rather than compensating controls, so this plan's "compensating controls" wording is superseded.

## Approach

Give every `hook-class: gate` hook a second machine-readable header line, `# tier-threat-model: <tiers>`, on line 3. Define the axes, the tier definitions and the per-hook classification once in a new `docs/hooks.md` § "Threat-model tiers". Add a short `## Hook threat model` section to the repo-root `CLAUDE.md` that states the cooperative default and its two exceptions, and cites that section. Pin presence, grammar, a floor for the `untrusted-input` gates, and docs↔header agreement in `test_hook_alignment.py`. The header line is the source of truth for a hook's tier; the docs table adds the one-clause rationale the header line cannot carry, and a test keeps the two from drifting.

**Three independent axes** (from the issue): (1) agent intent, assumed cooperative — the only thing the directive governs; (2) input trust, never assumed; (3) consequence reversibility, independent of (1). Axis (2) governs which findings a review may waive on cooperative-agent grounds; it is a disposition label, not a claim that any gate's matching logic is proven to resist steered input — adversarial robustness against a determined attacker is out of scope for a text-matching hook and lives, if anywhere, in capability removal or a git-native pre-commit/pre-receive layer (`docs/security-hardening.md`).

- **M4 — tier definitions and precedence, stated once in `docs/hooks.md` as reviewer instructions rather than adjectives.** `anchors: root`. A tier applies to a hook by its **worst member**: a hook whose denied set mixes reversible and irreversible outcomes takes the elevated tier (already how `require-worktree-for-git-writes.sh`, `block-gh-pr-merge.sh` and `deny-pii-in-commits.sh` are tiered).
  - `cooperative` — this gate guards a cooperative agent's honest mistakes. A review finding that requires a command or staged-content shape a cooperative agent would never emit is not a defect in this gate, unless the gate also lists `untrusted-input`. Over-deny on ordinary shapes a cooperative agent does emit stays in scope for every tier.
  - `untrusted-input` — **positive test, not a negative one:** this gate's header, or its `docs/hooks.md` / `docs/security-hardening.md` entry, states that steered input (prompt injection, adversarial content read from outside the session) is part of what the gate defends against; or another `untrusted-input` gate's header names this gate as its own backstop against deliberate evasion (M10's dependency invariant). The tier is a **disposition label**: it decides which findings a review may waive on cooperative-agent grounds, not a claim that the gate's matching logic actually resists steered input. A finding needing a shape a cooperative agent would not emit is live only when the change under review introduces or widens that gap; a pre-existing gap of that shape is accepted debt, recorded on the gate's header or the tracking issue it points to, and is not, by itself, a blocking finding (the regression-only rule, M12).
  - `irreversible` — bypassing this gate produces an outcome the session cannot retract: published or pushed content, a secret in model context, this session's or another session's uncommitted work destroyed. Over-deny is the correct trade; a false-positive-cost argument alone does not justify relaxing it. A commit-boundary gate is `irreversible` only when the gated content is secret, PII or private-identifying (i.e. its bypass is publication), not merely because a commit occurred. This tier governs relaxations only; it does not by itself suspend the cooperative waiver for gap findings.
  - Precedence rationale (from the `plan-architect` consult): reversibility calibrates deny-versus-allow; intent decides which shapes a gate must catch. Letting `irreversible` suspend the waiver would collapse the intent axis into the reversibility axis and make every gap finding on the ticket's motivating hook un-waivable.

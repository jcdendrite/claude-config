# RFR context-threshold check

## Context

Give `/ready-for-review` a context-budget measurement at its entry so a
session that is past its handoff threshold says so before running the gate,
instead of orchestrating a multi-step review on a session that is nearly out
of room. Today the only signal at that seam is
`nudge-handoff-near-context-cap.sh`'s own out-of-band hard block, which fires
on tool-call boundaries rather than at the pipeline seam where the engineer
could act on it cheaply. The intended outcome is a warn-only precondition in
RFR step 1 that reports the measurement and recommends a handoff, plus a
single canonical statement of the `--check` interpretation contract that
`plan-it` Step 7, `handoff`, and RFR all defer to rather than restate.

## Approach

Designate `handoff/SKILL.md`'s existing warrant-check section as the single canonical statement of how a skill reads `--check`'s output, reword its bullets so they describe the *measurement* rather than handoff's own action, and have `plan-it` Step 7 and a new warn-only `/ready-for-review` step-1 bullet each cite that heading and supply only their own verb. RFR's bullet reports `estimate`/`threshold` when `over_threshold` or `already_fired` is true, flags `nudge_disabled` inline when set, restates the measurement in whichever output ends the run, and never halts — every other status is silent.

The canonical home is a **stowed skill body, not `docs/`**. `docs/handoff-nudge.md` is the obvious candidate and is already cited by both existing callers, but every skill→`docs/` citation in the tree today points at *background* ("see X for why", "for the derivation", "for rationale") — never at instructions the skill must execute. `docs/` sits outside the stow package, so moving the action bullets there would make it the first load-bearing one and would silently degrade any run outside this repo. Cross-skill `§` citation is the mechanism the repo already uses for exactly this (RFR cites `git-feature-branch-sync/SKILL.md` and `subagent-delegation/SKILL.md` today), it resolves both in-repo and at `~/.claude/skills/handoff/SKILL.md` at runtime, and CI already checks it.

Two things stay duplicated on purpose. The four field names RFR acts on (`over_threshold`, `already_fired`, `estimate`, `threshold`) are the interface, not the contract — naming them keeps the common path citation-free, which matters because the citation's whole audience is a session we just measured as short on room. The `session_id` redaction rule stays inline at each site, because a safety rule that only fires if the reader follows a pointer is a safety rule that does not fire.

**Assumption ledger**

**Root:** `/ready-for-review` orchestrates a six-step review with no measurement of whether the orchestrating session has room left; the only signal at that seam is the nudge hook's out-of-band hard block, which fires on tool-call boundaries rather than where the engineer could act on it cheaply.

**Givens**

- **G1 — `SKILL.md` has no include/import/extends mechanism.** The harness owns skill loading; `@path` is CLAUDE.md-only. Cross-file sharing between skills is citation or nothing. `[verified: .claude/rules/skill-and-agent-self-review.md]`
- **G2 — `ready-for-review/SKILL.md` and `handoff/SKILL.md` are capped at 200 lines and sit at 195 and 198.** `limit_for()` special-cases only `code-review`, `plan-review`(+`ROUTING.md`), and `pr-description`; this change earns no new override. `[verified: claude/.claude/hooks/check-skill-length.sh:65-74]`

**Mechanisms**

- **M1 — canonical home = `handoff/SKILL.md` § "Before writing: is a handoff warranted?", cited by `plan-it` and RFR.** `anchors: root, G1, row12`. This is the lightest mechanism that is simultaneously stowed, already-tested, and already-used by RFR. Four lighter primitives considered:
  1. *`docs/handoff-nudge.md` § "Querying the current estimate (`--check`)"* — lightest of all, since the section exists and both callers already point at it. Fails on row 12: a stow consumer running `/handoff` in an unrelated repo cannot open it, and unlike every existing skill→`docs/` citation this one would be load-bearing rather than background.
  2. *A `_shared/` partial* — barred outright by the no-shared-partials rule, and G1 leaves no mechanism to load one anyway.
  3. *A co-located auxiliary file (`REFERENCES.md` / a `ROUTING.md` sibling)* — `REFERENCES.md` is edit-time only and never loaded at runtime; `ROUTING.md` is co-located with one skill. Neither is a cross-skill mechanism.
  4. *A path-scoped rule under `claude/.claude/rules/`* — `docs/skills.md:125` licenses this only when the need-moment matches a file-read trigger. The need-moment here is invoking a skill; no file read triggers it, so the rule would never load.
  5. *Teaching the hook a `--check --explain` mode* — a code change to a `PostToolBatch`-registered hook to solve a prose-duplication problem, and it puts English prose inside a JSON-contract script. Strictly heavier than a citation.
- **M2 — warn-only, reported in step 1 and re-measured in whatever output *terminates* the run.** `anchors: row1`. A warning emitted mid-gate scrolls past under steps 2–6's tool output, so it must be repeated where the engineer actually reads. The naive choice — the Completion summary — is wrong: steps 1, 2, 3, 4, and 7 all halt on fail, so Completion renders only on the clean-pass path, which is precisely the path where a degraded session matters least. A session short on context is likelier to halt inside the steps 2–4 fix loop, and that halt report is the terminal output it produces. So the restatement attaches to **whichever output ends the run** — the Completion summary on a clean pass, a halt report on any halt — one mechanism with two renderings, not two mechanisms. The restatement runs `--check` **again** rather than repeating step 1's number: steps 2–6 are exactly the tool output that grows the transcript, so the entry-time estimate is stale by the time the engineer reads it, and a stale number presented as current is worse than none. Re-running is free — `--check` exits 0 and writes nothing (row 5).
- **M3 — `docs/handoff-nudge.md:93`'s caller enumeration is replaced, not extended.** `anchors: row2`. An enumeration goes stale on every new caller; a pointer at the single canonical home does not. This makes handoff↔docs mutually referential, which is correct rather than circular: `docs` is canonical for the JSON schema and `reason` vocabulary, `handoff` is canonical for how a skill acts on it.
- **M4 — three new pinning tests in `test_skills.py`, no hook test.** `anchors: row1, row3, row13`. `test_skill_citations_resolve_to_real_headings` already fails CI on a heading rename, but nothing catches the cited section being *gutted*, and nothing catches a future editor flipping RFR's bullet to halt — a flip that RFR's own `## 1. Preconditions (halt on fail)` header actively invites. No hook changes, so no hook test.

**Rows**

1. `[engineer-verified]` Warn only, never halt; no two-tier halt-on-`already_fired`. RFR's judgment-heavy work runs in fresh subagent contexts, so an over-threshold parent degrades orchestration, not review quality, and the nudge hook's hard block still fires independently. **Qualifier the engineer's rationale did not name, and which the design must therefore surface:** that backstop is conditional. The hard block is suppressed when the global kill-switch file is present (`nudge_disabled`) and when a live `handoff` active-bypass marker exists for the session, including a stale one. In exactly those cases warn-only has nothing behind it, which is why row 13 requires RFR to report `nudge_disabled` inline rather than behind the citation.
2. `[engineer-verified]` DRY resolution is one canonical home with three deferrers, not a third copy — applied to the narrowed target (the four-branch reporting/action bullet list, not the JSON schema).
3. `[engineer-verified]` Scope is RFR step 1 only — not `/code-review` entry, not `/respond-pr`.
4. `[verified: claude/.claude/skills/tests/test_skills.py:2575-2615]` `_resolve_citation_target` resolves a `<skill>/SKILL.md` target by matching any skill directory's name, so `` `handoff/SKILL.md` § "Before writing: is a handoff warranted?" `` resolves in CI; `_normalize_heading` strips backticks, so a heading containing `` `--check` `` is citable verbatim.
5. `[verified: claude/.claude/hooks/nudge-handoff-near-context-cap.sh:74-80, 472-474, 484-530]` `--check` is dispatched before the unconditional stdin read, before `agent_type` is parsed, and before the subagent gate; it exits 0 on every branch. A Bash-tool call with no stdin redirect neither hangs nor is suppressed inside a subagent.
6. `[unverified]` **What session `--check` resolves when run from inside a subagent.** The Step 3 evidence claimed "the subagent's own session," but `capture-session-id.sh:106` writes one entry per *claude process PID* (`sessions/$CLAUDE_PID`), and a subagent shares the parent's `claude` process — which points the other way, at the parent's session. Not settled by reading. **The design is deliberately answer-independent and carries no subagent caveat in the skill body:** under the parent-session reading RFR warns correctly, and under the own-session reading a fresh subagent measures under threshold and RFR simply stays silent. Warn-only plus fail-silent means the worst case is a missed warning, never a false one. Settling it needs a live run of `--check` from inside a dispatched subagent, compared against the parent's own `--check` — worth doing, not worth blocking on, and not worth publishing an unverified claim into a stowed skill body.
7. `[verified: claude/.claude/skills/tests/test_skills.py:3782-3803]` `TestStowedScriptPathContract` forbids any SKILL.md from writing `<config-dir>/hooks/…` or `${CLAUDE_CONFIG_DIR:-…}/hooks/…`. The new RFR bullet must spell the recipe literally as `~/.claude/hooks/nudge-handoff-near-context-cap.sh --check`, matching `plan-it:137` and `handoff:30`. (Step 3's evidence read line 3802 as a fixture-presence check on the recipe string; it is a negative unit test on the path-templating matcher, and this is the constraint it actually imposes.)
8. `[verified: claude/.claude/skills/ready-for-review/SKILL.md]` RFR's body does not hard-wrap — steps 3, 5, and 6 each carry multi-sentence paragraphs on one physical line. A three-sentence bullet costs one line, so G2's 5-line margin is comfortable rather than binding.
9. `[verified: claude/.claude/scripts/select-tests.py:293-298, 371, 377]` `handoff/SKILL.md` carries an exact-path cross-domain exception adding scripts+hooks tests; any `docs/` file adds hooks+skills. The diff's union is hooks + scripts + skills tests.
10. `[verified: claude/.claude/skills/ready-for-review/SKILL.md]` Step 1 carries no `<!-- HOOK_TEST_FIXTURE -->`, `<!-- CACHE_RULE -->`, or `<!-- SCOPE_RULE -->` anchor today. The new bullet must not introduce one — `_EXPECTED_SCOPE_ANCHORS`/`_EXPECTED_CACHE_ANCHORS` are exact sets and would need updating for no benefit.
11. `[unverified]` Whether `check-skill-length.sh`'s comparison is `> limit` or `>= limit`. Treat 200 as a hard ceiling and target ≤199 for both capped files rather than resolving it.
12. `[verified: CLAUDE.md "Repo layout", install.sh]` `docs/` is not installed to `~/.claude` — the stow package is `claude/`, mapping `claude/.claude/` → `~/.claude/`, while `docs/` sits at repo root. This is a *reachable* condition, not a given: editing `install.sh` and the stow package would dissolve it. The plan declines to (see **Out of scope**), because doing so is heavier than the citation M1 chose, not lighter — it changes the install surface for every stow consumer to solve a prose-duplication problem. Without this condition, alternative 1 (`docs/handoff-nudge.md` as canonical home) would win on being the section that already exists.
13. `[verified: claude/.claude/hooks/nudge-handoff-near-context-cap.sh:422, 663-669]` `nudge_disabled` is a field inside `status:"ok"`, not a separate status, so it does not suppress the `over_threshold`/`already_fired` report. It must nonetheless be named **inline** in RFR's bullets rather than deferred to the citation: it is the one field that tells the engineer the hard block behind this warning is switched off, and a pointer is what a context-short reader is least likely to follow (M2's own reasoning).
14. `[verified: claude/.claude/skills/handoff/SKILL.md, claude/.claude/skills/plan-it/SKILL.md]` The section's original owner pays a small comprehension tax for being made canonical: `/handoff`'s branch bullets currently state condition *and* action together, and genericizing them moves handoff's own verb to a closing paragraph, adding one indirection step to the highest-stakes read path of the skill whose entire job is that write decision. Accepted, not dissolved — the alternative is no canonical home at all. Keep the closing paragraph adjacent to the bullets rather than at the section's end.
15. `[verified: claude/.claude/skills/tests/evals/run_skill_evals.py, test_pinned_scope_clause_matches_live_text]` The repo ships a stronger mechanism for the mandatory-vs-advisory ambiguity M4 names: `DISPOSITION_RULE`-anchored, live-model-judged disposition evals, built precisely because that reading "is not deterministically derivable from text alone." The plan **declines** it here, and says so rather than omitting the option: the evals are local-only and cost a model run per invocation, and this clause's failure mode is a future editor's textual flip, which a normalized-clause pin catches in CI at zero marginal cost. Prose-pinning is the honest ceiling for whether the executing model *obeys* an advisory bullet under a `(halt on fail)` header — no CI layer reaches that, and the disposition eval would only sample it.

## Out of scope

- **Any halt behavior in RFR**, including a two-tier halt on `already_fired`. Decided against this session; the design is warn-only end to end.
- **`/code-review` entry and `/respond-pr`.** The same precondition would fit both; adding it was explicitly declined.
- **Every change to `nudge-handoff-near-context-cap.sh`** — the `--check` JSON shape, the threshold constants, the subagent gate, and a `--check --explain` mode. The plan could change the hook and deliberately does not: the duplication is prose, and a code change to a `PostToolBatch`-registered hook is the wrong instrument for it.
- **Making `docs/` runtime-reachable.** Stowing it, or mirroring `handoff-nudge.md` under `claude/.claude/`, is the actual fix for the asymmetry in ledger row 12 and would make `docs/` a legitimate canonical home for load-bearing instructions. This is a condition the plan could reach (`install.sh` and the stow package are both editable here) and deliberately declines to change: it alters the install surface for every stow consumer, which needs its own decision, and it is heavier than M1's citation rather than lighter.
- **Settling ledger row 6 empirically.** Running `--check` from inside a dispatched subagent and diffing it against the parent's would resolve which session it measures; the design does not depend on the answer, and `docs/handoff-nudge.md`'s Known-limitations section — not this plan — is where the result would land.
- **Making the plan→implementation seam a mandatory handoff.** `plan-it` Step 7 keeps "continue in this one by default"; only its duplicated bullet list changes.
- **`README.md`, `docs/walkthrough.md`, `docs/hooks.md`.** None enumerates RFR's step-1 bullets, so none goes stale. `docs/handoff-nudge.md:93` is the only line that does.

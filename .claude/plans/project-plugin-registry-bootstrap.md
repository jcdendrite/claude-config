# Project-plugin registry bootstrap

## Context

Ask: when a trusted repo's checked-in settings enable plugins that are missing from the per-account plugin registry, install them automatically at `-s local` at session start, so later sessions no longer hit `plugin-cache-miss` errors and wait about a minute (the first session after a never-trusted repo's trust click still pays it). Applies to `github`, `directory` and `git` marketplaces under folder-trust consent. (Draft written by the agent and accepted by the engineer by selecting "Yes, use this draft" during plan review.)

Goal: every repo a user opens gets its checked-in `enabledPlugins` recorded in the per-account plugin registry automatically, so plugin skills are present in the first skill snapshot of a session instead of appearing seconds to tens of seconds late.

Claude Code writes an entry to the per-account registry `<config-dir>/plugins/installed_plugins.json` only when someone runs `claude plugin install <plugin>@<marketplace> -s <scope>`. A plugin enabled only through a repo's checked-in `.claude/settings.json` (`enabledPlugins` plus `extraKnownMarketplaces`) is never recorded. In every session that opens such a repo, the registry loads without the plugin, the first skill snapshot has no plugin skills, a `plugin-cache-miss` fires, and a background install completes a variable time later as a no-op re-copy of already-cached files. The registry is per account and never in git, so a checked-in settings change cannot fix it.

Why now: a peer session diagnosed the mechanism from debug logs, and one manual `claude plugin install ... -s project` removed the delay for that account. This plan automates that step.

**Scope resolution (engineer decision):** the original bug report's marketplace was a `source: git` private marketplace (row 15). Probe P9 (Verification) found that a folder-trust click registers and clones a git-source marketplace with no separate prompt, the same as a directory-source one. A source-type allowlist therefore tracks no consent boundary: in every case the consent is folder trust (M1a), which delegates to whatever marketplace the repo declares. The engineer's stated position: "folder trust as consent is fine." M4's allowlist admits `github`, `directory` and `git`, and fails closed on every other or unrecognized value. A value check (Verification, "Value check") reproduced the motivating latency on a git-source marketplace and showed a `-s local` install removes it, so the feature covers the motivating case.

Intended outcome: an approved implementation plan (not code) for a SessionStart hook plus reconciler that front-runs the install, on by default, as a workaround for vendor behavior.

Design origin: the shape of the hook and reconciler came from an agent-authored brief, not from the engineer. This plan tests that design and departs from it where noted (D1, D2, M2, M6, M9).

## Approach

A new SessionStart hook reads the opened repo's checked-in `.claude/settings.json`, compares its `true`-valued `enabledPlugins` ids against the per-account registry file `<config-dir>/plugins/installed_plugins.json`, and — only when an id is missing **and** its marketplace is already registered on this account — launches a detached, locked, timeout-capped reconciler that runs the supported `claude plugin install` for that id with the repo as cwd. The hook itself spawns no CLI and prints nothing; its only write is one bounded line to the shared M9 audit log on its own refusal decisions (M1a's two layers, M2's registry-trust rules, M10's unreadable local opt-out file), since those decisions are made and finalized inside the fast guard before any reconciler is ever launched — this is a local, cheap, CLI-spawn-free append, not the "no CLI spawn" cost M1a's fast-guard rationale is actually about. The reconciler's only write inside the repo is `-s local`'s `.claude/settings.local.json`, gated on a runtime ignore-and-tracked-file check (M6) — this is the one exception to "read-only to this mechanism" (see Out of scope); the registry entry it creates lands in time for the *next* session in that repo, which is the earliest any SessionStart mechanism can help.

### Decision D1 — marketplace-add policy (engineer asked directly; recommendation, overridable)

**Recommendation: the hook never adds a marketplace. It installs only ids whose marketplace name is already registered for this account, and ignores the repo's `extraKnownMarketplaces` entirely.**

The engineer's reasoning — "allowlisted marketplaces should be okay because clearly they were allowlisted by a human" — is sound about *where trust comes from* and lands one step short on *what carries it*. `extraKnownMarketplaces` maps a marketplace **name** to a **source**, and the repo controls both halves. An allowlist keyed on name therefore lets any repo bind a trusted name to an untrusted source; the allowlist would say "trust the marketplace called `<private-marketplace>`" while the repo decides what that name resolves to. Fixing that means keying the allowlist on the source (`owner/repo` for a github source, the full URL for a git source) and refusing on a name match with a source mismatch. But once the allowlist holds "sources I trust," it is a second copy of information `claude plugin marketplace list` already holds after one human `claude plugin marketplace add` — a single-source-of-truth violation whose two copies drift silently, and the weaker copy is the one the automation reads.

The capability difference is the deciding factor. `claude plugin marketplace add` fetches and trusts a new source of executable content (plugins ship hooks, skills, agents, MCP servers). `claude plugin install` from an already-registered source widens nothing. This plan needs only the second. With the hook on by default for every stow consumer and driven by the `.claude/settings.json` of whatever repo gets opened, the narrower primitive is the one that makes on-by-default defensible rather than contingent on each consumer curating an allowlist file correctly.

What D1 buys concretely: a stow consumer whose only registered marketplace is `claude-config` can have this hook install nothing except `claude-config`'s own plugins, which `install.sh` already installed for them. The feature is inert for such a consumer by construction, not by their correct configuration. Under any allowlist-add policy, on-by-default means every consumer inherits a mechanism whose blast radius depends on a file they have never seen.

**Phase-0 correction:** "already registered" is weaker than the paragraph above implies — see row 15 for the evidence. M4's marketplace-registered guard is still real (D1 itself adds no new marketplace), but it gates on a state the vendor already lets a repo populate through nothing more than a trust click **for directory-source and git-source marketplaces, both confirmed (probe P9 for git; the git case also performs a network clone on trust).** M4's allowlist admits `github`, `directory` and `git` because trust alone already registers each of them. See M1a, which this finding motivates directly.

**The git-source question dissolves under D1.** `register-marketplace.sh`'s `source_type != "github"` skip (lines 113-115) gates only account-level registration from `<config-dir>/settings.json`. The hook never registers marketplaces, so the skip never gates this feature and `register-marketplace.sh` needs no change.

**Cost the engineer is accepting by taking D1:** a marketplace that no repo has declared must be registered once per account per machine by hand. A repo that declares the marketplace in its own `extraKnownMarketplaces` needs no manual step, because a folder-trust click registers it (probe P9). The natural manual command, `claude plugin marketplace add <url> --scope user`, is **not yet safe to document**: round-1 CISO dynamically confirmed (scratch `CLAUDE_CONFIG_DIR`, CLI 2.1.278) that this command writes an `extraKnownMarketplaces` entry — source and URL — into `<config-dir>/settings.json`, through a stow-style symlink, into the tracked target file. Row 5 (unchanged, `[verified]`) confirms `<config-dir>/settings.json` **is** this repo's stowed, tracked `claude/.claude/settings.json` for every stow consumer — the exact file a private URL can never live in. This plan does not instruct that command until probe P10 (Verification) confirms a write target that stays untracked for a real stow consumer, or a guard is added that keeps the stowed file clean after the step. Until P10 clears, a stow consumer with a `source: git` private marketplace registers it by whatever means the private marketplace's own repo documents (row 6), and gets no README/`install.sh` guidance from this repo — a real, accepted cost, not a deferred TODO.

**If the engineer overrides to allowlisted-add**, the design must additionally: pin the source in each allowlist entry and compare source (never name) before adding; refuse when the name is already registered against a different source rather than re-adding; move the add into the detached child, since it is a network fetch; and add a new gitignored `<config-dir>` file with a `.gitignore` shadow entry (row 21), a `_lib_config_lines` reader (row 7), and its own tests. That is roughly a third mechanism's worth of surface for a capability the motivating case does not need.

### Decision D2 — do not fold `install.sh`'s project-scope block into the shared script (recommendation, overridable)

The prior design replaced `install.sh:731-753` with a call to the new script. The two call sites are genuinely different: different data source (`claude plugin list --json` at a TTY vs. the registry file with no CLI spawn), different idempotence key (projectPath-strict vs. name-keyed, row 22), different failure policy (warn a human vs. silent), different TTY assumptions (row 14). Unifying them is a forced abstraction that also rewrites `test_install_sh_project_scope_plugins.py` (506 lines, two extracted `INSTALL_TEST_FIXTURE` markers) for no behavioral gain. The only duplicated knowledge is the one-line jq expression already duplicated at `install.sh:736` and `register-marketplace.sh:144` — CLAUDE.md's named "a small duplicated value beats a bad abstraction" exception.

`install.sh` still has a role, just a smaller one: one TIP line in the style of its existing `check_private_projects_file` block, naming the one-time marketplace-registration step D1 depends on — **added only once probe P10 confirms a safe, generically-describable step** (D1's cost paragraph); until then `install.sh` gets no such line, and the Critical files/README bullets are scoped accordingly. That keeps the engineer's chosen "hook + install.sh" shape without the risky refactor, once P10 clears.

### Assumption ledger

**Root:** Claude Code records a plugin in the per-account registry only when `claude plugin install` is run; a repo's checked-in `enabledPlugins` alone never produces an entry, so every session in such a repo starts with an empty plugin-skill snapshot and re-runs a background install that never persists. This plan front-runs that install from the supported CLI path so the entry is already present when the next session loads the registry. It is a workaround for vendor behavior, not a fix, and is designed to go inert (fast guard finds everything present, exits 0 silently) if the vendor starts recording eagerly.

**Phase-0 caveat:** probe P1's fixture used a directory-source marketplace (already on local disk) rather than the git-source marketplace the original bug report used, and both cold-baseline sessions in that fixture resolved the plugin instantly with zero `plugin-cache-miss` lines — the fixture never reproduced the latency this plan exists to fix. The later Value check (Verification) did reproduce it on a git-source marketplace, which confirms row 1's cache-miss premise for that case; the mechanism rows below (10, 11, 13) were exercised by Phase 0. Separately, P1 also surfaced a case where the vendor's own background reconciliation *did* persist a second registry entry for a second worktree with no explicit install run against it — narrower than row 1's "never persists" but real; see row 1 below.

**Mechanisms:**

- **M1 — Fast guard, no CLI spawn, regular-file-and-size-capped read.** Read the payload's `.cwd` (`set-session-title-from-branch.sh:93`), resolve `<cwd>/.claude/settings.json` and fall back to `git -C "$PAYLOAD_CWD" rev-parse --show-toplevel` when that misses. Before any `jq` invocation, verify the resolved settings file is a regular file, not a symlink, under a size cap of `_LIB_SIZE_THRESHOLD_BYTES` (`_lib.sh:2694`, 5 MB) — `[ -L ... ]` plus `stat -c%s`/`stat -f%z` against that same shared constant, the same symlink-then-size-cap pattern and the same threshold this repo already applies to untrusted file content in `deny-data-file-reads.sh:118-127` and `ask-new-dependency-disclosure.sh:181-189`, rather than a second, separately-chosen number — a repo-controlled path that resolves to a symlink or a file over 5 MB is skipped, no jq run, same as a missing file. This matters independently of M1a's trust gate: trust is granted once per repo path, not per commit, so an already-trusted repo can later merge a commit that replaces `.claude/settings.json` with a symlink to `/dev/zero` or an oversized file, and M1a's trust check does not and cannot catch that. **This symlink-and-size-cap check lives inside the shared helper itself, not as a separate pre-check each caller must remember to run:** `_lib_missing_plugin_ids <settings-file> <registry-file>` performs the `[ -L ... ]`/size-cap check on `<settings-file>` internally, before its own `_lib_jq` invocation, and returns the same distinguishable "skipped: symlink or oversized" status to both callers — folding this check into the single shared seam the same way M3's `_lib_validate_plugin_id` already folds its own validation in, so the reconciler's independent re-read (M5) gets the guard "for free" rather than needing its own, separately-authored copy that could silently omit it. Once past that guard, the helper extracts every `true`-valued `enabledPlugins` id, diffs it against the registry, and — matching M2's fail-closed rule — returns a distinguishable exit status for "registry present but unparseable or `version != 2`" versus "ids missing." One implementation, one direct unit test independent of either caller, so the hook's launch decision and the reconciler's own re-derived missing-id set (M5) cannot silently diverge from a future change to the symlink/size-cap check, the extraction, or the corruption-handling logic. A `claude` spawn on every session start would re-pay the very startup cost this plan removes. *anchors: row8* — and the version guard below is what makes reading an undocumented file acceptable.
- **M1a — Trust-state precondition, two independent layers, both fail-closed (Phase-0 addition, pinned after round-2 review).** Before parsing the repo's `.claude/settings.json`, the fast guard must pass both of the following, with no CLI spawn (matching M1's own fast-guard rationale):
  1. **Persisted trust-record read.** Read the vendor's persisted per-repo trust record directly — at `<CLAUDE_CONFIG_DIR>/.claude.json`, field `.projects["<repo-path>"].hasTrustDialogAccepted`, the exact field `isTrusted()` itself consults (round-1 CISO's dynamic trace, `agent-reviews/ciso-reviewer-1789875192-auto-reload-plugins-.md`, Foundation concern and F1) — never a value computed through the vendor's runtime `isTrusted()` call, which that same trace confirmed returns `true` unconditionally for non-interactive sessions. Round-2 review found no precedent anywhere in this repo's hook/test code for the previously-floated alternative ("a field on the hook payload"); that option is dropped. The file resolves relative to this session's own `CLAUDE_CONFIG_DIR`, not a fixed `$HOME` path — confirmed by `.claude/plans/register-marketplace-config-dir.md`'s row G1 (`CLAUDE_CONFIG_DIR=relprof claude plugin marketplace list --json` from a scratch cwd created `./relprof/.claude.json` relative to that cwd) — so this read stays account-scoped on this machine's multi-account setup and cannot leak a trust decision across accounts.
  2. **Non-interactive-session refusal, independent of (1).** Refuse to launch when the session is non-interactive (headless: `claude -p`, an Agent SDK invocation, CI, a script) — a genuinely separate check, not a restatement of the trust-record read, so a bug in one layer doesn't also disable the other. The signal is the `CLAUDE_CODE_ENTRYPOINT` environment variable the hook inherits (probe P11): the hook proceeds to its remaining checks only when that variable is exactly `cli`, and anything other than exactly `cli` (another value, an empty value, or unset) is no-launch. The refusal is logged to the audit log (M9) only after layer 1 has passed, so a headless session in an unrelated or untrusted directory writes no line and scripted `claude -p` loops cannot evict install records; the line carries the observed entrypoint value, sanitized and length-bounded per M9, so a vendor rename or an IDE-session skip is diagnosable. IDE and desktop sessions probably report a different entrypoint and so skip the auto-install; that is untested and accepted by this plan (row 30). Layer 2's purpose is to stop the owner's own headless runs and scripts, a cooperative-guardrail purpose; it is not a defense against repo-controlled content, because a commit to a trusted repo that triggers an install triggers it in an interactive session as well. Whether a repo's checked-in `env` settings can set `CLAUDE_CODE_ENTRYPOINT` for the hook is unverified (row 31).

  Any read failure, missing field, or unrecognized shape in either check resolves to "not trusted" / "refuse," matching M2's fail-closed pattern for the registry file — this is undocumented vendor-internal state (row 8) and can drift across CLI versions. Phase-0 probe P7 confirmed the user-level `SessionStart` hook fires before, and regardless of, an *interactive* repo's trust decision — this session's `hooks.log` entry count incremented identically for the declined-trust and accepted-trust sessions (raw entries at 13:20:52, 13:41:07, 13:50:00 PDT on 2026-09-27). That is motivating evidence that a precondition is needed; it does not verify either layer's behavior for the headless case that actually matters most — see probes P8 and P11 in Verification: P8 found no vendor-side install under `claude -p`, and P11 settled the signal layer 2 reads (`CLAUDE_CODE_ENTRYPOINT`). Without both layers the hook would read and act on an untrusted or headless-opened repo's `enabledPlugins` on nothing but the hook harness's unconditional firing (round-1 CISO's F1) or `isTrusted()`'s non-interactive short-circuit (round-2 CISO's F1-continuation finding). *anchors: root; probe P7; probe P8*
- **M2 — Registry trust rules.** Treat a **missing** registry as empty and proceed (matching `install.sh:732-735`'s "proceeding as if none are installed"); treat a **present but unparseable** registry, or `version != 2`, as a reason to exit 0 and do nothing. Absence is a known state; corruption or a format change is not, and a format change must make the hook inert rather than wrong. Drop the prior design's `claude plugin list --json` fallback: it spends a CLI spawn exactly when we have decided the input is untrustworthy, which is a compounding defensive layer. *anchors: row8*
- **M3 — Plugin-id allowlist before argv, enforced at both ends.** Reject any `enabledPlugins` key not matching `^[A-Za-z0-9][A-Za-z0-9._-]*@[A-Za-z0-9][A-Za-z0-9._-]*$` before it reaches a command line — both halves must start with an alphanumeric character, closing the gap the prior class left open (`[A-Za-z0-9._-]+` alone admits a leading `-`, `.`, or `_`, so the stated anti-flag-injection purpose was met only by luck, not by the regex). Also reject the reserved pseudo-marketplace name `npm`: the CLI treats `<pkg>@npm` as a real install form, and `npm` would otherwise pass this regex and be blocked only by happening not to appear in the registered-marketplace list. Pass `--` before the id at the argv sink regardless, as defense in depth. The reconciler independently re-reads the repo's settings file itself (M5's pinned invocation contract — it receives only the resolved repo root, never a parsed id list), and re-validates every id against this same regex and the `npm` exclusion immediately before argv construction, so the check holds against a hand-run or stale-hook invocation, not only the intended call path. The regex and `npm` exclusion live in one shared `_lib.sh` function (e.g. `_lib_validate_plugin_id`) called from both the hook and the reconciler, so the two call sites cannot silently diverge if the regex is ever tightened again — a single unit-test module exercises the function directly, independent of either caller. Also skip every `false`-valued entry and never uninstall. *anchors: root*
- **M4 — Marketplace precondition (D1), fail-closed on listing failure, restricted to evidenced source types.** In the reconciler, not the fast guard, run `claude plugin marketplace list --json`. Any non-zero exit, timeout, unparseable output, or empty result skips every id for this run — fail closed, matching M1a/M2's pattern, rather than reading "no match found" and "listing failed" as the same case. On a successful listing, compare `${id##*@}` against the listed `.name` values with `grep -qFx` (the idiom at `register-marketplace.sh:62-63,134-137`) and additionally read the matched entry's top-level `.source` string — `[verified]` against live `claude plugin marketplace list --json` output, whose per-entry shape is `{"name", "source": "<type>", ...}` with `source` one of `github`, `directory` or `git`. This is written as an **allowlist, not a denylist**: proceed only when `.source` reads exactly `github`, `directory` or `git`; skip (fail closed) every other value, including `url`, an unrecognized type, absent, or null — so a wrong field name (which would make every read resolve to null) fails closed rather than silently admitting every marketplace. The allowlist is the source types the probes evidenced (`directory`, row 15; `git`, probe P9) plus `github`, which no probe covered, and fails closed on everything else, including `url`, which no probe covered either. It guards against unknown or future source types; it is not a consent boundary, because trust alone registers the evidenced types. **Why folder trust as consent holds, and what it leaves out.** The vendor already registers, clones and (after a delay) loads the same plugin in the same trusted session on the same click, and a trusted repo's own `hooks` already execute; M3, M6 and M7 (no `-y`, so a marketplace-declared install command fails without a TTY) also stand. Three residuals are not equivalent and the engineer accepts them ("Accept silence, record it"): (1) *persistence* — the hook's `-s local` install and its `settings.local.json` write outlast the repo's own declaration, so a plugin a repo stops declaring stays enabled locally until `claude plugin uninstall <id> -s local` (M10); (2) *silence* — the hook prints nothing and the gitignored audit log (M9) is the only inventory; (3) *consent binds later commits* — trust is recorded once per path, and whether a pulled commit that adds an `extraKnownMarketplaces` entry or a new `enabledPlugins` id is registered silently is untested (a small user-run probe: pull such a commit in a trusted throwaway repo and see whether it registers with no prompt). **Credential-bearing plugin exclusion:** M1a's trust gate establishes that a repo is trusted to run, not that its `enabledPlugins` list has been vetted plugin-by-plugin — a trusted repo can still name any plugin in an already-registered marketplace, including one documented as carrying live credentials. M4 additionally excludes any id on a short denylist of documented credential-bearing plugins (starting with `issue-triage@claude-config`, per `install.sh:743`'s own warning) from auto-install; those ids fall through to the existing human-run, warned `install -s project` path unchanged. Effective consent for every other id is folder trust (M1a), not per-plugin review — state that plainly rather than implying M4's marketplace check is also a content-vetting step. Nothing ties this denylist to plugin metadata, so a future credential-bearing plugin added anywhere is auto-installable unless someone remembers to add it here by hand — `docs/hooks.md` names this maintenance obligation explicitly (see Critical files). The fast guard stays CLI-free; the precondition costs a spawn only on the drift path. *anchors: row15*
- **M5 — Detached, capped, fd-isolated child, with a stated cap value, a required timeout binary, and a pinned invocation contract.** The hook launches `<config-dir>/scripts/reconcile-project-plugins.sh "$RESOLVED_REPO_ROOT"` with `</dev/null >/dev/null 2>&1 &` and returns immediately — `$RESOLVED_REPO_ROOT` is the exact path M1's fast guard already resolved (payload `.cwd`, falling back to `git -C "$PAYLOAD_CWD" rev-parse --show-toplevel`), passed as `$1` so the reconciler never has to re-derive it from its own process cwd. **This is a pinned decision, not left open:** a detached `&` background child inherits the *launching shell's* cwd, not the session's payload `.cwd` — the exact divergence `set-session-title-from-branch.sh`'s own `test_payload_cwd_overrides_process_cwd` test exists to catch, since a linked-worktree session's main-checkout cwd can differ from its payload `.cwd`. Passing the resolved root explicitly, rather than relying on inherited cwd, is what prevents the reconciler from silently installing into the wrong repository one hop downstream of the same bug class M1 was built to avoid for its own read. The reconciler `cd`s into `$1` before running any scoped plugin command (M6, M7) and independently re-reads that repo's `.claude/settings.json` and the registry itself, rather than receiving a parsed id list over argv, by calling the same `_lib_missing_plugin_ids` helper M1 calls (reused, not duplicated) — one settings-parsing-and-diff implementation shared by both processes, and no risk of an unbounded or injection-prone argv built from repo-controlled id strings. When that helper reports "registry present but unparseable or `version != 2`," the reconciler exits 0 and logs the same M9 decision type M1's own registry-trust rule (M2) would have refused on, so the two processes' corruption handling cannot drift into disagreement. This also resolves M3's own prior hedge ("if the reconciler independently re-reads... rather than receiving ids from the hook") into a firm decision: it always independently re-reads. The reconciler wraps each `claude` call (the M4 marketplace listing, and each id's install) in `_lib_capped_for 30`. No vendor SLA documents `claude plugin install`'s duration, so 30s is grounded by repo precedent rather than a vendor citation: it is double this repo's existing cap for the closest comparable network-fetching subprocess call, `git fetch` at 15s (`cleanup-merged-branches.sh:537`), doubled because an install can involve both a marketplace-metadata read and a plugin-content fetch rather than `git fetch`'s single round trip. `_lib_capped_for`'s own documented fallback (`_lib.sh:134`) is to run **uncapped** and only warn to stderr when neither `timeout` nor `gtimeout` is on PATH — on stock macOS with neither installed, this reconciler would silently lose its cap. The reconciler must therefore check for a timeout binary itself before its first `claude` call and refuse to launch (exit 0, no install attempted) if neither exists, rather than relying on `_lib_capped_for`'s permissive default; this converges with CISO F6's identical required control. The reconciler also checks `command -v claude` up front and exits 0 if absent, rather than letting the first capped call fail with a generic "command not found." Total wall-clock exposure per reconciler invocation is bounded by `(N distinct ids + 1) × 30s` — the `+1` is M4's own one-time `marketplace list --json` call per run, independent of id count, which the exposure statement must include since M4 makes exactly one such call regardless of how many ids follow it. `N` itself is repo-controlled (`enabledPlugins` sets its size); rather than leaving this uncapped, the reconciler additionally enforces a **total per-invocation wall-clock ceiling, independent of and in addition to the per-call 30s caps**: only *after* M8's lock is won (never before — a losing contender exits 0 per M8 without touching this file at all, so the marker's mtime is never reset by the "ordinary case" of several concurrent session starts racing for the same lock), the lock-winning reconciler creates a start-time marker file, `<config-dir>/plugin-bootstrap/.reconciler-start`, at a fixed literal name (distinct in shape from M9's hash-derived failure-stamp filenames, so the two never collide), overwriting any stale prior marker (mirroring this repo's own elapsed-time-testing idiom at `test_advance_past_commit_stall.py:972-973` and `test_lib_append_json_line_locked.py:84`, both of which compute elapsed time from a stat-able file's mtime rather than an in-process variable, precisely so a test can substitute a large elapsed value by backdating that file with `os.utime` instead of waiting 600 real seconds); before attempting each remaining id's install, it computes elapsed wall-clock time as "now minus that marker file's mtime," and skips (fail-closed, logging a new M9 decision type, "wall-clock ceiling reached, id skipped") any id whose attempt would begin after 600s (10 minutes) has elapsed by that computation. Grounded the same way as the per-call cap above (repo precedent, not a vendor SLA, since none documents this call's duration): 600s is 20× the per-call cap, giving headroom for roughly 19 ids plus the one marketplace-listing call (20 capped calls total) before the ceiling can bind — comfortably above any `enabledPlugins` list size this plan's own fixtures exercise — while still bounding worst-case exposure independent of however large a repo-controlled `N` grows. An id skipped this way remains missing from the registry and is picked up on a later reconciler run. That later run's own exposure is bounded the same way, and shrinks over successive runs: **M2 already treats the registry as the source of truth and launches only for ids still missing from it, so a large first-run `N` for a given repo is a one-time cost, not a recurring one** — as installs land, the missing-id set for that repo shrinks toward zero across sessions. The effect of any exposure that does occur is availability-only and self-limiting rather than session-blocking, since M8's lock already confines this to one reconciler per config dir, a losing concurrent invocation exits 0 immediately rather than queuing, and the hook itself returns immediately regardless of how long the reconciler runs — other sessions on the same account simply don't get the feature's benefit for the duration of one run, a graceful degradation to the pre-existing slow behavior. *anchors: row4*
  **Over-powered-primitive check (heavier execution context — a background process spawned from a session-start hook):** (a) *bounded synchronous run in the hook* — fails, because the install itself is the slow part and it would freeze the first session in every new repo; (b) *stamp-file-cached synchronous run, as `plugins/skill-management/hooks/provision-validator-venv.sh:30-34` does* — fails for the same reason: the cache makes the *decision* cheap, not the work; (c) *synchronous run from a SessionEnd hook, where blocking is free* — ruled out by Phase-0 probe H3a (row 4: killed mid-write past the pinned timeout). Combined with probe H2's confirmation that the detached-child mechanism below survives every tested teardown mode (row 13), M5 as designed is the mechanism Phase 0 supports; the SessionEnd fallback is no longer a live alternative absent a separate change to the pinned timeout.
- **M6 — Scope ladder, confirmed by Phase 0, gated on a runtime ignore check.** Use `-s local` (correct cwd, correct `projectPath`, side effects confined to `.claude/settings.local.json`) — probe P1 confirmed it produces a resolvable entry with a clean tracked tree (row 11), so the `-s project` fallback is not needed. `-s user` is disqualified (row 12; probe F3 confirmed it dirties a stand-in for the stowed public settings file, same as the positive control). Caveat carried from row 11: P1's fixture didn't reproduce the actual cold-cache/git-source bug (see Root), so this scope choice is validated on write-cleanliness and name-keyed resolution, the later Value check (Verification) confirms the `-s local` install fixes the reported latency on a git-source marketplace. Row 11 also found `.claude/settings.local.json` was gitignored in the tested fixture only via the *account's* global `~/.config/git/ignore`, not the repo's own `.gitignore` — the reconciler cannot assume every target repo's own `.gitignore` covers it, so before installing it runs `git -C <repo> check-ignore -q .claude/settings.local.json` and skips (fail closed, no install) on any non-zero exit. **`check-ignore` alone is not sufficient** (round-3 CISO finding): it answers "would this be ignored going forward," not "is this safe to write into today" — git does not stop tracking a file merely because a later `.gitignore` rule matches it, so a repo that has already committed `.claude/settings.local.json` *and* carries a matching ignore rule would pass `check-ignore` while still being tracked. The reconciler additionally confirms the path is not already tracked (`git -C <repo> ls-files --error-unmatch .claude/settings.local.json` must exit non-zero) and skips (fail closed) if it is. *anchors: row11*
  **Over-powered-primitive check (the prior design's synthesized scratch dir at `<config-dir>/plugin-bootstrap/<hash>/.claude/settings.json`):** rejected as the heaviest option of the four. It requires copying the repo's `extraKnownMarketplaces` into the scratch settings, which re-imports the repo-controlled marketplace source that D1 exists to exclude; it records a `projectPath` pointing at a directory that is not a repo, which is only harmless if row 10's name-keyed reading holds — and row 10 is a single observation never tested for scratch dirs; and it creates a new hash-named directory tree for a problem `-s local` solves with no new state at all. Lighter alternatives that do solve it: `-s local` (chosen) and `-s user` (P3). Restore-the-file-after-install was also considered and rejected as a racy compounding layer.
- **M7 — No `-y`.** The reconciler never passes `-y/--yes`. A plugin that declares an install-time command simply fails to install in the background and is left to the normal interactive path; auto-accepting a marketplace-declared command from a background process driven by repo-controlled input is the exact shape this design is avoiding. If a legitimately needed plugin declares a command, pin it with `--accept-command <sha256>` from the engineer's own gitignored config rather than enabling `-y` broadly. *anchors: row14*
- **M8 — One lock per config dir, keyed on PID plus process start time (round-4 fix, replacing round-3's self-recognition-only nonce).** The contended resource is the per-account registry, not the repo, so the lock is keyed on `<config-dir>`, not on the worktree. Use the `set -o noclobber` PID-file shape with once-only O_EXCL dead-PID eviction, modeled on `_lib_worktree_acquire_lock`/`_lib_worktree_reclaim_dead_lock` (`_lib.sh:2454-2503`) — the loser exits 0 silently and retries next session. Without it, several sessions starting at once — the ordinary case on this machine — each spawn an install writing the same registry, and a corrupted registry breaks every session on that account. Implement the lock inside the new script rather than generalizing `_lib_worktree_acquire_lock` itself, whose signature is worktree-bound and whose callers include the worktree-collision gate. **PID-wraparound fix, correcting round 3's mistargeted mechanism:** the gap (bare-PID comparison lets a PID recycled after wraparound to an unrelated live process read as "still held," wedging the lock indefinitely) is a *foreign-lock liveness* question — a contending process asking "is the original holder still alive" — not a *self-recognition* question. Round-3's nonce fix answered the wrong question: it modeled `docs/design-decisions/worktree-lock-session-id.md`'s `session_id` pattern, but that pattern exists to let the *same logical caller* recognize its own prior lock across a PID change (`--continue`/`--resume`); that document's own text states `kill -0` liveness is unchanged and still governs the foreign-lock case, which is exactly the case this gap needs closed. A random or self-generated token has no OS-observable correlate a contending process can re-derive from the live process now holding a recycled PID, so it cannot distinguish recycling from continuity — round-4 review (CISO, staff-platform-engineer, staff-sdet, independently) converged on this same conclusion. The fix instead feeds a **process-start-time comparison into the liveness check itself**, in place of the bare `kill -0` result: at lock-acquire time, stamp the lock file with the holder's PID plus `LC_ALL=C TZ=UTC ps -o lstart= -p "$pid"`'s output for that PID (confirmed portable on both BSD/macOS and GNU `ps`, unlike `flock`/`declare -A`) — the `LC_ALL=C TZ=UTC` pin is required, not cosmetic: `lstart`'s format and value are locale- and timezone-dependent (confirmed dynamically on this machine: `LC_TIME=fr_FR.UTF-8` changes the string, `TZ=Asia/Tokyo` changes the wall-clock value), so two reconcilers launched under different ambient `LC_TIME`/`TZ` would otherwise stamp and re-query different strings for the same still-live holder, causing a false wraparound-eviction of a lock that is genuinely still held; at contention time, when `kill -0 "$locked_pid"` succeeds, additionally re-query `LC_ALL=C TZ=UTC ps -o lstart= -p "$locked_pid"` (same pin, both call sites) and compare it to the stamped value — a match means the same process is still genuinely alive and holding the lock (back off), a mismatch means the PID was recycled to an unrelated live process (the original holder is dead; evict and proceed). The write mechanics are unchanged from round 3's shape and introduce no new race: a single `printf` under `noclobber`, mirroring `_lib_worktree_acquire_lock`'s existing PID+`session_id` write with one more field. **Residual, disclosed as a concern:** a lock believed held (ordinary contention, or the rare case a wraparound is caught mid-transition) produces no audit-log line under M9 as originally scoped — M9 now adds "lock held, skipped" as a logged decision type for exactly this reason, so a wedge is at least observable after the fact rather than presenting only as "the plugin never got installed." *anchors: row20*
- **M9 — Failure stamp keyed on input, not on a clock, plus a per-decision audit log written through this repo's existing locked-append primitive.** On a failed install, record `<plugin-id>` plus `_lib_hash_diff_text` of the repo settings file's contents (`_lib.sh:802`) under `<config-dir>/plugin-bootstrap/`, and skip that id while the recorded hash still matches. Drop the prior design's ~24h TTL: a TTL is a guess about when the world changed, whereas the hash is a fact about when the input changed. Accepted tradeoff: a transient network failure suppresses retry until the repo's settings change or the stamp is deleted by hand, so `docs/hooks.md` must name the stamp path and the manual clear. Derive the stamp filename from the hash, never from repo-controlled text. Separately from the failure stamp, a size-capped, append-only audit log under `<config-dir>/plugin-bootstrap/` gets one line per decision (UTC timestamp, writer PID (`$$`), repo root with control characters stripped before formatting, plugin id or `-` when not id-specific, decision, outcome), gitignored, never written to stdout, named in `docs/hooks.md`. Both processes write to it: the **hook** appends on its own fast-guard refusals (M1a's two layers, M2's registry-trust rules, and an unreadable local opt-out file, M10) before any reconciler launches, and the **reconciler** appends on every decision it reaches (successful install, M4 marketplace/source-type/credential-denylist skip, M6 write-target-guard skip, M8 lock-held skip, M9 stamp-suppressed skip, M5's wall-clock-ceiling skip, the reconciler's own M2-equivalent registry-unparseable/version-mismatch skip, and its own M10 `m10_local_optout_unreadable` skip, which the hook also writes on its own path, so either process may log it). Before this addition, none of these left any trace; without one there was no way to tell after the fact whether a plugin was installed by this automation, by a human, from which repo, or why a given id was silently skipped. The log is written by potentially many concurrent processes — M8's own text calls simultaneous session starts "the ordinary case on this machine," and every one of those sessions' hooks and reconcilers can append at once — so both writers use `_lib_append_line_locked` (`_lib.sh:3641`, tested by `test_lib_append_line_locked.py`), this repo's existing noclobber-lock-plus-bounded-retry primitive for exactly this shape of problem, rather than a bare `>>` append: a plain shell append is not guaranteed interleave-safe across processes for lines carrying variable-length fields (a repo root path, a plugin id), and this primitive is already built, tested, and used by other multi-writer log files in this repo. **The writer-PID field exists specifically because of that primitive's own dedup behavior:** `_lib_append_line_locked` no-ops a line that already exists verbatim in the file rather than appending a true duplicate, so without a per-writer disambiguator, two sessions hitting the identical decision (same repo, same decision, same outcome) within the same UTC second — M8's own text calls concurrent session starts "the ordinary case on this machine," and the hook's own fast-guard-refusal append is not covered by M8's reconciler-only lock — would collapse to a single logged line, silently undercounting how many times the decision actually fired. Including the writer's own PID in every line makes any two writers with overlapping process lifetimes byte-distinct, so the dedup only ever collapses a true repeat by the same still-running process, never two independent, temporally-overlapping events. Every stamped repo-root or plugin-id field is truncated to 4096 bytes before formatting — POSIX `PATH_MAX` on Linux, comfortably above any real filesystem path and a plugin id's own bounded shape (M3's regex), so no legitimate value is ever truncated while a crafted one is still bounded before it reaches the log. This is bounding untrusted-input field length on its own merits, independent of `_lib_append_line_locked`'s own behavior: that primitive's dedup comparison (`grep -qFx`, `_lib.sh:3646`) is an unconstrained whole-line match with no length assumption of its own, so the truncation isn't "matching" anything the primitive requires — it exists solely to keep a crafted field from growing the log line without bound. *anchors: root*
- **M10 — A machine-level key plus a per-plugin local `false`.** A `plugin_bootstrap` `bool` key defaulting `true`, `config-dir` scope, with empty `legacy-filename` and `legacy-polarity` fields (the shape of `test_selection_tracking`'s row, `config-keys.psv:107`), gated as `_config_enabled plugin_bootstrap || exit 0`. That gate exits only when the config directory cannot be resolved, `config-keys.psv` is unreadable, or the key's row is missing (as `set-session-title-from-branch.sh:86` does). An unreadable `claude-config.toml` and a malformed or wrong-type `plugin_bootstrap` value (for example a quoted `"false"`) fall back to the schema default `true`, so the hook stays on and `docs/config-file.md` warns on stderr; the engineer accepts that direction, as for every other key. On by default is the engineer's call (row 24); the engineer chose the config-key shape over a bare sentinel file and over no switch ("Config key (Recommended)"), after a CISO review (F3) and an architect consult found the nearest comparable hooks that take action all keep a machine-level switch. Per plugin and per worktree, setting the id to `false` in `<worktree>/.claude/settings.local.json` is honored by `_lib_missing_plugin_ids`; a `false` set in the main checkout does not carry into a linked worktree. Limits of the per-plugin `false`: it matches the exact id, it helps only after the user knows the id, and an id added in a later commit is not covered. A `settings.local.json` that exists but is unreadable or wrong-shaped (as the `_lib_missing_plugin_ids` header in `_lib.sh` defines) suppresses every install for that repo and logs `m10_local_optout_unreadable`. Rollback has two paths. To stop the hook installing a plugin in a repo that still enables it, set it to `false` in that repo's `.claude/settings.local.json`; whether the vendor also lets a local `false` override the project's `true` is unverified. To remove an install the repo no longer declares, run `claude plugin uninstall <id> -s local`, which sticks because no checked-in `true` remains to trigger a reinstall; M9's audit log lists what the hook installed. *anchors: row17*
- **M11 — Two files, not one.** Thin hook at `claude/.claude/hooks/bootstrap-project-plugins.sh`, reconciler at `claude/.claude/scripts/reconcile-project-plugins.sh`, invoked as `"$CONFIG_DIR/scripts/reconcile-project-plugins.sh" "$RESOLVED_REPO_ROOT"` per the repo's hook-to-script convention and M5's pinned invocation contract. A single file with a background-mode flag would make the detached child inherit the hook's stdin semantics for no gain. *anchors: root*

**Over-powered-primitive check for the root mechanism (a hook executing a code-fetching CLI on every session start, on by default for every stow consumer):** (a) *advisory-only hook that prints the exact command for the human to run* — fails: the engineer asked for automatic registration, and an advisory that fires until acted on is a per-session nag with the same recurrence the plan exists to remove; (b) *`install.sh` alone* — fails: `install.sh` runs once per machine, while the problem is per-repo and recurs as repos are cloned; (c) *a list-driven sweep like `update-claude-config-plugins.sh`, which iterates existing registry entries' `projectPath`s* — fails on the chicken-and-egg: a repo with no registry entry is exactly the case this plan is about, so it is invisible to a registry-driven sweep, and a hand-maintained repo list is the manual step being eliminated. The hook's distinguishing property is that it discovers the repo from the session itself.

# Review-loop cost-investigation runbook

## Context

Package the cost-investigation methodology used to diagnose a one-off
PR's review-loop-cost anomaly into a reusable, non-auto-triggering
runbook skill for claude-config, grounded in a corpus-wide sweep of
this repo's own PRs over $100 rather than in the single anecdote alone.

Why now: an agent's retrospective investigated an external PR,
`osv-scanner-stale-ignore-renewal`. That PR is confirmed via
`buckets --this-repo` to NOT be part of claude-config's own transcript
corpus. The retrospective found that a large majority of the PR's cost
fell outside formal code-review/plan-review/ready-for-review windows.
The cause was an 18-round loop re-grinding a plan document after the
code itself was already correct. The engineer wants to know whether
this points to a systemic problem in claude-config before treating it
as one.

This session's own sweep of claude-config's 20 branches over $100
surfaced a real methodology gap worth codifying. `review-round-cost`'s
"inside vs. outside formal review window" metric cannot, on its own,
distinguish a stuck loop from ordinary large-diff work happening
between review gates. The PR #997 investigation resolved that
ambiguity with a `git log` check: code froze at the first commit, and
every later commit touched only the plan file. This sweep had no
equivalent check.

Intended outcome: a `claude-skills/skills/` runbook skill, registered
`skillOverrides: name-only`, with two entry points —
single-branch deep audit and corpus-wide sweep-for-outliers — that
layers a git-log code-churn correlation on top of `transcript-analysis`'s
existing `cost`/`review-round-cost`/`subagent-mix` subcommands so the
"outside review window" signal becomes actually diagnostic instead of
ambiguous.

## Approach

Ship one new skill, `claude-skills/skills/review-loop-cost-audit/SKILL.md`, whose single load-bearing contribution is a **code-freeze correlation**: for a candidate branch, derive the date of its last code-bearing commit from `git log`, then partition `review-round-cost`'s already-dated round table at that date. The share of dollars falling outside review-round windows does not discriminate — in the grounding sweep every branch examined, including the ones that read as legitimate sustained infra work, sat in the same band as the suspected-thrash branch — so the skill is built to never use that share as a threshold, and to reach a verdict only from the freeze-date partition plus reviewer-dispatch skew. Two entry points: a **sweep** that ranks candidates and issues no verdict, and a **deep audit** that resolves one branch and does. The skill's invocation mode is `skillOverrides: name-only` (see G7 below).

**Why a separate skill rather than a mode of `transcript-narrative`.** Both are name-only, so invocation mode no longer separates them; the separation is structural. `transcript-narrative` carries `context: fork` and `background: false` (`transcript-narrative/SKILL.md:4-5`). Forking is a file-level frontmatter property, not a per-mode one, so folding a mode into it would:
1. Run forked.
2. Lose `AskUserQuestion` — needed for the sweep → deep-audit handoff.
3. Enter `_FORKED_SKILLS` under a criterion it does not meet (mechanism 4).

The working sets differ: raw JSONL prompt text versus aggregate CLI tables. The outputs differ: a narrative timeline versus a four-way verdict. `transcript-narrative` is 103 lines against `check-skill-length.sh`'s 200-line cap, leaving under 100 lines for a second complete workflow carrying two entry points, a three-tier churn resolution, and a rubric. Disambiguation follows the family's own convention — the redirect clause lives in each skill's own `description` (`transcript-narrative/SKILL.md:3` carries one pointing at `transcript-analysis`) — so the new skill's description names both siblings and no sibling file is touched.

### Assumption ledger

**Root problem.** A branch's review-loop spend cannot be diagnosed as a stuck loop versus ordinary large-diff work between gates, because the one available metric — share of dollars outside formal review-round windows — takes near-identical values in both cases, and nothing in the toolkit supplies the code-churn signal that separates them.

**Mechanisms**, each with its justification and anchor:

1. **A new `claude-skills/skills/` skill whose invocation mode comes from one `skillOverrides: name-only` entry in `claude/.claude/settings.json`, with no `disable-model-invocation` flag in its frontmatter.** `anchors: root` — settings is the single source of truth for the mode, and the flag would additionally fail `test_name_only_skill_does_not_carry_disable_flag` (`test_skills.py:376`). The description stays out of the listing budget (G7) while the skill stays reachable by exact name, so the audit **can** be dispatched into a `general-purpose` subagent (which carries the `Skill` tool per `CLAUDE.md` § Safety) or composed by another skill such as `error-mode-analysis`, keeping its cost and branch tables out of the engineer's main session. That route is now available, not required, and this plan wires no caller. Name-dispatch adds no model-reachable capability the corpus did not already have: the three transcript-family siblings that read the same multi-root corpus — `transcript-analysis`, `transcript-narrative`, `error-mode-analysis` — are already name-only (`settings.json:87-89`); the control that matters is the author-time never-publish / never-marker statement in the body (row 9). Alternatives weighed:
   - `disable-model-invocation: true` (the `issue-triage` mechanism) — forecloses name-dispatch entirely (G7's inverse); set aside by the engineer for that reason (row 11).
   - `skillOverrides: user-invocable-only` — the settings-side equivalent of that flag; same loss of delegability, with the mode split across two surfaces for no gain.
2. **One `git log --name-only` call per audited branch, classified in-context; no new script and no new `transcript-analysis.py` subcommand.** `anchors: row1` — a single-statement, `$(...)`-free Bash call satisfies the worktree Bash-guard discipline (`docs/worktree-bash-guard.md` Triggers A/B/E) with no new artifact. Heavier primitives rejected:
   - A `code-churn` subcommand in `transcript-analysis.py` — a large module plus tests plus a docs section, to compute what one `git log` already prints.
   - A dedicated `~/.claude/scripts/` script — justified only for a genuinely multi-step recipe; this is one command.
3. **Artifact written to a caller-supplied path, defaulting to `mktemp -d`.** `anchors: G5` — matches both forked siblings' precedent, creates at mode `0700`, needs no `$CLAUDE_CONFIG_DIR` reference (Trigger B), and keeps a DO-NOT-PUBLISH-class artifact off any durable shared path by default. Heavier options rejected:
   - A config-dir-rooted run directory — needs a new script plus a test plus a `docs/scripts.md` entry to resolve the account correctly, and a stale cost baseline misleads more than a re-run costs.
   - `docs/reports/<date>-<slug>/findings.md` — a public-repo path, barred outright by G5, since the sweep's primary table is a dated per-branch dollar series the toolkit itself stamps `DO NOT PUBLISH` under multi-root scope.
4. **No `context: fork`.** `anchors: row2` — `_FORKED_SKILLS` in `claude-skills/skills/tests/test_skills.py:2422` is a closed roster whose criterion is bulk working-set content pulled into the parent; this skill reads aggregate CLI tables, not raw JSONL or full PR payloads. Forking would also cost `AskUserQuestion` (needed for the sweep → deep-audit handoff) and would add six forked-skill contracts for a saving the artifact-path return already captures.
5. **No subagent dispatches inside the skill.** `anchors: row4` — `subagent-delegation/SKILL.md` § "Heavy command output — run inline" governs: the CLI calls run inline, and heavy output that overflows is grepped from the persisted `tool-results/` file rather than re-run. This is the skill's internal behavior; a caller dispatching the whole skill into one subagent (mechanism 1) is a separate, permitted choice.

### Skill body design

**Frontmatter and registration.** Frontmatter copies `transcript-narrative/SKILL.md:1-7`: `name: review-loop-cost-audit`; a one-sentence `description` with no TRIGGER blocks, carrying the family's redirect clause (for a narrative timeline of session prompts use `transcript-narrative`; for raw toolkit metrics use `transcript-analysis`); `argument-hint: "[branch-name | sweep] [output-path]"`. No `user-invocable` key — the default is user-invocable, which is how every name-only sibling is slash-invocable — and no `disable-model-invocation` key at all (mechanism 1). No `context`, no `background`, no `agent`. The invocation mode is one line in `claude/.claude/settings.json`'s `skillOverrides` block, `"review-loop-cost-audit": "name-only",`, copying `"transcript-narrative": "name-only"` exactly. Because a pre-v2.1.129 client ignores the override and falls back to `on` (G8), the description is written to be a poor auto-trigger match: no TRIGGER blocks, and phrased as what the skill produces rather than as a condition that recurs in ordinary work — the shape the sibling workflow utilities already use.

**Step 0 — scope and safety.** Quote the resolved-scope header verbatim for every subcommand run, per `transcript-analysis/SKILL.md` § "Scope confirmation"; a zero-match run is reported *with* its header, never as a bare absence. Run the single-account cross-check (row 5) before any figure is trusted. State that the skill never invokes `marker.sh` and never invokes a review skill (row 9). Caveats are referenced to `transcript-analysis/SKILL.md` § "Caveats" and `docs/transcript-analysis.md`, not restated (single source of truth, and the 200-line cap).

**Step 1 — mode select.** No argument or `sweep` → sweep mode. An explicit branch name → deep audit. Deep audit never infers its subject from the current branch, because the session running the audit is usually anchored in the audit's own worktree.

**Step 2 — sweep (candidates only, never a verdict).** One `review-round-cost --this-repo` run; read the per-branch reconciliation lines and rank by branch total (assumption 1). Default cut is **top 20 by branch total** — a rank, not a dollar threshold, so it ports to a repo of any corpus size; an optional argument accepts an absolute minimum instead. Cross-check completeness against `buckets --this-repo` (assumption 2). Then per candidate: round mix (a plan-review-heavy mix is the plan-grinding signature), and `subagent-mix --this-repo --branches <B>` for within-branch reviewer skew plus dispatches per round (assumption 7), with the corpus-wide unfiltered run supplying the ranking-aid denominator and an explicit label saying it is not a threshold. Output is a ranked candidate list with the reason each ranked; the sweep states in its own output that it has not distinguished thrash from large-diff work. Hand the top candidates to Step 3 — via `AskUserQuestion` when more than one is plausible.

**Step 3 — deep audit of one branch.** In order: (a) `buckets --this-repo --branches <B>` to confirm the branch exists in corpus scope; (b) `review-round-cost --this-repo --branches <B>` for the dated round table and reconciliation line; (c) the churn resolution, tiered — Tier 1 `git rev-parse --verify --quiet <ref>` succeeds → `git log --reverse --date=short --format='commit %h %ad %s' --name-only origin/main..<ref>` (substituting the repo's own default-branch ref; run from the worktree root; single statement, no `$(...)`); Tier 2 no ref → resolve the PR number with `pr-link --this-repo --branches <B>`, `git fetch origin refs/pull/<N>/head:refs/pr-audit/<N> --no-tags`, re-run the same `git log` against `refs/pr-audit/<N>`, then `git update-ref -d refs/pr-audit/<N>` (a named ref, not `FETCH_HEAD`, because `FETCH_HEAD` is repo-global and a concurrent fetch from another worktree clobbers it); Tier 3 both unavailable → **stop and report the churn signal as unavailable**, with the outside-window share labeled non-diagnostic. Tier 3 is a real outcome the skill prints, not a fallback to a weaker proxy. (d) Classify each commit as code-bearing or artifact-only — default artifact glob is `.claude/plans/*.md` (matching `pr-cost --plan-file-glob`'s own default), extensible by the caller via an explicit glob argument — and take the **code-freeze date** as the last code-bearing commit's date. (e) Partition the Step (b) round table at that date and report rounds and dollars after the freeze. (f) `subagent-mix --this-repo --branches <B> --per-session` for the skew signals.

**Step 4 — verdict rubric.** Four outcomes, decided on the freeze partition and skew, never on the outside-window share: **Stuck loop** — rounds keep opening after the freeze date and carry most of the branch's post-freeze dollars, with one reviewer type taking an outsized within-branch share and a high dispatches-per-round ratio. **Plan-grinding** — the same, with post-freeze rounds predominantly `plan-review` and post-freeze commits touching only artifact paths. **Legitimate large-diff work** — code-bearing commits spread across the branch's whole date range, i.e. no early freeze, whatever the outside-window share. **Inconclusive** — Tier 3, or a single squashed commit (assumption 8). The rubric states the non-discrimination rule in words, with no figures (G5).

**Step 5 — artifact and return.** Write one file to the caller-supplied path, or under `mktemp -d` when none is given, stating plainly that the default is temporary; before writing to a caller-supplied path, confirm it does not resolve inside a git-tracked tree unless `.gitignore` covers it (`transcript-narrative`'s own guard). The file opens with a not-for-publication line and carries the quoted scope headers, the round table, the churn table, the verdict, and which caveats applied. Return the path, the verdict, and the two or three discriminating facts — not the tables. That compact return is also what makes the optional delegated route work: a subagent invoking this skill by name returns the same three things, so every table stays in the subagent's context and the artifact file (mechanism 1).

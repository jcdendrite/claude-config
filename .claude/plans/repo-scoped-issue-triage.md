# Repo-scoped GitHub-issue-triage mechanism for claude-config

## Context

Give this repo (`jcdendrite/claude-config`) a repeatable way to triage its own
open GitHub issues, without shipping repo-specific triage instructions to
every other project that stows `claude/.claude/skills/` from this repo. A
session hand-triaged this repo's 47 open issues on 2026-09-01 and worked out
a real methodology (batched parallel evidence-gathering, cross-batch
synthesis, a verification pass, and careful handling of the GitHub-write
gate) — that methodology is worth codifying into a repeatable mechanism
instead of being re-derived by hand each time, and losing it to a fresh
session's cold start is the direct cost of not codifying it now.

Intended outcome: a committed, reviewed mechanism — the design below settles
on a project-scoped plugin under `plugins/<name>/`, evaluated against two
other candidates and ruled out for structural reasons (see Approach) — that
a session can invoke on demand to run the full batching → evidence dossier →
cross-batch synthesis → review-pass pipeline against this repo's currently
open issues and deliver a disposition report, without any part of it landing
in the stow-distributed `claude/.claude/skills/` tree.

Scope for this iteration, per engineer decision:
- **Stateless.** Every run re-triages all currently-open issues from
  scratch; no persisted triage-history state file.
- **Report-only.** The mechanism produces the disposition report; executing
  dispositions (closing issues, posting comments) is a separate manual
  follow-up using existing `gh`/`respond-pr` tooling, not part of this
  mechanism's own flow.

## Approach

Ship a new project-scoped plugin, `plugins/issue-triage/`, holding one user-invocable skill (`/issue-triage`) and the plugin manifest — and register it in the marketplace and in this repo's own `enabledPlugins` so claude-config self-installs it the way it already self-installs its other plugins. v1 also shipped a dedicated batch-evidence agent and a dedicated enforcement hook; both were removed post-ship — see M9 and M7 respectively. The skill orchestrates a stateless, report-only pipeline — fetch → theme-cluster → parallel Sonnet evidence dispatches that each write their own dossier fragment → one Opus cross-batch synthesis → one Sonnet claim-verification pass → drift recheck → report — writing every artifact to `<config-dir>/issue-triage/<owner>-<repo>/<run-timestamp>/`, outside the repository entirely.

Three judgment calls inside that shape are worth naming up front. **The verification step is a claim re-derivation dispatch, not `/plan-review` and not a fixed `ciso-reviewer`.** Evidence gathering and claim verification are read-only correctness checks, not inherently a security-domain problem; a fixed `ciso-reviewer` dispatch would surface only the claims that happen to be security-relevant in a given run's issue population, missing correctness failures elsewhere. A single Sonnet dispatch told to independently re-derive every load-bearing claim from current repo state and to check structural siblings for each confirmed defect targets that directly at a fraction of `/plan-review`'s weight, and it does not presuppose a domain angle that the next run's population may not have. **Batch agents write their own fragments; the parent never re-serializes findings.** Consolidating batch results in the parent means paying for that text twice — once inbound as each batch reports back, once written back out to a dossier — in a context that is re-read every turn. Pushing the write down to each agent and having them return only a one-line-per-issue summary plus a path keeps the parent's context roughly an order of magnitude smaller, and the Opus synthesis reads the fragments itself in its own fresh context. **All three of the pipeline's dispatches are `general-purpose`.** v1 gave the batch-evidence dispatch a dedicated agent instead, reasoning that its category-level `tools:` cap (no `Edit`, `Agent`, or network tools) and a canonical home for the untrusted-data standing rules were things a `general-purpose` dispatch couldn't carry. Post-ship, an engineer-requested `plan-architect` consult found the `tools:` cap didn't survive contact with the dispatch's own `Bash` grant — every excluded category (`Edit`, `Agent`, network tools) is independently reachable through `Bash` (`sed -i`/redirection, `claude -p` re-dispatch, `curl`) — so it bought accident-reduction, not the security property it was justified by, and didn't earn a permanent one-consumer agent-roster entry once M7 had already removed the hook it shipped alongside. The dedicated agent was collapsed into `general-purpose`; the standing rules and per-issue schema moved to `SKILL.md` as their canonical copy, now repeated verbatim in all three dispatch prompts rather than only the batch-evidence one — see M9.

Alternatives set aside:
- `plan-architect` for the synthesis dispatch — its two return grammars (plan sections, proportionate design-decision review prose) are neither a triage report, and `MODE=consult` is scoped to user-initiated architectural consults.
- A dedicated `plugins/issue-triage/agents/*.md` agent for any of the pipeline's three dispatches — a second consumer of that charter doesn't exist for any of them; each would add a permanent agent-roster row for one dispatch site. (v1 shipped one for the batch-evidence dispatch on a different, security-driven rationale; see M9 for why that rationale didn't hold and the agent was collapsed into `general-purpose` post-ship.)
- A supporting shell script for run-directory setup — the setup is three independent single-statement Bash calls; `docs/worktree-bash-guard.md`'s own Trigger B refuses any `$CLAUDE_CONFIG_DIR` reference in an otherwise-trivial single statement, so step 1's `mkdir -p` call does not in fact dodge that shape — this mirrors `handoff/SKILL.md`'s identical existing pattern and accepts the same already-live, currently-non-reproducing risk rather than working around it with a script.
- Any commit-time hook — report-only means there is nothing to gate.
- A fully credential-scoped read-only `gh` token, provisioned separately for this plugin's dispatches — the only control that would survive a determined, obfuscation-capable prompt injection (it fails at the token layer regardless of what shell command the model is tricked into running), rejected as a *required* v1 control because it adds a new required credential to plugin setup for an internal, engineer-only tool over this repo's own already-public backlog; named in Out of scope as documented, optional, future work.

### Assumption ledger

**Root problem:** claude-config has no repeatable mechanism for triaging its own open GitHub issues — the working methodology exists only in one session's transcript — and any mechanism placed in `claude/.claude/skills/` ships to every stow consumer.

**Givens:**
- **G1.** Everything under `claude/.claude/**` installs into every stow consumer's config dir on `git pull`, with no re-install. The stow package's distribution contract is owned by `install.sh` and the repo layout, not by this plan.
- **G2.** GitHub is the tracker and `gh` is the session's only interface to it — vendor-imposed.
- **G3.** Claude Code resolves `plugins/<name>/` only where `claude plugin install <name>@<marketplace> --scope project` has run; `enabledPlugins` plus `install.sh`'s install loop is this repo's only lever on that. Harness-imposed.
- **G4.** The comment-write boundary (`gh issue comment`, `gh pr comment`, REST/GraphQL comment mutations) belongs to `require-respond-pr.sh`, which documents itself as cooperative-not-adversarial; read subcommands sit outside it. Another skill's hook owns that line, and this plan does not touch it. No existing hook in this repo covers `gh issue close`, `gh issue edit`, or label mutations at all — `require-respond-pr.sh`'s own documented scope is comment writes only. v1's M7 hook was the only one that did; see M7 for why it was built, then removed.

**Mechanisms:**
- **M1 — a project-scoped plugin, not a lighter skill home.** `anchors: root`. A plugin is heavier than the alternatives (manifest, marketplace entry, version discipline, an install step), so the lighter primitives get enumerated: (i) *repo-root `.claude/skills/issue-triage/SKILL.md`* — one file, auto-discovered, never stowed, and genuinely the lightest thing that works, but it sits in a verified double enforcement gap: `require-skill-review.sh`'s staged-diff glob and `check-skill-length.sh`'s grep both cover `claude/.claude/skills/` and `plugins/*/skills/` and neither covers `.claude/skills/`, so the skill would be the repo's only SKILL.md exempt from both the review gate and the length cap; (ii) *a markdown playbook under `docs/`* — no registration, no invocation surface, discoverable only by someone who already knows it exists; (iii) *a `.claude/rules/` file* — file-open-triggered, structurally wrong for an on-demand workflow with no associated file type; (iv) *`skillOverrides: name-only`* — a listing-budget control over skills that already ship to every consumer, so it does not scope anything. The plugin route additionally makes the methodology installable in other repos — which none of the four alternatives do — subject to the install-fit conditions M10 states (the credential's reach, untrusted issue/comment input, and unredacted artifact retention, not a "public backlog" proxy); private-repo installs specifically are out of scope for v1 (see Out of scope).
- **M2 — skill only; no agents, no scripts, no hooks.** `anchors: root, row17`. Report-only means no repo write to gate. v1 gave the batch-evidence dispatch a dedicated agent, and separately a `PreToolUse` hook for command-level enforcement; both were removed post-ship (see M9 and M7 respectively) once the agent's `tools:` restriction was found not to survive its own `Bash` grant, and the hook was found disproportionate to a threat the standing rules already state in prose. All three dispatches (batch evidence, synthesis, claim verification) are `general-purpose`, matching M4.
- **M3 — run artifacts at `<config-dir>/issue-triage/<owner>-<repo>/<run-timestamp>/`.** `anchors: row4, row9`. Writes under the resolved config dir are explicitly exempt from worktree enforcement, so the skill runs identically from the main checkout or a linked worktree and needs neither a branch nor a worktree; keeping artifacts outside the tree also removes any path by which a raw dossier reaches a public repo.
- **M4 — fan-out: N Sonnet batch-evidence dispatches (fragment writers, `general-purpose`) → 1 Opus synthesis (`general-purpose`) → 1 Sonnet claim verification (`general-purpose`), none with `isolation`.** `anchors: root, row13, row17`. Evidence gathering and re-derivation are code reading (Sonnet); cross-batch pattern-finding and deriving a prioritization axis are judgment (Opus). All three stages are `general-purpose` — see M9 for why the batch stage's earlier dedicated agent (with its category-level `tools:` cap excluding `Edit`, `Agent`, and network tools) was collapsed. Each dispatch carries the `SKILL.md` Standing rules block verbatim in its own prompt as the only control on the write prohibition and repo-target confinement, with no separate enforcement layer (see M7 and Out of scope). `isolation: worktree` is omitted deliberately: nothing writes to the repo, so there is nothing to isolate, and the isolation Bash guard refuses `$CLAUDE_CONFIG_DIR` references, which every dispatch in this pipeline needs.
- **M5 — drift recheck bounded to exactly one pass.** `anchors: root`. A recheck pass catches issues filed mid-run without an unbounded loop; bound it to one pass, and list anything still drifting after it by number as explicitly untriaged.
- **M6 — `.gitignore` and state-path-regex entries for the new state directory.** `anchors: row9, row10`. Under stow directory-fold, `~/.claude/issue-triage/` materializes physically at `claude/.claude/issue-triage/` inside this repo, exactly as `handoffs/` and `briefs/` do; without both entries a run's artifacts show up in `git status` of a public repo and the new state-path convention has no enforcement.
- **M7 — no command-level enforcement ships for v1.** `anchors: row17, row18`. The standing rules — now canonical in `SKILL.md` (see M9) — are the only control on the write prohibition and repo-target confinement, backstopped by one disclosure sentence at delivery (SKILL.md step 9). A v1 `PreToolUse` hook attempting command-level enforcement was built, then removed as disproportionate to a threat the standing rules already state in prose; see the commit history for the sizing and review detail.
- **M8 — SKILL.md switched to `disable-model-invocation: true`, post-ship.** `anchors: row14`. `disable-model-invocation: true` removes a plugin skill's description from both the real listing budget and `test_skills.py`'s own corpus, since it is frontmatter the harness reads directly off the file rather than a settings.json `skillOverrides` entry, which is documented to not apply to plugin skills at all (`[verified: https://code.claude.com/docs/en/skills, fetched this session — "Hide individual skills by adding disable-model-invocation: true to their frontmatter. This removes the skill from Claude's context entirely."]`). The cost: it also blocks the model from invoking the skill at all, including a deliberate, non-auto-triggered dispatch by name. `issue-triage` can take this cost because nothing else in this repo ever dispatches it by name; `skill-review` can't, because `/code-review` and `require-skill-review.sh` both dispatch it that way — which is why `skill-review` instead keeps a minimized, always-counted description (docs/skills.md's note on `/skill-review`), the same already-known, still-unremediated budget gap that mirroring its `_NAME_DISPATCHED_NO_TRIGGER` exemption for `issue-triage` would have added a second instance of rather than fixed. The TRIGGER/DO NOT TRIGGER block was removed along with the switch — zero remaining routing value once auto-trigger is disabled.
- **M9 — batch-evidence dispatch collapsed from a dedicated agent to `general-purpose`, post-ship.** `anchors: row17, row18`. The engineer raised two design concerns after `/ready-for-review` reported the PR mechanically clean — one of them was why the dedicated `issue-triage-evidence` agent (M2, M4) still existed once M7 had already removed the hook it originally shipped alongside. An engineer-requested `plan-architect` consult (`MODE=consult`) checked the agent's `tools: Read, Grep, Glob, Bash, Write` grant capability by capability and found every excluded category independently reachable through the granted `Bash`: `Write` plus `Bash` redirection/`sed -i` reach what `Edit` would have; `Bash` can run `curl`/`wget`/`gh api` against arbitrary endpoints despite the network-tool exclusion; `Bash` can invoke `claude -p` with the operator's full permissions despite the `Agent` exclusion. The restriction bought accident-reduction, not the security property it was justified by, and the plan's own alternatives-considered reasoning (see Approach, "Alternatives set aside") already rejects a dedicated agent for one consumer everywhere else it applies — nothing distinguished this case once the security rationale fell away. `plugins/issue-triage/agents/issue-triage-evidence.md` was deleted; its standing rules and per-issue record schema moved to `SKILL.md` as their canonical, single-source copy, and are now required verbatim in all three dispatch prompts (§4, §6, §7) rather than only §4's. This also closes, structurally rather than by exception, the residual the plan previously carried in Out of scope about the synthesis/verification dispatches lacking the untrusted-data standing rule — every dispatch now carries the same rules because there is no longer a dispatch-type distinction to carry them unevenly across.
- **M10 — install-guidance predicate corrected, post-ship.** `anchors: row17, row18`. The engineer's second concern was that this plugin's install guidance (`plugin.json`, the matching `marketplace.json` entry, README.md, and `docs/skills.md`'s install-fit cell) read "all three dispatches hold live `gh` credentials and unrestricted `Bash` with no command-level enforcement, **so** install at project scope only in a repo with a public GitHub issue backlog" — a causal claim the same `plan-architect` consult found does not hold: a public backlog is precisely the one any GitHub user can file into, so it widens the injection surface rather than bounding it, and it says nothing about the operator's own credential's reach (a fact Out of scope's "A stronger, adversarial-grade enforcement layer" bullet already stated correctly). Public backlog is the right predicate only for the separate artifact-retention residual (Out of scope, "Retention/expiry policy" bullet), where it does hold. Fixed by replacing the false causal chain in `plugin.json`/`marketplace.json`/README.md, and by changing `docs/skills.md`'s install-fit cell from an invitation ("Repos with a public GitHub issue backlog that needs periodic evidence-backed triage") to a constraint naming the three actual conditions: the credential's reach, untrusted issue/comment input, and unredacted artifact retention. The generalizability claim these surfaces made was never load-bearing for M1's own plugin-vs-lighter-home decision (M1 wins on the enforcement-gap ground alone), so narrowing it does not reopen that decision.
- **M11 — Standing rules gained a fourth rule against spawning further sub-agents, post-ship.** `[ciso-reviewer finding, cumulative `/ready-for-review` pass]` `anchors: row17`. M9's collapse to `general-purpose` correctly found that the deleted agent's `Edit`/network-tool exclusions didn't survive its own `Bash` grant, but a fresh cumulative review found the same collapse silently dropped a *different* property the deleted agent's `tools:` cap also carried: excluding the `Agent` tool, which a `general-purpose` dispatch holds natively and unconditionally (`docs/design-decisions.md:538`). Without that exclusion, an injected instruction could redirect a dispatch to spawn a further sub-agent via the native `Agent` tool — a materially stealthier path than the already-accepted shell-obfuscation residual (Out of scope, "Restricting non-`gh` Bash commands…"), since a spawned sub-agent's own prompt is entirely attacker-controlled and would not automatically carry the Standing rules block at all. A same-round re-review of the fix found the first wording covered only the native `Agent` tool call, leaving open the identical-effect path M9 itself already catalogued — shelling out to `claude -p` (or any other agentic CLI) via `Bash` produces the same attacker-controlled, rules-free sub-dispatch. Closed by widening the fourth standing rule to name both paths ("Never spawn a further dispatch — neither via the `Agent` tool nor by shelling out to `claude -p` or any other agentic CLI via `Bash`") rather than reintroducing a dedicated agent — consistent with M9's finding that a dedicated agent's `tools:` cap is nominal defense-in-depth once `Bash` is granted, this residual is closed by a positive instruction, not a capability restriction, matching every other rule in this block.

## Critical files

**Create:**

- `plugins/issue-triage/.claude-plugin/plugin.json` — `name: "issue-triage"`, `version: "1.0.0"`, `author: {"name": "Cordova Strategy"}`, `"skills": "./skills/"`, and a `description` stating the actual install predicate (post-M9 fix — the credential's reach, untrusted issue/comment input, and unredacted retention, not a proxy "public backlog" framing; see M9 and Out of scope). No `version` in the marketplace entry.
- `plugins/issue-triage/skills/issue-triage/SKILL.md` — `name: issue-triage`, `user-invocable: true`, `disable-model-invocation: true` (post-ship fix, see M8 — human-invoked only via `/issue-triage`, no TRIGGER/DO NOT TRIGGER block since auto-trigger is disabled and the block would carry zero routing value), block-folded `description:`. Body under the hook-enforced 200-line cap; the three dispatch contracts are the compressible surface, so express each as a "the prompt must carry:" bullet list rather than a verbatim template. A "Standing rules for every dispatch" section (post-M9 — moved here from the now-deleted dedicated agent file) and the per-issue record schema are this file's canonical, single-source copy of both, quoted verbatim into every dispatch prompt below. Procedure:
  1. **Resolve the run target and directory.** Precede these with `gh auth status`, so an unauthenticated session fails here with a clear message rather than mid-pipeline. Then three independent single-statement Bash calls — `gh repo view --json nameWithOwner -q .nameWithOwner`, a UTC timestamp, then one `mkdir -p "${CLAUDE_CONFIG_DIR:-$HOME/.claude}/issue-triage/<owner>-<repo>/<timestamp>"`. Body prose uses `<config-dir>/…`; runnable commands use the `${CLAUDE_CONFIG_DIR:-$HOME/.claude}` form. No `VAR=$(…)`-then-reuse inside any fenced block — that shape is corpus-tested against.
  2. **Fetch the open set once, to disk.** `gh issue list --state open --limit <N> --json number,title,labels,createdAt,updatedAt,author > <run-dir>/open-issues.json`, starting at `--limit 100`. Bodies and comments are deliberately excluded here — batch agents fetch them per issue — so the parent never ingests comment text. Re-fetch at a higher limit if the returned count equals the limit; if still truncated after 3 re-fetch attempts, stop and report the truncation rather than looping.
  3. **Cluster by subsystem/theme and announce the run plan** in one line (issues, batches, dispatches). Clustering axis is read reuse: issues in one batch should send one agent to the same files. Name the two failure modes rather than a batch-size constant — one oversized batch loses per-issue rigor, one-agent-per-issue loses sibling-relationship detection and multiplies redundant reads. If there are zero open issues, skip clustering and every dispatch stage below and report "no open issues" directly. If the announced dispatch count exceeds roughly 15 batches, say so explicitly in the run-plan announcement so the invoking session can decide whether to proceed before the fan-out happens.
  4. **Dispatch one `general-purpose`, `model: sonnet` agent per batch, in parallel, no `isolation`.** Each prompt carries: the Standing rules block verbatim; its issue numbers; its own absolute fragment path (`<run-dir>/batch-NN-<theme>.md`); the run's resolved `<owner>/<repo>`; and the per-issue record schema (§5). Those standing rules are the only control on what the dispatch does with live `gh` credentials and unrestricted `Bash` — no command-level enforcement exists, and (post-M9) no tool-scoping restriction beyond what `general-purpose` grants by default (see M9). Each agent writes its fragment and returns only one line per issue plus the fragment path.
  5. **Per-issue record schema (defined once, referenced by every later step):** number, title, current-state verdict (live / stale / fixed / superseded / partially fixed), evidence citation, severity grounded in current verified impact, recommended disposition (close / keep / merge into #N / narrow / ask reporter), and `verification: confirmed | partial (<what is unverified>) | unverified`.
  6. **Dispatch one `general-purpose`, `model: opus` synthesis**, given the Standing rules block verbatim and the run-dir path so it reads the fragments itself: find cross-batch clusters no single batch could see, pick one lead finding, and derive this population's own prioritization axis — explicitly not importing a fixed tiering. It returns the report body; the parent writes it verbatim to `<run-dir>/report.md`.
  7. **Dispatch one `general-purpose`, `model: sonnet` claim-verification pass**, given the Standing rules block verbatim, over `report.md` plus the fragments: independently re-derive the lead finding's headline claim and every `fixed`/`superseded`/`stale` verdict from current repo state, and for each confirmed defect check structural siblings for the same shape. It returns per-claim `confirmed | wrong (+correction) | unverifiable (+what is missing)`. The parent applies corrections before delivery and downgrades anything unresolved to `verification: partial` with the gap named.
  8. **Drift recheck, exactly one pass.** Re-list open issues to `<run-dir>/open-issues-final.json` and diff number sets against step 2: numbers that appeared get one extra batch dispatch folded into the report; numbers that closed are marked closed-during-run and dropped from the disposition list. Anything still new after that pass is listed by number as explicitly untriaged. ## Out of scope

- **Executing dispositions** — closing issues, posting comments, relabelling. That stays a manual follow-up through existing `gh` and `/respond-pr` tooling. Two notes for whoever adds it later, neither actioned here:
  - It would reuse `marker.sh`'s existing `respond-pr` enum entry rather than needing a new one.
  - It would inherit `deny-private-project-refs.sh`'s complete absence of a `gh issue` branch — issue bodies are never scanned for redaction.
- **Persisted triage history or incremental re-triage.** Revisit only if run frequency makes full re-triage expensive.
- **An `AskUserQuestion` mode branch** (report-only vs auto-close vs auto-execute) and partial-verification as a first-class *outcome* type. The report's per-issue `verification:` field is in scope; branching on it is not.
- **Any fixed prioritization schema or batch-size constant.** The prioritization axis and batch sizing are derived fresh per run from that run's own issue population, not fixed in the skill.
- **A commit-time hook for this plugin.** Report-only means there is no repo write to gate.
- **A dedicated agent under `plugins/issue-triage/agents/` for any of the pipeline's three dispatches** and its own roster entry — revisit only when a second dispatch site needs the same charter. v1 shipped one for the batch-evidence dispatch on a security rationale (M2, M4); collapsed into `general-purpose` once that rationale was found not to survive the dispatch's own `Bash` grant — see M9.
- **A stronger, adversarial-grade enforcement layer for `gh` mutation and repo-target confinement.** No Bash-level enforcement hook exists for this plugin — the standing rules, plus the SKILL.md step 9 disclosure sentence, are the whole v1 control (see M7 for why the one hook that did this was built, then removed). That proportionality framing bounds the sensitivity of the attacker-controlled *input* (this repo's own already-public issue text). It says nothing about the *credential's* reach. The dispatch runs under the engineer's own ambient `gh` token, and this plan does not verify that token's actual scope — whether it can write to other repos, private repos, or org-wide resources. The off-target-`-R`/`--repo` residual named in the bullet below is a direct consequence of that unverified reach, not a hypothetical. The control that would actually close that gap is a separate, engineer-provisioned, read-only-scoped `gh` token used only for this plugin's dispatches, so a mutating call fails at the token layer regardless of what shell command the model is tricked into running.

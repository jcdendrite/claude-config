# Repo-scoped GitHub-issue-triage mechanism for claude-config

## Context

Give this repo (`jcdendrite/claude-config`) a repeatable way to triage its own
open GitHub issues, without shipping repo-specific triage instructions to
every other project that stows `claude/.claude/skills/` from this repo. A
session hand-triaged this repo's 47 open issues on 2026-09-01 and worked out
a real methodology (batched parallel evidence-gathering, cross-batch
synthesis, a verification pass, and careful handling of the GitHub-write
gate) — that methodology is worth codifying into a repeatable mechanism
instead of being re-derived by hand each time, and losing it to a fresh
session's cold start is the direct cost of not codifying it now.

Intended outcome: a committed, reviewed mechanism — the design below settles
on a project-scoped plugin under `plugins/<name>/`, evaluated against two
other candidates and ruled out for structural reasons (see Approach) — that
a session can invoke on demand to run the full batching → evidence dossier →
cross-batch synthesis → review-pass pipeline against this repo's currently
open issues and deliver a disposition report, without any part of it landing
in the stow-distributed `claude/.claude/skills/` tree.

Scope for this iteration, per engineer decision:
- **Stateless.** Every run re-triages all currently-open issues from
  scratch; no persisted triage-history state file.
- **Report-only.** The mechanism produces the disposition report; executing
  dispositions (closing issues, posting comments) is a separate manual
  follow-up using existing `gh`/`respond-pr` tooling, not part of this
  mechanism's own flow.

## Approach

Ship a new project-scoped plugin, `plugins/issue-triage/`, holding one user-invocable skill (`/issue-triage`), one dedicated batch-evidence agent, and the plugin manifest — and register it in the marketplace and in this repo's own `enabledPlugins` so claude-config self-installs it the way it already self-installs its other plugins. v1 also shipped a dedicated enforcement hook; it was removed post-ship — see M7. The skill orchestrates a stateless, report-only pipeline — fetch → theme-cluster → parallel Sonnet evidence agents that each write their own dossier fragment → one Opus cross-batch synthesis → one Sonnet claim-verification pass → drift recheck → report — writing every artifact to `<config-dir>/issue-triage/<owner>-<repo>/<run-timestamp>/`, outside the repository entirely.

Three judgment calls inside that shape are worth naming up front. **The verification step is a claim re-derivation dispatch, not `/plan-review` and not a fixed `ciso-reviewer`.** Evidence gathering and claim verification are read-only correctness checks, not inherently a security-domain problem; a fixed `ciso-reviewer` dispatch would surface only the claims that happen to be security-relevant in a given run's issue population, missing correctness failures elsewhere. A single Sonnet dispatch told to independently re-derive every load-bearing claim from current repo state and to check structural siblings for each confirmed defect targets that directly at a fraction of `/plan-review`'s weight, and it does not presuppose a domain angle that the next run's population may not have. **Batch agents write their own fragments; the parent never re-serializes findings.** Consolidating batch results in the parent means paying for that text twice — once inbound as each batch reports back, once written back out to a dossier — in a context that is re-read every turn. Pushing the write down to each agent and having them return only a one-line-per-issue summary plus a path keeps the parent's context roughly an order of magnitude smaller, and the Opus synthesis reads the fragments itself in its own fresh context. **The batch evidence dispatch is the only one of the pipeline's three dispatches that gets a dedicated agent, not a `general-purpose` one.** Issue and comment bodies are open to any GitHub user, and no dispatch-parameter or agent-frontmatter mechanism can block a specific `gh` subcommand for any dispatch type (assumption 17) — so what the dedicated agent buys is a category-level `tools:` cap (no `Edit`, `Agent`, or network tools — see M4) and one canonical home for the untrusted-data standing rules, neither of which a `general-purpose` dispatch can carry. The cross-batch synthesis and claim-verification dispatches (steps 6–7) stay `general-purpose` and read those agents' own output, which can quote or paraphrase issue/comment text — see Out of scope for that residual. v1 also shipped a `PreToolUse` hook for command-level enforcement; see M7 for why it was removed post-ship.

Alternatives set aside:
- `plan-architect` for the synthesis dispatch — its two return grammars (plan sections, proportionate design-decision review prose) are neither a triage report, and `MODE=consult` is scoped to user-initiated architectural consults.
- A dedicated `plugins/issue-triage/agents/*.md` synthesis agent — a second consumer of that charter doesn't exist yet; it would add an agent-roster row for one dispatch site. (This exclusion covers the *synthesis* dispatch only — the *batch evidence-gathering* dispatch uses a dedicated agent for the security reasons above, not this reasoning.)
- A supporting shell script for run-directory setup — the setup is three independent single-statement Bash calls; `docs/worktree-bash-guard.md`'s own Trigger B refuses any `$CLAUDE_CONFIG_DIR` reference in an otherwise-trivial single statement, so step 1's `mkdir -p` call does not in fact dodge that shape — this mirrors `handoff/SKILL.md`'s identical existing pattern and accepts the same already-live, currently-non-reproducing risk rather than working around it with a script.
- Any commit-time hook — report-only means there is nothing to gate.
- A fully credential-scoped read-only `gh` token, provisioned separately for this plugin's dispatches — the only control that would survive a determined, obfuscation-capable prompt injection (it fails at the token layer regardless of what shell command the model is tricked into running), rejected as a *required* v1 control because it adds a new required credential to plugin setup for an internal, engineer-only tool over this repo's own already-public backlog; named in Out of scope as documented, optional, future work.

### Assumption ledger

**Root problem:** claude-config has no repeatable mechanism for triaging its own open GitHub issues — the working methodology exists only in one session's transcript — and any mechanism placed in `claude/.claude/skills/` ships to every stow consumer.

**Givens:**
- **G1.** Everything under `claude/.claude/**` installs into every stow consumer's config dir on `git pull`, with no re-install. The stow package's distribution contract is owned by `install.sh` and the repo layout, not by this plan.
- **G2.** GitHub is the tracker and `gh` is the session's only interface to it — vendor-imposed.
- **G3.** Claude Code resolves `plugins/<name>/` only where `claude plugin install <name>@<marketplace> --scope project` has run; `enabledPlugins` plus `install.sh`'s install loop is this repo's only lever on that. Harness-imposed.
- **G4.** The comment-write boundary (`gh issue comment`, `gh pr comment`, REST/GraphQL comment mutations) belongs to `require-respond-pr.sh`, which documents itself as cooperative-not-adversarial; read subcommands sit outside it. Another skill's hook owns that line, and this plan does not touch it. No existing hook in this repo covers `gh issue close`, `gh issue edit`, or label mutations at all — `require-respond-pr.sh`'s own documented scope is comment writes only. v1's M7 hook was the only one that did; see M7 for why it was built, then removed.

**Mechanisms:**
- **M1 — a project-scoped plugin, not a lighter skill home.** `anchors: root`. A plugin is heavier than the alternatives (manifest, marketplace entry, version discipline, an install step), so the lighter primitives get enumerated: (i) *repo-root `.claude/skills/issue-triage/SKILL.md`* — one file, auto-discovered, never stowed, and genuinely the lightest thing that works, but it sits in a verified double enforcement gap: `require-skill-review.sh`'s staged-diff glob and `check-skill-length.sh`'s grep both cover `claude/.claude/skills/` and `plugins/*/skills/` and neither covers `.claude/skills/`, so the skill would be the repo's only SKILL.md exempt from both the review gate and the length cap; (ii) *a markdown playbook under `docs/`* — no registration, no invocation surface, discoverable only by someone who already knows it exists; (iii) *a `.claude/rules/` file* — file-open-triggered, structurally wrong for an on-demand workflow with no associated file type; (iv) *`skillOverrides: name-only`* — a listing-budget control over skills that already ship to every consumer, so it does not scope anything. The plugin route additionally makes the methodology installable in any other repo with a public GitHub issue backlog — private-repo installs are out of scope for v1 (see Out of scope) — which none of the four alternatives do.
- **M2 — skill, plus one dedicated batch-evidence agent; no other agents, no scripts, and (post-rework) no hooks.** `anchors: root, row17`. Report-only means no repo write to gate in general, but the batch evidence dispatch is the one place untrusted issue/comment text reaches a privileged agent — see the Approach section's third judgment call — so that one dispatch gets a dedicated agent definition rather than the "no agents" default. v1 also gave it a `PreToolUse` hook; removed post-ship, see M7. Every other dispatch (synthesis, claim verification) stays `general-purpose`, matching M4.
- **M3 — run artifacts at `<config-dir>/issue-triage/<owner>-<repo>/<run-timestamp>/`.** `anchors: row4, row9`. Writes under the resolved config dir are explicitly exempt from worktree enforcement, so the skill runs identically from the main checkout or a linked worktree and needs neither a branch nor a worktree; keeping artifacts outside the tree also removes any path by which a raw dossier reaches a public repo.
- **M4 — fan-out: N Sonnet batch-evidence agents (fragment writers, `issue-triage:issue-triage-evidence`) → 1 Opus synthesis (`general-purpose`) → 1 Sonnet claim verification (`general-purpose`), none with `isolation`.** `anchors: root, row13, row17`. Evidence gathering and re-derivation are code reading (Sonnet); cross-batch pattern-finding and deriving a prioritization axis are judgment (Opus). The batch stage alone uses the dedicated agent, scoped to `tools: Read, Grep, Glob, Bash, Write` — a category-level restriction excluding `Edit`, `Agent`, and the harness's own network-tool category, not a per-`gh`-subcommand one. It is also not a real network barrier, since full `Bash` still permits `curl`-based egress (see Out of scope). The standing rules given to the dispatch are the only control on the write prohibition and repo-target confinement, with no separate enforcement layer (see M7 and Out of scope). `isolation: worktree` is omitted deliberately: nothing writes to the repo, so there is nothing to isolate, and the isolation Bash guard refuses `$CLAUDE_CONFIG_DIR` references, which every dispatch in this pipeline needs.
- **M5 — drift recheck bounded to exactly one pass.** `anchors: root`. A recheck pass catches issues filed mid-run without an unbounded loop; bound it to one pass, and list anything still drifting after it by number as explicitly untriaged.
- **M6 — `.gitignore` and state-path-regex entries for the new state directory.** `anchors: row9, row10`. Under stow directory-fold, `~/.claude/issue-triage/` materializes physically at `claude/.claude/issue-triage/` inside this repo, exactly as `handoffs/` and `briefs/` do; without both entries a run's artifacts show up in `git status` of a public repo and the new state-path convention has no enforcement.
- **M7 — no command-level enforcement ships for v1.** `anchors: row17, row18`. The standing rules in the batch-evidence agent's own file are the only control on the write prohibition and repo-target confinement, backstopped by one disclosure sentence at delivery (SKILL.md step 9). A v1 `PreToolUse` hook attempting command-level enforcement was built, then removed as disproportionate to a threat the standing rules already state in prose; see the commit history for the sizing and review detail.
- **M8 — SKILL.md switched to `disable-model-invocation: true`, post-ship.** `anchors: row14`. `disable-model-invocation: true` removes a plugin skill's description from both the real listing budget and `test_skills.py`'s own corpus, since it is frontmatter the harness reads directly off the file rather than a settings.json `skillOverrides` entry, which is documented to not apply to plugin skills at all (`[verified: https://code.claude.com/docs/en/skills, fetched this session — "Hide individual skills by adding disable-model-invocation: true to their frontmatter. This removes the skill from Claude's context entirely."]`). The cost: it also blocks the model from invoking the skill at all, including a deliberate, non-auto-triggered dispatch by name. `issue-triage` can take this cost because nothing else in this repo ever dispatches it by name; `skill-review` can't, because `/code-review` and `require-skill-review.sh` both dispatch it that way — which is why `skill-review` instead keeps a minimized, always-counted description (docs/skills.md's note on `/skill-review`), the same already-known, still-unremediated budget gap that mirroring its `_NAME_DISPATCHED_NO_TRIGGER` exemption for `issue-triage` would have added a second instance of rather than fixed. The TRIGGER/DO NOT TRIGGER block was removed along with the switch — zero remaining routing value once auto-trigger is disabled.

## Critical files

**Create:**

- `plugins/issue-triage/.claude-plugin/plugin.json` — `name: "issue-triage"`, `version: "1.0.0"`, `author: {"name": "Cordova Strategy"}`, `"skills": "./skills/"`, and a `description` in the established install-guidance voice ("… so install at project scope only in a repo with a public GitHub issue backlog."). No `version` in the marketplace entry. No explicit `agents` key: the plugin format default-scans `./agents/` when the key is absent, and an explicit key would *replace* rather than extend that scan — leave it unset.
- `plugins/issue-triage/agents/issue-triage-evidence.md` — the batch-evidence dispatch's dedicated agent (invoked as `issue-triage:issue-triage-evidence`), `model: sonnet`, `effort: high` (a downstream claim-verification pass backstops it, matching the `code-writer`/`high`-effort rationale in CLAUDE.md's Model & Effort Routing), `tools: Read, Grep, Glob, Bash, Write` (no `Edit`, no `Agent`, no harness network-tool category — category-level scoping per assumption 17; full `Bash` still permits `curl`-based egress, see Out of scope — this is the only defense-in-depth layer, since no command-level enforcement hook exists). Body states the standing rules and per-issue record schema as their canonical, single-source copy; the dispatching skill (SKILL.md step 4) points to this file rather than restating them.
- `plugins/issue-triage/skills/issue-triage/SKILL.md` — `name: issue-triage`, `user-invocable: true`, `disable-model-invocation: true` (post-ship fix, see M8 — human-invoked only via `/issue-triage`, no TRIGGER/DO NOT TRIGGER block since auto-trigger is disabled and the block would carry zero routing value), block-folded `description:`. Body under the hook-enforced 200-line cap; the three dispatch contracts are the compressible surface, so express each as a "the prompt must carry:" bullet list rather than a verbatim template. Procedure:
  1. **Resolve the run target and directory.** Precede these with `gh auth status`, so an unauthenticated session fails here with a clear message rather than mid-pipeline. Then three independent single-statement Bash calls — `gh repo view --json nameWithOwner -q .nameWithOwner`, a UTC timestamp, then one `mkdir -p "${CLAUDE_CONFIG_DIR:-$HOME/.claude}/issue-triage/<owner>-<repo>/<timestamp>"`. Body prose uses `<config-dir>/…`; runnable commands use the `${CLAUDE_CONFIG_DIR:-$HOME/.claude}` form. No `VAR=$(…)`-then-reuse inside any fenced block — that shape is corpus-tested against.
  2. **Fetch the open set once, to disk.** `gh issue list --state open --limit <N> --json number,title,labels,createdAt,updatedAt,author > <run-dir>/open-issues.json`, starting at `--limit 100`. Bodies and comments are deliberately excluded here — batch agents fetch them per issue — so the parent never ingests comment text. Re-fetch at a higher limit if the returned count equals the limit; if still truncated after 3 re-fetch attempts, stop and report the truncation rather than looping.
  3. **Cluster by subsystem/theme and announce the run plan** in one line (issues, batches, dispatches). Clustering axis is read reuse: issues in one batch should send one agent to the same files. Name the two failure modes rather than a batch-size constant — one oversized batch loses per-issue rigor, one-agent-per-issue loses sibling-relationship detection and multiplies redundant reads. If there are zero open issues, skip clustering and every dispatch stage below and report "no open issues" directly. If the announced dispatch count exceeds roughly 15 batches, say so explicitly in the run-plan announcement so the invoking session can decide whether to proceed before the fan-out happens.
  4. **Dispatch one `issue-triage:issue-triage-evidence`, `model: sonnet` agent per batch, in parallel, no `isolation`.** Each prompt carries: its issue numbers, its own absolute fragment path (`<run-dir>/batch-NN-<theme>.md`), and the run's resolved `<owner>/<repo>`. The agent's own file carries the standing rules and per-issue record schema as their canonical, single-source copy — the skill points to it rather than restating them. Those standing rules are the only control on what the dispatch does with live `gh` credentials and unrestricted `Bash`: no command-level enforcement exists, backstopped only by the agent's own category-level `tools:` grant (no `Edit`, `Agent`, or network tools — see assumption 17). Each agent writes its fragment and returns only one line per issue plus the fragment path.
  5. **Per-issue record schema (defined once, referenced by every later step):** number, title, current-state verdict (live / stale / fixed / superseded / partially fixed), evidence citation, severity grounded in current verified impact, recommended disposition (close / keep / merge into #N / narrow / ask reporter), and `verification: confirmed | partial (<what is unverified>) | unverified`.
  6. **Dispatch one `general-purpose`, `model: opus` synthesis**, given the run-dir path so it reads the fragments itself: find cross-batch clusters no single batch could see, pick one lead finding, and derive this population's own prioritization axis — explicitly not importing a fixed tiering. It returns the report body; the parent writes it verbatim to `<run-dir>/report.md`.
  7. **Dispatch one `general-purpose`, `model: sonnet` claim-verification pass** over `report.md` plus the fragments: independently re-derive the lead finding's headline claim and every `fixed`/`superseded`/`stale` verdict from current repo state, and for each confirmed defect check structural siblings for the same shape. It returns per-claim `confirmed | wrong (+correction) | unverifiable (+what is missing)`. The parent applies corrections before delivery and downgrades anything unresolved to `verification: partial` with the gap named.
  8. **Drift recheck, exactly one pass.** Re-list open issues to `<run-dir>/open-issues-final.json` and diff number sets against step 2: numbers that appeared get one extra batch dispatch folded into the report; numbers that closed are marked closed-during-run and dropped from the disposition list. Anything still new after that pass is listed by number as explicitly untriaged. This one-pass bound is a stated tradeoff, not a verified one — the live-run window rarely contains a real mid-run filing, so the recheck's boundedness is accepted on that basis rather than exercised by Verification.
  9. **Reconcile and deliver.** Before delivering, confirm every issue number from `open-issues.json` (plus any drift-recheck additions) appears somewhere in the report's disposition list or the explicit untriaged list; if a batch agent died mid-dispatch and its issues are absent from both, surface that mismatch explicitly rather than silently under-reporting. Chat gets the lead finding in two or three sentences, counts by disposition, triaged-vs-open counts, any untriaged numbers, and the absolute `report.md` path — not the full table (terminal width-wrapping). One line states that run artifacts live outside the repository, persist indefinitely with no redaction pass (see Out of scope), and that committing any of them is a separate call inheriting the repo's redaction rules; a second line names `/respond-pr` (for comments/closes) as the manual next step for acting on the report.

## Out of scope

- **Executing dispositions** — closing issues, posting comments, relabelling. That stays a manual follow-up through existing `gh` and `/respond-pr` tooling. Two notes for whoever adds it later, neither actioned here:
  - It would reuse `marker.sh`'s existing `respond-pr` enum entry rather than needing a new one.
  - It would inherit `deny-private-project-refs.sh`'s complete absence of a `gh issue` branch — issue bodies are never scanned for redaction.
- **Persisted triage history or incremental re-triage.** Revisit only if run frequency makes full re-triage expensive.
- **An `AskUserQuestion` mode branch** (report-only vs auto-close vs auto-execute) and partial-verification as a first-class *outcome* type. The report's per-issue `verification:` field is in scope; branching on it is not.
- **Any fixed prioritization schema or batch-size constant.** The prioritization axis and batch sizing are derived fresh per run from that run's own issue population, not fixed in the skill.
- **A commit-time hook for this plugin.** Report-only means there is no repo write to gate.
- **A dedicated synthesis agent under `plugins/issue-triage/agents/`** and its own roster entry — revisit only when a second dispatch site needs the same charter. Distinct from the batch-evidence agent this plan does add (M2, M4); that one exists for the security reasons named there, not for a second-consumer argument.
- **A stronger, adversarial-grade enforcement layer for `gh` mutation and repo-target confinement.** No Bash-level enforcement hook exists for this plugin — the standing rules, plus the SKILL.md step 9 disclosure sentence, are the whole v1 control (see M7 for why the one hook that did this was built, then removed). That proportionality framing bounds the sensitivity of the attacker-controlled *input* (this repo's own already-public issue text). It says nothing about the *credential's* reach. The dispatch runs under the engineer's own ambient `gh` token, and this plan does not verify that token's actual scope — whether it can write to other repos, private repos, or org-wide resources. The off-target-`-R`/`--repo` residual named in the bullet below is a direct consequence of that unverified reach, not a hypothetical. The control that would actually close that gap is a separate, engineer-provisioned, read-only-scoped `gh` token used only for this plugin's dispatches, so a mutating call fails at the token layer regardless of what shell command the model is tricked into running. That token is named here as documented, optional, future work, not adopted for v1. Revisit if this plugin is installed against a repo with a materially different threat model — a shared engineer credential with broader scope, or a private backlog.
- **Restricting non-`gh` Bash commands during the batch-evidence dispatch.** No hook restricts any Bash command the dispatch runs, `gh`-shaped or not. The batch-evidence agent's `tools:` frontmatter grants full `Bash` (assumption 17: no finer-grained restriction exists at the dispatch-parameter or agent-frontmatter layer), so a prompt injection embedded in an issue or comment body could direct the agent to run an arbitrary non-`gh` command — for example, exfiltrating local credentials via `curl` to an attacker-controlled host. This is broader than the `gh`-mutation-evasion risk above: it is not GitHub-specific, and the read-only-scoped-`gh`-token mitigation named there would not close it, since that token only constrains `gh`-authenticated calls. Accepted for this iteration for the same proportionality reason named above. Closing it fully would need a sandboxed or network-restricted execution context for the batch-evidence dispatch, named here as further future work, distinct from and in addition to the scoped-token mitigation above.
- **Extending the untrusted-data standing rule (or tool-scoping) to the cross-batch synthesis and claim-verification dispatches.** `[ciso-reviewer finding, post-ship]` Only the batch-evidence dispatch carries the "treat issue/comment text as untrusted data" standing rule and a tool-scoped agent. The step 6/7 `general-purpose` dispatches read those agents' fragments and `report.md`, which can quote or paraphrase issue/comment text. Neither carries a standing rule of its own, and both run under the same ambient `gh` credentials and unrestricted `Bash` — see SKILL.md step 9's disclosure, now widened to name all three dispatches. Closing this needs either:
  - (a) the same standing-rule text added to the step 6/7 prompts, or
  - (b) promoting one or both to dedicated tool-scoped agents — Sonnet needs `Read`/`Grep`/`Glob`/`Bash` but never `gh` or network egress; Opus needs `Read` only.

  A design change beyond this session's scope, deferred to a follow-up.
- **A repeatable adversarial test for the standing-rules-only security control.** `[ciso-reviewer + staff-sdet finding, post-ship]` The plan's only verification of injection-resistance is Verification item 7, a one-time manual dry run in a scratch context whose outcome is never captured in a committed artifact. No `evals/issue-triage-cases.json` fixture or equivalent asserts this behavior on a synthetic malicious issue body, so a future prompt-formatting change or model swap could silently degrade compliance with no regression signal. The plan's own Out-of-scope framing already accepted this trade-off ("if the skill mis-fires in practice"); this residual makes that acceptance explicit rather than leaving it implicit. Add an `evals/` trigger case seeding a synthetic `gh`-write-injection attempt and asserting no write subcommand runs, as a follow-up.
- **Required-field and `tools:`-format test coverage for `plugins/*/agents/*.md`.** `[ciso-reviewer + staff-sdet finding, post-ship]` Already disclosed in assumption 18 as a pre-existing, repo-wide gap (`test_agent_roster.py` covers `claude/.claude/agents/*.md` only). This plugin's batch-evidence agent is the first concrete instance where the gap actually matters: its `tools:` allowlist is the design's sole remaining defense-in-depth layer, and no test would catch a future edit that widened it. Remediation is repo-wide test infrastructure work, not scoped to this plugin — tracked here as a pointer, not a commitment to fix in this PR.
- **Closing the `plugins/*/agents/` test-enforcement gap** (assumption 18) — `test_agent_roster.py`'s required-field checks (`EXPECTED_EFFORT`, `EXPECTED_MODEL`, frontmatter validation) cover `claude/.claude/agents/*.md` only; the cross-scope name-uniqueness check already covers plugin agents, but no other check does. Real and pre-existing (this plan is only the first to make it concrete rather than theoretical); a general test-infra gap, not specific to this plugin's security posture, and not work this plan takes on.
- **An `evals/issue-triage-cases.json` trigger-case file.** The eval harness is discovery-based and opt-in; a follow-up if the skill mis-fires in practice.
- **`permissions.allow` entries for the skill's `gh` commands.** Per-issue `gh issue view N` is not exact-matchable and CLAUDE.md bars globs, so the exact-match rules would cover only the list call while coupling repo settings to a plugin's internals.
- **Committing any run's report into `docs/reports/`.** The engineer's separate call, made per run.
- **Retention/expiry policy and a runtime repo-visibility check for run artifacts.** Each run's `open-issues.json`, fragments, and `report.md` persist indefinitely under `<config-dir>/issue-triage/…` with no scan or redaction pass for secrets or PII an issue body or comment might contain, and no age-based cleanup. Accepted as a stated decision for this repo (public backlog, content already public). This plugin is designed and supported for public-repo backlogs only for v1, per the engineer's explicit decision this session; installing against a private-repo backlog is out of scope until the scoped, rotated read-only `gh` token mitigation named above is built. Not built here because this repo's own install is the only install this iteration targets, and its backlog is already public.
- **An enforced (non-verbal) control on the human-copy-paste leak path.** The only controls against report content later reaching a public repo are the structural outside-the-tree artifact location plus the chat reminder in step 9 — a single non-enforced layer; `deny-private-project-refs.sh` is, per this repo's own CLAUDE.md Redaction section, a tracker-ID/project-name/structural-fingerprint detector with no generic secret-scanning detector, so it would not catch an API key or token pasted verbatim into an issue body and later hand-copied into a commit or PR. Accepted for this iteration; the concrete future work, if this becomes a recurring risk, is either a secret-pattern scan over `report.md`/fragments before they're presented for reuse, or an extension to `deny-private-project-refs.sh`'s own detector set (that hook's owners' call, since it would also backstop every other artifact-copy path in the repo, not only this plugin) — not a plugin-local reimplementation of either.

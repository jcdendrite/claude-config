# GH-783: Quoting bypasses the shared fragment-word matcher family

## Context

**Goal: make every gate hook's command matcher — word-based or regex —
recognize a gated word regardless of shell quoting, so `gh "pr" "create"`
can't walk past a gate that denies unquoted `gh pr create`.**

`_lib_fragment_invokes_git` (`claude/.claude/hooks/_lib.sh:525-538`) and
`deny-private-project-refs.sh`'s local `fragment_gh_gated_surface`
(`claude/.claude/hooks/deny-private-project-refs.sh:215-236`) both walk a
command fragment word by word (`for word in $fragment`) and compare each
word against a bare literal (`git`, `pr`, `create`, ...). Bash word-splitting
does not strip quote characters, so a quoted token (`"git"`, `"pr"`) never
equals its bare comparison string — quoting any gated word anywhere in the
command defeats detection entirely, not partially. Filed as GH-783 after
being found during review of an unrelated PR and confirmed against `main`
(reproduced this session too: `_lib_fragment_invokes_git 'git log'` detects;
`_lib_fragment_invokes_git '"git" log'` does not).

**Why now.** A September 2026 triage of the repo's open-issue backlog rated
this T0 ("reproduced fail-open in a security gate") and named it the top
priority in its "Do these things first" list, ahead of reviving the
unrelated, separately-scoped `GH-499/gate-effective-cwd` branch (a different
gate-authorization defect: gates resolving the wrong git tree via `.cwd`
rather than an embedded `cd`). The triage's own three sibling-matcher
functions confirm this is a matcher-family bug, not a single-function bug:
`_lib_fragment_command_word`/`_lib_fragment_invokes_tool`
(`_lib.sh:677-718`) and `_lib_fragment_has_token` (`_lib.sh:723-726`) share
the identical unquoted-comparison shape.

**Intended outcome.** Every caller of a fragment-word matcher function
recognizes a gated word regardless of shell quoting, using the same
`_lib_strip_shell_quotes`-before-split pattern already proven in
`deny-network-installs.sh` and `enforce-marker-script-shape.sh` — or, if the
architecture review below concludes the fix belongs inside the shared
matcher functions themselves rather than at each call site, an equivalent
guarantee with a single source of truth. GH-499 revival is explicitly out of
scope for this plan (see below) and is deferred to its own later `/plan-it`
pass, per this session's engineer decision.

## Approach

Normalize each affected hook's command text **once, at that hook's own input boundary**, before any word-walk or detection regex sees it: `COMMAND_UNQUOTED=$(_lib_strip_shell_quotes "$COMMAND")`, then split fragments and match against that variable. The shared `_lib_fragment_*` matchers keep their current quote-blind word comparison and gain an explicit caller contract in their doc comments, because the defect is not located in them — the identical blindness lives in four hook-local word-walkers and a dozen inline detection regexes that a shared-function fix would not reach.

This is the pattern already running in production in this repo: `deny-network-installs.sh:77` + `:352` and `enforce-marker-script-shape.sh:452` + `:397` both strip before splitting, and both are consequently not vulnerable. `deny-credential-bash-reads.sh:58` and `deny-pii-in-commits.sh:278` use the same helper for their content scans. The work is extending an established idiom to the hooks that missed it, not designing a mechanism.

**Alternatives weighed and set aside.**

- *Fix inside the shared `_lib_fragment_*` functions (each strips its own `$fragment`).* Rejected on three verified grounds. (1) **Incomplete downward:** it misses `fragment_gh_gated_surface` (`deny-private-project-refs.sh:215-236`), `_fragment_has_token_prefix` (`deny-reviewer-tree-mutation.sh:176-179`), `_relocation_positional_sources` (`deny-repo-relocation.sh:98-133`), `push_fragment_args_after_repo` (`require-ready-for-review.sh:145-168`), and the inline regexes at `require-ready-for-review.sh:238,241` and `deny-private-project-refs.sh:272,275` — each would still need its own fix. (2) **Incomplete sideways:** the git word-walk is duplicated in `_lib_git_argv_from_subcmd` (`_lib.sh:549-578`, same `[[ "$word" == "git" || "$word" == */git ]]` test), so `git "commit"` defeats `_lib_extract_git_subcmd` independently of `_lib_fragment_invokes_git`. Fixing only the four functions the ticket names leaves half the bypass open in `deny-pii-in-commits.sh:153-154` and `deny-private-project-refs.sh:250-251`, which require *both* checks to pass. (3) **Cost:** `_lib_fragment_command_word` is called up to ten times per fragment in `deny-reviewer-tree-mutation.sh:332-376`; stripping inside it multiplies a 2-fork cost by call count rather than paying it once per hook.
- *`xargs -n1` dequote round-trip.* Rejected: GNU `xargs` documents its quoting rules as differing from the shell's, and it exits non-zero producing no output on an unmatched quote. Under the `2>/dev/null` capture this codebase uses (`_lib.sh:618`) that is an all-or-nothing fail-open — one stray quote anywhere disables every matcher in the hook. `_lib_strip_shell_quotes` is monotone by construction (`_lib.sh:1395-1421`: "Each step only ever joins previously-separated literal characters -- never breaks an existing contiguous match"), so it cannot fail this way.
- *Reuse `parse-git-command.py`.* Rejected as over-powered and mis-scoped: python3-dependent (a documented machine-class gap, `docs/design-decisions.md` §32, cited at `require-worktree-for-git-writes.sh:148-153`), one interpreter spawn per hook per Bash call, and git-specific — it cannot tokenize `gh`, `mv`, `rsync`, `ruff`, or `sed`, which is most of the affected surface.

**Per-hook shape.** Four of the five word-matcher hooks take the uniform form — compute `COMMAND_UNQUOTED` immediately after the `TOOL_NAME`/empty-command guards, then `_lib_split_fragments "$COMMAND_UNQUOTED"`, and point every downstream `$COMMAND` regex in the same detection path at it too (`deny-private-project-refs.sh:272,275`; `require-ready-for-review.sh:238,241`).

`deny-pii-in-commits.sh` is the one principled exception: it keeps splitting from raw `$COMMAND` and strips **per fragment** for its two matcher calls, passing the *raw* fragment to `_lib_commit_fragment_has_worktree_target` (`_lib.sh:608-653` — hoisted out of this hook and into `_lib.sh` by an unrelated upstream PR since this plan's Context was first drafted, and now shared with the new `deny-invisible-commit-content.sh`; the exception's logic is unaffected by the move). That function tokenizes with `xargs -n1` (`_lib.sh:618`), which already performs quote-aware tokenization, so it is not vulnerable — and feeding it pre-stripped text destroys the information it depends on: `git commit -m "fix the thing"` becomes six bare words, `-m` consumes one, and the awk at `_lib.sh:639-640` reads the next as a pathspec, setting `HEAD_SCAN_NEEDED=1`. That would pull `git diff HEAD` into `SCAN_TARGET` (`deny-pii-in-commits.sh:302-314`) on essentially every multi-word commit message, so unstaged working-tree content would start blocking commits that never included it. The rule the exception expresses: **strip for matchers that use bash word-splitting; keep raw for any consumer that does real tokenization.**

`deny-invisible-commit-content.sh` is Phase 1's sixth file and its second `xargs`-tokenizer exception, added after the branch sync above landed it. It carries two instances of this plan's root cause. Its fast-reject grep (`:135`, copied verbatim from `require-code-review.sh:64` — the Phase 2 shape, row 12) matches raw `$COMMAND`, so `git add f && "git" commit -m x` exits the hook at `:137` before either arm runs; the fix is the uniform M1 shape — hoist `COMMAND_UNQUOTED` above the fast-reject, and let arm 1's existing `STRIPPED_COMMAND` (`:243`) become that same variable, which also removes a duplicate `_lib_strip_shell_quotes` fork. Arm 2 is the exception. It counts commit fragments over quote-*masked* text (`_mask_shell_quotes`, `:155-183`) rather than stripped text, deliberately: masking deletes a quoted span's interior, so an `&&` inside a `-m` message cannot synthesize a fake fragment, and the masked fragment it captures in `DIRECT_MASKED_COMMIT_FRAGMENT` keeps a multi-word `-m` value as one `xargs -n1` token for arm 1's worktree-target check (row 6's regression, in a second file). But masking also erases the letters of `"git"`, leaving `""`, which no downstream strip can recover — so the three word-comparison calls at `:215-218` never match a quoted invocation. The fix is one change inside the masker: emit a quoted span **unquoted** when its interior is a single safe word (`^[A-Za-z0-9._/-]+$`), and keep blanking it otherwise.

- Every character in that class is one `_lib_split_fragments` (`_lib.sh:660-662`) never splits on, and the class excludes whitespace and both quote characters, so an unquoted emission is exactly one token wide.
- Fragment topology and `xargs -n1` token counts are unchanged for every other input.
- Arm 2's loop needs no edit at all.

**Alternative weighed and set aside (arm 2).** A second split — `_lib_split_fragments "$COMMAND_UNQUOTED"` run alongside the masked split, paired positionally, matchers reading the stripped fragment and `DIRECT_MASKED_COMMIT_FRAGMENT` the masked one. Rejected as unsound, not merely heavier: the two splits do not produce the same number of fragments. `git commit -m "a && b"` masks to one fragment and strips to two, so index *i* in one list is not index *i* in the other, and every quoted operator shifts all later pairs — the misalignment is silent and unbounded, and it would feed the wrong fragment to arm 1's worktree check.

**Phase 2's scope — the eight raw-regex hooks.** The same root cause (gates matching raw command text where bash matches post-quote-removal text) is present, verified, in eight hooks outside the five this plan's Context scopes. Two are consequential: `require-code-review.sh:64` (`git "commit"` misses `git\s+commit`, so the commit proceeds with no code-review marker) and `block-gh-pr-merge.sh:67` (`gh pr "merge"` misses, so an agent merges its own PR). The other six are `check-skill-length.sh:63`, `check-claude-md-length.sh:58`, `guard-settings-session-keys.sh:57`, `deny-escaped-backticks-in-pr-body.sh:54`, `require-stow-reminder.sh:82,149`, and `require-respond-pr.sh:112-113`.

Phase 1 (the five word-matcher hooks above, plus `deny-invisible-commit-content.sh`) ships in this PR. Phase 2 is deferred to its own immediate next tracked dispatch — a separate branch/PR, not abandoned and not open-ended backlog — because CLAUDE.md's sibling-audit rule scopes a fix to the bug rather than to where it surfaced, and because shipping "quoting can no longer walk past a gate" while `require-code-review.sh` stays bypassable would be false in the plan's own terms.

Phase 2's internal-script fix is mechanical (one variable swap plus one test row per hook) but not identical across all eight, on two axes:

- **Checked vs. unchecked fork:** `require-respond-pr.sh:109-111`'s documented no-fork decision is resolved by ledger row 14 to use the fork-based strip like its siblings, but two of the eight (`require-code-review.sh`, `block-gh-pr-merge.sh`) get a checked/`emit_deny` fork while the other six stay unchecked (see the fail-closed disposition row after row 14).

**Phase 2 precondition — `settings.json`'s own `if`-dispatch layer.**

- Six of the eight Phase 2 hooks (`require-code-review.sh`, `guard-settings-session-keys.sh`, `check-skill-length.sh`, `check-claude-md-length.sh`, `require-stow-reminder.sh`, `deny-escaped-backticks-in-pr-body.sh`) are still gated in `claude/.claude/settings.json` by an `if`-condition glob (`"Bash(git commit *)"` / `"Bash(gh pr create *)"` / `"Bash(gh pr edit *)"`) that runs *before* the hook script itself — a layer this plan's internal `COMMAND_UNQUOTED` fix does not touch.

- Anthropic's hooks documentation (https://code.claude.com/docs/en/hooks) confirms the `if` matcher parses the command into subcommands (splitting `&&`/`;`/`|`, stripping leading `VAR=` assignments, unwrapping `$(...)`/backticks) rather than doing raw-text glob matching — a materially different and likely safer model than the hooks' own bash `for word in $fragment` scan — but does not explicitly document whether quote characters are stripped during that tokenization.
- `test_hook_alignment.py:307-320`'s `_SELF_FILTERING_BASH_GATES` list and its own docstring ("does not prove the harness actually invokes the hook... at runtime") confirm this repo already tracks the general shape of this risk under GH-774.

### Assumption ledger

**Root problem/threat.** Every hook in the gate suite matches the *raw, unexpanded* Bash command string, but the command bash actually executes has had quote and backslash characters removed first. Any gated word written in quotes (`gh "pr" "create"`, `git "commit"`) therefore matches nothing, and the gate allows — a total detection failure, not a partial one.

**Givens** (conditions this design treats as fixed, each beyond its own reach):

- **G1 — Bash removes quote and escape characters during word expansion, after the hook has already seen the string.** Imposed by the shell's own grammar; no hook can change it.
- **G2 — A PreToolUse hook receives the command as unexpanded text and never observes bash's tokenization.** The harness owns the payload shape; the hook cannot ask for an argv.
- **G3 — The threat model is a careless or undirected agent, not an adversarially-instructed one.** Repo-documented at `docs/security-hardening.md:711-713`; changing it is a repo-wide policy decision outside this plan. This is the scope boundary behind two Out-of-Scope bullets below ("Full shell tokenization, or canonicalizing via bash itself" and "Variable expansion and command substitution as indirection vectors") — both are acceptable residuals only under G3's non-adversarial framing, the same way G4 justifies the ANSI-C-escapes/backslash-continuation residual.
- **G4 — `_lib_strip_shell_quotes` does not close every bash de-quoting mechanism.** Multi-character ANSI-C escapes and backslash-newline line continuation remain exploitable, documented as such at `docs/security-hardening.md:720-739`, where closing them exhaustively is explicitly deferred. This plan inherits that boundary rather than moving it.

## Out of scope

- **Reviving or re-deriving `GH-499`/`gate-effective-cwd`** — a different gate-authorization defect (`.cwd` versus embedded-`cd` tree resolution), deferred to its own later `/plan-it` pass. Its own out-of-scope items travel with it: the semver-plugin relocation gap, `require-plan-review.sh`'s sibling-worktree escape, and `require-worktree-for-git-writes.sh`'s pipe gap.
- **`require-worktree-for-git-writes.sh`'s detection path**, beyond the stale comment correction at `:155-162`. Its `parse-git-command.py` tokenizer is quote-correct, so the whole-word quoting this plan targets does not reach it. One narrower residual was found and is recorded here rather than fixed: the raw-text fast-reject at `:201` requires a contiguous literal `git`, so an intra-word split (`gi\t commit`) exits the hook before the parser runs. This is, mechanically, the same non-adversarial character-removal class `_lib_strip_shell_quotes` closes for the five in-scope hooks — `docs/security-hardening.md:714-718` classifies single-character backslash splits as "simple enough to occur without deliberate adversarial intent," not the adversarial-only bucket (variable expansion, command substitution) the other Out-of-Scope items below cite G3 for. It is left unfixed here purely as the engineer's own scope call for this hook, not because the mechanism itself requires an adversarial actor. `[engineer-verified]` A sound, fork-free pre-filter exists (`[[ "$COMMAND" == *g*i*t* ]]` — stripping only deletes characters, so the letters must appear in order in the raw text), but adopting it is a separate change to a hook the engineer scoped out.
- **Closing `_lib_strip_shell_quotes`'s documented residuals** — multi-character ANSI-C escapes (`$'\x67\x69\x74'`) and backslash-newline line continuation, both recorded as confirmed exploitable at `docs/security-hardening.md:720-739`, where closing them exhaustively is already deferred. This plan inherits that boundary; it does not move it.
- **Full shell tokenization, or canonicalizing via bash itself** (see G3). Already considered and rejected in-repo at `docs/security-hardening.md:726-728`, on the grounds that a command string can carry `$(...)`/backtick substitution and canonicalizing through bash would execute attacker-controlled text inside a security hook.
- **`_lib_split_fragments`'s own residuals** — its split on any literal `|` including one inside a quoted argument, and the space-containing-quoted-binary case, both catalogued at `deny-network-installs.sh:31-43`. Both are pre-existing, both are widening rather than fail-open, and both would require changing a splitter shared by seven call sites.
- **Changing the shared `_lib_fragment_*` matchers' comparison semantics.** The approach section's rejected-alternative analysis is the reason; the doc-comment contract and characterization tests exist so a future reader reaches the same conclusion without re-deriving it.
- **Variable expansion and command substitution as indirection vectors** (`CMD=git; $CMD commit`, see G3) — the standing accepted gap for this whole hook family, unchanged by this fix.
- **GH-774's remaining `if`-dispatch migration work**, beyond the six-hook smoke test row 20/21 requires as a precondition for Phase 2. GH-774 tracks a broader "wrapped-invocation" gap (env-prefix, `-C`, indirection shapes) than the quoting-specific question this plan settles; migrating the six hooks off `if`-dispatch entirely, if row 20's smoke test finds it necessary, closes only the quoting instance of that broader gap, not GH-774 itself.

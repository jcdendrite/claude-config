# Scope the ready-for-review active-bypass to non-publication commands

## Context

Make `/ready-for-review`'s own publication act un-authorizable by the bare fact that the skill is running. `claude/.claude/hooks/require-ready-for-review.sh` checks its active-bypass marker before any command-shape scan and `exit 0`s unconditionally, so a live `.ready-for-review-active.d/<session_id>` marker exempts all three gated commands — `git push` to a branch with an open PR, `gh pr create`, and `gh pr ready` — not just the skill's own iteration pushes its header says the bypass exists for. A session was observed running step 0 (`marker.sh activate`), skipping step 3's cumulative `/code-review`, jumping to step 6, and publishing a PR with no completion marker ever written. Why now: that session was found and its account of the gate checked against the hook; the gap is real. Intended outcome: the publication act is re-gated on a marker naming the artifact, without reintroducing the false-positive denials that commit `d9941926` (GH-869, #922) fixed.

(Step numbers in this paragraph name the skill's layout at the time of the incident; the change below renumbers them.)

## Approach

Collapse the active bypass to one arm, and move the publication act behind the completion marker. The hook's release rule becomes "a live active marker releases `git push`, nothing else" — `gh pr create` and `gh pr ready` are both excluded outright, mirroring `require-plan-review.sh:258-266`'s exclusion of its own terminal command for both non-push arms. `/ready-for-review` reorders to match: final hygiene recheck → `marker.sh write ready-for-review` → `gh pr create` (non-draft, command text unchanged) → `marker.sh deactivate`. The create is then authorized by the ordinary path the hook already has — `:323` skips the `gh pr view` existence check for `is_gh_pr_create`, and `:345` allows on a completion marker whose stored SHA equals HEAD — and HEAD cannot move between the write and the create, because the hygiene recheck has already left the tree clean and fully pushed.

This is round 1's design minus two mechanisms. The draft-PR shape required a `--draft` flag on the skill's create, a draft regex in the hook, a second quote-normalization pass to keep that regex from being forged by a quoted argument, and a `gh pr ready` call added to a line-frozen skill. The reorder needs none of them, because what authorizes the create is a marker naming the artifact rather than a parse of the command text. Deleted outright: the masked-fragment draft scan (round 1's mechanisms 3 and 5), its rows 10 and 14, and the entire finding class raised against it — there is no second normalization left to disagree with the first, so there is nothing for a `--title "--draft"` value to forge.

State the residual plainly rather than letting the fix imply more than it closes. `marker.sh write ready-for-review` records HEAD and attests nothing about steps 2–5, so a session that skips the cumulative review can still write the marker and create the PR. What changes is the *kind* of act required: `marker.sh activate ready-for-review` is a true statement an agent makes before skipping ahead, while `marker.sh write ready-for-review` is a false attestation that the gate completed. Against the actor this gate actually defends against — a cooperative model abbreviating under context pressure — that gap is the change's entire value. Against a deliberately-steered agent it buys nothing: both are exact-match, no-prompt `permissions.allow` entries, so substituting one for the other costs the same, and the hook header at `:108-115` already names `block-gh-pr-merge.sh` plus CI as the backstop for that arm.

**Root problem.** An active `/ready-for-review` bypass marker releases all three gated commands, so a run that skips the gate's own verification steps can still create and publish a PR with no completion marker ever written.

**Givens** (conditions this design treats as fixed, each beyond its own reach):

- **G1 — The active marker is session-wide, repo-agnostic, and refreshed by every Bash call in the session.** The marker path carries no repo hash and subagents inherit the parent `session_id`, so one `activate` releases the `git push` arm in every tree the session touches for the session's practical duration. `[verified: claude/.claude/hooks/_lib.sh:1884-1886; docs/hooks.md:144, 148, 154]` Fixed because the marker-path recipe and the unconditional Bash dispatch are shared by four gates (`_lib.sh:1943-1946` enumerates them); re-keying either is a cross-gate change owned by GH-502/GH-915, not by this plan.
- **G2 — The completion marker attests HEAD, not procedure.** `marker.sh write ready-for-review` stores `git rev-parse HEAD` and nothing else. `[verified: claude/.claude/scripts/marker.sh:539-548]` Fixed because the marker's content grammar is shared with the hook's read side and with `marker.sh status`/`check`; a richer attestation is a different mechanism.
- **G3 — `claude/` is stowed into `$HOME`, so a `git pull` in any session swaps this hook live under every concurrent session.** A session mid-flight on the old SKILL.md text keeps its loaded step order while the new hook is already enforcing. `[verified: repo CLAUDE.md, "`claude/` is stowed into `$HOME`. Changes under `claude/.claude/**` go live on `git pull`"]` Fixed by the stow layout, which is the repo's distribution mechanism for every consumer, not a per-change choice.
- **G4 — The hook file edited in a worktree is inert until merge.** `~/.claude/hooks/require-ready-for-review.sh` resolves to the main tree's copy, so this branch's own `/ready-for-review` run executes the *old* hook. `[verified: same CLAUDE.md line as G3]` It means the tests are the verification, not a live end-to-end run.

**Mechanisms.**

1. **Initialize the flag, then hoist the release decision — not the refresh.** Add `ACTIVE_MARKER_LIVE=false` immediately before the marker check at `require-ready-for-review.sh:174`, matching the `is_gated_git_push=false` convention at `:263-265`; replace the `exit 0` at `:175` with `ACTIVE_MARKER_LIVE=true`, leaving the `_lib_active_bypass_marker_live_and_touch` call itself in place. `anchors: root` — without the unconditional `false`, the no-marker path (every gated command outside a gate run) dereferences an unset variable under `set -uo pipefail`, and a bash abort is a non-2 nonzero exit the harness treats as non-blocking, so the gate would fail **open** on its most common path.
2. **Per-arm conjunction, evaluated after the command-shape scan.** Immediately after the "no gated command present" early exit at `:291-293`, release only when every gated shape present is bypass-eligible: `if $ACTIVE_MARKER_LIVE && $is_gated_git_push && ! $is_gh_pr_ready && ! $is_gh_pr_create; then exit 0; fi`. Spell out all four terms even though `$is_gated_git_push` is implied by the early exit above — the conjunction is the whole fix, and a fourth arm added later must not silently inherit a release. `anchors: root` — matches the hook's existing per-fragment discipline ("a bypassable push chained ahead of a gated fragment does not exempt it", header `:41-42`), so `git push origin feature && gh pr create` denies.

**Round 2's mechanism 3 — a split-failure fallback that rescued a `_lib_split_fragments` failure by scanning the unsplit command — is deleted outright, not repaired.** Its fallback evaded detection when a shell operator sat glued directly before `gh`: `git push origin feature&&gh pr create ...` matched neither the create nor the ready regex, since both anchor on `(^|[[:space:]])`, and a live marker released the command undetected — round 2's blocker. The fix was never going to matter: `deny-private-project-refs.sh` is wired on the PreToolUse `Bash` matcher with no `if` condition (`claude/.claude/settings.json:237`), runs before `require-ready-for-review.sh` (`:288`), and at `deny-private-project-refs.sh:303-307` calls `_lib_split_fragments` and denies on non-zero exit with no marker exemption. In any session where that sed shape fails, every Bash call is already denied by the redaction hook — the rescue never rescued a real session. The `_lib_split_fragments` fail-closed deny at `:268-271` stays byte-identical; only the rescue around it is removed. A boundary-hardened version of the same fallback (giving it the create/ready regexes' own `(^|[[:space:]])` guarantees) was considered and set aside — see Out of scope.

3. **The skill's tail becomes hygiene → write → create → deactivate, four separate Bash calls.** Old step 7 (final hygiene recheck) becomes step 6; the completion-marker write becomes its own step 7; old step 6 (create PR if missing) moves to step 8 and also absorbs the body-landed confirmation; the deactivation becomes step 9. `anchors: root` — `enforce-marker-script-shape.sh` denies chaining `marker.sh` to anything but `git commit` (`VALID_CHAINED_COMMIT_PATTERN` `:649`; `VALID_MARKER_CHAIN_PATTERN` `:667`), so the write, the create, and the deactivate cannot be joined by `&&`. The body-landed confirmation has to move with the create: step 6 now runs before the PR exists, so its "whether step 5 edited it or step 6 created the PR from it" bullet can only cover the step-5 case. Two heavier alternatives were weighed and rejected:
   - *Keep the create where it is and release it on a draft flag* (round 1). Heavier: it adds a flag to the skill, a regex to the hook, and a second quote-normalization pass whose divergence from the first is itself a bypass surface — and it makes the authorization a parse of command text rather than a marker naming the artifact.
   - *Keep the create where it is and require the `cumulative-review` marker to release it.* Heavier and weaker: it makes the create depend on a marker written by the same self-attesting session, at a higher false-deny cost, for the same residual G2 leaves standing.
4. **Two clauses in one shared deny message, not three rewritten messages.** Initialize `ACTIVE_MARKER_NOTE=""`; when `$ACTIVE_MARKER_LIVE`, set it to two sentences and interpolate into the `gh pr ready` and `gh pr create` messages at `:353` and `:355`: first, naming what the marker does release (`git push` only) and what to do next for a genuine create/ready — finish the gate's remaining steps and run `~/.claude/scripts/marker.sh write ready-for-review`, rather than re-invoking the skill from the start; second, covering the free-text false positive (row 14) — if the command doesn't actually create or ready a PR, the fix is rewording it, not more review work. `anchors: row2` — the existing "Run the /ready-for-review skill now" call to action reads as "start over" to an agent already mid-skill, and that same sentence is the recovery instruction for G3's skew case. The push message at `:357` needs no clause: with a live marker the push arm is released, and a chained shape routes to the `gh pr ready` or `gh pr create` branch first.
5. **Header rewrite, scoped to what this change makes false.** `anchors: G1` — `[engineer-verified: "Narrow the header's claim per-arm"]` The bypass list at `:35-49` narrows its first bullet to `git push`; the per-arm threat model at `:103-107` says the create and ready arms are gated on a marker naming the artifact while the push arm is a cooperative mistake-catcher, because G1 leaves it fully open. `:36-38`'s claim that the bypass check "fires regardless of what they would decide" is false once the release moves after the scan: the *check* still precedes the scan, but the *release* no longer does — reword to say so. Lines `:17-18` and `:24-25` currently say "removed at step 7" and "Written at step 7" while SKILL.md has both at step 8 — a pre-existing error that this reorder would break again; name the roles instead ("written by the gate-completion step, before the skill creates the PR"; "removed by the skill's final deactivation step"). `:19`'s "(step 3 fix → push → loop)" becomes "(the fix → push → loop)", for the same reason. Carrying no cross-file step number anywhere in the header — round 2's broader ambition — is dropped; only the two step-number references above were ever stale.

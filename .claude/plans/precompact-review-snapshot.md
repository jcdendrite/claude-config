# PreCompact-based review-narrative continuity

## Context

**Goal: find out whether Claude Code's `PreCompact`/`PostCompact` hooks can make `/compact` safe enough for claude-config's multi-round review pipeline that the engineer can compact more often without losing review-narrative continuity.**

`token-cost-reduction.md` (merged 4 days ago as PR #622) rejected compaction as this repo's context-reset primitive in favor of `handoff`, on the grounds that a lossy mid-loop summary risks dropping "which finding a reviewer raised, which were addressed, what was decided and why." At the time, the plan checked only `/compact <instructions>` and CLAUDE.md's `# Compact instructions` block and found both "weakly steerable." It did not evaluate `PreCompact`/`PostCompact` hooks, which exist in Claude Code today and were not on that plan's radar.

The engineer wants to compact more often to control cost, but only if compaction can be made to actually preserve what `handoff` currently preserves — otherwise `/compact` (and, per the engineer, `/clear`) are non-starters. This plan tests that hypothesis rather than assuming an answer either way.

## Approach

**Bottom line up front:** the research this plan is built on points toward `PreCompact`-blocking being the wrong mechanism — it would compound two platform behaviors the official docs leave unspecified, which is exactly the "stacked defenses on an unverified foundation" pattern CLAUDE.md flags as a wrong-foundation tell. The more likely fix is to stop treating review-narrative as something compaction must rescue at the last second, and instead persist it incrementally to disk as review skills already do for markers — which would make compaction's lossiness irrelevant to review continuity regardless of when or how often it fires. Phase 0 exists to test that conclusion empirically, not to declare it without running the experiment the engineer asked for.

### What compaction can and can't be told to preserve (verified this session)

- `/compact <instructions>` and a CLAUDE.md `# Compact instructions` block both still work as documented — they steer a summarizer, they don't guarantee retention. `[verified: code.claude.com/docs/en/costs, "Add custom compaction instructions"]`
- Project-root CLAUDE.md and auto-memory **reload from disk automatically** after compaction; invoked skill bodies re-inject capped at 25K tokens total; path-scoped rules and nested CLAUDE.md are lost until re-triggered. `[verified: code.claude.com/docs/en/context-window#what-survives-compaction, "What survives compaction" table]`
- Nothing in that table, or anywhere else checked this session, re-injects *conversation content* — only things that were never conversation content to begin with (files on disk, re-read at compaction time). This is the load-bearing fact the whole plan hangs on: **compaction only "rescues" things that already live outside the conversation.** Review-narrative doesn't today; markers do.

### Why review markers already don't need this plan, and review-narrative does

- Review-gate markers (`code-review`, `skill-review`, `plan-review`, `ready-for-review`) are single-line opaque hashes/SHAs under `$CONFIG_DIR/*-markers/`, written by `marker.sh`, matched by `grep -qFx` against live git/filesystem state recomputed on every gated call. They were never in the conversation's context window, so compaction cannot touch them — confirmed by direct read of `marker.sh`, `_lib.sh`, and all three `require-*.sh` gate hooks this session. `[verified: claude/.claude/scripts/marker.sh, claude/.claude/hooks/_lib.sh, claude/.claude/hooks/require-{code-review,plan-review,ready-for-review}.sh]`
- Nothing on disk anywhere in this pipeline records *which finding a reviewer raised, which were addressed, or what was decided and why* — grepping for narrative-capture terms across `claude/.claude/` returns zero hits outside the plan file itself. That detail lives only in conversation history (lost on compaction) or in prose a session chooses to hand-write into a plan file. `[verified: this session's grep sweep, confirmed against marker.sh's four write arms]`
- `handoff/SKILL.md`'s artifact is the one place this detail is currently captured durably — but producing it is inherently a model-judgment activity (synthesizing §1 Goal, §2.5 incomplete prerequisites, §3 vs §3.5 categorization, §6 open questions from live conversation/task-list state), not a fixed-format template a shell hook could fill in mechanically. `[verified: claude/.claude/skills/handoff/SKILL.md, full read this session]`

That last point rules out the most literal reading of "PreCompact hook snapshots review-loop state to disk" — a hook cannot itself author a handoff-quality artifact. What it *can* do is gate on one existing, or nudge toward one.

### The three platform behaviors the docs leave unspecified

Fetched `code.claude.com/docs/en/hooks` directly (not a paraphrase) for the full "Exit Code 2 Behavior Per Event" table. Findings:

- `PreCompact | Yes | Blocks compaction` — confirmed blocking works.
- `PostCompact | No | Shows stderr to user only` — confirmed no blocking.
- Every other event whose stderr goes *only* to the user says so explicitly (`SessionStart`, `Setup`, `SubagentStart` all carry the line "Claude doesn't see it"). **`PreCompact`'s row says only "Blocks compaction" — it does not state whether the block reason reaches Claude or only the terminal.** This is a real gap, not an inference I'm filling in either direction.
- The table describes the exit-code-2/stderr path only. It says nothing about whether `hookSpecificOutput.additionalContext` on a normal exit-0 works for `PreCompact`/`PostCompact` the way it demonstrably does for `UserPromptSubmit`/`Stop` (`nudge-handoff-near-context-cap.sh` is the in-repo proof that channel works for those two events).
- Nothing in the docs, and nothing in this repo, says what happens when an **automatically-triggered** compaction (the session is at its context limit) gets blocked by `PreCompact` exiting 2. Does Claude Code retry, hard-fail with a too-long error, or let the session keep growing with no further compaction attempt? An automatic-compaction block that goes wrong is a session-breaking failure mode shipped to every stow consumer — this is the single highest-consequence unknown in the whole plan.

CLAUDE.md: "When uncertain about a CLI flag, tool behavior, or API detail, verify rather than guessing." None of these three are resolvable by reading further docs — the docs are silent on them. They need a real, live experiment.

### Assumption ledger

**Root problem:** review-narrative (which finding was raised, what was decided) exists nowhere durable today, so any context-reset — `/compact`, `/clear`, or an eventual future mechanism — loses it. `handoff` currently papers over this for `/clear` by requiring a model-authored artifact before the reset; nothing plays that role for `/compact`.

**Givens:**
- Producing a handoff-quality artifact requires model judgment; no hook can synthesize one mechanically. `[verified: claude/.claude/skills/handoff/SKILL.md]`
- Review-gate markers are already structurally immune to compaction — they were never conversation content. `[verified: claude/.claude/scripts/marker.sh, _lib.sh, the three require-*.sh hooks]`
- Handoff remains the prescribed primitive for `/clear`; that decision was engineer-verified in the parent plan and isn't reopened here. `[engineer-verified, inherited from .claude/plans/token-cost-reduction.md's Approach section — "Compaction is not an acceptable mechanism in this workflow; handoff is the prescribed context-reset primitive"]`
- `PreCompact`/`PostCompact` have zero precedent anywhere in this repo — greenfield, no existing convention to extend. `[verified: grep across claude/.claude/ and docs/, zero matches, this session]`

**Mechanisms:**
- *Phase 0 — live empirical spike of the three unspecified behaviors* — `anchors: root`. Not a saving; a precondition for trusting any design built on `PreCompact`/`PostCompact`. Lighter primitives considered and rejected: (a) proceed straight to implementation on the docs' literal text alone — rejected because the docs are silently incomplete on exactly the load-bearing questions (block-visibility, auto-compact-block safety), and shipping a hook to every stow consumer on an unverified guess about auto-compaction's failure mode is the kind of blast radius CLAUDE.md's safety section exists to prevent; (b) ask Anthropic support / file a docs issue and wait — rejected as slower than a 20-minute reproducible local test, and the answer needs to hold for *this repo's* settings.json shape regardless of what any answer implies for other configurations.
- *Phase 1 (contingent) — incremental on-disk review-narrative ledger, not a PreCompact-triggered snapshot* — `anchors: root`. Lighter primitive than the hypothesis as originally framed. Two heavier primitives considered and rejected:
  (a) **`PreCompact` blocks compaction until the agent runs a `/handoff`-equivalent write, then retries** — rejected pending Phase 0: this compounds two of the three unverified behaviors (block-visibility to Claude, and the auto-compaction-block failure mode) into a single load-bearing path. If either turns out to work the way a hopeful reading assumes, this is still a forcing-function pattern that adds a blocking dependency to every stow consumer's auto-compaction path — the compounding-layers tell CLAUDE.md names directly.
  (b) **The hook synthesizes a heuristic summary itself** (e.g., grep the last N `tool_use` blocks from the transcript) — rejected on the same evidence that ruled out mechanical handoff generation: §3 vs §3.5 categorization, live-or-historical marker labeling, and "which finding was addressed" are judgment calls the handoff skill spends most of its 166 lines on: a scripted heuristic reproduces the low-fidelity artifact that made compaction unacceptable in the first place, just relabeled.
  Instead: extend `code-review` (and, as a follow-on, `plan-review`/`ready-for-review`) to append a short, structured narrative entry — finding raised, addressed/deferred, why — to a new on-disk ledger file as it already runs, the same session that produces the finding, no compaction-time synthesis required. This is **not** a reuse of `marker.sh`'s existing contract: `_lib_marker_value_present` treats a marker file as one opaque exact-match line (`grep -qFx`), which is the wrong shape for narrative text — the ledger needs its own file convention, append-only, keyed the same way markers are (repo-hash + session-id) so it doesn't collide across worktrees.
- *Extend `session-marker-dashboard.sh` to also surface the ledger* — `anchors: row (additionalContext support, refuted for PostCompact; confirmed working for SessionStart)`. Phase 0 refuted `additionalContext` for `PreCompact`/`PostCompact` categorically, but `session-marker-dashboard.sh` already ships `additionalContext` successfully on `SessionStart` with matcher `startup|clear|compact` — a different, already-working event, not the one Phase 0 tested. Reading the current session's ledger file and folding a summary into that hook's existing output is a lighter primitive than standing up a second hook type: no new `hook-class` header, no new `docs/hooks.md` entry, no new settings.json registration. CLAUDE.md's "default-suspect over-powered primitives" and "audit structural siblings" rules both point here directly — this hook is the structural sibling already doing the identical job for markers. `[verified: claude/.claude/hooks/session-marker-dashboard.sh, ships additionalContext on SessionStart today]`
- *`PostCompact` archival of `compact_summary`* — `anchors: row (Phase 0's Design implication)`. Deferred out of the Phase 1 pass below, not built. It is a pure safety net (Phase 0: "a raw backstop for whatever the ledger didn't anticipate"), not required for the core mechanism — the ledger persists narrative before compaction ever runs, so nothing about it depends on capturing `compact_summary`. Standing up a second, brand-new hook (its own `hook-class`, `docs/hooks.md` entry, settings.json registration, and test coverage) to archive a value that's a nice-to-have rather than load-bearing is more mechanism than this phase's problem calls for; revisit as a named follow-on once the ledger itself has real dogfooding.

**Assumptions:**
- `PreCompact`'s block reason is not surfaced to Claude, only the terminal user — by analogy to the three sibling rows that are explicit about this and whose absence from `PreCompact`'s row is conspicuous rather than silent-by-omission. `[unverified]` — Phase 0 resolves directly.
- Blocking an automatically-triggered compaction risks the session growing past its context window with no further compaction attempt. `[unverified]` — Phase 0's highest-priority question; a wrong assumption here is the one failure mode serious enough to break sessions repo-wide if shipped unverified.
- `hookSpecificOutput.additionalContext` on exit-0 works the same for `PreCompact`/`PostCompact` as it demonstrably does for `UserPromptSubmit`/`Stop`. `[unverified]` — Phase 0 resolves; Phase 1's `PostCompact` mechanism is moot without this.
- A new append-only ledger file, keyed like markers but carrying free text, is a clean enough addition that it won't need its own gate hook or invalidation logic the way markers do. `[verified: this plan's own Phase 1 design, Critical files table below]` — resolved: the Phase 1 section adds no gate hook, only a non-blocking compliance-log line on an existing gate's already-passing path.
- Starting the ledger with `code-review` only (not `plan-review`/`ready-for-review` simultaneously) captures the highest-frequency, most multi-round gate first and is representative enough to validate the mechanism before extending it. `[unverified]` — a scoping bet, revisit after Phase 1's first PR.

## Phases

**Phase 0 — Live spike, not committed to the repo.** Answer the three unverified platform behaviors with a real, reproducible test before any hook design is finalized. Each of steps 2–6 needs **2–3 independent runs** before its result is written up as confirmed/refuted — a single manual trial of undocumented harness behavior risks a false "confirmed" on a one-off race or client-version quirk (this repo's own hook tests guard against exactly this by exercising boundary/re-arm sequences more than once, e.g. `test_second_fire_allowed_after_rearm_spacing` in `claude/.claude/hooks/tests/test_nudge_handoff_near_context_cap.py`).

1. In a throwaway directory outside this repo (scratchpad), create a minimal `.claude/settings.json` registering a debug `PreCompact` hook and a debug `PostCompact` hook (no matcher, fires on both `manual`/`auto`). Each hook dumps its full stdin JSON to a log file, unmodified, so the exact input schema (field names, whether a `trigger` key carries `manual`/`auto`) is captured rather than assumed. Record the exact `claude --version` tested — these are possibly-drifting, under-documented event types (see Approach), and this repo already tracks exactly this kind of drift explicitly elsewhere (`nudge-handoff-near-context-cap.sh:80-81`, "fetched 2026-08-03; re-verify by 2026-11-03").
2. Test the block-visibility question: run the `PreCompact` hook with exit 2 and a distinctive stderr string during a **manual** `/compact`. Check whether that string appears anywhere Claude can act on it (its next turn references or reacts to it) versus only in the terminal transcript.
3. Test the auto-compaction-block failure mode: set `/autocompact` to the minimum (100000 tokens) to force automatic compaction quickly, then repeat the exit-2 block test with `trigger=auto`. Observe what happens next — does Claude Code retry, error with a too-long-prompt message, or let the session continue growing unbounded. This is the question that gates whether `PreCompact`-blocking is ever safe to ship.
4. Test `additionalContext` on exit 0 for both `PreCompact` and `PostCompact`, independent of the blocking question — set a distinctive `hookSpecificOutput.additionalContext` string and check whether it shows up in Claude's context on the next turn, the same way it demonstrably does today for `UserPromptSubmit`/`Stop`.
5. **Repeat steps 2–4 for a subagent's own context window**, not just the main session — dispatch a subagent whose task generates enough transcript to approach its own auto-compact window, with the same debug hooks registered. `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` is documented to apply to both main conversations and subagents, and this repo dispatches subagents constantly (`staff-*` reviewers, `code-writer`, `Explore`); if `PreCompact`/`PostCompact` behave differently for a subagent, Phase 1's design needs to know that before it locks in a main-session-only mechanism.
6. Test two failure-mode cases beyond the deliberate single block: (a) **repeat-fire within one session** — trigger a second compaction after the first, and check whether block-visibility and `additionalContext` behave consistently on re-fire; (b) **unintentional hook failure** — a debug hook that crashes, hangs, or times out during a real compaction, as distinct from a deliberate `exit 2`. (b) is more relevant to Phase 1's "informational-class, never blocks" posture than the deliberate-block case, and matches how this repo's shipped hooks already test fail-open behavior heavily elsewhere (missing-PATH-tool, unwritable-dir, malformed-input, all in `test_nudge_handoff_near_context_cap.py`).
7. Record findings in a new `docs/precompact-hook-behavior.md` — this is the phase's only committed artifact. State the exact JSON schema observed (including the `claude --version` tested), and answer each of the three unverified assumptions above — plus the subagent and repeat-fire/failure-mode questions from steps 5–6 — as confirmed, refuted, or still ambiguous with what would resolve it.

**Phase 1 — Incremental review-narrative ledger.** Phase 0's findings resolve every platform question this phase was conditioned on: `additionalContext` is refuted for both `PreCompact` and `PostCompact`, categorically, three independent ways; `PreCompact` block-visibility is refuted (terminal-only, not model-visible); auto-compaction-block safety held up to ~120K tokens / 7 blocked cycles but was never proven at the real ceiling. Net: **no `PreCompact` hook, in any form, anywhere in this design.** The branch of the bulleted list this replaces is settled, not merely defaulted — the ledger is the whole mechanism; nothing about it depends on intercepting compaction.

### Design

**Ledger file.** `$CONFIG_DIR/review-narrative-ledger/<repo-hash>.<session-id>.jsonl` — JSON Lines, append-only, one finding-disposition event per line:
```json
{"finding": "<short summary>", "disposition": "ADDRESS"|"DEFER", "rationale": "<one line>", "source": "<file:line or \"n/a\">"}
```
Reuses `_marker_lib_repo_hash` and the existing session-id resolution helpers from `marker.sh`/`_lib.sh` for keying — repo-hash + session-id, matching the convention the Approach section above already commits to — but is **not** an extension of `_lib_marker_value_present`'s contract: that helper answers "has this exact state been reviewed" via whole-file exact-line match; the ledger answers "what happened, in order," a different shape by design. No timestamp field: chronological order in an append-only file already encodes sequence, and omitting it keeps the per-line dedup check below a plain `grep -qFx` — the same primitive `_lib_marker_value_present` already uses, just applied at single-line-append granularity instead of whole-file-state granularity. Field caps: `finding` ≤200 chars, `rationale` ≤300 chars, keeping every appended line comfortably under `PIPE_BUF` (commonly 4096 bytes) so an `O_APPEND` single-line write is atomic and a killed process mid-append cannot corrupt a prior line. `[verified: POSIX.1-2017 XBD 8.1 — a write of {PIPE_BUF} bytes or fewer to a file opened with O_APPEND is not interleaved with data from other writes]` This is a write-atomicity guarantee only — `marker.sh` itself is not a precedent for it (its writes are single-writer truncating writes, `>`, not concurrent `O_APPEND`); the corrected citation is POSIX directly, not this repo's prior code. Cap enforcement: `review-ledger.sh` **rejects** (nonzero exit, stderr message, no partial write) a `--finding`/`--rationale` over its cap rather than silently truncating — silent truncation would corrupt exactly the narrative fidelity the ledger exists to preserve, and 200/300 chars is generous enough for a "short summary"/"one line" that rejection should be rare in practice.

**Write path.** New script `claude/.claude/scripts/review-ledger.sh`, mirroring `marker.sh`'s shape (sources `_lib.sh`, same CLI-arg style, same `scripts/`-lives-here / `hooks/tests/`-tests-it split `marker.sh`'s own tests already use — `test_marker_script.py` et al. live in `claude/.claude/hooks/tests/` despite `marker.sh` itself living in `scripts/`):
```
~/.claude/scripts/review-ledger.sh append code-review --finding "<text>" --disposition ADDRESS|DEFER --rationale "<text>" [--source "<file:line>"]
```
Builds the JSON line via `jq -n` rather than hand-escaping free text — already this repo's convention for hooks handling untrusted/free-form strings. Before appending, checks for an identical existing line via `grep -qFx -e` (the `-e` is load-bearing, not optional — `_lib_marker_value_present`'s own comment documents why a bare positional value risks being read as a flag when it starts with `-`; this script reuses that same protection rather than reintroducing the bug it was written to fix) and no-ops if found — this is the append-path idempotency answer (**required decision 3**): a retried `/code-review` round that re-emits an unchanged finding+disposition+rationale triple is a no-op, not a duplicate; a *changed* disposition for the same finding (DEFER this round, ADDRESS next round) is a new, distinct line by design — that's the history the ledger exists to keep, not noise to suppress.

The check-then-append pair is not itself atomic — two concurrent invocations against the same session's ledger file could both see "not found" and both append, producing a duplicate line (not corruption; each individual write stays `PIPE_BUF`-atomic). The realistic trigger is narrow (same session, same repo-hash, genuinely concurrent invocations — different sessions never collide, since they key to different files), but this repo has proven precedent for closing exactly this race cheaply: `_lib_worktree_collision_guard`'s `noclobber` idiom. `review-ledger.sh append` acquires a same-directory `noclobber` lock file (`<ledger-path>.lock`) around the check-and-append critical section, bounded retries (small, fixed count) on contention, and — matching this feature's informational-only posture — falls through to an unlocked append rather than blocking if the lock can't be acquired, since a duplicate line is a low-consequence outcome (an inflated count in a summary), not data loss. The lock file is removed on exit from the critical section, success or failure alike (`trap ... EXIT`-style release, not just the happy path) — a lock left in place after every single append would exhaust the bounded retries and silently degrade every *subsequent* append in the same session to permanently-unlocked, defeating the guard after its first use.

Retention: `append` also performs a lightweight, best-effort sweep, scoped to the whole `review-narrative-ledger/` directory (not just the current session's own file — a rarely-appended-to repo's stale file would otherwise never get swept, since the sweep only runs when *something* triggers an `append`), removing both ledger `.jsonl` files and any orphaned `.lock` files older than 30 days by mtime before returning. This mirrors `nudge-handoff-near-context-cap.sh:450`'s own directory-wide `find ... -mtime +30 -delete` on `.handoff-nudge-fired.d` — the ledger accumulates one file per repo-hash × session-id indefinitely otherwise, with no other pruning mechanism (unlike `marker.sh clear-stale`, which sweeps a different marker class on PID liveness — not the right staleness signal here, since a ledger should stay readable long after its session ends). Folding `.lock` files into the same sweep closes the one leftover-file class the lock mechanism itself introduces: a lock abandoned by a process that crashed mid-critical-section (before its release step ran) has no other cleanup path. A manual `review-ledger.sh clear-stale [--dry-run]` subcommand, same 30-day-mtime rule and same directory-wide + `.lock`-inclusive scope, is also added for on-demand cleanup, mirroring `marker.sh`'s own `clear-stale` naming.

Read convenience: `review-ledger.sh show` resolves this session's repo-hash + session-id internally (reusing the same helpers as `append`) and prints the current ledger's contents, or a "no ledger for this session" message if absent — this is what the CLAUDE.md fallback instruction below actually invokes, so the path-naming convention lives in exactly one place (this script) rather than being hand-duplicated into CLAUDE.md prose.

Kill switch (**required decision 1**): checks `~/.claude/.review-narrative-ledger-disabled` first and exits 0 without writing if present (a `show` call still reads whatever was already written; the switch gates new writes, not read access), reusing the exact shape `nudge-handoff-near-context-cap.sh` already established (`~/.claude/.handoff-nudge-disabled`) rather than the heavier required/optout two-tier pattern reserved for enforcement-escalating mechanisms (worktree discipline, autonomous shipping) — this addition is informational-only and machine-scoped, the same risk class as the nudge hooks, not the enforcement class. `[verified: claude/.claude/hooks/nudge-handoff-near-context-cap.sh's kill-switch shape, this session's survey]`

**`code-review/SKILL.md` integration.** Anchors the ledger call at the existing **Finding disposition** section (the step that finalizes every finding's ADDRESS/DEFER tag) — **not** at DEFER persistence, the section immediately after it. DEFER persistence only executes when the disposition step produces ≥1 DEFER finding (`code-review/SKILL.md` line 317's own opening condition); anchoring there would silently skip the ledger write on every all-ADDRESS review, the opposite of "every invocation." Finding disposition always runs and always tags every finding, so the new instruction is: immediately once dispositions are finalized, call `review-ledger.sh append` once per finding (ADDRESS and DEFER alike), before control reaches the (still-conditionally-gated) DEFER-persistence step. Worded generically ("once dispositions are finalized," not "once the table is finalized") because the disposition output isn't always tabular — `code-review/SKILL.md` line 294 uses inline `ADDRESS:`/`DEFER (<criterion>):` tags for ≤2 findings and only switches to a four-column table at 3+; the ledger call applies identically to both formats. Deliberately **not** gated on "review is clean" the way the tail-end marker-write step is: the scenario the ledger exists to protect is a review that is *not yet* clean, mid-loop, still iterating — gating ledger writes on the same clean-only condition as the marker would silently exclude the exact case that motivated this plan. The PR-body DEFER list (still written by the unchanged, still-conditional DEFER-persistence step) and the ledger now diverge in shape on purpose: the PR body is *current state, replaced each run, DEFER-only*; the ledger is *history, accumulated, every disposition*.

**Read path — no new hook.** Extend `session-marker-dashboard.sh` (already `SessionStart`, already `hook-class: informational`) to also look for the resuming session's ledger file and, when it's non-empty, fold a compact summary (e.g. "N findings recorded this session: M addressed, K deferred — see review-narrative-ledger for detail") into the same `additionalContext` output it already emits for marker status. Its matcher must also change, from `startup|clear|compact` to `startup|clear|compact|resume` — `SessionStart` accepts a `resume` value the existing registration excludes, and a genuine session resume (`--resume`/`--continue`) is exactly the scenario the CLAUDE.md instruction below names; without this change that instruction's "if none appears" framing is backwards for resume specifically — no auto-injection would ever fire there, making the CLAUDE.md fallback the *only* mechanism for that case, not a backstop. This is a direct application of "audit structural siblings": `SessionStart` has five matcher values total (`startup`, `resume`, `clear`, `compact`, `fork`) — `resume` joins the three already registered; `fork` is deliberately left out, not overlooked, because the ledger is keyed by session-id and a forked session (`--fork-session`) gets a fresh session-id with no ledger entries of its own yet, so firing on `fork` would read an always-empty file and no-op, the same as it already does on plain `startup`. Gated on the same `~/.claude/.review-narrative-ledger-disabled` file the write path checks — one sentinel disables both sides of the mechanism, not two independently-named switches that could drift out of sync. This new sentinel governs only the ledger-summary addition; the hook's existing marker-status reporting stays always-on as it is today, so `session-marker-dashboard.sh` becomes dual-governed (one always-on code path, one switchable) rather than uniformly gated — worth knowing when maintaining it, not a defect. This resolves the plan's original "PostCompact reminder" goal through a mechanism Phase 0 didn't refute — `SessionStart`'s `additionalContext` is proven, shipped, working code, not the untested-then-refuted `PreCompact`/`PostCompact` channel.

**Static CLAUDE.md instruction (belt-and-suspenders, not the primary mechanism).** One line added to `claude/.claude/CLAUDE.md`'s **Safety** section, not Code Review — Safety already houses the sibling marker/gate mechanical-fallback bullet ("If a skill's active-bypass gate refuses to release... run `marker.sh clear-stale`"), and this instruction is the same shape (a mechanical recovery step for a marker-adjacent mechanism), while Code Review's existing content is pure trigger-condition prose ("run `/code-review` before..."):
> After a compaction or session resume mid-review, trust the auto-injected review-narrative summary before re-litigating a `/code-review` finding; if none appears, run `~/.claude/scripts/review-ledger.sh show` to inspect the current session's ledger directly.
Uses the new `show` subcommand rather than hand-constructing the `<repo-hash>.<session-id>.jsonl` path inline — the naming convention then lives in exactly one place (the script) instead of being duplicated into CLAUDE.md prose that drifts silently if the convention ever changes. This documents the mechanism and gives a manual fallback; it is not the delivery path. The `SessionStart` extension above (now including the `resume` matcher value) is what actually restores the narrative automatically for every case this instruction names — Phase 0's refutation of event-driven injection applies only to `PreCompact`/`PostCompact`, and this instruction was never contingent on that finding.

**Compliance backstop (required decision 2).** No hard gate — the ledger-write step is agent-followed prose exactly like the Finding-disposition and DEFER-persistence steps it extends, neither of which has mechanical enforcement today either. Explicit accepted risk, with one concrete mitigation: extend `require-code-review.sh` (already `hook-class: gate`, already runs on every `git commit`, already recomputes the repo-hash) to additionally check — **non-blocking, never affecting its exit code** — whether a ledger file exists for the current repo-hash/session-id, and append one line (`<iso8601> marker=<matched|unmatched> ledger=<present|absent>`) to `$CONFIG_DIR/.review-ledger-compliance.log`. `require-code-review.sh` has two independent exit paths, not a shared tail — match → `exit 0` and no-match → `emit_deny` (which itself falls off the end of the script rather than calling `exit` directly) — so the compliance-log write is inserted at both sites, immediately before each, not once "after the decision." Each insertion is wrapped in `_lib_capped` (already sourced via `_lib.sh`, this repo's existing timeout-wrapper primitive) rather than a bare `printf >>`: this hook sits on `git commit`'s blocking path, and an unguarded append is a materially worse hang risk here than the same pattern's accepted gap elsewhere in this repo (`docs/permission-prompt-tracking.md`'s unguarded-append caveat is on a `Notification` hook, where a hang degrades a dialog — not a `git commit`, and not shipped with no soak period to every stow consumer at once the way this hook's change is). Every existing `_lib_capped` call site in this repo wraps a command-substitution capture (`out=$(_lib_capped cmd)`); wrapping a redirect (`_lib_capped cmd >> file`) is syntactically valid — redirection attaches to the whole function-call compound command — but is a new shape for this primitive, worth a one-line implementer note rather than assuming it's already a proven pattern. A small, scoped addition to an existing gate hook's already-passing path, not a new hook and not a new blocking condition — a measured signal in place of an assumed one, at no added blast radius once timeout-wrapped.

**Soak-period / graduation signal (required decision 4) — correcting the plan's own premise.** This session re-verified `token-cost-reduction.md`'s citations directly: `handoff-ratio` and `review-trace` hit-rate are used there exclusively as **regression tripwires** ("must not fall," "a second tripwire alongside it") — a grep for "graduation" and "soak" across that file returns zero matches. There is no "named graduation metric" precedent to match; the earlier `/plan-review` round that produced this required-decision item cited a pattern that does not exist in the source it named, and this revision corrects that rather than repeating it. This plan does not need a graduation gate, because nothing in this design ships off-by-default and later flips on — the ledger write, the `SessionStart` extension, and the compliance-log addition are all informational-class from day one, matching Verification item 4's existing blast-radius commitment ("informational-class ... until Phase 0's findings and a soak period say otherwise" — Phase 0's findings now say `PreCompact` is off the table entirely, which was the actual source of that item's caution, not this ledger). The concrete signal this plan does commit to: once `.review-ledger-compliance.log` has data from real `/code-review` runs, `ledger=present` should track `marker=matched` at a healthy rate; a sustained gap is the tripwire that would trigger revisiting the accepted-risk call in required decision 2 — the same tripwire *shape* as `handoff-ratio`, honestly described as a tripwire rather than mis-cited as a graduation gate.

**Subagent scope.** Phase 0's subagent probe was inconclusive (never reached the 100K-token auto-compact floor). Unaffected either way: this design never depended on subagent-side `PreCompact`/`PostCompact` behavior in the first place — it persists narrative to disk from the main session's `code-review` skill invocation, and `code-review` runs in the main session, not inside a dispatched subagent's own context. No scoping decision needed here; the plan's earlier "main-session-only for its first cut" contingency was written for a hook-based design this revision no longer uses.

**Defense-in-depth note.** CLAUDE.md's "hooks must filter their own input by tool name; do not rely solely on settings.json `if` conditions" rule doesn't add a requirement at any of the three Phase 1 integration sites, for three different reasons worth naming rather than leaving silent: `review-ledger.sh` is never settings.json-registered (invoked from skill prose, like `marker.sh`) — the rule targets hook-matcher reliability, inapplicable to a plain script; `session-marker-dashboard.sh`'s ledger addition lives in a `SessionStart` handler, which carries no `tool_name` field to filter on; `require-code-review.sh`'s compliance-log addition sits inside that hook's already-established `TOOL_NAME=="Bash" && git commit` filter, adding no new filtering surface.

Docs: no new hook file is created in this phase, so `claude/.claude/hooks/tests/test_hook_alignment.py`'s Layer 0 (`docs/hooks.md` entry required per new `.sh` file under `claude/.claude/hooks/`) is not triggered — `review-ledger.sh` lives in `scripts/`, outside that test's scope, same as `marker.sh` today. `docs/hooks.md`'s existing `session-marker-dashboard.sh` and `require-code-review.sh` bullets still need their prose updated to describe the added behavior, for documentation accuracy, even though no test enforces it; the `require-code-review.sh` bullet update (the hook that writes it) must also add an opt-out note for `$CONFIG_DIR/.review-ledger-compliance.log`, mirroring the "not rotated automatically, trim it periodically" language this repo already documents for `.handoff-nudge.log`, `.error-mode-nudge.log`, `.commit-stall-block.log`, and `.permission-prompt-tracking.log` — the new compliance log is the same shape (unbounded append-only, one line per `git commit` across every repo using this config) and should follow the same documented convention rather than going undocumented. Known, harmless limitation, same shape as the existing `.handoff-nudge-fired.d` one-shot leak: reverting Phase 1 leaves already-written `review-narrative-ledger/` and `.review-ledger-compliance.log` files behind on stow-consumer disks — steady-state growth while the feature stays *enabled* is handled separately, by the Write path's mtime-sweep-on-append and `clear-stale` subcommand above, not left as an open gap.

## Verification

1. **Phase 0 is dogfooding, not pytest.** Its three questions are about harness routing behavior no synthetic-stdin test can observe — they require a live session. Findings go in `docs/precompact-hook-behavior.md` with the exact commands run, so they're reproducible if Claude Code's behavior changes in a later version.
2. **Phase 1's new script and the two extended hooks follow this repo's existing hook-test conventions** — the `_run_hook`/payload-builder pattern from `claude/.claude/hooks/tests/test_nudge_handoff_near_context_cap.py`, `$HOME` sandboxed to `tmp_path`. Specific new cases required (see Critical files table rows for the full lists): `review-ledger.sh`'s dedup/cap-rejection/concurrent-race/mtime-sweep/session-id-traversal behavior in its own new test file; `session-marker-dashboard.sh`'s ledger-present/absent/empty-boundary/kill-switch-scope cases layered onto its existing marker-status test file as a regression guard, not a replacement; `require-code-review.sh`'s both-exit-paths log line plus `_lib_capped`-timeout-on-unwritable-dir case. This covers the ledger script's own behavior and the two hooks' extended behavior when invoked; it does **not** cover whether `code-review/SKILL.md`'s instructions actually cause `review-ledger.sh` to be invoked during a real review — that's agent-followed prose, not hook code, and has no mechanical backstop beyond the compliance log (see the Approach section's compliance-backstop decision). Full `../../../.venv/bin/pytest claude/.claude/` + `ruff` + `shellcheck`.
3. **End-to-end**: run one real multi-round review-gated PR (code-review with at least one addressed and one deferred finding) with `/autocompact` set low enough to force a mid-loop compaction, and confirm (a) the resuming turn's injected context surfaces the recorded findings without re-litigating the deferred one, and (b) `.review-ledger-compliance.log` gained one `ledger=present` line at commit time.
4. **Blast radius**: no hook is newly created in Phase 1 — `review-ledger.sh` is a plain script (not registered anywhere in settings.json), and both extended hooks (`session-marker-dashboard.sh`, `require-code-review.sh`) keep their existing `hook-class` and add only non-blocking behavior on their already-passing paths. There is no soak-gated "off by default, later flip on" state to reach (see the Approach section's required-decision-4 correction) — everything ships live, informational-only, from the first merged PR.

## Out of scope

- **`/clear`'s lossiness.** Already mitigated by the existing `handoff` + `nudge-handoff-near-context-cap.sh` mechanism, which the parent plan already engineer-verified as this repo's prescribed context-reset primitive. Not reopened here.
- **Lowering the auto-compact window/threshold as a cost policy.** That's `token-cost-reduction.md`'s Phase 3/4 territory (re-arming the handoff nudge, `/clear`+`/compact` guidance lines) — a frequency question. This plan is about compaction *safety*, a precondition for the engineer choosing to raise that frequency personally via their own `/autocompact` setting, not a repo-side frequency change.
- **Extending the ledger to `plan-review` and `ready-for-review` in the same PR.** Phase 1 scopes to `code-review` first per the assumption ledger's scoping bet; extending to the other two gates is a named follow-on, not required here.
- **A `PreCompact` hard gate on every stow consumer's auto-compaction path.** Ruled out categorically — Phase 0 refuted both block-visibility and (up to the tested ceiling) offered no affirmative safety case for auto-compaction-block behavior; this design does not use `PreCompact` in any form.
- **A `PostCompact` hook archiving `compact_summary`.** Deferred, not built in this PR. Phase 0 surfaced that `PostCompact`'s input carries the full `compact_summary` Claude Code just generated, and archiving it would be a cheap safety net — but it is not load-bearing for the ledger mechanism, which persists narrative before compaction ever runs. Revisit as a named follow-on once the ledger has real dogfooding, if the compliance-log signal (required decision 4) or real incidents show the ledger alone misses something worth a raw backstop.

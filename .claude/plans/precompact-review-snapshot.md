# PreCompact-based review-narrative continuity

## Context

**Goal: find out whether Claude Code's `PreCompact`/`PostCompact` hooks can make `/compact` safe enough for claude-config's multi-round review pipeline that the engineer can compact more often without losing review-narrative continuity.**

`token-cost-reduction.md` (merged 4 days ago as PR #622) rejected compaction as this repo's context-reset primitive in favor of `handoff`, on the grounds that a lossy mid-loop summary risks dropping "which finding a reviewer raised, which were addressed, what was decided and why." At the time, the plan checked only `/compact <instructions>` and CLAUDE.md's `# Compact instructions` block and found both "weakly steerable." It did not evaluate `PreCompact`/`PostCompact` hooks, which exist in Claude Code today and were not on that plan's radar.

The engineer wants to compact more often to control cost, but only if compaction can be made to actually preserve what `handoff` currently preserves — otherwise `/compact` (and, per the engineer, `/clear`) are non-starters. This plan tests that hypothesis rather than assuming an answer either way.

## Approach

**Bottom line up front:** the research this plan is built on points toward `PreCompact`-blocking being the wrong mechanism — it would compound two platform behaviors the official docs leave unspecified, which is exactly the "stacked defenses on an unverified foundation" pattern CLAUDE.md flags as a wrong-foundation tell. The more likely fix is to stop treating review-narrative as something compaction must rescue at the last second, and instead persist it incrementally to disk as review skills already do for markers — which would make compaction's lossiness irrelevant to review continuity regardless of when or how often it fires. Phase 0 exists to test that conclusion empirically, not to declare it without running the experiment the engineer asked for.

### What compaction can and can't be told to preserve (verified this session)

- `/compact <instructions>` and a CLAUDE.md `# Compact instructions` block both still work as documented — they steer a summarizer, they don't guarantee retention. `[verified: code.claude.com/docs/en/costs, "Add custom compaction instructions"]`
- Project-root CLAUDE.md and auto-memory **reload from disk automatically** after compaction; invoked skill bodies re-inject capped at 25K tokens total; path-scoped rules and nested CLAUDE.md are lost until re-triggered. `[verified: code.claude.com/docs/en/context-window#what-survives-compaction, "What survives compaction" table]`
- Nothing in that table, or anywhere else checked this session, re-injects *conversation content* — only things that were never conversation content to begin with (files on disk, re-read at compaction time). This is the load-bearing fact the whole plan hangs on: **compaction only "rescues" things that already live outside the conversation.** Review-narrative doesn't today; markers do.

### Why review markers already don't need this plan, and review-narrative does

- Review-gate markers (`code-review`, `skill-review`, `plan-review`, `ready-for-review`) are single-line opaque hashes/SHAs under `$CONFIG_DIR/*-markers/`, written by `marker.sh`, matched by `grep -qFx` against live git/filesystem state recomputed on every gated call. They were never in the conversation's context window, so compaction cannot touch them — confirmed by direct read of `marker.sh`, `_lib.sh`, and all three `require-*.sh` gate hooks this session. `[verified: claude/.claude/scripts/marker.sh, claude/.claude/hooks/_lib.sh, claude/.claude/hooks/require-{code-review,plan-review,ready-for-review}.sh]`
- Nothing on disk anywhere in this pipeline records *which finding a reviewer raised, which were addressed, or what was decided and why* — grepping for narrative-capture terms across `claude/.claude/` returns zero hits outside the plan file itself. That detail lives only in conversation history (lost on compaction) or in prose a session chooses to hand-write into a plan file. `[verified: this session's grep sweep, confirmed against marker.sh's four write arms]`
- `handoff/SKILL.md`'s artifact is the one place this detail is currently captured durably — but producing it is inherently a model-judgment activity (synthesizing §1 Goal, §2.5 incomplete prerequisites, §3 vs §3.5 categorization, §6 open questions from live conversation/task-list state), not a fixed-format template a shell hook could fill in mechanically. `[verified: claude/.claude/skills/handoff/SKILL.md, full read this session]`

That last point rules out the most literal reading of "PreCompact hook snapshots review-loop state to disk" — a hook cannot itself author a handoff-quality artifact. What it *can* do is gate on one existing, or nudge toward one.

### The three platform behaviors the docs leave unspecified

Fetched `code.claude.com/docs/en/hooks` directly (not a paraphrase) for the full "Exit Code 2 Behavior Per Event" table. Findings:

- `PreCompact | Yes | Blocks compaction` — confirmed blocking works.
- `PostCompact | No | Shows stderr to user only` — confirmed no blocking.
- Every other event whose stderr goes *only* to the user says so explicitly (`SessionStart`, `Setup`, `SubagentStart` all carry the line "Claude doesn't see it"). **`PreCompact`'s row says only "Blocks compaction" — it does not state whether the block reason reaches Claude or only the terminal.** This is a real gap, not an inference I'm filling in either direction.
- The table describes the exit-code-2/stderr path only. It says nothing about whether `hookSpecificOutput.additionalContext` on a normal exit-0 works for `PreCompact`/`PostCompact` the way it demonstrably does for `UserPromptSubmit`/`Stop` (`nudge-handoff-near-context-cap.sh` is the in-repo proof that channel works for those two events).
- Nothing in the docs, and nothing in this repo, says what happens when an **automatically-triggered** compaction (the session is at its context limit) gets blocked by `PreCompact` exiting 2. Does Claude Code retry, hard-fail with a too-long error, or let the session keep growing with no further compaction attempt? An automatic-compaction block that goes wrong is a session-breaking failure mode shipped to every stow consumer — this is the single highest-consequence unknown in the whole plan.

CLAUDE.md: "When uncertain about a CLI flag, tool behavior, or API detail, verify rather than guessing." None of these three are resolvable by reading further docs — the docs are silent on them. They need a real, live experiment.

### Assumption ledger

**Root problem:** review-narrative (which finding was raised, what was decided) exists nowhere durable today, so any context-reset — `/compact`, `/clear`, or an eventual future mechanism — loses it. `handoff` currently papers over this for `/clear` by requiring a model-authored artifact before the reset; nothing plays that role for `/compact`.

**Givens:**
- Producing a handoff-quality artifact requires model judgment; no hook can synthesize one mechanically. `[verified: claude/.claude/skills/handoff/SKILL.md]`
- Review-gate markers are already structurally immune to compaction — they were never conversation content. `[verified: claude/.claude/scripts/marker.sh, _lib.sh, the three require-*.sh hooks]`
- Handoff remains the prescribed primitive for `/clear`; that decision was engineer-verified in the parent plan and isn't reopened here. `[engineer-verified, inherited from .claude/plans/token-cost-reduction.md's Approach section — "Compaction is not an acceptable mechanism in this workflow; handoff is the prescribed context-reset primitive"]`
- `PreCompact`/`PostCompact` have zero precedent anywhere in this repo — greenfield, no existing convention to extend. `[verified: grep across claude/.claude/ and docs/, zero matches, this session]`

**Mechanisms:**
- *Phase 0 — live empirical spike of the three unspecified behaviors* — `anchors: root`. Not a saving; a precondition for trusting any design built on `PreCompact`/`PostCompact`. Lighter primitives considered and rejected: (a) proceed straight to implementation on the docs' literal text alone — rejected because the docs are silently incomplete on exactly the load-bearing questions (block-visibility, auto-compact-block safety), and shipping a hook to every stow consumer on an unverified guess about auto-compaction's failure mode is the kind of blast radius CLAUDE.md's safety section exists to prevent; (b) ask Anthropic support / file a docs issue and wait — rejected as slower than a 20-minute reproducible local test, and the answer needs to hold for *this repo's* settings.json shape regardless of what any answer implies for other configurations.
- *Phase 1 (contingent) — incremental on-disk review-narrative ledger, not a PreCompact-triggered snapshot* — `anchors: root`. Lighter primitive than the hypothesis as originally framed. Two heavier primitives considered and rejected:
  (a) **`PreCompact` blocks compaction until the agent runs a `/handoff`-equivalent write, then retries** — rejected pending Phase 0: this compounds two of the three unverified behaviors (block-visibility to Claude, and the auto-compaction-block failure mode) into a single load-bearing path. If either turns out to work the way a hopeful reading assumes, this is still a forcing-function pattern that adds a blocking dependency to every stow consumer's auto-compaction path — the compounding-layers tell CLAUDE.md names directly.
  (b) **The hook synthesizes a heuristic summary itself** (e.g., grep the last N `tool_use` blocks from the transcript) — rejected on the same evidence that ruled out mechanical handoff generation: §3 vs §3.5 categorization, live-or-historical marker labeling, and "which finding was addressed" are judgment calls the handoff skill spends most of its 166 lines on: a scripted heuristic reproduces the low-fidelity artifact that made compaction unacceptable in the first place, just relabeled.
  Instead: extend `code-review` (and, as a follow-on, `plan-review`/`ready-for-review`) to append a short, structured narrative entry — finding raised, addressed/deferred, why — to a new on-disk ledger file as it already runs, the same session that produces the finding, no compaction-time synthesis required. This is **not** a reuse of `marker.sh`'s existing contract: `_lib_marker_value_present` treats a marker file as one opaque exact-match line (`grep -qFx`), which is the wrong shape for narrative text — the ledger needs its own file convention, append-only, keyed the same way markers are (repo-hash + session-id) so it doesn't collide across worktrees.
- *`PostCompact` informational reminder* — `anchors: row (additionalContext support, unverified)`. If Phase 0 confirms `additionalContext` works for this event, a `PostCompact` hook can point the resumed turn back at the ledger, mirroring the already-shipped `session-marker-dashboard.sh` pattern (`SessionStart` matcher `startup|clear|compact`) that already restores *marker* visibility after a compact/clear today — this hook is doing the same job one layer up, for narrative instead of markers.

**Assumptions:**
- `PreCompact`'s block reason is not surfaced to Claude, only the terminal user — by analogy to the three sibling rows that are explicit about this and whose absence from `PreCompact`'s row is conspicuous rather than silent-by-omission. `[unverified]` — Phase 0 resolves directly.
- Blocking an automatically-triggered compaction risks the session growing past its context window with no further compaction attempt. `[unverified]` — Phase 0's highest-priority question; a wrong assumption here is the one failure mode serious enough to break sessions repo-wide if shipped unverified.
- `hookSpecificOutput.additionalContext` on exit-0 works the same for `PreCompact`/`PostCompact` as it demonstrably does for `UserPromptSubmit`/`Stop`. `[unverified]` — Phase 0 resolves; Phase 1's `PostCompact` mechanism is moot without this.
- A new append-only ledger file, keyed like markers but carrying free text, is a clean enough addition that it won't need its own gate hook or invalidation logic the way markers do. `[unverified]` — Phase 1 design detail, not blocking Phase 0.
- Starting the ledger with `code-review` only (not `plan-review`/`ready-for-review` simultaneously) captures the highest-frequency, most multi-round gate first and is representative enough to validate the mechanism before extending it. `[unverified]` — a scoping bet, revisit after Phase 1's first PR.

## Phases

**Phase 0 — Live spike, not committed to the repo.** Answer the three unverified platform behaviors with a real, reproducible test before any hook design is finalized. Each of steps 2–6 needs **2–3 independent runs** before its result is written up as confirmed/refuted — a single manual trial of undocumented harness behavior risks a false "confirmed" on a one-off race or client-version quirk (this repo's own hook tests guard against exactly this by exercising boundary/re-arm sequences more than once, e.g. `test_second_fire_allowed_after_rearm_spacing` in `claude/.claude/hooks/tests/test_nudge_handoff_near_context_cap.py`).

1. In a throwaway directory outside this repo (scratchpad), create a minimal `.claude/settings.json` registering a debug `PreCompact` hook and a debug `PostCompact` hook (no matcher, fires on both `manual`/`auto`). Each hook dumps its full stdin JSON to a log file, unmodified, so the exact input schema (field names, whether a `trigger` key carries `manual`/`auto`) is captured rather than assumed. Record the exact `claude --version` tested — these are possibly-drifting, under-documented event types (see Approach), and this repo already tracks exactly this kind of drift explicitly elsewhere (`nudge-handoff-near-context-cap.sh:80-81`, "fetched 2026-08-03; re-verify by 2026-11-03").
2. Test the block-visibility question: run the `PreCompact` hook with exit 2 and a distinctive stderr string during a **manual** `/compact`. Check whether that string appears anywhere Claude can act on it (its next turn references or reacts to it) versus only in the terminal transcript.
3. Test the auto-compaction-block failure mode: set `/autocompact` to the minimum (100000 tokens) to force automatic compaction quickly, then repeat the exit-2 block test with `trigger=auto`. Observe what happens next — does Claude Code retry, error with a too-long-prompt message, or let the session continue growing unbounded. This is the question that gates whether `PreCompact`-blocking is ever safe to ship.
4. Test `additionalContext` on exit 0 for both `PreCompact` and `PostCompact`, independent of the blocking question — set a distinctive `hookSpecificOutput.additionalContext` string and check whether it shows up in Claude's context on the next turn, the same way it demonstrably does today for `UserPromptSubmit`/`Stop`.
5. **Repeat steps 2–4 for a subagent's own context window**, not just the main session — dispatch a subagent whose task generates enough transcript to approach its own auto-compact window, with the same debug hooks registered. `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` is documented to apply to both main conversations and subagents, and this repo dispatches subagents constantly (`staff-*` reviewers, `code-writer`, `Explore`); if `PreCompact`/`PostCompact` behave differently for a subagent, Phase 1's design needs to know that before it locks in a main-session-only mechanism.
6. Test two failure-mode cases beyond the deliberate single block: (a) **repeat-fire within one session** — trigger a second compaction after the first, and check whether block-visibility and `additionalContext` behave consistently on re-fire; (b) **unintentional hook failure** — a debug hook that crashes, hangs, or times out during a real compaction, as distinct from a deliberate `exit 2`. (b) is more relevant to Phase 1's "informational-class, never blocks" posture than the deliberate-block case, and matches how this repo's shipped hooks already test fail-open behavior heavily elsewhere (missing-PATH-tool, unwritable-dir, malformed-input, all in `test_nudge_handoff_near_context_cap.py`).
7. Record findings in a new `docs/precompact-hook-behavior.md` — this is the phase's only committed artifact. State the exact JSON schema observed (including the `claude --version` tested), and answer each of the three unverified assumptions above — plus the subagent and repeat-fire/failure-mode questions from steps 5–6 — as confirmed, refuted, or still ambiguous with what would resolve it.

**Phase 1 (contingent on Phase 0's findings) — Incremental review-narrative ledger.** Scope and hook design depend on Phase 0's answers:
- If `additionalContext` works for `PostCompact` (assumption 3 confirmed): build the ledger + `PostCompact` reminder as described in the Approach. No `PreCompact` hook needed — the mechanism doesn't require intercepting compaction at all, since the narrative was already persisted before compaction ever ran.
- If Phase 0 also confirms `PreCompact` blocking is both Claude-visible and safe on auto-triggered compaction: `PreCompact` becomes an optional, off-by-default soft nudge (never a hard gate on every stow consumer) reminding the agent to flush any not-yet-persisted narrative — a refinement on top of the ledger, not a replacement for it.
- If Phase 0 refutes `additionalContext` support for both events: the ledger still stands on its own (it survives compaction by construction, per the "What survives compaction" table's actual mechanism — being re-read from disk), but the *reminder* has to move to a lower-tech surface, e.g. instructing the resuming turn via CLAUDE.md to check the ledger when picking up mid-review, rather than automatic injection.
- If Phase 0's step 5 finds subagent compaction behaves differently from the main session: Phase 1 scopes to main-session-only for its first cut, and subagent-narrative protection becomes a named follow-on rather than a silent gap.

Before any hook registers in the shared `claude/.claude/settings.json`, the plan revision below must additionally settle four points this round of review surfaced, none of which Phase 0 resolves on its own:
1. **A concrete disable mechanism**, named and committed — not borrowed from `nudge-handoff-near-context-cap.sh`'s existing kill switch, which a brand-new hook type has no claim to inherit. This repo's `settings.json`/`settings.local.json` split (per `claude/.claude/CLAUDE.md`) makes the choice between a dedicated disable file, an env var, or an opt-in-only default a real fork to decide explicitly, given this plan itself calls an unrecoverable auto-compaction block "serious enough to break sessions repo-wide."
2. **A compliance backstop for the ledger-write step**, or an explicit accepted-risk statement if none is added. The write lives in `code-review/SKILL.md` as agent-followed prose, not hook code — pytest can cover the ledger script's behavior when invoked, but nothing mechanically verifies the skill actually invokes it during a real review, unlike markers' independent `require-code-review.sh` backstop.
3. **Append-path idempotency for the ledger** — partial/failed append, or duplicate entries on a retried `code-review` round within one session. The exact-match marker contract doesn't answer this (it's a different shape by design, see Approach), so the new file format needs its own answer.
4. **A concrete soak-period signal**, not just "a soak period" — matching the parent plan's named graduation metrics (`handoff-ratio`, `review-trace` hit-rate) rather than an unmeasured waiting period, since finding 1 above means this plan can't yet borrow the parent plan's blast-radius argument (that argument rests on an existing disable switch this hook doesn't have until finding 1 is resolved).

Detailed file-level design — including these four points — is deferred to a plan revision once Phase 0's answers are in; this plan does not commit to a specific ledger file format or hook implementation ahead of that. The revision must also add `docs/hooks.md` to Critical files (any new hook trips `claude/.claude/hooks/tests/test_hook_alignment.py`'s Layer 0 requirement for a per-hook entry there), and should note as a known, harmless limitation that reverting Phase 1 leaves already-written ledger files behind on stow-consumer disks — the same shape as the existing `.handoff-nudge-fired.d` one-shot leak.

## Verification

1. **Phase 0 is dogfooding, not pytest.** Its three questions are about harness routing behavior no synthetic-stdin test can observe — they require a live session. Findings go in `docs/precompact-hook-behavior.md` with the exact commands run, so they're reproducible if Claude Code's behavior changes in a later version.
2. **Phase 1's new ledger script and `PostCompact` hook, if it proceeds, follow this repo's existing hook-test conventions** — the `_run_hook`/payload-builder pattern from `claude/.claude/hooks/tests/test_nudge_handoff_near_context_cap.py`, `$HOME` sandboxed to `tmp_path`, asserting on `hookSpecificOutput` shape and ledger file contents. This covers the ledger script's own behavior when invoked; it does **not** cover whether `code-review/SKILL.md`'s instructions actually cause it to be invoked during a real review — that's agent-followed prose, not hook code, and has no mechanical test the way `require-code-review.sh` backstops marker compliance (see Phase 1's compliance-backstop requirement). Full `../../../.venv/bin/pytest claude/.claude/` + `ruff` + `shellcheck`.
3. **End-to-end**: run one real multi-round review-gated PR (code-review with at least one addressed and one deferred finding) with `/autocompact` set low enough to force a mid-loop compaction, and confirm the resuming turn does not re-litigate the deferred finding or re-ask a question already answered.
4. **Blast radius**: any hook shipped from Phase 1 is informational-class (never blocks) until Phase 0's findings and a soak period say otherwise — matching the parent plan's Phase 3 precedent for repo-wide hook changes (pull-based, non-atomic propagation to every stow consumer).

## Out of scope

- **`/clear`'s lossiness.** Already mitigated by the existing `handoff` + `nudge-handoff-near-context-cap.sh` mechanism, which the parent plan already engineer-verified as this repo's prescribed context-reset primitive. Not reopened here.
- **Lowering the auto-compact window/threshold as a cost policy.** That's `token-cost-reduction.md`'s Phase 3/4 territory (re-arming the handoff nudge, `/clear`+`/compact` guidance lines) — a frequency question. This plan is about compaction *safety*, a precondition for the engineer choosing to raise that frequency personally via their own `/autocompact` setting, not a repo-side frequency change.
- **Extending the ledger to `plan-review` and `ready-for-review` in the same PR.** Phase 1 scopes to `code-review` first per the assumption ledger's scoping bet; extending to the other two gates is a named follow-on, not required here.
- **A `PreCompact` hard gate on every stow consumer's auto-compaction path.** Ruled out unless Phase 0 affirmatively confirms both block-visibility and auto-compaction-block safety; the default posture per the mechanism section is that Phase 1 doesn't need `PreCompact` at all.

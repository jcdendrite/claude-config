# Plan-review gate disarms on an empty active plan set

## Context

Make `require-plan-review.sh` stop demanding a plan review for non-plan
`Write`/`Edit` calls during a trusted in-progress merge whose only plan-file
change is one the merge brought in from the default branch untouched.

`_lib_active_plan_files` already does the merge-aware half correctly: mid-merge it
excludes a plan file identical to the computed base, returning an empty active set.
`_lib_active_plan_hash` then re-arms the gate anyway — its empty-active-set branch
binds the hash to `sha256("plan-review-empty-base:$base")` instead of returning
empty, so the gate demands a marker for a plan set that is empty by construction.
No `/plan-review` run can honestly produce that marker, because there is no plan to
review. The gate is releasable rather than wedged: `/plan-review`'s Step 1 has no
"no plan found" branch, so it falls through to the most recent plan in
`.claude/plans/` — mid-sync, upstream's — and reviews content this branch did not
author. Both halves shipped in the same commit, `1c4ba8d8` (#994), and that
change's verification asserted `_lib_active_plan_files` at the primitive level
only — never the hook's end-to-end verdict — so the suite stayed green.

Why now: the gate charges every branch sync a review round it did not earn, and the
cost concentrates badly. In the reported incident a branch mid-`git merge --no-ff
--no-commit origin/main` had to clear a defect in an incoming `SKILL.md` before
`require-skill-review.sh` would let the merge commit through, and the `Edit` that
would fix it was denied — leaving a ceremonial review of an unrelated upstream plan
as the only way forward. Reproduced end to end in a throwaway repo: active set
empty, hash non-empty and equal to the sentinel oracle, verdict deny with no
`UNDETERMINED_BASE_NOTE` suffix.

Intended outcome: an empty active plan set disarms the plan-review gate whether or
not a trusted in-progress state is detected, with regression tests asserting the
hook's verdict (not just the primitive's output) across the merge and cherry-pick
arms, and the accepted residual recorded in a committed design-decision file. This
touches `claude/`, so the user surface is every stow consumer, not one machine.

## Approach

Delete the empty-active-set base binding from `_lib_active_plan_hash` so an empty active plan set returns empty stdout for any base, and drop the `require-plan-review.sh` fast-path conjunct that exists only to compensate for it. The gate then disarms whenever there is no plan to review, whether or not a trusted in-progress state is detected. The binding defends exactly one path — a forged base that reaches an admissible anchor — and that path is strictly dominated by a cheaper zero-gate bypass this repo has already accepted, so the binding buys no security while costing a recurring false re-review on the documented branch-sync workflow.

**Root problem.** `_lib_active_plan_hash` re-arms the plan-review gate on a plan set that is empty by construction, so a branch mid-sync is charged for reviewing a plan file it did not author.

**Givens** (fixed beyond this plan's reach):

- **G1 — `_lib_gate_diff_base` emits a non-empty base only for an in-progress state whose OID is an ancestor of `origin/<default>` or of `HEAD`** (`claude/.claude/hooks/_lib.sh:839-848`). The anchor set and its admissibility test are settled by a merged plan and `docs/design-decisions/merge-tree-base-recipe-for-gate-diff-base.md`; re-opening them is a separate design.
- **G2 — the clean-apply zero-gate bypass (residual 1) and the `bash -c`/`eval` wrapping bypass (residual 11) of `.claude/plans/merge-aware-review-gates.md` stay open.** Closing either needs a post-tool-call mechanism no hook in this layer has.
- **G3 — the write side (`marker.sh`) and the read side (`require-plan-review.sh`) must compute the plan preimage byte-for-byte identically**, or the gate wedges. `_lib.sh:453-460` states this as a load-bearing determinism contract, not a preference.
- **G4 — a completion marker's content *is* the authorization**, per `docs/hooks.md` § "Marker keying and gate-release authority". Decoupling authorization from the preimage would rewrite the mechanism all five marker kinds share.
- **G5 — this ships to every stow consumer.** `claude/` installs to anyone who runs `./install.sh`, so the user surface is every contributor, not this machine (repo `CLAUDE.md`, "Plans in this repo affect all stow users").

**Over-powered-primitive check.** M1 deletes a security binding, which is the widest-blast-radius form of this fix. Four lighter primitives were re-read for and rejected:

- **Option C — when the base-relative set is empty and the base is non-empty, recompute `_lib_active_plan_files "$repo" ""` and hash that HEAD-relative result** (`anchors: row5`). Fails: it re-arms the gate on exactly upstream's plan content, which is the defect the engineer reported, and converts a certain over-gate into a probabilistic one rather than removing it.
- **Scope the binding to `ExitPlanMode` and drop it for `Write`/`Edit`/`MultiEdit`** (`anchors: row7`). Fails: the binding lives in `_lib_active_plan_hash`, which `marker.sh:530` calls with no tool context, so a tool-conditional preimage makes the write side and read side compute different values for one state — a direct violation of G3.
- **Keep the binding and cheapen the release** — a dedicated `marker.sh` arm, or a deny message naming the exact release command (`anchors: row9`). Fails: the marker still attests possession of a base rather than review of anything, so it violates G4's own stated rule ("Matching a hash the subagent computed itself is not authorization"), and adding a release path to make an unearnable demand satisfiable is the compounding-defensive-layer tell, not a fix.
- **Narrow the binding to bases that reached no trusted anchor** (`anchors: row4`). Fails on a false premise: `_lib_gate_diff_base` returns empty for exactly those states (G1), so the narrowed binding would never fire and the deletion is its correct reduction.

**`test_require_plan_review.py` — `TestRequirePlanReviewEmptyActiveSetDisarms`:**

Mid-`git merge --no-ff --no-commit origin/main` where origin added a plan file the branch never touched: a `Write` to `src/unrelated.py` returns `allow` with no marker on disk. **This is the assertion whose absence let the bug ship** — the prior change's verification (`merge-aware-review-gates.md` line 337) asserted `_lib_active_plan_files` only.

- `test_conflicted_merge_with_untouched_upstream_plan_allows_unrelated_write` — the conflicted arm. The merge conflicts in a non-plan file while the incoming plan file stays unconflicted and base-matching, so `MERGE_HEAD` persists for the whole conflict-resolution window and the base stays non-empty across every `Write`/`Edit`. - `test_local_plan_edit_during_merge_still_denies` — the counter-assertion, parametrized over **both** the clean-merge and conflicted-merge fixtures, with a plan file the branch itself edited. A conflicted-cherry-pick or conflicted-revert fixture would re-test the product of two already-pinned axes.

**Clean-merge, conflicted-merge, and cherry-pick arms: in. Rebase and revert arms: out.** Mid-rebase, `REBASE_HEAD` ordinarily reaches no admissible anchor, so the base is empty and the state under repair is unreachable — the same claim with the same "in the ordinary case" hedge that `merge-aware-review-gates.md` residual 14 already records, cited rather than re-derived. Revert *can* reach the anchor (reverting an already-upstream commit makes `REVERT_HEAD` a trivial ancestor of `origin/<default>`), so it is declined as redundant with the cherry-pick arm rather than as unreachable — a fourth near-duplicate fixture with no discriminating power the cherry-pick arm does not already supply.

## Out of scope

Named residuals — each accepted, not overlooked, in the style `.claude/plans/merge-aware-review-gates.md` § "Out of scope" establishes.

1. **Option C is the pre-analyzed successor, not a rejected idea.** If the empty-active-set disarm ever needs tightening, the analyzed candidate is: when the base-relative active set is empty and the base is non-empty, recompute `_lib_active_plan_files "$repo" ""` and hash that HEAD-relative result. It is declined today because it converts a guaranteed over-gate into a probabilistic one and partially re-charges the merger for upstream's plan content. **Reopening criterion:** not accumulated annoyance, but the same trigger `merge-aware-review-gates.md` residual 14 already names for its own declines — residual 1 (clean-apply zero-gate) or residual 11 (`bash -c`/`eval` wrapping) being closed. While either stands, the forged-anchor path this plan stops defending remains dominated and Option C buys nothing.
2. **`marker.sh write plan-review` writes a newline-only marker when the hash is empty.** `marker.sh:536-537` has no emptiness guard; the fix makes that reachable in one further state (mid-merge with an empty active set) but does not introduce it — the base-empty, nothing-active case already reaches it today. Harmless as written: `require-plan-review.sh:248-250` exits before any marker read, and `_status_report_completion_marker` guards `[ -n "$current_value" ]` (`marker.sh:243`), so no reader ever matches an empty expected value. Adding the guard is a write-arm behavior change with its own test surface.
3. **`marker.sh status`'s plan-review arm gets no sentinel-exclusion step, and now needs none.** Code-review's arm excludes its sentinel at `marker.sh:785-790`; the plan-review arm at `:811` never had the analogue. The fix dissolves the need rather than leaving a gap — `_lib_active_plan_hash` returns empty and `_status_report_completion_marker` already treats empty as absent/historical. Recorded so a symmetry sweep does not add a now-meaningless exclusion.
4. **`_lib_reviewer_round_state_value` is not touched.** Its base threading concerns the staged diff, not the plan-set enumeration, and the round-3 gate's rebase disarm (`merge-aware-review-gates.md` residual 18) is unchanged in either direction by this plan.
5. **`marker.sh:511-519`'s "trusted-base preimage" comment is left as written** (row 14). Its claim — that the write side threads the same base the read side resolves — stays true, so editing it would be scope creep on a comment that is not false.
6. **`claude/.claude/tests/helpers.py` is not edited** (row 11). `write_plan_review_marker`'s written content is unchanged for every existing call site, and touching the file would force a full-suite run for no behavioral need.
7. **`plan-review`'s own no-subject behavior is not changed.** After this fix the gate no longer compels an invocation with no active plan, but a user can still invoke `/plan-review` there and Step 1's rule 2 will still select whatever plan is most recent in `.claude/plans/`. Giving the skill a "no plan to review" branch is a `SKILL.md` change carrying its own hook-enforced `/skill-review`.
8. **No `merge-aware-review-gates.md` decline is re-run** (row 9). Residual 14's reopening criterion fires on a bypass being closed; this plan relies on residual 1 continuing to exist rather than closing it.
9. **`docs/hooks.md` and `claude-skills/skills/plan-review/` are not edited** (row 15). Neither documents the binding, and `docs/hooks.md:164`'s description of the gate becomes strictly more accurate after the fix.
10. **Plan-review friction disappears for the whole conflict-resolution window of a trusted in-progress state whose plan file is base-matching** (row 9). Where the operation conflicts in some file other than the plan file, git cannot auto-commit, so the in-progress ref persists and the base stays non-empty across every `Write`/`Edit` — residual 1's zero-gate auto-commit is structurally unavailable there. Pre-fix each of those calls was denied and releasable only by a `/plan-review` pass; post-fix all proceed freely. Accepted for two reasons. The honest case is the bug itself: a conflicted sync carrying an upstream plan is exactly the over-gate this plan removes, and it is the more common shape, not an edge. The adversarial case is not a new capability: a forger who can set the anchor also chooses the merge's shape, and the clean variant is strictly better for them — it auto-commits with zero gates and leaves the forged plan permanently historical. What is genuinely lost is friction on the intervening calls, not a control over the plan file's content, which neither gate ever reviewed in this state before or after. **Row 24's audit-trail caveat does not transfer.** That row keeps its own dominance argument narrow because an adversary optimizing for a history that reads as genuine might still prefer the conflicted forgery, which leaves a passed marker and a compliance-log line the clean bypass does not. `require-code-review.sh` writes such a log; `require-plan-review.sh` writes none, and post-fix this substate exits at `:248-250` before any marker is read — so the conflicted path leaves no marker and no log either, and the asymmetry that makes row 24's caveat bite has nothing to bite on here. Named rather than denied, in the style `merge-aware-review-gates.md` row 24 uses for the same shape on the sibling code-review gate, and pinned by `test_conflicted_merge_with_untouched_upstream_plan_allows_unrelated_write` rather than left to prose.
11. **A plan-review marker written by the pre-fix code survives the `git pull` that lands this change, and becomes inert rather than dangerous.** `claude/.claude/hooks/**` goes live on pull with no re-install, so old-format markers (`sha256("plan-review-empty-base:$base")`) persist in `~/.claude/plan-review-markers/`. Such a marker cannot wrongly release: post-fix the same state yields `CURRENT_HASH=""` and `require-plan-review.sh:248-250` exits allow before any marker lookup. It cannot wedge, for the same reason. It cannot collide with a future write: the surviving branch hashes `path\nfilehash\n` per active file, a disjoint preimage space from the sentinel literal. The only visible residue is cosmetic — `marker.sh status` reports "historical" rather than "absent" for a repo holding only a stale marker, since `_status_glob_has_match` matches on existence. Recorded because no worked example of this rollout question exists yet, and this will not be the last `_lib.sh` preimage-format change shipped the same way.

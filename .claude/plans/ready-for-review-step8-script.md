# Script /ready-for-review step 8's body guard and title derivation

## Context

Goal: move the non-judgment parts of `/ready-for-review` step 8 (the body-file guard and the PR title derivation) out of SKILL.md prose and into one tested stdlib Python script, as `plan-shape.py` did for `/plan-it` Step 5 (PR #1323).

Origin: workstream 2 of the handoff `workstream2-scriptable-skill-steps-handoff.md`, starting with the step 8 body guard and title derivation. Over-length answer: "Truncate at word boundary (Recommended)".

## Approach

Add one stdlib Python script, `claude/.claude/scripts/pr-create-preflight.py`, with two modes. `ticket` runs in step 1 and prints the branch's `<TICKET-ID>` for step 5. `create '<path>'` prints the PR title and exits nonzero on any stop. Before printing, it holds the title and the body path as the script receives it (row 33) to one sink rule that admits only plain shell words, and checks that the file is a regular file holding more than whitespace, the check today's guard makes, with a NUL difference M6 names. Step 8 runs `create` once to learn the title, then opens the PR with `python3 ~/.claude/scripts/pr-create-preflight.py create '<path>' && gh pr create --title "<title>" --body-file <path>` as one Bash call. So a failed check still ends the create call before `gh pr create` runs, as today's guard does, and retrying that call re-runs the check. The gates that read that call and the hook tests that extract its `gh pr create --title` span stay unchanged. Steps 1 and 8 keep only when to run each mode and how to read its output. The module docstring owns the branch, TICKET-ID, slug, title, sink and body rules.

Script contract. The docstring states each rule, and they are listed here so review can test them:
- Usage: `pr-create-preflight.py ticket` or `pr-create-preflight.py create <body path>`. Any other argument list, `-h` and `--help` included, prints one `REASON: usage: ...` line and exits 2.
- Branch: read with `git symbolic-ref --quiet HEAD`. A nonzero exit or a ref outside `refs/heads/` stops with `not-on-branch` in both modes. A git that cannot start raises, so the run ends as `internal-error`.
- TICKET-ID: the branch's text before its first `/` (the whole name when it has no `/`), when that text fully matches `[A-Za-z]+-[0-9]+` under `re.fullmatch` with no flags, so only ASCII letters and digits match. Otherwise there is none, printed as `none`. By construction the value holds only ASCII letters, digits and one `-`, so it gets no sink check.
- Slug: the branch's text after its last `/` (the whole name when it has no `/`). Its words are its `-`-separated pieces with empty pieces dropped, so repeated, leading and trailing hyphens add no space.
- Title: empty when the slug has no words. Otherwise `<TICKET-ID>: ` followed by the slug's words joined by single spaces, or the words alone when there is no TICKET-ID.
- Over 70 characters: the title keeps the longest leading run of words that fits in 70 characters with its prefix. When even the first word does not fit, the title is the untruncated title's first 70 characters with trailing spaces removed. The count is in characters. The sink rule admits only ASCII, so in every printed title a character is a byte, and the docstring says so.
- Sink rule: `create` holds the two values the session copies into the `gh pr create` call to one rule. A value passes when it fully matches its pattern under `re.fullmatch`: `[A-Za-z0-9._: -]+` for the title and `/[A-Za-z0-9._/-]*` for the body path. A value that fails stops with `not-plain-word`. The rule judges the title as it would print, after truncation, and the `TITLE` line is built in one place, from a title that passed. The patterns carry no position rule, because no member ends or expands a shell word wherever it sits and no title rule can start a title with `-` or a space. The `+` alone refuses the empty title. One docstring line gives the why: these characters neither end nor expand a word inside the double-quoted `--title` argument or the bare `--body-file` word.
- `create` conditions, checked in this order, with the first failure ending evaluation:
  - `not-on-branch`, as above.
  - `not-plain-word` for the title. A slug with no words, as in `topic/---`, lands here, so it needs no code of its own.
  - `not-plain-word` for the body path, before any file access.
  - `body-unreadable`: `os.stat` on the path finds a file that is not regular, or the `stat`, the open or the read raises `OSError`. One `try` around all three maps any `OSError` to this code. `os.stat` follows a symlink, as `[ -f ]` does (row 39). A missing path, a directory, a FIFO and a device are refused, and a FIFO before any open, so nothing blocks.
  - `body-empty`: the file, read whole, holds no byte outside `_BODY_WHITESPACE`, the six bytes space, tab, LF, VT, FF and CR.
- Output: one write after the decision. `ticket` prints `TICKET_ID: <id>` or `TICKET_ID: none`. `create` prints `TITLE: <title>`. A stop prints one `REASON: <code>: <sentence>` line instead, never alongside a value line. Keys: `TICKET_ID`, `TITLE`, `REASON`. Codes: `usage`, `internal-error`, `not-on-branch`, `not-plain-word`, `body-unreadable`, `body-empty`. Every REASON sentence is fixed text, so none echoes branch, path or body characters. `not-plain-word` has two fixed sentences. The title's says the title "is empty or holds a character outside" its set and names the set, so an empty title, as from `topic/---`, does not send the engineer hunting for a bad character. The path's says the path "is not absolute or holds a character outside" its set and names the set, so a relative or empty path does not either. The docstring carries `Keys:` and `Reason codes:` lines in `plan-shape.py`'s form.
- Exit: 0 only when a value line prints. 3 on a stop. 1 on an unexpected exception, printing only `REASON: internal-error: <exception type name>`. 2 on usage. One docstring line gives the why for 3: a stop must end a `&&` chain before `gh pr create` runs. Nothing goes to stderr while stdout is writable, and git's stderr is captured, never relayed.

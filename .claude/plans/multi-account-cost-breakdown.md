# Multi-account cost breakdown: per-account token-class/model mix, cost-trend --config-dir

## Context

Close two verified gaps in `transcript-analysis.py`'s cost tooling so an engineer running multiple Claude accounts on one machine can see which token class, which model, and which week drives spend on each account individually — not just summed across every scanned account.

`cost --config-dir` (repeatable, multi-root — added in PR #607) already sums token-class and model-ID dollars across every scanned root into one combined table; there is no per-account breakout of *how* an account spends, only `--by-project`'s per-(account, project) *total* dollars. Verified this session: ran `cost --config-dir <a> --config-dir <b> --since 30d --by-project` and confirmed the token-class and model-ID sections stay combined-across-roots while `--by-project` tracks only a single total-dollar figure per group, no token-class/model split. Separately, `cost-trend` (per-ISO-week spend/Opus-share/`>=200k`-share trend) has no `--config-dir` flag at all — confirmed via `cost-trend --help`, which lists only `--projects`/`--this-repo`.

## Approach

**Root problem:** an engineer with N Claude accounts on one machine can already see combined multi-account cost totals (`cost --config-dir`) and combined multi-account agent-type dollars (`subagent-mix --config-dir`, PR #621), but cannot see *per-account* token-class/model composition, nor a *per-account-capable* week-over-week trend — both of which already exist in single-account form.

**Givens** (conditions this plan treats as fixed):
- `docs/cost-ledger.md`'s row schema (`(week, machine)` key, no account dimension) stays as-is this plan. [reason: engineer decision — see AskUserQuestion below] [engineer-verified]
- `cost`'s per-account breakdown auto-prints under multi-root with no new flag, matching `edit-format`'s existing precedent. [reason: engineer decision] [engineer-verified]

`_redaction_ordinals(roots)` is *not* listed as a given: it is inside this same file, reachable by this plan, not a platform boundary. Both mechanisms deliberately keep it as the sole source of "account-N" labeling rather than changing it — recorded under Out of scope with its reason (plan-review flagged the prior "out of reach" framing as unjustified; this is a discretionary choice, not a fixed boundary).

### Mechanism 1 — `cost`: per-account token-class + model-ID breakdown

Add a `per_account: dict[int, dict]` accumulator to `_cost_report`, keyed by `_redaction_ordinals` ordinal — the identical shape `edit-format` already uses (`transcript-analysis.py:6350-6360` [verified: read this session]). Each entry holds the same three structures the existing global accumulators use: `class_totals` (`dict.fromkeys(_TOKEN_CLASSES, 0.0)`), `class_token_totals` (`dict.fromkeys(_TOKEN_CLASSES, 0)`), and `model_totals` (`defaultdict(float)`) — see `transcript-analysis.py:5606-5608` [verified: read this session] for the existing global versions to mirror.

Unlike `edit-format`, which merges per-session batch stats (`_merge_edit_format_stats`, session-granularity), `cost`'s existing loop accumulates per-*turn* directly into flat dicts (`transcript-analysis.py:5667-5671` [verified: read this session]: `class_totals[cls] += dollars_by_class[cls]`, `model_totals[model] += turn_total`). The per-account accumulation must happen at this same per-turn point — not session-level — using each turn's already-resolved account ordinal. `--by-project`'s existing per-session `root_component` (`scoped_label[0]` when `multi_root`, computed at `transcript-analysis.py:5714-5716` [verified: read this session]) is exactly this ordinal, but it is currently computed only inside `if by_project:`; hoist that resolution (or an equivalent read of `redact_ordinals[resolved_scan_roots[_root_index_for_path(...)]]`, the same call edit-format makes at `6357-6359`) to run unconditionally under `multi_root` so it's available regardless of `--by-project`.

Extract the two existing inline print blocks — "Cost by token class" (`5781-5787`) and "Cost by model ID" (`5789-5792`, excluding the unpriced-tokens tail which stays global-only) [verified: read this session] — into two small helper functions (`_print_token_class_table(class_totals, class_token_totals, grand_total)`, `_print_model_id_table(model_totals, grand_total)`). Call each once for the existing global total (unchanged output) and once per account ordinal (new), under a `## Cost by account` section gated on `multi_root`, mirroring `edit-format`'s `if per_account is not None:` gate (`6433`) and one-block-per-`account-{ordinal}` loop shape (`6435-6436`) [verified: read this session]. This refactor is in-file scope (Axis 2 — reusing existing logic, not adding a parallel formatter) and is the direct enabler of the reuse: without it, the per-account tables would duplicate the print logic instead of calling it twice.

Two cross-check `AssertionError`s already guard `_cost_report`'s bucketing (main+subagent == grand total, per-project rows == grand total; `5734-5748` [verified: read this session]) — add a third: summed per-account `class_totals`/`model_totals` == the global totals, same defensive pattern, so a future edit to the accumulation point can't silently drop a turn from the per-account view without breaking a test.

The new accumulation point is unreachable under `--summary`: that mode already refuses `--config-dir` outright (`5505-5515` [verified: read this session]), so `multi_root` and `summary_mode` can never both be true at the point the per-account accumulator runs — state this explicitly at the accumulation site as a one-line comment, so a future relaxation of `--summary`'s refusal list doesn't silently make the combination reachable with no guard.

**Consumer check:** grepped this repo for `transcript-analysis.py cost` call sites — `claude/.claude/skills/pr-description/SKILL.md` is the one real external consumer of `cost`'s stdout shape, and it invokes `cost --summary`, which per the above can never reach the new section. No consumer breaks. `docs/cost-ledger.md`'s `--record` path uses `_resolve_scan_roots`/`_compute_cost_trend_data`, not `_cost_report` at all — confirmed unaffected. [verified: this session]

### Mechanism 2 — `cost-trend`: add `--config-dir`

`cost-trend`'s parser (`transcript-analysis.py:9158-9163` [verified: read this session]) only wires `_add_project_scope_args` (`--projects`/`--this-repo`). Its dispatch, `_cost_trend_report` (`7095-7137`), resolves roots via the generic `_resolve_scan_roots(args)` — a different function from `cost`'s `_resolve_cost_roots(args, subcommand=...)`, which is the one that understands a repeatable `--config-dir`/`extra_config_dirs` (`5232-5292` [verified: read this session]).

Three changes, mirroring `cost`'s own argparse block (`9006-9058` [verified: read this session]) exactly:
1. Add `p_cost_trend.add_argument("--config-dir", action="append", dest="extra_config_dirs", metavar="DIR", help=...)` — same help text convention as `cost`'s.
2. Switch `_cost_trend_report`'s root resolution from `_resolve_scan_roots(args)` to `_resolve_cost_roots(args, subcommand="cost-trend")`.
3. Add `"cost-trend"` to `_SUBCOMMANDS_WITH_OWN_CONFIG_DIR` (`5227-5229` [verified: read this session]) so `main()`'s top-level `--config-dir` refusal (`9296-9310`, confirmed present this session) correctly fires for `cost-trend` too — without this, the top-level flag and the new subcommand-level flag could both validate against two different accounts silently.
4. Add the same per-root scan diagnostic `cost` already prints when scanning multiple roots (`_cost_report`'s "WARNING: … no transcripts found for this scope" and "scanning root N/M" lines, `5561-5587` [verified: read this session]) to `_cost_trend_report`. `_cost_trend_report` today only reports "No priced turns found" when the *combined* multi-root dataset is empty (`7116-7120`) — with no per-root visibility, a stale or misconfigured `--config-dir` silently contributes nothing to the weekly trend with no signal. Since this plan's own framing is "mirror `cost`'s argparse block exactly," shipping without this diagnostic would be an inconsistent subset of that parity claim, not a smaller version of it.

`cost-trend` carries no `--no-redact` flag today and its output contains no project-identifying field (`week`/`$`/`Context%`/`Opus%` only, `7125-7134` [verified: read this session]) — switching to `_resolve_cost_roots` pulls in that function's `--no-redact`-refused-when-multi-root check (`5284-5290`) regardless, but it degrades to an unreachable branch (`getattr(args, "no_redact", False)` stays `False` with no such flag in the namespace) rather than a live check. Not a defect — noting it so a future `--no-redact` addition to `cost-trend` doesn't ship without deliberately deciding whether that refusal should actually apply, given `cost-trend`'s rows have nothing to redact today.

This closes the gap as a **combined-across-accounts** trend (the existing single weekly table, now summed over every `--config-dir` root) — not a per-account-per-week matrix. A week × account breakdown is a legitimate follow-on but adds real complexity (2D table, redaction-label interaction with a time axis) that wasn't part of the verified gap (`cost-trend --help` showing no `--config-dir` at all); recorded under Out of scope.

`cost-ledger` is explicitly **not** touched by this plan — [engineer-verified] this session. Its schema documents a row as "one row per week per machine" (`docs/cost-ledger.md` [verified: read this session]), with `machine` disambiguating physically distinct machines merged via git; no account dimension exists. Wiring `--config-dir` into `--record` would either silently blend N accounts' spend into one `(week, machine)` row (an undocumented semantic shift of what `machine` means) or require a schema change to a committed, append-only file with existing rows — both out of scope for this plan per the engineer's explicit choice.

### Alternatives considered

- **A new `--by-account` flag for `cost`** instead of auto-print under `multi_root`: rejected per engineer's explicit choice — inconsistent with `edit-format`'s existing precedent, and `cost`'s own `--by-project` section already auto-appears once requested rather than needing a second multi-root-specific flag.
- **`read-scope`'s raw-scan-order `per_account: list[dict]`** (`6872`, indexed by `_root_index_for_path`'s position, not `_redaction_ordinals`) as the template instead of `edit-format`'s: rejected — flagged this session as a real existing inconsistency (its account-N label can shift depending on which profile is currently active), not a pattern to propagate. `edit-format`'s ordinal-keyed `dict[int, dict]` is the convention every other per-account site in the file already commits to.

## Out of scope

- Changing `_redaction_ordinals` as the sole source of "account-N" labeling — reachable by this plan (same file, same repo), not attempted because it would silently renumber every other subcommand's existing account-N output (`cost`'s `--by-project`, `edit-format`, `read-scope`, `subagent-mix`). A discretionary choice to preserve compatibility, not a fixed boundary — reclassified here per plan-review (was previously listed as a "given," which the review correctly flagged as unjustified since the condition is reachable).
- `cost-ledger --record` gaining `--config-dir` or any account dimension in its schema — engineer's explicit choice this session, given the semantic-mismatch risk with the documented `(week, machine)` row contract.
- A per-account-per-week trend matrix for `cost-trend` (as opposed to a combined-across-accounts trend) — not part of the verified gap; would need its own design pass on table shape and redaction-label interaction with a time axis.
- Fixing the pre-existing test-coverage gap noted this session where `TestConfigDirFlag`'s parametrized refusal test (`327-420+`, `test_top_level_config_dir_refused_for_subcommands_with_their_own`) omits `"edit-format"` from its subcommand list despite `edit-format` being in `_SUBCOMMANDS_WITH_OWN_CONFIG_DIR` — unrelated pre-existing gap, flagged for awareness only, not fixed here per file-boundary scope discipline.

# Memory file audit

## Context

The engineer's persistent auto-memory store (`<config-dir>/projects/<this-repo-project-dir>/memory/`, 8 individual memory files plus a `MEMORY.md` index) is consuming 13.7k tokens per session load — far more than a lesson-recall store should cost. Several of these memories document facts that either (a) belong in a skill/hook/doc as their durable, single-source-of-truth home, since the memory is really an unfixed bug or an unrecorded fact about existing code, or (b) are already fully or mostly duplicated by documentation that already exists in the repo. The intended outcome is a slimmed-down memory store where each surviving memory earns its place (genuine, non-repo-representable, ongoing personal-machine state), and every other lesson has been migrated to its correct durable home (a skill fix, a doc addition, or a `/brief` file for a future session to root-cause).

# Approach

## Concluded design

Seven of the eight memory files in this repository's auto-memory store are retired: five have their lesson relocated to the one durable home that already owns that subject (one skill body, three doc sections, one README paragraph), one is deleted with no migration because the repo already states its fact, and one unresolved bug is scoped into a gitignored `/brief` continuity file for a future root-cause session rather than being papered over with a doc note. The eighth (`otel-raw-body-capture-needs-pruning`) stays, because gitignored per-machine runtime state has no repo-representable home. The work therefore splits along a hard boundary: five prose edits inside the git repository, and four file operations outside it (seven deletions, one index prune, one brief) that no `code-writer` dispatch can perform.

The session's settled design holds on all eight files. Three adjustments are folded in, each with its own reason below.

**Adjustment 1 — the `error-mode-analysis` Step 6 rewrite must preserve the leak-prevention property it currently states, not drop it.** The settled design says "instruct scrubbing a copy of Artifact A instead of authoring fresh." Step 6's present wording is not arbitrary: it carries an explicit security rationale ("a redaction pass that misses one span leaks it"), and Step 5 records that outside `claude-config` the manual scrub is the *only* defense against structural fingerprints. Flipping the instruction without carrying that property forward would trade a real leak control for fidelity. The fix instead makes the derivation explicit *and* names Step 5's already-mandatory line-by-line diff as the release gate for the derived copy — Step 5 already says "Do not commit or push Artifact B until the checklist above has been walked and the document has been diffed line by line," and already describes Artifact B as "Scrubbed of project-identifying content," which presumes derivation from something that contained the private span. So today's Step 6 contradicts its own Step 5; the rewrite removes an internal inconsistency rather than creating one, and that is a stronger justification than the fidelity report alone.

**Adjustment 2 — the handoff-nudge baseline gets its own Known-limitations bullet, not an append to the existing toolless-turn bullet.** These are two different claims. The existing bullet is about *hard-block escalation* never firing when growth happens on toolless turns. The memory's 5-of-137 figure measures *advisory-nudge coverage* lost by retiring the `UserPromptSubmit` registration. Appending the number to that bullet would attribute a measurement to a gap it does not measure. The new bullet is placed immediately after it so both toolless-turn facts sit together without being conflated. The migrated re-evaluation procedure also needs one correction: the log lines carry no timestamp field (`nudge-handoff-near-context-cap.sh` writes `nudged session=… est=… model=… window=… event=…` with no date), so "entries after the merge commit timestamp" is not executable against the log — the slice boundary is the first `event=PostToolBatch` line in the append-only file.

**Adjustment 3 — one scan-surface paragraph is added to `docs/private-project-redaction.md`, which the settled design did not include.** The settled design deletes the redaction-gate memory on the grounds that `chain_split_hint_if_chained()` already delivers the lesson live. That is true for the *remedy* — the hint fires on every deny whose command text contains `&&`/`||` and tells the reader to split the chain — but it fires only after a denial, and it never states the underlying *fact*: that the gate's scan target includes the invoking Bash command's own text, not only the staged diff and message. That fact has no home today; the doc `CLAUDE.md` names for "match semantics" contains no occurrence of the words "command," "Bash," or "chain." One paragraph closes an undocumented behavior at zero per-session context cost, which is precisely this plan's own routing principle. Set against it: the memory itself records three recurrences *despite* existing, which is why the preventive habit is not being re-homed anywhere that costs per-session load.

The marker.sh silent-chaining bug and its two sibling reproductions get no doc note at all. Publishing "chains are permitted, but one has been observed not to take effect" into a public doc, with no root cause and against a shape rule the same doc states, is a contradiction with n=1 — the `/brief` exists to resolve it first.

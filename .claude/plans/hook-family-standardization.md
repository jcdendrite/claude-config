# Hook-family standardization

## Context

Standardize `claude/.claude/hooks/*.sh` (43 hooks + one shared `_lib.sh`). This closes GH-783 Phase 2 (8 hooks still doing raw-regex command matching without the fail-closed quote-stripping idiom GH-783 Phase 1 established) and the duplicated-logic/inconsistency gaps a full structural audit found this session. It's phased so the 44-file scope doesn't become an unbounded catch-all for every related reviewer finding — a risk the engineer named explicitly up front, after past sessions lost time exactly that way.

Why now: GH-783 Phase 1 (fragment-matcher quote-split bypass, 9 hooks) just merged (PR #806, commit `d4d9904`). Phase 2 was deliberately deferred from that PR, and a parallel structural audit this session found the same foundational inconsistency (duplicated parsing/dispatch/formatting logic) is the root cause behind a long tail of open GitHub issues — the engineer wants one coherent effort closing that root cause, not another one-off patch.

Intended outcome: a phased plan (each phase an independently-mergeable PR) that (1) closes GH-783 Phase 2 via two new composed `_lib.sh` command-matcher helpers rather than 8 independent regex conversions, (2) collapses the highest-value duplicated logic found in the audit (a near-duplicate hook pair, uncapped secondary `jq` calls across 19 hooks, a 4-template deny-message inconsistency), and (3) explicitly defers the items that need their own decision session (an `_lib_repo_root` extraction blocked on a separate in-progress issue, an `_lib.sh` file-cohesion reorg, a settings.json dispatch-mechanism question already resolved empirically this session) rather than silently absorbing or silently dropping them.

**Phase 0 — resolved empirically this session, no further work.** A real contradiction existed between `require-code-review.sh`'s header comment (and 3 other hooks') claiming `settings.json`'s `if: "Bash(git commit *)"` predicate fires on all Bash commands, and `test_check_claude_md_length.py`'s docstring (~line 568-572) claiming the opposite. Two live commit probes in this worktree confirmed the `if` glob **does** match chained/prefixed commands: a `true && git commit ...` with a real unreviewed staged diff got a genuine deny from `require-code-review.sh`; an empty-diff variant was allowed only via that hook's own documented empty-diff exemption, not because the hook was never dispatched. Consequence: GH-783 Phase 2's regex hardening is live code for all 8 hooks, no `settings.json` `if`-condition removal is needed as a precondition, and the stale test docstring is corrected in Phase 1 below.

## Approach

Close GH-783 Phase 2 by adding **two composed command-matcher helpers** to `_lib.sh` and pointing all eight raw-regex gate hooks at them, then collapse the highest-value duplicated logic behind those helpers in three further phases — a shared staged-length-gate driver, a grouped small-defect pass, and one mass-mechanical pass folding the payload-parsing and deny-message duplication into `_lib.sh`. Repo-wide conformance tests land last, once the surface they assert over actually conforms. Every phase is an independently-reviewable PR against a fixed, ordered dependency chain (1 → 2 → {3a, 3b, 3c} → 4 → 5 — see Verification's "Phase ordering and independence"), each with an explicit file list and an explicit closes-list; nothing enters a phase that the phase's own file list does not already open.

**Two corrections to the originally-proposed single-helper design, both from reading the code.**

*The gh-family hooks cannot use the git matcher, and naive quote-stripping regresses them.* `block-gh-pr-merge.sh:65` documents that its regex deliberately **rejects** `echo "gh pr merge"` — "gh preceded by `"`". Swapping `$COMMAND` for a quote-stripped copy under the same regex turns that documented allow into a false deny, because the regex's exclusion mechanism is the literal quote character. The correct shape for the four gh-family hooks is fragment-plus-command-word matching, not strip-and-regrep: `_lib_fragment_command_word` resolves a fragment's *first word only*, after stripping. On the stripped fragment `echo gh pr merge`, command-word extraction resolves to `echo`, not `gh` — the exclusion survives because `gh` is never the fragment's first word once stripped, not because a quote character is preserved (`_lib_fragment_command_word` is itself quote-blind, per its own docstring at `_lib.sh:686-690`, which is exactly why the fragment must be stripped first). This design is actually stronger than the current regex: it also closes a real, currently-open gap `docs/hooks.md:30` records — `gh pr "merge"` (a genuine invocation the current regex misses due to a quote mid-command) — once the fragment is stripped before word-walking. So Phase 1 ships **two** helpers, not one.

*`deny-escaped-backticks-in-pr-body.sh:92`'s `SCAN_TARGET` is not the gap it was described as.* That hook's sole detector is `grep -qF -- '\`'` at line 118 — the literal two-character backslash-backtick sequence. `_lib_strip_shell_quotes` (`_lib.sh:1459`) runs `s/\\(.)/\1/g`, which *deletes* backslashes. A `SCAN_TARGET_BOTH` union would add a stripped copy from which the very character being detected has been removed. No input was found where the stripped half matches and the raw half does not (it requires stripping to newly juxtapose a backslash and a backtick; every candidate already matched raw). Recommendation: **leave `:92` unchanged** and record why. The genuine Phase 2 gap in that file is `:54`'s raw-`$COMMAND` `IS_GH_PR` dispatch, where `"gh" pr create` bypasses the entire gate.

**Two ordering defects in the original design, which placed both new conformance tests in Phase 1.** The "no bare `jq` outside a `_lib_*` wrapper" conformance test cannot pass there — 19 hooks violate it until GH-489 lands. And the "no bare `grep -qE` matching a subcommand outside `_lib_*`" test will fire on sites Phase 1 does not convert (`enforce-marker-script-shape.sh:572`'s raw-`$COMMAND` `marker.sh` grep; `require-stow-reminder.sh:188`'s `--fill` flag grep), forcing an allowlist written under merge pressure. Both tests move to the final phase, where the allowlist is derived from what actually remains rather than guessed. Phase 1 instead ships targeted per-hook quote-split characterization tests, the same shape the merged Phase 1 PR already established.

**One rejection of a heavier primitive.** The originally-proposed Phase 3 merges `check-skill-length.sh` and `check-claude-md-length.sh` into one hook file. Recommend against it: extract the shared body into `_lib.sh` as a driver and keep both hook files as thin callers. The merge would change `settings.json`'s hook roster, `test_hook_alignment.py`'s `ALL_HOOKS`, and both test files' subjects, and would put two independently-owned policies (Anthropic's documented 500-line skill ceiling with per-skill overrides; a flat 200 for CLAUDE.md/AGENTS.md) behind one gate. The driver extraction collapses the identical logic with none of that. The callback-by-convention shape it needs — caller defines `limit_for` before calling the driver — is already the repo's established pattern: `_lib_parse_tool_input_or_deny` resolves a caller-defined `emit_deny` at call time, and `test_hook_alignment.py` enforces that contract.

### Assumption ledger

**Root problem.** Eight gate hooks match command text with raw regexes over unstripped `$COMMAND`, which a quote-split (`"git" commit`) defeats — and the same command-parsing, payload-parsing, and deny-message logic is hand-copied across 43 hooks rather than living in `_lib.sh`, so each newly-found gap must be fixed between 5 and 19 times.

**Givens** (fixed beyond this plan's reach):

- **G1.** `_lib_strip_shell_quotes`'s residuals — multi-character ANSI-C escapes (`$'\x67\x69\x74'`) and backslash-newline continuation — stay open. `docs/security-hardening.md:720-739` records both as confirmed exploitable and defers them; the merged Phase 1 plan explicitly inherited that boundary rather than moving it.
- **G2.** Variable expansion and command substitution as indirection vectors (`CMD=git; $CMD commit`) stay accepted. Canonicalizing through bash would execute attacker-controlled text inside a security hook — rejected in-repo at `docs/security-hardening.md:726-728`.
- **G3.** GH-499's `.cwd`-versus-`$PWD` resolution semantics are owned by a separate in-progress branch (`.claude/worktrees/GH-499/gate-effective-cwd`). No phase here may freeze an answer to it.
- **G4.** `python3` is unavailable on a documented machine class (`docs/design-decisions.md` §32, cited at `require-worktree-for-git-writes.sh:148-153`), so no new matcher may depend on it — this is why `parse-git-command.py` is not the reuse target.

`_lib.sh` staying a single file is deliberately **not** listed as a given: every reason for it (stow's symlinking, `test_hook_alignment.py`'s exclusion, `test_lib.py`'s fixed path, per-consumer bootstrap) is an editable in-repo artifact, not an external party's constraint — so it belongs in Out of scope as a declined change, per the plan-review foundation check.

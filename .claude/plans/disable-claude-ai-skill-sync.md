# Disable claude.ai skill sync by default

## Context

Disable Claude Code's claude.ai→Claude-Code skill-sync feature repo-wide, because the engineer manages skills canonically in `claude-config` and manually copies them to claude.ai — the sync-back direction only duplicates skills this repo already holds, and syncing is on by default for every account once logged in via `/login`. This was surfaced in a private client-project session (a different account than this repo), but the fix belongs here: that account's `~/.claude/settings.json` is a stow symlink into this repo's `claude/.claude/settings.json`, so one edit here reaches every stowed account.

## Approach

Add a single top-level `"syncClaudeAiSkills": false` to the stowed user-scope `claude/.claude/settings.json`, which every stowed account and every stow consumer resolves through their `~/.claude/settings.json` symlink. Because that one line silently relocates a consumer's already-synced skills into `~/.claude/skills/.trash/`, ship it with a `docs/design-decisions/` entry recording the flip and the recovery path, a one-sentence pointer from `docs/skills.md`, and a `CHANGELOG.md` entry with a Migration note — matching this repo's own convention for the two prior shared-settings-default flips, both of which shipped all three. Pin the declared value with a unit test in `test_hook_alignment.py`, mirroring four existing sibling tests of the identical shape for other settings keys in the same file, so a later edit can't silently drop the key with no automated signal.

There is no competing implementation: the key name, its boolean semantics, and the `.trash/` relocation are fixed by Claude Code, so the only real design questions are scope (which settings file) and blast-radius documentation. Both are settled below.

**Assumption ledger**

**Root:** Claude Code's claude.ai skill sync injects skills into `~/.claude/skills/synced/` that duplicate the skills this repo already holds canonically, and it is on by default for every stowed account.

**Givens** (fixed beyond this design's reach):

- **G1 — The key name `syncClaudeAiSkills`, its boolean semantics, and the move-to-`.trash/` behavior on flip are vendor-imposed.** Claude Code defines them; this plan can only set the value, not choose the mechanism.
- **G2 — Sync is on by default when logged in via `/login`.** A vendor default; the design can override it but cannot remove the feature.
- **G3 — `~/.claude/settings.json` is a stow symlink into `claude/.claude/settings.json`, so one edit reaches every stowed account and every stow consumer.** The stow layout is the repo's install design; dissolving this change's dependence on it would be a decision outside this plan.

**Mechanisms**

- **M1 — `"syncClaudeAiSkills": false` in `claude/.claude/settings.json`.** The only file that reaches every account's session unconditionally, which is exactly the root's scope. `anchors: root`
- **M2 — A new `docs/design-decisions/claude-ai-skill-sync-disabled-by-default.md`.** The flip's consumer-visible side effect (row 2) needs a durable home a commit message cannot provide, and this is where the repo's two prior settings-default flips recorded the same class of change. `anchors: row2, row6`
- **M3 — One sentence in `docs/skills.md` pointing at M2.** `docs/skills.md` already collects the settings levers that affect skills, so it is the matched altitude for a consumer whose synced skills vanished — a reference, not a second copy of the rationale. `anchors: row2`
- **M4 — A `CHANGELOG.md` "### Changed" entry with a Migration note.** `CHANGELOG.md`, not `docs/design-decisions/` or `docs/skills.md`, is the artifact a consumer skimming "what changed" after `git pull` actually encounters; both prior shared-settings-default flips cited in row 6 shipped one (`CHANGELOG.md` lines 29, 43), and this plan's M2+M3 pair alone would be strictly weaker warning than that established convention for an identical change class. `anchors: row6, row12`
- **M5 — A declared-state unit test in `claude/.claude/hooks/tests/test_hook_alignment.py`.** `select-tests.py` already selects this file for any `claude/.claude/settings.json` diff, and the file already has four sibling tests of this exact shape (`json.loads` the settings file, assert one key's value) for other settings keys — `syncClaudeAiSkills` currently has no such pin, so a future edit (including the row-10 collision) could silently drop it with zero automated signal. `anchors: row8, row10, row13`

**Evidence-location note.** The `.trash/` relocation fact and the "no opt-back-in exists" fact each live in exactly one place — M2's body. M3 and M4 point at M2 rather than restating either fact; neither repeats the vendor citation or the scope-restriction reasoning in full.

**Over-powered-primitive check on M1.** M1 is wider-scope than the engineer's own accounts: it ships as the default for every stow consumer. Two lighter primitives, both rejected:

- **A per-account untracked settings file at the home config dir.** No such file exists — `README.md` line 466 states Claude Code scopes `settings.local.json` to a repository root, not the user's home config directory, so there is no home-scoped untracked override to write.
- **A gitignored per-account file inside each account's own config dir.** Reachable, but it must be repeated per account, is unversioned, and is invisible to any account created later — which re-creates the per-account duplication the change exists to remove.

Both fail against the stated goal of one canonical, versioned place. The wider scope is therefore accepted, with M2 and M3 as the mitigation for consumers who did not ask for it.

## Critical files

One `code-writer` dispatch, not split: five files, one coherent change, and the docs/test files depend on the settings edit's exact wording, so there is no non-overlapping partition to hand to parallel agents.

- **`claude/.claude/settings.json`** — insert `"syncClaudeAiSkills": false,` immediately after the `"disableWorkflows": true,` entry (line 80 in the committed file), grouping it with the other top-level feature booleans and keeping the diff a single added line. Change nothing else in the file (row 10). Placement is not load-bearing (row 9); if the separate main-tree diff later conflicts here, resolve by keeping the key wherever it lands. Expect one permission prompt from the settings-edit gate — approve it (row 4).
- **`claude/.claude/hooks/tests/test_hook_alignment.py`** — add one test function pinning `syncClaudeAiSkills: false` in the declared settings, mirroring `test_schedulewakeup_stays_denied_in_settings`'s single-file shape (row 13): `json.loads` the stow-source `claude/.claude/settings.json`, assert `settings.get("syncClaudeAiSkills") is False`, and carry the same docstring convention as its siblings — this proves the *declared* config state, not runtime behavior. No repo-local-settings sibling test is needed (unlike the `attribution.sessionUrl` pair): row 1/7 establishes that repository scope doesn't honor this key at all, so a single-file pin matches the key's actual valid-scope set.
- **`docs/design-decisions/claude-ai-skill-sync-disabled-by-default.md`** — new file, slug parallel to the existing `artifact-workflow-disabled-by-default.md`. Content, as two separate facts rather than one "recovery" story (row 2): (a) it takes effect at user scope (row 1) and already-synced skills are relocated to `~/.claude/skills/.trash/`, recoverable by moving them back manually; (b) separately, and independent of that relocation, there is no supported way to make sync resume for a single project — the key's own docs define `true` as always equivalent to unset, at every scope, not merely at lower precedence than user scope (row 2). State plainly that no minimum Claude Code version is documented for this key (unlike some sibling keys in the same reference table) — don't invent one. Also state why this repo defaults it off (skills are managed canonically here; the claude.ai→Claude Code direction is duplication), and note the rollout is pull-gated with no push mechanism or completion signal: a consumer who pulls rarely keeps sync on until their next pull, with no way for the engineer to detect that from this repo. **Reuse:** read `docs/design-decisions/attributionsessionurl-false-ships-in-both-settings.md` for the entry's exact shape rather than inventing one — H1 title, the italic provenance line (a date, since this is recorded after the directory split, per `docs/design-decisions.md`), a sources list (cite [settings-reference](https://code.claude.com/docs/en/settings-reference#syncclaudeaiskills)), and the affected-files list.
- **`docs/skills.md`** — one sentence added next to the existing settings-lever prose around line 195 (which already cross-references the artifact/workflow decision entry): claude.ai skill sync is disabled by default in the shared `settings.json`, with a pointer to the new decision entry for the recovery path and scope details. Do not restate the `.trash/` mechanics or the no-opt-back-in reasoning here — those facts live once, in the decision entry (M2); this sentence is a pointer, not a second copy. **Reuse:** line 195's existing pointer sentence as the model; link to the new decision entry by bare backticked path with no `§` marker, matching the citation-grammar rule for a non-section reference.
- **`CHANGELOG.md`** — one `### Changed` bullet under `[Unreleased]`, matching the shape of the two entries cited in row 12 (lines 29, 43): one-line summary, the rationale from the Context section, and a **Migration:** line stating (1) the setting is live on `git pull` with no reinstall but takes effect from the next `claude` launch rather than a running session, (2) already-synced skills move to `~/.claude/skills/.trash/`, and (3) no opt-back-in path exists at repository scope. **Reuse:** line 29's entry as the closest model in shape (a default flip with a version-controlled config file and a `.trash/`-equivalent no-op-if-inapplicable framing).

## Verification

1. `.venv/bin/python3 claude/.claude/scripts/select-tests.py` from the repo root, per `CLAUDE.md` § "Commands" (agents run the scoped selector, not the full suite). A JSON syntax error in `settings.json` surfaces here — several tests parse that file by path, as `select-tests.py`'s own comments at lines 137-143 record — so no separate JSON-lint step is warranted. This run also exercises the new `test_hook_alignment.py` assertion (row 13): confirm it fails against a checkout without the settings edit and passes with it, before trusting it as a regression guard.
2. If `select-tests.py` cannot map the new `docs/design-decisions/` path, report that as a bug in its rule table. It is not a licence to widen to the full suite by hand (`CLAUDE.md` § "Commands").
3. **Behavioral check, after merge — the only real proof the key works,** since no repo test can exercise vendor behavior. The worktree edit is not live: `~/.claude/settings.json` symlinks to the *main checkout's* copy, so this runs after merge and `git pull` in the main checkout, and takes effect from the next `claude` launch rather than a running session. Start a new session **from a repository other than claude-config**, in an account whose `~/.claude/skills/synced/` was populated — resolve that account's actual skills directory via its `$CLAUDE_CONFIG_DIR` (bare `~/.claude/` only for the `personal` account; every other account resolves under `~/.local/state/claude-accounts/<account>/`, per `CLAUDE.local.md`) — and confirm `synced/` is gone under that resolved path and the previously-synced skills are in the matching `.trash/`. This is a single-consumer spot check, not fleet-wide confirmation: rollout is pull-gated per consumer with no push mechanism, so any consumer who hasn't pulled yet is unaffected until their next `git pull`, with no signal back to this repo either way.
4. Confirm the edit produced exactly one settings-edit permission prompt and that no `/review-permissions` run was needed (row 4).
5. A few sessions after the change is live, run `git status` in the main checkout. An unstaged reappearance of `syncClaudeAiSkills` means Claude Code writes the key back (row 8) and the guard question reopens. The row-13 unit test does not catch this case (it asserts the committed file's declared value, not a working-tree drift) — this manual step remains the only backstop for a post-merge vendor write-back.

## Out of scope

- **The uncommitted main-tree diff to `claude/.claude/settings.json`** (key reordering, `promptCacheTtl`, `subagentPromptCacheTtl`, `autoCompactEnabled`, `agentPushNotifEnabled`). It predates this task and lives only in the main tree's working directory. Do not reference it, rebase onto it, or reproduce any part of it.
- **Adding `syncClaudeAiSkills` to `guard-settings-session-keys.sh`'s guarded key set.** Row 8's failure has not been observed, and the key is a deliberate shared default rather than one machine's state — which is the opposite of what that guard protects against. Guarding it now would be a defensive layer for an unobserved failure. Verification step 5 is the trigger to revisit.
- **Adding the key to the repo-root `.claude/settings.json`.** Row 1/7: that scope isn't honored for this key at all, so writing it there would be a no-op — worse than doing nothing, since it would misleadingly suggest project-scope control.
- **Editing `.claude/plans/skill-listing-duplication.md`.** It is a historical plan record — read-only under the preserved-content rule — and the fact it records (the key exists) stays true.
- **A README section.** The artifact/workflow README section earned its place by documenting two wrapper commands; there is no analogous surface here, and `docs/skills.md` is the matched reader altitude.
- **Hand-deleting or cleaning `~/.claude/skills/synced/` or `~/.claude/skills/.trash/`.** The vendor's flip performs the move; hand-deletion would be a destructive act on files outside this repo, for no added benefit.
- **Per-account manual steps.** The stow symlink is what makes one edit cover every account (G3); if it does not, that is a stow-layout question, not this change's.
- **Naming the private repository or account where this behavior was first observed**, in the plan file, the decision entry, the commit message, or the PR body (row 11). This plan file ships in the public repo in the same PR as the change.

# Widen require-ready-for-review.sh's active-bypass marker refresh

Issue: #869

## Context

Make a long `/ready-for-review` run keep its active-bypass marker for the life of the run. The skill activates the marker at step 0, then spends longer than the marker's 60-minute idle window (`_lib.sh:1280`; `docs/hooks.md:111`) on parallel specialist review dispatches; by step 6 the marker has been evicted and the gate denies PR creation with "no /ready-for-review gate run covering the current HEAD was found." The cause is placement: the marker's 60-minute idle window is refreshed on use, but `require-ready-for-review.sh` only reaches its refresh call after a command-shape filter that passes just three command shapes — and a `/ready-for-review` run issues none of them between step 0 and step 6. This is worth fixing now because it bit a real run. The only available remedy is re-running `marker.sh activate ready-for-review`, and nothing checks that remedy against the skill actually being mid-run. The expiry therefore trains a "denied → re-activate → retry" reflex indistinguishable from forging a gate release on a run that genuinely skipped steps. The intended outcome is that the refresh fires on every Bash call, matching the sibling gate that already has this property, without weakening the crash-recovery bound the idle window exists to provide.

## Approach

Move the existing active-marker bypass check in `require-ready-for-review.sh` from its current position (line 300, after command classification, repo resolution, and the default-branch check) to immediately after `SESSION_ID`/`CWD` are extracted from the payload (after line 155). The call itself, its arguments, and the primitive it uses are unchanged — only its position moves. Because a live marker already produces `exit 0` on every path that can reach it, the relocation changes no allow/deny verdict for any session that does not hold a live marker, and widens the marker's mtime refresh from "the three gated command shapes" to "every Bash tool call the session makes." That makes this gate's refresh trigger structurally identical to `require-respond-pr.sh`'s, which already refreshes at the top of its own body and has never exhibited this failure.

**Why this position and not a safer-looking one.** Four alternatives were weighed:

- *Place the refresh after the fragment-split fail-closed deny (line 250) instead, preserving that deny exactly.* Set aside. For a session holding a live marker, that deny protects nothing: the command it refuses to scan would be allowed by the same marker once scanned. A total `sed` absence still denies every session at the earlier, untouched deny (146–151) regardless of this choice; only a session hitting a *partial* `sed` failure between the two calls stays wedged at the later deny under this safer-looking position, and gets un-wedged under the relocation. That is a reduction in deadlock surface for that narrow subclass, not a fail-closed regression. It is the same disposition the marker bypass already grants that session for its pushes. It comes at a diagnostic cost: for that subclass, the actively-running session stops seeing the actionable deny message naming the environmental cause, while every other session's gated push in the same broken environment still trips it. Keeping the later position would also cost two things:
  - Forfeiting the structural match with `require-respond-pr.sh`.
  - Continuing to pay a `sed` fork plus per-fragment `grep`s on every Bash call for the duration of an active run.
- *Add a second, unconditional "touch if live" call early and leave the bypass where it is.* Set aside. It computes the same authorization verdict twice per call (two `find`, two `cat`, two `kill -0`), discards the first, and creates a second eviction point for the same marker. Computing an authorization verdict in order to throw it away is the wrong-foundation shape, and it buys nothing: how long the marker stays live is identical under both designs.
- *Raise the 60-minute constant.* Set aside. It moves the cliff instead of removing it (an arbitrarily long run still expires), it weakens the crash-recovery bound for all four gates including two that do not have this bug, and the constant is coupled to `session-marker-dashboard.sh`'s own staleness label plus two exact-boundary tests in `test_lib.py`.
- *Have the skill body re-run `marker.sh activate` at intermediate steps.* Set aside. That is the self-authorized release the change exists to stop training, it depends on the model following prose rather than on a mechanism, and it does not help at all when a single step (the parallel specialist dispatches) is itself longer than the window.

**On the default-branch broadening.** Once the refresh sits above the command-shape filter, a default-branch push during an active run refreshing the marker is not a separate case to decide — it is a subset of "every Bash call refreshes." Excluding it would require running `git rev-parse --abbrev-ref HEAD` plus `git symbolic-ref` (and up to three more `rev-parse --verify` calls in the fallback loop) on every Bash tool call in every session, to suppress a refresh whose allow outcome is unchanged either way. Reject it: the exclusion mechanism costs strictly more than the thing it excludes.

**What the change trades away, stated plainly.** After it, the 60-minute idle window bounds this gate's marker against a *quiet session*, not against a *halted skill in a busy session*. A `/ready-for-review` run abandoned mid-way leaves the active-bypass marker, and the push access it grants, alive for as long as the session keeps issuing Bash calls. Three things bound that:

  - PID-liveness eviction still covers the crashed-session case unchanged.
  - The skill's own `deactivate` at step 7 covers the normal path.
  - `marker.sh clear-stale` covers orphans.

The trigger *mechanism* this residual rides on is genuinely identical to `require-respond-pr.sh`'s: both refresh unconditionally at the first Bash-tool-call touchpoint, before any command-shape filter (`require-respond-pr.sh:86`, and this gate's new site). The *stakes* are not identical. `require-respond-pr.sh` guards a PR/issue comment posted without the `[Claude Code]` attribution prefix — a labeling defect, correctable by editing or deleting the comment. That hook's own header (lines 43–44) already frames it as best-effort rather than a security boundary. This gate guards pushing to a branch with an open PR, flipping a draft PR to ready, and creating a PR. Each of those publishes to a shared remote and invites human review attention, relying on the gate's stated guarantee having held. This is also a real behavior change, not only a framing one: today an abandoned run self-heals within 60 idle minutes; after the change it does not self-heal via time alone for as long as the session issues any Bash call at all. `docs/hooks.md` already has the sentence shape for stating a residual like this (line 122) — `require-ready-for-review.sh` joins that sentence, updated to reflect the stakes difference, rather than needing a new caveat.

**Sibling audit result.** All four gates in the family were checked. The bug is not "the trigger is narrow" — it is "the trigger is misaligned with what the owning skill spends its time doing." `require-ready-for-review.sh` is severely misaligned (the skill's hours go to test/lint Bash calls, parallel dispatches, and CI polling; none is a push/PR shape) and it bit a real run. `require-memory-skill.sh` is aligned — the gated action (writing `MEMORY.md` or a new topic file) *is* the owning skill's own primary action, and the skill has no long-running phase between activate and first write; it is excluded, with reasoning in **Out of scope**. `require-plan-review.sh` has a real, previously-unrecorded gap of the same shape (its refresh sits below the `agent-reviews/` exemption exit, so a `/plan-review` run's own reviewer-findings writes never refresh its marker). It is excluded here for scope and risk reasons stated in **Out of scope**, and should be filed. `require-respond-pr.sh` already has the target property and needs nothing.

**Documentation.** The fix collapses two of `docs/hooks.md`'s four per-hook bullets (lines 117–120) into one, but not all four: the two Bash-dispatched gates converge on "every Bash call," while the two Write/Edit-dispatched gates keep genuinely different scoping. Restate the list along that axis (dispatch class, then scoping) rather than as four unrelated facts.

### Assumption ledger

**Root:** `/ready-for-review`'s active-bypass marker expires during a run because its refresh is placed downstream of the gate's command-shape filter, so an hour of the skill's own non-push activity slides no window forward — and the only available remedy is a hand-run `marker.sh activate`, which is a self-authorized gate release indistinguishable from forging one.

**Givens:**

- **G1.** Subagent tool calls carry the parent session's `session_id`, so a dispatched reviewer's Bash calls key the parent's marker. Harness-owned; no design here can change it. `[verified: docs/precompact-hook-behavior.md:66]`
- **G2.** PID-liveness eviction covers the crashed-session case independently of mtime; the idle window bounds only the halted-skill-in-a-live-session case. Owned by `_lib.sh`'s shared predicate serving four gates — separating the two would be a family-wide redesign requiring a decision outside this plan. `[verified: _lib.sh:1279-1284]`
- **G3.** This gate's threat model is cooperative, not adversarial, with `block-gh-pr-merge.sh` plus CI as the backstop against deliberate evasion. Declared by the hook's own contract header; changing the threat model is a decision outside this plan. `[verified: require-ready-for-review.sh:95-103]`
- **G4.** `/ready-for-review`'s steps between activate (step 0) and PR creation (step 6) — preconditions, verification, code review, and skill-procedural-fidelity review — are none of them a push, draft-ready, or PR-create command shape. The gap is worst on a *clean* run: step 3's `/code-review` fix-push loop would refresh the marker if it fired, so a run with review findings may never hit the expiry, while a clean run — no fix commits, no pushes — reaches step 6 with nothing having refreshed it. `[verified: claude/.claude/skills/ready-for-review/SKILL.md]`

**Mechanism:** a single relocation of the existing `_lib_active_bypass_marker_live_and_touch` call — no new helper, no new constant, no second call site, no change to `_lib.sh`. `anchors: root`. This is the lightest primitive available: the alternatives enumerated above (second touch call site; raised constant; skill-body re-activation) are each strictly heavier and each fails for the reason given there.

One extra step, because the new test's whole value is that it fails today: confirm `test_non_gated_command_advances_active_marker_mtime` fails against the unmodified hook before the relocation lands. Bare `git stash` is off-limits in this repo — the stash stack is shared across 100+ live worktrees and another session can pop it mid-use. Instead, capture the pre-change hook straight from git's object store: `git show HEAD:claude/.claude/hooks/require-ready-for-review.sh > /tmp/require-ready-for-review-baseline.sh` (no working-tree mutation, no stash involvement). Then run the new test's body against that baseline copy via a throwaway `/tmp` script that points `run_hook` at the baseline path instead of `READY_FOR_REVIEW_HOOK`, and confirm it does not advance the mtime there. A refresh test that passes both before and after is vacuous.

Also note the measured per-call cost, so it is stated rather than implied. The no-marker case — the overwhelming majority of Bash calls machine-wide — adds exactly one subshell fork, from `_lib_config_dir` inside `_lib_active_bypass_marker_live_and_touch`, since `[ -f "$marker" ]` short-circuits before `find`/`cat`/`touch`. That sits on top of an existing ~12–14 fork floor for a non-gated command. Marker-holding sessions get net *fewer* forks than today. Cheap, not free.

Then `/code-review` before commit, per global `CLAUDE.md`. No `/skill-review`, `/agent-review`, or `plugin-semver` dispatch applies — no `SKILL.md`, agent file, or plugin-directory file is touched.

## Out of scope

- **`require-memory-skill.sh`** — audited and excluded. Its refresh trigger is a Write/Edit/MultiEdit to a memory path, which is precisely what the owning `ai-instruction-and-memory-files` skill exists to do; the skill has no long-running phase between its activate and its first gated write. The misalignment that produces the reported bug is therefore absent, and relocating its refresh above the path classification would extend the memory gate's bypass across the session's entire remaining lifetime for no observed defect. Excluded on evidence, not on scope convenience (ledger row 10).
- **`require-plan-review.sh`** — a real variant of the same bug exists and should be filed as its own issue rather than folded in: its refresh at 232–234 sits below the `agent-reviews/` exemption exit at 173–175, so a `/plan-review` run's own reviewer-findings writes — the dominant write shape during that skill — never refresh its marker (ledger row 11). Excluded here for three reasons: no observed failure; the fix is not the same one-line relocation, because the `TOOL_NAME != ExitPlanMode` carve-out splits the refresh from the bypass and an early relocation would also shadow the plan-mode branch (107–135) and the unhashable-plan fail-closed deny (197–214); and bundling it would triple the review surface of a one-line change in a hook whose ordering carries its own documented rationale.
- **`require-respond-pr.sh`** — already refreshes at the top of its body on every Bash call; nothing to change.
- **Raising the 60-minute constant**, or making it per-gate. Weighed and rejected in Approach; it is also coupled to `session-marker-dashboard.sh`'s staleness label and two exact-boundary tests in `test_lib.py`.
- **Tightening `marker.sh activate`** so a marker write verifies its owning skill was actually loaded this session. This is the reason the mid-run expiry is costly (an expired marker's only remedy is a self-authorized re-activate), but it is a separate gate-design question with a much wider blast radius across all marker-writing skills. Eliminating the expiry cuts both ways: it removes the routine occasion for that self-authorized re-activate, a partial mitigation, but a *successful* self-activation now also buys a bypass that lasts as long as the session keeps issuing any Bash call, where today it was bounded by the 60-minute idle window. Net, acceptable under this gate's cooperative threat model (G3): the same self-activation escape hatch already sat outside the mechanism's own guarantees before this change.
- **A new `docs/design-decisions.md` entry.** `docs/hooks.md`'s "Gate deadlock recovery" section is the canonical home for this family's refresh behavior and residual bounds; a decision-log entry would restate it. The alternatives-weighed reasoning belongs in the PR body.
- **The no-repo-hash tree-switching gap** (`docs/hooks.md:113`) — predates this change and is unaffected by it.

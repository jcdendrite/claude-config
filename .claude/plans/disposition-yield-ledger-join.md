# Stamp the reviewing lane on review-ledger rows

## Context

Goal: let a later measurement compute, per reviewer lane, what share of findings the author accepted (`ADDRESS`) versus declined (`DEFER`/`SETTLED`), by recording the lane on each ledger row at write time.

Ask: "If the findings are raised by several lanes, then have one row per lane. And lane column makes sense." — engineer, answering the proposal to add a `--reviewer` field to `review-ledger.sh append` and a `Lane` column to the disposition table. The engineer also said: "Feel free to get the analytics engineer's perspective before you do this, or if you want to just let them spawn as part of the planning process, that's okay too." Asked whether a finding raised by two lanes is stored as two rows or as one row carrying a lane list, the engineer selected "One row, lane list (Recommended)", which replaces the earlier per-lane-rows wording. Asked whether carry-forward and engineer-decided rows record the lane that raised the finding, the engineer selected "Yes, record the lane (Recommended)". Asked whether `--reviewer` should be optional, the engineer wrote: "I think making --reviewer optional will drop data and make analysis more difficult.. is there a way we can use determinism/scripting to force --reviewer to exist? or a linter for the logs? take several steps back and think about the design here. ask the architect for advice." Asked which of four reviewer-added pieces should stay, the engineer selected "Supersession notes", "Write-time lane echo", "Rewrite SKILL.md reopen lines" and "select-tests.py rule + test", wrote "Also have the architect adversarially review those items", and on where the roster pin lives wrote "Don’t over optimize for avoiding a full test run… your alternative will violate the single source of truth, right? Unless you abstract out the existing table parser so that test agent roster can use it". After that review the engineer selected "Drop the echo (Recommended)" and "Shared helper, drop select-tests (Recommended)", which replace the earlier selections of the echo and the select-tests rule. Asked whether a reviewer outside the roster gets a third lane literal or is accepted as a lost row, the engineer selected "Keep `unrostered-agent` (Recommended)".

Why now: ledger rows carry no lane field, so a join from a reviewer's findings to a ledger row can only key on session and cited `file:line`, and reconciliation merges findings only on an exact match (row 8). That join is a heuristic that cannot recover a lane, so the lane has to be recorded when the row is written.

Intended outcome: each new row that raises a finding carries the lane that raised it, and a re-log of a pre-schema-5 decision stores `[]`, so a follow-up `reviewer-yield` change can report per-lane disposition yield with no join to transcripts and no heuristics. Rows written before this change stay undeclared and are reported as such.

## Approach

Every ADDRESS, DEFER and SETTLED row that `review-ledger.sh append` writes stores the lanes that raised its finding in a sorted, duplicate-free `reviewers` array, and `append` exits 2 on a non-CLEAN row that passes neither `--reviewer` nor `--relog`. A repeatable `--reviewer <lane>` gives the lanes. A row that only re-logs its `--ref` decision passes `--relog` instead, which copies that decision's lanes, and a re-log of a pre-schema-5 decision stores `[]`. In `/code-review`:

- each finding stays one row;
- the disposition table's `Source` column is renamed `Lane`;
- each Lane cell comes from the findings file the finding came from;
- a finding no spawned reviewer agent raised is labeled `skill-tool` or `orchestrator`, and a finding a spawned reviewer agent outside the roster raised is labeled `unrostered-agent`.

Readers need no edit (M6).

Alternatives weighed:

- **One row per lane.** Set aside by row 1. A DEFER two lanes raised would also publish two PR-body rows, and a reopen would retire only one of them (row 10).
- **An optional `--reviewer`, with an empty list read as undeclared.** Set aside by row 4.
- **A linter over the ledger files.** Set aside: it flags a row only after the row lands, and the append-only ledger cannot correct it (row 26), while a write-time rejection costs one corrected retry (row 30).
- **A PreToolUse hook that checks the `append` command for `--reviewer`.** Set aside: it would re-parse command text the script already parses, for a check of the same kind as the script's own `--finding` and `--rationale` checks (`review-ledger.sh:422-426`).
- **Deriving the lane inside `append` from the round's findings files.** Set aside by row 9: matching a finding to a file is the heuristic join that cannot recover a lane (Context), unless the orchestrator names the file, which moves its declaration without removing it, and Skill-tool and orchestrator findings have no file.
- **A comma-joined string field.** Set aside: grouping by that field would treat each lane combination as one lane, and the follow-up would split text to unnest it.
- **A `--rationale` prefix, as `fix-plan:` and `challenge:<outcome>:<scope>` mark how a row was decided (`code-review/SKILL.md:388, 426`).** Set aside on four grounds:
  - Render publishes `--rationale` in the PR body's DEFER, SETTLED and carry tables (`_review-ledger-lib.sh:675-688`), so lanes would reach the human-facing text.
  - The lanes would share the 300-character `--rationale` cap (`review-ledger.sh:23`).
  - The script could force presence and roster membership only by parsing prose.
  - The follow-up would split text, as with the comma-joined string.

- **Leaving lane order and repeats to the caller.** Set aside by rows 12 and 13: the array enters the id and the dedup key, so a retry naming the same lanes in another order would land a second row for one finding.

- **Adding the lanes as a 16th field of `_review_ledger_lookup_ref`'s line.** Set aside by row 23: four positional `read`s parse that line, one of them through its last field, for a value only `--relog` rows use.

- **Lane validation in `review-ledger.sh`'s own body, beside the `--authoring-agent` check.** Set aside by row 28: the flag matrices live in the library's direct test.
- **Labeling a finding from a reviewer agent outside the roster `orchestrator`.** Set aside by M8: that literal means no reviewer agent raised the finding, so it would credit the runner with another agent's finding.
- **Rejecting the append of a finding from a reviewer agent outside the roster.** Set aside by M17: a rejected ADDRESS append loses its row and a rejected DEFER or SETTLED append is a blocking stop, where `unrostered-agent` lands the row.
- **Accepting any value shaped like an agent name.** Set aside: a typo would land as a lane, and a landed row's lanes are final (M14).

# Redacted cross-account `pr-cost` ledger export

## Context

Make the cross-account `pr-cost` export reproducible by giving it a durable home in `transcript-analysis.py`. A prior session hand-rolled a one-off script that read every declared Claude Code account's `pr-cost-ledger.tsv` and emitted a redacted cross-account TSV to feed a cost/telemetry case study comparing per-PR cost before and after a handoff-threshold change. That script lived in `/tmp` and is gone; only its redaction contract survives. The follow-on step — running the actual cross-account/cross-repo analysis with a partner session on another machine — is blocked on this surface existing, and re-deriving a one-off each time both wastes the work and risks a redaction slip. Everything under `claude/` ships to every stow consumer via `./install.sh`, so the user surface and threat model here are "every stow consumer," not one machine.

## Approach

Add a fourth pr-cost-family surface, `transcript-analysis.py pr-cost-export`, that reads every declared account's `pr-cost-ledger.tsv`, collapses each account's rows to the current row per PR, re-redacts the four identity columns into account-namespaced tokens, truncates the two remaining free-precision timestamps to a date, and writes the union to a single operator-named TSV — never to stdout. The subcommand makes no `gh` call and scans no transcript corpus: it is a pure local file transform over ledger files, which is why it reuses `_resolve_cost_roots` / `_pr_cost_ledger_path` / `_parse_pr_cost_ledger_file_text` / `_latest_pr_cost_row` for input resolution and selection, but shares none of `_pr_cost_report`'s network-and-corpus preamble.

**Root problem.** The pr-cost ledger is per-account and its rows carry `host` and `repo` raw at rest (`docs/pr-cost.md:99-103`), so the cross-account, cross-repo cost analysis this data exists to support has no reproducible, publishable input — only a one-off script that has since been deleted. The threat the design must hold is that the artifact produced for that analysis must not carry a private project's host, repo, branch, PR number, or minute-precision activity trace, and must not be copied into the transcript corpus it analyzes.

**Givens** (fixed conditions the design does not reach):

- **G1.** Stored `head_branch` labels are not stable identifiers across rows. `branch_map` is per-run (`redaction.py:220`, "this label is stable only within one run, not across runs") and `_new_pr_cost_row` stores the label rather than the branch, so account A's ledger can hold two rows whose stored `account-1/branch-1` refer to different branches recorded in different runs. Dissolving this needs a durable per-account branch map — a change to the ledger's write path and an ownership decision outside this plan. Recorded also under **Out of scope**.
- **G2.** `host` and `repo` are raw at rest in every existing ledger row, deliberately, because both are part of the row key and must stay comparable across runs (`transcript-analysis.py:8218-8222`). The export redacts on the way out; it cannot retroactively change what is already on disk. Recorded also under **Out of scope**.
- **G3.** `account-K` ordinals, and every `account-K/<kind>-N` token, are comparable only among runs built from the same declared-roots file and the same corpus (`redaction.py:130-134`, and `_assign_root_scoped_redact_label`'s own "stable only within one run, not across runs" at `redaction.py:220-221`). `_redaction_ordinals` (`scope.py:198`) has no cross-run anchor to offer, and adding one would change a contract ~16 other call sites share. Recorded also under **Out of scope**.

**Mechanisms.**

**M1 — A new `pr-cost-export` subcommand rather than a `pr-cost` flag.** `anchors: row1` (engineer's call), grounded in `row7`. The over-powered-primitive check, enumerated for a reader who was not in the session:

- *Lighter primitive A — a `--export PATH` flag on `pr-cost`.* Set aside because `_pr_cost_report` requires a git origin remote, `gh` auth, a live network discovery call, and a full per-root transcript scan before the first ledger read (`row7`). A pure local file transform would inherit a network dependency, and suppressing it means early returns threaded through a 300-line function that already carries read mode, `--record`, two multi-root refusals, and a per-branch enrichment loop.
- *Lighter primitive B — parse `pr-cost --all-accounts` read-mode stdout.* Set aside because `_print_pr_cost_ledger_rows` emits 6 of the 39 columns (`Repo/PR/Machine/Status/Join/CapturedAt`, :8275) and every metric column — the analysis payload — is absent. It also lands on stdout, which is `row2`'s exact problem.
- *Lighter primitive C — no tool at all: concatenate the ledgers and post-process with shell/pandas.* Set aside because `host` and `repo` are raw at rest (`G2`), so an unredacted concatenation *is* the leak, and reproducing `_redaction_ordinals` plus `_assign_root_scoped_redact_label`'s per-account counters outside Python is not a one-liner. This is what the deleted one-off was, and its loss is why this plan exists.

**M2 — `--out PATH` required, enforced in the command body (exit 2), no stdout path at all.** `anchors: row2`, enforcement site per `row19`. The mechanism is *more restrictive* than the convention, so the enumeration is of the lighter, more permissive shapes:

- *Lighter primitive A — stdout by default with an optional `--out`, the `user-input` (:11161) and `judgment-pair` (:11404) shape.* Set aside because the default invocation is then the leaking one: a bare `pr-cost-export` inside a session copies every exported row into that session's transcript.
- *Lighter primitive B — stdout behind an explicit confirmation flag.* Set aside as strictly more surface for the same outcome, and against the module's own precedent: `_pr_cost_report`'s docstring states "There is deliberately no --no-redact escape hatch for this subcommand, unlike cost/subagents" (:8337-8338). The file already treats stdout as a channel needing protection elsewhere — `audit-routing-samples` routes its scope header to stderr because "its stdout is a JSON (or curation-markdown) data stream a header line would corrupt" (`scope.py:461-467`).

Argparse `required=True` is rejected on two grounds: `row19`'s coverage loss, and that argparse's "the following arguments are required: --out" cannot carry the *why*, which is the non-obvious part.

**M3 — Reuse `_format_pr_cost_ledger_row` by adding a keyword-only `columns` parameter defaulting to `_PR_COST_LEDGER_COLUMNS`.** `anchors: row11, row13`. The four properties the export needs — `true`/`false` bools, `:.6f` floats, `str()` fallback, and the refuse-on-embedded-tab/newline guard — are exactly the four that function already owns. Re-implementing them in a second function duplicates a format contract across two sites, which CLAUDE.md's single-source-of-truth rule exists to prevent, and drifts the export's metric cells from the ledger's own the first time either changes. The durable-write path passes no `columns` argument, so `_write_pr_cost_ledger_file` is unchanged by construction. The lighter alternative — a shared `_assert_pr_cost_cell_safe(col, cell)` helper called from two independent join loops — was set aside because it shares only one of the four properties and leaves the other three duplicated. Per `row12`, the parameter is *not* extended to `_PR_COST_BOOL_COLUMNS`: the export's own new columns are rendered as strings/ints by the caller instead.

**M4 — Four separate redact maps, one per kind, and `str(row["pr_number"])` before tokenizing.** `anchors: row8`. The stringify satisfies `_assign_root_scoped_redact_label`'s `value: str` parameter contract (`redaction.py:198`) — it is *not* fixing a mixed-type-key runtime hazard, since under this design `pr_map` holds only `pr_number` keys. The same `str()` coercion is what `_format_pr_cost_ledger_row` already applies to this column.

**M5 — Re-tokenize `head_branch` even though it arrives already scrubbed, and rename the exported column to `head_branch_label`.** `anchors: G1, G3`. The stored label was assigned under whichever run's ordinal scheme recorded it, so passing it through puts two disagreeing `account-K` numberings in one row and invites a mis-partition by account. Re-tokenizing an already-opaque value discloses nothing. This contradicts `_print_pr_cost_ledger_rows`' own "would double-redact it" comment (:8270) — correct for its single-account print path, not for a cross-account export. Because `G1` makes the value a per-run label rather than a branch identity, it is not a valid join or grouping key: two rows recorded in different runs can collapse to one token, and one branch can appear under two. The export therefore renames the column so the trap is visible on sight rather than only in a doc a consumer may never open. The ledger's own on-disk column name is untouched.

**M6 — Iterate accounts in ordinal order (`sorted(ordinals)`), not `_resolve_cost_roots` order.** `anchors: row20`. Two exports taken from the same declared-roots file under different active profiles then produce byte-identical row order, which makes the artifact diffable.

**M7 — Create the output with `os.open(path, O_WRONLY|O_CREAT|O_EXCL, 0o600)` on a path whose final component is *not* symlink-resolved, catching `OSError`.** `anchors: row2, row25, row32, G2`.

Per `row32`, the path handed to `os.open` must be `resolved_out.parent.resolve() / resolved_out.name` — the parent chain resolved (which the git-tree check needs), the final component left as the operator named it — so `O_EXCL`'s own POSIX symlink refusal actually fires. Catch `OSError` rather than `FileExistsError` alone: a dangling symlink whose resolved parent is missing raises `FileNotFoundError`, and letting that escape produces exactly the traceback the symlink coverage forbids. The early fast-fail check uses `os.path.lexists()`, not `Path.exists()`, so it tests the directory entry rather than following the link and agrees with what `O_EXCL` will do. One primitive covers three needs: `O_EXCL` refuses to clobber an existing file (a `--out` pointed at a `pr-cost-ledger.tsv` would otherwise destroy an append-only, irreplaceable record whose source transcripts have aged out), it does so without a TOCTOU window, and `0o600` at creation avoids the umask-dependent world-readable window a `write_text`-then-`chmod` sequence leaves open. The heavier alternative — the ledger's own `mkstemp` + read-back + `os.replace` pattern (:7718-7744) — was set aside because `os.replace` clobbers, which is the behavior being refused. No `O_EXCL` precedent exists elsewhere in this file, so the collision message is authored net-new rather than reused; it must be caught and converted, never allowed to propagate as a traceback.

**M8 — Refuse an `--out` path inside a git working tree, via `_ledger_path_is_git_tracked(resolved_out, "pr-cost-export")`.** `anchors: row23`. The natural cwd for these sessions is a repo worktree, and this repo is public; the helper already exists, already fails closed, and already takes a subcommand label for exactly this reuse. Distinct failure mode from M7's (accidental commit vs. destroying the ledger), not a second layer over one gap. This is the tool's entire enforceable contribution to `row6`'s publication boundary — see M15.

**M9 — Refuse `PR_COST_LEDGER_PATH` when more than one root resolves; permit it at one root.** `anchors: row22`. Mirrors `pr-cost`'s own refusal, and keeps the env var usable as the test seam existing assertions rely on.

**M10 — Fail loud (exit 1) on a malformed ledger, naming `account-K` and never a path or a raw cell value.** `anchors: row21`. **Correction to a prior draft's citation:** `transcript-analysis.py:8434-8440` prints exactly `f"pr-cost: {exc}"` — it names neither a path nor an account. The `account-{ordinal}` discipline is demonstrated only at `:8452-8457` and `:8465-8469`, which cover a different failure mode (missing sentinel). The export's handler is therefore **net-new code**, composing `f"pr-cost-export: account-{ordinal}: {exc}"`, not a pattern copied from the malformed-ledger site. The no-raw-value discipline follows `_parse_pr_cost_ledger_row_cells`' own host/repo errors, which deliberately omit the offending value.

**M11 — Code lands in `transcript-analysis.py` beside the pr-cost block, not in a new `transcript_analysis/` module.** `anchors: row1`. Every helper it reuses is a private module-level function in the shim; `cmd_pr_cost` is itself still shim-resident (:8312) while `cmd_cost` has migrated, so landing beside the sibling matches the pr-cost family's actual state. `docs/transcript-analysis-architecture.md:6-12` frames the migration as deliberately leafward-first and incremental, and a new package module would require updating that doc's module list and one-directional import rule.

**M12 — No `--all-accounts` flag; scanning every resolved root is the default.** `anchors: row7, M1`. `pr-cost`'s multi-root refusal (:8340-8355) is justified by durable per-account writes and by read mode conflating two accounts' data in one listing. Neither applies: the export writes one file, every identity column is tokenized, and the `account` column makes the partition explicit rather than conflated.

**M13 — Collapse to one current row per `(host, repo, pr_number, machine)`, and replace `supersedes` with a derived `correction_count`.** `anchors: row10, row12, row14, row15`. The ledger is append-only, so a `--force` correction appends a row carrying `supersedes` = the prior row's `captured_at` rather than replacing it; passing every historical row through hands a consumer an artifact where `groupby([...]).sum()` silently double-counts every corrected PR.

The append-only rationale does not transfer to this artifact, and `docs/pr-cost.md:72` says why in its own words: append-only exists because "this ledger is the sole surviving record once transcripts age out." The export is not the sole record — every source ledger stays byte-identical on its own machine and the export is regenerable. What *is* at stake is grain integrity of a single-purpose extract, and that is protected by fixing the grain, not by mirroring the source's retention policy.

- *Alternative — keep every row and document it.* Not available, rather than merely weaker: making it workable requires `supersedes` and `captured_at` at full precision so a consumer can order same-day corrections, which is exactly the minute-precision trace this plan's root problem excludes.
- *Alternative — collapse plus an `is_current` column.* Set aside because the shipped history is still unusable — superseded rows' timestamps are still truncated, so they can only be filtered out, which the collapse already did — while roughly doubling the row-granularity metric tuples in an artifact whose handling constraint is "fewer joinable rows is better."

Collapse runs **per account, on raw untokenized rows, before redaction and before truncation**, by calling `_latest_pr_cost_row` once per distinct key in that account's parsed rows. Call it rather than re-deriving a `max()` inline: at this scale the cost is nothing and it keeps one definition of "latest."

Both halves of that ordering are mechanically required, not tidiness. **Before redaction:** `_latest_pr_cost_row`'s signature is typed (`host: str, repo: str, pr_number: int`) and it compares `r["pr_number"] == pr_number` as an `int` (`:7690`); redacting first would replace those cells with opaque token *strings* (M4's `str()` step), breaking the helper's contract and forcing a reimplementation — the duplication M13's own "one definition of latest" rationale exists to avoid. **Before truncation:** truncating `captured_at` to a date first would convert today's rare exact-second tie into a routine same-calendar-day collision for any PR corrected twice in one day, making M16's tie-break carry correctness it was never meant to carry.

After the collapse a shipped row's `supersedes` points at a row the file no longer contains — a dangling pointer inviting a join it cannot support, whose truncated form means nothing. Replace it with `correction_count`, an integer computed from the **full pre-collapse row group** for that key (`len(group) - 1`) — the dependency is row-membership completeness, not timestamp precision. An integer rather than a boolean per `row12`: a `bool` would render `True`/`False` through the formatter's `str()` fallback, since `_PR_COST_BOOL_COLUMNS` is a module constant M3's parameter does not reach. Renaming rather than retyping in place is deliberate — a same-named column with a changed type is worse than a renamed one.

**M14 — One `#`-prefixed provenance line above the TSV header.** `anchors: row6, row31, row33, row34, G3`. It makes four otherwise-stdout-only or undetectable facts travel with the artifact: whether two exports' `account-K` ordinals are comparable at all (`G3`), that a fully-skipped run produced a header-only file, the legacy-header provenance (`row27`), and the publication prohibition.

**Format is pinned, because the corpus digest is meant to be compared programmatically rather than read.** A single space-delimited `key=value` token sequence, not prose:

`# pr-cost-export DO-NOT-PUBLISH-no-tooling-enforces-this exported_at=<ISO8601 UTC> declared=<N> opted_in=<N> skipped_no_sentinel=<N> legacy_header_accounts=<N> corpus=<12 hex chars> corpus_override=<0|1>`

`corpus_override` was added during the testability-fixes pass: `1` flags a run against a `TRANSCRIPT_CONFIG_DIRS_FILE`-overridden (synthetic) root set rather than this machine's real declared accounts — see `docs/transcript-analysis.md`'s "Testing against a synthetic corpus" section. `0` and `1` are both real, expected values, not an error state.

**The digest is over corpus-derived values, not filesystem paths.** `hashlib.sha256("\n".join(sorted(<per-account identities>)).encode()).hexdigest()[:12]`, mirroring `_corpus_fingerprint`'s own construction (`redaction.py:167-176`) — naming the primitive explicitly because Python's built-in `hash()` is per-process salted, which would emit a different value on every real invocation while passing an in-process test vacuously. Each account contributes the `(captured_at, machine)` pair of its ledger's **first data row**, which `row34` establishes never changes or moves under append-only writes. This identifies the participating account set exactly as well as the paths would, discloses nothing the export does not already contain, and — unlike a digest over a small, structurally guessable set of config-dir paths — is not enumerable, since second-precision timestamps over a multi-year span carry real entropy. Hashing the resolved root paths was the first design and was rejected on that ground.

The digest certifies **ordinal/account comparability only**. It is orthogonal to schema drift, which the column-name-driven join handles independently — two exports of the same accounts across a ledger-schema change share a digest despite differing columns. Like `_corpus_fingerprint`, it is a same-corpus indicator, not a security boundary, and the docs say so.

`scope._DO_NOT_PUBLISH_BANNER` (`scope.py:471-473`) is **not** reused: its text names "real project names and session IDs," false for this artifact, and it is gated on `--no-redact` and printed to stderr rather than written into a file. Its 30+ existing occurrences all sit behind a genuine runtime gate, so the export's marker states inline that nothing enforces it — otherwise a reader who has met the phrase elsewhere in this file may take its presence as evidence the artifact was already vetted, and skip the manual review M15 depends on.

`legacy_header_accounts` needs a source the reused parser cannot give: `row33` establishes `_parse_pr_cost_ledger_file_text` discards `is_legacy_header`. Rather than widen that function's signature — which would drag in its two other call sites (`:7735`, `:8437`) under the structural-siblings rule — the export peeks at `lines[0]` of each account's raw text and compares it against `_PR_COST_LEDGER_LEGACY_HEADER_LINE` before handing the text to the parser. One comparison, no shared-contract change.

A sidecar file was set aside as the heavier of two equally effective options — it would need its own `O_EXCL`/`0o600` treatment for no gain over one line in the file already being written. Nothing in this codebase reads the export back, so a leading comment line creates no internal parsing-contract conflict; it does create one for the artifact's actual consumer, which the docs address.

**M15 — The publication boundary is documented, not enforced beyond M8, and the plan says so.** `anchors: row5, row6`. M8 makes it impossible for the tool to write the export into any git working tree — genuine enforcement. Everything after the file exists is outside the tool's reach: `docs/pr-cost.md:105-112` already documents this helper's blind spots (cloud-sync folders, bare-repo dotfile managers) for the ledger; a `cp` into the repo is a third, and a hand-written case-study table of row figures is a fourth no file-path check could ever see.

Extending `deny-private-project-refs.sh` with a detector was considered and rejected: a regex on `account-[0-9]+/(repo|pr|branch|host)-[0-9]+` collides with the documentation that explains the format — this plan's own test coverage asserts `account-1/repo-1` appears, and the CHANGELOG and docs carry examples — so it would block this very PR and need an allowlist, which is the compounding-defensive-layer shape CLAUDE.md warns against. A header-line detector fires only on a verbatim TSV paste, the accident least likely to happen and most obvious on review. Neither earns its place.

The rule therefore lives in prose, split to avoid restatement: the **prohibition** in root `CLAUDE.md`'s "Also redact structural fingerprints and provenance" subsection (which already covers it generically — what is missing is the named instance, and it earns one because the export's cells *are* tokenized, so the artifact looks redacted and an agent writing a case study will not spontaneously classify tokenized figures as private-corpus-derived); the **mechanism and safe-aggregate guidance** in `docs/pr-cost.md`, deferring to `CLAUDE.md` for the prohibition itself.

**M16 — Fix `_latest_pr_cost_row`'s tie-break to last-wins.** `anchors: row15, row16`. In scope under Axis 1's "required to make the ticket's change correct" carve-out, where *correct* means **M13's own correctness claim is honest** — not that anything crashes without it. M13's entire value to a consumer is "one row per key, correctly current"; shipping it over a selection that resolves ties backwards makes that guarantee false in exactly the case a corrected PR creates. The asymmetry that justifies touching a live write path: on `--record` a tie is a one-off rare event, but once a tie exists in a ledger it resolves wrong on *every* future export run, indefinitely.

Break ties by append position — `max(enumerate(matches), key=lambda p: (p[1]["captured_at"], p[0]))[1]` — in the shared helper rather than duplicating a corrected selection beside the existing one, per CLAUDE.md's structural-siblings rule. Behavior-identical at both existing call sites (`row16`), independently verified by two reviewers, so it carries no migration risk, and it also corrects the live `--force` path.

**Open decision left to the engineer:** none. Two micro-choices were settled by default: the `account` cell emits the full label `account-1` rather than the bare integer, because the label is the prefix of every token in its own row so a consumer can check row-internal consistency by string equality; and `correction_count` counts prior captures, so an uncorrected row carries `0`.

## Addendum: deterministic machine identifier for `--record`

### Context

Stop `--record` from taking the `machine` column's content from a human or an agent: the tool generates the identifier once per config directory, persists it locally, and stamps it automatically. `machine` is the one export column `pr-cost-export` deliberately never tokenizes (`docs/pr-cost.md:113, 115`), so an operator following the natural convention of naming machines after clients (`acme1`, `clientx`) writes an org name, in the clear, into an artifact this PR explicitly builds to leave the machine — a High-severity finding from a security review of the export (referred to below as **the CISO finding**: an operator-chosen machine label can leak an organization's identity into the redacted export). That review's own recommended fix was documentation telling operators to choose non-identifying content; the engineer rejected it, because the failure actually observed was not a careless CLI invocation but a **prior agent session asking a human what to name the machine**. A doc instruction does not reach that path — it *is* that path's input. The defect is the existence of a question to ask, so the fix deletes the surface that invites it rather than constraining the answer. This blocks #948 and lands as further commits on this branch.

**What this does not do.** Rows already recorded under hand-chosen values are not migrated, rewritten, or reconciled by this mechanism itself — the ledgers are append-only and hand-editing them is prohibited (`docs/pr-cost.md:60`). The mechanism stops new rows from repeating the mistake; it cannot fix history by itself. Separately, the engineer confirmed that their own `pr-cost-ledger.tsv` carries a single legacy value across all rows and wants it corrected once by hand — a private, unshipped, run-it-yourself script kept outside this repo is the answer to that, not a feature this addendum ships. See **Out of scope**.

### Approach

Both `--record` paths stop reading a machine identity from the command line. A shared helper reads `<config-dir>/machine-id`, and on first use generates `secrets.token_hex(4)` — exactly eight lowercase hex characters — and persists it atomically via `tempfile.mkstemp` plus `os.link`. `cost-ledger`'s `--machine-label` is deleted outright; `pr-cost` keeps the flag in its surviving read-mode-filter role and refuses it when combined with `--record`. The hostname check goes with the human choice it guarded.

**Root problem (addendum).** The `machine` cell's *content* is operator- or agent-chosen and validated only for shape (`_MACHINE_LABEL_RE`, `:6668`) and against one specific value (the local hostname, `:7239`, `:8392`), so nothing stops it naming an organization — in the export, in the terminal, and permanently at rest in both ledger files. The threat the design must hold is that no path remains by which a human's or an agent's choice reaches that cell, including the path where an agent reads a doc or a `--help` string and asks a human to supply one.

**Givens** (fixed conditions the design does not reach):

- **G4.** The `machine` column's name, position, and `^[a-z0-9]{1,8}$` shape are a shipped on-disk format that every existing row in both ledgers and both parsers depend on (`:6832`, `:7563`). This plan changes only how the value is *produced*; changing the column is a ledger-format migration with its own backward-compat contract — the same reason **G2** gives for `host`/`repo`. Recorded also under **Out of scope**.
- **G5.** No non-identifying, stable, machine-bound input exists to derive an identifier from. Hostname, MAC address, hardware serial, and `platform.node()` are each exactly the class of content this plan exists to keep out of the column, and a truncated digest over a guessable input is confirmable by anyone holding the export — the enumeration objection **row34** already sustained against hashing resolved root paths. "One machine" is therefore approximated by "one file this tool wrote," and its location is a design choice (M17), not a discovery.

**Mechanisms.**

**M17 — Generate the identity in-tool and persist it at `<config-dir>/machine-id`, resolved through the module-global `config_dir()` and deliberately *not* through `COST_LEDGER_PATH`/`PR_COST_LEDGER_PATH`.** `anchors: root, row41, row42, row43, G5`. Two lighter primitives that avoid a new file at all:

- *Lighter A — derive the value at runtime from a stable local input, storing nothing.* Set aside per **G5**: every hardware or host input is identifying, and the one non-identifying candidate (the config-dir path) is structurally guessable, so an 8-character digest over it is confirmable by anyone holding the export — the objection **row34** already sustained. It also silently changes identity if the operator ever moves or renames the directory.
- *Lighter B — infer the identity from the ledger's own most recent row's `machine` cell.* Set aside on **row43**: with either env override pointed at a shared or synced file, this imports another machine's identity; an absent or freshly-created ledger mints a new one with no signal; and the weekly and per-PR ledgers would drift apart on any machine where one exists and the other does not.

A machine-global path (`Path.home() / ".claude" / "machine-id"`, ignoring `CLAUDE_CONFIG_DIR` — the precedent `declared_roots_file()` sets at `_config_dir.py:33-39`) was the other real candidate and is set aside on **row41**: it writes into the contributor's real home directory, and CI's, on every `--record` test, and de-isolating it would need `Path.home` monkeypatched at ~80 sites. The consequence is **row54**'s per-account scope; the escape hatch needs no code, because `open()` follows a symlink on read and `os.link()` refuses to replace one — an operator wanting a single identity across accounts copies or symlinks the file, and the docs say so. Following a symlink to adopt a shared identity also inherits that target file's own mode rather than the `0o600` M20 guarantees for a tool-generated file; the docs note this is the operator's own responsibility, not a mechanism defect. This is deliberately the *opposite* of `docs/pr-cost.md:86`'s sentinel-symlink warning, which the new doc text must acknowledge so the two do not read as contradictory: a shared consent gate defeats a per-account opt-in, a shared identity is a legitimate operator choice.

**M18 — One identity shared by both subcommands, not one per ledger.** `anchors: row35, row50, row54`. Both columns are named `machine`, both are validated by `_MACHINE_LABEL_RE`, and the operator-facing point of the column is comparing figures for the same machine across the two ledgers — which works today only because an operator passes the same label to both. Two independently generated tokens would break that silently and buy nothing, since no tool joins the two ledgers and there is no key collision to avoid.

**M19 — `secrets.token_hex(4)`, not `random`, not a UUID, not a wider charset.** `anchors: row35, row36`. Four bytes render as exactly eight lowercase hex characters, the maximum `_MACHINE_LABEL_RE` admits and a strict subset of its class, so nothing downstream changes — that is the whole reason for the length. `random` is already imported at `:17` and is the tempting shortcut; it is rejected because all three of its uses in this file are `random.Random(seed)` for reproducible sampling (`:9635`, `:9964`, `:10024`), so a fourth, unseeded use would sit two paces from three deterministic ones and invite a later "make it seedable for tests" change that emits an identical identifier on every machine. `secrets` is the standard library's own documented answer for token generation (**row36**), which is what CLAUDE.md §Ground every choice requires before hand-rolling anything identity-adjacent. The value is an identifier, not a credential — nothing authenticates against it, so guessing it grants nothing; the only property 32 bits must carry is collision resistance across the handful of identity files one operator ever creates. `secrets.choice` over a 36-character alphabet (36⁸) was set aside as a charset constant and a loop bought for entropy the collision analysis does not need; `uuid.uuid4().hex` was set aside as 32 characters that would have to be truncated anyway, under a name implying a uniqueness guarantee the truncation discards.

**M20 — First use: read, else create via `tempfile.mkstemp` + `os.link`; on `FileExistsError` from the link, re-read and adopt what is there.** `anchors: row44, row45, row32`. Both this mechanism and **M7** refuse to clobber and both use atomic filesystem primitives, but M20 diverges from M7 in two ways: M7 aborts on `EEXIST` because clobbering an operator-named destination is the harm, while here another process establishing the identity first is correct to adopt, because the harm is two identities for one installation; and M20 cannot use `os.open(..., O_EXCL)` directly, because that primitive is atomic for *creation* but not for *creation-with-content* — a losing racer could read the winning process's file in the window between its `os.open` and its `write()`, land on empty content, and hit the read-side refusal below over ordinary concurrency, not corruption. `tempfile.mkstemp(dir=<config-dir>, prefix="machine-id.")` (mode `0o600` by construction) writes the token to a private temp file first; `os.link(tmp_path, target_path)` then publishes content and existence in one atomic step, so no reader ever observes a partially-written target. `os.unlink(tmp_path)` runs in a `finally` regardless of outcome. On `FileExistsError` from the `link()` call, re-read the target and adopt its value — another process's link already won. Any other `OSError` from `mkstemp`/`link` (permission, disk full) is caught the same way **M7** catches `OSError` around its own create call, so it surfaces as this tool's own refusal rather than a raw traceback. `tempfile` and `errno` are already imported (`:25`, `:10`); no import beyond `secrets` is new.

The race is real — `cost-ledger --record` and `pr-cost --record` can run concurrently, and each resolves identity before taking its own ledger lock. The ledger's own publish primitive (`os.replace`, `:7740`) is wrong here precisely because it clobbers: two racers would each install their own token and each stamp rows with the one it generated. The heavier alternative — an `flock` sibling file reusing `_acquire_cost_ledger_lock` (`:7088-7107`) — adds a second file and a timeout policy to serialize what the link already makes safe, and that lock's critical section is the ledger read-check-write, which identity resolution precedes. A bounded retry on the read side was considered and rejected: CLAUDE.md's numeric-literal-in-retry-context rule requires a primary-source-grounded interval, and no vendor or protocol document states how long a concurrent writer takes to persist eight bytes, so the constant would be ungroundable by construction.

Read-side handling, all of it load-bearing:

- Strip, then match `_MACHINE_IDENTITY_RE` (`^[0-9a-f]{8}\Z`) — a new constant, deliberately narrower than `_MACHINE_LABEL_RE` (`^[a-z0-9]{1,8}\Z`, unchanged and still live at all three parser sites and at `pr-cost`'s read-mode filter, **row35**). `secrets.token_hex(4)` can only ever produce eight lowercase hex characters, so the identity file's accepted class is exactly its generator's output class — a hand-written value that is valid under the wider `_MACHINE_LABEL_RE` (e.g. `acme1`) but outside `_MACHINE_IDENTITY_RE` is refused rather than silently adopted. This is what makes M23's "closed, not narrowed" claim actually hold: shape validation alone previously accepted anything the ledger's own column would, which is the residual **row53** exists to close.

- **A retry loop making a generated identity differ from the local hostname** (**M22**). The residual is a `token_hex(4)` collision with an eight-lowercase-hex-character hostname; accepted, not re-checked.
- **A `machine` filter for `cost-ledger` read mode.** `cost-ledger` has never had one (**row38**); adding one to give the removed flag something to do would be a new feature wearing a deprecation's clothes.
- **Editing the eight pre-existing `.claude/plans/*.md` files that mention `--machine-label`** (**row48**). Historical records under CLAUDE.md §Scope discipline Axis 3 — this plan document itself is a ninth, live hit, excluded from that count since it is not a historical record.
- **A general-purpose, shipped backfill subcommand** for relabeling legacy `machine` values across arbitrary ledgers. Evaluated and rejected by a `staff-data-engineer` consult: safe only when a ledger contains exactly one distinct legacy value (otherwise a rewrite risks silently merging what may be genuinely distinct machines, with no signal in the ledger to disambiguate), and even in the safe case it would need durable audit-trail machinery this ledger's plain-TSV schema has no home for without itself becoming a migration. The engineer's own single-value case is handled by the private script named above instead.
- **A retry loop or content screen catching a deliberately hand-written, well-formed identity.** An operator who writes exactly eight lowercase hex characters into `machine-id` before the first `--record` gets that value, accepted. This is not the CISO finding's failure mode: eight hex characters cannot name an organization, so hand-crafting a collision buys the operator nothing the mechanism exists to prevent. `docs/pr-cost.md:70` states the file is tool-written and inherits `:60`'s never-hand-edit contract, which makes this an unsupported act rather than an undocumented affordance.
- **Sweeping stray `machine-id.*` temp files** left by a crash between `tempfile.mkstemp`'s write and the `os.link` publish (**M20**). The next `--record` creates the identity normally; an orphaned temp file is inert and costs nothing to leave.

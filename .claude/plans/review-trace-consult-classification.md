# Plan: Make prescribed plan-architect consults machine-detectable

## Context

Make a `plan-architect MODE=consult` dispatch detectable from the transcript,
so `skill-fidelity-reviewer` records whether it saw one instead of staying
silent about the question.

`review-trace` classifies subagent dispatches into event kinds. One of them,
`reviewer-spawn`, is what `skill-fidelity-reviewer` reads to confirm that
`/code-review`'s required specialist dispatches actually ran. `plan-architect`
is absent from that classification. So a `MODE=consult` dispatch leaves no
trace either tool can see, even though `/code-review`'s Fix route and the
round-3 consult hook both prescribe one.

The gap surfaced on a live branch. Establishing that the prescribed consult
had in fact run required hand-tracing the raw session transcript, because
neither a grep nor the fidelity reviewer surfaced it. The reviewer's silence
is the worse half: it reported nothing at all rather than reporting the
question as one it could not answer.

## Approach

Add a fifth `review-trace` event kind, `architect-consult`. It is emitted when a main-thread `Agent`/`Task` tool_use block carries `subagent_type == "plan-architect"` and a first prompt line other than the literal `MODE=plan-sections`. That is the same classification `log-reviewer-round.sh:118-125` already applies to write §45's latch, re-expressed in a second runtime. A parametrized behavioral-parity table run against both runtimes' existing test harnesses holds the two in agreement.

Then give `skill-fidelity-reviewer` a mandatory-emission step over that event kind. It has exactly two outcomes: a `[DISCLOSED]` "consult observed" line, or an explicit *dismissed as undecidable* record. It can never honestly emit `[SILENT-SKIP]`.

Ledger rows 1-3 below carry the three engineer decisions this design is built on, tagged `[engineer-verified]`; the subsections here refer to them by row number. Row 2 in particular — report that a consult occurred, never which prescription it satisfied — is what caps the verdict set above.

### What the new check asserts, and why rows 2 and 3 pull against each other

The check **fires** on exactly the precondition the existing spawn-dispatch check already uses — a `review-trace` timeline present in the dispatch prompt — which in practice means every `/ready-for-review` Step 4 run. It is not conditioned on anything about consults, because no precondition about consults is observable from the reviewer's evidence.

It **asserts** one of two things, and must always emit one of them:

- **Consult observed.** One or more `architect-consult` rows on this branch's timeline, reported with their timestamps, as `[DISCLOSED]` — a recorded observation, never a finding.
- **No consult observed, prescription not decidable.** Zero such rows. Recorded under the agent's existing *Dismissed as undecidable* grouping with the one-line reason, counted in the pointer line's `<M>`, never in `<N>`.

It **cannot assert**: that a consult was prescribed; which of §37 / §42 / §45 prescribed it; that an observed consult was the prescribed one rather than an unrelated earlier one; that the consult asked the right question or that its return was honored.

**It can never legitimately emit `[SILENT-SKIP]`.** Three independent reasons, any one of which is sufficient:

1. **Absence is not evidence.** `cmd_review_trace` calls `_resolve_project_scope` without `include_subagents=True`, and `_review_trace_session_events`'s own comment (lines 1440-1443) states sidechain tool_use blocks are never present. A consult dispatched from inside a subagent — a `/code-review` pass running in a delegated agent taking §42's Fix route — is structurally invisible. Zero rows therefore means "no consult on a main thread in the scanned corpus," which is not "no consult."
2. **The prescription is invisible at two of three sites.** §37's explicit-user-ask gate is "not mechanically detectable, and deliberately not made so" (`docs/design-decisions.md:548`). §42's prescription lives in `/code-review`'s own `Fix route:` narration, which §25 already ruled out as an evidence source. A verdict of "unsatisfied" requires knowing an obligation existed; the reviewer cannot know that.
3. **Row 2 forecloses the remaining site.** §45's deny *is* visible — `require-architect-consult.sh` denials land as `denial` rows in the same timeline — so a "deny present, no consult after it" correlation would be decidable. That arm is rejected on two grounds. It would make the instrumentation claim a specific prescription site, which row 2 forbids. And it duplicates enforcement the `PreToolUse` gate already performs by blocking the reviewer fan-out until the latch exists — a detective layer closing a gap the preventive layer does not leave open, which is the compounding-defensive-layers tell CLAUDE.md names as a wrong-foundation signal.

**Why this is still a check step rather than visibility-only.** The incident in Context is not an unenforced obligation; §45's hook enforces it. It is *silence*: coverage was declined and nothing said so, and a human had to hand-trace a raw transcript. The agent's dismissal protocol (`skill-fidelity-reviewer.md:178-196`) is the instrument for that failure — a required, visible record that coverage was declined rather than clean, written into the findings file `/ready-for-review` reads. A timeline row alone would sit in report output nobody is obliged to read; the mandatory emission converts it into a statement.

**The step emits a required verdict but can never fail a gate.** That is the ceiling row 2 imposes, not a narrowing of row 3. A step that could return "unsatisfied" would need subagent records loaded, narration parsed, and per-site attribution — contradicting row 1, §25, and row 2 respectively.

### Resolving §25's "never assistant prose"

Reading a first line to test equality against a fixed literal is **not** ingesting assistant prose in §25's sense, provided the timeline emits only the classification result. §25's parenthetical — "(subagent_type/timestamp/branch metadata, never assistant prose)" — characterizes the reviewer's *evidence surface*, and its stated purpose is keeping "the deviating session's rationale" out of the reviewer's context. `MODE=consult` is not rationale; it is a protocol selector that `plan-architect.md:28-31` requires the caller to emit, whose value changes which grammar the dispatched agent answers in. It happens to travel in a prose-typed field.

That argument only holds if the property is structural, so the design makes it structural: classification happens inside `_review_trace_session_events`, the prompt string is never stored on the event dict, and the event carries a two-valued result plus the metadata the other kinds already carry. No printer can leak what no event holds. A test pins that no prompt-body substring reaches `review-trace` output.

**On evasion-training.** §25 rejected substring-matching known-invalid rationale phrases because "it trains its own evasion" — that matcher keyed on model-chosen vocabulary, so selecting on the literals selects for paraphrase. First-line `MODE=` matching does not have that property, for two reasons that must both hold. The token is prescribed by `plan-architect.md` and `plan-it` Step 5, not chosen by the dispatching session. And the fail-safe direction inverts the gradient: absent or unrecognized ⇒ classified as consult, so omission *increases* detection. Evading detection requires emitting `MODE=plan-sections` on a dispatch intended as a consult, which makes `plan-architect` read `plan-it/SKILL.md` and answer in plan-section grammar — self-punishing. The cost, stated: an unmarked plan-sections dispatch is misclassified as a consult. That is not new risk — it is exactly the classification the latch hook already applies, so the two runtimes stay in agreement — and because the check has no unsatisfied verdict, a false-positive consult can never suppress a finding; its worst effect is a `[DISCLOSED]` line where a dismissal was correct.

**§25's precedent supports row 3.** §25 fixed a structurally identical gap — an obligation with no artifact a reviewer could see — by extending this same agent "per §9's 'extend' arm" rather than adding a hook, and §9 names extend as the "cheap. Default move." This change is the same move on the same agent, one step further. The analogy breaks in exactly one place, and the break is why the verdict set above is what it is: §25's extension could reach a real `[SILENT-SKIP]` because the reviewer can independently re-derive which Change-type rows a diff matches. Here the reviewer cannot re-derive whether a consult was owed. Same method, weaker decidability, so a weaker output set.

## Out of scope

- **Extending `_REVIEWER_EXACT_NAMES` or `_is_reviewer_subagent_type`** to cover `plan-architect` (row 11a). Guarded by row 16's negative test.
- **Parsing `/code-review`'s `Fix route:` or `Spawn decisions:` narration** as a second compliance surface. It is assistant prose, it is the exact class §25 rejected, and matching it would train paraphrase.
- **Reading `<config-dir>/.architect-consult-latch.d/**` from the agent** (row 11b).
- **Per-site attribution** — telling §37 from §42 from §45. Forbidden by row 2 and by G2.
- **Making §37's explicit-user-ask gate detectable** (G2).
- **A deny-correlation arm** in the reviewer (row 13), even though it is technically decidable.
- **Loading subagent records into `review-trace`** (`include_subagents=True`). It would close row 5's blind spot, but it changes scan cost and output volume for every `review-trace` consumer and reopens the §25 blindness question with real sidechain prose in scope — a separate decision with its own plan.
- **A `--consult-only` or dispatch-content CLI filter.** The reviewer receives the whole branch timeline; no consumer needs the filter.
- **Any change to `require-architect-consult.sh`, `log-reviewer-round.sh`'s behavior, the latch's shape or sweep interval, `marker.sh`'s kind list, or `code-review/SKILL.md`'s Fix-route text.** The latch's content-free, presence-only, 30-day-swept shape is reachable — this repo owns the hook — but §45 chose it deliberately, and this design does not read the latch, so changing it would buy nothing here.
- **Making the `architect-consult` event completion-gated rather than initiation-gated** (row 18). Matching `log-reviewer-round.sh`'s `PostToolUse` semantics would require correlating each `Agent`/`Task` tool_use block with its `tool_result`, a second pass `review-trace` does not currently make. The consequence is capped at an overstated `[DISCLOSED]` line, so the plan documents the limit instead of building the correlation.
- **`cmd_skill_invocation`.** It filters to `Skill` blocks at line 2102 and sees no Agent/Task dispatches at all; widening it is a second mechanism for the same signal the new event kind already carries.

# Handoff active-bypass marker: close the bootstrap window

## Context

Close the remaining window in which `nudge-handoff-near-context-cap.sh`'s hard block can truncate `/handoff` before the skill has a chance to suppress it. PR #760 added a `handoff` active-bypass marker (`marker.sh activate handoff`) that the hook's hard-block branch checks (`HANDOFF_ACTIVE -eq 0`, hook lines 652-658) — but that marker activation is the skill's third step, issued as a separate Bash call after `mkdir` and the `--check` call, both of which follow the initial `Skill(handoff)` load. Each of those is its own `PostToolBatch`-checked tool-call batch. If the hard-block condition (`ESTIMATE >= BLOCK_AT && LAST_FIRED_AT` set) is already met at the moment `/handoff` is invoked — the exact scenario the block exists to drive the engineer toward — the very batch that loads the skill, or the `mkdir`/`--check` batches that follow it, can trip the block before `marker.sh activate handoff` ever runs, since `HANDOFF_ACTIVE` is still 0 at that point. `exit 2` then stops continuation, ending the turn with no marker set. **Severity correction** [verified: `nudge-handoff-near-context-cap.sh:592,671`, `docs/handoff-nudge.md:34`]: `nudge-handoff-near-context-cap.sh:671` writes `FIRED_MARKER` inside the hard-block branch, immediately before `exit 2`, and the re-arm suppression at line 592 exits 0 on every subsequent fire until the estimate advances `REARM_SPACING` (default 80000) past that point. So `/handoff` does not wedge — the failure is one lost turn that self-heals on the immediate retry, inside an 80,000-token runway, not "no forward progress." The fix below is still worth shipping, but for a different reason: it removes the block's dependence on the model reading and obeying skill prose in the right order, not because a session gets stuck.

## Approach

Add a `PostToolUse` hook matched on the `Skill` tool that activates the `handoff` bypass marker as soon as the handoff skill loads, and move the skill's own `marker.sh activate handoff` step to be its first instruction. The hook is the primary mechanism — `PostToolUse` fires per individual tool call and resolves before `PostToolBatch` evaluates the same batch, so the marker is already live when `nudge-handoff-near-context-cap.sh` evaluates the very batch that loaded the skill. The reordered skill step is the fallback for the case where the hook does not fire at all.

### Assumption ledger

**Root problem.** `nudge-handoff-near-context-cap.sh`'s hard block consults an active-bypass marker that only a model-issued Bash call sets, so the block can fire on the batch that loads `/handoff` — before any Bash call in that skill has run — costing one turn on a session that is already doing the right thing.

**Givens**

- **G1.** The harness's `PostToolBatch` stdin payload carries no per-tool-call information. Anthropic owns the payload shape; `docs/handoff-nudge.md:134` records that it was reverse-engineered empirically rather than specified.
- **G2.** A settings.json `matcher` scopes on `tool_name` only, never on `tool_input` contents. The harness owns matcher semantics; every matcher in this repo and in the hooks doc is a `tool_name` regex.
- **G3.** `exit 2` from a `PostToolBatch` hook stops the agentic loop with no JSON envelope, so a blocked turn ends and needs a fresh human prompt. Harness contract, recorded at `nudge-handoff-near-context-cap.sh:659-660`.
- **G4.** An active-bypass marker stays live until its stored PID dies or the owning skill deactivates it; there is no age bound. `_lib.sh:851-859` names this as a known weakness of `_lib_active_bypass_marker_live` and names age-bounding as the fix, deferred outside this plan.

**Mechanisms**

- **M1. New `PostToolUse` hook `activate-handoff-bypass.sh`, matched on `Skill`, self-filtering to the handoff skill inside the script.** The only execution point that runs after the `Skill(handoff)` call and before that batch's `PostToolBatch`. `anchors: row1, row2`
  - *Lighter primitive A — reorder the skill step only, no new hook.* Fails: the reorder cannot help the `Skill(handoff)` batch itself, because the model only learns to issue `marker.sh activate handoff` by reading the Skill tool's result, which arrives after that batch has already resolved. `anchors: row1`
  - *Lighter primitive B — have the existing `PostToolBatch` hook tail the transcript for a recent `Skill(handoff)` `tool_use` record.* It already holds `transcript_path` and already tails the file, so this needs no new registration. Fails on cost and fragility: it adds an unversioned second schema dependency to a hook that already carries explicit schema-drift detection (`nudge-handoff-near-context-cap.sh:559-569`) for the one schema it reads, and a fixed tail window cannot distinguish "handoff invoked this turn" from "invoked forty turns ago." `anchors: row2`
  - *Lighter primitive C — activate as a side effect of the `--check` invocation the skill already makes.* Fails twice: `--check`'s documented contract is that it writes nothing (`nudge-handoff-near-context-cap.sh:34-36`, `docs/handoff-nudge.md:66`), and `plan-it` Step 7 calls it in sessions with no handoff intent; and it is still the second batch, so it does not cover the skill-load batch either. `anchors: row1`
  - *Variant considered — `PreToolUse` on `Skill` instead of `PostToolUse`.* Set aside: it fires even for a call that is then denied or errors, and it puts a marker write on the blocking path. `PostToolUse` is already early enough. `anchors: row2`
- **M2. The hook invokes `marker.sh activate handoff` as a subprocess rather than writing `.handoff-active.d/<session_id>` directly.** Keeps exactly one writer of the active-marker layout, and reuses the code path PR #760 already validated against the nudge hook's read side. `anchors: row4, row5`
  - *Alternative — direct write from the hook via `_lib_resolve_claude_pid`,* the idiom `log-routing-read.sh:41-51` uses and which `_lib.sh:949-952` explicitly anticipates ("so a hook … can resolve its own session's live PID directly, with no subprocess spawn"). Set aside: it would fork the marker layout into a second writer, or force extracting a shared `_lib` helper and converting all five of `marker.sh`'s per-skill activate arms — a five-gate refactor riding along on a one-gate fix. The subprocess costs one process on `Skill(handoff)` loads only, a handful per session at most.
- **M3. The hook exits 0 when `.agent_type` is non-empty.** `marker.sh` resolves its session by walking process ancestors to the Claude main process, so a subagent that loads the handoff skill would otherwise disarm the *parent* session's hard block — the same attribution hazard `enforce-marker-script-shape.sh:110-115` guards for model-issued marker writes. The nudge hook's own subagent gate (`nudge-handoff-near-context-cap.sh:527-530`) means the block never fires in a subagent anyway, so there is nothing there to suppress. `anchors: row5, row12`
- **M4. The hook matches the skill-name field on its final component after the last `:` and `/`, not on exact equality with `handoff`.** This repo's own `CLAUDE.md` documents that stow-source skill copies render directory-qualified (`.claude/worktrees/<branch>/claude:code-review`) and that plugin skills render as `plugin:skill`, so an exact-string test would miss real invocations. **Accepted risk:** this suffix match has no namespace binding, so any plugin or stow-source skill anywhere on the machine whose bare name happens to be `handoff` — not necessarily this repo's own skill — trips the same activation. Not attacker-exploitable under this plan's threat model (disarming this nudge has no data-exposure payoff), and its effect is identical to row 10's accepted degradation, but it is a real name-collision path. Accepted rather than scoped to a prefix allowlist (e.g. this repo's stow path or `enabledPlugins` entries), because that allowlist would itself be a heavier mechanism than a Low-severity, non-adversarial collision risk justifies. `anchors: row3, row11`
- **M5. Reorder `handoff/SKILL.md` so `marker.sh activate handoff` is the first instructed step, and add one prose sentence on the not-warranted path directing deactivation.** Once M1 activates the marker at skill load, activation already precedes the warranted-check, so the reorder's only cost is already paid; what it adds is fallback coverage of the `mkdir`/`--check` batches when the hook does not fire, and consistency with the four peer skills that all put activation first. The deactivate sentence is the symmetric partner of the skill's existing post-write deactivate step, not a second defensive layer over M1 — M1 has no cleanup path of its own and needs one. `anchors: row6, row7`
- **M6. No change to `enforce-marker-script-shape.sh`.** It dispatches on `$TOOL_NAME` from a PreToolUse tool payload (`enforce-marker-script-shape.sh:233-296`); a hook's own subprocess is not a tool call and never reaches PreToolUse. Independently, `activate … handoff` is already inside its `MARKER_SHAPE` allowlist (`enforce-marker-script-shape.sh:576`) and enumerated in its denial message (line 644), so the shape would pass even if routed through the tool layer. `anchors: row8`

### Phasing and dispatch split

**Phase 1 — pin the field name (row 3). Not delegable to `code-writer`.** Resolve the `Skill` tool's skill-name field from an existing transcript rather than by editing any config: `jq` a session JSONL under `~/.claude/projects/*/` for a record where `.message.content[]?` has `.type == "tool_use"` and `.name == "Skill"`, and read its `.input` keys. Use Bash `jq`, not `Read` — `deny-data-file-reads.sh` gates JSONL reads and a `Read` would also burn context on transcript bulk. If no such record exists in any local transcript, fall back to the empirical-capture method `docs/handoff-nudge.md:134` records for this hook's own `PostToolBatch` shape: register a scratch `PostToolUse`/`Skill` hook writing `$INPUT` to a temp path, invoke any one skill, read the capture, and revert the registration. **Do not paste a captured payload verbatim into the plan file, PR body, or commit message** — transcripts mix private-project content, and this repo is public; extract key names only.

Also confirm `.agent_type` is present and non-empty on a **subagent-issued** `Skill` call specifically, not by analogy from other tools' precedent — M3's guard depends on this field existing on `Skill` payloads, which is unverified (row 3 covers only the skill-name field). Search for a `tool_use` record of this shape inside a subagent's own transcript; if none exists locally, extend the empirical-capture fallback above to dispatch a throwaway subagent that invokes any one skill and capture its `Skill` payload the same way.

**Phase 2 — one `code-writer` dispatch** covering the hook, its registration, the skill edit, both docs, and the tests. Do not split: the hook script, its settings.json entry, and its test share the field name pinned in Phase 1, and splitting would force restating that shared context in each prompt.

## Out of scope

- **Age-bounding active-bypass markers.** `_lib.sh:851-859` names this as the real fix for a bypass outliving the skill invocation it was scoped to, and notes `require-routing-read.sh` already bounds a sibling marker that way. It affects all five gates, not just `handoff`, and belongs in its own change.
- **The abandon-without-declining path (row 10), widened by this plan.** M1 changes this path's trigger surface, not just its timing. Pre-plan, the marker is set only by an explicit, model-issued `marker.sh activate handoff` Bash call, so a session that loads and then abandons the skill before that call runs never sets the marker at all — there is nothing live to abandon. Post-plan, M1 sets the marker automatically at skill load, before any of the skill's own logic executes, so skim-and-discard, interrupted-before-first-Bash-call, and mid-skill-compaction abandonment all newly reach this weakness. The failure mode — hard block silently degrades to advisory for the rest of the session — is the exact scenario this whole nudge system exists to prevent. Still out of scope here: closing it needs the age bound (`_lib.sh:851-859`), not another prose step. But a future age-bounding fix should be prioritized against this widened baseline, not the pre-plan one.
- **`_lib_capped_for`'s uncapped-fallback / no-force-kill gap.** `_lib.sh:1197-1202` already documents this as an accepted, unfixed residual risk for `_lib_worktree_collision_guard` (also `_lib_capped_for`-wrapped), called from `require-worktree-for-git-writes.sh` (`Bash`, `PreToolUse`) and `require-worktree-for-file-writes.sh` (`Edit|Write|MultiEdit`, `PreToolUse`) — both fire more often per session than `Skill` will, and both block *before* the tool call executes, a more consequential position than this new hook's post-execution block. This plan's hook inherits that identical, already-accepted gap rather than introducing a novel exposure. Closing it — a harness-level `timeout` key, or `-k`/`--kill-after` support in `_lib_capped_for` — is a shared-infrastructure fix affecting every `_lib_capped_for` caller, not scoped to this plan. Accepted here as a documented residual risk (see Critical files' entry for `activate-handoff-bypass.sh`).
- **Retuning `HANDOFF_NUDGE_BLOCK_AT` or `REARM_SPACING`.** The severity correction in Context shows the runway is what makes the residual small, but `docs/handoff-nudge.md:32` reserves that retune for an extended `rearm-backtest` once escalation-fire data exists.
- **A `Skill`-argument-level settings.json matcher.** G2 makes this the harness's to provide; the in-script filter is the standing repo convention and needs no upstream change.
- **`docs/handoff-nudge.md`'s "hard block unreachable on a 200k-window model" limitation** (line 135) — orthogonal, untouched here. This is root-caused in-session (this branch's originating conversation): confirmed against the current hook (`claude/.claude/hooks/nudge-handoff-near-context-cap.sh:652-658`) and skill (`claude/.claude/skills/handoff/SKILL.md`'s ordering of the `mkdir` / `--check` / marker-activation steps), and corroborated by post-#760 hard-block log lines in `~/.claude/.handoff-nudge.log` showing `skills=-` (marker not live at fire time). Outcome: `/handoff` can always reach the point of setting its own active-bypass marker, on the very first batch that touches the skill, regardless of how far past `BLOCK_AT` the session already is.

# Memory audit nudge

## Context

Claude's per-project auto-memory store accumulates durable, standing facts
about repo/hook/skill behavior that belong in version-controlled docs
instead of ephemeral memory — as `memory-file-audit` demonstrated by
manually migrating five such facts and deleting seven memory files.
Without an automated check, this drift is invisible until someone happens
to notice. The outcome: a new on-by-default hook that nudges (never
auto-executes) a memory-store audit once the store crosses a size-based
threshold, pointing at a reusable skill/checklist for the
migrate-verify-delete workflow, with a kill-switch opt-out matching this
repo's other on-by-default hooks.

**Engineer's answers to the three open design questions (binding on the
architecture below):**

1. **Audit criteria:** reuse `ai-instruction-and-memory-files/SKILL.md`
   §5's existing anti-duplication heuristic as the audit playbook, applied
   uniformly across all memory types (`user`, `feedback`, `project`,
   `reference`) via its content-based test — "does this generalize into a
   rule already covered elsewhere (CLAUDE.md/AGENTS.md/a hook)?" — not a
   type-tag proxy. No `type: project` (or any other type) carve-out from
   pruning consideration; `type: feedback` is equally named in §5's
   heuristic ("feedback calibration... with the *why* story") as content
   that earns its keep, on the same footing as `type: project`'s
   "time-sensitive project context." Do not invent separate audit criteria
   for this nudge.
2. **Beads:** park `~/External/beads` (third-party CLI/Dolt-backed
   MEMORY.md replacement) as a separate future initiative. Out of scope
   for this plan.
3. **Path scoping:** reuse the existing glob-all-projects pattern from
   `require-memory-skill.sh` rather than building new per-repo
   cwd-to-directory-name path resolution. The nudge fires on total memory
   bloat across every project on the machine, not this-repo-specific
   bloat.
4. **Deletion enforcement — superseded.** The initial decision (during the
   first `/plan-review` round) was to close the skill's Step-5 Bash `rm`
   bypass of `require-memory-skill.sh`'s Write/Edit/MultiEdit-only dispatch
   by extending that hook with a Bash-command enforcement arm (M10). A later
   `/code-review` on the implementation empirically confirmed the arm's
   text-pattern-match heuristic is bypassed by ordinary, non-adversarial
   shell idioms (`cd`+relative-path, `$HOME` indirection) with no marker
   check at all — a compounding-defensive-layers pattern per this repo's
   CLAUDE.md, not a sound foundation to patch further. The engineer's
   revised decision: deletion (and, per decision 7 below, issue-filing)
   require live, per-item human approval inside the audit skill's own
   session, replacing the autonomous heuristic gate rather than patching it.
   Whether any part of M10 survives is re-derived in this rework's Approach
   section below.
5. **Classification gains a fourth verdict: file as GitHub issue.** For
   memory content that reveals a harness or tooling gap — the motivating
   example is a memory noting "route code edits through code-writer, not
   inline Edit," which is a fix owed to the harness, not a rule to document
   and move on from — Step 2's classification table gets a fourth verdict
   alongside migrate/delete-on-contact/keep.
6. **Classification dispatches to a new Opus-pinned subagent, waited inline
   — no background/async machinery.** The categorization judgment is complex
   enough to warrant Opus-level reasoning, and it fires rarely (gated by the
   nudge's re-arm band). The engineer initially asked for this to be
   dispatched non-blocking of "the main thread," then clarified: the skill
   already runs in its own session, invoked by name after the SessionStart
   nudge advisory (the same `skillOverrides: name-only`, nudged-by-name shape
   `error-mode-analysis` already uses) — there is no main thread to protect
   inside that session, so a normal dispatch-and-wait `Agent` call (the same
   shape `plan-architect` itself uses) is sufficient. `plan-architect` is
   explicitly not reusable here — it is hard-scoped to `/plan-it` Step 5 by
   its own description — so this needs a new, narrowly-scoped agent
   definition.
7. **The skill files the GitHub issue itself, gated by the same per-item
   live-approval shape as deletion** — not a draft-only handoff. Because
   `deny-private-project-refs.sh` does not scan `gh issue create`/`gh issue
   comment` bodies at all (confirmed this session — its own header names the
   gap, and `gh api` calls are scanned while `gh issue` ones are not), this
   plan's Approach section must state plainly which mechanism the filing
   step uses and, if it is `gh issue create`, that the pre-filing human
   approval is the *only* safety net against a redaction miss on a public
   repo — the usual hook backstop does not apply on this path.
8. **Deletion quarantines rather than removes (added during this round's
   `/plan-review`).** The `delete-on-contact` verdict's terminal act was
   `rm`, the only path in this design with zero durable artifact before the
   irreversible step — `migrate` and `file-as-issue` both land a commit or a
   public issue first. `ciso-reviewer`'s fix-or-ask finding on this asymmetry
   was put to the engineer directly: move the approved file into a
   quarantine directory instead of removing it, so the human approval still
   gates the action but the action itself becomes reversible. The engineer
   chose quarantine over accepting the residual. M14 and Step 6 below
   reflect this.

# Approach

## Concluded design

The Bash-command enforcement arm added to `require-memory-skill.sh` is reverted in full: a text-pattern gate that `cd`+relative-path and `$HOME` defeat is not a control, and patching it further is the compounding-defensive-layers tell rather than a residual-risk tradeoff. In its place, the `memory-store-audit` skill dispatches a new read-only, Opus-pinned `memory-store-classifier` agent for its classification step (now carrying a fourth verdict, *file as issue*), and every deletion and every issue-filing call pauses on its own blocking `AskUserQuestion` immediately before the single irreversible or external command — a person in the loop per item, with no new marker or hook machinery invented to hold that promise.

**Why the revert, and why nothing of M10 survives.** `ciso-reviewer` confirmed empirically, by running the shipped hook against an isolated `$HOME`, that `cd ~/.claude/projects/<name>/memory && rm MEMORY.md` and `rm $HOME/.claude/projects/<name>/memory/MEMORY.md` are both **allowed with no marker check at all**, while the literal-tilde-with-trailing-slash form is denied. Neither allowed form is an evasion technique; both are ordinary shell phrasing an agent reaches for unprompted. The arm therefore does not do the one job it was deployed for even for the one verb (`rm`) the audit skill actually uses. Three further findings compound rather than mitigate: the arm routes `_lib_active_bypass_marker_live`'s *already-documented* unbounded-liveness weakness onto an irreversible action for the first time (S3); it is the only layer guarding content this plan's own skill body calls unrecoverable (S4); and its `"matcher": "Bash"` registration makes `require-memory-skill.sh` fork `timeout`+`jq` on **every Bash tool call machine-wide**, with none of the `if:`-narrowing 10 of its 11 siblings in that matcher array carry (`staff-platform-engineer` Q2). The lighter primitive is not a better heuristic — it is not putting an autonomous gate on this path at all, and instead gating the *one place the deletion originates* (this skill's own step) with a person. That is strictly stronger than what the arm delivered, because a `cd` cannot route around a human.

Partial survival was weighed and rejected on evidence, not caution. Keeping the arm but correcting its disclosed-bypass list (ciso S1/S2's stated required property) leaves a `hook-class: gate` script whose header would have to say, accurately, that it misses the most common phrasings of the verb it names — a gate documented not to gate. Keeping it and bounding the marker's freshness window (S3) fixes the marker, not the pattern match, and touches shared marker machinery every other gate depends on for a control this plan is removing. Keeping only the allow-fixtures (S5) pins a boundary on deleted code. Every ciso, `staff-sdet`, and `comment-discipline-reviewer` finding scoped **only** to the Bash arm is therefore moot by removal, and is named as such in Out of scope rather than dropped silently.

**Why a live `AskUserQuestion` and not a marker.** This session's research found no precedent anywhere in this codebase for a marker gated on a live human answer: `_lib_active_bypass_marker_live` and `marker.sh activate`/`deactivate` are self-activated by the owning skill's own Step 0, and every review marker records a *review that ran*, keyed on a content hash. Retrofitting either shape onto "a human said yes to this specific file" would be new machinery, not reuse — and CLAUDE.md's default-suspect-over-powered-primitives rule points the other way. `plan-review`'s fix-or-ask disposition rule is the existing precedent for the lighter primitive: a blocking, concrete, one-line decision point raised at the moment of the consequential act. The honest limitation, stated in the skill body and in `docs/memory-audit-nudge.md`, is that a skill-body instruction is an instruction and not an enforcement — nothing blocks an agent that skips the pause. That residual is accepted because the alternative was empirically shown not to hold either, while taxing every Bash call on the machine.

**Why `gh api`, not `gh issue create`.** `deny-private-project-refs.sh`'s own header (lines 104–110) and `docs/private-project-redaction.md`'s "Known gaps" both state that `gh issue create`/`gh issue comment` bodies are never scanned — the dispatch has no `gh issue` branch at all. The hook's `IS_GH_API` branch, by contrast, sets on any `-f`/`-F`/`--field`/`--raw-field`/`--input` flag and appends the full command string to `SCAN_TARGET`, so an inline `-f body="…"` literal is scanned by the tracker-ID scan, the six always-on structural detectors, and the user-local blocklist. Memory content is the *highest-risk* content class this repo could publish — machine-local, per-project, and by construction dense with exactly the strings those detectors exist to catch. Discarding the second line of defense for that class, on the strength of one human "yes," is the wrong default when a scanned path costs the same. The consequence, stated plainly: the scan only runs when the session's cwd is inside a repo whose `remote.origin.url` contains `claude-config` (hook lines 292–301), so the filing call must run from the `claude-config` checkout — which is also the only repo this skill files into (see M13).

**Why the find cap becomes a precondition rather than a watchdog.** `staff-platform-engineer` requires that `_lib_capped_for`'s uncapped fallback never be silently load-bearing for a hook that blocks session start. Three routes were weighed. A bash `SECONDS`-based watchdog cannot work: `SECONDS` is only readable between commands, and a foreground `find` blocked on a stalled mount never returns control for the check to run. A backgrounded scan with a poll-and-kill loop does work, but costs `mktemp` + a single composed `trap` + a poll loop in a hook whose entire contract is "exits 0 on every path," cannot use `wait -n` (macOS ships bash 3.2 and `test_no_bash4_constructs.py` enforces that floor), and killing the backgrounded `find` orphans its `wc` children. Hard-failing `install.sh` blocks installation for every stock-macOS stow consumer without Homebrew coreutils — an enormous blast radius across all consumers, imposed by one advisory hook. The lighter primitive both reviewers' framing missed is to **remove the uncapped path instead of racing it**: probe for a timeout binary before the scan and exit 0 silently when neither resolves. That enforces the cap unconditionally by construction, costs two shell builtins, changes no install behavior, and degrades exactly the way an advisory housekeeping signal should — the nudge simply never fires on an unequipped machine, which costs the user a reminder rather than a session.

**Everything else from the prior design stands unchanged:** the `SessionStart`/`startup` matcher and its on-disk-not-session-scoped argument, the count-scaled threshold and its single-primary-source derivation, the state file and re-arm band, the kill-switch and log, the distinct-skill-over-extending-`ai-instruction-and-memory-files` decision, and the no-skill-to-hook-handshake decision. Their rationale is in rows 1–7, 10–19, and 22–27 below and is not re-litigated here.

## Assumption ledger

**Root problem:** durable, standing facts accumulate in a machine-local memory store that no commit, no reviewer, and no CI check ever observes, so the drift from "recall store" to "un-versioned documentation" stays invisible until someone happens to look — and the audit that fixes it deletes gitignored, unrecoverable files and publishes to a public tracker, so it cannot run unattended.

**Givens** (conditions fixed beyond this design's reach):

- **G1.** The harness loads only the first 200 lines or first 25 KB of a project's `MEMORY.md` at session start and reads topic files on demand; this plan cannot change that load path, only what the store holds. *Reason: Anthropic owns the memory-load mechanism.* `[verified: claude/.claude/skills/ai-instruction-and-memory-files/REFERENCES.md, the block quote sourced to https://code.claude.com/docs/en/memory]`
- **G2.** Memory content is machine-local and gitignored, so no commit, PR diff, or CI run can observe it — a hook is the only surface that can. *Reason: the repo boundary, which this plan does not move.* `[verified: .gitignore, the claude/.claude/projects/ entry]`
- **G3.** A directory under `<config-dir>/projects/` is named after the working tree it belongs to, so its name identifies a project on this machine. Nothing this hook emits — nudge text, log line, doc, or plan — may carry one, and nothing this skill publishes may either. *Reason: the harness owns that naming, and the always-on redaction detectors are fixed by `deny-private-project-refs.sh`.* `[verified: repo CLAUDE.md "Redact private-project-identifying content" always-on tier; .gitignore's wholesale exclusion of claude/.claude/projects/]`
- **G4.** `<config-dir>` resolution is `_lib_config_dir`'s job and yields exactly one account's tree. *Reason: `_lib.sh` owns it; every hook in this repo goes through it.* `[verified: claude/.claude/hooks/_lib.sh _lib_config_dir; called by require-memory-skill.sh and nudge-handoff-near-context-cap.sh]`
- **G5.** An agent's `model:` and `effort:` frontmatter are dispatch *requests*, not guarantees, and resolution does not always follow them. This design pins both and additionally passes them explicitly at the dispatch site; it cannot do more. *Reason: the harness owns dispatch resolution.* `[verified: claude/.claude/CLAUDE.md "Model & Effort Routing" — "both are requests, not guarantees, and resolution doesn't always follow them"; docs/auto-mode.md for the measurement]`

# Memory audit nudge

## Context

Claude's per-project auto-memory store accumulates durable, standing facts
about repo/hook/skill behavior that belong in version-controlled docs
instead of ephemeral memory — as `memory-file-audit` demonstrated by
manually migrating such facts and deleting the memory files they duplicated.
Without an automated check, this drift is invisible until someone happens
to notice. The outcome: a new on-by-default hook that nudges (never
auto-executes) a memory-store audit once the store crosses a size-based
threshold, pointing at a reusable skill/checklist for the
migrate-verify-delete workflow, with a kill-switch opt-out matching this
repo's other on-by-default hooks.

**Engineer's answers to the three open design questions (binding on the
architecture below):**

1. **Audit criteria:** reuse `ai-instruction-and-memory-files/SKILL.md`
   §5's existing anti-duplication heuristic as the audit playbook, applied
   uniformly across all memory types (`user`, `feedback`, `project`,
   `reference`) via its content-based test — "does this generalize into a
   rule already covered elsewhere (CLAUDE.md/AGENTS.md/a hook)?" — not a
   type-tag proxy. No `type: project` (or any other type) carve-out from
   pruning consideration; `type: feedback` is equally named in §5's
   heuristic ("feedback calibration... with the *why* story") as content
   that earns its keep, on the same footing as `type: project`'s
   "time-sensitive project context." Do not invent separate audit criteria
   for this nudge.
2. **Beads:** park Beads (third-party CLI/Dolt-backed
   MEMORY.md replacement) as a separate future initiative. Out of scope
   for this plan.
3. **Path scoping:** reuse the existing glob-all-projects pattern from
   `require-memory-skill.sh` rather than building new per-repo
   cwd-to-directory-name path resolution. The nudge fires on total memory
   bloat across every project on the machine, not this-repo-specific
   bloat.
4. **Deletion enforcement — superseded.** The initial decision (during the
   first `/plan-review` round) was to close the skill's Step-5 Bash `rm`
   bypass of `require-memory-skill.sh`'s Write/Edit/MultiEdit-only dispatch
   by extending that hook with a Bash-command enforcement arm (M10). A later
   `/code-review` on the implementation empirically confirmed the arm's
   text-pattern-match heuristic is bypassed by ordinary, non-adversarial
   shell idioms (`cd`+relative-path, `$HOME` indirection) with no marker
   check at all — a compounding-defensive-layers pattern per this repo's
   CLAUDE.md, not a sound foundation to patch further. The engineer's
   revised decision: deletion (and, per decision 7 below, issue-filing)
   require live, per-item human approval inside the audit skill's own
   session, replacing the autonomous heuristic gate rather than patching it.
   Whether any part of M10 survives is re-derived in this rework's Approach
   section below.
5. **Classification gains a fourth verdict: file as GitHub issue.** For
   memory content that reveals a harness or tooling gap — the motivating
   example is a memory noting "route code edits through code-writer, not
   inline Edit," which is a fix owed to the harness, not a rule to document
   and move on from — Step 2's classification table gets a fourth verdict
   alongside migrate/delete-on-contact/keep.
6. **Classification dispatches to a new Opus-pinned subagent, waited inline
   — no background/async machinery.** The categorization judgment is complex
   enough to warrant Opus-level reasoning, and it fires rarely (gated by the
   nudge's re-arm band). The engineer initially asked for this to be
   dispatched non-blocking of "the main thread," then clarified: the skill
   already runs in its own session, invoked by name after the SessionStart
   nudge advisory (the same `skillOverrides: name-only`, nudged-by-name shape
   `error-mode-analysis` already uses) — there is no main thread to protect
   inside that session, so a normal dispatch-and-wait `Agent` call (the same
   shape `plan-architect` itself uses) is sufficient. `plan-architect` is
   explicitly not reusable here — it is hard-scoped to `/plan-it` Step 5 by
   its own description — so this needs a new, narrowly-scoped agent
   definition.
7. **The skill files the GitHub issue itself, gated by the same per-item
   live-approval shape as deletion** — not a draft-only handoff. Which `gh`
   surfaces `deny-private-project-refs.sh` scans is stated in that hook's own
   header and `docs/private-project-redaction.md`, not restated here; this
   plan's Approach section must state plainly which mechanism the filing step
   uses and that the pre-filing human approval is an additional control on a
   public repo, not the only one.
8. **Deletion quarantines rather than removes (added during this round's
   `/plan-review`).** The `delete-on-contact` verdict's terminal act was
   `rm`, the only path in this design with zero durable artifact before the
   irreversible step — `migrate` and `file-as-issue` both land a commit or a
   public issue first. `ciso-reviewer`'s fix-or-ask finding on this asymmetry
   was put to the engineer directly: move the approved file into a
   quarantine directory instead of removing it, so the human approval still
   gates the action but the action itself becomes reversible. The engineer
   chose quarantine over accepting the residual. M14 and Step 6 below
   reflect this.
9. **Classification folds inline into the audit skill's own session —
   supersedes decision 6 above (added after this design shipped to PR #817
   review).** A PR reviewer flagged `memory-store-classifier` (decision 6's
   new agent) as an anti-pattern: an agent whose only dispatch site is one
   skill's one step, the same shape a prior `plugins/issue-triage` design
   round already reversed. `plan-architect`, consulted per the reviewer's
   own request, confirmed it and went further — recommending the agent's
   tool cap be removed entirely rather than narrowed to a lighter dispatch
   (e.g. `general-purpose` with the criteria embedded in the prompt, the
   pattern `issue-triage` used). The engineer chose the fuller fold. See
   the new paragraph in Approach and M11's rewritten text below for the
   reasoning; Step 5 in the implementation table carries the resulting
   edit list.

   **Deviation from Step 5's stated reasoning (recorded post-implementation).**
   Step 5's row below drops the cross-file-isolation instruction and its
   Known Limitations bullet on the grounds that "the hazard has no referent
   once files are read one at a time in the classifying session itself."
   That reasoning does not hold: reading N files sequentially into one
   context window makes cross-file bleed *more* likely, not less, since the
   dispatch boundary was the actual structural isolation, and folding
   classification inline removed it rather than mooting it. The
   instruction, and its pinning test (now `test_step_2_forbids_cross_file_blending`),
   were kept rather than dropped, contrary to Step 5's stated reasoning.

# Approach

## Concluded design

The Bash-command enforcement arm added to `require-memory-skill.sh` is reverted in full: a text-pattern gate that `cd`+relative-path and `$HOME` defeat is not a control, and patching it further is the compounding-defensive-layers tell rather than a residual-risk tradeoff. In its place, the `memory-store-audit` skill classifies each file inline within its own session (now carrying a fourth verdict, *file as issue*) — decision 9 reverses this plan's original choice to dispatch a separate read-only agent for that step — and every deletion and every issue-filing call pauses on its own blocking `AskUserQuestion` immediately before the single irreversible or external command — a person in the loop per item, with no new marker or hook machinery invented to hold that promise.

**Why the revert, and why nothing of M10 survives.** `ciso-reviewer` confirmed empirically, by running the shipped hook against an isolated `$HOME`, that `cd ~/.claude/projects/<name>/memory && rm MEMORY.md` and `rm $HOME/.claude/projects/<name>/memory/MEMORY.md` are both **allowed with no marker check at all**, while the literal-tilde-with-trailing-slash form is denied. Neither allowed form is an evasion technique; both are ordinary shell phrasing an agent reaches for unprompted. The arm therefore does not do the one job it was deployed for even for the one verb (`rm`) the audit skill actually uses. Three further findings compound rather than mitigate: the arm routes `_lib_active_bypass_marker_live`'s *already-documented* unbounded-liveness weakness onto an irreversible action for the first time; it is the only layer guarding content this plan's own skill body calls unrecoverable; and its `"matcher": "Bash"` registration makes `require-memory-skill.sh` fork `timeout`+`jq` on **every Bash tool call machine-wide**, with none of the `if:`-narrowing 10 of its 11 siblings in that matcher array carry. The lighter primitive is not a better heuristic — it is not putting an autonomous gate on this path at all, and instead gating the *one place the deletion originates* (this skill's own step) with a person. That is strictly stronger than what the arm delivered, because a `cd` cannot route around a human.

Partial survival was weighed and rejected on evidence, not caution. Keeping the arm but correcting its disclosed-bypass list — to name `cd`+relative-path and `$HOME`-prefixed deletes, and to fix the `sed -i` mis-claim and the missing `mv`/`cp` overwrite-detection gap — leaves a `hook-class: gate` script whose header would have to say, accurately, that it misses the most common phrasings of the verb it names — a gate documented not to gate. Keeping it and bounding the marker's freshness window fixes the marker, not the pattern match, and touches shared marker machinery every other gate depends on for a control this plan is removing. Keeping only the allow-fixtures pins a boundary on deleted code. Every `ciso-reviewer`, `staff-sdet`, and `comment-discipline-reviewer` finding scoped **only** to the Bash arm is therefore moot by removal, and is named as such in Out of scope rather than dropped silently.

**Why a live `AskUserQuestion` and not a marker.** This session's research found no precedent anywhere in this codebase for a marker gated on a live human answer: `_lib_active_bypass_marker_live` and `marker.sh activate`/`deactivate` are self-activated by the owning skill's own Step 0, and every review marker records a *review that ran*, keyed on a content hash. Retrofitting either shape onto "a human said yes to this specific file" would be new machinery, not reuse — and CLAUDE.md's default-suspect-over-powered-primitives rule points the other way. `plan-review`'s fix-or-ask disposition rule is the existing precedent for the lighter primitive: a blocking, concrete, one-line decision point raised at the moment of the consequential act. The honest limitation, stated in the skill body and in `docs/memory-audit-nudge.md`, is that a skill-body instruction is an instruction and not an enforcement — nothing blocks an agent that skips the pause. That residual is accepted because the alternative was empirically shown not to hold either, while taxing every Bash call on the machine.

**Why `gh issue create`.** The skill files with `gh issue create --body-file <path> --title '<title>'` from the `claude-config` checkout. `deny-private-project-refs.sh`'s header lists `gh issue create`, `gh issue comment`, and `gh issue edit` among the surfaces it scans (its `IS_GH_ISSUE` dispatch scans the command string and reads every `--body-file`/`-F` path), so the filing call is on a scanned surface, and `gh issue create` is the purpose-built primitive for it. Memory content is the *highest-risk* content class this repo could publish — machine-local, per-project, and by construction dense with exactly the strings the detectors exist to catch — so the filing call must stay on a scanned surface. Two controls act on this call in every permission mode: the hook's scan of the command and body file, and the per-item live approval (M14). A permission prompt is an extra that exists only in modes that prompt: `docs/auto-mode.md` says auto mode replaces per-action prompts with a classifier that trusts the working repo's remotes, so the plan does not count the prompt as a control (no `permissions.allow` entry is added). The approval is an additional control on a public repo, not the only one.

- **Body delivery.** Memory text is dense in backticks, `$(...)`, and double quotes, which a shell evaluates inside a double-quoted argument, and the hook's Known-gaps list says it sees a `--body "$(cat file)"` body only as the literal `$(...)` string. The skill therefore writes the body with the Write tool to a regular file at a literal, whitespace-free, absolute temp path outside the checkout and passes `--body-file <that path>`. The hook reads that file, the approval shows its bytes, and `gh` posts them, so the approved, scanned, and posted bytes are identical and no memory-derived text is ever shell-interpreted. `gh issue create` has no title-file flag, so the title is a single-quoted literal, and a title containing `'` is reworded. The title is a single line with no newline or other control character, and `--body-file <path>` precedes `--title`: `extract_body_source_paths` tokenizes the command with `xargs -n1`, a newline inside the single-quoted title makes that tokenizer fail, and the hook then allows without reading the body file (with the flag order reversed the path is emitted before the failure and the file is scanned). The skill forbids `$(...)`, backticks, `$VAR` expansion, `-F -`, and any pseudo-file path anywhere in the command. The body file lives at a per-item unique path, mode 600 where the Write tool allows it (otherwise the skill states that it could not), and is removed after the item is approved and filed or declined, because a declined draft holds content the human refused to publish. `[verified: deny-private-project-refs.sh header Known gaps; extract_body_source_paths and the IS_GH_ISSUE branch, which read each --body-file path and fail closed on a pseudo-file (literal spellings only, per the header; an alias spelling such as a dotted /dev path is not caught) or an unreadable path; ciso-reviewer's round-4 probe of the newline-title and flag-order shapes]`
- **Scope of the scan.** The hook derives `REPO_ROOT` and `remote.origin.url` from its own process's cwd and exits 0 unless that remote contains `claude-config`, before the command's own `cd` has run. A one-call `cd <checkout> && gh issue create …`, and `-R <owner>/<repo>` from outside a `claude-config` checkout, are therefore not scanned. The hook reads its own process cwd and never the payload's `.cwd`. The skill verifies cwd is inside the checkout as a separate step before each filing call, runs any needed `cd` as its own prior Bash call, never combines `cd` with the filing call, and never passes `-R`/`--repo`. The skill runs the filing in the parent session's own cwd after verifying it; a dispatched agent's cwd resets between Bash calls, so an agent whose cwd will not persist downgrades the item to *keep* plus a report line. The filing target is this repo only (M13). `[verified: deny-private-project-refs.sh, the REPO_ROOT and REMOTE_URL scope check, which shows the chained-cd and -R shapes are unscanned; ciso-reviewer's round-3 probe of those shapes]` `[unverified: that a standalone cd in a prior Bash call makes the hook process's cwd the checkout, until Verification 10's live check has run; the hooks reference documents the payload cwd following a cd and does not say which directory a handler process starts in]` **Deviation (round-3 `/code-review`, CISO finding F3).** Step 4 no longer relies on this premise: rather than resolve whether a standalone `cd` retargets the hook's cwd, the round-3 fix removed the `cd` allowance outright — the session itself must now start inside the checkout, and Step 4 never `cd`s, unsets a variable, or passes `-R` to make a check pass (Critical files, the `memory-store-audit/SKILL.md` row).
- **Engineer's choice.** The engineer selected the option labeled "Switch to `gh issue create`" over `gh api repos/{owner}/{repo}/issues`. The "(Recommended)" rationale attached to that option was the assistant's, not the engineer's.

**Why the whole-process bound is the registration's `timeout`.** `staff-platform-engineer` requires that a hook Claude's first response waits on never be held open indefinitely by a stalled filesystem. A bash `SECONDS`-based watchdog cannot work: `SECONDS` is only readable between commands, and a foreground `find` blocked on a stalled mount never returns control for the check to run. A backgrounded scan with a poll-and-kill loop costs `mktemp`, a single composed `trap`, and a poll loop under a bash-3.2 floor, and orphans `wc` children on kill. Refusing to run without `timeout(1)`/`gtimeout(1)` bounds only the `find`/`awk`/`jq` calls, leaves the glob and the state-file reads and writes uncapped, and silently disables the hook on stock macOS. The lighter primitive is the per-hook `"timeout": 10` on the `settings.json` registration. The value is in seconds. The primitive bounds the whole hook process and needs no userland binary.

- **What it protects.** Per the hooks reference (https://code.claude.com/docs/en/hooks, SessionStart section), interactive SessionStart hooks run in the background and the user can type at once, but Claude's first response waits for them to finish. Without the field, a command hook's `timeout` defaults to 600 s (common-fields `timeout` row, which lowers the default only for other events), so a stalled scan could hold that first response for up to ten minutes.
- **What a cancel does.** Per the hooks reference's Timeouts section, a command hook that reaches its timeout is cancelled and its output discarded, "so on most events a timed-out hook renders no decision". The named exceptions are `PreModelSwitch` and the `PreToolUse` Agent SDK callback hook; `SessionStart` is not one. The reference documents a transcript notice on cancel for `UserPromptSubmit` only, so whether a cancelled `SessionStart` nudge is visible to the user is unverified either way.
- **Why 10.** It is a chosen ceiling, not a vendor-derived value. It sits above the 7 s worst case of a single inner-cap kill (the 5 s `_lib_capped` default plus the 2 s SIGKILL grace `_lib_capped_for` adds with `-k 2`), so an inner kill resolves before the registration cancels. `SessionEnd` also registers `"timeout": 10`, but the reference gives `SessionEnd` a separate 1.5 s budget that a longer per-hook value raises, so the two values carry different meanings and are not tied to each other.
- **The cancel window.** A cancel is not identical to the hook's own fail-open exit. The fire path appends the log line and writes the state file before it prints the advisory, so a cancel landing between those writes and stdout consumes the re-arm band and delivers nothing. That window is a few writes wide and is accepted; the nudge is advisory and the next band crossing fires again.
- **Unverified.** The reference does not say whether the harness's timeout kills only the hook's bash process or also its `find` child. The inner `_lib_capped_for` caps bound the `find`/`awk` calls independently where `timeout(1)` or `gtimeout(1)` exists.

The inner `find` and `awk` calls go through `_lib_capped`, and the `jq` calls go through `_lib_jq` (a `_lib_capped_for 5 jq` wrapper), so all three carry the same 5 s cap and accept the documented uncapped fallback, as `set-session-title-from-branch.sh` does. One shared cap-kill predicate helper, added beside `_lib_capped_for` in `_lib.sh` by this fix round (see Step 2's helper row), classifies a status as consistent with a cap kill (124/137/143); a scan whose `find` or `awk` ends in such a status is discarded, and `docs/memory-audit-nudge.md` documents that under Known limitations rather than logging it.

**Why not `"async": true`.** The hooks reference documents `async: true` for command hooks ("Configure an async hook"), which would take the scan off the first-response critical path. It is rejected for four reasons:

1. `async: true` hooks get no enforced timeout: "Once an async hook is running in the background, Claude Code doesn't enforce `timeout` on it" (also stated in the `timeout` field row). A stalled scan would become unbounded instead of ending at 10 s. The reference's next sentence says Claude Code still enforces `timeout` on a hook run with `asyncRewake`, so this reason does not cover that variant. `asyncRewake` is rejected separately: it is a failure-wake channel keyed on exit code 2, and the reference documents no delivery path for an exit-0 `additionalContext` advisory from it. `[unverified: whether the reference's next-conversation-turn delivery paragraph covers `asyncRewake`, and how `asyncRewake` handles exit-0 `additionalContext`; the reference describes the exit-code-2 wake path and does not say either]`
2. The reference documents the general latency benefit of `async: true` ("immediately continues" without waiting for the hook), and this design concedes it. The rejection rests on reasons 1, 3, and 4 plus the reference's statement that an async hook's `additionalContext` is delivered "on the next conversation turn", which would move a session-start advisory past Claude's first response. Whether the SessionStart first-response wait sentence also covers async hooks is unverified either way.
3. The reference's limitations section says each async execution creates a separate background process with no deduplication across firings. `[unverified: a cross-session pile-up of one stuck process per session start — the reference's sentence is about repeated firings of one hook, a `startup` matcher fires once per session, and the reference documents background-process teardown only for `-p` mode]`
4. The inner caps and the discard on a cap-kill status exist for total correctness, not only latency: a killed `find` yields a partial total that must not reach the threshold comparison. They stay under `async` unchanged, so `async` removes none of that machinery.

**Everything else from the prior design stands unchanged:** the `SessionStart`/`startup` matcher and its on-disk-not-session-scoped argument, the count-scaled threshold and its single-primary-source derivation, the state file and re-arm band, the kill-switch and log, the distinct-skill-over-extending-`ai-instruction-and-memory-files` decision, and the no-skill-to-hook-handshake decision. Their rationale is in rows 1–7, 10–19, and 22–27 below and is not re-litigated here.

**Why classification folds inline, not into a dispatched agent — including not the lighter dispatch of `general-purpose` with the criteria embedded in the prompt (decision 9).** Three findings, from `plan-architect`'s consult, each independently sufficient. First, the read-only tool cap this plan's original M11 relied on to make M14's human-in-the-loop promise "structural rather than aspirational" does not actually do that: the audit skill's own session holds `Bash` and `Write` unconditionally and performs every real act (the quarantine move, the `gh issue create` filing call), so capping the one participant that was never going to act constrains nothing — the promise was always carried by M14's approval pauses, not by any agent's tool grant, and the Critical files paragraph below is corrected accordingly. Second, the classification output does not survive as a standalone verdict: Steps 3 and 5 re-read each *migrate* or *file as issue* file's full content anyway to draft the migration text and the compression-diff table, and Step 4 drafts an issue body the returned table has no column for — so a dispatch (to any agent, purpose-built or `general-purpose`) fails `subagent-delegation`'s own output test, which keeps inline "a comprehension read whose content feeds your own writing, review, or design." Third, a dedicated agent's `description` loads into every session's Agent-tool schema on every machine that installs this repo, forever, for a workflow gated by a rare re-arm band — the cost `plan-architect` (this repo's one deliberate exception, `docs/design-decisions/plan-it-step5-pinned-opus-dispatch.md` and `docs/design-decisions/plan-architect-consult-mode.md` (formerly §30 and §37)) amortizes only because every `/plan-it` run reaches it, which this workflow does not. Folding inline does not moot the cross-file isolation control. Reading N files sequentially into one context window makes cross-file bleed more likely, not less, so Step 2 keeps its instruction that each file's verdict, destination cell, and any proposed title or body draw only on that file, and `test_step_2_forbids_cross_file_blending` keeps pinning it (see the recorded deviation in Context, decision 9). The original skill body's separate Known Limitations bullet on batched-dispatch isolation is absent from the tree, and stays absent. The one real cost: dispatching was the only way to force Opus reasoning onto the classification step from a Sonnet-anchored session; the skill body now asks the engineer to `/model opus` before Step 2 instead of guaranteeing it (row 5 already established that a `model:` pin is a request, not a guarantee, so this trade is smaller than it first appears).

## Assumption ledger

**Root problem:** durable, standing facts accumulate in a machine-local memory store that no commit, no reviewer, and no CI check ever observes, so the drift from "recall store" to "un-versioned documentation" stays invisible until someone happens to look — and the audit that fixes it deletes gitignored, unrecoverable files and publishes to a public tracker, so it cannot run unattended.

**Givens** (conditions fixed beyond this design's reach):

- **G1.** The harness loads only the first 200 lines or first 25 KB of a project's `MEMORY.md` at session start and reads topic files on demand; this plan cannot change that load path, only what the store holds. *Reason: Anthropic owns the memory-load mechanism.* `[verified: claude-skills/skills/ai-instruction-and-memory-files/REFERENCES.md, the block quote sourced to https://code.claude.com/docs/en/memory]`
- **G2.** Memory content is machine-local and gitignored, so no commit, PR diff, or CI run can observe it — a hook is the only surface that can. *Reason: the repo boundary, which this plan does not move.* `[verified: .gitignore, the claude/.claude/projects/ entry]`
- **G3.** A directory under `<config-dir>/projects/` is named after the working tree it belongs to, so its name identifies a project on this machine. Nothing this hook emits — nudge text, log line, doc, or plan — may carry one, and nothing this skill publishes may either. *Reason: the harness owns that naming, and the always-on redaction detectors are fixed by `deny-private-project-refs.sh`.* `[verified: repo CLAUDE.md "Redact private-project-identifying content" always-on tier; .gitignore's wholesale exclusion of claude/.claude/projects/]`
- **G4.** `<config-dir>` resolution is `_lib_config_dir`'s job and yields exactly one account's tree. *Reason: `_lib.sh` owns it; every hook in this repo goes through it.* `[verified: claude/.claude/hooks/_lib.sh _lib_config_dir; called by require-memory-skill.sh and nudge-handoff-near-context-cap.sh]`
- **G5.** An agent's `model:` and `effort:` frontmatter are dispatch *requests*, not guarantees, and resolution does not always follow them. With classification folded inline (decision 9), nothing in this design dispatches to a pinned model, so nothing guarantees Opus reasoning reaches Step 2; the skill asks the engineer to `/model opus` instead (M11). *Reason: the harness owns dispatch resolution.* `[verified: claude/.claude/CLAUDE.md "Model & Effort Routing" — "both are requests, not guarantees, and resolution doesn't always follow them"; docs/auto-mode.md for the measurement]`

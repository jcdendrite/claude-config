# Consolidate default-branch resolution across duplicated implementations

GH-879.

## Context

GH-879 consolidates "resolve the repo's default branch," which is independently reimplemented across seven in-tree shell sites with five different failure postures. The duplication was flagged as a deferred finding on PR 863 and again by a `plan-architect` consult on that PR's design; a predecessor plan (`.claude/plans/pr-diff-default-branch-fallback.md`, merged as PR 803) had already named "a shared default-branch resolver across all three call sites" as a real DRY improvement deliberately left out of its own scope. Why now: the duplication is no longer only a DRY concern — one of the copies, in a script that deletes branches, can cause an unprompted branch deletion. The intended outcome is one shared, hardened helper; every site that should use it migrated; every site that deliberately shouldn't documented as such on investigated grounds; and the deletion-safety hole closed with a regression test.

Three of the ticket's stated premises changed under investigation, and the plan below reflects the corrected versions rather than the ticket's:

- The ticket's table lists six sites. There are **seven** — `set-session-title-from-branch.sh` resolves the default branch the same way and additionally performs a dangling-symref verification the shared helper documents itself as *not* doing.
- The ticket records "none (deliberate)" as the fallback posture for the two divergence sites. No comment, test, or commit in either file records any such intent; that claim is an assumption, and this plan decides those two sites on consequence rather than asserting intent.
- The ticket asks whether `cleanup-merged-branches.sh`'s hardcoded `main` fallback could mis-scope a *merged* classification. It can, but the Tier-B path it hypothesized is bounded by an interactive prompt. A worse path exists: the default-branch exclusion is a pure string match, so a wrong resolution lets the repo's real default branch be swept as an ordinary candidate and deleted with no prompt at all.

## Approach

Split the shared resolver into two layers inside `claude/.claude/hooks/_lib.sh` — `_lib_default_branch_from_origin_head` (reads `refs/remotes/origin/HEAD`, verifies the target actually resolves to a commit, returns the short name) and `_lib_default_branch_or_guess` (calls the first, then probes `main master develop`) — both returning non-zero with empty stdout when they cannot answer. Then migrate each of the seven sites to whichever layer its own consequence-of-a-wrong-answer justifies, and make `cleanup-merged-branches.sh` abort rather than fall back to a literal branch name, because a guessed default is what lets it sweep the real default branch into an unprompted delete.

**The discriminator, stated once:** a site may take the guessing layer when a wrong name only produces a diff, a message, or a *withheld* gate; a site must take the no-guess layer when a wrong name selects the base it fetches, rebases onto, or deletes against. **The rule has a third failure shape it does not by itself decide: a gate wrongly *granted*.** `require-ready-for-review.sh` is the one site where that shape is live, and it is assigned to the guessing layer by behaviour-preservation, not by this rule — see its table row and the Out of scope entry. `set-session-title-from-branch.sh` is likewise assigned by behaviour-preservation (its wrong-answer consequence is cosmetic, so the rule alone would permit either layer). The rule plus that named tiebreaker assign all seven sites, and row10's test enforces the resulting table.

**Naming.** The guessing layer is renamed from PR 863's `_lib_resolve_default_branch` to `_lib_default_branch_or_guess`. "Resolve" reads as the authoritative, general-purpose call and is the name a future implementer reaches for by default at an eighth site, which is the exact inversion of what the safety argument needs — the riskier operation must not carry the more inviting name. This is a rename of an unmerged, single-consumer function, so the churn is confined to Phase 1.

**Mechanisms**

- **row1 — Two functions, not one.** `anchors: root`. Three sites must not guess and three may; one function forces the guess on all of them. Over-powered check — two lighter primitives considered: (a) a single function with a `--strict` flag, rejected because it turns a two-outcome contract into a three-way one and adds argument validation to a path every hook calls; (b) leaving the no-guess sites with their inline `symbolic-ref` read, rejected because that is precisely the duplication the root line names. The two-function split is the lighter shape: each function is one nameable behaviour and neither takes a mode argument. `[verified: _lib.sh:261-266 and _lib.sh:1453-1462 show the same one-behaviour-per-function shape already]`
- **row2 — `return 1` + empty stdout, replacing the always-exit-0 contract.** `anchors: row1`. Over-powered check — two lighter primitives: (a) keep always-exit-0 and have each caller test `[ -z "$x" ]`, rejected because "the caller forgot to check" is the exact shape of the `cleanup-merged-branches.sh` bug in the root line; (b) a distinct exit code per failure cause (as `_lib_worktree_lock_pid` uses), rejected because no caller branches differently on *why* resolution failed. `return 1` is also the prevailing convention. **Consequence this contract creates, and the mechanism that contains it:** under `set -e`, a bare `X=$(helper)` aborts the caller the moment the helper returns 1 — pipeline or not. Every migrated call site therefore uses a guarded form (`if ! X=$(…); then`), prescribed per-site in Critical files. `[verified: _lib.sh:261-266, _lib.sh:1449-1462; empirically reproduced this session — `v=$(f)` where `f` returns 1 aborts under `set -euo pipefail`, while the same call inside an `if !` condition does not]`
- **row3 — Drop the `sed` pipeline for `${ref#…}` (stripping the literal `refs/remotes/origin/` prefix).** `anchors: row1`. **Corrected rationale.** Removing the pipeline does *not* by itself make any caller `set -e`-safe — that protection is entirely row2's guarded call form, because the abort is governed by the call site, not by the helper's internal shape. The pipeline is dropped for two narrower, real reasons: without `pipefail` active a trailing `sed` silently masks git's failure and yields an empty string that reads as success, and dropping it removes a fork and matches the existing style at `set-session-title-from-branch.sh:117` and `branch-divergence-status.sh:26-27`. Use the non-`--short` form plus an explicit prefix strip. `[verified: empirically this session — `v=$(false | sed …)` continues under `set -eu` and aborts only under `set -euo pipefail`, while `v=$(false)` aborts under `set -eu` alone; `${ref#…}` (stripping the literal `refs/remotes/origin/` prefix) is a literal anchored strip that preserves slash-containing names such as `release/v2`]`
- **row4 — The verification moves into `_lib_default_branch_from_origin_head`.** `anchors: row1`. A dangling `origin/HEAD` still reads back through `symbolic-ref -q`, so without the check the helper returns a name that fails to resolve; two sites already re-implement the check independently (`set-session-title-from-branch.sh:116`, `check-branch-divergence.sh:91`). `[verified: those two lines, read directly]` `[engineer-verified: G5]`
- **row5 — The guess/no-guess discriminator above,** including its named third failure shape (a gate wrongly granted) and the behaviour-preservation tiebreaker that assigns `require-ready-for-review.sh` and `set-session-title-from-branch.sh`. `anchors: root`. Stated as one rule plus one named tiebreaker so row10's test has something to check and a future eighth site has something to apply.
- **row6 — Both divergence sites take the no-guess layer, and each keeps its current failure posture.** `anchors: row5`. This is the ticket's "deliberate" claim resolved on evidence rather than on an assertion of intent: `branch-divergence-status.sh` is the `/ready-for-review` pre-push gate and `/respond-pr` precheck, and `check-branch-divergence.sh` emits an advisory instructing the agent to offer `/git-feature-branch-sync` — in both, a guessed name selects the branch a rebase or force-push is taken against. The record also already prefers the pointer over a guess for this family: `claude-skills/skills/git-feature-branch-sync/SKILL.md:15-16` tells the reader to check with `git symbolic-ref refs/remotes/origin/HEAD` and names no fallback, and `branch-divergence-status.sh:23` already prescribes the actual repair (`git remote set-head origin -a`), which fixes `origin/HEAD` once for all seven readers instead of each guessing per read. Over-powered check — two lighter primitives than adding a candidate probe here: (a) keep the pointer-only read, which is what this row chooses; (b) adopt the probe but disclose the guess in the output text, rejected because disclosure helps a human reading `branch-divergence-status.sh` but not the SessionStart advisory, whose consumer is an agent already instructed to act on it. The two postures stay different — silent `exit 0` for the implicit session-start hook, loud `exit 1` naming the repair for the explicitly-invoked script — because their invocation contexts differ. `[verified: claude-skills/skills/git-feature-branch-sync/SKILL.md:15-16,23-28; branch-divergence-status.sh:9-11,23; check-branch-divergence.sh:44-46]` **What the record cannot settle:** nothing in any comment, test, or commit says the *absence of a candidate fallback* was chosen deliberately. This row argues from consequence, not intent, and the comments it prescribes state the consequence.
- **row7 — Accepted behaviour change at BOTH divergence sites: each loses a self-healing path when `origin/HEAD` dangles but its target is still live on the remote.** `anchors: row6`. Today each site reads the dangling name, attempts its own bounded `git fetch origin "$DEFAULT_BRANCH"` — which resolves the name against the live remote regardless of the local tracking ref — and only then verifies. After row4 the helper verifies first and each site gives up before that fetch. The two consequences differ and are accepted separately: `check-branch-divergence.sh` loses an advisory (silent `exit 0`, no gating effect); `branch-divergence-status.sh` spuriously fails the `/ready-for-review` pre-push gate and `/respond-pr` precheck with "could not resolve origin/HEAD" where it previously recovered. The second is the higher-stakes site and fails in the safe direction (blocks rather than wrongly allows), but it is a real false-positive increase on a guardrail, so it is disclosed and pinned by its own test rather than inherited silently. Two lighter ways to preserve the self-heal were rejected: (a) expose a third, unverified name-only function — reintroduces the shape row4 removes; (b) have each site run `git remote set-head origin --auto` itself — a network write from a SessionStart hook, and the repair belongs with the operator. The affected state (a stale `origin/HEAD` after an upstream default-branch rename) is realistic on any `timeout`-capable machine with a reachable remote, not a rare edge case; both sites' error paths name the repair. Pin both with tests. `[verified: check-branch-divergence.sh:80-91 and branch-divergence-status.sh:21-25,44-49 read directly; neither site's existing tests cover the dangling-but-remotely-live case, only fully-unset origin/HEAD]`
- **row8 — `cleanup-merged-branches.sh` aborts instead of falling back to `main`, on every invocation mode including `--dry-run`.** `anchors: root`. Three tiers: helper → `git remote set-head origin --auto` → helper again → `exit 1` naming the repair and disclosing that the auto-repair was already attempted. The guessing layer would not have closed this: with a real default of `develop` and an `origin/main` present, the probe still returns `main`, `develop` is still not excluded at lines 516/529, and `classify_branch` can still route it to Tier A, which goes to `TO_DELETE` with no prompt. Over-powered check — two lighter primitives: (a) keep the literal and add a "is this really the default?" guard before deletion, rejected as a second defensive layer closing a hole the first layer opened; (b) keep the literal and require `--dry-run` when resolution failed, rejected because it defends an input problem the discovery tiers dissolve. **`--dry-run` aborts too, deliberately:** it is auto-approved via `permissions.allow` and shares this resolution step, and a preview computed against a guessed default would report a candidate list that the real run would not produce — a misleading preview is worse than a refusal that names the repair. CLAUDE.md's destructive-path rule points the same way — discover the target, and when discovery comes up empty, do not act. `[verified: cleanup-merged-branches.sh:285-298, 516, 529, 340-350, 648-651, 774; the no-prompt Tier-A path and the --dry-run-only flag set at :101 re-read this session; claude/.claude/settings.json:22-23 confirms --dry-run is auto-approved; docs/scripts.md:76 confirms it shares the resolution step]`

It writes to the local ref store and talks to the remote, so folding it into a shared read-path helper would be a strictly wider primitive than any caller needs. (This holds on the read-path argument alone, independent of call frequency.)

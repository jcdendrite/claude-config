# TTL-verdict consistent-root gate fix

## Context

The `cache-rebuild --ttl-verdict` analyzer (shipped in PR #995, plan at
`.claude/plans/cache-ttl-tuning-analysis.md`) gates a committed TTL
default behind unanimous agreement across every "consistent" root. Its
full-window XOR consistency test conflates a transient vendor
auto-fallback signal with a stable tier assignment. This structurally
excludes most heavy 1h-tier `main`-bucket roots from ever contributing
to a verdict. The defect is invisible in the tool's own output, since
an excluded root's row is never printed at all today — only a lumped
count survives. A live run of the prior plan's Phase 3
(`.claude/plans/cache-ttl-tuning-analysis.md`) surfaced this: too few
consistent roots per bucket to license any verdict.

This plan fixes it in two parts, landing as one PR on branch
`cache-ttl-verdict-gate-fix`:

1. Print each excluded root's own row with an explicit reason label,
   making the real per-root tier-split evidence visible.
2. Replace the too-strict XOR exclusion with a dominant-tier-share
   test, whose threshold is picked from that live evidence and
   documented as an explicit engineer-decided value.

An informative two-slice cross-check for mixed roots is added
alongside part 2; it never feeds the verdict or the consistent-root
count. Neither part changes the prior plan's unanimity-based shipping
safety property (G7) or its unanimity unit (root, never root-slice).

## Approach

The two parts are described in Context above. This section gives the rationale for each, plus the exact mechanics: what changes is only which roots are eligible to be counted, and what the report discloses about the ones that are not — the unanimity property the prior plan shipped (G7 there) and its unit (one root, never a root-slice) are both preserved exactly.

**Why the current gate is wrong.** `transcript-analysis.py:7121-7126` treats "this root wrote both 5m-tier and 1h-tier tokens somewhere in the 30-day window" as evidence that the root has no single live tier. But the vendor behaviour the prior plan's row 2 cited is a *transition*, not a tier assignment — "once you go over your plan's usage limit ... Claude Code drops the main conversation to the cheaper five-minute TTL" — so a single over-limit episode in 30 days stamps an otherwise-1h root as mixed forever.

That exclusion is anti-correlated with volume: the heaviest `main`-bucket roots are the likeliest to have gone over limit at least once, and they are precisely the roots the 1h→5m direction most needs to hear from.

The defect is confined to the *eligibility* test. Every downstream piece keeps its current signature and stays correct as written:

- `_cache_rebuild_root_verdict_input`
- `_cache_rebuild_margin_clears`
- `_cache_rebuild_token_tiebreaker_favors_5m`
- `_cache_rebuild_ttl_verdict`

**Part A — print every root's row (no gate change).** The `continue` at `:7126` currently suppresses the row itself, so an excluded root leaves no trace but a lumped `excluded (mixed-tier or no data) roots=N` count. Restructure the loop so the row always prints and only the *contribution* is conditional: an excluded root appends nothing to `root_inputs` and increments `excluded_roots` exactly as today. The row carries a named exclusion reason in the `Clears` column, reusing the module's established labelled-reason convention (`_CAUSE_*` constants collected into `_CACHE_REBUILD_CAUSES`, `:6042-6063`, whose own comment states the excluded diagnostic bucket "gets its own explicit row here rather than silently falling into 'unexplained'" — the identical argument): two new constants `_TTL_EXCLUDE_MIXED_TIER = "excluded(mixed-tier)"` and `_TTL_EXCLUDE_NO_DATA = "excluded(no-data)"`, plus `_TTL_ROW_NOT_APPLICABLE = "--"`, collected into an ordered tuple beside `_CACHE_REBUILD_TIER_5M`/`_1H`. **Every reason label must be a whitespace-free single token** — `_extract_ttl_verdict_root_row` (`test_transcript_analysis.py:8303-8321`) maps columns by `dict(zip(header.split(), row.split()))`, so a label containing a space silently shifts every column to its right. That is why the labels above are `excluded(mixed-tier)`, not the spaced form `_CAUSE_TS_ANOMALY` uses.

One new column, `Share`, is added in Part A rather than Part B: it holds the dominant tier's share of that root's `W5m + W1h`, which is the exact quantity Part B's threshold is compared against, so the table the engineer reads at step 3 already contains the decision input rather than two numbers to divide by hand. It renders `1.000` for a pure root and `n/a` for a no-data root. Row shapes:

- consistent root — first seven columns byte-identical to today, `Share` = `1.000`.
- mixed root — `Tier` names the *dominant* tier (computed for display only; the XOR gate still excludes it), `W5m/W1h`, `X/Z` and `Net$` show that tier's own accumulators, `Favors` shows that tier's direction, `Clears` = `excluded(mixed-tier)`, `Share` = e.g. `0.812` (a synthetic illustrative value, not drawn from any real corpus run).
- no-data root — `Tier` = `none`, counts `0`, `Net$` = `n/a`, `Favors` = `--`, `Clears` = `excluded(no-data)`, `Share` = `n/a`.

Showing `Net$`/`Favors` on a mixed row is deliberate: whether the excluded roots would have agreed with the counted ones is the single fact that determines whether a threshold is worth setting at all. The `excluded(...)` token on the same line keeps it unambiguous that the row did not count.

`all_root_ordinals` iterates every ordinal in `redact_ordinals`, so after Part A **every root prints one row in every bucket** — including roots that have only `main`-origin records, which now print a `no-data` row in the `subagent` section. That is an intended output-volume increase; see Critical files (Dispatch 1) for its test-coverage consequence.

**Step 3 — the live check (engineer gate, not a dispatch).** After Part A is reviewed and committed, re-run `cache-rebuild --ttl-verdict --since 30d` at default multi-root scope locally. Two outputs: (a) the per-root `Tier`/`Share` evidence the engineer reads to pick Part B's threshold, and (b) a count of in-scope records that carry `cache_creation_input_tokens > 0` but no nested `cache_creation` block, gathered by a throwaway script written **outside the repo tree** (e.g. under `$TMPDIR`, never in the worktree) that imports the same `corpus`/`scope` helpers so "in scope" means what the report means, and prints only a count and a share — never a record. Both outputs — (a) the `--ttl-verdict` table's own `Tier`/`Share` columns, and (b) this script's count/share — inherit the prior plan's Phase 3 discipline unchanged: neither output is pasted into the PR body, a commit message, the plan file, or any committed file. This binds the live command's own printed output, not only the standalone script's.

**Part B — dominant-tier-share gate.** Replace the XOR test with: compute `share = max(W5m, W1h) / (W5m + W1h)`; when `W5m + W1h == 0` the root is `excluded(no-data)`; when `share >= _CACHE_REBUILD_TTL_DOMINANT_TIER_SHARE_MIN` the root is consistent-by-dominance in its dominant tier; otherwise it is `excluded(near-tie)` (the `_TTL_EXCLUDE_MIXED_TIER` constant is renamed to `_TTL_EXCLUDE_NEAR_TIE` — "mixed-tier" stops being an *explanation* once mixing alone no longer excludes). The comparison is `>=`, so a root sitting exactly at the threshold counts.

The reduction mechanics for a dominance-resolved root: **only the dominant tier's own accumulators feed its verdict input** — literally the same `_cache_rebuild_root_verdict_input(...)` call the code already makes for a consistent root of that tier, with no signature change. Three reasons this is the only coherent choice, not merely the convenient one:

1. Each direction's delta accumulator is already tier-scoped by construction — `switch_delta_5m_to_1h_*` increments only inside `in_w5m_branch` and `switch_delta_1h_to_5m_*` only inside `in_w1h_branch` (`:6754-6792`) — and the two carry opposite savings-positive sign conventions. No formula exists that combines them into one net, and inventing one would be new unvalidated algebra in the single function the ship decision rests on.
2. `_cache_rebuild_margin_clears` divides the net by a dollar volume; that volume must be the same tier's volume that produced the net, or the 10% margin means a different thing on each root.
3. Every existing unit test of `_cache_rebuild_root_verdict_input` and `_cache_rebuild_ttl_verdict` stays valid, so Part B's diff is confined to branch selection inside the print loop.

The accepted approximation is that the minority tier's own spend is excluded from both the net and the margin denominator, and the threshold is what bounds its size. Three bias channels follow from the accumulation code and must be disclosed rather than assumed symmetric:

- **1h-dominant, `Z` inflation.** `z_by_origin_root` accumulates read tokens on any primary-idle-band call where `in_w1h_branch` fires, and that branch fires on `read_tokens > 0 and is_idle_sensitivity` even when the call wrote no 1h tokens (`:6740`) — so a mixed root's `Z` is inflated relative to a pure-1h root, pushing the raw-token tiebreaker away from favouring a drop to 5m.
- **1h-dominant, dollar-margin inflation.** The same warm-read-inclusion condition inflates `switch_delta_1h_to_5m_by_origin_root` (and its 60s-boundary sibling) directly: a call with no 1h write still contributes a switch-cost-positive term to `net_primary`/`net_sensitivity` via `_cache_rebuild_1h_to_5m_delta_dollars` whenever `is_idle_primary` also holds (`:6775-6792`). This is an independent channel from `Z`, not merely a `Z/W1h` ratio effect, and it agrees in sign with the first: both push toward declining to change, never toward a spurious adopt.
- **5m-dominant, denominator shrinkage.** `W5m` and `X` both increment only inside `in_w5m_branch`, so there is no counterpart read-driven inflation — but omitting the 1h minority's dollars shrinks the margin denominator, making `clears` marginally easier.

That third channel is not merely "marginal" near the low end of the threshold range. The two tiers are priced asymmetrically (1.25x for 5m writes, 2x for 1h writes, `pricing.py:25-26`), so a *token* share as low as 0.5 does not imply the counted tier also holds the *dollar* majority. Solving for the token-share breakeven where the discarded minority's dollars equal the counted majority's gives ~0.615 for a 5m-dominant root to guarantee it also holds the dollar majority, and ~0.385 for a 1h-dominant root (the looser bound, since 1h is the pricier tier). A threshold chosen near 0.5 can admit a root as "5m-dominant by tokens" while its actual dollar majority still belongs to 1h.

**This is a correctness invariant independent of the empirical threshold value step 3 picks: the threshold must satisfy `0.5 < threshold < 1.0` strictly.** At or below 0.5, the exact-tie case (`W5m == W1h`) becomes reachable with no defined tier-selection rule. Near 1.0, the gate reproduces the old exclusion defect this plan exists to fix. The ~0.615/~0.385 bounds above are additional context for *where in that range* to land, not a substitute for the invariant.

**The two-slice cross-check (informative only).** For any root with both `W5m > 0` and `W1h > 0` — whether or not dominance resolved it, and never for a no-data root — print one note line per root naming each slice's own favoured direction and whether the two agree, computed with the same sign rule `_cache_rebuild_root_verdict_input` uses for `favors` (`net > 0 → positive_favors`). It runs **no margin check at all**: margin-clearing against a slice's own possibly-tiny volume is a false-positive generator the current design does not have. It must never append to `root_inputs`, never reach `_cache_rebuild_ttl_verdict`, and never increment `consistent_5m_roots`, `consistent_1h_roots`, or `excluded_roots` — counting slices would silently change the unanimity unit from root to root-slice, which is the same hazard the prior plan's "a lone root is not evidence of invariance" disclosure rule exists to prevent. Implementation constraint: these lines must **not** begin with the root label token. `_extract_ttl_verdict_root_row` asserts `len(rows) == 1` after matching on `ln.split()[0] == root_label`, and `split()` discards leading whitespace, so indenting a line that starts with `account-1` would still break every existing per-root row test. Lead each line with a fixed literal instead — `tier-split account-1: 5m-slice favors 1h, 1h-slice favors 5m (disagree)`.

**Conditional `pricing.py` change**, gated on step 3 (b) finding records that lack the nested block. The recommended mechanism is *not* to change `_cache_write_split`'s return contract (`pricing.py:189-201`). That function feeds every cache-rebuild section — the default-path `w5m_by_origin`/`x_by_origin`/`switch_delta_by_origin` accumulators, `_cache_rebuild_excess_dollars`, and the dispersion oracle — and the prior plan's M1 regression guard exists specifically to forbid a default-path output change. Instead add an additive sibling predicate in `pricing.py` (e.g. `_usage_has_nested_cache_write_split(usage) -> bool`) and consult it inside the `--ttl-verdict` accumulation block only, gating **`in_w5m_branch`'s own boolean definition and `in_w1h_branch`'s write-disjunct** (`eph_1h > 0`) — not the individual downstream increment lines. `X` (`x_by_origin_root`) and both switch-delta accumulators are populated inside the same `if in_w5m_branch:` block as `w5m_by_origin_root` (`:6754-6773`), keyed off the identical `eph_5m` value the flat fallback manufactures; gating only the `w5m_by_origin_root` increment itself would leave those three accumulators silently inheriting the phantom 5m attribution while the new disclosure counter reports the case as handled. `in_w1h_branch`'s read-token-driven second disjunct (`read_tokens > 0 and is_idle_sensitivity`, `:6740`) is independent of this record's own write tiering and must stay ungated. A flat-only write record is thus routed into neither `w5m_*` nor `w1h_*` at the point both branches are decided, and instead into a new pooled `untiered_write_turns`/`untiered_write_tokens` disclosure counter printed beside the existing `unpriced_ttl_verdict_turns` line (`:7175-7179`), which is the established pattern for exactly this kind of "excluded from every figure above" disclosure. Rationale: a record with no tier field is not evidence about either tier, and attributing it to 5m manufactures the phantom contamination this check exists to rule out — but the fix belongs where the tier question is being asked, not in shared pricing that other sections consume for a different purpose. **The engineer already confirmed this fix ships in this plan rather than a separate one; the design here narrows the mechanism, not that scope decision.** If the engineer wants `_cache_write_split`'s own attribution changed for every section, that is a distinct call in direct tension with M1's regression guard and needs an explicit override plus regression coverage across all four consuming sections; it is not assumed here. If step 3 (b) finds zero such records, nothing ships in `pricing.py` and the finding is recorded in the ledger — the docstring is *not* edited to claim no such record exists, since a zero count on one corpus is not that claim.

**Redaction constraint on the threshold's own rationale.** The governing property: no figure with a per-account or per-corpus numerator or denominator may reach the plan file, a commit message, the PR body, or a code comment. This covers:

- a per-root tier share
- a flat-only record count
- an aggregate ratio like "N of M roots"

`CLAUDE.md` § "Also redact structural fingerprints and provenance" bars publishing a figure carrying a per-account dimension absolutely. The pooled-tooling carve-out (prior plan row 11) is closed at tool calls / sessions / dispatches, and does not reach any figure in that class.

The constant's comment, the commit message, the PR body, and the ledger row state the threshold and a *shape* of reason instead — for example, "set above the incidental-fallback shares observed in the live check and below the genuinely-mixed ones." Use only comparative, non-numeric language: no number, percentage, range, or magnitude word of any kind. A hedged approximation ("roughly 95%," "in the low 90s") is exactly as prohibited as the exact figure, since it narrows the true value once paired with the threshold constant that *is* published exactly.

**Over-powered-primitive check on Part B's mechanism.** A share-based gate is the lightest mechanism that actually solves the problem; three lighter or simpler options were checked against the source and fail:

- *A fixed absolute-dollar contamination tolerance* (treat a root as consistent when the minority tier's dollar volume is under a fixed `$N`) — does not scale with root volume, which is the whole defect: a heavy root's 2% fallback is many dollars while a light root's 40% mixing is pennies, so one cutoff simultaneously excludes the heavy roots the fix targets and admits genuinely mixed light ones. It also needs an engineer-set ungrounded number of its own, so it is not less surface, only less meaningful surface.
- *Shortening the window so fallback episodes fall outside it* (no code change at all) — G5 makes 30 days the entire evidence budget, shrinking it degrades every root's margin precision, and there is no window short enough to miss fallback episodes on the heaviest roots yet long enough to be representative. It is also an operator action, not a property of a shipped analyzer, so it cannot be pre-registered.
- *Dropping the eligibility test entirely* and letting the margin check filter — the 10% margin measures net against volume and has no ability to detect tier mixing, so a genuinely 50/50 root would contribute a verdict its own data cannot support, and a root with data in both directions would produce two inputs or an arbitrary pick.

*Rejected as heavier, for completeness:* per-call or per-slice tier attribution replacing the root-level tier concept — that changes the unanimity unit from root to slice, the exact hazard the cross-check above is deliberately kept out of the verdict to avoid.

**Over-powered-primitive check on how the threshold is exposed.** A module-level constant `_CACHE_REBUILD_TTL_DOMINANT_TIER_SHARE_MIN`, sibling to `_CACHE_REBUILD_TTL_MARGIN_FRACTION` — not a CLI flag. A flag would let an operator tune the eligibility gate after seeing the verdict, destroying the pre-registered-decision-rule property the prior plan established, and buys nothing the constant does not.

**One decision bundled into step 3, not blocking this plan.** `share` can be denominated in tokens or in tier-priced dollars. The recommendation is **tokens**, for three reasons: dominance asks which tier the root is *running* (a state fact), and dollar weighting re-scores it by the very price structure the verdict is about; the 2x/1.25x weighting is direction-asymmetric, so a single threshold would mean 85/15 when the majority is 5m and 94/6 when it is 1h — reintroducing exactly the direction-specific bias this fix removes; and `w5m_dollars_by_origin_root` increments only when `_model_rates` returns a price (`:6756-6758`, `:6777-6779`) while `w5m_by_origin_root` always increments, so a dollar share is computed over a subset of the tokens in its own denominator. The engineer confirms the metric alongside the threshold at step 3, since they are one decision.

**Transcription precision.** Part A prints `Share` rounded to 3 decimals. When the engineer reads a printed value at step 3 and transcribes it into the `_CACHE_REBUILD_TTL_DOMINANT_TIER_SHARE_MIN` constant, the stored comparison is `>=` against the *unrounded* float underneath, which can be strictly greater than the printed figure (e.g. an underlying `0.97251...` prints as `0.973`; using `0.973` literally as the threshold would then exclude the very root that motivated the choice). Round down from the printed value (or otherwise choose a value strictly below every printed share meant to qualify) when setting the constant, and note this in the commit's non-numeric rationale.

### Assumption ledger

### Root problem

`--ttl-verdict`'s consistency gate reads a transient vendor tier transition as a permanent per-root tier assignment and suppresses the row that would reveal it, so the heaviest roots are structurally barred from ever contributing to a verdict and the exclusion cannot be diagnosed from the tool's own output.

### Givens (fixed beyond this design's reach)

- **G1 — The vendor owns the usage-limit auto-fallback.** A subscription root over its plan limit has its main conversation dropped to the 5-minute TTL mid-window; this design cannot stop a heavy root from writing both tiers inside one 30-day window, only decide how to score one that does. `[verified: vendor doc quoted in .claude/plans/cache-ttl-tuning-analysis.md row 2 — "Once you go over your plan's usage limit ... Claude Code drops the main conversation to the cheaper five-minute TTL"]`
- **G2 — `cache_read_input_tokens` carries no tier split.** `Z` can never be attributed to a tier, so a mixed root's `Z` inherently includes reads that occurred under the minority tier; the design discloses the resulting bias rather than removing it. `[verified: pricing.py:189-201 splits writes only; no read-side tier field exists in the record schema]`
- **G3 — No vendor or protocol source prices how much tier mixing invalidates a single-tier premise.** The dominance threshold has no external grounding by construction and can only be an engineer-set value from local evidence. `[verified: absence across both vendor pages cited in the prior plan's G1/G4]`
- **G4 — `claude/.claude/settings.json` is one committed file stowed to every consumer.** It cannot hold two values, so cross-root unanimity remains the gate on shipping a default; this plan changes root *eligibility*, never that rule. `[verified: CLAUDE.md "Plans in this repo affect all stow users"]`
- **G5 — Claude Code deletes transcripts.** The 30-day window is the whole evidence budget and the step-3 live check is a one-shot measurement that cannot be re-derived later. `[verified: docs/transcript-analysis.md's cost-ledger section states this as the reason the ledger exists]`

### Mechanisms

- **M1 — Move the row print above the contribution decision, leaving `excluded_roots` / `root_inputs` semantics untouched.** The `continue` at `:7126` conflates "does not count" with "is not shown"; only the second is a defect. `anchors: root, row1`
- **M2 — Name each exclusion reason as a whitespace-free module constant in an ordered tuple, mirroring `_CACHE_REBUILD_CAUSES`.** The in-file convention already exists for a diagnostic bucket that earns its own row, and the extractor's `split()`-based column mapping makes whitespace-free mandatory, not stylistic. `anchors: row2`
- **M3 — Add one `Share` column in Part A, before the gate changes.** The threshold's own input has to be on the table the engineer reads at step 3, or the decision is made by hand arithmetic over two columns. `anchors: row3, row6`
- **M4 — Replace the XOR gate with `share >= threshold`, feeding only the dominant tier's own accumulators into the unchanged `_cache_rebuild_root_verdict_input` call.** The two directions' delta accumulators are tier-scoped and oppositely signed, so no combined net is definable; reusing the existing per-tier call path leaves every downstream invariant and its tests intact. `anchors: root, row4, row5`
- **M5 — Keep the two-slice comparison strictly informative: no margin check, no `root_inputs` append, no count increment, and no line beginning with a root label.** Slice-level margin-clearing is a false-positive generator, and counting slices changes the unanimity unit. `anchors: row7, row8`
- **M6 — Handle a flat-only cache-write record with an additive `pricing.py` predicate gating `in_w5m_branch`/`in_w1h_branch`'s own boolean definitions, plus a new `--ttl-verdict`-local disclosure counter, not by changing `_cache_write_split`'s return contract.** The shared function feeds four default-path sections the prior plan's M1 regression guard protects; gating the branch booleans themselves (rather than one downstream increment) ensures `X` and both switch-delta accumulators cannot silently retain phantom 5m attribution. `anchors: row9, row10`
- **M7 — Over-powered-primitive check on Part B.** An absolute-dollar tolerance, a shortened window, and dropping the gate entirely are each lighter and each fail (Approach section); a module constant rather than a CLI flag keeps the rule pre-registered. `anchors: root, G3`

# GH-895 + GH-896: consult visibility across the plan-file route and the subagent scan gap

## Context

A `plan-architect` consult prescribed by `docs/design-decisions.md` §42 becomes invisible to `skill-fidelity-reviewer`'s architect-consult check in two independent ways, and both need fixing before that check's `[SILENT-SKIP]` ceiling can be safely narrowed. GH-895: on a branch carrying a plan file, §42 routes the escalation through `plan-it` Step 5's `MODE=plan-sections` re-dispatch, and both `log-reviewer-round.sh`'s latch writer and `transcript-analysis.py`'s `_is_architect_consult_dispatch` classify that literal as "not a consult" — so a fully §42-compliant escalation writes no latch and emits no `review-trace` event. GH-896: `review-trace`'s scan is main-thread-only, so a consult (or an entire `/code-review` round) dispatched from inside a subagent is structurally invisible regardless of §42 compliance. The intended outcome is that a `plan-architect` consult is observable by both `require-architect-consult.sh`'s gate and `review-trace`'s event stream no matter which route it took, and that `skill-fidelity-reviewer` can then treat a still-missing consult row as a real finding rather than an automatic skip, for the two cases this closes.

## Decisions (engineer-confirmed this session)

If the return endorses the new mechanism and a plan file exists, follow with `plan-it` Step 5's revision re-dispatch to insert the sections (this second dispatch only fires on endorsement). If it endorses and no plan file exists, §42's existing "enters through `/plan-it` on its own terms" sentence already covers it. If it rejects, there is no second dispatch and no plan edit. `[engineer-verified]`

Denial/friction counts move as an accepted consequence; the affected published figures (cost-ledger.md, three case-study docs) get a disclosure note rather than a compatibility shim, since they are already dated snapshots against a growing corpus. `[engineer-verified]`

## Corrected premise (do not plan against the GH-896 issue text as filed)

Empirical measurement this session (3 runs each, real corpus) found that widening scan scope alone changes **zero** skill/reviewer/architect-consult events (160/160, 544/544, 26/26 identical with `include_subagents=True` on vs off) — only denial (+364) and friction (+6) counts move, because `_review_trace_session_events` gates skill/reviewer/consult detection on `not bool(rec.get("isSidechain"))` but carries no such gate for denial/friction detection. **Both the scan-scope default and this detection-time guard must change together**; scope alone (as GH-896 proposes) fixes nothing for the problem it names.

Two of GH-896's three stated hazards are empirically absent, verified against the real corpus:
- **Timestamp ordering**: all 842 subagent files' timestamp ranges overlap their parent session's span; none sits entirely before or after it. A widened scan still needs an explicit timestamp sort for the emitted timeline to stay chronological, since today's `include_subagents=True` concatenates each subagent file as a contiguous block after the main file (`transcript-analysis.py:877`) rather than interleaving by time. `line_no` is a position in that flat concatenated list, not a file line — its meaning needs explicit documentation (or replacement) once the stream is sorted.
- **Branch attribution**: 0 of 840 subagent files carried a `gitBranch` differing from their parent's main-thread branch at dispatch time. `_review_trace_session_events`'s branch/model carry-forward trackers (`last_branch`/`last_model`, transcript-analysis.py:1547-1564) already update only on non-sidechain records, so a sidechain event already inherits the correct parent branch once it starts being processed — no new attribution logic needed.

GH-896's "outlier" framing is also inaccurate and should not be repeated in the plan's rationale: 12 subcommands pass `include_subagents=True`, 2 expose a CLI flag, and 19 (including `review-trace`) do not. The 19 share a property: they measure main-thread *orchestration* signal (did a dispatch/denial/gate event happen), where only the fact of the event matters, not what happened inside the dispatched agent. `review-trace` is consistent with that cohort, not an outlier from it — see `cost-ledger`'s own three-iterator split (transcript-analysis.py:6669 widened, :6676 widened, :6670 narrow) as the clearest existing instance of the same convention. The GH-896 issue's claim that widening `review-trace` alone would "silently move published cost-ledger denial counts" is backwards: `_compute_deny_summary_data`'s two call sites (1890, 6710) resolve scope independently today, so widening one without the other makes them *disagree* — it doesn't move the other one's number. That is why the engineer-confirmed fix above widens both together.

## Approach

**The concluded design in plain language.** Two independent blindnesses hide a compliant `plan-architect` consult, and they get fixed in two sequenced PRs off this one plan.

GH-896 (first PR) makes `review-trace` able to see a consult at all. Widening scan scope is necessary but not sufficient: `_review_trace_session_events` gates skill/reviewer/consult detection on `not bool(rec.get("isSidechain"))` (`transcript-analysis.py:1593`) while carrying no such gate on denial/friction, which is exactly why scope-alone moved denial and friction counts and nothing else. So the guard at `:1593` comes off — and only that one: the *separate* `isSidechain` test at `:1556` guards the branch/model carry-forward trackers, not detection, and it stays exactly as it is (lifting it would attribute a sidechain event to its own record's `gitBranch` instead of the parent's). `cmd_review_trace`'s scope call at `:1882` passes `include_subagents=True`, and `cost-ledger`'s narrow `deny_session_iter` (`:6670`) widens in the same commit so its `denials` column and `review-trace --deny-summary` cannot disagree. Two consequences of merging a second source file into one stream are handled at the same time: the merged records are timestamp-sorted before the detection loop so the timeline is chronological rather than main-block-then-subagent-block, and every event dict gains a `thread` field (`main`/`sidechain`) so a reader can tell which rows the `line_no` column still indexes.

GH-895 (second PR) makes a consult *happen on a route the existing detectors already recognize*. `/code-review`'s Fix-route block currently forks on plan-file existence and sends the plan-file arm through `plan-it` Step 5 carrying `MODE=plan-sections` — a literal that both `log-reviewer-round.sh:125` and `_is_architect_consult_dispatch` define as *not a consult*. Direction 3-amended collapses the fork: always dispatch `MODE=consult` first, passing the plan file's path when one exists, and re-dispatch through `plan-it` Step 5 only on endorsement. Nothing in the hook layer changes.

**The finding that changes this plan's disclosure scope.** The `160/160, 544/544, 26/26` result measured scope-widening *with the guard intact* — the one configuration that suppresses exactly the events in question. How far skill, reviewer-spawn, and architect-consult counts move once the guard also comes off is **unmeasured**. That matters because the published figures needing a note are not only denial counts: `docs/case-studies/handoff-threshold-impact.md:91-94` publishes review-trace-derived reviewer-spawn totals (1,090 / 408) and per-branch spawn rates, and `docs/case-studies/review-vs-babysitting.md:28,30` publishes review-skill-invocation and specialist-spawn counts alongside its 946-denial headline. Measure the five per-kind deltas at merge-base vs. HEAD before writing any disclosure note, and scope the note to whichever kinds actually moved.

**The SILENT-SKIP narrowing's trigger.** The narrowing cannot hang on §37's user-ask gate or §42's Fix-route narration: `skill-fidelity-reviewer`'s evidence is the invocation list, the diff, the plan, and the timeline, and both of those explanations live only in conversation. The engineer confirmed anchoring it to an observable trigger instead. `require-architect-consult.sh` emits `Blocked by architect-consult gate: …` (`:38`, `:115`), and a hook deny is already a `denial` event whose message `review-trace` prints (`transcript-analysis.py:1953`). A branch whose timeline carries that deny row and no later `architect-consult` row, yet reached `/ready-for-review`, is decidable from the timeline alone — this is the one obligation trigger `skill-fidelity-reviewer` can actually observe. The check keys on that printed `msg=` text, never on the row's `hook=` field, which is empty for every current-shape denial (row 18). This is not §48 reason 3's rejected latch correlation: the latch correlation duplicates what the preventive gate already enforces, whereas this detects the case where the preventive gate fired and was routed around, which the gate by construction cannot see itself. §48 reasons 2 and 3 (`docs/design-decisions.md:1000-1001`) stand untouched — this closes only reason 1 (subagent invisibility) plus the fourth blindness (§42's plan-file misclassification) that §48 never enumerated. §48's own ceiling sentence (`:997`) is superseded by PR 2's new entry, not edited (M8).

**§48's out-of-scope declaration holds for GH-895 — confirmed, not assumed.** `log-reviewer-round.sh:137-141` calls `_maybe_write_consult_latch` for any `SUBAGENT_TYPE = "plan-architect"`, and that function returns early only when the prompt's first line is literally `MODE=plan-sections` (`:125`). Under the unified route the first dispatch's first line is `MODE=consult`, so the latch is written with no hook edit; the conditional second dispatch carries `MODE=plan-sections` and correctly writes nothing, which is harmless because the latch already exists. `require-architect-consult.sh:112-113` tests only `[ -f "$LATCH_FILE" ]` and is mode-unaware. Its deny message (`:115`) already instructs "Dispatch `plan-architect MODE=consult` first," which the unified route makes *more* accurate, not less. No hook, no latch shape, and no gate behavior changes.

**§48's stated worry about reopening §25 does not survive contact with the code.** §48 declined the widening partly because it would "reopen the §25 blindness question with real sidechain prose in scope." The guard being lifted is a *detection* guard, and detection stores only a classification result plus branch/model/timestamp — pinned at the event-dict layer by `test_architect_consult_event_key_set_carries_no_prompt_derived_field` (`test_transcript_analysis.py:3109-3123`). Denial and friction events do carry free `message` text, but they carried it before this change for main-thread records and `skill-fidelity-reviewer` already reads it; widening changes the volume of an already-accepted text class, not its kind, and adds no assistant-authored prose.

### Assumption ledger

**Root problem.** A `plan-architect` consult prescribed by §37, §42, or §45 can be dispatched in full compliance and still leave no latch and no `review-trace` row, through two independent mechanisms: §42's plan-file arm carries a mode literal both classifiers define as not-a-consult, and `review-trace` neither loads sidechain records nor detects consults in them.

**Givens** (fixed beyond this plan's reach):

- **G1.** `MODE=plan-sections` / `MODE=consult` is a two-valued protocol literal the caller must emit, with mode never inferred from prompt shape. §37 settled this; reopening it would invalidate `CONSULT_CLASSIFICATION_TABLE` against both the bash and Python runtimes simultaneously.
- **G2.** Claude Code owns the `<session_id>/subagents/*.jsonl` split-transcript layout, its `isSidechain: true` flag, and the fact that a subagent record carries the *parent's* `sessionId` rather than its own.
- **G3.** `_resolve_project_scope` returns a fresh single-use iterator per call, and `read_session_file` hands callers a flat record list with no per-source-file boundary. Changing that contract touches every `cmd_*` entry point, so it is not this plan's to change.
- **G4.** Transcripts are deleted on a rolling `cleanupPeriodDays` window, so any corpus figure is a dated snapshot that cannot be re-derived later — a compatibility shim over a moving corpus would be fiction.
- **G5.** `docs/case-studies/*` and `docs/reports/*` figures are preserved records under CLAUDE.md §Scope discipline Axis 3. Only additive methodology notes are permitted; a recorded number is never recomputed in place.

**Over-powered-primitive check, for the two mechanisms that add structure.**

M4 sorts, where two lighter options exist. *Sort only the emitted events, leaving records in concatenation order* — rejected: the branch/model carry-forward trackers (`:1547-1564`) update only on non-sidechain records, so with the main file processed entirely first, every sidechain event would inherit the session's **final** main-thread branch rather than the one live at dispatch time. Sorting the records instead makes that attribution correct by construction. *Leave the stream unsorted and document the per-file block ordering* — rejected: it makes the timeline non-chronological precisely where the new rows land, which defeats a reviewer reading it as a sequence. The rejected *heavier* option is real too and is the reason `line_no` is not replaced outright: threading `_read_session_file_partitioned` (`corpus.py:35-67`) through scope resolution would give sidechain rows a true file-and-line locator, but it changes the session-iterator contract for every `cmd_*` entry point (G3) to improve one column on one subcommand.

M5 adds a key, where two lighter options exist. *Document `line_no`'s dual meaning without a marker* — rejected: the reader has no per-row way to tell which meaning applies, so the column silently lies on half the rows. *Derive the thread at print time* — rejected: the event dict deliberately retains no reference to its source record, and reintroducing one would weaken the very property `test_architect_consult_event_key_set_carries_no_prompt_derived_field` pins. The `main`/`sidechain` vocabulary is not invented here; it is `skill-invocation --include-subagents`'s existing `thread` column (`docs/transcript-analysis.md:364`).

**The sort key's three components, each a decision rather than a default.** `effective_ts` alone is not a total order, because `_parse_ts` returns `None` for an absent or malformed timestamp and `None < float` raises `TypeError` (row 22) — the forward-fill and the leading-record `-inf` fallback are what make the key total, not a cosmetic nicety. `effective_ts` governs **ordering only**: the `--since`/`--until` filter at `:1578-1584` keeps testing the record's own `_parse_ts` result, so a filled value never admits a record the window would otherwise drop. `thread_rank` converts an artifact into a choice: Python's sort is stable, so a timestamp-only key would resolve every tie by pre-sort position, which for sidechain records is `read_session_file`'s sorted-*filename* order (row 23) — not chronological, and not anything a reader could predict. Main-before-sidechain is the right direction for the common collision, a dispatch record and the first record of the subagent it spawned sharing one timestamp: it puts cause before effect, and it is the ordering that lets M1's untouched `:1556` trackers set `last_branch`/`last_model` from the dispatching record *before* the sidechain event that should inherit them is processed. `pre_sort_index` last keeps within-thread order stable and keeps `line_no` meaningful.

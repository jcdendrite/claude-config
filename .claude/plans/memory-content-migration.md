# Memory content migration

## Context

Auto-memory audit of `claude-config`'s project-scoped memory (`~/.claude/projects/-home-<user>-MyCode-claude-config/memory/`, 44 files) found that a meaningful fraction of the content encodes rules that either duplicate an already-committed CLAUDE.md rule, or belong in a durable git-tracked surface (global CLAUDE.md, a skill body, `docs/design-decisions.md`) rather than in memory scoped to one project/account/machine — which is the likely cause of Claude Code behaving inconsistently across the user's machines when working on `claude-config`. The goal is to migrate each misclassified fact to its correct durable home and remove it from memory once promoted, so the rule fires deterministically regardless of which machine or account the session runs under.

## Approach

Every rule in the audited set gets exactly one durable home chosen by **where it fires**, not by convenience: a rule that fires every session goes in `claude/.claude/CLAUDE.md`, a rule that fires when a file type is open goes in a path-scoped `claude/.claude/rules/*.md`, a rule that fires inside one skill's workflow goes in that skill's `SKILL.md`, a claude-config-only rule goes in the repo's own project layer under `.claude/skills/*-claude-config/`, and a decision record goes in `docs/design-decisions.md`. Each memory file is then removed once — and only once — its content has a live durable home, so nothing is dropped in the gap. This routing is not invented here: `ai-instruction-and-memory-files/SKILL.md` Step 1 items 1–4 and §5's two routing tables already prescribe it, and this plan is that skill applied to a backlog it was written to prevent.

**Four of the audit's "not covered" verdicts flip to "covered" on re-check, and those memories are deleted rather than promoted.** Step 3's coverage pass compared candidate rules against `claude/.claude/CLAUDE.md` only. Extending the check to skill bodies and project layers found:

- **GH API reply-vs-edit** is fully covered by `claude/.claude/skills/respond-pr/SKILL.md` step 7, which names the PATCH hazard in the same sentence as the `/replies` recipe, plus `claude/.claude/scripts/respond-pr-safe-patch.sh`, which enforces the ownership check that makes a PATCH safe.
- **Integration-test auto-allow** is covered by `claude/.claude/skills/review-permissions/SKILL.md` checklist item 18, which names the same shared-database concurrency risk and the same four runners.
- **Memory-vs-CLAUDE.md classification** is covered four times over inside `ai-instruction-and-memory-files/SKILL.md` — Step 1 item 1, Step 1 item 4, the §4 routing row, and §5's "Delete on contact" heuristic.
- **plan-review user surface / stow distribution** is covered by root `CLAUDE.md` line 71 *and* by `.claude/skills/plan-review-claude-config/SKILL.md`, whose entire body is that rule. The memory's claim that the pointer went stale is itself now stale.

Promoting any of those four would have created the duplicate-drift the migration exists to remove. Two more — don't-auto-merge (root `CLAUDE.md` + `block-gh-pr-merge.sh` + global `CLAUDE.md` §Shipping "Merge stays human-only") and code-review specialist dispatch (`code-review/SKILL.md` Step 0.6, the Change-type table, the mandatory *Spawn decisions:* line, and the closed list of invalid skip rationales) — were already known duplicates. Eight of the twenty audited files therefore need no promotion at all.

**The remaining promotions are placed at their firing point, and most avoid `CLAUDE.md` entirely.** `CLAUDE.md` is the most expensive surface in the system — every line is re-read in every session in every repo — so it takes only the four rules that genuinely have no narrower trigger: presentation ordering when surfacing a decision, never publishing the owner's email in a public repo, discovering rather than accepting destructive-script targets, and syncing a PR body in the same turn a commit resolves a pending item. Everything else lands narrower. The `$HOME`-shadowing rule goes to `claude/.claude/rules/shell-script-conventions.md`, which auto-loads on `**/*.sh` and already carries a `local`-scoping bullet of exactly that shape. Worktree-crossing goes to `branch-management`. The preprint clause goes to `verify-sources`. Ready-vs-draft goes to `ready-for-review` step 6, the one place in this system that creates a PR. Three memory-hygiene rules go into `ai-instruction-and-memory-files` itself, where the hook (`require-memory-skill.sh`) guarantees they are loaded at the exact moment a memory is being written.

**Two edits close gaps rather than relocate rules.** The code-review specialist memory's one surviving claim — spawn every affected lane, not only lanes whose files appear in the diff — is added as a trailing clause on the existing Change-type row at `code-review/SKILL.md:257`, whose test ("demonstrably changes the *output* or *decision* that lane's specialist would review") is already the right test but reads as scoped to edited files. Extending that row was chosen over the two other candidate anchors (Step 0's domain classifier, line 230's contract-blast-radius bullet) because Step 0's domains are too coarse to discriminate here — every file in this repo classifies as "Claude Code config" — and because adding a third site for one idea is the compounding-prose-layer pattern this repo names as a wrong-foundation tell. The plan-freshness memory has no coverage anywhere and gets one new paragraph in `plan-it` Step 7, placed there because Step 7 already establishes per-phase `code-writer` dispatch as the execution unit, which gives the "before a major scope decision" checkpoint a concrete boundary it otherwise lacks. One paragraph covers both of the memory's checkpoints; a second edit in `ready-for-review` was considered and rejected as a stacked layer with the same remedy.

**The `plan-review` cross-reference is a heading fix, not new prose.** `.claude/skills/plan-review-claude-config/SKILL.md` heads its section `## User surface (Step 2)`, but the user-surface question lives at `plan-review/SKILL.md` Step 4, question 1 — Step 2 is problem restatement and Step 2.5 is the project-layer load. Retitling the heading to `## User surface (Step 4, question 1)` lands the layer where the question actually is, which is the whole mechanism the memory wanted and costs one line. Editing the global `plan-review/SKILL.md` was rejected: global skill bodies must stay platform-agnostic per `.claude/rules/skill-and-agent-self-review.md`, so a claude-config-specific stow-distribution rule cannot go there, and a generic restatement would be a third copy of a rule root `CLAUDE.md` already states.

**The CI-eval memory becomes a two-sentence index entry, not a restatement.** `evals/README.md`'s "Why local only — never CI" section currently and completely documents all three objections. `docs/design-decisions.md` §32 therefore follows §20's shape — name the decision, name the three objection categories, point at the holding site — so a future plan searching the decision register finds the closed question without a second copy of the reasoning. Critically, the entry is sourced from the current `evals/README.md` and `evals/run_skill_evals.py`, not from the memory: the memory names `evals/run_trigger_evals.py` (renamed) and "three pilot skills" (now five skills across four measurement methods).

**One memory is kept unchanged.** `feedback_dont_violate_the_rule_you_just_cited.md` records a genuine incident and its calibration language, and its two substantive claims are already enforced elsewhere — `CLAUDE.md` §Working Style's compounding-layers bullet, `CLAUDE.md` §Engineering Judgment's "locally-valid patch can signal a wrong foundation" ladder (cast → upstream type, helper → call site, label → canonical name), and `plan-review` Step 4's "Self-referential findings" tripwire, which fires on exactly the observable shape. Adding a fourth prose site for the same idea would be the anti-pattern the memory itself names.

**Sequencing is promote-then-remove, in two phases, and the second phase cannot be delegated to `code-writer`.** All in-repo edits land and commit first, so every rule has a live durable home before its memory copy disappears. Memory teardown runs second, from the parent session or a `general-purpose` subagent: `require-memory-skill.sh` gates every `MEMORY.md` write behind the `ai-instruction-and-memory-files` active marker, and per `CLAUDE.md` §Safety `code-writer` and reviewer agents are denied marker writes. Deleted bodies are moved to a session scratch directory rather than `rm`'d — auto-memory is unversioned, so `rm` is irreversible, and `mv` costs nothing while the change is under review.

**Cross-machine memory drift — resolved as out of this plan's scope, not a filename-list handoff.** This PR removes the stale memory copies on *this* machine and account only. The same rules may or may not be duplicated in every other machine's and account's `projects/<project-dir>/memory/` for this repo — auto-memory is Claude-written and accrues independently per machine, not stowed, so no two machines carry the same file set and a filename list from this machine's audit does not transfer. The promoted rules will fire everywhere once the repo is pulled regardless; only the stale-duplicate cleanup is machine-local. The right fix for that is a repeatable, re-runnable audit mechanism, not a one-off list produced by this session — this plan does not attempt to build one.

### Assumption ledger

**Root problem.** Twenty auto-memory files in this repo's memory directory encode rules that either duplicate an already-enforced durable surface or belong in a git-tracked one; because auto-memory is machine- and account-local, those rules fire inconsistently across the user's machines while burning index budget on every session everywhere.

**Givens** (conditions the design treats as fixed and cannot reach):

- **G1. Auto-memory lives at `<config-dir>/projects/<project-dir>/memory/`, is unversioned, and the harness loads only the first 200 lines or 25KB of `MEMORY.md` each session.** Vendor-imposed by Claude Code; no repository artifact changes it.
- **G2. Memory directories on the user's other machines and other `CLAUDE_CONFIG_DIR` accounts are not reachable from a git change to this repo.** Dissolving the plan's dependence on this requires a per-machine action by the user, which is a decision outside this plan.
- **G3. Load semantics differ by surface: `CLAUDE.md` loads every session, a `.claude/rules/*.md` loads on `paths` match, a `SKILL.md` loads when its skill fires, a project layer loads via the base skill's glob, and a `docs/` file loads only on demand.** Harness-imposed; it is the constraint the entire routing decision is built on, not something the plan selects.

**Mechanisms:**

- **M1 — Delete-without-promotion for eight already-covered memories.** `anchors: root` — a memory restating an enforced rule is pure load, so removing it advances the root problem with zero risk of dropping a rule.
- **M2 — Four new `CLAUDE.md` entries (§Working Style ordering clause; §Safety email and destructive-input bullets; §Code Comments no-memory-citations bullet; §Shipping PR-body-sync bullet).** `anchors: root`. **Over-powered-primitive check** — `CLAUDE.md` is the heaviest available surface (every session, every repo), so two lighter primitives were tested against each entry and fail: a **path-scoped `.claude/rules/*.md`** cannot carry any of the four, because none is triggered by a file type being open (presentation ordering fires in chat, email publication fires across `SECURITY.md`/commit messages/PR bodies alike, destructive-target discovery fires at design time before any file exists, and PR-body sync fires on a commit); a **skill body** cannot carry them either, because each fires outside any single skill's workflow — the PR-body rule is the closest call, but `pr-description` only runs when invoked, and the rule's entire content is *when* to invoke it. `AGENTS.md` was also considered and set aside: this repo has no `AGENTS.md`, and per the skill's own §4 table one is added only when a non-Claude agent reads the repo.
- **M3 — Promotions into `branch-management`, `verify-sources`, `ready-for-review`, and `shell-script-conventions.md`.** `anchors: root`, and each is the *lighter* primitive M2 rejected for its own four: these four rules do have a single firing point, so they cost zero every-session budget.
- **M4 — Three additions inside `ai-instruction-and-memory-files/SKILL.md`.** `anchors: root` — the hook gating memory writes guarantees this skill is loaded exactly when the rules apply, which no other surface can match. The three are orthogonal (where ephemeral state goes, how to scope what is saved, what to confirm before deleting), not layers closing each other's gaps.
- **M5 — One trailing clause on `code-review/SKILL.md`'s instruction-artifact Change-type row.** `anchors: row 4` — extends an existing test rather than adding a row, bullet, or step.
- **M6 — One paragraph in `plan-it` Step 7.** `anchors: row 5` — Step 7 already names per-phase dispatch, giving the "major scope decision" checkpoint a concrete boundary; one paragraph covers both of the memory's checkpoints.
- **M7 — Heading correction plus a severity-nuance sentence in `.claude/skills/plan-review-claude-config/SKILL.md`.** `anchors: row 6` — the project layer is the only surface that may carry a claude-config-specific rule without violating global-skill platform-agnosticism.
- **M8 — `docs/design-decisions.md` §32 as a pointer entry.** `anchors: row 7` — modeled on §20 so the decision register gains an entry without a second copy of `evals/README.md`'s reasoning.
- **M9 — Memory teardown by `mv` to a scratch directory, then index-line removal.** `anchors: root`. Lighter alternatives considered: `rm` (rejected — auto-memory is unversioned, so the delete is irreversible and the change is still under review) and leaving the bodies in place while removing only index lines (rejected — an unindexed body is unreachable clutter that a later audit re-discovers as a live memory).

## Critical files

Notation: `<mem>` is this checkout's auto-memory directory — the directory holding the `MEMORY.md` already loaded into the executing session's context. Resolve it from that loaded context rather than hardcoding a path; the absolute path names the contributor's home directory and this plan file ships in a public repo.

**Dispatch split.** Phase 1 (all in-repo edits, files 1–10 below) is one `code-writer` dispatch — nine small prose insertions plus one one-line hook-cap bump with its mirrored test pair (item 6), all with wording fully specified here, no shared state to restate, and no output feeding another dispatch's input. ### Phase 1 — in-repo promotions

**1. `claude/.claude/CLAUDE.md`** (149 lines; must stay ≤200)

- **§Working Style, the first bullet** ("Walk through your proposed approach…"). Append to that bullet: ordering matters as well as evaluation — open with the one sentence naming why it is a genuine decision (competing consumers, incompatible invariants, a false premise, two correct readings of one artifact), then the options; if that sentence cannot be written, pick the sensible default and say so instead of escalating. *Why:* the existing bullet requires a recommendation but says nothing about sequence, and opening with the option list is what drew the correction.
- **§Safety, after the "Never commit secrets, credentials, API keys…" bullet.** New bullet: never publish the session owner's email address in a public repo — the `userEmail` context identifies the user to you, it is not contact copy for `SECURITY.md`, `CODE_OF_CONDUCT.md`, `README.md`, a commit message, or a PR body, and git history cannot retract it. Route security reports to GitHub private vulnerability reporting and other contact to a published business form; if a template genuinely demands a `mailto:`, propose a role mailbox and confirm before committing. *Why:* the owner's own address is explicitly outside the redaction hook's person-name detector, so no mechanical control covers it.
- **§Safety, after the principle-of-least-privilege bullet.** New bullet: in destructive paths, discover the target instead of accepting it as input — when a script deletes, resets, or force-writes, ask first whether the target can be discovered from local state (git, filesystem, an API query); discovery removes the input-validation problem rather than defending it, since a supplied identifier still needs a grammar, a length cap, and often a paired hook; fall back to a supplied identifier only when discovery is genuinely impossible. *Why:* least-privilege's structural sibling — narrow the input surface, not just the permission — and distinct from §Engineering Judgment's over-powered-primitive bullet, which is about mechanism weight rather than input sourcing.
- **§Code Comments, Documentation, and Prose → "When to write it and what to include", after the "No 'used to be X'" bullet.** New bullet: no auto-memory citations — auto-memory is per-user and per-machine, so a `feedback_*.md` reference resolves for no other reader; cite the `CLAUDE.md` line, skill body, or doc that states the rule, and if none does and the rule is general, put it there first. *Why:* the section already requires durable docs to be readable without the PR description; a memory citation fails the same test for a different reason.
- **§Shipping, as a new top-level bullet after the autonomous-shipping bullet and its sub-bullets.** New bullet: a commit that resolves something the PR body flags as pending, TBD, or decision-needed updates the body in the same turn — run `/pr-description` and land the updated body before moving on, because nothing re-reads the body for you. *Why:* `pr-description` already *checks* for stale TBD markers, but only when invoked; the missing rule is when to invoke it.

**2. `claude/.claude/rules/shell-script-conventions.md`** — new bullet after the `local`-for-function-scoped-variables bullet. Never shadow a high-blast-radius environment variable with a test-scope one: a script needing an isolated home names it `TEST_HOME`, never `HOME`, and passes it per-command to the subprocess under test rather than as a shell-wide `export`; never combine such a variable with `rm -rf`, letting the temp-directory lifecycle clean up instead; the same applies to `PWD` and to credential-path variables. *Why:* auto-loads on `**/*.sh` and `**/*.bash`, which is the incident's actual shape, at zero every-session cost.

**3. `claude/.claude/skills/branch-management/SKILL.md`** — new section `## Crossing to a different branch mid-session`, inserted between `## Anchor the session in the worktree` and `## Plan files go on the implementation branch`. Two short paragraphs: (a) when the engineer has uncommitted work in the main checkout and the next task is on another branch, add a worktree rather than `git checkout` / `git switch` / `git stash` in place — stashed work in progress is fragile and easily left unpopped, a linked worktree leaves the main checkout untouched, and stashes and refs are shared across worktrees so an earlier stash still pops from inside the new one; (b) when more than one session may be running against this repo, use a worktree even when the destination branch matches current HEAD, and state branch and PR facts from the remote (`git fetch`, then `origin/<branch>` or `gh pr view`) rather than from a local worktree snapshot that can be captured between a sibling's commit and its cleanup — unexpected `git worktree list` entries, a main-checkout HEAD you did not check out, or unfamiliar recent commits on a remote branch each signal a sibling session. *Reuse:* the section sits directly above the existing plan-files rule and reuses the `git worktree add` form already shown in the anchoring section; do not restate the `EnterWorktree` mechanics, which that section owns.

**Not changed, deliberately:**

- **The 200-line `CLAUDE.md` cap** (`check-claude-md-length.sh`'s `limit_for()`). It is this repo's own artifact and therefore in reach, but the planned additions fit inside it comfortably; raising a documented Anthropic-sourced threshold to fit a migration would be the wrong direction.
- **`require-memory-skill.sh`'s gate shape.** Phase 2 works within it by invoking the skill; the gate's Bash-tool bypass is a known, documented property and is not a hole this plan should close.
- **The global `plan-review/SKILL.md` Step 4 text.** The stow-distribution rule is claude-config-specific and cannot go in a platform-agnostic global skill; the project layer carries it.
- **`code-review`'s Step 0 domain classifier and its "Contract blast radius" bullet.** The one real specialist-dispatch gap is closed at the Change-type row that already owns the test; adding a second or third site for the same idea is the compounding-layers pattern.
- **A second plan-freshness checkpoint in `ready-for-review`.** `plan-it` Step 7's paragraph covers both the mid-execution and pre-PR checks with one remedy; a second site would be a stacked layer.
- **A `CLAUDE.md` bullet duplicating the `$HOME`-shadowing rule.** The path-scoped rule covers the incident's shape, and the inline-heredoc residual is already caught by the permission classifier that caught the original.
- **Restating `evals/README.md`'s three CI objections in `docs/design-decisions.md` §32.** The README is the holding site; §32 is an index entry pointing at it.
- **A standing regression test for the new "no memory citations in durable docs" `CLAUDE.md` bullet.** `feedback_add_test_enforcement_for_new_conventions.md` (kept, Out of scope above) says a new convention should ship with an enforcing test in the same PR, and this one is mechanically checkable — the same shape as `TestPerAccountStatePathContract`'s regex scan. Adding a permanent scanner (which durable-doc classes to cover, what counts as a false positive — a doc discussing memory-file *naming conventions* in the abstract, for instance) is new test-design work this migration's evidence doesn't cover; noted here as a follow-up rather than silently dropped. The `limit_for()` cap bump in item 6 is a different, narrower case — it extends an existing test pattern with the same shape as its neighbors, which is why it's in scope above and this broader scanner is not.

**Removing the same stale memory content from other machines and other `CLAUDE_CONFIG_DIR` accounts.** Those directories are unreachable from a git change, and each has its own independently-accrued memory set — a filename list from this machine's audit doesn't transfer. Closing that gap needs a repeatable, re-runnable audit mechanism rather than a per-migration list; this plan does not build one.

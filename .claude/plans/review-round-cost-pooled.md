# review-round-cost: `--pooled` render mode

## Context

Add a `--pooled` render mode to the `review-round-cost` subcommand
(`claude/.claude/scripts/transcript_analysis/review_rounds.py`) so that
future cost-share write-ups in `docs/cost-levers-considered.md` can cite
tool output directly instead of hand-summed arithmetic across
branches/accounts. Why now: the prior phase (PR #927, merged, commit
`7606de3c`) shipped the first cross-machine `review-round-cost` run and
produced a hand-summed, imprecise 10-15% figure in
`docs/cost-levers-considered.md` (line ~565) that this mechanism is
meant to eventually let the repo replace with real tool output (that
replacement is a later phase, out of scope here). `docs/cost-levers-considered.md`
states its other dollar-and-count figures as ratio-only phrasing, consistent
with this plan's own no-absolute-figure design choice (see row 5 and the Out
of scope section for the current state of each). Intended outcome: a
`--pooled` flag that computes and prints
cross-account pooled Cost-share and round-count figures compliant with
`docs/private-project-redaction.md`'s "Publishing a pooled tooling
measurement" section, replacing the ad hoc hand-summing.

## Approach

Add `--pooled` to `review-round-cost` as a **dedicated render path that emits percentages and nothing else** — no dollar amount, no raw count, no per-account or per-branch split — computed by summing `compute_review_round_costs`'s existing return value across its `(root_idx, branch)` keys, with a branch-cluster percentile bootstrap giving every share a 95% CI. The flag refuses every scope-narrowing flag at two layers (CLI boundary and inside the render function), suppresses the `DO NOT PUBLISH` banner that the per-round table needs, and prints an in-band pointer to the redaction doc's human approval gate. `compute_review_round_costs` itself is not touched.

The load-bearing choice is that the pooled block emits **no absolute figure of any kind**; row 5 carries that argument and its citations.

This revision closes the silent-exclusion bug class at the scan-root, project-directory, and main-transcript levels of the traversal `--pooled` reads. The dispatch-transcript level stays open (row 28). The listing and read that already happen now record each unreadable directory or transcript in an opt-in counter, and the pooled block refuses when that counter is non-empty (rows 20-27). A missing path, or one that is not the kind of object its level expects, stays an empty scope rather than a gap, as it was before this revision (rows 32, 33). Because the root-level listing now matches `--projects` against one directory name, the CLI rejects any value `Path.glob` would read as another shape, rather than let it silently select nothing (row 36). The pooled stderr filter also fails closed: an unrecognized diagnostic is withheld behind one fixed notice rather than printed (row 29).

Alternatives set aside: (a) a `--summary`-style block that also prints median `$` per round — rejected, because a permitted per-round rate composes with that already-published round count into the raw pooled total `docs/private-project-redaction.md:132-133` bars outright; (b) mirroring `cost --summary`'s single-root requirement — rejected, because the figure this exists to produce is machine-wide across every declared account (`docs/cost-levers-considered.md:552-554`), so a single-account requirement would make the feature unable to compute the thing it was asked for; (c) sharing a refusal-policy helper with `cost --summary` — rejected, because the two policies differ in the root-count direction (summary refuses multi-root, pooled requires it), so one helper would be an abstraction over two different rules. This revision's own set-aside alternatives sit in rows 21, 26, 29, 30, 32, 33, and 36.

### Cross-machine reporting

A single `--pooled` invocation can only pool the scan roots reachable
from the machine it runs on (see given G4 below); it deliberately emits
no raw dollar weights, so a correct hand-combination of two machines'
shares into one true pooled figure isn't mathematically possible from
this output alone. This design's own answer is: report each machine's
share separately (with its own CI, or as a range across machines) —
consistent with existing practice already in
`docs/cost-levers-considered.md:541-543`. G4's per-invocation
constraint means `--pooled`'s own per-machine output is correct
independent of whether a separate cross-machine merge mechanism exists
elsewhere.

### Assumption ledger

**Root problem.** Every published figure from `review-round-cost` today is hand-summed from output that prints one dated, dollar-valued row per round per branch (`review_rounds.py:550-562`), so the command is not itself an aggregation boundary in the sense `docs/private-project-redaction.md:106-109` requires, and any figure taken from it inherits the private half of the corpus's composition.

**Givens** (fixed beyond this design's reach):

- **G1.** The redaction doc's two closed lists and its human approval gate are the owner's policy, and the gate is purely a human sign-off with no programmatic component anywhere in the doc — this plan may satisfy the policy but cannot widen or automate it. `[verified: docs/private-project-redaction.md:111-169, 333-354]`
- **G2.** `compute_review_round_costs`'s round-window detection semantics and its `{"rounds", "branch_totals"}` return shape are fixed by the existing contract and its tests; `--pooled` is a consumer of that output. Changing detection is a different plan. `[verified: review_rounds.py:259-392; docs/transcript-analysis.md:1068-1074]`
- **G3.** `review_rounds.py` must not import `cost.py` — a documented module invariant, so `cost._LIST_PRICE_CAVEAT` / `_LIST_PRICE_CAVEAT_ALERT` are unavailable here and dissolving that boundary is a separate architectural decision. `[verified: review_rounds.py:14-18 module docstring; import line at :29]`
- **G4.** One invocation pools only the scan roots reachable from the machine it runs on (`scope.resolve_scan_roots` = `PROJECTS_DIR` + declared roots). Cross-*machine* pooling is outside any single command's reach. `[verified: scope.py:332-366]`
- **G5.** The transcript toolkit runs on the stdlib alone — no numpy/scipy/pandas import exists anywhere under `claude/.claude/scripts/`, so the bootstrap is hand-written. `[verified: grep for numpy|scipy|pandas under claude/.claude/scripts/ returns nothing; only `random` and `statistics` appear, at transcript-analysis.py:17,22]`
- **G6.** `Path.glob` returns no matches, rather than raising, when a directory it walks cannot be listed, and when the path it is called on is not a directory. On CPython 3.12, `_WildcardSelector._select_from` catches every `OSError` from `scandir`, and `_Selector.select_from` returns nothing when `is_dir()` is false. This is standard-library behavior the design cannot change. `[verified: /usr/lib/python3.12/pathlib.py:163-170, 199-206, 1083-1096 — the standard library of this repo's .venv interpreter, CPython 3.12.3 per its pyvenv.cfg; CI pins python-version '3.12' at .github/workflows/tests.yml:138]` Other interpreter versions are `[unverified]`. Verification's mutation check 1 re-confirms it at runtime on the interpreter under test.

The approver, not a mechanical rule, is the right layer to judge whether two dated CI citations together cross a line.

11. **Mechanism — branch-cluster percentile bootstrap, B = 2,000, fixed seed.** `anchors: row4`. Two lighter primitives were checked and fail: a **normal/Wilson analytic interval** assumes an unclustered binomial proportion and would understate the interval badly on a dollar ratio dominated by a few expensive branches; a **jackknife** is cheaper still but is known to be unreliable for ratio and non-smooth statistics, which is precisely this statistic's shape. Reusing an existing repo implementation is not an option (G5, and no resampling code exists anywhere in the repo — the `2,000-resample` citations at `docs/cost-levers-considered.md:205,368` are a different statistic, direction-of-effect on session-level rows). `[verified: grep for bootstrap/resample/percentile( across claude/.claude/scripts/ and claude-skills/ returns no statistical implementation]`

38. **Mechanism — a dominance-precision floor bounds relative weight, not only contributing-account count.** `anchors: row8`. Row 8's floor (`contributing_roots >= 2`) bounds count alone: a 99/1 split between two contributing accounts still clears it and prints a real, citable figure that functions as a near-single-account disclosure. The rule: for any computed share `P` with its own bootstrap CI `(lo, hi)` and `w_max` the dominant contributing account's own fraction of that share's denominator, solving `P = w_max·d + (1 - w_max)·r` for the dominant account's own true share `d` as the combined non-dominant share `r` ranges over `[0, 100]` gives the exact interval `[(P - (1 - w_max) * 100) / w_max, P / w_max]` (clipped to `[0, 100]`) of `d` values consistent with the observed `P`. The share is a dominance breach when that exact interval sits entirely inside `[lo, hi]`, meaning the CI pins the dominant account's own true share down to the CI's own stated precision. A breach also fires automatically, regardless of that formula, when `P` itself falls outside `[lo, hi]`. That second case is a fail-closed backstop: a percentile bootstrap over few branches can place the point estimate outside its own resampled interval, where the exact-interval containment test has no meaningful answer — without this backstop the floor would silently pass exactly the shape it exists to catch. This reuses only quantities the share already computes (its `[0,100]` range and its own CI) — no new arbitrary numeric literal. Alternatives considered and rejected:
    - A branch-count floor (e.g. requiring each account contribute at least N branches) — rejected, because it fails on 3-vs-3-branches-but-$990-vs-$10: count parity says nothing about dollar-weight parity.
    - A majority/50% rule (breach whenever any account's weight exceeds half) — stricter than the chosen floor, and considered, but not chosen: it would flag plenty of pools where the CI itself already discloses genuine mixing, which the precision-based rule correctly keeps.
    - Docs-only disclosure (the round-1 choice this fix replaces) — stating the residual in prose without a mechanical check left every lopsided pool publishable; this design closes the checkable part mechanically instead.

    Consequence of a breach: unchanged from round 3 — a breach blanks the share's own figures in `--pooled`'s default output, exactly as already shipped (`review_rounds.py:893-894`). This session considered replacing that blank with a banner printed alongside the real figures, and reverted after `/plan-review` spawned `ciso-reviewer` and `staff-sdet`: the banner made disclosure depend on a human reading six lines of text above numbers formatted identically to the publishable case, with no machine check anywhere refusing to embed a breached block downstream. See row 39 for the accepted way to let the account owner see a withheld figure without weakening the default output's own guarantee.

    Residual left below this floor, matching row 8's own kind of residual: a pool that clears this precision-based floor but is still somewhat imbalanced is accepted — the floor bounds "functionally single-account at the CI's own stated precision," not "perfectly balanced." A minimal two-branch, one-per-account pool always trips this floor for any share where the two branches differ in kind (each branch is then 100%/0% of that share, exactly the boundary this floor is designed to catch) — several hand-built test fixtures need one zero-dollar filler branch per account (two branches per account, four total) to clear it, per the uniform padding rule below (Design detail, Critical files' Dispatch 3).

    An exact 0% or 100% share always breaches at any `w_max`: its CI collapses to the point, and so does the exact interval. This is intended, since such a share pins every account. The two gap shares are excluded from the floor because they print only under `--show-withheld` (row 17).

    **Residual: a passing share's numerator can still be concentrated (false negative).** This floor bounds *sensitivity* — how far an unknown redistribution of every non-dominant account's own share of the denominator could swing the point estimate — computed from each share's own denominator weight, `w_max`. For `spend_inside`/`spend_outside`/`spend_reviewer_only` (denominator `branch_dollars`) this is also a direct bound on realized concentration: every account's activity on a branch it touches sits inside that same `branch_dollars` population, so `w_max` computed from `branch_dollars` already weighs the population the numerator is drawn from. For `skill_spend:*`/`skill_rounds:*` (denominator `round_dollars`/`round_count`) and `gap_dangling`/`gap_unpriced` (denominator `round_count`), the numerator is a further, per-account-correlated subset of that same population, and `w_max` is still computed from the shared denominator field, not from each key's own numerator distribution — so a share can clear this floor (no breach, real figure prints) while its own numerator is drawn overwhelmingly from one account (e.g. one skill's dollars coming entirely from a single account at a small fraction of pool spend, while no account dominates `round_dollars` overall). A consistent realized-concentration floor built from each key's own numerator, rather than the shared denominator, would trip on nearly every real pool, including the headline `spend_inside` line — two accounts each contributing about half of branch dollars but at very different inside/outside-round ratios would already trip it there — so `--pooled` would almost never print a real figure under that reading. Engineer-confirmed choice: bound sensitivity via the shared denominator, not realized concentration via each key's own numerator. Accepted deliberately: the residual this leaves open is a reader with independent outside knowledge of one account's activity (e.g. "I know skill X only ran on one project"); that judgment call stays with the owner at each figure's own publication-approval gate (row 8's own residual; Out of scope's note on programmatic approval). Non-pooled per-account runs already show the concentration directly to the owner. `[engineer-confirmed this session — sensitivity/shared-denominator floor chosen over a realized-concentration/per-key-numerator floor]`

**Aggregation** (confirming the briefed estimate): yes, ~10 lines. **Bootstrap.** Module constants `_BOOTSTRAP_RESAMPLES = 2000`, `_BOOTSTRAP_SEED = 0`, `_CI_LEVEL = 0.95`. Use a local `random.Random(_BOOTSTRAP_SEED)` instance, never the module-global RNG. Per resample: draw `len(per_branch)` entries with replacement (`rand.choices`), accumulate the same vector, recompute all shares from that one draw so every reported CI comes from a mutually consistent set of resamples. Percentile bounds by index on the sorted per-statistic resample distribution: `lo_idx = round(0.025 * (B - 1))`, `hi_idx = round(0.975 * (B - 1))`.

Comments the implementer must include (durable one-liners, no plan/PR narration):
- On `_BOOTSTRAP_RESAMPLES`: names the technique (percentile bootstrap, resampled over branches) and grounds the count in this repo's own prior use at `docs/cost-levers-considered.md:205`. Do not invent a textbook page or section number.
- On `_BOOTSTRAP_SEED`: fixed so a published figure is reproducible by whoever checks it; the value itself is arbitrary.
- On the resampling unit: the branch is the cluster because every reported statistic is a ratio of two branch-level sums.

Degenerate cases: fewer than four branches in scope, fewer than two contributing roots (`review_rounds.py:761-767`), or a zero denominator, print `(95% CI not computed — too few branches in scope)` / `(95% CI not computed — no priced branch spend)`. Neither wording may contain a digit (see the enforcing test below).

**Bootstrap-validity floor raised to four branches.** `too_few_for_bootstrap` requires `len(per_branch) >= 4`, not `>= 2` as originally shipped in round 1. At `len(per_branch) == 2`, `rand.choices(per_branch, k=2)` with replacement has only 3 distinct outcomes ({A,A}, {A,B}/{B,A}, {B,B}) regardless of `_BOOTSTRAP_RESAMPLES`, so the percentile-index formula (`_resample_percentile`) draws its 2.5th/97.5th bounds from a resample distribution with essentially 3 support points — a CI width and shape that reflects the resampling arithmetic's own coarseness, not real branch-to-branch variation. Four branches give `4^4 = 256` distinct ordered draws, enough for the percentile indices to land on a resample distribution shaped by the data rather than by the small-sample combinatorics.

    Three hand-built test fixtures — the extreme-split and moderate-balanced-split dominance tests and their mutation guard (Critical files, Dispatch 3) — pad from two branches to four total: one zero-dollar, zero-round filler branch added per account (two branches per account, four total), never a second real branch. `_pooled_dominance_breach` computes a separate `w_max` per stat key from whichever of three denominator fields `_POOLED_SHARE_DENOMINATOR_FIELD` names for that key — `branch_dollars` for the spend shares, `round_dollars` for `skill_spend:*`, and `round_count` for `skill_rounds:*`/`gap_dangling`/`gap_unpriced` (`review_rounds.py:574-582`) — and returns `True` on the first key that breaches, so every denominator field's own `w_max` is load-bearing to these tests' outcomes, not only `branch_dollars`'s. A zero-`branch_dollars`, zero-round filler leaves `branch_dollars`'s own `w_max` exactly unchanged (`_render_pooled_block:844-849, 873-875`) — 99/1 and 60/40 respectively, which is what each test's stubbed CI half-width (5 and 20 points) is built to test against. The other two fields stay safe here for a narrower reason specific to these three fixtures: each already has exactly one round per account before padding, so adding exactly one filler round per account preserves `round_count`'s 1:1 ratio as 2:2, and each filler round's `main_dollars=agent_dollars=0.0` leaves `round_dollars` untouched in absolute terms — not a general consequence of "keep `branch_dollars` at 0.0" alone. A future fixture that starts from an unequal round count per account, or that pads unevenly, must re-check `round_dollars` and `round_count` parity independently rather than assume the zero-`branch_dollars` property alone preserves them. A filler branch with any nonzero dollar value would risk silently moving `w_max` across the boundary each test exists to pin, with no test failure to flag it.

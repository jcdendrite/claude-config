# Re-ground the inline-check-run rule and give diagnosis-delegation a canonical home

## Context

`claude/.claude/skills/subagent-delegation/SKILL.md` § "Heavy command output — run inline" tells the parent session to run check suites (test, lint, typecheck, build) inline rather than delegating them, and justifies it with a bare, undated literal: "Bash output truncates at 30 KB — well above typical check-suite size — so an inline heavy run costs the parent only the ~2 KB failure tail." A contributor reading this in live use flagged it as possibly stale and possibly inconsistent with other skills that dispatch `/root-cause-analysis` to a subagent on failure. Investigation confirmed four real defects:

1. The harness figure is factually wrong for the current Claude Code version — 30,000 bytes, not 30,720.
2. The same paragraph contradicts its own section's overflow bullet on whether the preview is the head or the tail.
3. The figure sits undated in a runtime-loaded skill body, against this repo's own stated placement principle.
4. A second rule — "delegate the failure diagnosis" — is stated at two different scopes in two skills, with no canonical home and no cross-reference.

The intended outcome is four matching deliverables:

1. A re-grounded, correctly-cited inline-run rule.
2. A canonical home for the diagnosis-delegation rule that names why its two variants differ.
3. A test that keeps section cross-references from going stale again.
4. The measurement procedure preserved as a repeatable skill rather than a one-off session artifact.

## Approach

Fix the inline-check-run rule in three separable moves, then ship the measurement procedure itself as a stowed skill so the re-grounding is repeatable rather than a one-off. The three moves: replace the wrong `30 KB`/`~2 KB` figures in `subagent-delegation/SKILL.md` with a version-dated, as-of measurement relocated into that skill's co-located `REFERENCES.md`; give the "delegate the failure diagnosis" rule a canonical sub-section in `subagent-delegation/SKILL.md` with `ready-for-review`'s whole-skill dispatch documented there as a named variant; and add one mechanical pytest that resolves every `` `target` § "Heading" `` citation in the skill tree to a real heading. The fourth deliverable is a new name-only skill, `measure-check-output`, carrying the two-half procedure this plan performs by hand — **Half 1** re-probes the harness's own output limits, and **Half 2** measures a project's documented check commands against the threshold Half 1 established. Dated historical records in `docs/` are corrected by a dated addendum, never in place.

Six findings from reading the current text shape the design beyond the four defects named in Context above.

**The skill body contradicts itself today.** `subagent-delegation/SKILL.md:72-74` says an inline heavy run "costs the parent only the ~2 KB failure tail … with no follow-up read needed," while `:87-89` says the harness returns "the *first* 2 KB, usually the startup banner — grep/sed the persisted file for what you need." The 2026-09-02 harness re-probe (row 4) confirms `:87-89` is right and `:72-74` is wrong on both counts (head, not tail; a follow-up read *is* needed on overflow). Correcting the number without correcting this leaves the more actionable defect in place, so the rewrite replaces the whole justification paragraph rather than patching the literal.

**The measurement grounds the pass path, but the rule's claim is about the failure path.** The 2026-09-02 pass-path measurement covered four green runs (9,429 bytes max, 31% of threshold). The rule's load-bearing sentence is about what an inline run costs *when a check fails* — the case that measurement explicitly did not cover. Dispatch 1 therefore includes a bounded failure-path measurement before the number is written down (recipe in Critical files), because writing a re-grounded rule on a pass-path-only figure repeats the original defect at a smaller scale.

**Figures are recorded as-of, not re-measured at the end.** Every figure this PR writes carries three qualifiers: the byte count, the suite size it ran against, and the date plus Claude Code version — e.g. "9,429 bytes at 7573 passed / 54 skipped, 2026-09-02, Claude Code 2.1.259." No re-measurement pass runs at the end of implementation, and no figure is dropped for fear of staleness. This is what makes the observe-then-mutate ordering safe: Dispatch 1's Step 0 measures the failure path before any file is edited, and simply records the suite size it ran against, so a later diff that changes the suite size does not silently invalidate the figure — it dates it.

**Canonical home for the figure: `subagent-delegation/REFERENCES.md`, on co-location — and both homes are defensible.** `docs/design-decisions.md` §22 put a dated ratio in `docs/` because "a dated, drifting ratio has no staleness gate to keep it honest in an auto-triggering skill body." §22 weighed `docs/` against `SKILL.md` and never considered the third option. `REFERENCES.md` satisfies §22's actual concern — it is never loaded at skill runtime, so a stale figure there cannot reach an auto-triggered session. That makes `REFERENCES.md` and `docs/` *equally* admissible under §22's own reasoning; the tiebreak is co-location with the only rule that consumes the figure, so an editor revising that rule finds it in the same directory rather than three levels away. It is a tiebreak, not a disqualifier, and the commit message says exactly that. `docs/` is fully reachable for a stow consumer: `install.sh:275` runs `stow -v … -t "$HOME" claude` from the clone it was invoked in, so every consumer has `docs/` on disk, and nine stowed skill bodies already cite bare `docs/*.md` paths (`code-review/SKILL.md:318`, `handoff/SKILL.md:37,189`, `ready-for-review/SKILL.md:68`, `plan-it/SKILL.md:137`, `git-feature-branch-sync/SKILL.md:27`, `transcript-analysis/SKILL.md:82,98`, `error-mode-analysis/SKILL.md:16`, plus `plan-review` and `agent-review`). A `docs/` pointer from a skill body is this repo's normal practice, not a dead pointer.

**The repeatable procedure is a stowed skill, not a `docs/` runbook.** The deliverable is `claude/.claude/skills/measure-check-output/SKILL.md`, name-only, no TRIGGER blocks. The decisive property is not reach — reach is a wash, per the paragraph above — it is *routing under the conditions the procedure actually runs in*. Half 2 (measure a project's own check commands against the threshold) executes from inside an arbitrary consuming project, where nothing would surface a claude-config `docs/` file; a skill sits in `~/.claude/skills/` in every session on the machine and is invocable by name from any repo. A runbook cited from `subagent-delegation/REFERENCES.md` routes only at edit time inside claude-config, which is precisely when half 2 is *not* what anyone is doing. No TRIGGER blocks, for two reasons: on v2.1.129+ a name-only description is excluded from the listing budget, so TRIGGER text there is permanent cost with zero routing value — the same rationale `docs/skills.md:55` records for `skill-review`; and on pre-v2.1.129 clients name-only degrades to `on`, where a TRIGGER block matching check-suite context would collide head-on with `subagent-delegation`'s own auto-trigger surface. Voice and structure follow `claude/.claude/skills/transcript-analysis/SKILL.md` — the closest existing body, a name-only measurement-toolkit skill whose "Scope confirmation" section (`:18-24`) requires quoting the resolved-scope header verbatim before reporting any statistic. That is the exact pattern the as-of block needs. `transcript-analysis` does carry TRIGGER blocks; the model is for prose and section shape, not frontmatter.

**`docs/skills.md:37`'s no-TRIGGER count is already wrong by one.** It reads "Nine skills carry no TRIGGER blocks: eight workflow utilities and one debugging playbook; the three knowledge-domain skills and one dispatcher-reached reviewer skill carry TRIGGER blocks." Grepping `TRIGGER` across `claude/.claude/skills/**/SKILL.md` returns five of the thirteen name-only skills — `transcript-analysis`, `error-handling`, `test-conventions`, `sql-query-conventions`, `agent-review` — so the true split today is eight/five, not nine/four. `transcript-analysis` is on the wrong side: `transcript-analysis/SKILL.md:7-13` carries both `TRIGGER when:` and `DO NOT TRIGGER when:`. Adding `measure-check-output` as a no-TRIGGER workflow utility makes the sentence's *numbers* correct as written (nine no-TRIGGER = eight workflow utilities + one playbook; five with TRIGGER; fourteen total), so the numeric edit at that clause is **no change** — but the trailing clause must gain `transcript-analysis`, or it accounts for only four of five. This is in scope rather than incidental: the plan edits that same sentence, and leaving it self-contradictory while changing "Thirteen" to "Fourteen" would ship a knowingly wrong count. Name it in the PR body so a reviewer is not surprised by a correction the ticket did not ask for.

**Cross-reference test grammar, fully specified.** The regex is `` `(?P<target>[^`\n]+)`\s+§\s+"(?P<heading>[^"\n]+)" `` over prose, requiring the backticked target to be *adjacent* to the `§` with only whitespace (which may include one newline, so hard-wrapped prose still matches) between them. A `§ "…"` with no adjacent backticked target resolves against the citing file's own headings. Target resolution, in order: (1) a repo-root-relative path that exists (`docs/case-studies/check-runner.md`, `CLAUDE.md`); (2) `<skill-dir>/<file>` under any of `_all_skill_md_files()`'s three roots (`subagent-delegation/SKILL.md`); (3) a bare filename with no `/`, as a same-directory sibling of the citing file. Unresolvable target ⇒ failure naming citing `file:line` and the target. Comparison normalizes both sides identically — strip leading/trailing `#`, strip `` ` ``, `*`, `_`, collapse whitespace runs, strip ends — then exact equality, so `### Debug-investigation probe → \`general-purpose\` or \`Explore\`` is citable without backticks in the quoted text.

Scanned corpus: every `SKILL.md` from `_all_skill_md_files()`, plus every `REFERENCES.md` and `ROUTING.md` sibling in those same skill directories. Widening the scanned corpus past `SKILL.md` files alone is necessary, not scope creep: the one stale citation this PR fixes lives in `review-permissions/REFERENCES.md:53-54`, and a `SKILL.md`-only scan would leave the actual defect unguarded. `REFERENCES.md` and `plan-review/ROUTING.md` are the two co-located auxiliary files `.claude/rules/skill-and-agent-self-review.md` already names, so the widened corpus is closed, not open-ended.

**Reuse trap.** The test must reuse `_blank_frontmatter` and `_closed_fence_line_indices` but must **not** call `_blank_code_regions` — that helper blanks inline code spans, and this test's target token *is* an inline code span. Blanking them would silently reduce every citation to the same-file branch and pass vacuously.

**Alternatives set aside.** A repo-wide markdown link checker was rejected: it validates `[]()` links, and none of these citations are links. A `grep`-based CI assertion was rejected: it can find the `§` occurrences but cannot resolve a target path to a file and compare normalized heading text, so it degrades to a spelling check. Extending `validate_skill_structure.py` (the commit-time gate) was rejected on the same reasoning `test_skill_bodies_carry_no_citation_urls` records at `test_skills.py:2098-2104` — that validator ships to downstream repos inside the `skill-management` plugin, so a claude-config-internal citation convention there would be imposed on every plugin consumer.

**Root problem:** `subagent-delegation/SKILL.md`'s inline-check-run rule is justified by a wrong, undated harness figure that also contradicts the same section's own overflow bullet; the paired "delegate the failure diagnosis" rule exists at two scopes in two skills with no canonical home, no cross-reference, and no test keeping either honest; and the measurement that would re-ground the figure exists only as an ad hoc session procedure that nothing preserves.

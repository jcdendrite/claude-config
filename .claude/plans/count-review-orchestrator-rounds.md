# Count review-orchestrator rounds in transcript analysis

## Context

Goal: the transcript analyses (`review-round-cost`, `cost-counts`, `author-outcome`) count and price a `/code-review` round that runs inside the `review-orchestrator` agent merged in PR #714, and a latent flat-layout pricing bug is fixed on the way.

Ask: "I do think the config key follow up is worth doing as well as the transcript analysis fix" (the config key is a separate, later plan). Scope was widened in this session by two answers: "Include it (Recommended)" to fixing the flat-layout pricing bug, and "I think fix author outcome too. Ask the architect". The option descriptions behind those labels were the session's. Fable's suggestion to do the cheap half first is a model's read, not the engineer's.

Why now: the agent runs a round in a sidechain, and its dispatch is an `Agent` tool call, not a `Skill` tool call. These analyses read main-thread records only, so no round window opens and the agent's spend lands in the non-round remainder. The post-merge dogfood of the agent should be auditable in these tools. While checking, the nested-dispatch pricing was found to look for a directory layout the harness never writes.

Intended outcome: an orchestrator dispatch opens one `code-review` round, its reviewers and `code-writer` dispatches are priced into it, and `author-outcome` classifies it. `reviewer-yield`, `review-trace` and `cost-counts` get documentation changes only.

## Approach

Ship one PR with two ordered commits and three sequential `code-writer` dispatches.

1. Commit 1 (dispatch 1): price nested dispatches from the session's one flat dispatch index.
2. Commit 2 (dispatches 2a, then 2b; one `/code-review`; one commit): make a main-thread `review-orchestrator` dispatch a `code-review` round for every `detect_round_windows` consumer. 2a opens the round and excludes it from the review-bench miner. 2b teaches author-outcome to classify it. It is one commit because `author_outcome._code_review_rounds` and `mine_review_rounds._collect_round_entries` change the moment the round opens.

Commit 1 passes `/code-review` and lands before dispatch 2a starts.

reviewer-yield, review-trace and cost-counts get documentation or docstring changes only.

**Commit 1: flat-layout pricing.** In `review_rounds._price_dispatch`, delete the `nested_index` lookup at :215 and recurse with the `dispatch_index` the caller passed in. Keep `visited`. A single shared index makes a self-referencing dispatch reachable for the first time, and `visited` is what stops that cycle. Rationale: the harness writes depth-2 `.meta.json` files into the session's own flat `subagents/` directory (row1, row2), so the session index already holds every nested dispatch.

Alternatives set aside:
- A `parentAgentId` walk. It reads a field nothing else needs, and the `toolUseId` join already resolves each dispatch.
- Keeping the nested-layout lookup as a fallback. No such directory exists on the roots checked (row1). On a hypothetical nested corpus, those dispatches would go back to dangling, which is the same result as today on the real layout.

**Commit 2, round-open part (dispatch 2a): round-open on the orchestrator dispatch.**
- Add a private `_ROUND_OPEN_AGENT_SKILLS: dict[str, str] = {"review-orchestrator": "code-review"}` with the one-line comment `# Agent types whose main-thread dispatch runs a review skill in the agent's own transcript, mapped to that skill.`
- Add a public `spawn_round_skill(block: dict) -> str | None`. It returns the mapped skill for a `tool_use` block whose `name` is in `pricing._SPAWN_TOOL_NAMES` and whose `input["subagent_type"]`, normalized through `_round_skill_name`, is a mapping key. Otherwise it returns None, including for a `block` that is not a dict, an `input` that is not a dict or a `subagent_type` that is not a str. The non-dict-block guard lives in the helper, so its three callers (`_round_open_skill`, the miner skip, `_orchestrator_spawns`) need none of their own and a stray non-object in a content list cannot abort a scan (corpus.py's decode policy).
- `_round_open_skill`'s assistant branch checks per record, not per block: every block is tried against the existing `Skill` shape first, and only when no block of the record opens a round does it try `spawn_round_skill` on each block in order. A record holding a `Skill` `plan-review` block and an orchestrator spawn therefore opens `plan-review`. A record opens at most one round, so a record holding two orchestrator spawns opens one `code-review` round. The `isSidechain` guard stays, so an orchestrator dispatched from inside another subagent never opens a round.
- Extend the OUTPUT INVARIANT docstring with two sentences: `From an Agent/Task tool_use block only input["subagent_type"] is extracted.` and `input["prompt"] and input["description"] carry free text and must never be extracted or surfaced here.`

- `mine_review_rounds._collect_round_entries` skips any window whose open record carries a `spawn_round_skill` block, and its docstring gains one line saying so. The skipped window is still a round-open, so it still closes the preceding kept window: that narrows the earlier round's `_round_scope` reads and moves `_main_thread_edited_between`'s start, as a `plan-review` or `ready-for-review` window already does. The docstring line says this too and no code changes for it. The docstring line makes no parity claim with the deduped consumers: the miner calls `detect_round_windows` on undeduped records (mine_review_rounds.py:172-174).

These parts stay unchanged: windowing, branch attribution, closing rules and the pricing loop.
- The window starts at the dispatch record. The loop at :349-365 therefore prices the orchestrator dispatch into the round, plus its reviewers and `code-writer` once commit 1 is in.
- When the orchestrator's return is a `tool_result` record, the parent's turns after it stay in the window until the next fresh prompt or the next round-open (row11). When the return is delivered as a task-notification user record (row 9), `_is_fresh_user_prompt` (render.py:35-59) filters non-user, sidechain, isMeta, compaction-summary, `tool_result` and empty-text records, so the notification reads as a fresh prompt and ends the window. That is the existing behavior for any background dispatch and is not fixed here.
- No double-count guard is needed. The orchestrator's own `Skill` call lives in its own transcript, which no main-thread detector reads (row4).
- `review-round-cost` and `cost-counts` count a main-thread orchestrator dispatch as a round whether or not it invoked a review skill, because neither consults a subagent transcript to decide whether a round exists (review-round-cost opens dispatch transcripts only to price them, review_rounds.py:211).
  - An orchestrator that halts at review-orchestrator.md item 3 (`Skill` or `Agent` not held) invokes no skill. It is still a round in all three subcommands, so the cost-counts caption "Each invocation of a review skill is one round" over-counts by the number of such dispatches. It appends no ledger block, so in `author-outcome` it is a round-open with no block. That makes its session a round-number mismatch only when the session also holds another round-keyed ledger block. With zero round-keyed blocks the session is not evaluated, the round reads UNATTRIBUTED (unless the session is flagged possibly swept) and the mismatch counter does not move (see dispatch 2b's "No drop rule" bullet). The docs edits state this.
  - An orchestrator that halts after its first ledger append counts as one round in all three, and is not a mismatch.
  - A halt followed by an inline `/code-review` counts as two rounds in all three subcommands, and is the designed path after a round-ending `HALT:`. In `author-outcome` the session is a round-number mismatch when the inline round appended a block and the halted round appended none.

Normalizing through `_round_skill_name` rather than matching the exact string is deliberate. The recorded spelling is unverified (row8), and a missed round would be silent. The only false positive would be a plugin agent with the same name.

Alternatives set aside:
- Detecting the orchestrator's own `Skill` call by merging subagent transcripts. That breaks the main-thread record indices every window and branch computation relies on, and it reopens the double-count the main-thread-only rule exists to prevent.
- Having the orchestrator write a main-thread breadcrumb. That adds a runtime write to solve an analysis problem, and it changes the merged agent (G2).

**Commit 2, author-outcome part (dispatch 2b).** All helpers live in `author_outcome.py`. They have one consumer, so they don't move to a shared module until reviewer-yield's follow-up becomes the second.
- `_OrchestratorSpawn(NamedTuple)` retains derived facts only, never raw transcript records, because an orchestrator transcript carries the dispatch prompt, the reviewed diff and reviewer findings that no later edit should be able to surface. It holds four fields:
  - `spawn_idx`: the main-thread record index of the spawn.
  - `has_clean_marker_write`: whether `_records_have_clean_marker_write` is true over the orchestrator's deduped transcript records.
  - `nested_dispatches`: `(tool_use_id, start_ts, completion_idx)` triples for the transcript's dispatches of the `--agent` type. `start_ts` is the parsed timestamp of the nested dispatch's own tool_use record. `completion_idx` is `spawn_idx` when the nested dispatch has a paired `tool_result` in the transcript, else `None`.
  - `readable`: False when the transcript is dangling, unreadable, or readable with no parseable line (`corpus._parse_jsonl_records` returns `None` for unreadable and `[]` for an empty or all-malformed file; `_orchestrator_spawns` treats both as not readable, so the field cannot tell the three apart).

  The transcript records are parsed, deduped, scanned and dropped inside `_orchestrator_spawns`, one transcript at a time.
- `_orchestrator_spawns(jsonl, records, code_review_rounds, agent_type, data_quality)` collects these spawns. It applies two independent conditions: the block predicate `review_rounds.spawn_round_skill(block) == _CODE_REVIEW_SKILL`, and the round-open gate, which admits only a record whose index is a round-open `open_idx` in `code_review_rounds` (the list `_code_review_rounds` already returns). It has no `isSidechain` check of its own: `_round_open_skill` never opens a round on a sidechain record, so the gate is the sole sidechain filter. The gate is the same record-level predicate as 2a's round-open, so the two paths cannot disagree: a record that opened `plan-review` through its `Skill` block and also holds an orchestrator spawn yields no `_OrchestratorSpawn`, its transcript is never scanned into the preceding round's marker span, and its nested dispatches attribute to nothing. A record holding both a `Skill` `code-review` block and an orchestrator spawn opens `code-review`, so its spawn is collected. It builds `corpus._index_subagent_dispatches(jsonl)` at most once per session, and only when at least one such spawn exists. Two spawns in one record yield two `_OrchestratorSpawn` entries that share one `spawn_idx`.
- Marker fallback:
  - Extract the inner scan of `_round_has_marker_write` into `_records_have_clean_marker_write(records)`, which applies no sidechain filter.
  - `_round_has_marker_write` keeps its main-thread `isSidechain` filter for that slice.
  - It also reads `has_clean_marker_write` of every orchestrator spawn whose `spawn_idx` falls in `[open_idx, span_end)`. The new parameter is optional (default: no spawns), so the existing three-positional-argument calls at test_author_outcome.py:112 and :119 keep working unchanged.
  - The marker-write signal is "attempted, not confirmed": a `marker.sh write code-review` tool_use counts whether or not its paired `tool_result` is an error, on the inline path today and on the orchestrator path. Requiring a present non-error paired result on the orchestrator path alone would make the two paths disagree, and requiring it on both would change the inline path's existing numbers for every stow consumer, so neither is done here. A failed or denied marker write (review-orchestrator.md item 8 anticipates one) therefore reads as PASS in a ledger-less session. That is a documented false-PASS residual, pinned by a characterization test in 2b and stated in docs/transcript-analysis.md. The impact is analytics integrity only: it can inflate the PASS share and carries no privilege change.
- Nested dispatches:
  - Add a keyword-only `skip_sidechain: bool = True` to `_agent_dispatch_tool_use_ids` and `_build_tool_result_index_map`.
  - `_orchestrator_spawns` calls both with `False` on the orchestrator's records, because every record in that file is a sidechain record.
  - A nested dispatch's start timestamp is its own tool_use record's timestamp.
  - A nested dispatch's completion index is its orchestrator's spawn index, so it attributes to the first round-open after the orchestrator's round. review-orchestrator.md items 1 and 7 make that the round that reviews the fix.
  - A nested dispatch with no paired `tool_result` in the orchestrator transcript has completion index `None` and is UNDECIDABLE, as on the main thread. An ack satisfies that check on both paths (row 23).
  - Residuals, both the same launch-position limitation as the main thread (row 23):
    - A main-thread round that opens while the orchestrator is still running gets credited with its fix.
    - The orchestrator can return while a nested `code-writer` is still in flight. The nested `tool_result` is the launch ack, so the UNDECIDABLE check passes, and the fix lands after the next round opens, which is credited with it.
- `compute_author_outcomes` builds one list of `(tool_use_id, start_ts, completion_idx)` triples from the main-thread path (its own start timestamp and result lookup) and from each `_OrchestratorSpawn.nested_dispatches`. Apart from reading those three values, the loop body stays the same.
- No drop rule. Every main-thread orchestrator spawn stays in author-outcome's round-open set, so all three subcommands count the same rounds. A spawn whose round ends before its first ledger append (item 3, or a round-ending item 8 `HALT:` before dispositions are finalized, code-review/SKILL.md:401) is a round-open with no block, exactly as an inline round that halts before its append already is. What follows depends on the session:
  - The session also holds another round-keyed ledger block: the block count is short of the round-open count, so the session is a round-number mismatch (author_outcome.py:596-598), counts under the existing mismatch key, leaves its rounds unclassified and excludes its dispatches from the headline.
  - The session holds zero round-keyed blocks: `_round_number_mismatch` returns False (:402-403, row 12), the halted round has no block and no marker, so `_classify_round` returns UNATTRIBUTED (:484) and the mismatch counter does not move. This holds unless the session is flagged possibly swept: `_ledger_possibly_swept` (:440-449) returns True for a session with a round-open, no ledger rows attributed to it, no opened session-keyed ledger file and an earliest round-open older than the 30-day floor, and its dispatches then leave the headline under that counter.
  - The orchestrator halts after its first ledger append (a finding-level stop-and-ask ends only that finding's handling, item 8): one block exists, so there is no mismatch.
- `readable` False counts under `_DQ_ORCHESTRATOR_TRANSCRIPT_UNREADABLE`.
- Add one key to `_DATA_QUALITY_KEYS` (:78), appended last, after `_DQ_SETTLED_PASS_ROUNDS`: `orchestrator dispatches with no readable transcript records`. The print loop (:751-753) already iterates the tuple in order, so only the tuple changes. The counter is:
  - per spawn, counted once per spawn even when two spawns share a record;
  - corpus-wide, not `--since`-filtered, like the malformed-dispatch-id counter (docs :1405);
  - transcript-side, so a round-number-mismatched session still counts it.
  - A non-zero value explains an inflated "authoring_agent inconsistent" count: an unreadable orchestrator's nested `code-writer` vanishes and `transcript_side` reads `inline`.

Intended consequences, when every orchestrator round appends a block:
- Orchestrator-only sessions, and mixed sessions where the parent re-syncs its round count, stop counting as round-number mismatches (row13). A mixed session whose parent keeps a stale in-memory count can still mismatch (row 7). A round-ending `HALT:` before the append introduces a mismatch when the session holds another round-keyed block (an inline round plus a halted orchestrator is not a mismatch today: one round-open, one block), and keeps one only where another orchestrator block already made the session a mismatch (see "No drop rule").
- A main-thread `code-writer` dispatch that used to be attributed to a later inline round is now attributed to the orchestrator round in between, which is the round that judged it. If that round halted before judging, the dispatch attributes to a round that judged nothing: in a session with no ledger rows it reads UNATTRIBUTED (unless the session is flagged possibly swept) where the later inline round's marker used to make it PASS.
- The `authoring_agent` cross-check sees the orchestrator's `code-writer` dispatches.

Four further shifts follow from the same change and are not intended gains, so the post-commit read-only run (Verification) expects them:
- A dispatch with no later inline round used to be UNRESOLVED and now classifies through the orchestrator round.
- A session that leaves the mismatch exclusion adds its dispatches to the headline outcomes.
- A session with a halted orchestrator round plus any other round-keyed block newly counts under the mismatch key and drops its dispatches from the headline.
- An orchestrator-only session older than the 30-day floor and holding no surviving ledger rows (never appended, or appended and since swept) used to have no round-open, so `_ledger_possibly_swept` returned False (:440-441). It now has one, so its dispatches leave the headline under the swept counter. A large rise here can come from ordinary old orchestrator sessions whose rows were evicted, not only from halts before the append.

Alternatives set aside:
- `include_subagents=True`. It flattens files and breaks the main-thread indices that all of author-outcome's ordering compares.
- Reading the orchestrator's `Marker:` return line. That line is model-written prose, not the hook-guaranteed shape `_is_clean_marker_write` relies on (:101-105), and it carries no nested dispatch ids.
- Projecting nested dispatches for any depth-1 parent. See Out of scope.

## Critical files

There are three `code-writer` dispatches (1, 2a, 2b), run in sequence and never in parallel. Dispatches 1 and 2a both edit `review_rounds.py` and its test file. Dispatch 2b uses dispatch 2a's `spawn_round_skill`, its `_write_subagent_dispatch` import and its single orchestrator-transcript builder. Dispatches 2a and 2b share one commit and one `/code-review`. Each docs or docstring edit sits in the dispatch whose change makes it false.

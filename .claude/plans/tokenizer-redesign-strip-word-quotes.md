# Tokenizer-based redesign of `_lib_strip_word_quotes`

## Context

`_lib.sh`'s fragment-scanning security gate does not decode bash's ANSI-C
(`$'...'`) multi-character escapes before matching fragment words against
dangerous-flag denylists, which is a confirmed, currently-open bypass:
`docs/design-decisions.md` §40 documents `$'--tex\x74conv'` reaching
`--textconv` (arbitrary command execution via git's `--textconv`/`--ext-diff`),
a NUL-embedded escape bypassing `git grep --no-index` (arbitrary filesystem
read), and a write-target flag bypass via `--output=` (arbitrary-path write).
Four regression tests already pin this gap by asserting `== "allow"`:
`test_require_review_orchestrator_bash.py`'s
`test_git_log_textconv_ansi_c_hex_escape_bypass_allowed` /
`_octal_escape_bypass_allowed`, and their twins in
`test_deny_reviewer_tree_mutation.py`. §40 accepted the gap "pending a
tokenizer-based redesign of the fragment-scanning approach... rather than
patched incrementally in this function again" — this plan is that redesign.

Exploration for this plan surfaced a second, sibling gap in the same
territory: `_lib_fragment_invokes_git` does no quote-stripping at all, not
even the single-character stripping `_lib_strip_word_quotes` already does.
A boundary-quoted `'git'` or `$'git'` word therefore evades git-detection in
4 hooks: `deny-pii-in-commits.sh`, `deny-private-project-refs.sh`,
`deny-reviewer-tree-mutation.sh`, and `require-ready-for-review.sh`. PR
#714's own body DEFERred this as high-severity, and no existing regression
test covers it.
`deny-reviewer-tree-mutation.sh` is affected by both gaps at the same call
site (`_lib_fragment_invokes_git` gates whether its flag checks even run),
and per the engineer's decision, this plan closes both gaps
together rather than leaving one open in the same PR. The engineer also
confirmed `${var:-flag}` parameter-expansion default resolution (also named
in §40's residual) is in scope, narrowed to the `:-` (use-default-if-unset-
or-empty) operator only.

Intended outcome: a shared word-decoding primitive in `_lib.sh` that fully
decodes bash's `$'...'` ANSI-C escape grammar and resolves `${var:-default}`
before quote-stripping, used by both `_lib_strip_word_quotes` and
`_lib_fragment_invokes_git`'s word-matching, with all four existing
regression tests flipped from `"allow"` to `"deny"` and new coverage added
for the `_lib_fragment_invokes_git` boundary-quote gap across its 4 call
sites.

## Approach

Add one bounded, non-executing **word decoder** to `_lib.sh` that resolves the two bash constructs the current scan is blind to — `$'...'` ANSI-C escape sequences and `${NAME:-DEFAULT}` parameter defaults — and run every existing word-level security comparison through it. `_lib_strip_word_quotes` keeps its name, arity, and `_LIB_STRIPPED_WORD` global and simply gains a decode pass ahead of its existing character removal, so all five of its call sites are fixed without touching their shape. The quote-blind `[[ "$word" == "git" || "$word" == */git ]]` test, which appears verbatim in four places, is replaced by a shared `_lib_word_is_git` helper built on that same decode-then-strip pipeline.

This is deliberately **not** the "tokenizer" §40's residual paragraph names. A real tokenizer would have to own quote-aware *fragment splitting* too (`_lib_split_fragments`), which is a separate layer with a much wider blast radius; and `docs/security-hardening.md:724-728` already forecloses the only exhaustive tokenizer (running the text through bash). What actually closes the three confirmed exploits is decoding, applied to already-split words. Scope follows the bug.

### Assumption ledger

**Root threat.** `_lib.sh`'s word-level security comparisons match a fragment word against dangerous-flag denylists and against the literal `git` using only single-character quote/backslash removal, so an attacker-authored command reaching a restricted agent's Bash tool can spell `--textconv`, `--no-index`, `--output=`, or the `git` command word in a form the scan misses but bash reassembles at exec time — yielding arbitrary command execution, arbitrary filesystem read, and arbitrary-path write against every agent these hooks restrict.

**Givens**

- **G1 — the hook may never execute the untrusted command text to canonicalize it.** The same string can carry `$(...)`/backtick command substitution, so canonicalizing via bash would execute attacker-controlled code inside a security hook. `[verified: docs/security-hardening.md:724-728]`
- **G2 — shipped `.sh` under `claude/.claude/` must run on macOS bash 3.2.57.** Enforced repo-wide, so no `[[ -v ]]`, no nameref, no `declare -A`, no `mapfile`, no `${var^^}`. `[verified: claude/.claude/scripts/tests/test_no_bash4_constructs.py:1-14]`
- **G3 — the harness hands hooks the raw command text, not a parsed argv.** Nothing upstream of `_lib_split_fragments` normalizes quoting; the hook family's entire detection surface is static text matching. `[verified: docs/security-hardening.md:701-713]`
- **G4 — `_lib_fragment_invokes_git`'s scope for this plan is both gaps, and parameter-expansion support is the `:-` operator only, resolved by env lookup.** `[engineer-verified]`

**Ledger**

1. **A bounded `$'...'` decoder, not a general shell parser.** Decoding only bash's documented ANSI-C escape grammar inside already-identified `$'...'` spans is the smallest mechanism that turns `$'--tex\x74conv'` into `--textconv`, and it never touches text outside those spans, so it cannot execute anything. `anchors: root` `[verified: docs/security-hardening.md:714-739 rules out the two heavier alternatives]`

2. **Lighter primitives considered and rejected (over-powered-primitive check for row 1).** Four exist in the source system; none works:
   - `printf '%b' "$whole_word"` in one builtin call — rejected on two counts. `%b`'s grammar diverges from `$'...'` (`\0nnn` vs `\nnn` for octal; `\c` means *terminate output* in `%b` but *control-character* in `$'...'`), and applying it outside `$'...'` spans **regresses an existing catch**: today `--text\conv` strips to `--textconv` and denies, whereas `%b` would read `\co` as Ctrl-O and produce a non-matching word. This is the concrete reason the decoder must track spans. `anchors: row1` `[verified: claude/.claude/hooks/tests/test_lib.py:877-880 pins the backslash-splice catch]`
   - `bash -c`/`eval` canonicalization — rejected by G1. `anchors: row1` `[verified: docs/security-hardening.md:724-728]`
   - An external tokenizer (Python `shlex.split`, or the existing `parse-git-command.py`) — rejected twice over: it adds a subprocess to a per-word hot path, and `shlex` treats `$` as an ordinary character, so it decodes no ANSI-C escape at all and closes nothing. `anchors: row1` `[unverified: shlex behavior asserted from its documented POSIX mode, not empirically run]`
   - More `${word//…}` substitutions inside `_lib_strip_word_quotes` — rejected by §40 itself ("rather than patched incrementally in this function again"), and structurally impossible: a `\xHH` → byte conversion is a value-to-character map, which pattern substitution cannot express. `anchors: row1` `[verified: docs/design-decisions.md:606]`

3. **`printf -v ch '%b' "\\x$hh"` as the per-escape code-point materializer.** This *is* the lighter primitive relative to a hand-rolled hex/octal→character table. It is a builtin, so it adds no fork, satisfying `_lib_strip_word_quotes`'s documented hot-loop constraint. Using the running interpreter's own `printf` also means the decoder's fidelity automatically tracks that interpreter's own `$'...'` fidelity: on bash 3.2 neither supports `\uHHHH`, on 4.2+ both do, so the decoder can never over- or under-decode relative to the shell that will actually run the command. The decoder parses the escape grammar itself (greedy digit counts per form) and hands `%b` only a single, self-constructed, unambiguous escape, so none of row 2's `%b`-vs-`$'...'` divergences apply. `anchors: row1` `[verified: G2 + claude/.claude/hooks/_lib.sh:655-662]`

4. **NUL-producing escapes truncate the word; decoding stops there.** `\x00`/`\000` end decoding immediately and emit only the bytes decoded so far — the same word-truncation behavior real `/bin/bash` 3.2.57 exhibits, confirmed empirically on 2026-09-01: `$'--textconv\x00SAFE_TAIL'` executes as exactly `--textconv` (10 bytes), with everything after the NUL discarded, not spliced together. Drop-and-continue was considered and rejected. It would decode that same fragment to `--textconvSAFE_TAIL`, which fails the exact-match denylist check at `_lib_fragment_has_command_invoking_git_flag` and reopens the `--textconv` bypass this plan exists to close. That is an allow-direction miss, not an accepted false-positive. Truncation is also the only choice consistent with G3: a bash variable cannot hold a NUL byte, so whatever the decoder does with the pre-NUL bytes must match what bash's own word-splitting does with them, and bash truncates. `anchors: root` `[verified: empirical reproduction against real /bin/bash 3.2.57, 2026-09-01]`

5. **`${NAME:-DEFAULT}` resolved by indirect expansion, gated on a strict name regex.** `NAME` must match `^[A-Za-z_][A-Za-z0-9_]*$` before it reaches `${!name…}`. This is a **hard security requirement, not a nicety**: bash evaluates array subscripts during indirect expansion, so `${!name}` on an attacker-controlled name of the shape `x[$(...)]` is a command-execution primitive — exactly the G1 violation this whole design exists to avoid. A word whose `${…}` span fails the name regex is left un-substituted. `anchors: root, row1` `[verified: empirical reproduction against real /bin/bash 3.2.57(1)-release, 2026-09-01 — `${!name:-default}`/`${!name:+...}` are both available, and `name="x[$(echo INJECTED)]"` executes the subscript's command substitution when the name-regex gate is absent, confirming the gate is load-bearing]`

6. **Parameter defaults resolve before ANSI-C decoding.** `${VAR:-$'--tex\x74conv'}` must substitute first so the decoder then sees the `$'...'` span. The inverse ordering error (a literal `${…}` inside a real `$'...'` span, where bash performs no expansion) resolves in the over-deny direction only. `anchors: row5`

7. **A fast-path gate keeps the hot loop free.** A word containing neither `$'` nor `${` returns unchanged after one `[[ == ]]` test, so the added cost on every legitimate command is one pattern match per word. `anchors: row1` `[verified: claude/.claude/hooks/_lib.sh:655-660 states the constraint this preserves]`

8. **Per-word budgets, fail-closed on exhaustion.** Cap escape decodes and `${…}` resolutions per word; on exhaustion the decoder returns non-zero and the caller treats the word as a match (deny). This mirrors the existing budget-plus-fail-closed precedent at `require-review-orchestrator-bash.sh:195` (`_FRAGMENT_CMD_RESOLVE_BUDGET=10`) rather than inventing a convention. Adding a return status is contract-safe: every hook under `claude/.claude/hooks/` uses `set -uo pipefail` with no `-e`, and no script outside that directory calls either changed function. For `_lib_word_is_git` specifically, "treat as a match" means resolve to git, not "not git" — the inverse of `_lib_strip_word_quotes`'s own exhaustion direction. A git-identity predicate's fail-closed direction must be "assume it is git," so downstream flag checks still run on budget exhaustion rather than being silently skipped. `anchors: row1` `[verified: every `^set -` line in claude/.claude/hooks/*.sh is `set -uo pipefail`; the name grep over claude/.claude found no scripts/ call site]`

9. **`_lib_git_argv_from_subcmd` must be decoded too, or the `_lib_fragment_invokes_git` fix closes nothing.** Three of the four newly-in-scope hooks gate on `_lib_extract_git_subcmd` returning a specific subcommand (`deny-pii-in-commits.sh:186`, `deny-private-project-refs.sh:251`, `require-ready-for-review.sh:225`). With only `_lib_fragment_invokes_git` hardened, `'git' commit -m <pii>` passes the git test, then `_lib_git_argv_from_subcmd`'s own quote-blind `past_git` scan never fires, the subcommand resolves empty, and the hook `continue`s — the PII bypass survives untouched. The same holds for a quoted *subcommand* word (`git $'com\x6dit'`), which `_lib_extract_git_subcmd`'s trailing-character strip reduces to the empty string. `anchors: root` `[verified: claude/.claude/hooks/_lib.sh:594-633 against the three call sites above]`

10. **The escape grammar is grounded by a differential test against the real interpreter, not by a transcribed doc table.** `test_lib.py` gains an oracle test that expands a fixture list of `$'...'` words through `/bin/bash` itself and asserts the decoder agrees. This is stronger grounding than quoting the GNU Bash manual's "ANSI-C Quoting" section, for three reasons: it verifies against the exact interpreter every hook shebang pins; it resolves the NUL question mechanically rather than by transcription; and it fails loudly on a bash-version difference. Executing fixture text in a test is safe: the fixtures are author-controlled, never hook input. This is categorically different from G1, since the hook itself never execs anything as part of its own logic. The implementation must still cite the manual section beside the escape table in the function's comment. `anchors: row1, row3, row4` `[verified: claude/.claude/hooks/tests/test_lib.py:852-865 establishes the /bin/bash subprocess idiom this extends]`

11. **Over-decoding is safe here because every in-scope consumer denies on match.** All five `_lib_strip_word_quotes` call sites and all four `_lib_fragment_invokes_git` call sites are denylist-direction. A decoded word that over-matches produces a false-positive deny, consistent with this hook family's stated false-positive tolerance. `anchors: root` `[verified: claude/.claude/hooks/_lib.sh:692-696 documents the identical accepted-false-positive posture for the `--` pathspec collision]`

12. **`_lib_fragment_command_word` / `_lib_fragment_invokes_tool` stay undecoded.** They are the one family whose output feeds an **allowlist** (`_fragment_invokes_canonical_git`, `require-review-orchestrator-bash.sh:114-118`) as well as denylists, so decoding there moves a gate in the permissive direction and needs its own threat analysis. Their arms are also not the identical `word == "git"` expression this plan abstracts. Deferred with a named follow-up rather than bundled. `anchors: root` `[verified: claude/.claude/hooks/_lib.sh:878-919 and require-review-orchestrator-bash.sh:114-118]`

13. **`_lib_fragment_has_env_assignment_before_git`'s and `_lib_fragment_is_bare_env_assignment`'s `^[A-Za-z_][A-Za-z0-9_]*=` test on raw words is already correct and is not changed.** Bash recognizes an assignment prefix only when the name is literally unquoted, so `$'GIT_CONFIG_COUNT=1' git log` is a command name, not an assignment — there is no quoting bypass to close in those regexes. Only the `git`-word *boundary* inside the first function is replaced, which narrows an existing over-scan. Recording this so a reviewer does not read it as a missed sibling arm. `anchors: root` `[unverified: bash's assignment-recognition-before-quote-removal rule is asserted from POSIX/bash parsing semantics, not empirically run — pin it with a test]`

14. **The new false positives are instances of an already-pinned class, not a new one.** Decode-then-strip makes `_lib_fragment_invokes_git` match `grep "git" README`, where today it already matches the unquoted `grep git README`. `test_lib.py:1220` exists precisely to force a change to this function to notice that class; its docstring's mechanism sentence needs updating, and the test itself keeps passing. `anchors: row11` `[verified: claude/.claude/hooks/tests/test_lib.py:1220-1228]`

15. **`docs/design-decisions.md` §40 gets a forward-pointer sentence, not a rewrite; the redesign gets its own §42.** §40 is a dated decision record (CLAUDE.md Axis 3), and the repo already uses exactly this pattern — see `docs/design-decisions.md:548`, which names "the residual risks this entry's forward-pointer sentence updates." §42 must state precisely what remains open after this change rather than claiming the residual is retired. `anchors: root` `[verified: docs/design-decisions.md:548, 588-613; the 2026-09-01 origin/main sync added §41 (Attribution), so §42 is the next free number]`

16. **The env lookup behind `${!name:-DEFAULT}` reads the hook process's own environment, which may not be the environment the fragment eventually executes under.** `${VAR:-DEFAULT}` resolves `VAR` at hook-eval time, inside the hook process. If Claude Code's harness ever runs the `PreToolUse` hook and the eventual Bash-tool subprocess with different environments, a fragment word like `${SOME_VAR:-safe}` could resolve to a benign default in the hook's check while the real execution resolves `SOME_VAR`'s live, possibly attacker-influenced value — an allow-direction miss structurally identical to row 4's original NUL bug. This cannot be confirmed or refuted from this repo's own sources: it requires the harness's own contract for `PreToolUse`-hook-process-env vs. Bash-tool-subprocess-env, which is undocumented in this repo. `anchors: root, row5` `[engineer-verified pending]` — before Phase 1 ships, either cite a primary source for that env-inheritance contract, or get the engineer to confirm empirically that the two environments are identical, and record whichever as `[engineer-verified]` here.

17. **Decoded and resolved word values must never appear in a deny reason.** `${!name}` resolution reads an arbitrary named environment variable's live value — including one holding a secret — into `_LIB_RESOLVED_WORD`/`_LIB_DECODED_WORD`. This is new exposure surface: today every `emit_deny` call site across the touched hooks echoes only the raw, undecoded `$fragment`, so no secret-leak channel exists, but nothing states this as an invariant. Because each of the five touched hooks constructs its own deny-message string independently before handing it to the shared `emit_deny` printer, this is a per-hook invariant, not one a single hook's test can backstop for the rest — one hook standing in for all five leaves the other four free to reopen the leak with no test failure. `anchors: row5, row1` `[verified: ciso-reviewer's plan-review pass confirmed every touched hook's emit_deny call site currently passes the raw fragment, never a stripped/decoded word]`

# Route review findings that invent new mechanisms through plan-architect

## Context

Extend `/code-review`'s Finding-disposition step so that an ADDRESS-tagged finding whose proposed fix would introduce a new mechanism — rather than change the surface already under review — routes through `plan-architect` before implementation, instead of going straight to `code-writer` or being free-handed inline.

A fully-transcript-documented failure in this repo shows the exact gap this closes:

1. A plan-file's own `/code-review` gate surfaced a single `ciso-reviewer` BLOCKER.
2. The orchestrating session responded by inventing a new dedicated agent plus a new ~220-line enforcement hook, entirely in prose, with the design never passing back through the plan's own `plan-architect`/`plan-review` gate.
3. That decision shipped across three further fully-autonomous handoffs with zero human touchpoints.
4. Every subsequent review round checked the new control's correctness, never whether it should exist.
5. The engineer caught the overreach only when reading the opened PR.
6. An ad hoc `plan-architect` consult, dispatched at that point, correctly recommended deleting the hook and keeping the agent for only one of its two stated justifications.

A corpus-wide search across this operator's session history (multiple accounts, not scoped to this repo) found this is the only clean instance of the pattern — treat it as one complete, well-evidenced case, not a demonstrated high-frequency one.

Two designs were weighed for the trigger: gate on a "new architectural primitive" classification, or consult `plan-architect` unconditionally on every ADDRESS finding. `plan-architect` was consulted directly on both, including after the engineer proposed the unconditional design specifically to pressure-test it against measured volume (319 `/code-review` invocations/month vs. 41 `plan-architect` runs/month in this repo, per a committed case study) and against this skill file's own precedent (`Ripple effect triage` resolves the identical dispatch-cost-vs-under-dispatch tradeoff as gate-plus-mandatory-visible-rationale, not spawn-everything). The engineer agreed to keep a gate, sharpened rather than removed, after `plan-architect` demonstrated its own first draft would have misclassified the originating case's hardest sub-decision (a new arm added to `marker.sh`, describable as extending an already-generic mechanism, that should have fired anyway).

Intended outcome: a committed edit to `claude/.claude/skills/code-review/SKILL.md` making this routing a standing rule, with one-clause reconciliations on `plan-it/SKILL.md`, `plan-architect.md`, and `claude/.claude/CLAUDE.md` so a skill-prescribed dispatch doesn't read as violating existing "human-initiated only" language, a new `docs/design-decisions.md` entry recording the rejected unconditional alternative and its falsifier, and a `_EXPECTED_DISPOSITION_RULE_ANCHORS` test update.

Explicitly out of scope: loosening §37's ad hoc human-ask gate on unprescribed `MODE=consult` dispatches; the independent round-count-based `plan-architect` consult trigger another session is building; an unconditional consult-on-every-finding design (considered in depth and rejected — see Approach and Out of scope).

## Approach

Add one governing rule to `/code-review`'s Fix-route step: an ADDRESS finding whose fix would introduce a new mechanism rather than change the surface already under review is a design question, and it goes to `plan-architect` before anyone writes it. Two routes, both reusing entry points that already exist — a `plan-it` Step 5 revision re-dispatch when the branch has a plan file, a `MODE=consult` dispatch when it doesn't — plus one-clause corrections on the three surfaces that currently describe the consult mode as human-initiated only, so a skill-prescribed dispatch doesn't read as a contradiction. No new hook, no new agent, no new mode, no new marker.

Four judgment calls inside that shape are worth naming.

**The trigger is stated in platform-neutral vocabulary, not this repo's own instances.** The failure class is not Claude-Code-specific — a reviewer proposing a distributed lock, a new queue, or a new middleware layer is the same shape. So the rule reuses CLAUDE.md §Engineering Judgment's own already-platform-neutral vocabulary verbatim ("heavier, more privileged, or wider-scope… a more privileged execution context, a more complex coordination pattern, a more invasive integration"), which `plan-it` Step 5's ledger rule already restates in a global skill body — established precedent for exactly this phrasing at exactly this altitude. The repo-specific instances go in the `docs/design-decisions.md` entry, where they are allowed and where the reader who needs them is.

**The rule derives from `subagent-delegation`'s existing carve-out rather than contradicting it.** `subagent-delegation` currently says the post-review fix is delegated to `code-writer` by default, with a carve-out for a finding "still being re-decided — fails condition (1), stays inline." A finding whose fix invents a new mechanism is definitionally in that class: the reviewer named a problem, not a design. So no new exception is created, and `subagent-delegation` needs no edit — which matters, because that file sits at 201 lines against a 200-line cap and the predecessor plan (`.claude/plans/code-writer-review-feedback-delegation.md`) explicitly rejected raising a cap to fit new prose. The `code-review` block cites the carve-out by name so the two read as one rule from either direction. What `code-review` adds is only where the finding goes instead of inline, which is `code-review`'s own Fix-route business.

**No hook — and the compliance point is already hook-enforced anyway.** A `PreToolUse` gate is the obvious over-reach here, and rejecting it is the plan's own thesis applied to itself. Three independent reasons:

1. The `Write`/`Edit` payload carries a path and content, never "this is a fix I designed mid-review," so there is no predicate at the decision point (G2).
2. A Write-time gate fires after the design choice is already made, which is the wrong moment.
3. Distinguishing a legitimately-planned new hook from an unplanned one would need its own marker, which is the compounding-layers shape `docs/design-decisions.md` §41 declined for a structurally identical case.

The design gets mechanical enforcement anyway, for free, on the branch where the failure actually occurred: the rule's compliance act is *editing the plan file*, and `require-plan-review.sh` re-arms on any modified plan file and denies every non-plan `Write`/`Edit` until a marker covering the new plan state exists. The observed failure escaped the plan-review gate precisely because the plan file was never touched. Routing through the plan file converts an advisory rule into a hook-backed one without writing a hook.

**Proportionality.** This closes one fully-documented instance, not a measured pattern, so the design stays at one paragraph plus one-clause reconciliations. That is defensible because the blast radius per occurrence is severe and the detection latency is terrible — the instance ran through three fully-autonomous handoffs, shipped roughly 750 lines of gate machinery, and was caught only when a human read the opened PR, with every intervening review round checking the new control's correctness rather than whether it should exist. `/plan-review` should read this as calibrated, not as a skeleton to elaborate: any finding proposing a hook, a marker, a new agent, or per-vector machinery here is proposing the exact failure the change exists to catch. The engineer's own alternative — consult unconditionally on every ADDRESS finding — was weighed seriously and set aside on measured volume and on charter drift, not on principle; the gate's falsifier is recorded in the design-decisions entry.

Alternatives set aside:

- **Re-running `/plan-it` end to end on the existing plan** instead of a bare Step 5 revision re-dispatch — heavier (Steps 2–4 re-run for one finding), and it collides with `plan-it`'s own description, which says DO NOT TRIGGER when a plan already exists; taking that route would force a description edit plus a local re-run of `plan-it/evals/trigger-cases.json`. The Step 5 re-dispatch already exists, already takes a plan path, and the plan-review gate is enforced by hook rather than by the skill's Step 6 prose.
- **A prose rule with no dispatch** ("stop and ask the human before adding a new mechanism") — the observed session had every relevant CLAUDE.md rule in context and still free-handed the design; a fourth restatement of a constraint that was already loaded is what §41 rejected. The dispatch is what supplies the missing thing: an independent reader that did not just spend a review round agreeing with the finding.
- **Relying on the existing plan-review gate alone** — it only fires once the plan file is modified, and the failure mode is precisely not modifying it.
- **A new `DEFER` criterion** ("fix requires a design decision") — wrong axis. The finding is still ADDRESS; only the author of the fix changes. `code-review` already declares severity and size invalid disposition axes, and adding a sixth criterion would invite parking real findings.
- **Widening `plan-architect` with a third mode** — the consult grammar already fits (conversational prose, committed recommendation, names what it didn't verify), and §37 chose mode-widening over agent-proliferation on base-context-cost grounds that apply equally to mode-proliferation.
- **Consult unconditionally on every ADDRESS finding, no gate** — pressure-tested at the engineer's explicit request and rejected, on three independent grounds (M3 below points here rather than restating this list):
  1. It does not remove the contestable judgment — it relocates it to arguing the rule's scope, the same failure mode this file's two existing invalid-rationale lists already document happening.
  2. It does not shrink the design — the consult-vs-revision choice and the dispatch's question both survive, and a third de facto genre inside `MODE=consult` re-opens what §37's explicit mode literal closed, likely dragging in an `effort` change against §24.
  3. It costs a measured several-fold-to-9x rise in `plan-architect` volume (see Assumption ledger rows 17–18).

  The closest structural sibling in this same file — Ripple effect triage — resolved the identical dispatch-cost-vs-under-dispatch tension as gate-plus-mandatory-visible-rationale, not spawn-everything.

### Assumption ledger

**Root problem:** `/code-review` Step 1's implementation-fitness gate catches over-elaboration in code already written, and nothing catches over-elaboration in code the review itself is about to cause — so an ADDRESS finding whose fix invents a new mechanism is authored inline or dispatched straight to `code-writer`, bypassing every design gate the surrounding work went through.

**Givens:**

- **G1 — a subagent cannot verify who or what dispatched it.** It receives its dispatch prompt plus its startup load and nothing else. Harness-owned; §37 already recorded this and deliberately did not try to close it.
- **G2 — `Edit`/`Write` tool payloads carry a path and content, not a semantic label for edit-kind.** A property of the harness tool schema, owned by Anthropic. Same given the predecessor delegation plan recorded.
- **G3 — everything under `claude/.claude/**` installs into every stow consumer's config dir on `git pull`.** Owned by `install.sh` and the repo layout, not by this plan. This is what forces M3's platform-neutral wording.

**Mechanisms:**

- **M1 — the rule lands in `code-review`'s `## Finding disposition`, immediately after the `Fix route:` paragraph.** `anchors: root, row1, row2`. That paragraph is where the route is already decided and already emitted as a reviewable artifact, so the marginal cost is one more possible value on a line the skill already mandates. *Lighter primitives rejected:* (a) Step 1's implementation-fitness gate — it evaluates the diff as written, and the over-powered mechanism does not exist in the diff yet; (b) the `Ripple effect triage` table — it routes *reviewer* spawns off the diff's content, and this trigger keys on a proposed fix that no table row can see.
- **M2 — two routes, both existing entry points.** `anchors: root, row3, row4, row5`. Plan-file branch: `plan-it` Step 5's revision re-dispatch (`MODE=plan-sections`, plan path, the finding), whose return is inserted verbatim, which re-arms `require-plan-review.sh` and forces the design back through `/plan-review` before any further code write (row 4). No-plan branch: `MODE=consult`, with a one-clause tail stating that an endorsed new mechanism is design work entering through `/plan-it` on its own terms — otherwise the no-plan arm reproduces the original failure with a consult stapled on. *Heavier alternative rejected:* a `PreToolUse` gate — G2 leaves no predicate, Write-time is after the decision, and separating a planned from an unplanned primitive would need a marker (see Approach). *Lighter primitive rejected:* prose-only stop-and-ask, per Approach.
- **M3 — trigger stated as one observable limb plus one judgment limb, with a closed list of invalid skip rationales.** `anchors: row5, row6, row16`. The primary limb is mechanical: the fix cannot be expressed as a change to files already in the diff under review. The secondary limb covers a new mechanism added inside an existing file, in CLAUDE.md's over-powered-primitive vocabulary. A classification-only trigger was drafted first and rejected against the originating case's own evidence: that work's new `marker.sh` arm is describable as extending an already-generic, already-tested mechanism (row 16), so a bare "is this a new primitive?" test gets its hardest sub-decision wrong. The closed list — reuse-of-an-existing-mechanism when a new arm is what's added, single-file scope, and the reviewer's own Suggested-fix field — mirrors the two invalid-rationale lists this file already carries, which exist because near-unconditional defaults in this same skill were reasoned around. The verdict is stated on the `Fix route:` line either way, affirmatively when the gate doesn't fire, per the *Spawn decisions:* no-match precedent. *Alternative rejected — consult on every ADDRESS finding, no gate:* see Approach's Alternatives-set-aside bullet for the three-ground rejection (rows 17, 18 carry the volume evidence); not restated here.
- **M4 — three one-clause reconciliations, so the prescribed dispatch does not read as a violation.** `anchors: row7, row8, row9`. `plan-architect.md`'s description currently enumerates two triggers and says DO NOT TRIGGER "when the user has not asked"; `claude/.claude/CLAUDE.md`'s Model & Effort Routing bullet says "never dispatch it this way on your own initiative." Both are literally satisfiable under CLAUDE.md's "a prescribed dispatch is an authorized dispatch," but the failure direction of a misread is a session declining the dispatch and free-handing the design — the exact failure being closed — so the inference is not left implicit. §37 itself names the agent description plus the CLAUDE.md bullet as the preventive control for this call site, which makes them the consistent place to state the third one. *Lighter primitive rejected:* relying on the Agent Briefing rule alone — an absolute "never" in a more specific bullet is exactly the shape that overrides a general rule stated elsewhere in the same file. **Deliberately not done:** a fourth restatement inside `code-review`'s new block; three surfaces already resolve it and a fourth is the compounding-layer smell.
- **M5 — `DISPOSITION_RULE:` anchor pair around the new block, plus the exact-set test update.** `anchors: row10`. Layer 1 of the disposition-fidelity harness is a deletion guard for exactly this artifact class — a single governing paragraph inside a 460-line skill — and the convention here is to ship the enforcing test with the convention. *Lighter primitive rejected:* no anchor — leaves the rule with no mechanical guard, which is what the anchor mechanism exists to prevent.
- **M6 — a new `docs/design-decisions.md` entry.** `anchors: root, row11, row12`. Records why the route is a dispatch and not a hook, why §37's ad hoc gate is untouched, why the unconditional alternative was rejected (with its falsifier as a Revisit trigger), and carries the repo-specific instances of the trigger that M3 keeps out of the skill body. Extends §30/§37 with a forward-pointer rather than editing either dated record.

  3. A finding fixed by adding a new privileged execution context (must fire).

  5. A new arm added to an existing shared state mechanism (must fire — this is the originating case's own hardest sub-decision).

# Subagent idle-gap cache-rebuild split

## Context

Measure the subagent-specific share of idle-gap prompt-cache rebuild cost in this repo's own `transcript-analysis.py`, and decide whether raising `experimental.cacheTtl` for chronically-idle-gap-prone subagent types is worth building. Why now: a `plan-architect` consult on branch `correct-cachettl-read-caching-scope` (PR #903) found that every existing `cacheTtl` analysis in `docs/cost-levers-considered.md` prices *inter-dispatch* prefix sharing (repeat dispatches of one reviewer agent type reusing a warm cache across separate `Agent` calls), which nets to roughly break-even ($17.65 cost vs. $17.35 benefit) because that benefit is capped at the same-session-repeat subset. Nobody has priced *intra-dispatch* idle-gap rebuilds — a single subagent's own conversation going cold mid-dispatch due to concurrent-session cache contention. This register's own "Context cost root cause" section already found that cause, not operator breaks, accounts for 92.9% of main-thread idle-gap rebuilds (7.1% are breaks). But the `cache-rebuild` subcommand pools main-thread and subagent-originated rebuild events with no split. So the subagent-specific share of a $1,513.55/30-day rebuild pool (`docs/cost-levers-considered.md:198`) is unknown. Intended outcome: a `cache-rebuild` main/subagent split restricted to the existing 300–3600 second idle-gap band, gated behind a pre-registered decision rule, that either produces a scoped follow-up design or records a decline with the measured reason in `docs/cost-levers-considered.md`.

One mechanical unknown from the original framing is already resolved and does not need re-verification: Claude Code's own prompt-caching guide (`https://code.claude.com/docs/en/prompt-caching`, fetched and quoted verbatim in an earlier session this branch descends from) states that a subagent "warms a cache of its own across its turns" and that subagents "fall outside the main-conversation TTL bucket, so they get five minutes even on a subscription until you choose a longer one." This confirms `experimental.cacheTtl` in subagent frontmatter governs a subagent's own intra-dispatch conversation writes across its own turns — no live harness probe is needed to establish this. What remains genuinely unmeasured is the idle-gap distribution and dollar magnitude specifically for subagent-originated rebuilds, which the main/subagent split below addresses.

## Approach

**Ship the main/sidechain split as a measurement instrument, but gate the decision on a *ratio*, not on the subagent share of the rebuild pool — because the dispatch's framing prices only half of what raising `cacheTtl` costs.** Raising a subagent from the 5-minute to the 1-hour tier does not recover its idle-gap rebuild excess for free: it raises the write multiplier from 1.25x to 2x on *every* cache write that subagent makes, including all the warm incremental ones that were never rebuilt. So the subagent share of the $1,513.55/30-day pool can comfortably clear $50 while adoption still *loses* money. The quantity that decides the sign is the share of subagent 5-minute-tier write volume that idle-gap rebuild accounts for, and that number is not in any report today.

### The break-even, derived

Let `W5m` = all 5-minute-tier cache-write tokens in subagent conversations over the window, and `X` = the subset of those written by a call classified `idle 5m-1h` (⊂ `W5m`). Multipliers against base input rate are `pricing.py:25-27`: 5m write 1.25x, 1h write 2x, cache read 0.1x for every model **except** `claude-fable-5-1`, whose cache-read multiplier is 0.025x instead (`pricing.py:35-36`, `_REDUCED_CACHE_READ_MULTIPLIER`/`_REDUCED_CACHE_READ_MODEL_IDS`). Observed 1h-tier tokens drop out of both arms unchanged, so they cancel:

- Status quo: `1.25·W5m`
- After the switch: `2·(W5m − X) + r·X` — the `X` tokens are no longer rebuilt, they are read warm at the model's own cache-read multiplier `r` (0.1 by default, 0.025 for `claude-fable-5-1`); everything else still gets written, now at 2x.
- Delta = `0.75·W5m − (2 − r)·X`, so **adoption pays only when `X / W5m > 0.75 / (2 − r)`** — 0.3947 for a default-rate model, 0.3797 for `claude-fable-5-1`.

The pricing helper (Phase 0b) must resolve `r` per call; it must not hardcode `1.9`. `(2 − r)` is `1.9` only when every `idle 5m-1h` call priced into `X` is a default-rate model — the plan's own worked examples below use `1.9`/`0.3947` as reference figures because `claude-fable-5-1` subagent traffic is expected to be rare in this repo's corpus. This does not change Phase 0c's decision rule: the 0.50 robustness margin exceeds both possible break-evens (0.3947 and 0.3797), so criterion 2 holds regardless of model mix.

This is why the plan measures tokens and a ratio, not just the dollar pool the original framing named. It is also why `idle >1h` stays out of the numerator: a 1-hour cache is cold past 3600s too, so those rebuilds happen under either tier. Restricting to the existing 300–3600s band is correct, and this is the reason.

### Phase 0a — the free pre-gate and premise check (zero code)

`cache-efficiency` already prints a `main`/`sidechain` split with `Write1h`, `Write5m`, `Read`, `ColdTok`, and `Cold/Wr` per thread (`transcript-analysis.py:5586-5598`), classifying per record off `isSidechain` (`:5547`). Run it before writing any code. It gives two things for free:

1. **An absolute ceiling.** Even at the impossible `X = W5m`, net is `1.15·W5m` per unit rate — at `claude-sonnet-5`'s $2.00/MTok that is $2.30 per MTok of sidechain `Write5m`, so clearing a $50 floor needs at least ~21.7M sidechain 5m-write tokens in the window. If the corpus is under that, the whole plan declines with no code written.
2. **A premise check.** The vendor states subagents "fall outside the main-conversation TTL bucket, so they get five minutes even on a subscription until you choose a longer one," and no agent file in this repo sets `cacheTtl` (repo-wide grep: hits only in `docs/` and `.claude/plans/` prose, none under `claude/.claude/agents/`). So sidechain `Write1h` should be ≈0. A materially non-zero value falsifies the counterfactual model above and the plan stops to re-derive it rather than proceeding.

It cannot serve as the gate itself: its `ColdTok` comes from the read-collapse rule, which detects *that* a prefix went cold, not *why* — it pools the `>1h` band that a 1-hour TTL does not rescue, so it cannot isolate the numerator.

### Phase 0b — the instrument change

Extend `_cache_rebuild_report` (`transcript-analysis.py:5809-6057`) with a per-origin split and a tier-switch block. Six design calls that are not free choices:

**Classify origin per record via `isSidechain`, not by `group_index > 0`.** They are not equivalent: the group index encodes "which file the record came from," while `isSidechain` encodes "this is a subagent turn," and the runtime drift canary (`pricing.py:479-482`) exists precisely because the split-file layout is a harness detail that can move. More decisively, the gate's numerator is divided by a denominator that must reconcile against `cache-efficiency`'s sidechain row, and that row is built from per-record `isSidechain`. Two subcommands both printing "sidechain" while disagreeing on what a sidechain record is would make the ratio unreconcilable. Use the identical expression `bool(rec.get("isSidechain"))`.

**The ratio accumulators are threshold-independent; the cause table stays threshold-gated.** `cause` is already computed for every call at `:5936`, before the `in_tail` gate at `:5951` — so accumulating `W5m` and `X` for every in-scope call is a one-line addition and needs no `--threshold 0` rerun. This is required, not cosmetic: `W5m` must include the small warm incremental writes, because those are exactly the tokens the 2x uplift is charged against. The new block therefore prints its own denominator and states in its header that it is threshold-independent, so no reader divides it by the tail figures above it.

**Price per call, do not hand-multiply aggregate tokens.** Rates vary per model and `_price_turn` applies fast-mode and US-geo multipliers per call. Add one helper beside `_cache_rebuild_excess_dollars` (`:5772-5796`) that returns this call's signed contribution to the switch delta — `0.75 ×` its 5m-tier write tokens as cost, minus `(2 − r) ×` its 5m-tier write tokens when its cause is `idle 5m-1h`, where `r` is *this call's own model's* cache-read multiplier — mirroring that function's existing `_model_rates` + fast/geo body (which already resolves `r` per model via `_REDUCED_CACHE_READ_MULTIPLIER`/`_REDUCED_CACHE_READ_MODEL_IDS`, so no new per-model table is needed) and its `(value | None, unpriced_tokens)` unpriced-model contract. **`(2 − r)` must be computed per call, never hardcoded as `1.9`** — a corpus with `claude-fable-5-1` subagent idle-cause calls needs `1.975` for those specific calls, and a hardcoded `1.9` would misprice them (see Verification test 9).

Sign convention: the report negates the accumulated per-call sum before printing it as "net." Accumulated across all in-scope calls the helper's own return values sum to `0.75·W5m − Σ(2 − r_call)·x_call` — which equals `0.75·W5m − 1.9·X` only when every `X`-contributing call is a default-rate model — this is the Approach section's "Delta," cost-of-switching-positive. The printed net dollar figure is the negation of that sum, so it is savings-positive, matching Phase 0c's decision rule and Verification test 5. The helper itself is not restated with a flipped sign; only the print-time summation-then-negation differs from the helper's own per-call return value.

**Do not split the concurrency table by origin.** `session_key` is file-level across every group (`:5890`, docstring `:5908-5911`), so a sibling subagent's or the parent's activity during a subagent's stall counts as *this* session and lands the rebuild in "Everything idle (a break)." For a subagent stalled on a long `Bash` call that label reads as an operator break and means nothing of the kind. Leave the corpus-wide concurrency table exactly as it is; the new subagent block reports origin counts, excess dollars, and the ratio figures only.

**Per-dispatch dispersion, not per-agent-type attribution.** Per-agent-type attribution is a materially heavier change: it needs the `meta.json` → parent-`Agent`-tool_use join (`reviewer_yield.py:53-98`) plus a `--this-repo`-gated disclosure surface `cache-rebuild` does not have, because `subagent_type` is redacted under multi-root and discloses only for repo-tracked types (`transcript-analysis.py:2576-2585`, `:2387-2389`) — the same instrument block that stopped the `opus-frontload-review-rounds` within-agent gate. The lighter primitive that answers the same question: compute `X` and `W5m` **per subagent group** (each group is one dispatch's own conversation), threshold-independently exactly as the pooled accumulators are (row 6) — a sub-threshold call must still count toward its own group's `X`/`W5m`, for the identical reason the pooled figures need it — and report three aggregate numbers — how many dispatches individually clear their own break-even ratio, what share of total `W5m` they carry, and the net dollars restricted to that subpopulation. A group with `W5m = 0` (a dispatch that made no 5-minute-tier writes at all — e.g., an all-1h-tier or all-read subagent) has an undefined ratio and is excluded from the clearing-count and share figures, though its (zero) net dollars still contribute to the subpopulation total. No join, no type names, no new redaction surface.

**Key the sequential gap-chain per (group, origin), not per group alone.** Mirroring `_scan_cache_efficiency_group`'s `chain_key = (session_key, thread)`, keep separate `prev_ts`/`prev_model` chains for main-thread and subagent-origin records within one group. Without this, an inline sidechain record's *cause* — not just its origin label — would be computed against whichever record preceded it in file order regardless of origin, which could misclassify an interleaved subagent call's idle-gap cause and corrupt `X` (Verification test 2 extends to cover this).

That third number is an **ex-post oracle bound**: it selects dispatches by their realized ratio, which a real policy cannot do (a policy picks agent *types* in advance). It therefore overstates any achievable selective policy — which makes it a valid one-sided test. If even the oracle bound misses the floor, no selective policy can clear it and the decline is final.

### Phase 0c — the pre-registered decision rule

Fixed before the numbers are read, in the discipline `reviewer-instance-continuation.md:61-66` and `delegate-instrument-authoring.md` both used. Three outcomes:

1. **Adopt (uniform).** Pooled subagent net (priced per call, per the corrected coefficient above) exceeds **$50**, *and* the pooled ratio `X/W5m ≥ 0.50`. The $50 floor is adopted by analogy — it is the same floor `docs/cost-levers-considered.md:410-436` already applied once to a cacheTtl-adjacent (but distinct, bundled) decision (row 11). The 0.50 ratio is a robustness margin — ~27% relative headroom over the 0.3947 break-even — so a re-measurement against a fresher window cannot flip the sign of a change that is already live for every stow consumer. It mirrors the stress-margin discipline `opus-plan-boundary-handoff` applied (`docs/cost-levers-considered.md:182`).
2. **Not excluded (selective).** Pooled fails but the ex-post oracle bound exceeds $50. Record the row as "selective lever not excluded," naming per-agent-type attribution as the instrument change a follow-up would need first.
3. **Decline.** Both fail. Record the row with the measured reason; the split ships regardless as the durable instrument.

**Expectation is outcome 3, stated on the record before the run.** A subagent dispatch that never stalls past five minutes contributes `X = 0`. For the pooled ratio to clear 0.3947, stalls must be both common *and* dominate the stalling dispatches' own write volume. This cannot be resolved without running the tool, so it stays `[unverified]` — but the plan should not be surprised by a decline, and the register row is a real deliverable either way.

### Phase 1 — conditional, and deliberately not bundled

If the gate clears, the mechanism is `experimental.cacheTtl: 1h` in the frontmatter of the qualifying agent files. **Do not make that edit in this plan.** Three independent reasons, not one: the field sits in an `experimental.` namespace this repo has already twice recorded as "not a stable surface for repo-shared config" (`docs/cost-levers-considered.md:345`); `claude/` installs to every stow consumer, so the blast radius and threat model are categorically different from a read-only analysis subcommand; and the repo has written precedent that adoption is "its own change with its own review" (`.claude/plans/audit-cost-intelligence-guide.md:111`). The follow-up `/plan-it` run inherits a named charter: which agent types qualify, uniform-vs-selective, `/agent-review` across every touched file, and how an `experimental.`-namespace field is presented to stow consumers who did not ask for it.

### Over-powered-primitive check

**Mechanism A — a permanent `transcript-analysis.py` change rather than a one-off scan.** Three lighter primitives examined:

1. **`cache-efficiency` as it stands, zero code.** Adopted for what it can do — Phase 0a's ceiling pre-gate and premise check run entirely on it. Rejected as *the* gate: its cold classifier is the read-collapse rule, which detects that a prefix went cold, not why, so its `ColdTok` pools the `>1h` band a 1-hour TTL does not rescue and cannot isolate the numerator. (row 3, row 5)
2. **A one-off scan script over the corpus.** Rejected on three grounds. It would re-derive `_dedup_turns_by_request_id`, `_price_turn`'s fast/geo multipliers, and the group-boundary reset that `TestCacheRebuildGroupBoundary` exists to pin. This register's own prior one-off scan is recorded as "undeduped by `requestId` — treat the ratio as the finding and the absolutes as unreliable" (`docs/cost-levers-considered.md:213-214`), and this gate's rule is a dollar floor whose absolutes must hold. And the register already committed the route in writing: a subagent figure "needs a `transcript-analysis.py` change, not a rerun" (`:345`). (row 15)
3. **Rerun `cache-rebuild` under a subagent-narrowing scope flag.** Rejected — no such flag exists; `include_subagents` is hardcoded. (row 15)

The reusability question lands opposite the `reviewer-instance-continuation` `R`-measurement precedent, and for a stateable reason: `R` was one number for one gate that would never be asked again, whereas `cache-rebuild` is a documented standing subcommand whose own register entry instructs re-measurement against a fresher rolling window (`:198`). The split is asked every rerun.

**Mechanism B — flipping `experimental.cacheTtl` on agent frontmatter (Phase 1).** Three lighter primitives:

1. **Cut the gaps at the source instead of paying to survive them.** If row 13 holds, the stalls are long in-dispatch `Bash` calls, and this repo already mandates the fix (`CLAUDE.md` Commands: agents run `select-tests.py`, not the full suite). Zero new config, no experimental field, and it shrinks `W5m` as well as `X`. Not adopted *instead* here only because Phase 0b does not attribute gaps to a cause — but it is the first thing a cleared gate should re-examine, and it belongs in the register row either way.
2. **Decline and record the row.** Free, and the correct answer under outcome 3. Genuinely the expected result.
3. **A conversation-level or per-machine TTL setting reaching subagents.** Rejected on the vendor's own words: subagents "fall outside the main-conversation TTL bucket," so no main-conversation control reaches them (G2).

New test cases, each pinning one design call above rather than restating coverage:

Every new test that places a subagent record via `_write_subagent_jsonl` must manually set `isSidechain: true` on it, mirroring `TestCacheRebuildGroupBoundary`'s existing pattern — `_write_subagent_jsonl` writes records verbatim and does not tag `isSidechain` itself. Since origin classification is now `isSidechain`-based rather than group-based (row 7), an untagged subagent fixture would pass identically under the correct classifier and the rejected `group_index`-based one, defeating its own discriminating purpose.

1. **Origin split.** One main-thread and one subagent `idle 5m-1h` rebuild in the same fixture session; each lands in its own row and the corpus-wide totals are unchanged from today's.
2. **Inline-sidechain classification.** A record carrying `isSidechain: true` written into the **main** transcript file counts as subagent. This is the test that pins row 7 — a `group_index > 0` implementation passes test 1 and fails this one. The same fixture also asserts the record's *cause* — not only its origin label — is computed against the correct per-origin predecessor in the gap-chain (a chain keyed per group alone would instead compare it to the immediately preceding main-thread record in file order, which this fixture's interleaving is built to catch).
3. **Threshold independence.** A sub-threshold subagent 5m-tier write counts toward `W5m` but does not appear in the tail cause table. A sibling case pins the decision-critical half of this design call: a sub-threshold subagent call whose `cause` is `idle 5m-1h` counts toward `X` while remaining invisible in the tail cause table — the likelier implementer mistake is gating `X`'s accumulation on the same `in_tail` check that gates the cause table, rather than accumulating it unconditionally as row 6 requires.
4. **Numerator boundaries.** An `idle >1h` subagent rebuild and a pure-1h-tier subagent write inside a 6-minute gap both stay out of `X` (extends `TestCacheRebuildCacheTierGapMismatch`'s fixture shape, `:7809-7829`).
5. **Break-even arithmetic.** A fixture with `X = 500,000` and `W5m = 1,000,000` on `claude-sonnet-5` (a default-rate model, $2.00/MTok base) must print net `(1.9 × 500,000 − 0.75 × 1,000,000) ÷ 1e6 × $2.00 = $0.40`. This pins both coefficients for the default-rate case; a fixture at the break-even ratio alone would not distinguish a transposed pair. The expected sign is savings-positive per Phase 0b's negation step — a fixture that instead asserted the helper's own pre-negation per-call sum would expect `−$0.40`.
6. **Break-even boundary.** `0.3947` is a rounded display of the true break-even fraction `0.75/1.9 = 15/38`, so a fixture built at the rounded decimal sits measurably off the actual boundary and cannot discriminate `>` from `>=`. Use exact integers instead: `X = 150,000`, `W5m = 380,000` (default-rate model) — `150,000/380,000 = 15/38` exactly, so `0.75 × 380,000 = 1.9 × 150,000 = 285,000` and net is exactly `$0`. This fixture must **not** count as an individually-clearing dispatch in the per-group dispersion count (test 8) — pinning the strict `>` in "adoption pays only when `X / W5m > 0.75/(2−r)`" against a `>=` off-by-one.
7. **Zero state.** A corpus with no sidechain records prints a zero-valued subagent row, matching the per-account zero-seeding convention.
8. **Per-group dispersion.** A fixture with at least three subagent groups — one whose own `X / W5m` ratio individually clears its break-even, one that does not, and one with `W5m = 0` (no 5-minute-tier writes at all) — asserts: the reported clearing-dispatch count, `W5m` share, and net dollars are computed against each group's own `X` and `W5m`, not pooled against the corpus-wide denominator (this is the mechanism Phase 0c's Outcome 2 reads off; a group's ratio computed against the pooled `W5m` instead of its own would silently corrupt the oracle bound); the `W5m = 0` group is excluded from the clearing-count and share figures without raising a division error, and contributes zero to the net-dollars total; and a sub-threshold call inside one of the clearing groups still counts toward that group's own `X`/`W5m` (per-group threshold-independence, mirroring test 3's fix for the pooled accumulators).

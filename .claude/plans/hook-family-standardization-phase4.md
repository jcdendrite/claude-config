# Hook-family standardization — Phase 4 (mass mechanical)

## Context

Phase 4 ("mass mechanical") of the hook-family-standardization effort closes GH-489 and GH-580: 43 hook files hand-copy two mechanisms — tool-input `jq` field extraction, and deny-message identity prefixes — that Phases 1-3 already extracted shared helpers for elsewhere in `_lib.sh` but did not touch for these two concerns. Why now: Phases 1, 2, 3a, 3b, 3c are all merged into `origin/main` (verified this session — `1ecb55c` Phase 3a, `ee78b35` Phase 3c, `8cb0ef0`/PR #852 Phase 3b), and the master plan's own ordering note states Phase 4 cannot land before every Phase-3 sub-PR merges, since Phase 4's file list is "all 43 hooks" including every hook Phase 3a/3b/3c touched — landing Phase 4 earlier would turn each Phase-3 PR into a conflict resolution instead of a clean merge. That precondition is now satisfied. Intended outcome: `_lib_parse_tool_input_or_deny` extended to cover the fields hooks currently re-parse via a redundant secondary bare-`jq` call; hook deny-message prefixes made to derive from a per-hook declared identity instead of each hook hand-writing its own identity string at every call site; every hook and test file this touches updated to match; and `transcript-analysis.py`'s denial-classification scheme updated so historical (immutable) transcripts keep classifying correctly and — per the engineer's explicit priority — so the infra-failure-vs-behavioral-denial distinction the analysis relies on becomes a cross-cutting signal available for all 26 gate hooks, not an accident of 2.

Seed material: `.claude/plans/hook-family-standardization.md`'s Phase 4 Critical-files bullet (~lines 152-159), Assumption-ledger rows 13, 14, 19, 24, the "Phase ordering and independence" paragraph, Phase 4's Verification bullet (~line 217), and the Out-of-scope section (`_lib.sh` staying one file, `settings.json` `if`-dispatch migration, `plugins/skill-management` as a separate stow package are all pre-existing boundary calls this phase inherits).

## Approach

Phase 4 folds four additional payload fields into `_lib_parse_tool_input_or_deny`'s existing single delimited `jq` call, and gives `_lib_emit_deny` a per-hook identity prefix that each gate hook declares **once** as a shell variable rather than hand-writing at every call site. The prefix is a declared label with a `$0`-derived fallback — not a pure `$0` derivation, because 15 of the 24 enumerated gate labels deliberately do not match their filename, and a filename derivation would silently reclassify every one of them in `transcript-analysis.py`. A second, separable piece of work ships alongside and **first**, as Dispatch 0: `transcript-analysis.py` gains a denial-cause axis — *what caused this denial* — orthogonal to *which gate fired*. It is authored and merged against pre-Phase-4 wording, so it is not part of the wording change's justification; the "Dispatch ordering" paragraph below is where that decoupling is argued.

**Scope decision — Group A only, plus a mechanical `_lib_jq` swap for Group B.** The engineer's lean toward Group-A-only scope is confirmed: the two hooks that already document *why* settle it: `nudge-unexpanded-skill-mention.sh:79-83` states that `.prompt` must never go through the combined pass because the `head -c` byte cap has to apply before any split, and `nudge-transcript-toolkit.sh:107-110` states that `MultiEdit`'s fields are not independent (`edits[] | length` gates which field is read next). Group B is not one shape with one missing helper; it is a set of hooks whose fail posture is *exit 0 silently*, which is the opposite of the helper's deny-on-parse-failure contract. Converting them would need a second no-deny variant of the helper — a new mechanism wider than the task. What Group B *should* get is the one-token swap from bare `jq` to `_lib_jq`, which closes GH-489's actual named defect (uncapped secondary calls) at those sites and keeps Phase 5's "no bare `jq` outside a `_lib_*` wrapper" conformance test from needing an 11-file permanent allowlist — the master plan moved that test to Phase 5 precisely so its allowlist would be derived from what genuinely cannot conform.

**Dispatch ordering — the cause axis ships first, and the hook rewrite is one atomic commit.** The cause axis has no technical dependency on the wording change: row 21 establishes that its four markers already sit in the body of the *current* wording, so the classifier is authored, tested, and merged against pre-Phase-4 text before a single hook changes. Running it first (Dispatch 0) buys three things a bundled ordering does not. The classifier's fixtures *are* the pre-Phase-4 wording, frozen where they were written rather than reconstructed later. Every subsequent dispatch's own `select-tests.py` run re-executes those fixtures against the changed hooks, so the G1 non-regression claim becomes a live, continuously-re-proven property of the branch instead of a one-time assertion. And the wording unification is then evaluated on its own DRY and attribution-coverage merits, with the analytics benefit already banked and no longer serving as part of its justification.

The opposite constraint applies to `_lib.sh` and the hooks: **Dispatch 1 and Dispatch 2 are one commit.** `_lib_emit_deny`'s prefix activates globally the instant `_lib.sh` changes, while `DENY_GATE_LABEL` declarations and call-site strips land per-hook in Dispatch 2 — so any state between them emits a doubled, `$0`-mislabeled prefix (`Blocked by require-architect-consult gate: Blocked by architect-consult gate: …`) from every not-yet-migrated hook. Making the prefix conditional on a declared `DENY_GATE_LABEL` would restore independent verifiability, and is rejected: it trades away the forgotten-declaration fallback — the one place the `$0` derivation does real work — to buy a checkpoint the branch never ships from, since `~/.claude/hooks/*.sh` symlinks resolve to the main checkout, not this worktree. Dispatch 1's own gate is therefore a targeted `test_lib.py` run, not a green `select-tests.py`; the Verification section names exactly which tests are expected red in between and forbids chasing them.

**Deny-prefix design — a declared label, not a `$0` basename.** Each gate hook sets `DENY_GATE_LABEL="<its current label>"` immediately above its bootstrap `emit_deny` stub. Both the stub (pure parameter expansion, no fork, no `_lib.sh`) and `_lib_emit_deny` read it and emit one canonical shape: `Blocked by <DENY_GATE_LABEL> gate: <body>`. Every call site passes a prefix-free body. Three consequences make this strictly better than the prescribed `$0` derivation:

- **No label churn.** Every post-change label is already a member of `_DENIAL_HOOK_LABELS`, with the two exceptions row 23 names. A `$0` derivation would change 15 of 24 (`block-gh-pr-merge.sh` → `gh-pr-merge`, `deny-private-project-refs.sh` → `redaction`, `check-claude-md-length.sh` → `CLAUDE.md length`, and so on), forcing ~15 union additions and invalidating 15 of `TestDenialHookLabelEnumerationRealHooks`'s 24 real-subprocess rows.
- **Row 19's bootstrap carve-out dissolves.** The master plan assumed the bootstrap stubs "cannot derive a prefix from `$0`" because `_lib.sh` has not sourced. True for `_lib_emit_deny`; false for the prefix itself — `${0##*/}` and a variable read need no library. Both paths emit the same identity, so the two-identities-per-hook split a carve-out would create never arises.
- **It matches the decision this effort already shipped.** `_lib.sh:1010-1015` (merged Phase 2) documents `_lib_staged_length_gate`'s `GATE_LABEL` parameter as "the exact sentence each caller already used… verbatim, not a generic template, because transcript-analysis.py's `_denial_hook_label` parses that exact wording." Phase 4 must not reverse that six weeks later.

Alternatives set aside: **(a) pure `$0` derivation**, per GH-580's own wording and `gh557-denial-friction-census.md:292` — rejected on the 15/24 mismatch above; that census's claim that it "dissolves the pattern table" does not survive contact with the label inventory, though its other two observations (a user-visible change for every stow consumer, no help for historical transcripts) hold and are absorbed here. **(b) A second `_lib_emit_deny` argument** carrying the prefix — rejected because passing it at every call site is the duplication being removed; the repo's established shape for this is caller-defined-name-resolved-at-call-time (`emit_deny`, `limit_for`), which a variable matches and a parameter does not. **(c) Leave the zero-prefix call sites alone** — rejected: those messages (`deny-private-project-refs.sh`'s pseudo-file-path denials, `deny-escaped-backticks-in-pr-body.sh`'s two body-source denials, `block-gh-pr-merge.sh`'s three bare "Blocked:", `deny-pii-in-commits.sh`'s `Commit blocked by PII/credential guard:` sites, `enforce-marker-script-shape.sh`'s parse-failure deny) currently classify as `unmatched`, so uniform prefixing is a net gain in attribution coverage, not just consistency. **(d) Ship the cause axis as its own PR entirely, deferring the wording change** — rejected in favor of the reordering above, which captures the same decoupling (the classifier is authored and proven against unchanged wording, and no part of its correctness rests on the hook rewrite) without a second branch, plan, and review cycle; the residual half that genuinely does depend on the rewrite — the label-set additions and the `DENY_GATE_LABEL` conformance test — stays in Dispatch 4 where that dependency is real.

**Denial cause classification — a second axis, not a wider label set.** `transcript-analysis.py` gains `_denial_cause_kind(message) -> str`, a sibling of `_denial_hook_label` returning one member of a closed five-value vocabulary: `behavioral` (the agent tripped the gate), plus four infra causes — `lib-source` (`_lib.sh` failed to source), `input-parse` (the tool-input payload failed to parse), `helper-proc` (`sed`/`tr`/`awk`/`grep` missing, killed by the timeout backstop, or errored), and `deny-encode` (`jq` missing, failed, or timed out, so the deny envelope could not be built). Classification is a substring match against one literal marker per family, in a fixed-precedence cascade. Three properties make this the right mechanism:

- **It is the only option that classifies a historical denial.** G1 makes the analyzed corpus immutable, and that corpus is the entire input to `error-mode-analysis`. A structural marker emitted by the hooks — a sentinel token, or a new `_lib_emit_infra_deny` every fail-closed site calls — has zero coverage over every transcript already recorded, so it answers the engineer's question only after months of new corpus accumulate. It would also re-route ~30 call sites across 14 hooks (row 20's census) on top of Dispatch 2's existing 26, and put a machine token into prose an agent reads, for every stow consumer (row 17).
- **It is what `_denial_hook_label` already does.** That function reads the gate identity off the message text via a regex cascade rather than a structured field, precisely because the current transcript shape carries no structured hook identity (`transcript-analysis.py:1241-1251`). The cause axis has the same input and the same constraint, so it gets the same mechanism.
- **The markers survive Phase 4 unchanged.** Every one of the four lives in the message *body*, after the lead-in boundary, and Phase 4's call-site rule is strip-the-lead-in / preserve-the-body-byte-for-byte. So one pattern per family covers the pre- and post-Phase-4 eras alike, with no legacy/current union of the kind `_DENIAL_HOOK_LABELS` itself needs (row 22).

Two lighter primitives were weighed and rejected. **A boolean `is_infra_failure` instead of the five-value vocabulary** — rejected because the four infra families map to four different fixes (restore the stow symlink, fix the harness payload, install coreutils, install jq), the four literals must each be matched regardless, and returning `str` rather than `bool` from the same cascade costs nothing; the boolean remains derivable as `kind != "behavioral"`. **No new axis at all — preserve just `require-memory-skill.sh`'s and `require-routing-read.sh`'s existing two-label split** — rejected by the engineer, and independently by row 12: that split covers 2 of 26 hooks and, even for those 2, misses the `helper-proc` and `deny-encode` families row 20 censuses.

**The classifier's input contains agent-authored text, and that is an accepted, documented limit rather than a defended one.** Row 26 censuses the exposure: roughly twenty deny sites across nine hooks interpolate an agent-shaped value (`${COMMAND:0:200}`, `$TRUNCATED`, `$FILE_PATH`, `$RESOLVED`) into the message body, at both ends of it — `Read of '<path>' denied by …` puts agent text at offset zero, while `Command (truncated): <cmd>` puts it at the tail. An agent can therefore plant `failing closed` in a path or a command and push its own genuinely-behavioral denial into the `helper-proc` bucket. Scoping the marker search to the hook-authored span was weighed and rejected on that census: with agent text at both ends there is no single positional rule, so scoping would need a per-site boundary table — per-vector machinery for a soft, analytics-only harm.

The one shape-based heuristic available — ignore single-quoted spans — is unsound in **both** directions, and `block-gh-pr-merge.sh`'s helper-process deny demonstrates both at once. That message reads `Blocked: could not determine whether '<COMMAND>' invokes gh pr merge (status N) — sed/tr may be missing, killed, or errored. Failing closed per this gate's documented fail-closed posture rather than letting an unscanned command bypass the self-merge block.` An odd number of apostrophes inside the agent's own `$COMMAND` flips quote parity for the entire remainder of the message, so the hook's genuine `Failing closed` marker falls inside what the heuristic reads as a quoted span and is suppressed — a real `helper-proc` event silently recorded as `behavioral`. The hook's own `gate's` flips parity a second time for anything after it. So the heuristic does not merely leak agent text into the classifier occasionally; on this message it **undercounts infra**, which is the exact direction row 20 says the engineer's question is sensitive to. Hook prose containing apostrophes is not rare — `don't merge your own PRs` sits in the same file. G1 closes the remaining escape: the historical corpus already carries the interleaved shape permanently, so no emitted-side restructuring reaches the transcripts the analysis actually consumes. What ships instead is honesty at the right altitude — a `docs/transcript-analysis.md` caveat that names this as *adversarial* manipulation with a motive, kept separate from the accidental-false-positive sentence, and a test that pins the known shape (row 24).

The two extra labels therefore collapse into their hook's single `DENY_GATE_LABEL`, as originally designed. This holds up: the cause axis is strictly finer than the accident it replaces, and keeping both would make the two axes partly redundant and partly contradictory (row 12).

**Call-site reconciliation — strip-only by default, three named judgment families, and a total enumeration rather than a pattern hunt.** The lead-in is deleted; **the body text after it is preserved byte-for-byte**. The lead-in boundary is the first `: ` **or** the first sentence-ending `. ` that closes a gate-attribution clause, whichever comes first — several messages use a period rather than a colon there (`Read of '<path>' denied by env-read gate. Dotenv files…`, `Memory write blocked by ai-instruction-and-memory-files gate. You are writing to…`, `PR comment access blocked by respond-pr gate. Run the /respond-pr skill…`), and a colon-only rule has nothing to key on in those. A message with **no** gate-attribution lead-in at all (`gh pr command passes a body-source flag…`, `git commit passes a message-source flag…` — the sites alternative (c) recovers) gets the new lead-in prepended and **nothing deleted**; applying the strip there would destroy the message's first sentence. That default rule is what keeps the existing test suite largely unedited — `test_enforce_marker_script_shape.py`'s `"marker.sh invocation denied" in reason` and `test_deny_private_project_refs.py`'s body assertions all match text that survives.

Three families need judgment rather than a strip:

1. **Action-carrying lead-in.** A lead-in naming *what* was blocked (`Commit blocked by…`, `Memory write blocked by…`, `Agent spawn blocked by…`, `PR creation blocked by…`, `Marker write denied:`, `Read of '<path>' denied by…`, `Read of '<path>' denied:`) loses that action under a plain strip. The action moves into the body's first clause, with the gate attribution dropped and an em dash joining it to the surviving text. Two instances carry the action but **no** gate name at all and so match no attribution-shaped pattern: `deny-env-reads.sh`'s `Read of '<path>' denied: symlink target is unresolvable or missing. Fail-closed — …` and `Read of '<path>' denied: the symlink resolves to '<resolved>', whose basename matches a denied env pattern.` Applying the plain-strip default to these verbatim would delete `Read of '<path>' denied:` outright and drop the file path from the emitted message — the one fact that tells an agent *which* read was denied. They are family-1 sites and take the fold.
2. **Parenthesized disambiguator.** `require-worktree-for-file-writes.sh`'s `(file-writes)` moves into the body, because parentheses are outside `_DENIAL_HOOK_NAME_RE`'s `[\w .-]` capture class and a parenthesized label would classify as `unmatched`. It matters because both worktree hooks share the single label `worktree-enforcement`, so without it the two are indistinguishable in the emitted text.
3. **Gate identity restated inside the body.** Some bodies name the gate themselves, so a plain strip plus the new lead-in stutters. Disposition: **delete the clause that restates the identity the lead-in now supplies — a trailing `for <gate> gate`, or a `by (the) <gate> gate` attribution — and keep every other byte.** A mid-body sentence *about* the gate's reasoning (`Fail-closed — the env-read gate cannot verify what file would actually be read.`) is not a restatement of identity and stays. Verified instances of the trailing form: `block-gh-pr-merge.sh` and `deny-env-reads.sh`, both at their `_lib_parse_tool_input_or_deny` argument; the attribution form recurs across the `Read of '<path>' denied by the <gate> gate:` family in `deny-env-reads.sh`, `deny-credential-file-reads.sh`, and `deny-data-file-reads.sh`, where it overlaps family 1.

**Families 1 and 3 compose, and the fold wins.** Most family-1 lead-ins also name the gate, so both dispositions fire on one site. The rule is a single operation, not two: replace the whole lead-in with the action clause folded into the body, so the gate name disappears with the lead-in rather than being deleted a second time. `deny-env-reads.sh`'s `Read of '<path>' denied by env-read gate. Dotenv files commonly hold secrets;…` therefore becomes `Blocked by env-read gate: Read of '<path>' — Dotenv files commonly hold secrets;…`, matching the worked family-1 example below, **not** `Blocked by env-read gate: Read of '<path>' denied. Dotenv files…`, which is what a literal family-3-only reading would produce.

**The family assignment comes from a total enumeration, not from pattern-matching known shapes.** Dispatch 2's first step, before any edit, is a census of every deny-message argument in `claude/.claude/hooks/*.sh` — the first argument of `emit_deny`, of `require-worktree-for-git-writes.sh`'s `emit_deny_folding_fresh_lock_context` wrapper, of `_lib_parse_tool_input_or_deny`, and of `_lib_staged_length_gate` — with each assigned to exactly one of the four dispositions. Two shapes the enumeration must not lose: an argument passed as a variable rather than a literal (`require-worktree-for-git-writes.sh`'s `emit_deny "$reason"` inside that wrapper, whose real text is the wrapper's own callers' literals), and the `emit_deny() { _lib_emit_deny "$1"; }` re-point line present in all 26 hooks, which is a definition and not a call site. **Family-1 candidates are then the complement, not a pattern:** every enumerated literal whose text does not begin with the token `Blocked`. That rule catches the two `denied:` sites above by construction rather than by an implementer noticing them, and it catches a future site written in a shape nobody has thought of yet — which is the property a family-shaped grep cannot have. Family 3 keeps its own grep as a cross-check within the `Blocked`-prefixed remainder.

Worked examples, one per family plus the default:

- **Plain strip — emitted bytes unchanged.** `deny-private-project-refs.sh`'s quote-strip failure.
  Before: `Blocked by redaction gate: could not quote-strip the command text (exit 2) — sed/tr may be missing, killed, or errored. Failing closed rather than allowing an unscanned command.`
  After: `DENY_GATE_LABEL="redaction"`; call site passes `could not quote-strip the command text (exit ${COMMAND_UNQUOTED_EXIT}) — sed/tr may be missing, killed, or errored. Failing closed rather than allowing an unscanned command.`
  Emitted: identical to Before, byte for byte. This is the majority case, and the `failing closed` marker sits untouched in the body.

- **Family 1, action-carrying lead-in.** `deny-data-file-reads.sh`'s extension deny.
  Before: `Read of '/tmp/export.csv' denied by the data-file read gate: the '.csv' extension is a data-file shape that commonly holds PII/PHI. Reading it pulls the records into Claude's conversation context. …`
  After: `Blocked by data-file read gate: Read of '/tmp/export.csv' — the '.csv' extension is a data-file shape that commonly holds PII/PHI. Reading it pulls the records into Claude's conversation context. …`

- **Family 2, parenthesized disambiguator.** `require-worktree-for-file-writes.sh`'s collision deny.
  Before: `Blocked by worktree-enforcement hook (file-writes): Write targets '/repo/notes.md' — <collision reason>. This is a repo where worktree discipline is active (repo-level .claude/worktree-required committed, or your machine-level ~/.claude/worktree-required).`
  After: `Blocked by worktree-enforcement gate: file-writes arm. Write targets '/repo/notes.md' — <collision reason>. This is a repo where worktree discipline is active (repo-level .claude/worktree-required committed, or your machine-level ~/.claude/worktree-required).`

- **Family 3, identity restated in the body.** `block-gh-pr-merge.sh`'s parse-failure deny.
  Before: `Blocked: could not parse tool-input JSON for gh-pr-merge gate.`
  Naive strip-and-prefix (**wrong**): `Blocked by gh-pr-merge gate: could not parse tool-input JSON for gh-pr-merge gate.`
  After: `Blocked by gh-pr-merge gate: could not parse tool-input JSON.` — the `for <gate> gate` clause deleted, row 21's `could not parse tool-input JSON` fragment intact, so the classifier is unaffected. `deny-env-reads.sh`'s parse-failure deny takes the identical treatment.

**Field extraction — one `jq` call, six fields, split by one `read`.** The jq format string grows from two 0x1f-delimited fields to six: `.tool_name`, `.tool_input.command`, `.cwd`, `.session_id`, `.tool_input.file_path`, `.agent_type`. Splitting is a single `IFS=$'\x1f' read -r -d '' TOOL_NAME COMMAND CWD SESSION_ID FILE_PATH AGENT_TYPE _lib_parse_overflow <<< "$jq_out"$'\x1f' || true` — the trailing `|| true` is defensive: `read -r -d ''` returns non-zero at EOF-without-NUL on every invocation regardless of well-formed or shifted input (row 6), so without it a future hook that adopts `set -e` would abort on this call's own success path; `-d ''` is required because `COMMAND` legitimately contains newlines and a default-delimiter `read` would truncate at the first one; the appended sixth delimiter plus a trailing variable absorbs the herestring's own newline so no real field is polluted; `IFS` holds no whitespace, so no leading/trailing trimming occurs and today's byte-exact `COMMAND` preservation is retained. `mapfile`/`readarray` is the obvious alternative and is **forbidden in this repo** — `claude/.claude/scripts/tests/test_no_bash4_constructs.py:26-28` guards both tokens for bash-3.2/macOS compatibility. Parameter-expansion chaining is excluded by the master plan's own Verification bullet and does not generalize past two fields without a positional off-by-one.

**Folding introduces one new fail-open, and the same change must close it — with the trailing variable, not a jq guard.** Today a 0x1f byte inside `COMMAND` is harmless: `${jq_out#*$'\x1f'}` puts everything after the first delimiter into `COMMAND` regardless. Under a six-field positional split, an injected 0x1f shifts every later field — `CWD` becomes a fragment of the attacker's own command or a path to a different real repo, `git -C <fragment> rev-parse` fails or resolves somewhere unintended, `REPO_ROOT` ends up empty or wrong, and `require-code-review.sh:84-87` exits 0. That is a silent gate bypass created by this refactor.

The fix is the seventh `read` variable, which `read` fills with everything after the sixth delimiter. For a well-formed payload that is exactly the herestring's own trailing newline and nothing else; **any other content means a value carried a 0x1f and the fields shifted**, because a single injected delimiter necessarily raises the field count above six no matter which field carries it. `_lib_parse_tool_input_or_deny` denies on that condition before returning, so no caller ever reads a shifted global. This converts the delimiter-safety claim that `_lib.sh:218-221` currently only asserts ("Unit Separator cannot appear in a valid Claude Code tool name or shell command") into a checked precondition, at the cost of one parameter expansion and zero forks.

A per-field guard **inside the jq program** was the first design and is rejected on three counts. It is per-field, so a seventh field added in a later phase silently escapes it, where the count check covers a seventh field automatically and fails loudly if the jq field list and the `read` variable list ever diverge. It routes into the shared `$deny_msg`, making the phase's own headline security event — a deliberate field-shift bypass attempt — indistinguishable from a malformed harness payload and permanently classified `input-parse` (infra) rather than `behavioral`. And it forces a choice among jq builtins (`test()`/`match()` need the optional oniguruma module and would deny every tool call on a build without it), a constraint the count check does not have at all. The count check instead gets its **own**, pinned deny message (Dispatch 1) carrying none of the four cause markers, so it classifies `behavioral` by fallback with no classifier change. The one residual: a harness that somehow emitted a 0x1f legitimately would also file as `behavioral`; `_lib.sh`'s own comment is the standing claim that it cannot.

### Assumption ledger

**Root problem.** Sixteen gate hooks fork a second (and third) `jq` process to re-read fields the shared parser already had the payload for, and twenty-six hand-write their gate identity into every deny message in at least four inconsistent wordings — so a new field costs sixteen edits, roughly fifteen deny messages reach the agent with no identity at all and classify as `unmatched` in the repo's own denial analytics, and nothing in those analytics distinguishes a denial caused by agent behavior from one caused by a broken tool.

**Givens** (fixed beyond this plan's reach):

- **G1.** Analyzed transcripts are historical and immutable. Nothing this plan does can re-classify a denial already recorded, so `_DENIAL_HOOK_LABELS` can only grow or be re-annotated, never have a member removed, and any new classifier must key on text those transcripts already carry.
- **G2.** `mapfile`/`readarray` are unavailable: the repo targets bash 3.2 for stock macOS and mechanically forbids both tokens. The extraction mechanism must be expressible in bash 3.2.
- **G3.** Command substitution cannot carry NUL bytes, which is why 0x1f is the delimiter rather than the conventional `\0`. Bash strips NUL from `$(...)` output; this is a shell property, not an in-repo choice.
- **G4.** GH-499's `.cwd`-versus-`$PWD` resolution semantics are owned by a separate in-progress branch. Folding `.cwd` into the shared parser must preserve each hook's own existing `[ -z "$CWD" ] && CWD="$PWD"` fallback verbatim and freeze no answer to it.

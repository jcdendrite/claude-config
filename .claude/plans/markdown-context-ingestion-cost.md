# Markdown context-ingestion cost

## Context

Decide, on measurement, whether this repo should build a markdown retrieval mechanism to reduce how much markdown enters agent context. The repo and its stow consumers lean heavily on markdown — 42,141 bytes of always-loaded `CLAUDE.md` at `c3065ee` (9,687 repo-root plus 32,454 global; a machine's own `CLAUDE.local.md` adds to this and is not counted here), 418,140 bytes of skill bodies, 993,261 bytes of docs — and the opening hypothesis was integrating a markdown LSP so an agent could fetch one section rather than a whole file. Why now: the repo's own prose addresses documentation by section 407 times (`§N`, "see X's Y section") while offering no way to retrieve one, and nobody had measured what markdown actually costs. Intended outcome: a grounded decision about whether to build a retrieval mechanism, fix specific defects, change the always-loaded surface, or publish the measurement — with the measurement itself as a durable record so a later plan does not re-walk this ground.

Six discovery agents produced the evidence: the Claude Code and LSP surfaces verified at primary sources, a static inventory of this repo's markdown, a transcript measurement across 394–397 sessions, a cost re-weighting that corrected the metric, and a root-cause pass on subagent skill reads. Two findings reframed the question. First, the subagent-dominant read picture was an artifact of summing bytes across independent context windows; weighted by turn amplification it inverts. Second, the largest measured item is the always-loaded baseline, which is not a retrieval problem at all.

## Approach

**Fix the two verified fidelity defects, document the one CLAUDE.md-budget gap a commit-time hook structurally cannot see, publish the measurement into the two registers that already own this ground, and explicitly decline the markdown-LSP/section-retrieval mechanism.** The evidence does not support building a retrieval mechanism: the waste heuristic found no evidence of waste for a retrieval tool to recover, and the one lever that *is* the largest measured item (the always-loaded baseline) is not a retrieval problem at all.

State the size of this deliverable plainly rather than overselling it, and be precise about what "already fenced" means. The largest measured lever is the always-loaded baseline at 1.41× every main-thread markdown read combined, measured in **byte-turns**. What prior work fences is **lines**: `check-claude-md-length.sh` has capped both `CLAUDE.md` files at 200 lines since 2026-05-26. Those are different axes, and row 26 is the disproof sitting in this same document — commit `bdf5fcf` added 398 bytes with **zero** line-count change, growth the line cap could not see. So byte weight within the 200-line envelope is unwatched here; the sibling branch's byte gate addresses it on a different branch, and trimming is owned by that same effort. The posture stays "note it, don't act" per the engineer's explicit instruction — but the lead must not imply the lever is contained when only one proxy for it is.

What remains here is **two instruction fixes** (Phase B's read-then-discard ordering, Phase C's ledger-instruction inlining), **one doc-consistency assertion** (Phase D), and a durable record of the measurement. The cross-PR accumulation gap is documented and left open — see row 27 for why the existing mechanism cannot close it.

### Why not the mechanism (over-powered-primitive check, the headline call)

A markdown LSP cannot do the job even if built. **No LSP request returns document text** — `documentSymbol` returns `{name, detail?, kind, range, selectionRange, children?}`, ranges and labels only. A markdown language server could hand back the line range of `§37` and nothing else; retrieving the section would still require a `Read` with `offset`/`limit`. The mechanism is not a cheaper read path; it is a locate step wearing a plugin, a third-party server, and a `.lsp.json` dependency that is inert in cloud sessions.

Two lighter primitives already do this, and one of them is already mandatory:

1. **`Grep '^#{1,6} '` on the target file, then `Read` with `offset`/`limit`.** This reproduces `documentSymbol`'s heading ranges *and* returns the text, in two calls, with zero infrastructure. I used exactly this inside this dispatch: one `Grep` for `^## ` on `docs/cost-levers-considered.md` returned all 24 H2 line numbers, and one ranged `Read` retrieved the two sections I needed out of a 48,882-byte file. It fails only in that the section terminator is judged rather than parsed — which the `§N` convention already makes unambiguous.
2. **`Read` with `offset`/`limit` against a known `§N`.** Cheaper still when the citation already names the target, which is the shape of most of the 407 durable section references.

Both are covered by the global `CLAUDE.md` rule "Locate before a whole-file read," adopted on measurement in `docs/case-studies/targeted-read-discipline.md`. So the heavier mechanism is not merely unjustified — the lighter one is already required, and `targeted-read-discipline.md` additionally *declined a `PostToolUse` Read hook* on the ground that advisory context injected on every `Read` call "spends context to save context." A section-extract helper faces the same objection one level down, plus a new-dependency decision (`mdast-util-heading-range` is Node with no npm toolchain here; `markdown-it-py`/`mistune` give heading tokens but no section utility).

### Answering the two ideas the engineer named

**"Have `code-writer` read those important skills ahead of time" — refuted by the measurement, not merely unattractive.** Across 812 dispatches with ≥2 markdown reads, all 812 favor observed-spread over preload-at-turn-1; zero favor preload, and no crossover exists. Under byte-turns, turn-1 loading maximizes remaining-turns for the entire payload. The `code-writer` case compounds it: its `test-conventions` read is *correctly conditioned* and fires on only 20% of dispatches (`code-writer.md:37`), so a `skills:` preload would pay full cost on 100% of dispatches to save on 20%. One axis is honestly unmeasured — preload avoiding a *second* full read of the same file — and that is recorded, not resolved.

**"What's the difference between reading a skill and invoking it?" — almost none in-turn, and the difference that exists favors invoking.** Both put the full rendered body into the conversation as a message that persists; Claude Code does not re-read a skill file on later turns. The asymmetry is at compaction: invoked skill bodies are re-injected capped at 5,000 tokens per skill and 25,000 total, while read files are re-read for at most five paths and **a file over 5,000 tokens comes back as a path reference without its content**. So a `Read` of the 63,714-byte `code-review/SKILL.md` survives compaction as a bare path; an invocation of it survives as its first 5,000 tokens. That is a real difference, but it is not a cost reduction — the in-turn byte cost is identical, so switching agents from `Read` to `Skill` saves nothing. The governance worry is also correct and worse than feared: `tools:` omitting `Skill` disables skill invocation *entirely*, and no per-skill allowlist is documented. There is no selective-restriction surface. Idea closed.

`context: fork` is a genuine reduction mechanism — only the subagent's result returns — but it is wrong-shaped for every surface measured here, because the forked skill "won't have access to your conversation history." `code-review`, `plan-review`, and `handoff` are exactly the skills that need it.

### What we do instead

**Phase A — publish, and evaluate the pre-registered triggers.** The measurement's home already exists: a section in `docs/cost-levers-considered.md` (the register whose stated purpose is "so a seventh plan doesn't re-measure ground already covered") plus a full empirical record in `docs/case-studies/`, following the pattern of five existing entries. Phase A also runs the one piece of genuinely valuable additional data, at the cost of a single existing command: `targeted-read-discipline.md` shipped four numeric revisit triggers, all re-derivable via `transcript-analysis.py read-scope`, and nobody has evaluated them since the 2026-08-10 snapshot. **The new figures do not evaluate them** — 32.3% targeted is markdown-only and main-thread-only; the trigger is defined over all `Read` calls in all scopes against a 45.6% baseline. Comparing them directly would repeat precisely the denominator error that case study was written to correct.

**Phase B — `skill-fidelity-reviewer`'s read-then-discard ordering.** F2 and F3 are one defect, not two. Name resolution (`skill-fidelity-reviewer.md:62-68`) instructs a `Read` of *every* label's body, and both filters that would avoid the read run afterward: the out-of-scope list and the decidability test at line 77. That single ordering explains `handoff/SKILL.md` being read whole 43 of 44 times and dismissed one step later, *and* the 44 unsanctioned whole-file reads of `code-review/SKILL.md` — a file the agent is told to exclude "for every question except the one named below," whose only sanctioned read is the targeted one at line 93. The fix is one edit: resolve existence with `Glob` (the agent holds it), apply the out-of-scope and decidability filters, and `Read` a body only for skills that survive both. This is a correctness fix first — the agent currently spends a whole-file read to reach a verdict its own text says needs no body.

**The filter must early-exit only on a confident name match, never on an unfamiliar skill.** The out-of-scope list and the enumerated undecidable exemplars (`branch-management`, `subagent-delegation`, `handoff`, `brief`, `pr-description`, `respond-pr`) are baked into the agent's own prompt, so classifying those needs no body. A skill *not* on either list is different: judging whether its output is diff-visible genuinely requires reading it. A bare "filter before read" instruction would invite guessing "undecidable" for an unfamiliar skill without inspecting it — and that dismissal is indistinguishable in output shape from a correctly-reasoned one, so the regression would be silent in exactly the property this agent exists to protect. The edit therefore states explicitly that decidability defaults to reading the body whenever the label alone cannot settle it.

**Phase C — `plan-review/ROUTING.md`'s ledger cross-check.** Line 55 says to "include this instruction in every spawned reviewer's prompt," and sampled dispatches carried a pointer instead. This is a fidelity bug with a cost side-effect, not the reverse: a specialist that opens ROUTING.md to resolve the pointer pays for a 16,743-byte file (#4 under byte-turns, up from #12 by raw bytes), and one that doesn't may run the wrong check. The fix makes the inlining obligation unmissable at the spawn step rather than stated once in a subsection.

**Phase D — pin the hook's limit to its prose claim; the cross-PR accumulation gap is documented, not closed.** The 200-line cap is **already enforced**, and the plan must not claim otherwise: `claude/.claude/hooks/check-claude-md-length.sh` has gated it at commit time since 2026-05-26 (`GH-315`), wired at `claude/.claude/settings.json:262` as a `PreToolUse` hook on `Bash(git commit *)`, with its own test suite at `claude/.claude/hooks/tests/test_check_claude_md_length.py`. `ai-instruction-and-memory-files/SKILL.md:53` says so directly.

The residual gap is structural, not a bypass. `_lib.sh:1066-1069` compares the staged file against **the committing branch's HEAD**, so two concurrent PRs each taking the file 184→194 both pass legitimately, and whichever squash-merges second lands 204 on main. A commit-time hook cannot see across PRs by construction; a check that runs on the merged result can. Secondary residual: commits authored outside Claude Code, or by contributors who never ran `./install.sh`.

**The accumulation gap is recorded and left open, because the existing hook cannot be made to close it.** Three test designs were attempted across two review rounds and each failed on a different axis: an empty HEAD makes `old=0`, so the check reads as a flat cap and goes red against the incoming 25,600-byte gate; seeding HEAD with the committed content makes `new == old`, so `_lib.sh`'s `new -gt old` is false and the deny branch cannot fire — the test then passes whether `limit_for` returns 200, 0, or the comparison is inverted; and seeding HEAD plus a growth delta stops testing the real files at all and re-tests hook logic that `test_check_claude_md_length.py`'s synthetic fixtures already cover.

The common cause is a category mismatch, not three separate mistakes. `_lib_staged_length_gate` is a **ratchet**: it answers "did this grow?", never "is this within budget?". No arrangement of its inputs yields a threshold answer about the current files. Closing the accumulation gap needs a merge-base comparison, which belongs in CI rather than pytest and whose `origin/main` freshness dependency is a flake source in the worktrees this repo uses constantly. That is a separate piece of work with its own design question, and inventing it here would be the fourth attempt at a shape that has already failed three times.

**What Phase D ships instead is one assertion**, on a mechanism with no ratchet in it: a `DocCountFact` tying the hook's actual limit to the `200` claimed in `ai-instruction-and-memory-files/SKILL.md:46`. Only the prose *sentence* is pinned today (`test_skills.py:577`), so lowering `limit_for` would leave that doc claiming 200 with every test green — a gap that goes live the moment the in-flight trimming effort touches the limit. Scope the `Occurrence.pattern` to the word "lines" specifically, not a generic "under N X per CLAUDE.md file" shape, so the sibling branch's incoming byte paragraph cannot produce a second match.

The all-PRs-blocked failure mode is real but bounded, and the plan should not overstate it: CI runs the full suite on nearly every push, so a breach fails every open PR — but any PR bringing the file back under the limit passes, so the fix unblocks itself. There is no deadlock. The escape hatch for a longer trim already ships: `limit_for`'s case structure accepts a per-file override, so a maintainer can set it to the current count, trim across several PRs, then lower it.

This is deliberately *not* the "trim the always-loaded surface" lever, which is out of scope and owned elsewhere.

**Phase E — dropped, decided now rather than deferred.** The original draft made a `--weight-by-turns` flag on `read-scope` conditional on "if the diff is running long," which names no metric and would let two implementers reach opposite conclusions from identical text. Deciding it here: **drop.** `targeted-read-discipline.md` already asserts the qualitative version of the finding ("a token saved there is worth less than one saved on the main thread"), so the flag would quantify a conclusion the register already carries; the register's majority convention is one-off scans labelled as such; and the proposed acceptance criterion — reproducing the 0.78× ratio — is not checkable by anyone else, since it depends on this machine's 11-day local corpus that no contributor and no CI run has. Phase A satisfies the grounding rule by naming the scan non-rerunnable. Recorded in **Out of scope** with the trigger that would reopen it.

### Assumption ledger

**Root:** Markdown ingestion cost is real but is not a retrieval problem — the largest measured item is an always-loaded surface with no growth control, and the reads that *are* addressable are addressable because they are instruction defects, not because whole-file reading is wasteful.

**Givens** (fixed beyond this design's reach):

- **G1.** No LSP request returns document text; `documentSymbol` and siblings return ranges and labels only. Vendor/protocol-owned (LSP specification).
- **G2.** Claude Code's `LSP` tool activates only via a plugin shipping `.lsp.json` at its root, and is inactive in cloud sessions. Vendor-owned.
- **G3.** Compaction rate is not measurable from the transcript schema — no `compact_boundary` record observed, and the available proxy cannot be distinguished from ordinary cache invalidation. Vendor-owned schema.
- **G4.** The session-start baseline is capped at n=10; only 10 sessions carry the full startup attachment bundle, confirmed independently twice. Downstream of G5 — the sessions that would widen it have already been deleted.
- **G5.** The corpus holds 11 days of history (2026-08-25 → 2026-09-05). Retention itself is *not* vendor-owned — it is `cleanupPeriodDays`, a settable Claude Code field defaulting to 30 days (`docs/cost-ledger.md:6`, `docs/pr-cost.md:3`). What is beyond reach is only the deletion that has already run: transcripts outside the window are gone, and no setting recovers them, so this measurement's window cannot be widened retroactively. Raising the setting to widen *future* corpora is a change this plan could make and declines — see **Out of scope**.
- **G6.** The repo declares `pyyaml==6.*` and no markdown parser, and has no npm toolchain. Adding either is a new-dependency decision requiring the engineer's confirmation under `CLAUDE.md` Safety — outside this plan.

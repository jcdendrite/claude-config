# Sentinel config migration

## Context

claude-config's file-based sentinel/marker scheme — 17 rows in `install.sh`'s
`SENTINEL_INVENTORY`, each a standalone presence- or content-checked file
under `$CLAUDE_CONFIG_DIR` — has already produced one confirmed bug: a
CRLF-authored `pr-cost-disclosure` sentinel reports `ENABLED` via
`install.sh`'s `[:space:]` trim but publishes nothing via
`pr-cost-section.sh`'s `[:blank:]` trim, because two independent parsers of
the same file have silently diverged. A structurally identical divergence
exists one level down: `CLAUDE_CONFIG_DIR` itself is resolved to an absolute
path by three independent implementations (`_lib_config_dir` in bash,
`config_dir()` in Python, and `install.sh`'s own inline copy, since
`install.sh` runs standalone before `_lib.sh` is stowed into place). Rather
than patch the one instance, this plan replaces the scheme's per-sentinel
state resolution with a single shared config file and one parser per
language runtime, so this whole class of divergence becomes structurally
impossible rather than individually re-patched. This supersedes the
narrower, already-reviewed-but-unimplemented
`.claude/plans/sentinel-trim-grammar-alignment.md` plan (commit `6457e07`,
branch `sentinel-trim-grammar-alignment`), which this plan recommends
abandoning once this one is approved.

The intended outcome: a config file anchored at `$CLAUDE_CONFIG_DIR` (not the
stow tree — `docs/design-decisions.md` #43 already established that a
stow-distributed file can't express a genuinely per-machine/per-account
toggle, since it's identical bytes for every consumer), in a format that
preserves the human-hand-editable `docs-anchor` convention the current
sentinels carry, with one parser every consumer — bash hooks, `install.sh`,
Python scripts, and skill-body prose via a new query CLI — reads through.

Engineer-confirmed scope decisions this session:
- Preserve each sentinel's current resolution semantics (union of
  `$CLAUDE_CONFIG_DIR` and legacy `$HOME/.claude` for `worktree-required` /
  `autonomous-shipping-required`; single resolved path, no union, for
  everything else) — the schema carries a resolution-mode field rather than
  standardizing on one rule.
- Fold `.authorization-boundary-disabled` into the new schema. It's a
  machine-scope kill switch shaped identically to the 17 inventoried
  sentinels but missing from `SENTINEL_INVENTORY` today.
- Ship a small query CLI (e.g. `claude-config get <key>`) for non-code
  consumers — currently `pr-description/SKILL.md` and (found during
  `/plan-review`) `transcript-analysis/SKILL.md:89`, both of which instruct
  the agent to check a sentinel's presence directly in prose — rather than
  teaching skill bodies the new file's internal format.

## Approach

Replace the 14 machine- and account-scope sentinel files with **one hand-editable state file per config dir** (`<config-dir>/claude-config.toml`) plus **one in-repo schema data file** (`claude/.claude/hooks/config-keys.psv`) that declares every key's type, default, resolution mode, and legacy-file mapping. Every consumer — bash hooks, `install.sh`, Python scripts, and skill prose via a new `config-get.sh` — resolves state through one reader per language runtime, and a differential test pins the bash and Python readers to byte-identical verdicts over a shared fixture corpus. The four repo-scope committed markers stay files. The current sentinel files keep working forever as a schema-declared legacy fallback, so nothing silently goes dark on `git pull`.

The divergence this closes has two layers. The `[:space:]`/`[:blank:]` trim bug is the *content-grammar* layer: `install.sh:531-547` and `pr-cost-section.sh:18-24` each re-derive "what does this file's content mean." Under the new design that grammar exists once — the schema declares `pr_cost_disclosure` as `enum:dollars` and both call sites ask `_config_value` / `config_value()`. The config-dir resolver is the *path* layer, and it has **five** implementations, not three: `_lib.sh:110`, `_config_dir.py:22`, `install.sh:525-528`, `plugins/skill-management/hooks/_lib.sh:29`, and `plugins/lovable-cloud/lib/token-path.sh:18-22`. This plan collapses the first three to one bash definition plus one Python definition; the two plugin copies are a given (G1) and stay out of scope.

Two design calls are worth stating up front because they change observable behavior, both deliberately:

**Key polarity flips to positive sense.** `polarity: opt-out` exists in today's schema only because file-absence cannot express "on by default." A key-value file can, so `pr-description-tighten-prose-optout` becomes `pr_description_tighten_prose = true` (default `true`) and every `*-disabled` kill switch becomes a positively-named capability defaulting to `true`. The concept `polarity` disappears from the new file entirely; it survives only as a `legacy-polarity` column describing what the old file's presence meant. Inversion is the obvious hazard, so the schema is the single place the flip happens and a table-driven test asserts every key's effective value across the (legacy present/absent × key declared/absent) matrix against today's behavior.

**`install.sh` writes to the resolved config dir, not `$HOME/.claude`.** Today `configure_machine_level_opt_ins` (`install.sh:394`) always writes `$HOME/.claude/$path_template`, while four of the six promptable keys are read from the resolved config dir with no union — so on a machine with `CLAUDE_CONFIG_DIR` set, answering `y` to the PR-cost-ledger prompt writes a file nothing reads. This is the same write-path/read-path mismatch family as the trim bug, and leaving it in place would make the migration import a silent no-op for those keys. Writing to the resolved config dir is a no-op when `CLAUDE_CONFIG_DIR` is unset and a fix when it is set.

**Agent-mediated writes to the config file are hook-denied; human hand-edits are not.** `/plan-review` (`ciso-reviewer`) found that consolidating 14 toggles into one file, plus the query CLI's missing `set` subcommand, doesn't close the self-authorization gap it targets. Nothing stops an agent from sourcing `_config.sh` and calling `_config_set` directly, or from using the `Write` tool on the file's bytes directly. Consolidation also raises blast radius: a single write can now touch any of the 14 keys, including the five enforcement-critical ones (`worktree_required`, `autonomous_shipping`, `round_consult_gate`, `commit_stall_block`, `authorization_boundary_restore`). Both close with one fix: a new dedicated hook, structurally mirroring `enforce-marker-script-shape.sh`'s existing path-shape gate (which already denies non-`marker.sh` Write/Edit/MultiEdit and Bash writes to `*-markers/`/`.*-active.d/` paths), that denies Write/Edit/MultiEdit writes to the resolved `claude-config.toml` path and Bash commands invoking `_config_set`. This blocks only Claude-Code-tool-mediated writes — a human editing the file directly with their own editor, outside Claude Code, is unaffected, preserving the file's hand-editable design goal while closing the self-authorization path. `install.sh`'s interactive `[y/N]` prompt path (`_prompt_sentinel_opt_in`) is unaffected in practice: it already gates on `[ -t 0 ]` (row 9), and a Claude Code Bash tool call carries no attached TTY, so this path was never reachable from an agent's own Bash tool call to begin with.

**Round 2 (`ciso-reviewer`) found the Bash arm above, as first designed, insufficient: a name-scan for `_config_set` alone.** `claude-config.toml`'s format is a trivial hand-editable `key = value` grammar with no hashing or structure (row 8), so an attacker gains nothing from calling `_config_set` specifically. `printf 'autonomous_shipping = true\n' >> ~/.claude/claude-config.toml` contains no `_config_set` substring, yet it reproduces round 1's gap for all five enforcement-critical keys with no function call at all. The fix is the same shape as the marker hook's *actual* defense against raw writes: `enforce-marker-script-shape.sh`'s Bash arm closes this not through its `marker.sh`-name scan (Stage 1/2) but through a separate redirect/utility-write candidate scan (`_bash_marker_redirect_candidates`/`_bash_marker_fragment_candidates`, run *ahead of* the name scan) that extracts every `>`/`>>`/`tee`/`cp`/`mv`/`dd of=`/`sed -i` write target in a command and shape-tests each one against the protected path, independent of whether the command mentions `marker.sh` by name. The new hook's Bash arm needs the equivalent: a redirect/utility-write candidate scan targeting the resolved `claude-config.toml` path, run in addition to (not instead of) the `_config_set` name-scan (row 27). With this fix, the write surface is fully enumerated for Claude-Code-tool-mediated writes; a script-file-indirection vector (`printf ... > /tmp/x.sh && bash /tmp/x.sh`) remains — the same inherited limitation `enforce-marker-script-shape.sh`'s own header already accepts for `python3 -c "open(...).write(...)"` and here-doc bodies, disclosed rather than fixed (row 28).

**DRY: the candidate-resolution engine is shared logic, not copied logic.** `ciso-reviewer` flagged that describing the new hook as "mirroring" the marker hook's shape-matching and redirect-scanning functions means hand-copying ~90+ lines of intricate, security-critical logic (nocasematch scoping, realpath-budget bookkeeping, config-dir-aware shape variants) into a second file — two independently maintained copies of exactly the kind of fact this migration exists to stop duplicating, one layer up from config values. The two hooks stay separate files (folding config-write gating into `enforce-marker-script-shape.sh`'s charter — "guard review-marker state" — would blur its single responsibility and further bloat an already ~740-line file), but the shape-matching engine (`_marker_shape_match`) and the redirect-candidate-extraction pair move into `_lib.sh` as primitives parameterized by the protected-path pattern(s), with both hooks calling the shared primitive (row 29).

**`config-keys.psv` governs the same enforcement-critical resolution logic the new hook protects at runtime, but sits outside its scope.** The schema file is git-tracked and stow-distributed, not per-machine state, so the new hook correctly doesn't gate it — a change lands only via a committed, PR-visible diff. But nothing currently requires the same reviewer scrutiny already mandated for the hook file: a change to `autonomous_shipping`'s `legacy-probe-on-resolution-failure` from `false` to `true` is exactly the shape of change row 18 itself calls "a live self-authorization risk," yet only ordinary code review would catch it. `claude-hook-review` is required on any PR touching `config-keys.psv`'s `resolution` or `legacy-probe-on-resolution-failure` columns for the five enforcement-critical keys — a review-process addition matched to this file's git-native threat model, not a hook (row 30).

**Legacy-file precedence is explicit for all fourteen keys, not just the two union keys.** Row 4's OR-union covers `worktree_required`/`autonomous_shipping` only. For the other twelve, once a key has any row in the state file, that value is authoritative — the legacy file is consulted only when the key is entirely absent from the state file. This closes a `/plan-review` gap (`ciso-reviewer`, Finding C): without an explicit rule, a legacy file re-created or hand-edited after migration (a stale doc, a script that still knows the old filename) could silently win over, or silently lose to, an explicit post-migration state-file value with no defined outcome either way.

**The one-time legacy import also checks `$HOME/.claude` for keys the schema marks `config-dir-and-home` in a new `legacy-import-locations` column, and only ever writes a key once.** An engineer consult during `/plan-review` found this paragraph originally hardcoded "the six config-dir-only keys." That count doesn't reconcile with the schema (12 config-dir keys total), and it misstates why `pr_cost_disclosure` specifically needs the two-location check — `pr_cost_disclosure` is account-scope, never touched by the write-path bug this paragraph cites. Both are a live instance of the "two re-derivations of one fact" bug class this migration exists to close, one level up. The fix is schema data, not a recounted sentence: `config-keys.psv` gains a `legacy-import-locations` column (`config-dir` | `config-dir-and-home`) per key, derived per key during the row-15 audit (row 40) rather than asserted as a fixed count in prose. For whichever keys the audit marks `config-dir-and-home`, the write-path bug above means a diverged-`CLAUDE_CONFIG_DIR` user's prior opt-in may physically exist only at the buggy `$HOME/.claude` location — a location the corrected config-dir-only resolution semantics never reads from going forward. The one-time import pass is a read-only recovery step, distinct from post-migration resolution: it checks both `$HOME/.claude/<path>` and the resolved-config-dir legacy path for each `config-dir-and-home` key and treats either as "legacy value present," so a real prior opt-in isn't silently discarded as a false "never configured" (`staff-platform-engineer` finding). Import also writes a key's legacy-derived value only on first encounter — once a key has any row in the state file, whether from import or a hand-edit, no later `install.sh` run touches it via the legacy path again, so a hand-edit to the hand-editable file survives a re-run (`staff-platform-engineer` finding).

**The legacy-import/scaffold/report logic is a standalone script `install.sh` executes, not inline `install.sh` code — an engineer-requested revision confirmed via a `plan-architect` consult.** The non-interactive phase (import, then scaffold per row 34, then a per-file report) moves to `claude/.claude/scripts/migrate-legacy-config.sh`, executed by `install.sh` (matching the existing `register-marketplace.sh` precedent, `install.sh:621`) rather than sourced — sourcing would turn on `set -u`/`pipefail` for the rest of `install.sh`, fatal on an empty array under macOS system bash 3.2 (`install.sh:99-101` already documents this exact reason for a sibling script). `install.sh` calls it with `|| echo "[install] warning: ..."` (matching `install.sh:667`'s existing shape), since a failed migration must not abort the rest of the installer. This buys a real test seam for row 34's ordering invariant — `subprocess.run([script], env={HOME, CLAUDE_CONFIG_DIR})` exercises the real call sequence directly, rather than fighting the `INSTALL_TEST_FIXTURE` block-extraction harness `install.sh` needs today because its own header says never to `source` it — and gives stow users a one-command way to materialize `claude-config.toml` between full `install.sh` runs, relevant because G3 means code goes live on `git pull` but state doesn't (row 35).

**The script also prompts, per legacy file, to delete it after import — a second engineer-requested revision, confirmed via a further `plan-architect` consult.** Modeled on `install.sh`'s existing `_report_and_clean_stale_migration_copy`/`_prompt_delete_stale_migration_copy` pair (`install.sh:138-172`), which already solves the structurally identical problem for a stale migration copy: the non-interactive import/scaffold phase reports every legacy file found, then a per-file `[ -t 0 ]`-gated prompt shows what key/value was derived from that file and asks `[y/N]` (default No) whether to delete it now, leaving it in place on a non-TTY invocation with a message to re-run from a terminal. This TTY gate is **hang-prevention, not a security control** — worth stating explicitly, since nothing today stops an agent from running `rm` on a legacy sentinel directly (the new write-gating hook's redirect/utility-write scan covers write-shaped operations only, never `rm`), so recording this gate as the thing that closes a bypass would be the same unsupported-closure-claim defect `/plan-review` round 2 caught in rows 9 and 10. Two safety conditions on the offer itself, both required: (a) never offer to delete a key's legacy file when that key wasn't actually imported this run — it already had a state-file row, so the existing row may hold a different value than the file, reachable under rows 19 and 22; (b) never offer `$HOME/.claude/worktree-required` at all, engineer-confirmed. Row 18's `legacy-probe-on-resolution-failure: true` keeps that file load-bearing as a resolution-failure fallback after migration — deleting it would flip a fail-closed degraded state to fail-open for the one key designed to fail closed (row 42). Row 12 is rewritten, not deleted, to reflect confirmed per-file interactive deletion as the new default shape, with the copy-pasteable `rm` retained only for `worktree_required`'s legacy file.

**Import itself is also gated for the five enforcement-critical keys — a `/plan-review` round-4 finding, not an engineer request.** `ciso-reviewer` traced that row 36's original safety argument ("the script grants no authority a present legacy file doesn't already grant") holds only for what value is achievable, not for how hard that value is to reverse: promoting a legacy value into a state-file row makes it *harder* to reverse than the raw legacy file, since the new write-gating hook then denies every later Claude-Code-mediated attempt to flip it back. Because no hook today gates writes to the legacy kill-switch files themselves, an agent can plant one. On any machine that has pulled this migration's code but not yet run `install.sh` — a state G3 treats as expected, not narrowly transient — the agent can then entrench that planted value in one non-interactive script call with zero confirmation. Row 45 closes this the same way row 42 closes the delete-side risk: the import step for the five enforcement-critical keys requires the identical `[ -t 0 ]`-gated confirmation before writing, skipping the import entirely (not performing it silently) on a non-TTY invocation. Unlike row 42's gate, this one is doing real security work, not hang-prevention — it is the only thing standing between an agent's Bash tool call and an irreversible-via-Claude-Code write for exactly the five keys this plan's own row 30 already flags as needing elevated scrutiny.

**Consumers migrate before `install.sh`'s writer, reversing the original phase order.** `/plan-review` (`staff-platform-engineer` B9, `staff-backend-engineer` B3) found the original install.sh-then-consumers order unsafe if the two phases reach `main` as separate merges. A user opting in via the migrated `install.sh` before consumers read the new file gets a silent no-op — the exact write/read mismatch this plan exists to close, reproduced transiently at the phase boundary. Consumers depend only on Phase 1's reader and its permanent legacy fallback (row 11), so migrating them first is safe with the state file entirely absent: the fallback carries every key through unchanged. `install.sh`'s writer therefore lands last, after every reader already understands the new file. **Phases 1–3 land as sequential commits on one branch/PR, never as independently merged PRs** — `/plan-review` round 2 (`staff-platform-engineer`) found the ordering was enforced by prose only ("must land before," "do not land ahead of"), which a contributor working from the Critical Files list in isolation, or cherry-picking the smaller Phase 3 diff first, could violate with no mechanical check catching it. Stating the single-PR constraint explicitly, rather than adding new CI machinery, matches this plan's own minimal-change discipline for a solo/near-solo-team repo.

### Assumption ledger

**Root:** Every machine-level toggle in this repo is a bare file whose location, presence semantics, and content grammar are re-derived independently by each consumer, so any two consumers of the same toggle can disagree — one confirmed instance shipped (`pr-cost-disclosure` reports `ENABLED` and publishes nothing), and five independent config-dir resolvers plus twelve independent presence checks are the remaining surface.

**Givens:**

- **G1 — Marketplace plugins cannot source the stowed library.** `plugins/skill-management/hooks/_lib.sh:2-14` and `plugins/lovable-cloud/lib/token-path.sh:13-22` each carry their own config-dir resolution because a plugin installed without this repo stowed has no `~/.claude/hooks/_lib.sh` to source. The plugin distribution boundary is Claude Code's, and repo `CLAUDE.md` ("Plugin skills must stand alone") already fixes it as policy.
- **G2 — `install.sh` runs before stow exists.** It can only source by repo-relative path (`$REPO_DIR/...`), never `~/.claude/...`. Its own purpose is creating those symlinks, so the ordering is not this plan's to change.
- **G3 — `claude/.claude/**` goes live on `git pull` with no re-install** (repo `CLAUDE.md`, "Working in this repo"). Hooks therefore update on a pull that never runs `install.sh`, so a read path that requires a completed migration would silently drop enforcement for every stow consumer.
- **G4 — bash 3.2 floor, no `declare -A`** (`install.sh:406-407`). Apple's system bash imposes it.
- **G5 — Python 3.11 floor** (`install.sh:30-35`), already enforced at install time.
- **G6 — No first-party Claude Code mechanism covers this.** Plugin `settings.json` supports only `agent` and `subagentStatusLine`, and its root is never `~/.claude/`; Claude Code's own `settings.json` is strict comment-free JSON and is vendor-schema-owned. Vendor-imposed, established by this session's verify-sources pass.

**Mechanisms (over-powered-primitive check):**

- **New on-disk state file format** — `anchors: root`. Two lighter primitives rejected: (a) keep one file per key and add only shared readers — this closes the parser divergence but leaves `install.sh`'s writer creating N files whose names are a duplicated constant across 12 hooks, and gives the human no single surface for the query CLI that Step-4 answer 3 requires; (b) store the keys in Claude Code's own `settings.json` — rejected on G6, since the file is vendor-schema-owned (a future first-party key could collide) and comment-free, which kills the `docs-anchor` convention the file must carry.
- **Two runtime readers rather than one** — `anchors: row7`. The lighter primitive is a single Python reader that bash hooks shell out to; rejected because `require-worktree-for-file-writes.sh:134` fires on every Write/Edit and today does a bare `[ -f ]`, and this repo already treats per-fire subprocess spawning as a cost worth engineering around (`advance-past-commit-stall.sh:58-67` exists specifically to "skip spawning jq for the common case"). The second lighter primitive — two hand-maintained copies pinned by an equality test, the pattern `test_require_skill_review.py:849-876` already uses — is rejected for the *schema* (a data file makes divergence structurally impossible rather than test-caught) but is exactly what the differential test provides for the *parsers*, where a shared file is not available across runtimes.
- **Pipe-delimited schema rather than TOML for the in-repo file** — `anchors: row6`. Two lighter, simpler-than-TOML alternatives considered and rejected: (a) reusing the state file's TOML grammar for the schema too — rejected because a schema row is a fixed-arity record needing tables or arrays, which a bash TOML-table parser would need strictly more machinery to read than `IFS='|' read -r` already provides, and (b) a bare space- or comma-delimited row — rejected because several columns (`human-name`, `prompt-description`) are free-text that can itself contain spaces or commas, while `|` is already reserved and excluded from every current sentinel's human-readable fields. `install.sh:392` already uses `IFS='|' read -r` and `test_install_sh_sentinel_inventory.py` already covers it, so the pipe-delimited choice is both the lighter and the already-proven option, not a compromise between two heavier ones.
- **Query CLI as a script rather than prose** — `anchors: row13`. Lighter primitives: teaching `pr-description/SKILL.md` the file format (rejected by Step-4 answer 3, and it re-creates a parser in prose that nothing tests), or one script per key on the `autonomous-shipping-active.sh` model (rejected — N scripts, each re-embedding a path constant).
- **New dedicated hook for config-write gating, rather than extending `permissions.deny` or relying on the default permission prompt** — `anchors: row17`. Two lighter alternatives rejected: (a) rely on Claude Code's default per-call permission prompt with no repo-level hook — rejected because a permissive allow-list or a human clicking through prompts leaves exactly the self-authorization gap `/plan-review`'s `ciso-reviewer` flagged, unenforced by anything mechanical; (b) a `permissions.deny` glob on the config file's path — rejected because `permissions.deny` matches file-write tool calls only, not Bash command text, so it cannot close the `source _config.sh && _config_set ...` vector, and this repo's `review-permissions` skill already discourages broad path-glob deny rules.

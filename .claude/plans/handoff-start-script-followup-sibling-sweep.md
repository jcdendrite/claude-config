# Separate handoff's pre-write recipes, default deferrals to a documented limit, sweep review-fix siblings

## Context

Three recurring error modes surfaced by an error-mode analysis of this repo's review traces get their cheapest fix each, in one PR. First, the handoff skill presents its two pre-write commands (marker activation and handoffs-directory creation) as adjacent one-line recipes, and agents fuse them into one Bash call that the marker-shape gate denies. The analysis found that fusion recurring. Second, agents propose or file follow-up issues by default, and the engineer has pushed back on such proposals. Third, when a PR reviewer flags a design distinction at one site, respond-pr fixes only that site and replies FIXED while the same distinction survives at sibling sites, so the reviewer re-raises it comment after comment. The intended outcome has three parts:
- A handoff recipe whose two pre-write commands no longer sit adjacent, with the marker activation kept as the routine first step and run as its own Bash call.
- Deferral dispositions in code-review and respond-pr that accept a documented limit in place of a ticket.
- One respond-pr step that sweeps siblings before replying FIXED.

Ask: "yeah that sounds great actually, go do that" — accepting the session's own proposal (session wording, not the engineer's): "plan the first three as one small PR and EM1 as its own, since EM1 touches the shared library and should be reviewed alone", where "the first three" were EM2 (handoff step fusion), EM6 (follow-up issues by default), and EM9 (one-site fixes under review comments).

## Approach

The handoff skill keeps `marker.sh activate handoff` as its routine first step and now runs it as its own Bash call. Its directory-creation recipe moves to just before drafting, so the two one-line recipes no longer sit side by side. A deferral at code-review's DEFER criterion 2, or at respond-pr's `OUT-OF-SCOPE`/`DEFERRED`, is satisfied by a documented limit by default, and a ticket is filed only on request. respond-pr's `FIXED` replies gain a required `other-sites` field, and step 6's `code-writer` dispatch applies each fix wherever else in the PR's changed files the reviewer's point holds.

Line numbers throughout are pre-edit locators. Apply each edit by its anchor text, or bottom-up within a file.

**Threat model.** The surface is every stow consumer's cooperative agent running respond-pr in that consumer's repo. The engineer settled that a hostile commenter is out of scope (Row 51), so a review finding whose premise is a steered commenter is out of scope for this PR's respond-pr text. Calling the prose "scope discipline for a cooperative agent" is this plan's framing, not the engineer's words. What reviews a sweep's edit, including one to a hook, gate or permission file, is not the sweep boundary. Every step-6 edit lands unstaged, and the parent commits it in step 8. That commit passes the content-keyed code-review gate, and a push to an open PR passes `/ready-for-review` [verified: ciso-reviewer trace of `code-writer.md:21-22`, `require-code-review.sh`, `require-ready-for-review.sh`].

**EM2: separate the pre-write recipes.** Row 10 blames the fusion on two adjacent one-line fences. Alternatives set aside:

- **A start script that runs both commands.** It needs a new script and a settings allow entry for a fusion that costs one retried call.
- **Widen the marker-shape gate.** Declined; see Out of scope.

**EM9: the sibling sweep.** A required field is respond-pr's own forcing mechanism, and it shows the reviewer whether the sweep ran (Rows 23-25). The field takes `file:line` entries, `none changed — swept the files the PR changes`, or `not swept — <reason>` when step 6 had no changed-files list. The fixed `none` wording tells a reviewer who has not read the skill how far the sweep reached. Step 5 states the reviewer's point as one general sentence, which gives the sweep a defined reach (Row 41). The sweep covers the PR's changed files: the parent lists them with `gh pr diff --name-only` and passes the list to `code-writer` in the prompt. When that command fails or lists nothing, no sweep runs, and the cited-site fixes still do. There is no whole-repo search and no `found, not changed` field. The comment's own cited-site fix is unbounded, as on main (Row 24). The reason for the bound: EM9's observed failure was re-raises inside one file the PR changed [verified: every inline review comment in this repo's PR #1259 anchors to `claude-skills/skills/review-pr/SKILL.md`, per a local export of that PR's review threads]. That is one PR. A top-level or issue-level comment that cites an unchanged file is the case this evidence does not cover; its cited-site fix still runs, and its siblings in unchanged files are not swept.

Alternatives set aside:
- **A whole-repo sibling search that lists out-of-PR siblings as `found, not changed`.** Row 50 cut it: the changed-files sweep covers the observed failure. An out-of-PR sibling is then neither searched for nor surfaced, an accepted cost.
- **Surface out-of-PR siblings to the engineer only, not in the public reply.** It keeps a search outside the PR's changed files, the reach Row 50 cut.
- **Rely on the global rule "Audit structural siblings before scoping a fix narrowly" alone.** That rule was already in force when the one-site failure happened (Row 23).
- **Add a step-6 sentence with no field.** Nothing in the reply would expose a skipped sweep.
- **Sweep in step 4's holistic triage.** Triage works across comments, but sibling sites carry no comment.
